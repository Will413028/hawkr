| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-11-19 至 2026-11-21（Will 決定） |
| 影響範圍 | 單體 `review`、`im`、`crm`、`moderation`、`seller` 模組；website、admin、buyer-app、seller-app 的評價、聊天、CRM 與檢舉畫面 |

## 脈絡

review-service、im-service、crm-service 的舊行為有多處是缺陷或沒有人決定過的取捨（封鎖沒有效果、賣家看得到買家電話與 Email、刪帳不處理評價、presence 無授權等，盤點 RD／ID／CD）。搬遷時每個行為都要決定「照搬或改」，這份收其中屬於產品與資料政策的部分。聊天通道在 `2026-11-22-im-realtime-delivery-connect-streaming.md`，停用身分的守門在 `2026-11-22-deactivated-identity-guard-at-owner.md`。

- 外部：個資法與刪帳期待：評價文字可能含個資；刪帳申請期間買家仍有開啟中的訂單要處理。
- 繼承：Java ordering、product 仍在舊系統，只消費 review 事件、發布訂單與退款事件；舊服務在 gateway 後面服務到 A6-6e，仍成立，因此模組不能提早取代它的讀寫（並行期單一生效者）。
- 繼承：封鎖放在發起者的模組，讀寫都帶觀看者，不影響計數（A7 封鎖語意）；沿用理由：它是 A7 已定案的社群封鎖語意，評價與聊天用同一條規則才不會出現兩套封鎖。
- 繼承：社群內容處分走 seller 措施，店家處分要有申覆（A7-D5′）；仍成立，是產品決定。
- 繼承：系統從未上線，沒有相容性約束，舊資料不搬（根目錄 `AGENTS.md`）。

## 決定

| # | 決定 | 否決的方案與理由 |
|---|---|---|
| D1 | 有進行中訂單或未結案售後時，封鎖不擋聊天，雙向一致（A6-D1）。「進行中」是雙方間訂單狀態 10–40，以現有 RPC 組出、不改 Java（A6-D14 W1 (c)）；停權賣家的例外用同一定義，不存綁定欄位（W2）。基準：Shopee、eBay 封鎖不中斷進行中交易的溝通，糾紛走客服（`decision-brief.md`） | 封鎖一律擋所有聊天：履約溝通被切斷。只擋新對話：同樣擋住進行中的訂單。新增 Java RPC 精確判定：違反舊服務只做維持運作的修改，且 B8 就刪；(c) 錯的方向是多擋，不是放行。照舊 `NOT IN (0,80)` 且永久放行：曾成交一筆封鎖就永遠失效 |
| D2 | 店家等待刪除時仍可聊，只有關閉才擋（A6-D14 W3）；買家的訊息抹除等 `BuyerDeleted`，等待刪除期間仍可為開啟中的訂單聯絡店家（W4 (ii)）；店家可主動開啟對話（W5，照舊） | 等待刪除算停業：店家正在出貨，買家要能聯絡，且與 seller 能力表一致。申請刪帳就抹除並禁止送訊息：聊天是處理開啟中訂單的管道，與公開內容不同。只讓買家開啟對話：產品收緊，seller-app 選擇對象畫面要改，未取得同意 |
| D3 | CRM「黑名單」刪除，封鎖只在 seller 的店家封鎖名單（A6-D2 (i)）；客戶列表拿掉關鍵字搜尋，賣家以分類、標籤、排序找人（A6-D18 W5 (a)）；兩項 UI 改動 Will 已同意 | 保留標籤：它沒有任何阻擋效果。改名「封鎖名單」並讀 seller：一個功能兩個入口，且多一條 crm→seller 依賴。搜尋改 buyer 加暱稱前綴 API：多一個查詢面與結果集上限，換回一個被刪掉電話快取的功能 |
| D4 | 觀看者封鎖了作者（買家對買家）或店家，就看不到該評價；店家封鎖買家不影響公開顯示；評分統計一律不過濾（A6-D4）；過濾在 SQL 述詞內、keyset 之前 | 店家封鎖買家就隱藏評價：評價是公共資訊。統計也過濾：與 A7「封鎖不影響計數」衝突。只過濾商品列表且在分頁後（舊行為，RD1）：分頁錯位 |
| D5 | 買家刪帳時刪除其評價並重算評分，不保留匿名（A6-D6）。基準：Amazon、Google 地圖刪帳時刪除評價（`decision-brief.md`） | 保留內容、作者顯示已刪除用戶：評價文字可能含個資。保留文字、刪圖片：兩種處理規則並存。多數市集保留匿名化評分，本專案選刪除，因為刪帳等於刪除本人產生的內容，最符合當事人期待 |
| D6 | 先評價、後全額退款的評價仍計入評分，延後到 ordering 搬遷（A6-D7 (a)）。退款後的訂單本來就不能評（只放行狀態 50） | review 在本階段消費 `aftersales.refund.completed`，已有評價不計分：約多半個 session，且缺口只剩這一種情況；觸發條件是 ordering 搬遷 |
| D7 | 賣家 CRM 只顯示暱稱與訂單統計，不回電話與 Email（A6-D8）；不回優惠券數、不建 coupon legacy client（A6-D18 W3）；標籤上限每店 200、每客戶 20（W4）；刪 `lookup`，優惠券選買家改從客戶名單挑（A6-D23 W5）；CRM 不暴露訂單，改用店家訂單列表加 `buyer_id` 篩選（W6） | 有訂單關係就給電話：賣家可探測任何買家個資（CD8）。`lookup` 改成以電話精確比對只回暱稱：電話仍是查詢鍵，可列舉探測。CRM 代為暴露訂單：訂單屬 ordering，由它的擁有者提供。標籤不設上限：`ListTags` 不分頁，需要有界 |
| D8 | 刪帳由 review、im 訂閱 buyer、seller 的刪除事件，同 transaction 只寫刪帳者複本與排清除 job，accountdeletion 不認識它們（A6-D9）；crm 同理，刪除該買家的分類、標籤、統計與 ledger，以 `inactive_parties` 擋舊事件重放（A6-D18 W2 (b)） | accountdeletion 直接呼叫各模組：它要認識每個上層模組，依賴表隨之增加。crm 不訂閱、資料保留：標籤是對可識別個人的主觀註記，刪帳應清除。只刪標籤、統計保留：兩種保留規則並存 |
| D9 | 店家評分統計的讀取與 CRM 的 VIP 查詢留在舊服務，到 A6-6e 與刪路由同一個變更才換成模組並刪 legacy client（A6-D11、A6-D18 W1） | 在模組完成時就換：寫入還在舊服務，模組讀到空表，評分與 VIP 顯示全錯，違反並行期單一生效者 |
| D10 | moderation 新增 `ReverseHide`：案件維持結案，另記還原欄位與稽核，同 transaction 呼叫擁有模組的 `Restore`（A6-D21 W1）。基準：撤銷記在原決定旁（DSA 第 20 條申訴後撤銷，`step-4-design.md` W1） | 只在 review、im 開還原 RPC：案件不知道處分被撤。本步不做入口：「檢舉→隱藏→還原」無法驗收；A7 刻意不做 `RestorePost`，這裡因要驗收而補上 |
| D11 | 店家寫的聊天訊息與評價回覆走 seller 內容下架，新增 `CHAT_MESSAGE`、`REVIEW_REPLY` 對象，im、review 讀取 join `seller.pub_content_takedowns()`（A6-D21 W2）。基準：市集把賣家違規訊息算進帳號健康與申覆（Amazon Account Health、蝦皮罰分） | 店家作者只能判無違規：買家被店家訊息騷擾沒有處置。直接 `im.Hide`：違反 A7-D5′，店家處分沒有申覆 |
| D12 | 檢舉人二選一：買家或店家，只有 `CHAT_MESSAGE` 接受店家檢舉（A6-D21 W3）；店家身分由訊息歸屬推導，`SubmitReport` 不加欄位（A6-D23 W2）；`GetCase` 帶依種類分開的快照，後台只看被檢舉訊息前後各 5 則的固定快照（A6-D21 W4、A6-D3） | 店家檢舉走 seller 通報：同一則訊息的兩方檢舉落在兩個系統。不開放：買家騷擾店家沒有路徑。`GetCase` 不帶快照：管理員只能回頭讀整段對話，正是要禁止的。加 `store_id` 欄位：多一個「只收某種類」的特例 |
| D13 | 店家退場時，同 transaction 清該店以店家檢舉人身分送出的說明、冪等紀錄與每日計數列，檢舉列與檢舉人鍵保留（A6-D22） | 不清：說明文字與冪等紀錄留著店家的內容，與買家刪帳的處理不一致 |

## 後果

- 接受：被刪的 CRM 搜尋與電話查找、聊天卡片與打字中使用者看得到的功能縮減；先評後退款的評分偏差到 ordering 搬遷。
- 接受：D1 的 (c) 在「較新訂單已結案、較舊訂單還在配送」時多擋，仍可走訂單頁與客服；B8 換成精確的 in-process 查詢。
- 接受：聊天前後文含檢舉人自己的訊息，保留到上線前隱私審查（`step-4-design.md` F4）。
- 重新評估：D9 在 A6-6e 之後不再適用；D6 在 ordering 搬遷；D3 若賣家要在客戶列表看到封鎖標記，才加 crm→seller 依賴；D1 若上線後量到被濫用，改精確判定。
