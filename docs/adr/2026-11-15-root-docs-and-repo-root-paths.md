# 跨專案文件放根目錄 `docs/`，文件裡的路徑一律從 repo 根目錄起算

| 項目 | 值 |
|---|---|
| 狀態 | accepted（Will，2026-11-15） |
| 日期 | 2026-11-15 |
| 影響範圍 | 全部 ADR、四份跨專案規範（`API 設計規範（Connect）`、`使用者面用語術語表`、`Git 分支與交付路徑規範`、`設計文件治理規範`）、跨專案計畫的位置；所有文件與程式註解裡指向文件的路徑寫法；repo-hygiene 的路徑檢查 |
| 相關 | 執行步驟在 `backend/docs/plans/2026-11-05-root-docs.md`（D1–D8）；完成的計畫分流後刪除（同計畫 D9） |

## 脈絡

`backend/docs` 是公司時期多 repo 的 backend repo 自帶的文件，併成 monorepo 時整包帶進來，位置沒有重新決定過。ADR 與四份規範的影響範圍早已跨到 website、admin、兩支 App 與 `packages/`，backend 以外引用 `backend/docs` 69 處（2026-11-15 量測）。backend 內的檔用「相對 backend」的 `docs/…` 寫法，共 1,547 處、696 檔。

約束：
- 繼承：程式在 `backend/` 目錄執行時讀的路徑字串不能改（工具的實際執行路徑）；仍成立，只改註解與文件。
- 繼承：ADR 寫下就不改結論（`設計文件治理規範.md` §4）；仍成立，搬家只改位置、路徑與表頭中繼資料。
- 不再成立而拿掉：「進行中的 `payment-onboarding` 分支會大面積衝突」。PR #284 已在 2026-11-14 合併。
- 系統從未上線，沒有相容性約束（根 `AGENTS.md`）。

## 決定

1. **全部 ADR 搬到根目錄 `docs/adr/`，維持單一份決策紀錄**（D1）。ADR 已有「影響範圍」欄，不再依子專案分兩處。
2. **四份跨專案規範放 `docs/共通規範/`**（D4），只有後端用的規範留在 `backend/docs/開發規範/`。
3. **新開的跨專案計畫放 `docs/plans/`，backend 專屬的留 `backend/docs/plans/`**（D5）。
4. **文件與註解裡的路徑一律從 repo 根目錄起算**（D8）：`docs/adr/…`、`backend/docs/modules/…`；markdown 連結用 `/` 開頭。終點是只有一種解析規則。
   - 過渡：將隨遷移刪除的檔（`backend/services/`、`backend/gateway/`、`backend/pkg/`、`backend/docs/詳細設計書/`）保留相對 backend 的舊寫法，列在 `docs/README.md` 的「遺留基準」清單並排除在檢查外；隨這些檔刪除，清單歸零。
5. **搬過去的 ADR 正文裡既有的相對 backend 路徑不改寫**（D2），在表頭加一列「路徑基準｜`backend/`」。新 ADR 一律從 repo 根目錄起算。
6. **歷史計畫與舊設計書裡指向搬走檔案的路徑字串照第 4 條改，內容不動**（D3）。
7. **路徑檢查只管搬家相關的前綴**（`docs/adr/`、`docs/共通規範/`、`docs/plans/`），從第一天零容忍，前綴寫成清單以便之後擴大（D7）。
8. **舊 gateway 的本機 `/docs` 檢視器不再顯示 ADR**（D6）。

## 考慮過的方案

「基準」是同樣條件下、假設還沒有程式碼時的業界做法；標「推測」的是沒有核到官方出處。

- **路徑寫法**：
  - **基準：從 repo 根目錄起算。** Bazel 的 `//pkg` 標籤、Go 的 import path 都只有一個基準〔量測：兩者的語法〕；GitHub 把 markdown 裡 `/` 開頭的相對連結解析成 repo 根目錄〔推測，開工時在 GitHub 頁面確認〕。
  - 未採「相對所在子專案，靠根目錄與 `backend/docs` 的第一層目錄名不重複消歧義」：同一個前綴依檔案位置指向兩處，檢查與讀者都要多記一條規則，而且永遠要守住「目錄名不重複」這個額外約束。它原本的主要優點是避開與進行中分支的衝突，這個優點已不存在。
- **ADR 位置**：未採「只搬影響範圍含後端以外的」：113 份要逐份分類，之後每份新 ADR 都要先判斷放哪，ADR 互相引用還會跨兩個目錄。
- **ADR 裡的舊路徑**：未採「全部改成從根目錄起算」（470 處、83 份）：不少路徑指向已刪除的舊服務，無法用「檔案存在」驗證改寫是否正確。
- **歷史引用**：未採「不改，放舊路徑對照表」：歷史紀錄的連結會打不開，檢查也得為它們開例外。
- **規範目錄名**：未採 `docs/開發規範/`：與 `backend/docs/開發規範/` 同名，搜尋與口頭指稱容易混淆。

## 後果

- 改寫量：還會留下的檔裡相對 backend 的 `docs/…` 寫法約 620 處要改成 `backend/docs/…`（1,547 處扣掉排定刪除的檔約 927 處，2026-11-15 量測）。
- 「過渡基準」清單（Will，2026-11-15）：根目錄 `docs/` 建好之前，清單內的 `backend/` 檔解析不到時退回以 `backend/` 為基準；終點是清空並刪除退回邏輯，觸發：計畫步驟 4c 完成。
- 「遺留基準」清單是暫時例外，終點是清空；觸發：遷移計畫刪除各舊服務與舊設計書。
- 可逆性：中。改回相對寫法要再改同樣數量的引用。

## 推翻條件

- GitHub 不把 `/` 開頭的連結解析成 repo 根目錄：markdown 連結改用相對路徑，路徑字串的規則不變。
- 出現必須讓同一份文件同時給多個 repo 使用的需求（例如拆 repo）：重新評估根目錄起算的寫法。
