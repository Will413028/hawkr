# 元件庫怎麼維護

這裡是買家 App、賣家 App 與主網站含賣家中心的共用審查入口。**產品外觀與行為以正式 runtime tokens 和元件來源為準；Storybook 展示現況、使用方式與待收斂差異。** 元件庫更新不會自動發布網站或手機 App。

[三端對照](?path=/story/cross-platform-comparison--overview) · [買家 Dart API](?path=/docs/apps-buyer-api--docs) · [賣家 Dart API](?path=/docs/apps-seller-api--docs)

## 選元件與修改方式

1. 先在目錄找現有元件，用 MCP `docs-list`／`docs-show` 看實際 props。Web 從正式 `@/components/...` 匯入；Flutter 使用各自 Dart API 文件。
2. 改正式元件時一起更新 stories，至少補齊適用的載入、停用、錯誤、空狀態、選取、focus 與長中文案例。
3. 修改 App API 時，更新該 App 的 `docs/component-library.md`；Buyer API／Seller API 頁面在 build 時直接讀入它。
4. 改共同 token 時同步三端來源與 `cross-platform-tokens.json`。六項既有差異仍在 exceptions 中，不能因相近就當成一致。
5. 把改動範圍、版本影響、已知限制與驗證結果放進同一個 PR。

## 視覺基線

新舊畫面要固定 Story ID、args、來源、viewport、theme、文字倍率、locale、字型與瀏覽器版本。至少比較窄版、長中文、大字級，以及平台實際支援的主題。

有意改版先說明差異，由設計系統負責角色審查後再更新基線。**核可基線是在確認設計意圖；測試通過是在確認實作符合該基線。** 不可批次接受所有差異來消除測試失敗。

目前互動／a11y／widget tests 和人工截圖，不等於完整自動像素回歸系統。自動 snapshot pipeline 建好前，每次有意改版需保存人工比較與審查紀錄。

## 工具與平台

兩 App 的 `.fvmrc` 固定 Flutter 3.47.7，catalog 使用 Web JavaScript build；升級 Flutter、renderer 或改用 Wasm 應另開可審查的工具鏈變更。保留各自的 lockfile。

小螢幕至少覆蓋 320／390／768px 與 1.4 倍字級；不得為了畫面一致而關閉使用者文字縮放。原生 safe area、鍵盤、輸入法與字型 fallback 要在受影響平台驗證。

## 開發檢查入口

```sh
pnpm storybook:mcp test-run
pnpm storybook:typecheck
pnpm design:check --apps-root ..
```

在各 App 目錄執行 `bash scripts/component-catalog.sh test`，再跑受影響的既有 widget tests 與 analyze。完整元件庫建置使用 `pnpm storybook:build:all`。
