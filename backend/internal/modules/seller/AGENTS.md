# seller 模組

店家業務身分與店家 profile 的擁有者：申請開店、profile、logo 與封面、商家名單（站外業者的 BD 名單）、商品瀏覽數、措施（警告、停權與終止合作，依據是認定、風險類型或契約條款）與停權狀態的檢查、商家治理（通報、認定、措施、申訴）、關店，以及刪除帳號時的店家參與者。來源是 seller-service（遷移計畫 A3b 步驟 7a 核心、7b 治理）；7c 階段 1 加入 KYC 認證與處分的身分比對，階段 2 加入 PayUni 子商店的綁定、同步與審核狀態；階段 3 加入關店後的未結訂單檢查與關店後的清理（現行：30 天退場、6 個月清個資）；階段 4 加入商家名單與商品瀏覽數。入口與舊服務仍走 seller-service，切換在步驟 9。

## 職責

- 申請開店（設計書 44）：驗證全部輸入、建立 stint、寫入 profile、授予 SELLER 在同一個 transaction。
- 入駐同意（ADR `2026-10-19-seller-kyc-payuni-consolidated`「入駐同意紀錄」）：現行版本與網址（站內路徑，對外由 `internal/httpapi` 以 `PUBLIC_WEB_ORIGIN` 組成絕對網址，PayUni 的本來就是絕對網址）只在 `internal/model/agreement_gen.go` 的 `CurrentAgreements`，它由 `website/scripts/generate-legal.ts` 從 `website/docs/legal/` 的正本與 manifest 產生，不得手改；改版是改正本（版本行）或 manifest 後在 `website` 跑 `pnpm gen:legal`。同意的紀錄與開店、送出 KYC 的寫入在同一個 transaction，每次同意事件一列（KYC 的列綁定那次送出的審核紀錄，食品業者登錄的告知列綁定那次送出的登錄，各自由資料表的 CHECK 把關）；關店 184 天的第二段清理（`StoreRetention`，連線紀錄）把來源 IP 與 User-Agent 清成 NULL，其餘保留。
- 店家 profile、logo、封面的讀寫，所有寫入者以版本做樂觀鎖。
- 店家封鎖（`store_blocks`，遷移計畫 A7-1b）：店家封鎖一位買家，主鍵 (store_id, buyer_id)，buyer_id 不建外鍵，買家刪帳時 accountdeletion 在同一個刪帳 transaction 呼叫 `ClearBlocksAgainstBuyer` 刪掉以他為對象的列（在買家的刪除事件派發之前）。單向：只擋買家在這家店的新互動（檢查在 social），不擋下單。`BlockBuyer`／`UnblockBuyer` 冪等，回「有沒有改變」；模組 API 不做能力檢查（封鎖是保護動作，停權時仍要能封鎖與解除），誰能代表店家操作由 httpapi 的 `ActingStore` 決定。`ListBlockedBuyers`（keyset）、`StoreBlocksBuyer`、`StoresBlockingBuyer`（批次，給列表每列的 `viewer_can_comment`）。不發布 `seller.pub_blocks`：封鎖不篩選讀取，檢查是依 ID 的查詢。`TestStoreBlockAndUnblockAreIdempotent`、`TestStoreBlocksAreDirectedAndBatchedPerBuyer`、`TestListBlockedBuyersPaginatesNewestFirst`、`TestClearBlocksAgainstBuyerDeletesOnlyThatBuyersRows` 驗證。
  - `BlockBuyer` 不鎖也不查對象買家（seller 不依賴 buyer，`internal/arch/modules.go` 擋，模組內無法檢查）：與買家刪帳並發時可能留下指向已關閉買家的列，也收得進不存在的 buyer_id；這是接受的現況，因為對已關閉買家沒有效果，對象是否存在由 A7-2 的 handler 從留言參照或買家 API 解析時把關。封鎖名單裡的已關閉買家由 A7-2 的 handler 組裝名單時顯示成已刪除，模組不提供這個行為。出現 seller 依賴 buyer 的理由，或名單顯示出現問題時重新評估。
- 措施與停權（ADR `2026-10-18-seller-governance-consolidated`「決策」的「認定、措施與效果」「申訴、補正與凍結」、設計書 32）：措施是效果的唯一來源，種類是警告、停權或終止合作（條款第 21 條），依據是違規認定（`violations`，只是認定）、風險類型（RISK，條款第 17 條）或契約條款（CONTRACT，只配終止合作）；停權狀態在讀取時推導（以帳號為單位，不存），停權期間與事件、到期與對帳由 `Recompute` 與 job 維護。管理員不再有獨立的停權與解除，也沒有直接關店：停權就是建立一個停權措施，解除就是結束（RISK）、撤銷、接受申訴或接受補正；平台關店就是建立終止合作，關店與恢復由措施驅動。
- 商家治理（ADR `2026-10-18-seller-governance-consolidated`「決策」的「通報與案件」、設計書 32）：通報（一位檢舉人的一次送出，登入的買家或匿名者；檢舉與食安同一張表）與案件（同一家店、同一個平台判定類別同時最多一個進行中，決定即結案）分開：通報有自己的結果，由 admin 分案、設定結果或移到其他案件，同一位檢舉人再次送出併成補充；嚴重度、決定、內部註記與 FDA 轉報在案件；認定（升級規則以帳號計）、措施（建立、改理由與結束時間、結束、撤銷與連帶撤銷、複審期限、內部註記）與申訴；佐證圖片的 media 引用；匿名聯絡欄位的保留期限清理。
- 店家能力的推導（`model.CapabilitiesOf(store)`：每個能力的狀態與缺的條件，含店家狀態 `PUBLIC_LISTING`；能力名稱沿用 ADR `2026-09-18-seller-capability-authorization` 及其 2026-10-08 修訂）與檢查（`ActingStore`，ADR `2026-09-29-seller-suspension-and-business-identity-in-monolith`）。
- 關店（賣家自己關店；店家有未結訂單時拒絕）、終止合作生效後由系統關店與撤銷時恢復營業（`internal/closing`）、`accountdeletion` 的參與者動作（進入等待刪除、關閉）；關店可逆，圖片的釋放與不可逆的下游動作（`StoreRetired`）都在關店 30 天後的退場（第一段清理）；每次關店記下為什麼關的（賣家自己、終止合作連同造成關店的措施、隨帳號刪除）。
- 後台的店家讀寫（遷移計畫 A3b 步驟 8e）：目前店家的清單（店名、電話或 `store_code` 搜尋，依 KYC 申請狀態或「待審核」篩選，keyset）與統計、以店家讀 KYC 申請（`StoreKYC`）；停權與關店由措施的建立、結束與撤銷產生（後台沒有直接關店的方法）。
- 後台的 KYC 審核與 PayUni（遷移計畫 A3b 步驟 8f；`SellerAdminService`）：審核佇列 `AdminKYCApplications`（只列送出過的申請；篩選審核中依送出時間舊到新，其他與沒有篩選新到舊；`Query` 搜姓名、公司名稱與統編；keyset `KYCCursor{SubmittedAt, ApplicationID}`）、單筆檢視 `AdminKYCApplication`（遮蔽值、審核紀錄、銀行帳號命中的標記；顯示全文與證件讀取的稽核各自分頁：`ListKYCReveals`、`ListKYCDocumentAccesses`，新到舊的 keyset，申請不存在回 NotFound）、`ApproveKYC`／`RejectKYC`（etag；理由與 comment 共用 `platform/auditreason`；回傳的後台檢視在同一個 transaction 內讀）、`RevealKYCSensitive`（顯示全文，同時是 15 分鐘的證件授權）、`ReadKYCDocument`（以授權讀證件圖片）、`PayUniRegistrationOf`、`RebindPayUni`、`PayUniObservations`（keyset）、`RefreshPayUniStatus`。
- 關店後的兩段清理（ADR `2026-10-19-seller-kyc-payuni-consolidated`「關店與個資保留」與 2026-10-20 修訂，`internal/purge`）：**第一段（退場）**：stint 關閉之後過了 `model.StoreRetireAfter`（720 小時，30 天；因終止合作而關閉的到帳號上未撤銷終止中最晚的申覆期限，且不早於這 30 天），清公開內容（說明、獎項、網站），logo 與封面在這時才釋放，發 `StoreRetired`（relay 轉成 `seller.deleted`，下游刪除商品、貼文、聊天的個資等），記下 `stores.retired_at`；待審的食品業者登錄撤回、仍核准中的結束（`STORE_RETIRED`）；退場之後不能恢復營業。**第二段（個資清理）**：已退場、關閉之後過了 `model.StoreRetention`（4416 小時，184 天，詐欺犯罪危害防制條例第 37 條第 1 項的六個月；終止合作的式子同上），註冊、身分與連線資料一併清成 NULL：店名、店家聯絡（電話、聯絡人姓名與手機、客服信箱）與地址、KYC 個人欄位與證件、登記資料查詢、PayUni 的自由文字、食品登錄的字號與理由、同意紀錄的 IP 與 User-Agent，記下 `pii_purged_at`；審核事實、PayUni 狀態碼與措施的身分快照保留。兩段的時間條件只有 `RetireDueStores` 一支（`second_stage` 選段，時數由 `StoreRetireAfterHours`／`StoreRetentionHours`、`AppealWindowHours` 傳入），保存條件只有 `StoreHolds` 一支：`appeal_hold`（帳號上未撤銷的終止，或未撤銷的關聯終止的來源措施，有待處理申覆）擋兩段，也讓恢復營業（`closing.ReopenPlan`：第一段的時間條件成立而且沒有 `appeal_hold` 就是「保留期已過」）不恢復；`preservation_hold`（帳號上有沒撤銷登記、`hold_until` 晚於現在的主管機關來函指名，不指定店家或就是這家店）擋兩段與食品登錄審核紀錄的 2 年刪除，不影響恢復營業。每一批：時間條件選候選並鎖住（keyset，`FOR UPDATE SKIP LOCKED`）→ 鎖住之後以同一支查詢再判斷時間、再問 `StoreHolds` → 只處理仍然成立而且沒有被保存的（審核紀錄的刪除時間條件單調，只問保存）。
- KYC 認證（ADR `2026-10-19-seller-kyc-payuni-consolidated`）：賣家填寫草稿、送出與取消，管理員審核（核准、退回、顯示全文與限時的證件圖片授權）；身分證號、負責人身分證號、銀行帳號加密保存，另以 blind index 做身分比對：別的帳號有生效中停權措施的身分證號或統編不能通過認證，銀行帳號命中只標記。證件圖片的 media 引用。
- 公司型申請的登記資料快照（同一份 ADR「登記資料快照」，遷移計畫 A3b 步驟 10a 第 4 刀）：送件（`kyc_applications.submission_seq` 每次轉成 SUBMITTED 加一，退回後重送是新的一輪）時在同一個 transaction 新增一列 PENDING 的 `kyc_registration_checks`（綁定這一輪的 `submission_seq`）並排入 `seller.kyc_registry_check`（`internal/kyc`；以 `check_id` 為 River 唯一鍵，狀態集合不含 completed、discarded；寫入的冪等仍由條件寫入保證）。job 在 transaction 內認領（申請不是這一輪審核中、同一輪已有更新的查詢，或已不是公司型就寫 `CANCELLED` 結束）、transaction 外呼叫 `Registry` port（`platform/gcis` 的 client 直接是它的實作，回來源的原始資料；轉成模組型別、現況分類、停業期間的合理性與地址拆分只有 `model.NewRegistration` 一處，互動的 `LookupBusinessRegistration` 與快照共用），再用另一個 transaction 寫入結果（只在仍是 PENDING 時；最後一次嘗試的任何失敗都記 `UNAVAILABLE`，不留 PENDING）。查詢是有期限的資源（2b 設計簡報題 1 (b′)）：建立時寫入 `deadline_at`（`requested_at` 加 15 分鐘，後台的 `deadline_time` 讀它），伺服器保證在期限前到終態。PENDING 的出口：寫入結果、認領時放棄、後台重新查詢取代、job 執行時已過期限直接記 `UNAVAILABLE`（不再呼叫資料來源）、掃描 job `seller.kyc_registry_sweep`（每 1 分鐘：`deadline_at` 不晚於現在加一個掃描間隔的 PENDING 收成 `UNAVAILABLE`／`CANCELLED`，閒置超過 3 分鐘的補排 job）；`RequeryKYCRegistration`（只在 SUBMITTED）把這一輪的 PENDING 全部收成 `CANCELLED` 再新增一筆並回傳它（帶期限）。FOUND 時存登記資料與現況並逐欄比對（名稱、設立日期、地址；組織型態在快照裡，申請人不填，不比對）：不一致與無法比對只記錄，不改申請狀態。後台顯示申請目前這一輪 seq 最大的已完成查詢（這一輪還沒有就沒有快照），「查詢中」只在 SUBMITTED 時計算；後台 etag 是申請版本加顯示的查詢序號，核准與退回把顯示的查詢記進審核紀錄。個資清理一併刪除查詢列。
- PayUni 子商店（同一份 ADR「核准與綁定」「PayUni webhook」）：核准時在同一個 transaction 寫入綁定意圖並排入以 `store_id` 為唯一鍵的 job，job 在 transaction 外向 PayUni 綁定（MerID 已存在時查詢認領）與同步店家的聯絡資料、地址；管理員重新綁定失敗的註冊（在 `kyc_reviews` 留下 `REBIND` 紀錄：誰（管理員 ID）、何時、哪一份申請，`TestAdminRebindIsRecorded`；回傳的註冊與一般讀取一致，帶賣家型態）；PayUni 的審核狀態（webhook、輪詢、手動刷新、綁定認領）先追加成觀測再套用，cert 軸與 PayUni 軸合成流程狀態。賣家看到的 PayUni 狀態在 `KYCFlow.payuni`（`PayUniState`、說明句、審核意見、能修正的欄位），由 `model.SellerPayUniOf` 推導（階段只經 `PayUniPhaseOf`）；流程、PayUni 狀態與不能重送的原因出自 `payuni.SellerViewOf` 的同一次註冊載入（帶賣家型態與店家缺的欄位），`DeriveKYCFlow` 的 `CanResubmit` 與 `SellerPayUniOf` 吃同一份、呼叫同一個 `sellerPayUniOf`，`KYCFlow` 不帶 PayUni 的事實（它們在 `PayUniRegistration`）；`KYCFlow.can_resubmit` 是 `SaveKYCDraft` 與 `SubmitKYC` 此刻會被接受（PayUni 階段 ⇔ 推導結果是 FIXABLE），不能做的原因與句子只在 `model.ResubmitUnavailableReasons`，兩個 RPC 的 `failed_precondition` 與 `resubmit_unavailabilities` 同一個函式；沒有 `GetMyPayUni`。綁定重試用完（`PAYUNI_UNAVAILABLE`）進後台待辦 `review_payuni_bind_retry`（`bind_failed_at` 起算 24 小時）；重新綁定的可用性與方法同一個函式（`model.RebindUnavailableReasons`，見下一條）。
- admin 對店家的動作（遷移計畫 A3b 步驟 10e 第 5b 刀，`step10e-5b-design.md`；`model/store_action.go`）：建立警告、停權與風險措施（`CREATE_MEASURE`）、代行營運的店家狀態那一半（`DELEGATE`，由 `CapStorefrontWrite` 缺的條件對應，delegation 讀同一個函式）、核准、退回、重新查詢商家認證（`APPROVE_KYC`、`REJECT_KYC`、`REQUERY_KYC`）、重新綁定 PayUni（`REBIND_PAYUNI`）、核准與退回食品業者登錄的前置條件，**只有一張有效組合表 `storeActionRules`**：每個動作是一串依先後排列的 `(原因, 條件, 種類)`，推導就是依序跑條件；`blocking` 的原因方法回 `failed_precondition`、訊息是第一個原因的句子（`ErrStoreActionUnavailable`），`idempotent` 的原因（只有 `PAYUNI_BIND_IN_PROGRESS`）方法不回錯誤、回目前的註冊，沒有句子；句子只有 `StoreActionUnavailableText(reason, action)`（`text/` 的 `staff` 段，沒有通用句：漏掉的組合是內部錯誤）。已關閉的店家對 admin 是存在的資源：不是 `not_found`，是 `failed_precondition`（`STORE_CLOSED`；建立終止的兩個擋下也是）；案件與通報建立措施被擋下的原因句與 `CreateMeasure` 同一句。**店家不是營運中（已關閉、等待刪除）或帳號停權時商家認證審核暫停**：核准、重新查詢不可用，申請維持 `SUBMITTED`，不在後台待辦、沒有審核期限；停權只擋核准、退回照舊可用（但件不在待辦）；恢復營業或停權結束時回到待辦，開始時間是送出、最近一次恢復營業（`store_closures.reopened_at`）、最近一次停權結束（`account_sanction_lifted_at`）三者最晚的時間，食品業者登錄的期限函式同樣取恢復營業。重新綁定的原因依序是 `PAYUNI_MERCHANT_TERMINAL`、`STORE_CLOSED`、`STORE_PENDING_DELETION`、`PAYUNI_BIND_IN_PROGRESS`（idempotent）、`PAYUNI_BOUND`、`KYC_NOT_APPROVED`（註冊所根據的申請不是已核准，例如賣家正在修改）。後台待辦 `PAYUNI_BIND_RETRY` 的成員是「重新綁定此刻可做」的子集（`TestBindRetryQueueIsASubsetOfRebindableStores`）。`GetStore`（`can_create_measure`）、`GetKYCApplication`、`GetPayUniRegistration`（`can_rebind`、`flow_status`＝`PayUniPhaseOf`）、食品業者登錄的讀取與清單的 `delegation_unavailabilities` 都帶原因；client 只呈現。`TestStoreActionTextIsTheApprovedCopy`、`TestDelegateReasonsAreTheMissingStorefrontWriteRequirements`、`TestKYCReviewPausesWhileTheStoreIsClosedAndResumesFromTheReopening`、`TestAwaitingReviewIsOneDefinitionAcrossTheQueueTheListAndTheStats`、`TestRebindReasonsAndErrorsAreTheSameFunction`。

## 發布的讀取介面（pub_*）

形狀宣告在 `db/pub.sql`（依賴表允許的上層模組的 sqlc 讀它，`internal/arch` 的 `TestSQLCReadsOnlyItsOwnSchemaAndAllowedPubContracts` 擋住讀內部表），定義在 `db/objects.sql` 與手寫的 migration，`cmd/hawkr` 的 `TestPubContractsMatchMigrations` 比對兩者（欄位、型別、參數與回傳，雙向；函式的寫法由 `TestSchemaFileMatchesMigrations` 檢查）。`pub.sql` 裡宣告成表的 `pub_exposable_store` 只是函式回傳列的形狀，消費端的 query 不得直接參照它，只能呼叫函式（同一個 arch 測試；pgx 手寫的 SQL 字串不在檢查範圍，現在單體的正式程式碼裡沒有 seller 表的手寫 SQL）。改 `pub_*` 的形狀等於改契約：同一次變更內更新 `pub.sql` 與所有消費端；底層欄位改型別或刪除時在同一份 migration 內 drop 再建。

- `seller.pub_exposable_stores(at timestamptz) RETURNS SETOF seller.pub_exposable_store (store_id bigint)`：`at` 這一刻可以公開曝光的店家，曝光規則唯一的家（ADR `2026-09-24-go-modular-monolith` 文末修訂的曝光規則段）。`at` 由呼叫方以請求的 clock 傳入，不用 `now()`；函式會被內聯（沒有 Function Scan），join 時每家店對 measures 的讀取是以帳號為鍵的索引探測。上層用法：`EXISTS (SELECT 1 FROM seller.pub_exposable_stores(sqlc.arg(now)::timestamptz) e WHERE e.store_id = p.store_id)`。`store_exposures`、`StoreExposureChanged` 與 15 分鐘對帳只為行程外的 legacy 消費者保留，B4 把 product 搬進單體後刪除。
- `seller.pub_review_items(at timestamptz) RETURNS SETOF seller.pub_review_item (kind, item_id, 對象的鍵, store_id, store_name, start_at, due_at)`：`at` 這一刻營運要處理的全部待辦（12 種，都有期限），是 12 支 `review_<種類>(at)` 的 `UNION ALL`，成員、開始與期限的規則只在那些函式（`step10e-3d-design.md` E10）。`reviewqueue` 模組讀它排序分頁（`due_at, start_at, kind, item_id` 的 keyset），沒有排序保證；`at` 由呼叫方傳入。`TestPubReviewItemsIsTheUnionOfTheReviewFunctions` 鎖住它等於逐支函式的集合。

- 根套件只保留 `Module`、`New`、`Migrations`、轉呼叫方法、對外型別別名（治理的在 `governance.go`）與事件（`events.go`）。

- 依賴圖的唯一來源是 `internal/arch/modules.go`（模組之間與模組內）。各子領域在自己的套件宣告最小的 `Deps` 與 identity 介面，由根套件逐欄組裝。

## 不變量

## 已知限制

- Java 仍以 BIGINT 存 `store_id` 與停權期間的 `period_id`（product 的停權快照以 `period_id` 為 scope），兩者暫用 IDENTITY；最後一個數字 ID 的消費者改寫時依 row-identity ADR 換 UUID（階段 C）。措施與請求的 ID 沒有 Java 的消費者，是 UUIDv7。
- 店家的未結訂單檢查（`Orders` port，見上面的不變量）有一個保留的時間窗：它在 transaction 外問 ordering 的現況，與之後鎖帳號、關店之間仍可能有新訂單成立（舊服務的訂單不在單體的鎖裡）；訂單搬進單體之後以 ordering 自己的判斷在同一個 transaction 內檢查（CARRYOVER「7c 審查後的結論」）。
- 新轉正的資產要在 media GC 的 7 天寬限內被同步 job Link（轉正之後、同步完成之前沒有引用）；job 失敗由 River 重試並記 error log。B1 把引用移進業務列的 transaction 後，同步 job 與退場表消失。
- 不在這次清理範圍：治理的通報、違規與停權紀錄（自由文字、處分原因）不在這次清理範圍，各有自己的保留規則（匿名檢舉人的聯絡欄位 `greatest(建立 + 90 天, 結果 + 30 天)`、其餘結論見上一則）；`kyc_reviews.reason` 與 `kyc_reveals.reason` 是審核員的文字、不含申請人的欄位值，保留。
- 清理不處理對未來處分的覆蓋：見 `CARRYOVER.md`「處分的身分快照與清理的關係」。
- 商家名單：公司時期的名單資料沒有搬（repo 沒有資料，上線前不受相容性約束）；邀請子系統整套不搬（沒有消費者，盤點 Q8），admin 的邀請面板在步驟 10 移除；`category`、`region` 的自由文字與分類樹 ID 並存（盤點 Q10，結構化需要整份名單重標）；ILIKE 搜尋是全表掃描，名單在數千列以內不是問題，成長之後再加索引；分類標註工具 `cmd/prospect-category-gen` 隨 A9 處理；分類由後台 `CreateProspect`、`UpdateProspect` 的 `category_ids` 寫入；共用平台的排除清單（`prospectSharedHosts`）只有匯入資料裡已知的 `linktr.ee` 與 `pinkoi.com`，新的共用平台出現時加進去。
- 商家名單的合併不搬圖片（引用依 `prospect_id` 登記，沒有搬移的操作）：輸家的圖片釋放，贏家沒有圖片時要重新上傳。
- 身分比對（`SubmitKYC`）是身分證號、統編存在與否的探測面（泛用錯誤不夠，攻擊面是重複送出），所以頻率限制在入口：`internal/httpapi/seller` 的宣告表給 `SubmitKYC` 每個帳號每小時 5 次的額度（`limitedTo`，在能力檢查通過之後、handler 之前計數）。計數在 serve 程序的記憶體內，多個 instance 各自計數；模組本身不限流，直接呼叫模組的程式（job、測試）不受它約束。
- 瀏覽數的匿名打點入口是 `SellerPublicService.RecordProductView`（步驟 8c）：只計訪客，有呼叫者時回成功但不寫入（登入買家由 `RecordVisit` 計，所以 website 在步驟 10 之前繼續對登入者送 beacon 也不會算兩次），每個來源 IP 每分鐘 120 次（`internal/httpapi/ratelimit.go` 的 `procedureTiers`，在這個程序的記憶體內計數）；website 的 beacon 只給未登入者在步驟 10（盤點 D11、D14）。商品層級的排行（設計書 45）屬後續：重用這張原始事件表、另加彙總維度，不改彙總表。
- 管理員的自由文字理由（措施的 `statement_to_seller` 與內部註記 `governance_notes`、後台刪帳號的 `request_attempts.reason`）是稽核文字，可能夾帶賣家的個資（結論：保留，個資清理不動它們）。重新評估：隱私政策定稿時，或 A8（notification 與資料保存期限）。
- 後台清單的店名與電話搜尋是全表掃描（上線前的資料量不是問題）；觸發條件在 `CARRYOVER.md` 的觸發條件表（店家超過 1 萬列或 p95 超過 200 ms 時加 pg_trgm GIN）。
- 證件圖片的讀取（`ReadDocument`）經 media 的 `ServerReadSecureAsset`，整份內容在記憶體（media 的 RPC 不串流），只適合證件大小的檔案；這個 RPC 要求 `secure/` 前綴的物件，所以轉正時要求 media 回報 `is_secure`（草稿存檔拒絕非機敏的證件），讀取時 media 回 400（不是機敏資產）是 `media.ErrNotSecure`，與找不到分開。終點：每次讀取都要記錄（Will 2026-10-04），簽章網址記不到讀取、R2 存的又是 media 加密過的密文，所以 B1 之後擁有者的端點仍然代理，只有 `media.Media.ReadSecure` 後面的 adapter 從 Java 的 gRPC 換成單體內的 media。沒有通用的 admin 機敏下載：證件影像只經這條端點。
- 證件讀取的 media 失敗分三種（`mediaref.ReadSecure`，佐證共用；`TestKYCDocumentReadFailuresAreDistinguished`）：引用的同步還沒結算（`media_ref_sync.synced_seq < seq`，新轉正的證件，job 最多落後一個週期）是 `ErrFileNotSynced`，端點回 503 加 `Retry-After`（warn）；同步過了、我們的資料庫有這張證件而 media 說沒有是 `ErrFileMissing`，不是機敏資產是 `media.ErrNotSecure`，兩者都是資料不一致，端點回 404 並記 error（要人處理）。三種都已經先寫了讀取紀錄。
- 佇列為什麼篩選審核中是舊到新：審核的服務水準以等待時間計，等最久的先看（SLA）；其他狀態與全部是回頭查紀錄，新的在前。兩支 query 的篩選條件必須一致，`TestAdminKYCQueueVariantsFilterIdentically` 驗證；KYC 佇列的 ILIKE 搜尋（姓名、公司名稱、統編）是全表掃描，觸發條件在 `CARRYOVER.md`。
- 本模組的事件由 `internal/legacy/sellerrelay`（`cmd/hawkr` 的 `subscribeSellerRelay`，serve、worker 與 `reannounce-exposures` 都訂閱）轉成 RabbitMQ 訊息給 Java 與晚搬的 Go：`seller.deleted`（由 `StoreRetired`，關店 30 天後的退場時；`StoreClosed` 與 `StoreReopened` 不轉送：關店可逆，曝光與停權的變化各有事件）、`seller.suspended`、`seller.unsuspended`、`seller.profile.changed`、可曝光變化的 `seller.exposure.changed`（Java 依它在讀取時隱藏不可曝光的店的商品，等待刪除也由它涵蓋；ADR `2026-10-05-store-exposure-to-legacy.md`）與 `merchant.verification.*`；不轉送的事件（`StoreOpened`、`StoreClosed`、`StoreReopened`、`StorePendingDeletion`、`KYCSubmitted`、`KYCApproved`、`KYCCancelled`、`PayUniBindFailed`）與原因在 sellerrelay 的套件說明。治理事件（`ReportReceived`、`ReportResolved`（每筆通報有了結果發一次：個別設定、案件結案帶入都算）、`MeasureCreated`、`MeasureRevised`、`MeasureEnded`、`MeasureRevoked`、`MeasureRequestSubmitted`、`MeasureRequestDecided`、`MeasureRequestClosed`）由 A8 的 notification 訂閱並保存送達紀錄；在那之前賣家、檢舉人與 admin 都以拉取的方式看到結果。
- 登入檢舉人的 `reporter_buyer_id` 不隨買家刪除清掉（結論：保留）：它是指向買家墓碑列的擬名鍵，買家的個資由 buyer 自己的刪除流程清除，seller 不依賴 buyer；清掉它會讓檢舉人無法查自己的檢舉、也讓去重失效。匿名通報與補充的描述是自由文字，可能含個資（結論：保留）：它們是通報的實質內容，FDA 轉報與後續調查需要它；保留期限的清理只動聯絡欄位。重新評估：隱私政策定稿時，或 A8（notification 與資料保存期限）時。
- 開店只鎖帳號列、不鎖舊 stint：開店與「延長舊 stint 上已到期的處分」併發時，新 stint 已經停權（能力在讀取時推導，即時正確），但停權期間與 `StoreSuspended` 要等每小時的對帳補上。只影響事件的時間，不影響權限；若下游需要即時，開店改成先 `LockAccountOf`。
- 入口、gateway 與舊服務都讀本模組，店家只有一份資料。SELLER 角色與現任店家成對（開店與授予、關店與移除各在同一個 transaction）：有 SELLER 卻沒有現任店家是不變量被破壞，`gatewayproxy` 回 500、`accountdeletion` 回 internal，不當成「沒有店家」。
- KYC 的身分比對只擋「同一個身分」：用別人的證件、人頭入駐不在防線內（ADR 後果）。處分建立之後才由被處分帳號新增的申請不在快照裡（被處分的帳號開不了新店，既有的申請核准要求帳號沒有停權，所以不會被核准）。核准與「另一個帳號的處分同時寫入」不需要額外的鎖：處分在核准讀取之後才 commit，結果等於「先核准、後處分」，是合法的序列順序，之後的核准都會看到快照。快照只能取到處分當下還沒清理的 KYC：舊 stint 關閉滿 184 天（第二段清理）、KYC 已清理之後才被處分時，舊 stint 用過的身分不在快照裡（目前 stint 的身分仍在）；這是「關店 184 天後清註冊與身分資料」的代價（ADR 的資料最小化），不另外保留 hash。
- KYC 金鑰（`KYC_ENCRYPTION_KEYS`、`KYC_HASH_KEYS`）必填；啟動檢查（serve 與 worker，`CheckKYCKeys`）：資料庫參照的每一把金鑰 ID（KYC 密文開頭、申請的 hash、處分身分快照）都要在金鑰環裡，缺了就不啟動（`TestStartupChecksThatEveryKeyReferencedByTheDatabaseIsConfigured`）。**第一次輪替任何 KYC 金鑰之前，要先有重算 hash 的 job**（申請的 blind index 與處分快照的 hash 以新金鑰重算，否則新的比對查不到舊金鑰寫入的列以外的新值；加密金鑰輪替則是解密後重寫）。快照沒有明文可以重算，用來算快照 hash 的舊 HMAC 金鑰要留在金鑰環直到對應的處分結束；輪替加密金鑰時以解密後重寫的 job 遷移（沒有資料之前不做）。
- identity 的 `source_id` 柵欄還在（只為 seller-service 的非同步移除）：開店與關店照樣帶 `store_id` 當來源，步驟 11 拿掉。
- PayUni：webhook 的 consumer（`sellerconsumer`）跑在 worker，`merchant.verification.*` 由 relay 轉送（`PayUniBindFailed` 沒有舊 routing key，不轉送）。`ExecuteTime` 的格式（`yyyyMMddHHmmss`）與時區（台北）取自 Java 測試的樣本與 PayUni 慣例，沒有對真實的通知驗證；輪詢（事件時間用我們的時鐘）與 webhook（PayUni 的時鐘）混用，假設兩邊的時差遠小於狀態改變的間隔。沒有 sandbox 與真實呼叫：`platform/payuni` 只以本機的 httptest 驗證，欄位名稱、`search_merchant_status` 的回應格式與 AES-GCM 的格式照舊 `pkg/payuni`（PayUni 規格要求固定的 IV，同一把金鑰下相同的明文產生相同的密文，是規格的限制）；2 QPS 的外部限制由 `platform/payuni` 的 `golang.org/x/time/rate` 限流器守住（`PAYUNI_MAX_QPS`，預設 2，burst 1，一個程序一個 client，**限流器只在程序內：只能有一個 worker 程序，第二個 worker 需要共用的限流器才能開**；排不進 deadline 的呼叫回暫時性錯誤、由 River 重試）。
- PayUni：`seller.payuni_sync` 結果寫入之後、River 標記完成之前的空檔內到達的改動，因為唯一鍵含 `running`，不會另排 job；`seller.payuni_sweep` 在閒置 10 分鐘後補排（最多延遲約一個掃描週期）。同步被 PayUni 永久拒絕（`sync_error_code`）時賣家要再改一次才會重送，沒有自動重試。

## 特性測試

不採用雙跑的特性測試（遷移計畫 A3 決定第 11 項，比照 identity、buyer）：舊的一側要起 seller-service、gateway 與它們的資料庫，成本高；API 在步驟 8 重新設計後 REST 與 Connect 兩個 driver 對不上；而且盤點刻意修正的缺陷（先建店後驗證、整筆覆寫清掉電話、以 account_id 釋放圖片、停權的賣家不能關店）會讓兩側得到不同的結果。行為由本目錄與 `internal/closing` 的 integration 測試覆蓋，盤點的缺陷各有一個會在舊行為失敗的回歸測試；Connect handler 的測試在步驟 8。
