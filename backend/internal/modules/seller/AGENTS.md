# seller 模組

店家業務身分與店家 profile 的擁有者：申請開店、profile、logo 與封面、商家名單（站外業者的 BD 名單）、商品瀏覽數、措施（警告、停權與終止合作，依據是認定、風險類型或契約條款）與停權狀態的檢查、商家治理（通報、認定、措施、申訴）、關店，以及刪除帳號時的店家參與者。來源是 seller-service（遷移計畫 A3b 步驟 7a 核心、7b 治理）；7c 階段 1 加入 KYC 認證與處分的身分比對，階段 2 加入 PayUni 子商店的綁定、同步與審核狀態；階段 3 加入關店後的未結訂單檢查與關店後的清理（現行：30 天退場、6 個月清個資）；階段 4 加入商家名單與商品瀏覽數。入口與舊服務仍走 seller-service，切換在步驟 9。

## 職責

- 申請開店（設計書 44）：驗證全部輸入、建立 stint、寫入 profile、授予 SELLER 在同一個 transaction。
- 入駐同意（ADR `2026-10-19-seller-kyc-payuni-consolidated`「入駐同意紀錄」）：現行版本與網址（站內路徑，對外由 `internal/httpapi` 以 `PUBLIC_WEB_ORIGIN` 組成絕對網址，PayUni 的本來就是絕對網址）只在 `internal/model/agreement_gen.go` 的 `CurrentAgreements`，它由 `website/scripts/generate-legal.ts` 從 `website/docs/legal/` 的正本與 manifest 產生，不得手改；改版是改正本（版本行）或 manifest 後在 `website` 跑 `pnpm gen:legal`。同意的紀錄與開店、送出 KYC 的寫入在同一個 transaction，每次同意事件一列（KYC 的列綁定那次送出的審核紀錄，由資料表的 CHECK 把關）；關店 184 天的第二段清理（`StoreRetention`，連線紀錄）把來源 IP 與 User-Agent 清成 NULL，其餘保留。
- 店家 profile、logo、封面的讀寫，所有寫入者以版本做樂觀鎖。
- 店家封鎖（`store_blocks`，遷移計畫 A7-1b）：店家封鎖一位買家，主鍵 (store_id, buyer_id)，buyer_id 不建外鍵，買家刪帳時 accountdeletion 在同一個刪帳 transaction 呼叫 `ClearBlocksAgainstBuyer` 刪掉以他為對象的列（在買家的刪除事件派發之前）。單向：只擋買家在這家店的新互動（檢查在 social），不擋下單。`BlockBuyer`／`UnblockBuyer` 冪等，回「有沒有改變」；模組 API 不做能力檢查（封鎖是保護動作，停權時仍要能封鎖與解除），誰能代表店家操作由 httpapi 的 `ActingStore` 決定。`ListBlockedBuyers`（keyset）、`StoreBlocksBuyer`、`StoresBlockingBuyer`（批次，給列表每列的 `viewer_can_comment`）。不發布 `seller.pub_blocks`：封鎖不篩選讀取，檢查是依 ID 的查詢。`TestStoreBlockAndUnblockAreIdempotent`、`TestStoreBlocksAreDirectedAndBatchedPerBuyer`、`TestListBlockedBuyersPaginatesNewestFirst`、`TestClearBlocksAgainstBuyerDeletesOnlyThatBuyersRows` 驗證。
  - `BlockBuyer` 不鎖也不查對象買家（seller 不依賴 buyer，`internal/arch/modules.go` 擋，模組內無法檢查）：與買家刪帳並發時可能留下指向已關閉買家的列，也收得進不存在的 buyer_id；這是接受的現況，因為對已關閉買家沒有效果，對象是否存在由 A7-2 的 handler 從留言參照或買家 API 解析時把關。封鎖名單裡的已關閉買家由 A7-2 的 handler 組裝名單時顯示成已刪除，模組不提供這個行為。出現 seller 依賴 buyer 的理由，或名單顯示出現問題時重新評估。
- 措施與停權（ADR `2026-10-18-seller-governance-consolidated`「決策」的「認定、措施與效果」「申訴、補正與凍結」、設計書 32）：措施是效果的唯一來源，種類是警告、停權或終止合作（條款第 21 條），依據是違規認定（`violations`，只是認定）、風險類型（RISK，條款第 17 條）或契約條款（CONTRACT，只配終止合作）；停權狀態在讀取時推導（以帳號為單位，不存），停權期間與事件、到期與對帳由 `Recompute` 與 job 維護。管理員不再有獨立的停權與解除，也沒有直接關店：停權就是建立一個停權措施，解除就是結束（RISK）、撤銷、接受申訴或接受補正；平台關店就是建立終止合作，關店與恢復由措施驅動。
- 商家治理（ADR `2026-10-18-seller-governance-consolidated`「決策」的「通報與案件」、設計書 32）：通報（一位檢舉人的一次送出，登入的買家或匿名者；檢舉與食安同一張表）與案件（同一家店、同一個平台判定類別同時最多一個進行中，決定即結案）分開：通報有自己的結果，由 admin 分案、設定結果或移到其他案件，同一位檢舉人再次送出併成補充；嚴重度、決定與內部註記在案件；認定（升級規則以帳號計）、措施（建立、改理由與結束時間、結束、撤銷與連帶撤銷、複審期限、內部註記）與申訴；佐證圖片的 media 引用；匿名聯絡欄位的保留期限清理。
- 店家能力的推導（`model.CapabilitiesOf(store)`：每個能力的狀態與缺的條件，含店家狀態 `PUBLIC_LISTING`；能力名稱沿用 ADR `2026-09-18-seller-capability-authorization` 及其 2026-10-08 修訂）與檢查（`ActingStore`，ADR `2026-09-29-seller-suspension-and-business-identity-in-monolith`）。
- 關店（賣家自己關店；店家有未結訂單時拒絕）、終止合作生效後由系統關店與撤銷時恢復營業（`internal/closing`）、`accountdeletion` 的參與者動作（進入等待刪除、關閉）；關店可逆，圖片的釋放與不可逆的下游動作（`StoreRetired`）都在關店 30 天後的退場（第一段清理）；每次關店記下為什麼關的（賣家自己、終止合作連同造成關店的措施、隨帳號刪除）。
- 後台的店家讀寫（遷移計畫 A3b 步驟 8e）：目前店家的清單（店名、電話或 `store_code` 搜尋，依 KYC 申請狀態或「待審核」篩選，keyset）與統計、以店家讀 KYC 申請（`StoreKYC`）；停權與關店由措施的建立、結束與撤銷產生（後台沒有直接關店的方法）。
- 後台的 KYC 審核與 PayUni（遷移計畫 A3b 步驟 8f；`SellerAdminService`）：審核佇列 `AdminKYCApplications`（只列送出過的申請；篩選審核中依送出時間舊到新，其他與沒有篩選新到舊；`Query` 搜姓名、公司名稱與統編；keyset `KYCCursor{SubmittedAt, ApplicationID}`）、單筆檢視 `AdminKYCApplication`（遮蔽值、審核紀錄、銀行帳號命中的標記；顯示全文與證件讀取的稽核各自分頁：`ListKYCReveals`、`ListKYCDocumentAccesses`，新到舊的 keyset，申請不存在回 NotFound）、`ApproveKYC`／`RejectKYC`（etag；理由與 comment 共用 `platform/auditreason`；回傳的後台檢視在同一個 transaction 內讀）、`RevealKYCSensitive`（顯示全文，同時是 15 分鐘的證件授權）、`ReadKYCDocument`（以授權讀證件圖片）、`PayUniRegistrationOf`、`RebindPayUni`、`PayUniObservations`（keyset）、`RefreshPayUniStatus`。
- 關店後的兩段清理（ADR `2026-10-19-seller-kyc-payuni-consolidated`「關店與個資保留」與 2026-10-20 修訂，`internal/purge`）：**第一段（退場）**：stint 關閉之後過了 `model.StoreRetireAfter`（720 小時，30 天；因終止合作而關閉的到帳號上未撤銷終止中最晚的申覆期限，且不早於這 30 天），清公開內容（說明、獎項、網站），logo 與封面在這時才釋放，發 `StoreRetired`（relay 轉成 `seller.deleted`，下游刪除商品、貼文、聊天的個資等），記下 `stores.retired_at`；退場之後不能恢復營業。**第二段（個資清理）**：已退場、關閉之後過了 `model.StoreRetention`（4416 小時，184 天，詐欺犯罪危害防制條例第 37 條第 1 項的六個月；終止合作的式子同上），註冊、身分與連線資料一併清成 NULL：店名、店家聯絡（電話、聯絡人姓名與手機、客服信箱）與地址、KYC 個人欄位與證件、登記資料查詢、PayUni 的自由文字、同意紀錄的 IP 與 User-Agent，記下 `pii_purged_at`；審核事實、PayUni 狀態碼與措施的身分快照保留。兩段的時間條件只有 `RetireDueStores` 一支（`second_stage` 選段，時數由 `StoreRetireAfterHours`／`StoreRetentionHours`、`AppealWindowHours` 傳入），保存條件只有 `StoreHolds` 一支：`appeal_hold`（帳號上未撤銷的終止，或未撤銷的關聯終止的來源措施，有待處理申覆）擋兩段，也讓恢復營業（`closing.ReopenPlan`：第一段的時間條件成立而且沒有 `appeal_hold` 就是「保留期已過」）不恢復；`preservation_hold`（帳號上有沒撤銷登記、`hold_until` 晚於現在的主管機關來函指名，不指定店家或就是這家店）擋兩段，不影響恢復營業。每一批：時間條件選候選並鎖住（keyset，`FOR UPDATE SKIP LOCKED`）→ 鎖住之後以同一支查詢再判斷時間、再問 `StoreHolds` → 只處理仍然成立而且沒有被保存的。
- KYC 認證（ADR `2026-10-19-seller-kyc-payuni-consolidated`）：賣家填寫草稿、送出與取消，管理員審核（核准、退回、顯示全文與限時的證件圖片授權）；身分證號、負責人身分證號、銀行帳號加密保存，另以 blind index 做身分比對：別的帳號有生效中停權措施的身分證號或統編不能通過認證，銀行帳號命中只標記。證件圖片的 media 引用。
- 公司型申請的登記資料快照（同一份 ADR「登記資料快照」，遷移計畫 A3b 步驟 10a 第 4 刀）：送件（`kyc_applications.submission_seq` 每次轉成 SUBMITTED 加一，退回後重送是新的一輪）時在同一個 transaction 新增一列 PENDING 的 `kyc_registration_checks`（綁定這一輪的 `submission_seq`）並排入 `seller.kyc_registry_check`（`internal/kyc`；以 `check_id` 為 River 唯一鍵，狀態集合不含 completed、discarded；寫入的冪等仍由條件寫入保證）。job 在 transaction 內認領（申請不是這一輪審核中、同一輪已有更新的查詢，或已不是公司型就寫 `CANCELLED` 結束）、transaction 外呼叫 `Registry` port（`platform/gcis` 的 client 直接是它的實作，回來源的原始資料；轉成模組型別、現況分類、停業期間的合理性與地址拆分只有 `model.NewRegistration` 一處，互動的 `LookupBusinessRegistration` 與快照共用），再用另一個 transaction 寫入結果（只在仍是 PENDING 時；最後一次嘗試的任何失敗都記 `UNAVAILABLE`，不留 PENDING）。查詢是有期限的資源（2b 設計簡報題 1 (b′)）：建立時寫入 `deadline_at`（`requested_at` 加 15 分鐘，後台的 `deadline_time` 讀它），伺服器保證在期限前到終態。PENDING 的出口：寫入結果、認領時放棄、後台重新查詢取代、job 執行時已過期限直接記 `UNAVAILABLE`（不再呼叫資料來源）、掃描 job `seller.kyc_registry_sweep`（每 1 分鐘：`deadline_at` 不晚於現在加一個掃描間隔的 PENDING 收成 `UNAVAILABLE`／`CANCELLED`，閒置超過 3 分鐘的補排 job）；`RequeryKYCRegistration`（只在 SUBMITTED）把這一輪的 PENDING 全部收成 `CANCELLED` 再新增一筆並回傳它（帶期限）。FOUND 時存登記資料與現況並逐欄比對（名稱、設立日期、地址；組織型態在快照裡，申請人不填，不比對）：不一致與無法比對只記錄，不改申請狀態。後台顯示申請目前這一輪 seq 最大的已完成查詢（這一輪還沒有就沒有快照），「查詢中」只在 SUBMITTED 時計算；後台 etag 是申請版本加顯示的查詢序號，核准與退回把顯示的查詢記進審核紀錄。個資清理一併刪除查詢列。
- PayUni 子商店（同一份 ADR「核准與綁定」「PayUni webhook」）：核准時在同一個 transaction 寫入綁定意圖並排入以 `store_id` 為唯一鍵的 job，job 在 transaction 外向 PayUni 綁定（MerID 已存在時查詢認領）與同步店家的聯絡資料、地址；管理員重新綁定失敗的註冊（在 `kyc_reviews` 留下 `REBIND` 紀錄：誰（管理員 ID）、何時、哪一份申請，`TestAdminRebindIsRecorded`；回傳的註冊與一般讀取一致，帶賣家型態）；PayUni 的審核狀態（webhook、輪詢、手動刷新、綁定認領）先追加成觀測再套用，cert 軸與 PayUni 軸合成流程狀態。賣家看到的 PayUni 狀態在 `KYCFlow.payuni`（`PayUniState`、說明句、審核意見、能修正的欄位），由 `model.SellerPayUniOf` 推導（階段只經 `PayUniPhaseOf`）；流程、PayUni 狀態與不能重送的原因出自 `payuni.SellerViewOf` 的同一次註冊載入（帶賣家型態與店家缺的欄位），`DeriveKYCFlow` 的 `CanResubmit` 與 `SellerPayUniOf` 吃同一份、呼叫同一個 `sellerPayUniOf`，`KYCFlow` 不帶 PayUni 的事實（它們在 `PayUniRegistration`）；`KYCFlow.can_resubmit` 是 `SaveKYCDraft` 與 `SubmitKYC` 此刻會被接受（PayUni 階段 ⇔ 推導結果是 FIXABLE），不能做的原因與句子只在 `model.ResubmitUnavailableReasons`，兩個 RPC 的 `failed_precondition` 與 `resubmit_unavailabilities` 同一個函式；沒有 `GetMyPayUni`。綁定重試用完（`PAYUNI_UNAVAILABLE`）進後台待辦 `review_payuni_bind_retry`（`bind_failed_at` 起算 24 小時）；重新綁定的可用性與方法同一個函式（`model.RebindUnavailableReasons`，見下一條）。
- admin 對店家的動作（遷移計畫 A3b 步驟 10e 第 5b 刀，`step10e-5b-design.md`；`model/store_action.go`）：建立警告、停權與風險措施（`CREATE_MEASURE`）、代行營運的店家狀態那一半（`DELEGATE`，由 `CapStorefrontWrite` 缺的條件對應，delegation 讀同一個函式）、核准、退回、重新查詢商家認證（`APPROVE_KYC`、`REJECT_KYC`、`REQUERY_KYC`）、重新綁定 PayUni（`REBIND_PAYUNI`）的前置條件，**只有一張有效組合表 `storeActionRules`**：每個動作是一串依先後排列的 `(原因, 條件, 種類)`，推導就是依序跑條件；`blocking` 的原因方法回 `failed_precondition`、訊息是第一個原因的句子（`ErrStoreActionUnavailable`），`idempotent` 的原因（只有 `PAYUNI_BIND_IN_PROGRESS`）方法不回錯誤、回目前的註冊，沒有句子；句子只有 `StoreActionUnavailableText(reason, action)`（`text/` 的 `staff` 段，沒有通用句：漏掉的組合是內部錯誤）。已關閉的店家對 admin 是存在的資源：不是 `not_found`，是 `failed_precondition`（`STORE_CLOSED`；建立終止的兩個擋下也是）；案件與通報建立措施被擋下的原因句與 `CreateMeasure` 同一句。**店家不是營運中（已關閉、等待刪除）或帳號停權時商家認證審核暫停**：核准、重新查詢不可用，申請維持 `SUBMITTED`，不在後台待辦、沒有審核期限；停權只擋核准、退回照舊可用（但件不在待辦）；恢復營業或停權結束時回到待辦，開始時間是送出、最近一次恢復營業（`store_closures.reopened_at`）、最近一次停權結束（`account_sanction_lifted_at`）三者最晚的時間。重新綁定的原因依序是 `PAYUNI_MERCHANT_TERMINAL`、`STORE_CLOSED`、`STORE_PENDING_DELETION`、`PAYUNI_BIND_IN_PROGRESS`（idempotent）、`PAYUNI_BOUND`、`KYC_NOT_APPROVED`（註冊所根據的申請不是已核准，例如賣家正在修改）。後台待辦 `PAYUNI_BIND_RETRY` 的成員是「重新綁定此刻可做」的子集（`TestBindRetryQueueIsASubsetOfRebindableStores`）。`GetStore`（`can_create_measure`）、`GetKYCApplication`、`GetPayUniRegistration`（`can_rebind`、`flow_status`＝`PayUniPhaseOf`）與清單的 `delegation_unavailabilities` 都帶原因；client 只呈現。`TestStoreActionTextIsTheApprovedCopy`、`TestDelegateReasonsAreTheMissingStorefrontWriteRequirements`、`TestKYCReviewPausesWhileTheStoreIsClosedAndResumesFromTheReopening`、`TestAwaitingReviewIsOneDefinitionAcrossTheQueueTheListAndTheStats`、`TestRebindReasonsAndErrorsAreTheSameFunction`。
- 商家名單（遷移計畫 A3b 步驟 7c 階段 4、8h-1，來源 seller-service 的 `seller_prospects`；ADR `2026-10-04-prospect-contact-points-and-matching`）：BD 的站外業者名單。管理員的建立（含建立前的比對）、清單、讀取、部分更新（含 logo 與封面的上傳）、封存與還原、合併、手動轉成店家、統編對帳與疑似重複；採購候選搜尋（給 ai-service，P5，每筆帶主要的網站）與 `ProspectContact`（主要的 email 與狀態，給 7d 的 vendor portal 邀請供應商；在呼叫方的 transaction 內讀時那一列帶 `FOR SHARE`，與封存、合併序列化，讓邀請的建立不會晚於封存的撤銷）。聯絡方式是清單（`prospect_contacts`，每個類型恰好一個主要的），統編是權威識別碼、由資料庫保證唯一，聯絡方式的比對鍵相同只是比對訊號（確認不是同一家才寫入），名稱相同與比對鍵相同的配對永不自動合併；候選配對的處理方式是合併，或 `MarkProspectsDistinct`（直接標記不是同一家：不帶版本，只限兩個進行中的業者，冪等，不改寫第一次的管理員與時間；`TestMarkProspectsDistinctDismissesACandidatePair`）。邀請子系統不搬。

是台北日曆日）。`stores` 沒有停權欄：停權狀態由措施推導。`store_exposures`（每家店最後公告的可曝光與公告序號 `version`，與店家列同一個 transaction 建立，version 0 是還沒公告過）。另有 media 引用的同步狀態 `media_ref_sync` 與退場資產 `retired_assets`。

SQL 的 view 與函式（寫在 `db/objects.sql`、手寫 migration，單體規則 6；Atlas 只讀 `schema.sql`）：`store_requirement_flags`（view，每家店與時間無關的條件一欄一個布林：`active`、`not_pending_deletion`、`kyc_approved`、`has_store_name`、`has_logo`、`has_town_code`；`stint.WithConditions` 讀它填 `Store.Conditions`）、`effective_measures(at)`（「措施生效中」唯一的定義，回傳 `effective_measure (id, account_id)`；`EffectiveMeasures`、`EffectiveMeasuresAll` 與 `pub_exposable_stores` 都讀它；寫成單一 SELECT，不用 UNION ALL，外層的帳號條件才推得進 `measures_enforced_suspension`，`TestExposableStoresJoinProbesMeasuresByAccount`）。`has_store_name` 只看 NOT NULL，「不是空白」由 `stores_store_name_check` 保證（頭尾不是 Unicode 空白，`platform/trimtext.Check`，與寫入端的 `trimtext.Trim` 同一個集合，`TestStoreNameCheckRejectsEveryUnicodeSpaceAtEitherEnd`）。

## 發布的讀取介面（pub_*）

形狀宣告在 `db/pub.sql`（依賴表允許的上層模組的 sqlc 讀它，`internal/arch` 的 `TestSQLCReadsOnlyItsOwnSchemaAndAllowedPubContracts` 擋住讀內部表），定義在 `db/objects.sql` 與手寫的 migration，`cmd/hawkr` 的 `TestPubContractsMatchMigrations` 比對兩者（欄位、型別、參數與回傳，雙向；函式的寫法由 `TestSchemaFileMatchesMigrations` 檢查）。`pub.sql` 裡宣告成表的 `pub_exposable_store` 只是函式回傳列的形狀，消費端的 query 不得直接參照它，只能呼叫函式（同一個 arch 測試；pgx 手寫的 SQL 字串不在檢查範圍，現在單體的正式程式碼裡沒有 seller 表的手寫 SQL）。改 `pub_*` 的形狀等於改契約：同一次變更內更新 `pub.sql` 與所有消費端；底層欄位改型別或刪除時在同一份 migration 內 drop 再建。

- `seller.pub_exposable_stores(at timestamptz) RETURNS SETOF seller.pub_exposable_store (store_id bigint)`：`at` 這一刻可以公開曝光的店家，曝光規則唯一的家（ADR `2026-09-24-go-modular-monolith` 文末修訂的曝光規則段）。`at` 由呼叫方以請求的 clock 傳入，不用 `now()`；函式會被內聯（沒有 Function Scan），join 時每家店對 measures 的讀取是以帳號為鍵的索引探測。上層用法：`EXISTS (SELECT 1 FROM seller.pub_exposable_stores(sqlc.arg(now)::timestamptz) e WHERE e.store_id = p.store_id)`。`store_exposures`、`StoreExposureChanged` 與 15 分鐘對帳只為行程外的 legacy 消費者保留，B4 把 product 搬進單體後刪除。
- `seller.pub_review_items(at timestamptz) RETURNS SETOF seller.pub_review_item (kind, item_id, 對象的鍵, store_id, store_name, start_at, due_at)`：`at` 這一刻營運要處理的全部待辦（12 種，都有期限），是 12 支 `review_<種類>(at)` 的 `UNION ALL`，成員、開始與期限的規則只在那些函式（`step10e-3d-design.md` E10）。`reviewqueue` 模組讀它排序分頁（`due_at, start_at, kind, item_id` 的 keyset），沒有排序保證；`at` 由呼叫方傳入。`TestPubReviewItemsIsTheUnionOfTheReviewFunctions` 鎖住它等於逐支函式的集合。

## 模組內部結構

- 根套件只保留 `Module`、`New`、`Migrations`、轉呼叫方法、對外型別別名（治理的在 `governance.go`）與事件（`events.go`）。
- `internal/onboarding` 申請開店；`internal/profile` 讀取與 profile、logo、封面的寫入；`internal/suspension` 停權期間的維護（`Recompute`）、身分快照（`RecordIdentities`）、`ActingStore`，以及措施的到期與對帳 job；`internal/measure` 措施的建立（含認定、升級、終止事由與關聯帳號、`request_id` 冪等）、修改、結束、撤銷與連帶撤銷（認定撤銷、來源終止撤銷）、複審期限、申訴與裁定、內部註記、讀取（停權一律經 `suspension.Recompute`）；`internal/governance` 通報、補充與佐證的寫入、分案、設定結果、移動，案件的決定、改嚴重度與註記，以及聯絡欄位的清理；`internal/closing` 關店（查店家未結訂單的 port `Orders` 在這裡宣告）、終止合作生效後的關店（`seller.termination_effect`、每小時的 `seller.reconcile_terminations`）、恢復營業（`ReopenPlan`、`Reopen`）與刪帳參與者；`internal/purge` 關店後的兩段清理（每小時 River 排程：關店 30 天退場——清公開內容、釋放 logo 與封面並發 `StoreRetired`；關店 184 天清店家的註冊資料、KYC 與 PayUni；證件在刪除時記成退場並排入引用的同步）；`internal/mediaref` 是 logo、封面、業者圖片、證件與佐證在 media 的引用同步（退場資產、版本與 `seller.media_sync` job，演算法是 `media.Sync`）；`internal/kyc` 是 KYC 認證（草稿、送出、取消、審核、顯示全文、身分比對、證件圖片；加密與 blind index 用 `internal/platform/seal`，與 identity 共用）；`internal/payuni` 是 PayUni 註冊（意圖、sync／輪詢／webhook 套用的 job、觀測、流程狀態、錯誤目錄的使用；呼叫 PayUni 的 port `Client` 在這裡，真正的 HTTP client 是 `internal/platform/payuni`，payuni 不碰 KYC 金鑰，解密由 kyc 以 `KYCSource` 提供）；`internal/prospect` 是商家名單（建立、比對、更新、封存、合併、轉換、對帳、搜尋、圖片；比對鍵的解析器 `model.ContactMatchKey` 在 `internal/model/prospect_match.go`，沿用舊 seller-service 的 P1 並加共用平台的排除）；`internal/views` 是商品瀏覽數的彙總與統計；`internal/exposure` 是可曝光規則的套用（`Classify`）與公告（`Announce`）；`internal/stint` 是共用的列鎖（`LockAccountOf`）、停權狀態的推導（`Derive`、`Load`）、型別轉換與快取失效；`internal/model` 是型別、儲存的代碼、能力、事件與輸入規則；`internal/store` 是 sqlc 生成物。鄉鎮市區代碼的表在 `platform/twaddr`。
- 依賴圖的唯一來源是 `internal/arch/modules.go`（模組之間與模組內）。各子領域在自己的套件宣告最小的 `Deps` 與 identity 介面，由根套件逐欄組裝。

## 不變量

守門測試在本模組；規格唯一來源是 `docs/modules/seller.md`。

- 一帳號最多一個目前 stint，SELLER 與它成對授予、移除。守門：`stores_current_account`、`TestApplyRejectsSecondStoreAndReonboardsWithNewStint`。規格：§2。
- 鎖順序：identity 帳號列、帳號全部 stint（`LockAccountStores`）、通報／案件／詢問／措施列（依 id 升序）、公告列；跨帳號依 `account_id` 升序。守門：`TestConcurrentSourceRevokeAndLinkedCreateNeverDeadlock`。規格：§18。
- 停權不存，推導點只有 `stint.Derive`；措施「生效中」的 SQL 定義（`EffectiveMeasures`、`EffectiveMeasuresAll`、`ScheduledMeasureIDs`、`account_sanction_lifted_at`）與 `StateOf` 在邊界一致。守門：`TestEffectiveMeasuresAndStateAgreeAtTheBoundaries`。規格：§5、§17。
- 措施版本只經 `InsertMeasure`／`AdvanceMeasureRevision`；停權期間只由 `suspension.Recompute` 寫，先鎖再讀。守門：`TestRecomputeReadsMeasuresAfterLockingTheStores`。規格：§5。
- 動作可用性各只有一處來源（`Can*`、`*UnavailableReasons`、`Availability()`、`BlockFor`、`OpeningBlockers`），API 的 `can_*` 共用。守門：`TestCanFlagsMatchWhetherTheActionSucceeds`。規格：§5–§8。
- 能力只由 `model.CapabilitiesOf` 推導，`ActingStore` fail-closed；停權不擋關店與刪帳。守門：`TestActingStoreFailsClosed`。規格：§10。
- 關店只走 `closing.close()`，紀錄只在 `store_closures`，自己關店先確認沒有未結訂單。守門：`TestEveryClosePathRecordsWhoClosedTheStore`、`TestSelfCloseFailsClosedWhenOrdersCannotBeChecked`。規格：§11。
- 兩段清理只在期滿且無保存條件時做，候選鎖住後重判。守門：`TestPurgeRechecksTheAppealHoldAfterLockingTheCandidates`。規格：§11。
- 可曝光公告只經 `exposure.Announce`，先鎖再算。守門：`TestAnnouncementLocksBeforeItComputes`。規格：§12。
- media 引用只由 `seller.media_sync` 寫，transaction 外只 `Finalize`，退場資產不能寫回。守門：`TestImagesLinkByStoreIDAndUseVersion`。規格：§9。
- 寫入以版本樂觀鎖，拒絕都在 token 轉正之前。守門：`TestUpdateProfileVersionCAS`、`TestRejectedProfileUpdateDoesNotConsumeTheStagedToken`。規格：§3。
- 通報只指向公開過的店，重複送出併成補充；佐證與證件先寫讀取紀錄才讀。守門：`TestSupplementsAttachToTheOriginalReport`、`TestEvidenceReadIsRecordedBeforeTheBytesAreRead`。規格：§7、§9。
- KYC 個資只存密文，型別不帶明文，顯示全文先稽核；身分比對只讀 blind index 快照。守門：`TestKYCNeverReturnsOrStoresPlaintext`。規格：§13。
- PayUni 外部呼叫不在 transaction 內，一店一個 sync job，先追加觀測再套用。守門：`TestSyncJobIsUniquePerStoreInRiver`。規格：§14。
- 商家名單統編在未封存業者間唯一，每類型恰一個主要聯絡方式。守門：`TestTaxIDIsUniqueAmongLiveProspects`。規格：§15。
- 瀏覽數以 `store_id` 與台北日計，請求路徑不呼叫商品服務。守門：`TestRollupBucketsByStoreAndTaipeiDayOfOccurrence`。規格：§16。
- 事件與快取失效在寫入的 transaction 內；儲存代碼 UPPER_SNAKE 加 CHECK 等於 `Values()`。守門：`TestEventFailuresRollBackTheWholeCommand`、`TestChecksMatchGo`。規格：§18、§20。

## 特性測試

不採用雙跑的特性測試（遷移計畫 A3 決定第 11 項，比照 identity、buyer）：舊的一側要起 seller-service、gateway 與它們的資料庫，成本高；API 在步驟 8 重新設計後 REST 與 Connect 兩個 driver 對不上；而且盤點刻意修正的缺陷（先建店後驗證、整筆覆寫清掉電話、以 account_id 釋放圖片、停權的賣家不能關店）會讓兩側得到不同的結果。行為由本目錄與 `internal/closing` 的 integration 測試覆蓋，盤點的缺陷各有一個會在舊行為失敗的回歸測試；Connect handler 的測試在步驟 8。
