## 沿用盤點

social-service 的每個機制，搬進來時都重新判斷過（遷移計畫「模組完成的定義」）：ID 方案、extension、套件、共用 helper、舊的檢查邏輯、schema 慣例、CodeMeta 的值域與錯誤碼。從零設計會不同的，完成前提出來決定。對外 API（舊 gateway 的 handler）的機制在下一節。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| TSID bigint 當實體主鍵（M1，`SI/usecase/di.go:29`） | Java 消費者要以數字 ID 讀 | 不成立：Java 沒有呼叫 social；社群實體不被別的模組以 ID 指稱成 bigint | 應用層 UUIDv7（ADR 2026-09-25-row-identity-by-data-kind） | 改：social 擁有的實體 UUIDv7，讚、標籤、瀏覽、分享用複合自然鍵；`actor_id`、`store_id`、`buyer_id` 因 buyer、seller 仍是 bigint 而維持 |
| 貼文讚表帶 `actor_kind`（M2，`SI/domain/constants.go:19-22`、`schema.sql:188`） | 店家也能對貼文按讚 | 不成立：貼文讚恆為買家（舊 CHECK 把它鎖死為買家） | 不存永遠只有一個值的欄位 | 改：`post_likes (post_id, buyer_id)`；留言的讚與留言、討論區仍帶 `actor_kind`（互動者 (kind, id)） |
| 計數存在貼文與留言列上，經 `counter.delta`（RabbitMQ）非同步加減，10 分鐘全表對帳（M3，`SI/worker/counter_delta.go:31-78`、`counter_reconcile.go:24-66`） | 熱門內容的 row-lock 競爭（ADR 2026-09-18-mq-social-counter-async-delta）；`counter.delta` 不冪等、會丟 | 競爭的前提仍可能成立、目前沒有量測；跨服務已不成立（同一個 DB）；沒有外部消費者 | Lemmy 的 aggregates 表加 trigger、Mastodon 的獨立 stats 表加手動重算、Discourse 的定期對帳（`counts-brief.md` v4） | 改：獨立的 stats 表，trigger 同 transaction 加減，外部事實改變排重算，每日對帳與 `social-recount`；換做法的觸發：負載測試量到單一 stats 列持續鎖等待 → 分片計數列或緩衝批次寫入（取代舊 ADR，D2 寫新 ADR） |
| 留言數只算頂層，為了和列表 API 的 total 一致（`SI/usecase/comment.go:220-221`） | 列表 API 回總數 | 不成立：新 API 不回總數（AIP-158 keyset） | 主流消費產品與 Lemmy 的留言數含回覆 | 改：留言數含回覆；每則頂層另有回覆數 |
| 頂層留言刪除或隱藏後底下的回覆行為（舊：回覆留在 DB、列表只列頂層，等於回覆跟著消失） | 無 | 產品決定（Will 2026-10-23） | Reddit、Discourse 留佔位符 | 改：頂層不可見而底下有可見的回覆時回佔位項目（只有 ID、時間、狀態），回覆照常顯示並計入；沒有可見回覆時整則不出現。佔位符文字在 A7-4 的 UI 稿核可 |
| 貼文留言的回覆只限貼文所屬的店（買家不能回覆貼文留言；`SI/usecase/comment.go:178-198`） | 產品規則：回覆是店家對買家留言的回應 | 成立（沿用計畫預設，Will 沒有推翻） | 主流社群產品多數允許任何人回覆 | 沿用舊產品規則。因為店家可以回覆多次，且頂層留言可以被刪除或隱藏，同串 FK（`thread_id` 複合 FK）與佔位項目是店家回覆本身就需要的，不是為了買家回覆預留。觸發：產品決定開放買家回覆時，不需要改 schema，只改 `comment.Create` 的身分檢查，以及 A7-2 的 `viewer_can_*` 欄位裡回覆能力的推導 |
| 隱藏是留言與討論區上的 `hidden_at`／`hidden_reason` 欄，貼文也有（M13、`posts.sql`） | 一個欄位夠用 | 不成立：要多次隱藏與還原、稽核、理由與來源；店家內容的隱藏屬於 seller 的措施 | 獨立的紀錄表 | 改：`hides` 表（只收買家寫的留言與討論區留言），部分唯一索引保證同一則最多一筆未還原；貼文與店家身分的內容走 seller 的內容下架措施（A7-1c） |
| 單篇讀取不過濾、列表不看貼文狀態與隱藏（SD1、SD2，`posts.sql:1-2`） | 無（缺陷） | 不成立 | 讀取一律套用同一個可見性述詞 | 改：述詞寫在 Go 的 `internal/visibility`（Will 2026-10-23），讀取的 query 用 go-jet 在上面組成（`internal/reads`）。先前的 view 加每支 query 固定 join 因 migration 單獨套用的真約束（view 與 `BEGIN ATOMIC` 函式在建立時就綁定，不能參照 seller、buyer 的 `pub_*`）才那樣切，規則散在三處、靠數次數的測試守；sqlc 沒有片段可以組合。守門測試取代 `readpolicy_test.go`（入口型別、登記表、golden SQL、邊界、Describe 形狀），見 ADR `2026-09-27-module-internal-structure.md` 的修訂 |
| 店家退場時整店軟刪、釋放圖片引用，hashtag 計數用 `post_count` 欄 ±1（SD16，`SI/worker/seller_deleted.go`） | 計數要存 | 不成立：標籤數量改成讀取時依公開述詞計算 | 值的集合不存聚合 | 改：`post_hashtags` 是貼文的值的集合（整批替換），不建 `hashtags` 實體表、不存 `post_count`，因此沒有「照 id 升冪」的鎖順序；退場由 `pub_exposable_stores` 在讀取時擋住，實體清除由 job 做 |
| 反正規化的作者名稱、頭像快照與兩支回填指令（M19、M25） | 跨服務時列表要快 | 不成立：同一個 DB，讀取時由 buyer、seller 批次補；買家刪除後列上不留 PII | 讀取時補 | 刪：留言與討論區不存快照；回填指令刪除 |
| 髒字詞典 `pkg/moderation`（14 個詞的子字串比對，只擋建立，SD6） | 詞典要擋 | 成立，但編輯會繞過 | 詞庫應有擁有者與後台維護 | 照搬一份到 `platform/textfilter`（實際 16 個詞），所有寫入路徑（建立與編輯）共用；`pkg/moderation` 到 A6 才刪。已知誤擋：子字串比對會誤擋正常文案（`pkg/moderation/dictionary.go:10-14` 記載三個詞因此移除）。機制保留（所有寫入路徑在寫入前拒絕，SD6 已決定）；詞表是過渡的內容：詞典的內容與維護屬於 moderation（`domain-inventory.md` M17、Q12；計畫 A7-1d），social 只呼叫 `platform/textfilter`。觸發：A7-1d 的後台維護詞典上線時，詞表改讀它，並在那時把比對改成 token-boundary 或更精準的比對 |
| 軟刪保留內容與圖片引用（M15，`SI/usecase/post.go:522-535`、`schema.sql:71`：跨服務時 media 無法列舉引用） | 跨服務時 media 無法列舉引用 | 舊理由不成立（單體）；新的必要條件：軟刪的保留期還沒訂 | 依隱私權政策訂保留期、排清理 job | 保留：貼文、留言軟刪時內容與引用先留著（買家刪帳的清除 job 是例外：他的留言與討論區留言內文設 NULL，見 M23）；店家退場的清除 job 照樣釋放圖片引用。重新評估的觸發：隱私權政策訂出保留期（計畫「延後」的保留期與清理 job） |
| 圖片引用在 `AddUnlink` 之外由 media reconciler 掃描（`SI/usecase/post.go:352-369`、#2772） | 跨服務 | 不成立 | 擁有者寫業務列與退場紀錄，同步 job 精確 Link／Unlink（content 的做法） | 改：照 content 的 `mediaref` 與 `media.RefSyncer`；新圖的轉正在 transaction 外（上傳者是店家所屬帳號），transaction 內寫列、記退場、排同步 job |
| 貼文 `publish_status` smallint 4401／4402／4403，沒有 CHECK（CodeMeta） | CodeMeta 的舊契約 | 凍結，不新增值域 | UPPER_SNAKE 代碼加 CHECK | 改：`status` TEXT，`DRAFT`／`PUBLISHED`／`UNPUBLISHED`，CHECK；4401、4402、4403 依序對應；`published_at` 與狀態的 CHECK（草稿沒有、發布過的一定有） |
| 排程欄 `schedule_*`、`scheduled_by_session_id` 在貼文列上 | 排程發布 | 這一步不做（A7-1f，形狀由 A7-D6 決定） | — | 不建；A7-1f 再加 |
| 停權旗標讀自 gRPC metadata，讀不到時放行；只擋店家身分的留言與討論區留言（M13，`SI/grpc/handler.go:25-33`、`usecase/comment.go:196-198`、`forum.go:88,122`） | gateway 注入旗標 | 不成立（SD25）：在同一個程序讀權威資料 | `seller.Authorize` 每次由店家的條件與處分推導，fail-closed | 改：店家身分的寫入收已解析的 `seller.Store`，在 social 內以 `seller.Authorize` 檢查能力：建立、編輯、發布貼文與留言、討論區、留言按讚要 `CapMarketing`，下架與刪除要 `CapContentContract`（停權時仍授予）。舊碼只擋留言與回覆，貼文寫入由 gateway 擋；新碼三條路徑（帳號、代行）同一個入口 |
| 貼文帶的商品 `product_id` 不驗證（SD24） | 無 | 缺陷 | 寫入時驗證存在、上架、歸屬 | 改：`ProductVerifier` port（`cmd/hawkr` 注入 `productservice`），在 transaction 之前呼叫；讀取時不重驗；B4 catalog 搬進單體後換成 in-process |
| 瀏覽、分享直接 `+1`，沒有去重，委派者也算（SD18，`post.go:538-551`） | 無 | 缺陷 | Discourse 型：先寫去重列，真的新增才加一；匿名用每日換 salt 的雜湊（Plausible） | 改：`post_views`（貼文、台北日、觀看者鍵）與 `post_shares`（貼文、買家）的主鍵是去重，trigger 在新增時加一；匿名的觀看者鍵是 `HMAC-SHA256(當日 salt, 貼文 ‖ IP ‖ UA)`，表裡沒有 IP 與 UA；salt 每台北日一列，週期 job 清掉舊的 |
| 每日對帳與 `social-recount` 一個對象一個 transaction（舊 social 的 `counter` 重算與 A7-1a 初版） | 全量掃描要能在可接受的時間內完成，且不能蓋掉並行的加減 | 全量掃描成立（外部事實的改變落在沒有被寫入的對象上，只追蹤被寫入的對象會漏）；逐個對象不成立 | 批次的集合語句：鎖一批、分組計數、只覆寫不同的列 | **改（DR-A1）**：對帳依 ID 的 keyset 每 500 列一批，每批一個 transaction、三個語句（依 ID 由小到大 `SELECT … FOR UPDATE` 鎖這批的 stats、一個分組 COUNT 的 UPDATE 只覆寫與現值不同的列、`RETURNING` 前後值給漂移報告）；先鎖再算讓並行的加減不被蓋掉。旗標修正（`reevaluateAll`）仍在最前面。守門：`TestBatchRecountDoesNotOverwriteAConcurrentWrite`、`TestRecountAllIsBatchedAndOverwritesOnlyDriftedRows`；全量耗時在 `step-1a-perf/README.md` |
| 標籤的貼文列表以貼文的 `published_at` 排序（`ListHashtagPosts`） | 列表要依發布時間 keyset | 成立 | 把排序鍵放進被驅動的索引（反正規化），游標才是 Index Cond | **改（P1b，Will 2026-10-23）**：`post_hashtags.published_at` 是貼文 `published_at` 的複本，`NULL` 表示貼文還沒有發布（草稿；索引是 partial，不收）；貼文第一次發布時由 trigger 寫進它所有的標籤列，標籤列在貼文已發布後才寫入時由 trigger 帶入，貼文的 `published_at` 一旦有值就不能改（trigger 擋），所以複本不需要同步。必要條件是 DR-A2 的不變性（`published_at` 固定在第一次發布）；「公開可讀」仍由 `visibility.ReadablePosts` 組成，不在標籤列上另寫一份。守門：`TestHashtagPublishedAtIsACopyOfThePost` |
| `ListHiddenContentOf` 的游標是 join 上的 Filter | 作者只讀自己被隱藏的內容 | 成立 | 作者自己的有界集合（一個買家被隱藏的留言與討論區留言），不需要為它反正規化 | **不改（P1b，Will 2026-10-23）**：集合驅動、成本與游標深度無關；觸發：實測 p95 > 300 ms（量測在 `step-1a-perf/README.md`） |

## M1–M27 逐項（盤點 `domain-inventory.md` §2）

四欄來自設計書 §8：現況（舊碼出處，`SI/` 是 `backend/services/social-service/internal/`；行號沿用盤點快照 `172260d31`，抽查過 `di.go:29`、`comment.go:178-181,220-221`、`counter_delta.go:31`、`counter_reconcile.go:20-23`、`post.go:139,522-524`、`report.go:35`）、從零設計、去向（新碼與證據）、重新評估的條件。M4、M8、M10、M12、M24 與 M11 的資料面不屬於 social，放在表後一節說明去向。

|---|---|---|---|---|

## pg_trgm spike 與效能量測

詳細結果、環境與指令：`backend/docs/plans/2026-10-18-a7-social/step-1a-perf/`（`README.md`、`seed.sql`、`measure.go`、`spike-trgm.sql`）。環境：`postgres:18-alpine`（PostgreSQL 18.6，musl）、locale `en_US.utf8`（libc provider）、128 MB `shared_buffers` 的預設設定；資料是合成的（店家 10⁴、貼文 10⁵、標籤列 4×10⁵、留言 7×10⁵、讚 10⁶）。

- **「包含」搜尋用 `LIKE '%q%'`，不加 pg_trgm**：1–4 個漢字共 332 個查詢字串，`LIKE` 與 `strpos` 的列數全部一致；不用索引的謂詞掃描 14–17 ms（397,437 列，Parallel Seq Scan），完整的建議 query（含對每個比對到的列探測店家可曝光）p95 85–146 ms，低於 300 ms 的門檻。停止條件（CJK trigram 不可用而包含搜尋必要）不成立。
- **pg_trgm 在這個 locale 下可用，但對常見的查詢長度沒有幫助**：漢字被當成字詞字元切 trigram（`show_trgm('烘焙茶')` 有 4 個），3 個漢字的包含搜尋走 GIN 5 ms、4 個漢字 0.7 ms；1–2 個漢字抽不出 trigram，有索引也是 Seq Scan（16 ms）。在複本上加 GIN 與其他索引後整組量測反而更慢（建議 244–651 ms），所以沒有留索引、沒有 migration。重新評估的觸發：包含搜尋的完整 query p95 超過 300 ms 時，3 字元以上加 GIN、1–2 個字元靠限制最短長度；正式環境換成 glibc 的 Postgres 時重跑 `spike-trgm.sql` 的第 1 節（切分看 libc 的 `iswalnum`）。
- **10⁵ 貼文下的讀取情境**：初量 28 個中 27 個 p95 ≤ 300 ms，超過的是 `TrendingHashtags` 取近 365 天（392 ms）；主 session 2026-10-23 決定窗口上限降到 30 天（見 M6 的沿用盤點），近 30 天 p95 45–92 ms（三次量測，機器有雜訊）。每個 `pub_*` 都被內聯（沒有 Function Scan）。
- **keyset 游標是單一列比較**：`NOT has_cursor OR (row) < (...)` 在 generic plan 下是 Filter（成本與游標深度成正比，動態牆 90% 深度 54.78 ms 對第一頁 2.70 ms），所以 13 支 keyset query 全改成 `(a, id) < ($, $)`（Index Cond），第一頁由 `model.DescStart()`／`AscStart()` 給方向的極值游標（`TestKeysetQueriesCompareOneRowAndHaveNoBooleanSwitch` 擋回頭；`TestFirstPageEqualsSentinelCursorAndDeepPagesHaveNoGapsOrDupes`）。`ListHashtagPosts` 的排序鍵複製在 `post_hashtags.published_at`（索引 `post_hashtags_feed`：`(name, published_at DESC, post_id DESC)`，partial `published_at IS NOT NULL`），游標也是 Index Cond（熱門標籤第一頁 p50 78 ms → 4 ms）；唯一的例外是 `ListHiddenContentOf`，見下一列。細節與量測在 `step-1a-perf/README.md`。

## 與 social-service 的差異

資料沒有搬移（系統從未上線），schema 是新的 baseline。

- 標籤：`hashtags` 實體表與 `post_count` 刪除，改 `post_hashtags` 值的集合（不建 `hashtags` 表的理由：隨貼文整批讀寫、不被以 ID 指稱）。
- `comments` 與 `forum_entries` 不合併：容器不同（貼文與店家）、留言有讚而討論區沒有，合併要「容器恰好一個」的 CHECK 與兩套讀取。
- 買家的社群處分 `sanctions`：`kind` 目前只有 `WARNING` 一個值，`ends_at` 沒有讀者（警告不限制參與）。這是計畫 A7-D9（a7 核可）明寫的形狀「紀錄帶型別、可為空的 `ends_at`、理由」，不是這一步多加的欄位；A7-1d（moderation）沒有第二個種類，名字出現在計畫「不做」清單：有期限的參與限制（Q2 (iii)，階梯參數等買家條款寫好）。必要條件：第二個種類落地時不必改欄位、`MySanctions` 的回傳形狀與 proto／uitext 的種類 enum。今天成立的只有「計畫已決定帶型別」，沒有第二個種類的需求，所以這是預留，不是需要。觸發：買家條款寫好（有第二個種類）→ 值與規則加進 `SanctionKindValues` 與 CHECK；A7-2 定 proto 之前若 Will 決定不預留，刪 `kind`、`SanctionKind` 與 CHECK（改動範圍：schema、`model.Sanction`、`Warn`、`MySanctions`、測試）。
- 熱門（本週主題）`TopPosts`：照搬 website 現行算法（最新 30 篇公開貼文中依瀏覽數取前幾名），畫面不變；改算法（加權、時間窗）是產品題。
- 「計入」的單一定義在資料庫的 `reevaluate_comments`／`reevaluate_forum_entries`（`BEGIN ATOMIC`，只讀 social 自己的表：`deleted_at`、`hides`、`content_takedowns`、`inactive_authors`），結果存在每則留言與討論區留言的旗標 `counted`；讀取直接用旗標，重算是旗標的加總（`reads/recount.go`，一個 keyset 範圍一個語句、分組 COUNT、只覆寫不同的列）。trigger、買家刪帳的訂閱者與每日對帳都只呼叫 reevaluate（ADR `2026-10-23-social-counts-in-stats-tables.md` 文末兩則修訂）。舊的 `comment_counted` 函式與 view 刪除。資料集測試 `TestStatsMatchTheDatasetAfterRandomWrites` 以獨立寫的 SQL（對 `buyer.buyers` 的現況）對照計數與旗標。
- 買家刪帳的事實複本 `inactive_authors`（D-sync，Will 2026-10-23）：必要條件是「資料庫端維護的旗標依賴 buyer 擁有的事實，而函式不能參照別的模組」。業界：Discourse、Lemmy 的旗標由發動的請求同步寫入；replication of reference data 是模組化單體的標準做法。只增不刪（買家不會回到營運中）。觸發：`reevaluate_*` 改成不存旗標（讀取時推導）時複本不再需要；內容下架複本 `content_takedowns` 用同形狀但可刪除（下一列）。
- 內容下架複本 `content_takedowns`（D-sync，Will 2026-10-23；A7-1c）：必要條件同 `inactive_authors`（旗標與公開讀取依賴 seller 擁有的措施，而 social 的函式與讀取不能參照 seller 的內部表）。業界做法同上（發動的請求同步寫複本）。與買家那張不同：措施可撤銷，所以建立插入、撤銷刪除，並重新求值；同一則內容可被多個措施下架，所以以 (措施, 內容) 為唯一鍵，刪一個措施的列不影響另一個的。每則內容一個外鍵欄位（比照 `hides`）加恰好一個的 CHECK，內容不存在時外鍵讓措施的建立回滾。貼文沒有計入旗標，公開讀取的述詞對 `post_id` 做 NOT EXISTS（`visibility.ReadablePosts`，走 `content_takedowns_post`，EXPLAIN 在 `TestTakedownPredicateKeepsTheReadPlansIndexed`）；貼文底下的留言跟著父貼文，不另寫列。每日對帳雙向核對 `seller.pub_content_takedowns()`（Go 查詢，單體規則 2 允許），不 join 它。觸發：同 `inactive_authors`。
- 批次寫入者的 stats 鎖（Q2/FDR3）：trigger 維持 row-level，必要條件是單列寫入各自求值最簡單；row-level trigger 對一批列會交錯取 stats 鎖，所以逐列寫入的批次寫入者（清除 job）一律經 `stats.Service.Lock` 依固定順序先鎖；`MarkAuthorInactive` 是一次集合呼叫 `reevaluate_*`，函式在寫入前自己依同一順序鎖整批，不需要 `Lock`（A7-1a C4-6，necessity：拿掉 `Lock` 後鎖的順序與取到的鎖都相同）。觸發：出現不能用 `Lock` 的逐列批次寫入者時，改 statement-level trigger（transition table；量測於 PG 18.6：一個 trigger 只能一個事件，所以約 9 個拆成 14 個；不能有欄位清單；WHEN 不能引用欄位值，要把 `deleted_at` 的比對搬進 body，並防 reevaluate 自己更新 `counted` 造成的遞迴；statement trigger 在零列時也會觸發）。
- 留言列表的頂層索引不排除已刪除的列：佔位項目要列出已刪除的頂層留言。
- 圖片資產 ID 是 `TEXT`（media 的資產 ID 是字串）。
