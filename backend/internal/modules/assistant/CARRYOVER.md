## 沿用盤點

ai-service 的每個機制，搬進來時都重新判斷過（遷移計畫「模組完成的定義」）：ID 方案、extension、套件、共用 helper、舊的檢查邏輯、schema 慣例、CodeMeta 的值域與錯誤碼。從零設計會不同的，完成前提出來決定。對外 API（舊 gateway 的 handler）的機制在下一節。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| ID 方案（M1）：全 TSID BIGINT（Go 端產生），ADK 表用 TEXT | Java 需要認得 ID（舊服務互通） | 否：對 Java 只有 `order_no`、`prospect_id`、`store_id`、`buyer_id` 是外部鍵（`idrefs.csv:19`），run、request、candidate 等自己的實體沒有 Java 消費者【推】 | 自己的實體用 UUIDv7（row-identity ADR）；外部鍵維持 bigint 到最後一個 Java 消費者退場（同 A6 M1） | 實體 UUIDv7；buyer、store、prospect 引用維持 bigint |
| gRPC 內部服務、method policy、metadata 注入身分（M2） | 兩個進程之間要信任邊界 | 否：單體內 session 就是身分 | 入口層（`internal/httpapi`）從 session 取身分，模組公開 API 收 `buyer.ID`、`store.ID` 參數 | 刪 gRPC 與 metadata；method policy 改為 Connect 層 interceptor 宣告（同 `adminauth`） |
| ADK v2、GORM session service、pgx（M3）：session、event 持久化在自己 4 張表 | 需要 ADK 的 agent loop 與 AG-UI 事件 | 部分：助理 coordinator 靠 ADK | 狀態機在業務表，agent loop 輕量；若留 ADK，用它的 pgx 原生儲存而非 GORM 第二套 ORM | A9-D5：保留 ADK、session 改 pgx 實作 `session.Service`，以 ADK 的 `RunServiceTests` 當驗收（`spikes.md` §1；A9-2）；GORM 不進單體。A9-2a 已實作（原在 `internal/adksession`，A9-3a 依 A9-D19 S7 抽成 `internal/platform/adksession`，表名由呼叫模組的 schema 決定，本模組傳 `assistant`；4 張表，細節見下列各列） |
| LLM SDK（M4）：Gemini 走 `google.golang.org/genai`；DeepSeek、OpenRouter 走 `openai-go/v3` 的 `/responses`；修圖手寫 HTTP | 需要多 provider 切換 | 部分：只有 `EXTRACTOR_MODEL` 一個開關；登記表 4 個、其中 gemma 是 `:free`（無 SLA）【量】 | 一個 `LLM` port 加 provider adapter；明確的 timeout、retry、budget；修圖也走同一個 port | A9-D10：只搬 Gemini、DeepSeek，不搬 OpenRouter；單一建構點與架構測試（AD5）在 A9-1c 落地，本模組只依賴該 port，不自建 client |
| 金鑰與設定（M5）：env 讀取（反射加 strict env 警告）；`GEMINI_API_KEY`、`DEEPSEEK_API_KEY`、`OPENROUTER_API_KEY`、`LLM_API_KEY` 等 | 單一進程讀 env | 否：單體有統一設定載入（`cmd/hawkr`） | 設定集中在 composition root；secret 不進 repo | 併入 `cmd/hawkr` 設定；`LLM_API_URL`、`LLM_API_KEY`、`LLM_MODEL` 全 repo 無讀取者，不搬（AD13） |
| timeout 與 retry（M6）：assistant 30s；SDK 自帶重試關掉 | 外部 provider 要有 deadline | 成立：每個外部呼叫都有 deadline【量】 | 同；加 provider 層熔斷與併發上限 | 保留並集中到 LLM 單一建構點（A9-1c）；timeout 常數與 `observability` 的直方圖 bucket 鏡像要保持同步 |
| prompt 儲存（M7）：coordinator、specialist 的 prompt 與 `return_policy.go` 以 Go 字串常數寫在程式裡 | 需要不經部署修改 prompt | 否：沒有 prompt 版本欄位；`return_policy` 有「gateway 先讀 key `return-policy`、沒有值才退 ai-service 固定文案」的過渡 | prompt 進程式碼並隨版本控管，加 eval gate；後台可改的文案走 content 模組 | 留在程式碼；`return_policy.go` 與 content 的關係在 A9 結案（Q8）；coordinator prompt 內「生鮮賣家小幫手」「食安責任」「農產品圖片」等農產文案隨 scope cut 改寫（Q4） |
| observability（M8）：OTel meter（24 個 instrument）加 Prometheus `promauto` gauge；告警規則在 repo 外 | 有 Prometheus、OTel pipeline | 單體：待定（計畫 A7 延後項說「單體告警管道」尚未建立） | 單一 metrics 入口、標籤封閉基數 | 沿用指標名（告警規則依賴），指標命名照 A9-D11（沿用 `ai_procurement_llm_*`）；等單體告警管道（Q10） |
| 用 gRPC client 取別的服務資料（M12）：tool 呼叫 buyer 與 ordering | 資料在別的服務 | 部分：buyer 已在單體；ordering 還在 Java | 模組公開 API；未搬的走 `internal/legacy/*` | buyer 換成模組 API；ordering 經 `internal/legacy` 補 client，模組只依賴 port（A9-D11；Q3） |
| fx 組裝、`pkglogger`（zap）、`syncutil.SafeGo`（M17） | 單進程 DI | 否：單體 composition root 手動接線 | 同單體規則 | 全改成 `cmd/hawkr` 接線；`go-pkg/{identity,tsid,outbox,mq,errors/bizcode,grpcclient}` 換成單體的 `platform` 對應 |
| bizcode 數字碼加 CodeMeta（M18）：例如 `9703` | 舊 REST 契約 | 否：新契約用 `ErrorReason` | `api/` 的 `ErrorReason` 加 Go 型別 | 全部轉 `ErrorReason`；`procurement_error_reason_registry_test.go` 已有註冊表概念，可沿用【量】 |
| session 表的 event 欄位（M3 的細部）：舊 GORM 版把 event 拆成約 20 個欄位 | 欄位要能被 SQL 查詢或索引 | 否：assistant 只依 `timestamp` 與 `seq` 排序與篩選，沒有任何查詢讀 event 內容欄位【量，A9-2a 的 query 清單】 | event 整份存 JSON，查詢用的欄位另存 | 整個 `session.Event` 存 `events.event`（JSONB，ADK 公開並測試過的往返編碼），`timestamp`、`seq` 另存（`id` 只是主鍵）；ADK 新增 event 欄位不需改 schema |
| 並行寫入防護（M3 的細部）：GORM 版 `AppendEvent` 比對 session 更新時間，過期就回 stale 錯誤 | 兩個 append 可能同時改同一份 state | 部分：同一對話可能同時有兩輪（重送、雙裝置）；這個防護擋「讀到舊 session 再寫」，但不阻止兩輪交錯寫 event | 寫入端用列鎖與原子合併保證不丟更新；輪次層序列化同一對話的輪次 | 不搬 stale 檢查：`AppendEvent` 鎖 session 列、state 以 jsonb `\|\|` 在 SQL 內合併，並行 append 不丟 key（CI 測試 `TestConcurrentAppendsKeepEveryStateKey`）；同一對話兩輪交錯的 event 序列由輪次執行器（A9-2b）決定是否序列化，不在儲存層擋 |
| state 的 JSON 往返（M3 的細部）：19 位 TSID 要先轉字串才不被 float64 改寫（舊 `getInt64State` 的註解） | state 經 JSON 存取 | 是：新儲存也是 JSONB，讀回的數字是 float64 | 以字串存大整數 ID | 維持：寫入 state 的 ID 一律字串（`user_id` 本身就是字串）；數字型 state 值只保證 float64 精度 |
| agent 拓撲（A9-2b-1）：buyer coordinator 加 3 個 specialist（agenttool 委派），按鈕端點直接跑 specialist | 要把「訂單、物流、問答」分給不同 prompt 與 tool 集合 | 部分：只剩訂單與物流兩個 specialist（A9-D2 刪 seller_match）；舊 ADR 實測 coordinator 27/28、all-tools 20/28【引】 | 一個 agent 掛少量 tool，或 router 加單一職責 agent | 沿用 coordinator 加 2 specialist：每輪重新建構（tool 回呼綁這一輪）；主題決定入口（訂單、物流直接進 specialist，問答進 coordinator）；不在這步重新設計 prompt（Q4 的農產文案已不在買家路徑） |
| tool 的買家身分（A9-2b-2）：從 session state 讀 `buyer_id`，值型別接受 string、int64、float64 | state 經 JSONB 往返，ID 以字串存 | 否：新儲存一律寫字串；float64 會改寫 19 位 ID | 身分取自驗證過的呼叫者，tool 不信 model 與可變 state | tool 讀 `ctx.State()`，只接受字串，且必須等於這一輪的買家（輪次由 session 登入身分決定），不符回錯、不呼叫訂單服務；int64、float64 兩個舊 session 相容分支刪除（系統未上線） |
| 事件翻譯（A9-2b-3）：`RunAssistantStream` 的 sentText 補尾巴規則、thought 過濾、tool 回應重置 | ADK SSE 模式先送 partial 再送完整回應 | 是 | 同；事件由 runner 回呼推到緩衝 | 原樣搬（characterization 鎖行為）；改變：error 之後不再送 done（proto：error 是終止事件）、tool 完成時另送 `tool_result`（只帶 tool 列舉與成功與否，不帶參數，A9-D13 修訂）、client 斷線不再取消輪次（送出是 unary，A9-D12）、finished 要求迭代正常結束且看過根 agent 的最終回應，取消、逾時與其他提早結束一律以 error 結束（A9-D15 第 4 點） |
| 空訊息與預設訊息（A9-2b-4）：按鈕端點空訊息用預設文字（訂單、物流），其餘回 InvalidArgument | 有按鈕不讓使用者打字 | 否：proto 把 `message` 標為必填，預設訊息不會被用到【推】；buyer-app 的按鈕送出的是一則真的訊息 | 入口層驗證必填，沒有隱含預設 | 已決（A9-D17 第 1 點）：刪除。handler 對空訊息（含退貨政策）回 `INVALID_ARGUMENT`（指向 `message`）；輪次執行器對退貨政策以外的空訊息仍回 `ErrMessageRequired` 當自己的防線；text 目錄的 `default_message.*` 刪除（刪前以 `rg` 確認只有執行器用）；characterization 兩份錄製以預設訊息送出的 fixture（`orders_happy_path`、`tracking_partial_detail_failure`）在測試裡補回當時的文字，比對不變 |
| 退貨政策固定文案（M7 的細部） | 退貨政策不需要 LLM | 是 | 靜態內容放目錄 | 進 `text/*.json`（zh-TW、en）；固定回覆與 coordinator prompt 共用同一個 zh-TW key（`return_policy.facts`）；不建 session，finished 帶請求的 session_id（可為空）；與 content 模組的 `return-policy` key 的關係仍在 A9 結案（Q8） |
| 輪次事件暫存（A9-D12） | 單體是單一進程 | 是 | 小量、短命的串流事件放記憶體緩衝；有界、不靜默丟事件 | 每輪只增不減的緩衝，上限 4096 個事件（A9-D15 第 5 點：寫滿時中止這一輪、以 error 終止，最後一格留給終止事件；因此沒有 cursor 過期），結束後保留 10 分鐘（常數 `DefaultBufferCapacity`、`DefaultRetention`；數字已由 A9-D17 第 2 點定案）；輪次 ID 是隨機 UUID 且須買家相符。輪次超過保留期被清掉後，訂閱回 `NOT_FOUND`（與不存在、重啟、別人的輪次同一個回應，不洩漏它存在；A9-D17 修訂，沒有「cursor 過期」）；cursor 超前回 `FAILED_PRECONDITION` + `REPLAY_CURSOR_AHEAD` |
| 同對話單一輪次（A9-D14） | ADK `session.Service` 沒有條件寫入 | 是 | 輪次層序列化同一對話 | 記憶體佔用標記，結束時先釋放再發終止事件；`Submit` 的順序是 closed 檢查、佔用、`wg.Add`（同一把鎖）、伺服器產生 session ID、寫 session，任何失敗路徑都釋放（A9-D15 第 4 點）；`runner` 的 `AutoCreateSession` 關掉：帶了不存在的 session ID 回 `ErrSessionNotFound`（舊行為會用該 ID 自動建立一個沒有 `buyer_id` 的 session，tool 之後全部失敗；疑似缺陷） |
| 輪次逾時 | 外部呼叫要有 deadline（規則：沒有 deadline 的外部呼叫不允許） | 是 | 每輪有上限 | `DefaultTimeout` 2 分鐘（A9-D17 第 3 點定案）；舊服務是 gateway 的單 turn 120 秒加 LLM 呼叫自身的 30 秒 |
| agent 回覆語言：agent prompt 寫死「使用繁體中文」回覆 | 舊服務只服務 zh-TW 買家 | 否：買家介面是 zh-TW／en | 回覆語言跟隨使用者的語言 | 已決（A9-D15 第 2 點）：以買家這則訊息的語言回覆，判斷不了才用請求語系；退貨政策固定文案與 coordinator 的退貨流程依請求語系 |
| tool 回給模型的內容（A9-2b 修正輪）：中文狀態標籤、中文提示句、下游錯誤文字（`查詢訂單失敗: %w`）原樣給模型 | 模型要看得懂結果 | 否：標籤表與 prompt 的狀態碼不一致，下游文字可能含內部位址或 stack | tool 輸出結構化代碼，語言由模型依使用者轉換；錯誤只給代碼，細節進 log | 已決（A9-D15 第 2、3 點）：`status` 是 CodeMeta OrderStatus 的代碼，狀態碼表在系統提示並由測試比對 CodeMeta；錯誤是 `tool_failed`、`upstream_unavailable`、`order_not_found`、`forbidden`、`unknown_tool`、`delegate_failed`；追蹤 tool 查「20,30,32,35,40,54」（A9-D16 第 1 點；舊的只查 20 是缺陷），每個包裹帶自己的狀態碼 |
| tool 的 panic 與錯誤處理（A9-2b 修正輪）：靠 ADK functiontool 內建 recover，錯誤文字（含 stack）原樣回給模型 | tool 內可能 panic、參數可能不合法 | 是 | 一層統一的包裝處理 panic、錯誤與可觀測性 | 已決（A9-D15 第 3 點）：`guardedTool` 包在 `tool.Tool.Run` 外層，是唯一能掛上 agent 的型別；panic stack 只進 slog、每次呼叫（含參數驗證失敗）恰好一個 `tool_result`；解碼端以 Gemini `VALIDATED`＋`AllowedFunctionNames` 防未知 tool（修訂），事後防線：模型叫了不存在的 tool 只記 log、不發 `tool_result`、模型看到 `unknown_tool` |

## 傳輸層的沿用盤點

舊 gateway 的 handler 與 gRPC 的機制，以機制為單位（認證與身分、錯誤、分頁、快取、請求大小、限流、trace、下游呼叫的逾時與重試）。新的對外 API 照〈API 設計規範（Connect）〉。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| 認證與身分：gateway 驗 Clerk token，把 `buyer_id` 放進 gRPC metadata（`WithBuyerID`）；ai-service 信 metadata | 兩個進程之間要信任邊界 | 否：單體內 session 就是身分 | 入口層從 session 取身分，handler 解析買家，模組方法收 `buyerID` | 已決（上方 M2 列、ADR 身分驗證）：`AudienceApp` 的 interceptor 要顧客帳號，`rpc.AccountBuyerID` 取 buyer_id；每支 RPC 自己再以買家驗輪次與對話的擁有者（訂閱與讀歷史也是；執行入口單獨被呼叫也擋得住越權）。送出以 `EffectWrite` 宣告（停權的帳號不能開一輪），訂閱與讀歷史是 `EffectRead` |
| 錯誤：SSE 的 AG-UI `RUN_ERROR` frame（in-band，HTTP 恆 200）；開不了串流回 HTTP 424 envelope | 舊契約是 REST＋SSE | 否：新契約是 Connect | Connect code＋`ErrorInfo.reason`＋`LocalizedMessage`；串流中途的失敗以串流內的 error 事件帶 reason | 已決（A9-D14、D15、D17、API 設計規範〈八、錯誤〉）：進行中 `FAILED_PRECONDITION`＋`ASSISTANT_TURN_IN_PROGRESS`；對話或輪次不存在或不屬於呼叫者 `NOT_FOUND`；cursor 超前 `FAILED_PRECONDITION`＋`REPLAY_CURSOR_AHEAD`；`ErrShuttingDown` `UNAVAILABLE`；空訊息、未指定主題、`client_request_id` 缺或格式錯、同鍵不同內容 `INVALID_ARGUMENT`；error 事件 reason 一律 `ASSISTANT_TURN_FAILED`，`FailureKind` 只進 log。Connect 錯誤的文字目前是 apperr 的 zh-TW 字面值（ADR 2026-10-17 的 apperr 延後組字尚未落地，與其他模組相同）；串流 error 事件的 `localized_message` 依請求語系 |
| 重送安全：舊 SSE 開不了串流不重試（有副作用的 LLM 呼叫） | 送出會花 LLM 成本、寫對話 | 是 | 冪等鍵讓 client 能安全重送 | 已決（proto、A9-D17 修訂）：`client_request_id` 以（買家，鍵）為範圍，存請求內容雜湊與 `(turn_id, session_id)`，與該輪的 10 分鐘保留期一起清除；同鍵同內容回放第一次（不看對話是否進行中），不同內容 `INVALID_ARGUMENT`；第一次受理失敗不留紀錄；同時送出同一個鍵的請求等第一個的結果 |
| 請求大小：gateway 的 BodyGuard（一般路由） | 請求可能很大 | 是 | 入口統一上限 | 沿用（API 設計規範〈十〉）：入口 `maxRequestBytes`（2 MiB）；助理的請求只有文字與圖片網址，不收圖片位元組，不另設 |
| 限流：三個 AI 路由群組曾在 gateway 豁免，後來刻意移出（`TestAIRoutesAreNotRateLimitExempt`），落在預設級別 | 送出花 LLM 成本 | 是 | 入口以身分限流；成本高的操作另設並行或額度上限 | 入口沿用預設：`AudienceApp` 級別（每分鐘 300、以登入帳號計）；另加每位買家的助理上限（A9-D18(1)）：同時進行中的輪次最多 2 輪（跨對話）、每分鐘最多送出 10 次，記憶體計數（單體是單一進程），超過回 `RESOURCE_EXHAUSTED`（沒有 reason，帶 `RetryInfo`；比照修圖的同時上限）。計數在 `turn.Executor`，常數 `DefaultMaxConcurrentTurns`、`DefaultMaxSubmitsPerMinute`；以同一個 `client_request_id` 重送已受理的請求不計入也不受上限擋；受理前失敗的送出（建立對話失敗、對話不存在、讀取失敗）釋放同時輪次的名額，也撤回每分鐘的那一次（proto 的冪等契約：第一次受理失敗不留紀錄）；兩個上限同時超過時 `RetryAfter` 取較長的。退貨政策（固定文案）只計每分鐘次數 |
| trace：gateway 注入 `traceparent` 給 ai-service | 跨進程要串 trace | 否：同進程 | 入口開 span，log 帶 trace id | 沿用入口的 `withTracing`（每個請求新 trace，`X-Trace-Id` 回應標頭，interceptor 的 log 帶 trace_id）；背景輪次用 `context.WithoutCancel` 保留 ctx 的值，請求結束後仍可帶著 trace 值寫 log |
| 逾時：gateway 單 turn 120 秒（衍生自 request ctx，client 斷線即取消上游）、每次寫入 150 秒、`: ping` keepalive；ai-service 的 LLM 呼叫自身 30 秒 | SSE 經 Cloudflare（約 100 秒 idle 斷線）與 Vercel rewrite | 是 | 長任務與連線脫鉤：伺服器端有自己的 deadline，連線只負責觀看 | 已決（A9-D12、D17）：輪次 2 分鐘上限，與連線脫鉤（client 斷線不取消輪次，所以重連可以接續）；串流每條最長 100 秒就正常結束、client 以 cursor 接續；unary 走 interceptor 的預設 15 秒。**keepalive 不搬**：proto 沒有心跳事件，窗口 100 秒取代它【推：計畫沒有明寫；靜默期最長是一個窗口，邊界與 Cloudflare 約 100 秒 idle 相同，未實測】 |
| 下游呼叫的逾時與重試：order-service 經 gRPC，共用連線加 circuit breaker（stream interceptor） | 下游可能慢或掛 | 是（ordering 還在 Java） | 每次呼叫有 deadline；失敗不拖垮上游 | 沿用 `internal/legacy/orderservice`：每次呼叫 5 秒 deadline（`timeout` 常數）、不重試（讀取由模型決定是否再問）；tool 失敗回給模型的是固定代碼 `upstream_unavailable`（A9-D15 第 3 點）；circuit breaker 不搬（單進程內沒有共用連線的雪崩問題由 5 秒 deadline 限制，【推】無量測） |
| 快取：SSE `Cache-Control: private, no-store`、`X-Accel-Buffering: no`、每 frame flush | 串流不能被緩衝或共享快取 | 是 | 回應 `private, no-store`，中介層不緩衝 | 沿用入口：`AudienceApp` 一律 `private, no-store`；`TestConnectStreamIsNotBuffered` 守串流不被中介層緩衝 |
| 分頁：舊 `sessions/latest` 回整段歷史，無分頁 | 對話歷史有大小上限 | 是：session 只增不減，讀取端要設上限【量：`history.Latest`、`adksession.Get` 的實作】 | 有界的回傳（分頁或最近 N 則） | 已決（A9-D18(2)）：`GetLatestAssistantSession` 只回最近 100 則文字訊息、不分頁（常數 `history.MaxMessages`，寫進 proto 註解）；資料庫讀取以最近 `MaxMessages*eventsPerMessage`（400）個 event 為界，tool 呼叫特別密集的對話可能不足 100 則（proto 註解有寫） |
