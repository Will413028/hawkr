# payment 模組的沿用盤點

## 沿用盤點

這個模組不是從舊服務搬來的：收款帳戶原本寫在 seller 的 `internal/payment`，後來搬到這裡（收款開通 ADR D28、D29）。下表是搬遷時照搬或改掉的機制，每一項都重新判斷過「從零設計會怎麼做」。舊的 Java payment-service 不在這次範圍（B2）。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| seller 內的 webhook inbox 表（`seller.payment_provider_events`） | 只有一個模組收 webhook | 不成立：B2、B10 也會收 provider 事件，各建一份同形狀的表 | transactional inbox 是共用的基礎設施，模組只寫業務列並標記已處理 | 不沿用；改用 platform 的 `inbox.events`（D29），payment 只登記 handler 與保存期 |
| 核准時 upsert 帳戶列（還沒有外部 ID 時以新信箱覆寫） | 核准與帳戶在同一個模組 | 不成立：帳戶在下層模組，核准的 transaction 已鎖住 seller 的列，再鎖 payment 的既有列違反全域鎖順序 | 上層只新增、下層的既有列由下層自己的 job 寫 | 改成 `INSERT … ON CONFLICT DO NOTHING`；再次核准不改信箱（規格 §8 已知限制） |
| 同步 job 直接寫閘門與防詐 hash、重新公告 | 快取與閘門在同一個模組 | 不成立：閘門、hash、公告屬於 seller | 擁有者發事件，上層以同 transaction 的訂閱者複製需要的事實 | 改成 `PayoutAccountChanged`，seller 的訂閱者寫副本、hash、公告（D12、D28） |
| 建立 job 讀店家狀態、輪詢 SQL join 店家表 | 帳戶與店家在同一個 schema | 不成立：payment 不讀 seller | 由組裝點注入擁有者查詢（依賴反轉） | `Owners.OwnerActive`；輪詢先選候選再問 |
| 擁有者鍵 `store_id` | 擁有者只有店家 | 成立（D28） | 單一擁有者時用業務鍵，第二種擁有者出現再通用化 | 沿用；不建跨 schema FK |
| 一店一個建立、一個同步 job（River 唯一鍵）、15 分鐘輪詢、冪等鍵 UUID 存在列上 | 外部呼叫在 transaction 外、事件可能遺失或合併 | 成立 | 同（Stripe 的冪等鍵與 webhook 重送建議） | 沿用；job kind 改成 `payment.*` |
| 收到事件後經 platform 的派送 job 再呼叫模組的 handler（多一跳） | 入口不能在請求內呼叫模組的處理（規則 5：commit 後才回 2xx）、platform 不認得模組的 handler | 成立：platform 只依 provider 查登記的 handler（D29），派送 job 讓 handler 失敗時由 River 重試、用完由補掃重派 | transactional inbox 由背景 worker 消化，入口只持久化 | 採用；派送 job 以 (provider, event_id) 為唯一鍵 |
| 收款事件 payload 保存 30 天（`EventRetention`） | 需要涵蓋 provider 的重送期與事後查核 | 部分成立：Stripe 重送最多 3 天；30 天是查核用的預設值，沒有法規或合約要求 | 保存期依用途訂，到期刪除 | 先用 30 天預設；觸發重新評估：需要更長的爭議／稽核追溯、或隱私政策訂出 webhook 資料的保存期時 |
| 後台待辦的成員函式在 seller（`review_payment_account_create_failed`） | 帳戶列在 seller | 不成立 | 擁有者發布 `pub_*_review_items`，reviewqueue 排序分頁 | 改由 `payment.pub_review_items` 發布；店名由後台入口組裝 |
| 手寫的 Stripe HTTP client（`internal/platform/stripe`） | 沒有官方 SDK | 不成立（D51） | 用官方 SDK | 改用 `github.com/stripe/stripe-go/v87` v87.1.0，所有呼叫用 SDK 釘住的 API 版本（`2026-10-28.endive`），不覆寫 `Stripe-Version`（D51、E1 修訂）。手寫保留的只有 SDK 不提供的：429 依 `Retry-After` 退避（最多 3 次、一次呼叫總上限 30 秒；SDK 的自動重試關掉，其餘失敗交給 River job 重試）、在 HTTP 層記下非 2xx 的狀態與本文（SDK 的錯誤型別依 API 版本與種類而異、有的不帶狀態碼，錯誤分類只看這份）、取回應本文的 `requirements` 原始 JSON（SDK 型別只保留它認得的欄位）、webhook 簽章時間戳的容忍（SDK 只拒絕過舊的）、`CloseAccount` 對已關閉帳戶的 403 改讀帳戶確認；webhook 簽章只用 SDK 驗證，SDK 只拒絕過舊的時間戳、不拒絕未來太遠的時間戳（舊手寫版兩邊都拒），簽章之後只讀 `id`、`type`、`related_object` 不用 SDK 的型別化結構 |
| 收款帳戶快取整列覆寫、不比時間 | 同一帳戶同一時間只有一個同步（River 唯一鍵） | 不成立：賣家端的同步重讀在 job 之外呼叫外部讀取，與同步 job 並行（D32、D49） | 以讀取開始時間做樂觀條件，較舊的讀取不覆蓋較新的 | `ApplyPaymentSnapshot` 只有讀取開始時間不早於已存的 `fetched_at` 才寫；被擋下的那次不標記 inbox 事件、不發 `PayoutAccountChanged`。必要條件是有 job 以外的同步呼叫；那個呼叫拿掉時，條件一起拿掉 |
| 賣家與管理員觸發的重讀名額（`seller_read_claimed_at`，10 秒） | 外部讀取由賣家或管理員觸發，頻率不受 job 唯一鍵約束 | 成立（D33） | 對由使用者觸發的外部呼叫限頻 | 在讀 provider 之前以條件式 UPDATE 搶名額，失敗與並行的讀取都占名額，名額內依 `fetched_at` 回成功或 `ResourceExhausted`（帶剩餘秒數）。`httpapi` 的限流器是傳輸層行程內的固定時間窗計數（`internal/httpapi/ratelimit.go`），不看帳戶列上的讀取結果；這裡的回答要看快取是否已涵蓋占名額的讀取，所以名額放在帳戶列。呼叫拿掉時，名額與該欄一起拿掉 |
| 快取存 `requirements` 的原始 JSON | 補件內容只用來顯示，狀態不從它推導 | 成立（D13） | 開通完成看 `stripe_transfers.status`，`requirements` 只用來顯示要補什麼 | 整份原樣存（非物件的值存成 `{}`，`accounts_requirements_check`），只有後台經 `httpapi/payment` 轉成公開條件（`requirements()` 不匯出，賣家端的 `PaymentAccount` 不帶 `requirements`）；不另建欄位表，Stripe 增減條目不需要 migration |
| 記憶體內的 fake provider | 本機與測試要在沒有真的金流商時走完開通 | 成立 | 以 fake 取代外部服務，正式環境不可選 | `PAYMENT_PROVIDER=fake` 只在 `requireDevEnvironment` 成立時選得到（有 `DEV_AUTH_KEY_FILE` 且沒有 Cloudflare Access 設定），否則啟動失敗（`cmd/hawkr/payment.go`）；每個呼叫檢查不在 DB transaction 內且有 deadline（規則 5），`AutoActive` 讓不認得的外部帳戶也回轉帳已啟用 |
| 核准時把聯絡信箱複製到帳戶列（`contact_email`） | 帳戶還在 seller，核准與建立在同一個模組 | 不成立（D50，修訂 D23） | 下層不存上層個資的副本，需要時向擁有者讀 | 欄位刪除；`Owners.OwnerContactEmail` 在建立外部帳戶的當下讀擁有者目前的信箱，讀不到時不建立、記成建立失敗（永久失敗，補填後由管理員重試）；建立分兩步（D55）：第一步只帶 `metadata.store_id` 與列上的冪等鍵，信箱在第二步的更新寫入，所以信箱換了也不會 `idempotency_error` |
| 結果未知的建立請求放超過 Stripe v2 冪等鍵的保存期（30 天）再重試 | 冪等鍵保存期內同一把鍵回同一個帳戶（D55） | 部分成立：超過保存期同一把鍵會建出第二個帳戶 | 以 `metadata.store_id` 對帳，找出並關閉多出的帳戶 | 已處理（D63，9g，取代 D59 的列出對帳）：列上有「已呼叫」時刻（`create_called_at`），「呼叫過、沒有外部 ID」的列由週期掃描（`payment.account_resolve`，不論擁有者是否營運中、是否等待清理或已記建立失敗）以同一把鍵重送取回 ID；7 天（`UnresolvedDeadline`，小於保存期，任何重送都在保存期內）仍了結不了就進終局：非清理的列記建立失敗進待辦，清理的列進 `purge_blocked`（`unresolved_creation`）；自動的路徑之後不重送、不換新鍵、不列出帳戶（v2 帳戶列表不能依 metadata 篩選、最終一致，列出全平台帳戶在約 1000 個帳戶以上失效）。管理員「重試建立」：保存期（30 天）內以同一把鍵重送（不確認、不換鍵、已呼叫時刻不變，取回 ID 後接續建立），超過保存期的列等於聲明金流商那邊沒有這家店的帳戶：要明確確認（`acknowledge_no_provider_account`），才換新鍵並重設已呼叫時刻；兩種都寫後台紀錄。`metadata.store_id` 與 `metadata.hawkr_namespace`（`STRIPE_ACCOUNT_NAMESPACE`）照寫，之後做全平台孤兒帳戶稽核不必回填。觸發重新評估：出現第一筆因逾期進終局的列，或上線前要做孤兒帳戶稽核（排程的全平台對帳，游標落庫）；推翻條件：Stripe 為 v2 帳戶提供 metadata 篩選，或實測同鍵重送拿不回原帳戶 |
| `provider` 欄位：帳戶列記下建立它的 provider | 同一個部署同時只設定一個 provider，但列要知道外部 ID 屬於誰 | 成立 | 外部 ID 與 provider 一起存，唯一鍵含 provider | 列的 provider 與目前設定不同時，同步、建立與重新整理略過它，賣家端重讀回 `FailedPrecondition`，清理不關也不刪、記警示 log（列在清理 job 的第一步已標 `purge_pending_at`）；舊列沒有自動搬遷或重建的去向，換 provider 的流程還沒有設計。觸發重新評估：接第二家金流商時 |
| 清理的永久失敗沒有終局狀態 | 金流商回報帳戶不存在、或列的 provider 沒有設定時，關不掉也不能刪列 | 部分成立：分不出「帳戶真的不存在」與「金鑰指向另一個 sandbox」，所以不刪對應 | 有終局狀態或人工處理入口 | 已處理（D59、D60，9g）：永久拒絕立即、其餘從標成等待清理起 7 天（`PurgeDeadline`）仍關不掉或問不到 provider，列標 `purge_blocked_at` 與原因進終局，週期掃描與清理 job 不再處理（沒有設定 provider 時掃描仍重排等待清理的列，呼叫過 provider 的列才會在期限後進終局；`TestSweepWithoutAProviderRequeuesPurgeAndTheRowReachesTheTerminalStateAfterTheDeadline`），後台待辦 `PAYMENT_ACCOUNT_PURGE_STUCK`，管理員「重試關閉」（清除終局、期限重算）或「已在金流商處理，刪除對應」（寫 platform 的 `adminaudit` 紀錄、刪列，權限 `payment.accounts.delete_mapping`，D62）。沒有終局之前的限制不再成立。永久拒絕不含 Stripe 的 401、403（金鑰或權限設定問題，維持可重試到期限）；結果不明逾期（`unresolved_creation`）也進終局，這種終局在冪等鍵保存期內可重試關閉（同一把鍵取回 ID 再關閉；重送期間 `purge_replay_requested_at` 擋下刪除對應與再次重試），超過保存期不能；job 自己被取消不記成 `deadline_exceeded`（細節見 `backend/docs/modules/payment.md` §2） |
| 同步讀到已關閉的外部帳戶沒有終局狀態 | 已關閉的帳戶讀取時回應沒有 `stripe_transfers` 能力，adapter 回一般錯誤，同步 job 當成暫時性失敗重試（sandbox 實測 2026-11-14） | 部分成立：清理是關閉後就刪列，正常讀不到；帳戶在金流商那邊被關閉時才會遇到 | 讀取分辨「已關閉」並把列帶到終局狀態或人工處理入口 | 已處理（D61，9g）：adapter 在讀取時看 `closed`（先於能力檢查，不再讀銀行帳號），回 `Snapshot.Closed`；`StatusOf` 推導成 `DISABLED`、原因碼 `closed`（`ReasonClosed`），轉帳能力關閉並照常發布 `PayoutAccountChanged`；輪詢的 SQL 把原因碼 `closed` 視為終局，不再排同步。原因碼只給後台，沒有新的對外列舉值或賣家文字（賣家看到的是 `DISABLED` 的既有目錄文字）。不經輪詢的明確動作（webhook 事件、賣家與管理員的重新整理）仍會重讀，結果相同 |
| 帳戶列的建立事實：第一次呼叫前記 `create_called_at`、第一步拿到外部 ID 就寫、第二步成功才記 `create_completed_at`（「已建立」「可開通」「輪詢」「同步」看它，不看有沒有外部 ID） | 建立是兩次對外呼叫、外部呼叫不在 transaction 內，兩次之間與回應遺失都可能中斷；冪等鍵會過期 | 成立（D55、D59） | 外部副作用先記意圖（outbox），拿到結果立刻存，完成與否用單獨的事實表示 | 欄位約束（`accounts_created_check`、`accounts_snapshot_check`、`accounts_create_failed_check`、`accounts_completed_check`、`accounts_called_check`）以 `create_completed_at` 判斷；半建立的列對外仍是 `NOT_CREATED`；不另建 outbox 表，意圖就是列上的 `create_called_at`。必要條件是建立分兩步，改成一步時三個欄位與約束一起拿掉 |
| 對帳不列出帳戶（D63 刪除 `ResolveAccount`、列出帳戶、多帳戶關閉、換鍵與列表安全間隔） | 結果不明的列由持有的冪等鍵在保存期內取回；全平台列出在帳戶數大時失效（v2 帳戶列表不能依 metadata 篩選、最終一致） | 成立（`/code-review` 與 Stripe 文件，2026-11-14） | 以不變的業務鍵對帳 | 已處理：只在 7 天內以同一把鍵重送（`AcquireAccount`），不列出；`platform/stripe` 的 `ListAccountIDsByStore` 與兩個列表 fixture 一併刪除。觸發重新評估見上一列 |
| 清理終局（`purge_blocked_at`、`purge_blocked_reason`）與後台待辦 `PAYMENT_ACCOUNT_PURGE_STUCK`；後台動作的紀錄改在 platform `adminaudit`（D62，取代 payment 自有的 `account_mapping_deletions`） | 關閉會被金流商拒絕或 provider 長期問不到，要有人處理，且處理（刪對應、重試）要留下是誰做的 | 成立（D59、D60、D62） | 終局狀態加人工處理入口、不可逆動作留稽核紀錄 | 期限 7 天（`PurgeDeadline`）；管理員兩個動作各有權限；紀錄由 platform 保證與領域變更同 transaction，讀取端是 `cmd/hawkr` 的 `admin-audit`（沒有畫面）；`account_mapping_deletions`、`MappingDeletions` 已刪。觸發重新評估：第二位管理員（檢視畫面），或需要紀錄不可被資料庫管理員改寫時 |
| 輪詢補漏（15 分鐘）對所有未啟用的帳戶，沒有年齡上限或退避 | 事件可能遺失，要有補漏 | 成立 | 輪詢加上限或退避 | 沿用，不設上限。觸發：上線前定上限 |
| `inbox.events` 的未處理事件永不刪、沒有終局狀態 | 目前只有收款帳戶一個 handler，補掃重派到被處理為止 | 成立（只有一個 handler） | 事件有終局狀態（死信），到期後移出補掃 | 沿用：`Purge` 只刪已處理而且過了保存期的事件，未處理的由補掃或模組的掃描處理，每個新 handler 要自己補掃。觸發：第二個 handler 接上 inbox 時 |
| 付款事件的 handler 只排同步 job、不標記已處理，同步重讀後標記讀取開始前收到的事件（account 的做法，D29）；付款以付款 ID 為唯一鍵 | 事件只是「這個物件變了」的訊號；Stripe 事件可能亂序、重複、遺失；handler 在派送 job 的 transaction 內不能呼叫 provider | 成立（3a） | 重讀物件而不信事件內容（Stripe 文件對 webhook 的建議）；handler 只入列 | 沿用，鍵換成付款 ID（UUID）。守門：`TestTheEventHandlerNeverTrustsTheEventContent` |
| 呼叫過、沒有外部 ID 的列在期限內以同一把冪等鍵重送，超過進終局，不換鍵（account 的 D63，期限 7 天） | provider 只保證冪等鍵在保存期內回同一個結果，超過的鍵重送可能建出第二個物件 | 部分成立：只在「不明的物件沒有搬錢」時安全，建立 PaymentIntent 尚可，轉帳、撤回、退款不成立 | Stripe 的冪等鍵至少保存 24 小時；四種搬錢呼叫統一：確定失敗換新鍵、不明只查回才收斂（Stripe 文件 Idempotent requests、Error handling） | 不沿用期限後進終局（D10、ADR D68）：`ResendWindow` 23 小時內同鍵重送、之後只查回（`Find*`，依嘗試 ID），查無再滿 `NotFoundAfter`（24 小時，等於保存期）才 FAILED，與 provider 不符或查回連續失敗（`LookupFailureLimit`）進 `ANOMALY`；常數的編譯期檢查是 `ResendWindow` 小於 `IdempotencyRetention`。終局的列在買家再次建立時換新鍵重設（原 PaymentIntent 從沒交到 client 手上，不會被付款） |
| 冪等鍵存在列上、寫列時由資料庫產生的 UUID（account 的 D59） | 每次重送要同一把鍵，而且不能從業務鍵推導（共用 provider 帳號的兩個環境不能撞） | 成立 | 隨機 UUID 存在請求的紀錄上 | 沿用：`payments.create_idempotency_key`；轉帳 `transfers.idempotency_key`（3b）、退款撤回 `refunds.reversal_idempotency_key`（3b）、退款 `refunds.idempotency_key`（3c）各有自己的鍵欄位，同一把鍵每次重送都沿用 |
| 轉帳與撤回的「呼叫過、結果不明」：呼叫前記 `transfers.called_at`／`refunds.reversal_called_at`，期限內同鍵重送，超過進 FAILED（`unresolved_transfer`、`unresolved_reversal`） | provider 只保證冪等鍵在保存期內回同一個結果；轉帳與撤回重送錯會多轉、多撤 | 不成立：FAILED 讓出 `transfers_active_payment`，provider 那邊其實已轉帳時之後的 `RequestTransfer` 會重複撥款；平台餘額不足也被算成結果不明 | 結果三分（成功、確定失敗＝可重試／終局、不明），換新鍵前以強一致查回證明上一次不存在，異常進對帳例外佇列 | 改成 D68：`ErrRetryableRefusal` 換新鍵（`transfers.idempotency_key`、`refunds.reversal_idempotency_key` 換掉並清 `called_at`，同時是嘗試 ID）、不計期限；不明同鍵重送到 `ResendWindow` 後查回；`ANOMALY` 佔住 `transfers_active_payment` 與退款額度、補掃跳過、發 `MoneyAnomaly`，後台以 `ResolveAnomaly` 人工結案（同 transaction 寫 adminaudit，Connect 端點在步驟 5）。`unresolved_*` 終局原因已移除；轉帳與撤回在 charge 內各自實作、不抽共用 |
| Java 的轉帳 job 以訂單為單位撥款（PayUni 撥款對帳） | PayUni 是批次撥款 | 不成立（D1：SCT，付款帶 `source_transaction` 逐筆轉帳） | Stripe separate charges and transfers | 不沿用：一筆付款最多一筆有效轉帳（`transfers_active_payment`），金額是付款扣掉非失敗退款 |
| 平台餘額不足視為失敗 | 轉帳需要平台餘額 | 不成立（spikes #8：帶 `source_transaction` 仍會因平台總餘額不足被拒，補錢後重試成功） | 可重試錯誤 | 一般錯誤，job 重試、PENDING 不變；賣家負餘額不是錯誤（#9），撤回沒有餘額分支 |
| 付款列主鍵（account 用業務鍵 `store_id`） | 付款是被 API、事件與 job 指稱的實體 | 成立 | row-identity ADR D1：實體用應用層產生的 UUIDv7，不設 DEFAULT；給人看的訂單號另開唯一欄 | 不沿用 account 的鍵形：`payments.id` 是 UUIDv7，`order_no` UNIQUE 守「一張訂單一個 PaymentIntent」（D8）；`refunds`、`transfers` 同樣是 UUIDv7 |

| `inbox.events` 的未處理事件永不刪（上表末列的觸發：第二個 handler 接上 inbox） | 每個 handler 要自己補掃 | 觸發了：charge 是第二個 handler | 事件有終局狀態（死信） | 仍沿用：charge 有自己的補掃（久未讀的未結案付款、有舊的未處理事件的付款，`payment.charge_sweep`），沒有 payment 無法處理的事件類別留在 inbox；死信延後。觸發：3b、3c 加入退款與轉帳事件的 handler，或上線前 |

|---|---|---|---|---|
| 後台的 3 支收款帳戶 RPC 在 `SellerAdminService` | 帳戶在 seller | 不成立 | 資源的 API 在擁有者的 service | 搬到 `hawkr.admin.payment.v1alpha1.PaymentAdminService`，權限改成 `payment.accounts.*`（D30） |
| 賣家端的 `GetMyPaymentAccount`、`CreatePaymentOnboardingSession` 在 `SellerAppService` | 要先確認呼叫者是店家擁有者 | 成立：payment 是葉節點，不能向上讀 seller 驗證擁有者 | 擁有者驗證留在上層的入口 | 沿用；seller 的 handler 確認店家後呼叫 payment（D30） |

## 與 舊服務的差異

- 系統未上線，資料沒有搬移：seller 的 `payment_accounts` 與 `payment_provider_events` 刪除，`payment.accounts` 與 `inbox.events` 是新的 baseline。
- 後台 RPC 的 service 與權限名稱改變（見上表）；admin 同一次更新。
- 付款（3a，B2）：Java 在 transaction 內呼叫 order gRPC、PayUni 與寫列同一個 transaction；改成 transaction 外讀訂單、寫列與補做 job 一個 transaction、提交後在請求內建立 PaymentIntent（D7 修訂）。
- 付款一張訂單一列、同時只有一個有效的 PaymentIntent（D8 與補充；`CANCELED` 且訂單仍可付時同一列換新鍵重設，舊嘗試留在 `payment_attempts`，舊 PaymentIntent 晚到的成功仍對得到列，兩個都成功記重複入帳、不自動退款）：Java 的嘗試序號、換付款方式與復活舊列都不存在；`CreatePayment` 重送回既有的列。
- 零元訂單：Java 直接記 PAID；3a 回 FailedPrecondition（Stripe 不能收零元），由訂單一方在步驟 4 決定怎麼完成零元訂單。卡片金額上下限（1–199,999）是 PayUni 的限制，不搬；provider 對金額的拒絕是永久失敗，進 CREATE_FAILED。
- 付款失敗：Java 的 FAILED 是終局；Stripe 的失敗嘗試讓 PaymentIntent 回到等待付款，列只記 `last_error`，買家在同一個 PaymentIntent 上重試。重複付款、過期列的 CONFLICT 與 rescue 退款不存在（D5 修訂：訂單一方判斷並發起自動退款）。
- 逾期付款的取消（Java 的 `ExpiredTransactionScheduler`）與 `ClosePaymentByOrderNo`：port 與 fake 有 `CancelPayment`，use case 與逾期 job 在步驟 4；3a 沒有。
- 付款成功事件給訂單：`PaymentChanged`（狀態改變才發，含 `Previous`），取代 Java 的 outbox `payment.success`／`payment.failed`；relay 與路由鍵在步驟 4。
- 轉帳與撤回（3b）：`RequestTransfer`（訂單完成後入口，步驟 4 的 `GrantPayment` 呼叫）在 transaction 內只寫 PENDING 轉帳與 job；`Transfer`、`Reverse` 是 job 本體（`payment.transfer_create`、`payment.transfer_reversal`）。3b 不發轉帳事件（沒有消費者；步驟 4 的 relay 需要時再加）。撤回成功後退款停在 `REVERSED`，3c 的退款 use case 要在同一個接點（`Reverse` 的寫結果 transaction）接上「排退款呼叫」；3c 寫 `REVERSING` 列時必須設定 `reversal_amount` 並在同 transaction 呼叫 `EnqueueReversal`，且 `reversal_amount` 不得超過轉帳的剩餘可撤額度（超過是 `ErrAnomaly`）。

- 結果不明的收斂（3a′，D10）：3a、3b 審查的清單全數處理——不明不再讓出唯一索引（L1、L2）、不符與前置條件異常進 `ANOMALY`（L4、L5）、孤兒的撤回結果記 error log 並發 `MoneyAnomaly`（L6）、掃描有 partial index（L7）、`transferTerms` 的 DB 錯誤立刻返回（L8）、`Transfer`、`Reverse`、`Create` 拒絕在 transaction 內呼叫（L9）、註解不寫步驟與 spike 編號（L10、L11）。人工結案的語意（`ResolveAnomaly`）：付款的成功是連上證據的 PaymentIntent、暫記 `AWAITING_PAYMENT` 並排同步，真正的狀態由重讀推導；退款只處理撤回階段的 `ANOMALY`（成功＝撤回成立，記撤回 ID、累加轉帳的 `reversed_amount`、進 `REVERSED`），退款階段的 `ANOMALY` 與結案由 3c 補。
