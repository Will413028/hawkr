# agent 模組的沿用盤點

從 seller-service 沿用的 vendor portal 機制重新判斷的結論（遷移計畫「模組完成的定義」），以及與 seller-service 的差異。模組現行的職責、資料與不變量在同目錄的 `AGENTS.md`。依據是 7d 開工時的盤點（缺陷 D1 至 D10）與 ADR `docs/adr/2026-10-03-vendor-portal-invite-scoped-access.md`（下稱 ADR）。

## 沿用盤點

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| `vendor_portal_identities`：每個 prospect 一筆，帶 email 快照與 `status`（ACTIVE、REVOKED） | 存取範圍要有一個擁有者；撤銷要有地方記 | 不成立：存取範圍本來就是單張邀請，identity 只帶 email 快照，`REVOKED` 從沒被寫過（D5） | 存取權綁定單一資源，敏感動作再驗證身分（DocuSign 每份文件每個收件人各自驗證；Coupa 供應商不需帳號） | 拿掉 identity 表（ADR「身分與 session 的範圍」）：邀請存 `prospect_id` 與寄出時的 email 快照，session 與驗證都綁單張邀請；需要長期往來的供應商帳號等 A9 有需求時從 prospect 建立 |
| 邀請單次兌換（`consumed_at` 以 CAS 搶） | 被轉寄的 bearer 連結不能被重複使用 | 不成立：單次兌換沒有比較安全（被轉寄的人先點一樣進得去），卻讓業者換裝置、cookie 過期或 session 被撤就進不來，而且沒有重寄的路徑 | 多日的商業文件用到期前可重複使用、可撤銷的連結，敏感動作再驗證（DocuSign、Coupa）；單次 magic link 是 15 分鐘的登入用途 | 可重複兌換到到期或撤銷（ADR「邀請連結」），沒有 `consumed_at`；每次兌換發新 session，正式送出仍要驗證 email（步驟 8 檢查）；`TestExchangeIsReusableAndEverySessionIsNew` |
| 兌換時撤銷同一個 identity 的全部 session | 新登入取代舊登入 | 不成立：identity 以 prospect 為鍵，同一個業者兩張 RFQ 時點第二張會踢掉第一張已驗證的 session | session 屬於它的資源，不跨資源互踢；每個資源的同時登入數設上限 | 兌換不撤銷任何既有 session，只在同一張邀請的有效 session 超過 5 個時，在同一個 transaction 撤銷多出來的（邀請列加鎖，併發不會交錯）：候選排除本次新發的 session，先撤最舊的未驗證，全部都已驗證才撤最舊的（拿到轉寄連結的人兌換 5 次，擠不掉業者已驗證的 session；ADR 2026-10-04 修訂）；`TestExchangeCapsSessionsPerInviteAndLeavesOtherInvitesAlone`、`TestConcurrentExchangeKeepsTheCap`、`TestExchangeOverCapKeepsTheNewSessionAndRevokesTheOldestVerifiedWhenAllAreVerified`、`TestExchangeOverCapRevokesTheOldestUnverifiedFirst` |
| 兩段式 Ensure（回傳明文 secret）加 Mark（標記寄出）與 `secret_delivered_at`，寄出後鎖死 | 明文 secret 要在信寄出前拿到；notification 與 ai-service 分別在 A8、A9 才搬進單體，寄信與建立邀請不能同一個 transaction | 成立（到 A8 為止） | 建立邀請與寄信同一個 transaction 加 transactional outbox，沒有兩段式 | 保留兩段式給 notification（ADR「Ensure／Mark」），觸發條件是 A8 notification 搬進單體：改成 transaction 加 outbox，拿掉 `secret_delivered_at` 與換 secret 的邏輯。結果分開：已寄出 `ErrInviteAlreadyDelivered`、已撤銷 `ErrInviteRevoked`、prospect 不是進行中 `ErrProspectNotActive`、沒有可寄的 email `ErrNoDeliverableEmail`（舊實作把已兌換或已撤銷的還沒寄出邀請說成「已寄出」，邀請無聲地不寄，D2）。Mark 帶寄出的那一把 secret，只有它仍是目前的 secret 才標記（單一條件 UPDATE），過時的回 `ErrInviteSecretSuperseded`，同一把重送冪等（`TestMarkInviteDeliveredIgnoresASupersededSecret`、`TestMarkInviteDeliveredRacesWithRotation`）。**同一把 secret 重寄目前做不到**：Send 成功、Mark 失敗後的重送會換 secret，先寄出的信失效。可以做到的兩條路是在 Mark 之前加密保存 secret，或用伺服器金鑰從邀請推導 secret，兩者都讓寄出之前有一把可還原的 secret 躺在資料庫（現在只有 SHA-256，資料庫外洩不能還原），而 A8 的 outbox 讓建立與寄信同一個 transaction，兩段式本身就消失，所以不為這幾個月的視窗付這個代價；觸發條件 A8；legacy gRPC 的映射在 `internal/legacy/sellerserver/errors.go`、Mark 帶 secret 在 `invites.go` |
| `EnsureInvite` 沒有 transaction（D1）：identity upsert 與 invite insert 分開，併發的第二個 INSERT 撞唯一鍵回 Internal | 同一個 RFQ 收件人的併發呼叫（MQ 重送、多 consumer）要正確 | 成立 | 以資料列鎖或 upsert 序列化，唯一鍵衝突不外漏 | 一個 transaction：`SELECT … FOR UPDATE`，沒有就 `INSERT … ON CONFLICT DO NOTHING`，輸的一方改鎖既有列走 rotate；`TestEnsureInviteConcurrentCallsNeverSurfaceAUniqueViolation`。Send 成功但 Mark 失敗後的重送會再換 secret，先寄出的信失效：見上一列（同一把 secret 重寄的取捨），記在 `docs/modules/agent.md` §10「已知限制」。併發的 Ensure 與 Mark 由邀請列鎖與 Mark 的條件 UPDATE 序列化，不會出現「標記寄出但寄出的連結已失效」 |
| token 格式與雜湊：32 bytes 亂數轉 hex，DB 存「hex 字串」的 SHA-256 的 hex（varchar 64），無 salt | 不透明的 bearer secret，資料庫外洩不能還原出可用的 secret | 成立 | 256 位元亂數存 SHA-256，不需要 salt 或 HMAC（OWASP session 管理）；URL 用 base64url | 32 bytes `crypto/rand` 的 base64url（無 padding，43 字元，連結較短）；存原始 bytes 的 SHA-256（`bytea`，CHECK 長度 32、UNIQUE）；查詢以 hash 為鍵所以不需要常數時間比較；解碼不是剛好 32 bytes 的標準編碼就不查資料庫。保留的優點：secret 放在連結的 fragment、用 POST 兌換，信件掃描器的預取不會消費邀請（步驟 8、website） |
| server-side session 表，每個請求一次資料庫往返（ValidateVendorPortalSession RPC） | 對外部業者要能撤銷、有 idle 與絕對期限；舊的往返是跨服務 RPC | 撤銷的需求成立；RPC 的成本不成立（in-process） | 不透明 token 加伺服器端狀態（可撤銷）；簽章 token 無法撤銷 | 保留 session 表；`ValidateSession` 是一個函式呼叫加一個 statement，不再有 RPC；不改簽章 token |
| idle 24 小時、絕對 7 天、`Touch` 節流 5 分鐘且錯誤被吞（D7） | 外部業者的 session 要有界；節流避免每個請求寫一次 | 成立（期限）；吞錯誤不成立 | idle 滑動加絕對上限，寫入節流 | 期限沿用（ADR）；滑動與驗證在同一個 statement（CTE），寫入失敗就是 `ValidateSession` 失敗，不吞；絕對期限被邀請的到期截斷，session 不會比邀請活得久（idle 不超過絕對期限，CHECK）；`TestValidateSessionSlidesIdleWithAThrottle`、`TestSessionNeverOutlivesTheInvite` |
| Google step-up：`assurance`（`INVITE_ONLY`、`GOOGLE_VERIFIED`）存在 session，只支援 Google，比對 identity 的 email | 正式送出是不可撤回的商業承諾，要證明持有被邀請的信箱 | 成立；只有 Google 與比對對象（identity 而非邀請）不成立（D10） | 寄一次性驗證碼到該信箱（email OTP）證明擁有信箱，Google 是捷徑 | 改成驗證紀錄：`verification_method`（現在只有 `GOOGLE`）、`verified_email`、`verified_at` 三者同有同無，綁單一 session；比對對象是邀請寄出時的快照（邀請寄到哪就驗哪，prospect 之後改 email 不影響），去前後空白、不分大小寫，在單一條件 UPDATE（CAS）內；相同 email 重送冪等；Google token 由步驟 8 經 identity 驗證，模組只收已驗證的 email；email OTP 的寄送與畫面在 A8（ADR「email 的驗證方式」）。補上舊實作缺的 repository 層測試（大小寫與空白、過期與撤銷的 session 不被救活、已驗證不被覆蓋）：`TestVerifySession*` |
| 兌換與預覽的限流 key 是 `sha256(secret):ip`（D3）、Google 驗證沒有專屬限流（D4）、Redis 掛掉退回進程內（degrade-open） | 限制濫用與資源消耗（每次兌換寫 session、每次驗證打 Google 公鑰）；不是為了擋猜 secret：secret 是 256 bits 亂數，無法猜中 | 需求成立；key 不成立（換 secret 就是新 key，完全不受限） | 以來源（IP）為 key，驗證端點專屬限流；全域失敗率只在有分散式濫用時才需要 | 屬於入口，模組不做（ADR「後果」）；入口（步驟 8i）在 `internal/httpapi/ratelimit.go` 以來源為 key：預覽與兌換共用一個計數器，每個來源 5 分鐘 20 次（不是各 20 次），`VerifySession` 另計，每個來源 10 分鐘 10 次；`TestVendorPortalInviteProceduresShareOneQuota`、`TestVendorPortalVerifyIsLimitedToTenPerTenMinutes`。全域失敗率：不需要，限流是每來源、secret 有 256 bits；重新評估的觸發：出現分散式濫用的證據，或 CD 加上 CDN 層的限流。模組這一側只保證不洩漏成因（錯誤一律不分原因） |
| `expires_at` 不驗證（D6）：過去的時間產生立刻失效卻照寄的邀請，過遠的時間產生長效 bearer | 邀請的壽命要有界 | 不成立 | 在建立端驗證壽命上限 | `ExpiresAt` 必須晚於現在、不超過現在起 180 天，否則 InvalidInput（ADR）；`TestEnsureInviteValidatesExpiry`。上限是一個保守的固定值：180 天比舊實作實際用的值（回覆截止日加 7 天，無截止日 30 天）寬，給 RFQ 的回覆期留餘地，又讓外洩的 bearer 連結不會無限期有效。這是在沒有 RFQ 截止日可用時的代用品：A9 採購搬進單體後，邀請在 RFQ 發布的 transaction 內建立，到期時間改由 RFQ 的截止日推導（加上寬限），固定上限屆時拿掉或改成保險絲。觸發條件 A9 |
| 沒有任何寫入者撤銷邀請（D5） | prospect 被封存或合併、買家取消時，既有連結與登入要失效 | 不成立：舊實作只能等 TTL | 資源狀態改變時在同一個 transaction 撤銷存取 | seller 在封存的 transaction 內發 `ProspectArchived`，agent 的 handler 在同一個 transaction 撤銷該 prospect 的邀請與 session，記下原因；`cmd/hawkr/agent_events.go` 接線；撤銷不可逆，還原不復活。**合併不撤銷**：`ProspectMerged` 的 handler 把輸家的邀請改掛贏家（`prospect_id` 改成 target，email 快照、secret、session、驗證都不動），之後贏家封存才撤銷；理由是業者進行中的詢價不該因為 BD 整理名單而中斷（MDM survivorship，Salesforce、HubSpot 的 duplicate merge 改掛子記錄），與 seller 把比對鍵改掛贏家一致（ADR「合併時的邀請」）。`rfq_recipient_id` 是 UNIQUE，改掛不會與贏家既有的邀請衝突。買家取消 RFQ 發布時撤銷等 A9。`TestProspectArchivedRevokesItsInvitesAndSessions`、`TestProspectMergedRepointsTheSourceInvitesToTheWinner`、`TestProspectArchiveAndMergeRevokeVendorPortalAccess` |
| `EnsureInvite` 不檢查 prospect 的狀態（`seller.ProspectContact` 任何狀態都讀得到） | 封存之後不會再冒出有效的邀請 | 不成立：封存的撤銷只撤銷當時存在的邀請，之後才建立的邀請沒有人撤銷 | 建立存取權的動作與資源狀態的改變序列化（讀取帶鎖，或把狀態檢查放進同一個條件寫入） | Ensure 在自己的 transaction 內以 `seller.ProspectContact` 讀 prospect，那一列帶 `FOR SHARE`（與封存、合併的 `FOR UPDATE` 衝突）：讀到進行中之後封存要等 Ensure 提交，之後它的撤銷會撤掉這張邀請；封存先到則讀到非進行中，回 `ErrProspectNotActive`（封存、被合併、已轉成店家一律）。鎖的順序固定 prospect 再邀請，與封存一致，不互鎖。只有一個 API（`ProspectContact` 加 `Status`），transaction 外呼叫時等於普通的讀取。既有邀請掛的 prospect 與輸入不同時 InvalidInput，不改任何東西。`TestEnsureInviteRequiresAnActiveProspect`、`TestEnsureInviteRejectsAnotherProspectsRecipient`、`TestProspectContactInTransactionBlocksArchiveUntilCommit`、`TestProspectArchiveAndMergeRevokeVendorPortalAccess`（併發封存） |
| session 的驗證紀錄（方式、email、時間）綁在 session 上，隨 session 清理 | 正式送出是不可撤回的商業承諾，事後要能證明誰在何時以哪個信箱送出 | 成立；但 session 是會被清理的授權狀態，不是證據 | 電子簽署的慣例：證據跟著簽署的文件保存（DocuSign 的 Certificate of Completion） | session 上的紀錄只用於授權；證據在送出、撤回、婉拒時由入口以 `X-Vendor-Portal-*` header 帶著 session 的驗證紀錄（方式、email、時間、session ID）交給 gateway，再轉給 ai：送出存在不可變的報價版本列，撤回與婉拒存在 ai 只追加的指令紀錄（ADR「驗證的證據」與 2026-10-04 修訂）。模組這一側的義務是 `ValidateSession`、`VerifySession` 的 `SessionInfo` 交出 `SessionID` 與 `Verification{Method, Email, At}`（`TestSessionInfoCarriesTheVerificationEvidence`） |
| 三張表沒有清理，`invited_email` 永久保存（D8） | email 是個資，不留超過需要的時間 | 不成立 | 設保留期限，由排程清理 | 每天一個 River job（啟動即執行）：絕對期限過了超過 7 天的 session；到期或撤銷超過 90 天的邀請連同 email（session 由 CASCADE 帶走）；分批、每批一個 transaction；`TestPurgeDeletesOnlyWhatIsPastRetention`。不放進 seller 的個資清理：email 的擁有者是 agent |
| `vendor_portal_identities.prospect_id` 的跨模組 FK（FK 到 `seller_prospects`） | 防止指向不存在的 prospect | 不成立：搬出 seller 後跨 schema FK 違反單體規則 2 | 跨模組以 ID 參照，存在性由對方 API 判斷 | `prospect_id` 只存 ID，無 FK；建立與重取邀請時 email 由 `seller.ProspectContact` 讀（NotFound 原樣回傳）；prospect 的封存由事件處理、合併改掛贏家，建立時的狀態由上面 `EnsureInvite` 那一列的共享鎖保證。`rfq_recipient_id` 同樣沒有 FK，A9 之前無法驗證存在（AGENTS.md 已知限制） |
| bigint 主鍵（應用端 `newID` 發號） | 多服務各自發號 | 不成立（agent 擁有的實體只有自己用） | row-identity ADR：實體 UUIDv7 在應用層產生 | `invite_id`、`session_id` 是 UUIDv7（`uuid.NewV7`，無 DEFAULT）；`rfq_recipient_id`（ai-service）、`prospect_id`（seller）是別的服務的 ID，保持 BIGINT |
| 事件 payload 的 `inviteId` 實際是 `rfq_recipient_id`（D9）；proto 與 ai 端 `invite_id` 混用 | 詞彙一致 | 不成立 | 一個名詞一個意思 | 模組內 `InviteID` 只指本模組的邀請（UUID），`RfqRecipientID` 只指 ai-service 的收件人。legacy adapter（`internal/legacy/sellerserver/invites.go`）把 notification 傳來的 `rfq_recipient_id`（事件的 `inviteId`）對到 `EnsureInviteInput.RfqRecipientID`；回應的 `invite_id` 是 UUID 字串（舊的是十進位 int64），`MarkVendorPortalInviteSecretDelivered` 收同一個字串；notification 把它當不透明字串，已確認：`services/notification-service/internal/client/seller/client.go` 的 `EnsureInvite` 以 `resp.GetInviteId()` 回傳 string、`MarkInviteSecretDelivered(ctx, inviteID, secret string)` 原樣送回，`internal/worker/vendor_invite.go` 的 `MarkSent func(ctx, inviteID, secret string)` 也只傳 string，沒有解析或轉型，所以改成 UUID 字串不影響它 |
| notification 的結果處理：`AlreadyExists` 跳過、`FailedPrecondition` 一律記成 `no_email`（`worker/vendor_invite.go`），Mark 的請求只有 `InviteId` | 呼叫方要能分辨「不寄」的原因與「過時」，才不會把撤銷說成沒有 email | 不成立：舊映射把撤銷與沒有 email 都變成 `FailedPrecondition` | 每個可行動的結果對應一個可區分的狀態 | legacy adapter 以 gRPC code 加 `ErrorInfo.reason`（domain `hawkr`）讓四種結果可區分，reason 是 legacy proto 列舉 `VendorPortalInviteErrorReason` 的名稱，兩端共用生成的列舉：已撤銷（`ErrInviteRevoked`，FailedPrecondition，`INVITE_REVOKED`）、prospect 不是進行中（`ErrProspectNotActive`，FailedPrecondition，`PROSPECT_NOT_ACTIVE`）、沒有可寄的 email（`ErrNoDeliverableEmail`，FailedPrecondition，`NO_DELIVERABLE_EMAIL`）、Mark 的 secret 過時（`ErrInviteSecretSuperseded`，Aborted，`INVITE_SECRET_SUPERSEDED`）；已寄出是 AlreadyExists，不帶 reason。`MarkVendorPortalInviteSecretDeliveredRequest` 有 `secret` 欄位，notification 的 `MarkSent` 把 Ensure 回來的 secret 一併傳回。notification 依 reason 各記一個 `vendor_portal_invite_email_total` 的 label（`invite_revoked`、`prospect_not_active`、`no_email`、`secret_superseded`；皆不重試，ack 掉；沒有或不認得 reason 的 FailedPrecondition 記 `precondition_unknown`，以 `mq.Permanent` 進死信以便重放）；InvalidArgument 與 NotFound 記 `rejected`，同樣以 `mq.Permanent` 直接進死信。測試：`TestInviteErrorMapping`、`TestInviteErrorsCarryErrorInfoOverTheGRPCWire`、`TestVendorPortalInviteRPCsUseTheAgentModule`（單體），`TestVendorInviteHandler_EachOutcomeHasItsOwnLabelAndIsNotRetried`（notification） |
| `IsDeliverableEmail`：prospect 的 `public_email` 是自由文字，用它判斷收不收得到信 | 對「待確認」「N/A」「0912…」這類值發邀請等於靜默失敗 | 成立 | 建立時驗證位址語法，不可寄就不建立並回明確錯誤 | 規則原樣搬入 `internal/model`（單純的 addr-spec、網域含點，去前後空白）並加上單元測試；儲存的是去空白後的值（CHECK 禁止前後空白）；不可寄回 `ErrNoDeliverableEmail`，不留邀請列；沒有改成 MX 查詢（要外部呼叫，且 A8 的 OTP 會證明真的收得到） |
| `MaskEmail`：預覽只顯示 `v***@example.com` | 拿到連結的人認得出寄到哪，又不洩漏完整位址 | 成立 | 部分遮罩 | 原樣搬入 `internal/model`（本地部分只留第一個字元，一個字元或沒有 `@` 全遮），單元測試沿用舊案例 |
| 對外錯誤不分成因（兌換 NotFound、驗證 Unauthenticated、StepUp PermissionDenied） | 猜 secret 的人不能分辨成因 | 成立 | 同一個回應 | 沿用，分類同舊實作；`TestExchangeAndPreviewShareOneOpaqueNotFound`、`TestValidateSessionRejectsEveryUnusableStateWithOneError`、`TestVerifySessionRefusesUnusableSessions` 檢查分類與訊息一致 |
| 歷史資料（舊的 identity、invite、session） | 上線後使用者持續使用 | 不成立：系統從未上線，邀請與 session 都沒有真實資料 | 上線前不搬 | 不搬；schema 是新的 baseline |

## 傳輸層的沿用盤點

舊 gateway 的 handler 與 gRPC 的機制。對外的入口是步驟 8、notification 的 adapter 在 `internal/legacy/sellerserver`，這裡只記模組這一側的結論。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| gateway 的 `hk_vendor_portal` cookie（HttpOnly、Secure、SameSite=Lax、`Path=/api/v1/public/vendor_portal`、Max-Age 為絕對期限剩餘秒數） | 瀏覽器端保管不透明 token，JavaScript 讀不到 | 成立；`Path` 不成立：cookie 要同時送到 Connect 與 gateway 的 RFQ 路由，舊的 Path 涵蓋不到 Connect | OWASP 建議 `__Host-` 前綴（`Secure`、不帶 `Domain`、`Path=/`），不透明 session 放 HttpOnly cookie，期限與伺服器一致；Path 不是安全邊界（RFC 6265 §8.5） | 入口（步驟 8i）：每張邀請一個 cookie `__Host-hk_vp_<rfq_recipient_id>`（舊的單一 `__Host-hk_vendor_portal` 讓同一個瀏覽器只有一格，兌換第二張邀請會蓋掉已驗證的 session），`Path=/`、`Secure`、`HttpOnly`、`SameSite=Lax`，Max-Age 是 `IssuedSession.AbsoluteExpiresAt`（已被邀請截斷）剩餘的秒數、至少 1；名稱與屬性只在 `rpc.VendorPortalCookieName`、`rpc.NewVendorPortalCookie`，同名多個視同沒有（ADR `docs/adr/2026-10-03-vendor-portal-invite-scoped-access.md` 2026-10-04 兩次修訂；`TestExchangeInviteIssuesTheInvitesCookieAndNonce`、`TestVendorPortalFromInviteToTheGateway`） |
| 一個瀏覽器一個 cookie，兌換一律發新的 session 蓋掉它；請求不指名邀請，取 cookie 裡唯一的那個 | 同一業者可能同時有多張邀請（同一封信重開、不同 RFQ、兩個分頁） | 不成立：session 屬於一張邀請，A 分頁的驗證會驗到 B 的 session；重開信件會蓋掉已經 Google 驗證過的 session | 瀏覽器同時持有多個授與，每個請求指名要用哪一個，建立一個不使另一個失效（Google 多帳號的 `/u/N/`、DocuSign 每個收件人各自的簽署 session） | 選擇：Connect 的請求訊息 `rfq_recipient_id`（必填）、gateway 的路徑 `{id}`，只讀名稱含那個 ID 的 cookie（`rpc.VendorPortalCookieToken`），session 的收件人不是指名的 ID 一律 `unauthenticated`（Connect）或不設 header（gateway）。沿用：`ExchangeInvite` 先以 `PreviewInvite` 解出邀請（模組的 `InvitePreview` 帶 `InviteID`、`RfqRecipientID`，不進對外 API），請求帶這張邀請的有效 session 就沿用（不新增 session 列，也不重設 cookie：它的 Max-Age 已是同一個絕對期限），回應是那個 session 的驗證與 nonce；無效或別張邀請的 session 就兌換，新的 `Set-Cookie` 蓋掉舊的，別張邀請的 cookie 不動。上限：請求帶超過 20 個 `__Host-hk_vp_*` 時，回應清掉多出的：看不到 cookie 的年齡，清收件人 ID 最小的（ID 依序發號，小的是較舊的邀請），格式不對的最先清，不含發出或沿用的那個（`rpc.ExcessVendorPortalCookies`）。觸發重新評估：A9 從 prospect 建立供應商帳號、改以帳號登入（`TestExchangeInviteReusesTheSameInvitesValidSession`、`TestExchangeInviteIssuesANewSessionForAnInvalidOrForeignCookie`、`TestExchangeInviteClearsVendorCookiesBeyondTheCap`、`TestTwoCookiesInOneRequestEachMethodTouchesOnlyTheNamedInvite`、`TestVendorPortalFromInviteToTheGateway`） |
| Google ID token 不綁 session（沒有 nonce，也沒有新鮮度檢查） | step-up 提升既有 session 的保證等級，token 要能證明是為這個 session 取得的 | 不成立：任何當下有效的 Google token 都能拿來驗證任何 session，而驗證紀錄是正式送出的證據 | OIDC Core §3.2.2.1 要求 `nonce`，§15.5.2 建議以 session cookie 值的雜湊當 nonce；GSI 的 `initialize` 接受 `nonce`，但沒有 `max_age`，`iat` 是唯一的新鮮度訊號 | `google_nonce` = base64url（無 padding）的 SHA-256（用途前綴加 session token），在 `internal/httpapi/agent` 每次由 token 算、不儲存，與本模組存的 token 雜湊不同輸入（`TestGoogleNonceIsDerivedAndDiffersFromTheStoredHash`）；`ExchangeInvite` 與 `GetSession` 回給 client；identity 的 `VerifyGoogle(ctx, idToken, wantNonce)` 要求 nonce 相等（空字串是程式錯誤，回 internal）且 `iat` 不早於 10 分鐘前，不符與無效 token 同一個錯誤，入口仍回單一 `permission_denied`。本模組只收驗證過的 email，不知道 nonce |
| 以 cookie 認證的方法放在 `VendorPortalPublicService`，以方法為單位的宣告表（`needsSession` 或理由）決定哪個方法驗證 cookie | 公開 service 的 GET 會被共享快取（API 規範 §九），私人資料不能放在那裡；每個方法都要知道誰驗證它 | 宣告表的必要條件成立、形式不成立：cookie 認證改放在 `VendorPortalInviteeService` 之後，驗證與授權跟著 service 的邊界，Public 的兩個方法都沒有 session，表只剩單一值 | 授權跟著 service 的使用者類別（API 規範 §二：`PublicService`、`AppService`、`AdminService`），不是每個方法再宣告一次 | 新的使用者類別 `*InviteeService`（`rpc.AudienceInvitee`，授權不讀 Clerk 身分，快取一律 `private, no-store` 包括 GET，額度每來源每分鐘 300 次單獨計數）；interceptor 掛在整個 service，請求沒有 `rfq_recipient_id` 欄位時回 internal（`TestEveryInviteeRequestNamesTheRecipient`、`TestInterceptorRefusesARequestThatDoesNotNameTheRecipient`、`TestVendorPortalResponsesAreNeverCacheable`）。`GetSession`（`NO_SIDE_EFFECTS`，GET）讀驗證狀態與 nonce，不含絕對期限（`SessionInfo` 沒有，ADR 也不要求）；ADR 2026-10-04 修訂 |
| 七條路由每次請求經 gRPC 驗證 session | session 要能撤銷 | 成立；RPC 不成立 | 邊界驗證 session，把已驗證的身分以受信任的 header 交給後端（IAP、oauth2-proxy、Cloudflare Access） | 入口（步驟 8i）直接呼叫 `ValidateSession`，錯誤一律轉成同一個 Unauthenticated。Connect 的 `GetSession`、`VerifySession` 由只掛在 `VendorPortalInviteeService` 的 interceptor 以請求的 `rfq_recipient_id` 選 cookie 並驗證；ai 的 RFQ 路由到 A9 都在 gateway：入口對每個轉給 gateway 的請求先刪掉 `X-Vendor-Portal-*`，`/api/v1/public/vendor_portal/rfqs/{id}/…` 以路徑的 `{id}` 選 cookie、session 的收件人等於 `{id}` 時才設上 `X-Vendor-Portal-Rfq-Recipient-Id`、`X-Vendor-Portal-Session-Id`，session 已驗證時再設 `X-Vendor-Portal-Verification-Method`、`X-Vendor-Portal-Verified-Email`、`X-Vendor-Portal-Verified-At`；驗證失敗、`{id}` 格式不對或別張邀請的 session 不帶 header（gateway 回 401），驗證時資料庫等出錯回 503（API 設計規範（Connect）§二；`internal/legacy/gatewayproxy`）。`SessionInfo.RfqRecipientID` 是存取範圍 |
| 正式送出、撤回、婉拒要求 `GOOGLE_VERIFIED`（缺 session 值 fail-closed，403） | 不可撤回的動作要驗證身分 | 成立 | 敏感動作要求驗證 | 步驟 8 檢查 `SessionInfo.Verification != nil`（缺值視為未驗證）；草稿不要求（ADR「驗證」） |
| Google step-up 鏈：gateway 讀 cookie、經 account-service 驗證 Google token、拒絕 `!email_verified` 或空 email、再呼叫 StepUp | 只有已驗證的 email 才能拿來比對 | 成立 | 驗證在入口，領域只收結果 | 入口（步驟 8i）的 `VerifySession` 先驗指名那張邀請的 cookie（無效回 `unauthenticated`），再經 identity 的 `VerifyGoogle`（帶由 session 推導的 nonce）驗證 Google token 並檢查 `EmailVerified`（identity 不強制），最後呼叫 `agent.VerifySession(token, GOOGLE, email)`；email 只取自 Google 驗證的結果，不接受 client 自報。token 無效、未驗證、email 不符一律 `permission_denied` 同一段訊息，公鑰問不到回 `unavailable`；模組不驗 token |
| `Idempotency-Key`（送出、撤回、婉拒）轉成 ai 的 `client_request_id` | 重送不重複送出 | 成立，但屬於 RFQ 的回覆 | 命令帶冪等鍵 | 不屬於 agent：在 ai-service（A9 之前由入口轉傳） |
| gRPC 的錯誤映射（AlreadyExists、FailedPrecondition、NotFound、Unauthenticated、PermissionDenied） | notification 依狀態碼決定重試或放棄 | 成立 | 錯誤分類映射到傳輸的狀態碼 | 模組以 `apperr` 的分類與可用 `errors.Is` 判斷的 sentinel 回傳；`internal/legacy/sellerserver/errors.go` 的 `connectError`：狀態碼由 `apperr.KindOf` 查一張分類對狀態碼的表（InvalidInput 對 InvalidArgument、NotFound 對 NotFound、VersionConflict 對 Aborted、AlreadyExists 對 AlreadyExists、FailedPrecondition 對 FailedPrecondition 等，沒有分類的是 Internal），`ErrorInfo.reason` 另由 sentinel 對列舉的表查，只有已撤銷、prospect 不是進行中、沒有可寄的 email、secret 過時四個結果帶 reason |
| 兌換與預覽共用 20 次 5 分鐘的限流 | 擋猜測 | 成立 | 以來源為 key，驗證端點專屬限流 | 見上方限流一列：入口以來源計數，預覽與兌換一個計數器，`VerifySession` 另計（10 分鐘 10 次），`GetSession` 用受邀供應商類別的一般額度（每分鐘 300 次） |
| `email_verified` 的檢查位置：identity 的 `VerifyGoogle` 回傳 `EmailVerified` 但不強制，由呼叫方檢查 | 以 email 授權的呼叫方不能收未驗證的 email | 成立；位置沒有第二個呼叫方的理由 | 驗證函式只回傳已驗證的 claims（OIDC 的 verifier 回傳 claims，授權決策在 relying party） | 檢查放在入口 handler（`internal/httpapi/agent`，`TestVerifySessionDeniedCasesShareOneCodeAndMessage`；計畫 8i，Will 2026-10-04）：`VerifyGoogle` 目前只有這一個 in-process 呼叫方。重新評估的觸發：出現第二個 `VerifyGoogle` 的呼叫方，屆時把檢查搬進 identity，只回傳已驗證的 email |
| ai 的 `procurement_seller_response_commands`（與報價版本表）只追加，靠查詢慣例加一個掃描 `db/queries` 是否出現 UPDATE、DELETE、TRUNCATE 的測試 | 證據不可被改寫 | 慣例成立；資料庫層沒有強制 | 資料庫強制：trigger 擋 UPDATE／DELETE，或撤銷應用程式角色的權限 | 接受到 A9：採購搬進單體時，送出、撤回、婉拒三種指令統一成一份稽核軌跡（ADR 2026-10-04 修訂），那時在資料庫層強制（trigger 或 REVOKE）。觸發：A9 |
| `GET` 預覽（secret 在 `Authorization: Invite` header） | 預覽沒有副作用 | 不成立：secret 是 bearer 憑證，GET 放進 URL 會進日誌與歷史（RFC 9110 §17.9、CWE-598），公開 service 的 GET 還會被共享快取（API 設計規範（Connect）§九） | 憑證放請求本文，以 POST 呼叫 | `PreviewInvite` 是 POST，secret 在請求訊息，不標 `NO_SIDE_EFFECTS`；`PublicService` 兩個方法與 `InviteeService` 的回應都是 `private, no-store`（`TestVendorPortalResponsesAreNeverCacheable`） |

## 結束狀態

- 以 cookie 認證的受邀供應商使用者類別已在 8i 建立（`VendorPortalInviteeService`，回應一律 `private, no-store`，ADR 2026-10-04 第二個修訂）。A9 採購搬進單體時，ai 的 RFQ 路由改成這個 service 的方法（請求都帶 `rfq_recipient_id`），`gatewayproxy` 的路徑解析、`X-Vendor-Portal-*` 與入口對 gateway 的處理一併刪除。重新評估 cookie 模型的觸發：A9 從 prospect 建立供應商帳號、改以帳號登入。
- 驗證紀錄的 email 隨報價版本、撤回與婉拒的指令紀錄存在 ai，保存期限跟著報價；A9 為採購紀錄訂保存期限時一併處理。

## 與 seller-service 的差異

資料沒有搬移（系統從未上線），schema 是新的 baseline。

- 沒有 `vendor_portal_identities`；邀請直接存 `prospect_id` 與 email 快照，session 與驗證都綁單張邀請。
- 邀請可重複兌換到到期或撤銷（舊的單次兌換）；兌換不撤銷別的 session，只限制同一張邀請最多 5 個有效 session。
- `assurance`（`INVITE_ONLY`、`GOOGLE_VERIFIED`）改成驗證紀錄（方式、email、時間）；`StepUp` 改名 `VerifySession`，比對邀請的快照；入口新增 `GetSession`（驗證狀態與 Google nonce）。
- `EnsureInvite` 是一個 transaction、併發安全，只替進行中的 prospect 建立或換 secret（與封存序列化），結果分成四個 sentinel；`MarkInviteDelivered` 帶 secret，過時的不生效；`expires_at` 要在未來且不超過 180 天。
- 邀請與 session 會被 prospect 的封存撤銷、合併時改掛贏家，並有每天的清理。
- 主鍵是 UUIDv7；token 與 secret 是 base64url 的 32 bytes，資料庫存 `bytea` 的 SHA-256（舊的是 hex 字串的 SHA-256 hex）。
- `ValidateSession` 的滑動與驗證在同一個 statement，寫入失敗不吞。
- 對外是 Go 的函式呼叫；舊的六支 gRPC 與 gateway REST 在步驟 8、9 由入口與 adapter 取代。
