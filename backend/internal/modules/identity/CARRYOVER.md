# identity 模組的沿用盤點

從 account-service 沿用的每個機制重新判斷的結論（遷移計畫「模組完成的定義」），以及與 account-service 的差異。模組現行的職責、資料與不變量在同目錄的 `AGENTS.md`。

## 沿用盤點

account-service 的每個機制，搬進來時都重新判斷過（遷移計畫「模組完成的定義」）。對外 API（舊 gateway 的入口與 auth handler）的機制在下一節。代行的沿用盤點在 delegation 的 `CARRYOVER.md`。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| 每個 provider 各自使用 go-oidc 與遠端 JWKS；未知 kid 觸發抓取 | 多個 issuer 的簽章與 claims 各不相同 | claim policy 不同成立，重複 verifier 與無限抓取不成立 | [RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3) 要求限制 alg 並驗證 issuer／audience；[jwx jwt](https://pkg.go.dev/github.com/lestrrat-go/jwx/v3/jwt) 以 key set 與 validator 組裝驗證；遠端快取另加未知 kid 限頻 | jwx/v3 v3.3.0；Clerk 固定 PEM，Access／Google／Apple 用 jwk.Cache，刷新最短一分鐘。RS256、精確 iss、exp／nbf 五秒 leeway、sub；Clerk 必填 authorized parties、可缺 azp、sts 只接受 active |
| JIT 建帳以 Backend API User 讀姓名與 email | token 不含建帳所需資料 | 不成立：Clerk 支援 custom session claims | [Clerk session token](https://clerk.com/docs/guides/sessions/session-tokens) 支援自訂 claims；[手動驗證](https://clerk.com/docs/guides/sessions/verifying) 後只取顯示所需的最小欄位 | dashboard 設 email／name；缺值以空字串建帳，移除 User 與 ClerkUser；只保留停權、刪帳 API |
| dev admin 與顧客各自簽 token；go-jose 簽章 | 本機 issuer／aud 不同 | claim 不同成立，重複簽章不成立 | [jwx jwt.Sign](https://pkg.go.dev/github.com/lestrrat-go/jwx/v3/jwt#Sign) 可簽 RS256 與 ES256；共用函式以 claims 表達差異 | 共用 SignDev，移除 NewDevClerk issuer 參數；dev 與 Apple client secret 均改用 jwx 簽章 |
| session cookie 對所有路徑生效；限流只看 origin-auth／IP | 下載導覽無法帶 Bearer；Worker 共享出口 | 下載需求成立，所有路徑收 cookie 與登入者共享額度不成立 | [OWASP Fetch Metadata](https://cheatsheetseries.owasp.org/cheatsheets/Fetch_Metadata_Resource_Isolation_Policy_Cheat_Sheet.html) 依 Sec-Fetch-* 限定跨站資源入口；依可信 principal 計數 | cookie 只收 GET + navigate + /api/v1/；principal 優先，admin 不簽 origin-auth，gateway 依單體身分 header 計數；下載搬成 Connect 時以 Bearer 取檔 |
| JWKS 快取之外的未知 kid 刷新閘門 | `jwk.Cache.Refresh` 沒有限頻 | 成立；偽造 kid 可造成反覆抓取 | [jwx jwk.Cache](https://pkg.go.dev/github.com/lestrrat-go/jwx/v3/jwk#Cache) 管快取；應另限制手動刷新頻率 | 保留一分鐘刷新閘門，失敗也限頻；既有 kid 不等待刷新。 |
| 遠端 verifier 的生命週期 | 背景更新須在 serve／worker 關閉時停止 | 成立 | [jwx jwk.NewCache](https://pkg.go.dev/github.com/lestrrat-go/jwx/v3/jwk#NewCache) 接收生命週期 context | 組裝點傳入 process context，不以 Background 作正式環境的生命週期。 |
| dev 與 Apple 簽章沿用 go-jose | 既有套件提供必要功能 | 不成立；jwx 已提供兩種演算法 | [jwx jwt.Sign](https://pkg.go.dev/github.com/lestrrat-go/jwx/v3/jwt#Sign) 統一簽驗；[RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1) 限制演算法 | 正式與本機的執行路徑都用 jwx；測試仍以 go-jose 作獨立驗章對照。 |
| 根套件的完整 `Deps` 與同時包含認證、帳號管理方法的 `Clerk` 介面，原本搬到 `internal/model` 後傳給各子領域 | 舊的單一 `Module` 執行所有 use case；同一個 Clerk application 同時提供驗證與使用者管理 | 根套件仍須組裝所有依賴、Clerk client 仍提供兩種能力；各子領域只使用其中一部分 | 各子領域定義最小依賴與使用端介面，由根套件逐欄組裝，可由型別限制能力 | `Deps` 留在根套件，各子領域宣告只含所需欄位的 `Deps`；auth 的建帳能力以使用端介面依賴 account。根套件的 provider API 接受完整 `Clerk`，組裝時分別轉成 auth 驗證與 account job 所需的窄介面。 |
| 帳號主鍵由 `GenerateAccountID` 產生（兩位年份加 8 碼亂數，撞號不重試）；管理員與 `auth_providers.id` 用同一個產生器 | 多個服務各自發號，ID 要能看出年份 | 不成立：單一資料庫；年份沒有讀取端；撞號時直接回錯 | 資料庫發號或 UUIDv7（ADR `2026-09-25-row-identity-by-data-kind.md`） | 帳號、管理員用 `bigint GENERATED ALWAYS AS IDENTITY`（過渡規則：Java 存 `BIGINT`），階段 C 換 uuid；OAuth 連結隨改用 Clerk 移除（登入方式由 Clerk 保存）。`GenerateStoreCode` 的重複實作（pkg-refactor-plan）隨之消失 |
| session、稽核、outbox 與 refresh family 用 TSID | 單一 replica | 不成立：serve 多個 replica 加上 worker | UUIDv7 | 身分 session 等由 Clerk 管理，不建這些表；代行的 ID 決定見 delegation 的 `CARRYOVER.md` |
| 角色 bitmask `accounts.account_type` 與 `account_roles` 並存（#1544 Phase 1），bitmask 烘進 JWT、gRPC 回應與 admin 的 SQL 篩選 | 舊的 wire 契約讀 bitmask | 新契約不需要；舊服務（buyer、seller、social、crm、coupon、gateway）搬遷前仍讀 | 角色是集合，存成關聯表 | 新 schema 只有 `account_roles`；bitmask 只在 `internal/legacy/accounttype` 投影給舊呼叫方（買家位元由「帳號活著」合成，W5），隨它們退場。#1544 的 Phase 2 到 4 就此完成 |
| `account_roles` 是 append-only 的授予歷史（`granted_at` 在主鍵、`revoked_at`） | 有人要查誰在什麼時候被授予或撤銷 | 不成立：`ListAccountRoleHistory` 沒有呼叫端 | 現況表；需要稽核時另外記事件 | 現況表 `(account_id, role)`，保留 `granted_at` 與 `source_id` |
| `source_id` 柵欄：移除角色時帶來源（`store_id`、`buyer_id`），目前的授予屬於較新的來源就不移除（#3189） | seller-service、buyer-service 以 outbox 非同步呼叫 `RemoveRole`，可能晚於重新入駐 | 成立到 A3 | 在同一個 transaction 內直接呼叫就不會亂序 | 沿用到 A3b：買家不再是角色（W5），柵欄只剩 seller-service 非同步移除 SELLER 需要；記在 `AGENTS.md` 的「已知限制」，A3b 步驟 11 拿掉欄位與柵欄 |
| 角色字串刻意不加 CHECK（「多一個角色不該要 migration」） | 角色常常增加 | 不成立：只有賣家（買家不是角色，W5），多一個角色本來就要改程式 | 儲存的碼由模組的 Go 型別與 CHECK 定義（ADR `2026-09-25-codemeta-retirement.md` D3） | 加 CHECK，值等於 Go 常數（`SELLER`） |
| 買家存成角色（`BUYER`，建帳時授予、刪帳時移除；最後一個角色移除時刪帳號） | 買家與賣家都是可以單獨加入、單獨退出的身分 | 不成立：建帳就是買家（W1），後台不再只刪買家（W3），帳號活著 ⇔ 買家活著；存成角色只多一個會與帳號狀態漂移的來源 | 由不變量推導的屬性不另外儲存 | 刪除（Will 2026-10-01 W5）：角色只剩要另外申請的 SELLER；last-role cascade、`RoleState`、BUYER 的授予與移除都刪除，移除 SELLER 永遠不刪帳號。舊契約需要的買家位元（`account_type`、`X-Login-Role`、`X-Account-Type`）由 `internal/legacy/accounttype` 在邊界合成。migration `buyer_is_not_a_role` 刪掉既有的 BUYER 列並收緊 CHECK |
| 管理員是另一張表、ID 與帳號同格式；Redis 的 `auth:epoch:<id>` 不分類型、legacy refresh 對管理員查錯表（盤點 G8） | 管理員的登入與權限不同於帳號 | 分表成立；ID 混用不成立 | principal 帶類型 | 沿用分表；principal 帶類型。顧客由 Clerk、後台由 Access 簽 token，認證以 issuer 區分，兩邊同號時不互相認證成對方（測試） |
| 管理員的密碼登入（bcrypt）與 `cmd/create-admin` | 有 client 使用 | 不成立：admin 只用 Google 登入 | 不做沒有讀取端的功能 | 刪除（Will 2026-09-27） |
| 管理員第一次 Google 登入時，email 網域在白名單內就自動建立；比對的是 email 字串 | 網域代表組織成員 | 不成立：公司 Workspace 已停用；個人信箱網域不是組織邊界 | IdP 或 zero-trust gateway 的明確 allowlist，在後端驗簽與 audience，首次使用時建立本地身分 | Access application 的 email 白名單是唯一開通來源；單體驗 JWT 的簽章、`aud`、`iss`、`exp`、`nbf`，以 `sub` 建管理員列，email 只供顯示（ADR `2026-09-27-identity-clerk.md` 文末修訂） |
| 本機管理員沿用 Clerk 形狀的 dev token，再以 adapter 轉成後台身分 | 後台也用 Clerk 的 session 與使用者查詢 | 不成立：後台 token 是 Access JWT，只有 `sub`、`aud`、`email` 等 claim | 本機 token 複製正式憑證的 claim 形狀，走同一條驗簽路徑 | `make dev-token -admin` 簽 dev issuer、dev AUD、`sub` 與 `email`；固定本機公鑰供 共用 `oidc.Verifier` 驗證，移除 Clerk adapter |
| 後台用複數 verifier 清單依未驗證 `iss` 選 application | 正式後台與 dev 管理員 application 可能同時設定 | 不成立：Access 與 dev key 互斥，每個部署只有一個後台 verifier | 單一後台 verifier；未驗證 `iss` 只用於顧客與後台路由，避免未知 issuer 觸發遠端 JWKS；後台 verifier 自行驗簽並檢查 issuer 與 AUD | `Providers.Admin` 是單一欄位，移除後台清單與搜尋 helper；未知 issuer 直接拒絕 |
| 管理員列與 API 保存姓名、大頭照 | IdP 提供這兩個欄位且後台需要顯示 | 不成立：Access JWT 只有 email | 只保存身分來源能提供且畫面需要的資料 | 移除 `admins.name`、`picture_url` 與 proto 欄位，後台顯示 email |
| 手寫遷移重寫 Clerk 管理員 ID，沿用欄位並改名 | 已有資料需要保留並避免身分碰撞 | 正式資料不存在，但本機舊 migration 的管理員列要能保留；Clerk `user_…` ID 與 Access subject 不會碰撞 | 以 `schema.sql` 為 desired state，改名保留既有 subject、索引與 NOT NULL constraint | Access migration 將 `clerk_user_id`、unique index 與 PG 命名的 NOT NULL constraint 改名，刪除姓名與大頭照；不改寫既有值，重新計算 Atlas hash |
| 憑證：HS256 JWT（7 天、角色烘在 claim）、refresh 輪替與重放偵測、`revoked_tokens`、`auth_epoch`、`roles_epoch`、Redis 的撤銷名單與 blacklist | 驗證憑證的 gateway 讀不到帳號的資料 | 不成立：單體裡同一個 process 讀自己的 schema | opaque session（OWASP） | 改用 Clerk（ADR `2026-09-27-identity-clerk.md`，Will 2026-09-27；取代 ADR `2026-09-27-identity-opaque-sessions.md` 的 D1、D2） |
| web session 以 `web_sessions` 為權威、Redis 為加速層，cookie 與 token 由 gateway 產生 | 同上 | 不成立 | 同上 | 同上：session 由 Clerk 管理，web 的請求帶 SDK 取得的 Bearer，Clerk 的 `__session` cookie 僅供 GET REST 瀏覽器導覽 |
| `Touch` 延長 session 時沒有 `expires_at > now` 的條件，過期但還沒被清掉的 session 會復活（盤點 G12） | — | — | 過期的 session 一律無效 | session 由 Clerk 管理；token 效期 60 秒，停權與刪除以本模組的狀態為準，每個請求讀 |

| OTP 的每日上限以 UTC 日期為 key | 需要「每天」的額度 | 部分成立：UTC 的換日在台灣是早上 8 點 | 滑動的時間窗 | 隨驗證碼移除 |
| 簡訊發送失敗不重試（mitake ADR D6） | 重試會重複扣點 | 不成立：三竹的 `clientid` 可以去重 | intent 加 job（單體 ADR D5） | 隨驗證碼移除（不用三竹） |
| 三竹經舊公司 GCP 的 Cloud Run egress proxy（固定 IP、SA key 檔） | 三竹以 IP 白名單鎖定來源 | 白名單是外部約束，仍成立；proxy 在舊公司的 infra（D9） | 固定的出口 IP（NAT） | 隨驗證碼移除（不用三竹，也不需要固定的出口 IP） |

| Google、Apple 的 ID token 驗證不檢查 nonce | ID token 被竊取後重放的風險可以接受 | Google 的 vendor portal step-up 不成立：step-up 提升既有 session 的等級，token 要綁定那個 session；Apple 的 `LinkAppleCredential` 成立（`aud` 限定在自己的 client ID，token 只經 TLS 直接送到 API，單體不記 body，重放的後果只是替呼叫者自己的帳號再排一次換 token（Apple 換 token 簽發的 ID token 必須與連結時驗證的身分相同，code 只能用一次）） | OIDC Core §3.2.2.1 的 nonce（§15.5.2 建議以 session cookie 的雜湊推導）；GSI 的 `initialize` 接受 `nonce`，而 GSI 沒有 `max_age`，`iat` 是唯一的新鮮度訊號 | Google：`VerifyGoogle(ctx, idToken, wantNonce)` 必填 nonce（空字串是程式錯誤、回 internal），token 的 nonce 要相等，`iat` 不得早於 10 分鐘前（`iat` 在未來的容忍度是 oidc 的 5 秒時間差），不符與其他無效 token 同一個錯誤類別；nonce 由 session token 推導，在 `internal/httpapi/agent`（ADR `2026-10-03-vendor-portal-invite-scoped-access.md` 文末修訂）。Apple 與 Clerk 的登入不加 nonce（Clerk 負責 OAuth 的 state 與 nonce）；`GOOGLE_CLIENT_IDS` 加第二個 client 時，先確認所有 Google 驗證的呼叫方都帶 nonce |
| Google 驗證加斷路器（連續 5 次失敗開路 10 秒） | JWKS 抓取常常失敗 | 不成立：公鑰有快取，只在過期或遇到新的 `kid` 時抓 | 快取公鑰、抓取有逾時 | 拿掉斷路器 |
| Google 或 Apple 沒有設定時換成停用的 verifier（9701、9702）；但 Apple 的 P8 沒有設定時服務起不來（盤點 G2） | 本機與測試沒有 provider 的設定 | 成立 | 缺少的整合讓該功能不可用，不影響啟動 | Google（vendor portal 的 step-up）沿用；Apple 在部署的環境必填（缺設定啟動失敗），只有本機開發可以不設（`LinkAppleCredential` 回 unavailable，刪帳號不受影響）；Clerk 同樣整組選填，沒有設定時該類使用者無法登入 |

## 傳輸層的沿用盤點

舊的對外入口是 gateway：全域中介層（`internal/infrastructure/di.go`）、認證（`internal/middleware/auth.go`）與 auth 的 handler（`internal/handler/auth*.go`）。新的入口是單體的 `internal/httpapi`（計畫步驟 3），還沒搬的 REST、SSE 與 WebSocket 由它轉給 gateway。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| 憑證可以放在 `Authorization`（非 Bearer 的 scheme 也整段當 token）、`token` header 或 `?token=`（#2511）；帶任何 token 就豁免 CSRF | 某個 client 只能用 query 帶憑證 | 不成立：四個 client 都沒有這樣送；WebSocket 用一次性的 ticket | RFC 6750 的 `Authorization: Bearer` | 只接受 `Authorization: Bearer` 與 Clerk 的 `__session` cookie（兩者都有時以 Bearer 為準；web 的請求帶 Bearer，cookie 給瀏覽器直接導覽的下載）；query 與 `token` header 一律不讀 |
| 入口沒有全域刪除 client 帶來的身分 header，OptionalJWT 沒解出身分與不需要認證的路由會原樣往下傳（#1859） | — | — | 入口一律刪掉，只設自己解出來的 | 單體在入口刪掉 `X-Account-Id`、`X-Account-Type`、`X-Login-Role`、`X-Active-Role`，認證過才設上身分 header（契約寫進〈API 設計規範（Connect）〉§二） |
| 身分以明文 header 傳給單體，單體只信任網路位置 | 服務只能被 gateway 連到 | 方向反轉：入口移到單體後，由單體以明文 header 傳給 gateway | 網路隔離，做不到時簽身分 | 單體→gateway 用明文 header；gateway 與舊服務不會部署（後端 CD 以遷移完成後的單一 image 為對象），所以只存在於本機與 CI。「只有入口連得到 gateway」仍記進 wiki 的 CD 待辦，以防順序改變 |
| gateway 的 Connect 代理（依 service 名稱授權、`connectServices` 清單、錯誤改寫成 Connect） | 單體在 gateway 後面 | 不成立：入口移到單體 | — | 刪除（步驟 4）；gateway 的 `TestConnectServicesMatchTheContract` 與轉接層一起刪 |
| `X-Active-Role`：提示必須在帳號的角色內，否則退回 JWT 的 loginRole 或 session 持久化的角色；結果以 `X-Login-Role` 往下傳，是視角、不是授權 | 同一個帳號在 web 切換買家、賣家的工作區 | 成立；持久化的角色沒有 client 使用 | 同 | Connect 不使用視角（ADR `2026-10-07-connect-without-perspective`）：`Account.perspective` 與 `rpc.Principal.Perspective` 刪除（`rpc.Principal` 包裝隨後也刪，ctx 直接放 `identity.Principal`），identity 的公開 API 不再有 `Perspective`、`PerspectiveOf`。「正在看哪個工作區」是 client 的 UI 狀態（website 以儲存的工作區與是否有賣家角色決定預設）；`X-Active-Role` 名稱不改（舊 wire），只留在舊 REST、SSE、AI chat 與 chat ws-ticket 的送出端，由 `internal/legacy/gatewayproxy` 從轉發的請求讀它，以 `internal/legacy/accounttype.OfLoginRole` 推導 `X-Login-Role`（提示是 SELLER 而且帳號有賣家角色時是賣家，其他情況是買家，管理員沒有；每個帳號都是買家）。session 不存角色。退場條件：最後一個讀 loginRole 的 gateway handler 或 IM 消費端退場，屆時 header 與推導一起刪除 |

## 與 account-service 的差異

資料沒有搬移（系統從未上線），schema 是新的 baseline；決定的理由在上面兩張沿用盤點表。

- 帳號與管理員的主鍵是 IDENTITY（原本是兩位年份加 8 碼亂數）。
- 登入、登出、session 與帳號連結由 Clerk 處理（ADR `2026-09-27-identity-clerk.md`）：沒有 JWT、refresh token、`revoked_tokens`、`auth_epoch`、`roles_epoch`、Redis，也沒有 OAuth 連結與 1304 的確認。帳號以 `clerk_user_id` 對應，第一個認證過的請求時建立。
- 角色只存現況（`account_roles`），沒有 bitmask 與授予的歷史；角色只有 `SELLER`（買家不是角色，帳號活著就是買家）。角色、停權與刪除每個請求都從 DB 讀。
- 新帳號不驗證手機：帳號沒有手機、沒有驗證碼與簡訊（原本一定要驗證手機，簡訊經三竹）。
- email 是建帳時 Clerk session 的 email claim，只給後台顯示與搜尋，不唯一、不同步。
- 刪除帳號是一個 transaction：刪角色、清掉 email 只留墓碑（保留 `clerk_user_id`）、排入 job 刪除 Clerk 的使用者，發出 `AccountDeleted`（原本刪除時不刪連結，同一個 Google 身分每次登入都會建一個新帳號）。保存的 Apple refresh token 在同一個 transaction 內取走並排入撤銷。
- 停權時排入 job 停用 Clerk 的使用者；停權的理由只寫 log。
- 管理員由 Cloudflare Access 的 Google 登入與 email 白名單開通；單體驗 Access JWT，以 `sub` 建管理員列；沒有密碼登入與 `create-admin`。
- 拿掉：provider 的列出、綁定、解綁；`VerifyPhone`；登出全部裝置；持久化 active role；公開的手機檢查；管理員的密碼登入；後台帳號的 get、suspend、unsuspend、stats 端點（停權留在模組的公開 API）；App Review 的 demo 登入與手機 bypass；`auth_audit_log`；Better Auth 的 schema。
- 代行資料與 credential 的新歸屬、型別及差異見 delegation 的 `CARRYOVER.md`。
- 管理員登出由 `internal/httpapi/identity` 直接呼叫 delegation 撤銷；identity 不發登出事件，legacy 的 `RevokeSessionsByActor` 不實作。
