# media 模組的沿用盤點

從 Java media-service 沿用的每個機制，搬進 Go 時重新判斷的結論（遷移計畫「模組完成的定義」）。計畫與範圍在 `backend/docs/plans/2026-11-21-b1-media.md`；R2 實測事實在 `backend/docs/plans/2026-11-21-b1-media/spike.md` (e)。本表由 B1-2a 建立，B1-2b、B1-2c 落地的機制隨步驟補列（B1-2c2：機敏串流上傳與信封加密的列；B1-2c3：key 後綴、錯誤傳遞方式、機敏上傳的重試補償與內部直接寫入的列，都在表尾）。

## 沿用盤點

本節的表由 B1-2a（儲存層）建立，B1-2b（暫存與資產生命週期）的列接在後面。

Java `StorageService` 的操作與 Go port 的對應：`generatePresignedUploadUrl` → `PresignPut`；`getObjectStream` → `Get`；`statObject` → `Head`；`uploadStream` → `Put`；`deleteObject` → `Delete`；`generateObjectKey`、`generateFinalObjectKey` → `NewKey`；`copyObject`、`generatePresignedDownloadUrl`、`isEnabled` 不搬（見下表）。

| 沿用的機制 | 必要條件 | 今天是否成立 | 業界在同樣條件下的做法 | 決定 |
|---|---|---|---|---|
| 預簽 PUT 讓 client 直傳（`R2StorageService.java:126-148`） | 檔案不經應用伺服器 | 成立：圖片與機敏檔都由 client 直傳 | [R2 預簽網址](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)是官方的直傳做法 | 沿用；簽章改綁 `Content-Length`、`Content-Type`、`Content-MD5`、`If-None-Match: *`（Java 只綁 `Content-Type`，`R2StorageService.java:41`，大小要靠事後 HEAD 兜底）。R2 不支援表單 POST，無法綁大小範圍，只能綁確切大小（spike (e)） |
| 暫存物件放 `tmp/` 前綴，確認前不進正式前綴 | 確認前的上傳不能被公開讀取，且過期要能整批清除 | 成立 | [R2 lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) 可依前綴過期 | 沿用，前綴固定為 `tmp/`、`public/`、`secure/`；Java 的暫存 key 是 `{visibility}/{yyyyMMdd}/{uuid}{ext}`（`AbstractStorageService`），暫存與正式混在同一前綴，lifecycle 無法只清暫存，不沿用 |
| 完整性用 `Content-MD5`，不用 `x-amz-checksum-sha256` | R2 PutObject 認得的完整性 header | R2 文件列 `Content-MD5`，`x-amz-checksum-*` 在 PutObject 是否支援沒寫（spike (e)） | [R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/) | 用 `Content-MD5`；SDK 的 checksum 計算設為 `WhenRequired`，預簽網址不多綁 `x-amz-checksum-*` |
| object key 含檔名副檔名與日期（`{uuid}{ext}`） | 讀取端靠副檔名判斷型別 | 不成立：辨認改依 magic bytes（B1-2c），型別存在資產列 | 以不可猜的隨機 key 加伺服器端記錄型別 | `NewKey` 只產 `<prefix>/<uuid v4>`，不含呼叫端檔名（缺陷 5.16）、不含 `.attempt-`（缺陷 5.15）；v4 隨機讓確認前的暫存 key 不可猜 |
| 未配置時走 mock／skip（`R2StorageService.java:121-131`，`isEnabled`） | 本機沒有 R2 時還能跑 | 不成立：本機與 CI 用 MinIO 容器（Will 2026-11-22） | 缺設定就啟動失敗（fail-fast） | 不搬 `isEnabled` 與假網址；`MEDIA_STORAGE=r2\|s3compat` 明確選擇，缺選擇或缺任一設定，建構時回錯誤、啟動失敗（缺陷 5.12），絕不退回 fake；`storage.Fake` 只由 Go 測試接線 |
| `copyObject`：確認時把暫存複製到正式路徑（`R2StorageService.java:241`） | 暫存與正式物件內容相同 | 不成立：處理 job 讀暫存、剝除 metadata 或加密後寫正式 key | 處理後的位元組不同於原檔，不能複製 | 不搬；port 沒有 Copy |
| `generatePresignedDownloadUrl`（`R2StorageService.java:151`） | 公開圖片由 client 直接下載 | 不成立：公開出口是 image gateway 與 CDN；機敏下載由擁有者端點代理 `Get`（ADR `2026-10-03` 修訂） | — | 不搬 |
| Java 用 AWS SDK v2、R2 region 固定 `auto`、endpoint `https://<account>.r2.cloudflarestorage.com`（`R2StorageService.java:90-101`） | 與 R2 的 SigV4 相容 | 成立 | [R2 S3 相容](https://developers.cloudflare.com/r2/api/s3/api/) 官方用 AWS SDK | 沿用到 aws-sdk-go-v2（`aws` 與 `service/s3` 兩個直接依賴，Will 2026-11-22 同意）；憑證用 `aws.CredentialsProviderFunc`，不加 `credentials`、`config`。`s3compat` 帶自訂 endpoint 與 path-style，同一個 adapter |
| `Put` 同 key 重寫 | 處理 job 重試要冪等 | 成立 | S3 PutObject 預設覆寫；預簽 PUT 才帶 `If-None-Match: *` | `Put` 覆寫；`If-None-Match` 只綁在預簽 PUT，避免 client 覆蓋已存在的暫存物件 |
| 暫存 → 確認的狀態機：Java `upload_session` 的 INIT／COMPLETED／EXPIRED，確認時 CAS，再複製物件、寫資產列（`UploadSessionService.java:62-63,142-151`） | 暫存、處理中、可確認、已確認、回收要各自分得出來，轉換在並發下只有一方成功 | 部分成立：Java 的狀態不分「處理中」與「可確認」，因為確認時才複製與寫資產列；Go 的處理在確認之前由 job 做完 | 直傳流程的常見做法是上傳完成事件觸發非同步處理，處理完才可被引用（Shopify staged uploads、Active Storage 的 attachment 與業務列同一 transaction 才綁定） | 重設計：`PENDING → UPLOADED → READY｜REJECTED → CONFIRMED`，GC 走 `DELETING → DELETED`；每個轉換都是條件式 UPDATE（`WHERE state=<預期>`），0 列就是輸給對方；`READY` 之前資產列不存在。確認只剩一個 UPDATE，沒有物件操作，所以能放進擁有者的 transaction。狀態值是 Go 型別加 CHECK（UPPER_SNAKE），不用 DB enum |
| staged token 是 HS JWT（`StagedTokenService.java:90`），簽章加表裡的 INIT 列兩份真相 | 暫存列在單體內就在同一個 Postgres | 不成立：有表就不需要簽章的第二份真相；JWT 也撤銷不了 | 不透明隨機 ID 加查表（B1-D2，Will 2026-11-21） | 改成 32 位元組隨機 token（base64url），資料表只存 SHA-256，不存明文；token 與暫存列一對一，過期與撤銷都在列上；形狀不對的 token 不查資料庫；未知 token 與非上傳者回同一個 NotFound，不洩漏 token 是否存在。token 是高熵隨機值，所以用快速雜湊即可，不需要 bcrypt 類的慢雜湊 |
| TSID 資產 ID（BIGINT，序列化成字串） | ID 需要單機產生、不撞號、可排序 | 單機產生與可排序仍成立，BIGINT 與 node 編號的限制不再有理由 | UUID v7（ADR `2026-09-25-row-identity-by-data-kind`，B1-D8） | 資產與暫存列的主鍵都是應用層產生的 UUID v7、不設 DEFAULT（`Deps.NewID`，組裝點給 `uuid.NewV7`）；擁有者模組的 `*_asset_id` 欄位改型別隨 B1-5。object key 另用 v4 隨機值（`storage.NewKey`），不由 ID 推得 |
| 暫存 TTL 30 分鐘（`media.upload.session-ttl-minutes`），完成時再延長為預覽 TTL 3600 秒（`UploadSessionService.java:62-63`） | 使用者上傳到擁有者表單送出之間的時間夠用，過期的暫存能被回收 | 部分成立：兩段時間是為了「完成後給預覽時間」，Go 的狀態機不需要延長（處理在確認之前、列的期限一直是同一個） | 一個從建立起算的期限，涵蓋上傳、處理、填表與確認 | 單一常數 `model.UploadTTL = 1 小時`（從 BeginUpload 起算，整個模組唯一定義，`media.UploadTTL` 是它的別名），不延長；預簽網址有效期 `PresignTTL` 15 分鐘，啟動時檢查不超過 TTL。1 小時是比 Java 的 30 分鐘加 60 分鐘更短的單一期限（Will 2026-11-22 同意；卡住列的寬限 `StuckUploadGrace` 3 小時與重試間隔上限 `ProcessMaxBackoff` 15 分鐘同日同意），改長只改這一處 |
| 過期暫存的 GC：搶 60 分鐘租約、刪物件、標 EXPIRED，R2 失敗保留列（`MediaGarbageCollectionJob`，`GC_LEASE_MINUTES`） | 多個 worker 不重複刪、物件刪失敗不遺失 | 部分成立：租約是為了避免 Java 多個 pod 重複刪；單體的 River periodic job 由 leader 排入，刪物件本身冪等 | 先標記後刪物件，刪失敗留在標記狀態重試（單體規則 5） | 不搬租約：階段一在 transaction 內以 `FOR UPDATE SKIP LOCKED` 把過期且未確認的列轉 `DELETING` 並提交，階段二在 transaction 外刪 `tmp/` 物件、暫存列記的正式 key（`READY` 或處理中途 `REJECTED` 都可能已寫出）與資產列的物件，階段三另一個 transaction 轉 `DELETED`；刪失敗的列留在 `DELETING`，下一輪（job 重試或 5 分鐘後的排程）重來，不會有「列已刪、物件還在」或指著不存在物件的有效列（缺陷 5.17）。`UPLOADED`（處理中）正常由處理 job 的最終失敗轉 `REJECTED` 後進 GC；job 遺失、崩潰或暫時錯誤卡住的 `UPLOADED` 列，過期超過 `model.StuckUploadGrace`（3 小時，大於所有嘗試加退避，`TestStuckUploadGraceOutlastsEveryProcessAttempt` 守）也由 GC 回收。處理完成後刪 `tmp/` 物件失敗，由 bucket 對 `tmp/` 的 lifecycle 兜底（`CONFIRMED` 的列不進 GC） |
| 孤兒資產 GC（`cleanOrphanedAssets`，刪沒有引用的資產） | 資產與引用分在兩處，所以要掃沒人引用的資產 | 不成立：引用只存在擁有者的資料表（B1-D1），資產要嘛已確認（擁有者持有，只有 `MarkDeleted` 才刪），要嘛仍是暫存（走過期暫存 GC） | 擁有者的刪除指令加物件回收，不掃孤兒 | 不搬；「GC 只刪過期、未確認的暫存」寫進模組不變量，由 `TestGC_NeverDeletesConfirmedAssets` 守 |
| 刪除指令走 outbox 事件（ADR `2026-10-03` 決策段字面） | media 要獨立部署、指令不能遺失 | 不成立：同一個 Postgres、同一個單體 process，沒有獨立部署的計畫（B1-D9） | 同 transaction 的狀態標記加 job（單體規則 4） | `MarkDeleted(ctx, assetIDs)` 在擁有者的 transaction 內把 `ACTIVE` 的資產轉 `DELETING` 並排實體刪除 job（job 合併；正在執行的那一輪之後才標記的列由下一輪 GC 補掃，因為 GC 一併處理所有 `DELETING` 的列）；冪等，未確認、已刪、不存在的 ID 忽略。ADR 文末修訂隨 B1-5 |
| 確認時才建資產列（Java 在 Finalize 內複製物件並寫 `media_asset`） | 資產要在被引用之前存在 | 不成立：處理 job 已在確認之前寫好正式物件 | 處理完成時建資產列，確認只改狀態 | 處理 job 以一個 transaction 建資產列（`STAGED`）並把暫存列條件式轉 `READY`；`Confirm` 在擁有者 transaction 內把暫存列 `READY → CONFIRMED`、資產 `STAGED → ACTIVE`，重入回暫存列記的同一個資產，只回這筆暫存的資產（缺陷 5.1：Java 的 `findExistingAsset` 在 session 沒有資產時退回該上傳者最新的任一資產，可能回別次上傳的；Go 找不到就報內部錯誤）。處理中途列過期時條件式轉換失敗，刪掉剛寫的正式物件並把列轉 `REJECTED`（原因 `EXPIRED`，讓 GC 回收 `tmp/`；這一步是計畫沒寫明的補充） |
| 白名單加逐段搬運的 metadata 剝除，不解碼不重新編碼（`ImageMetadataStripper`） | 原圖會被 image gateway 原樣直出，相機寫的 GPS、序號不能跟著公開 | 成立 | 業界常見的是用圖片函式庫（libvips、ImageMagick）解碼後重新編碼：輸出只含像素，不必逐一理解各容器的區段 | 不沿用；`internal/image` 以 `github.com/cshum/vipsgen`（libvips）重新編碼，取代逐位元組剝除（ADR `2026-11-22-media-public-image-reencode.md`）：magic bytes 只放行 JPEG／PNG／WebP／GIF，解碼後套用方向、轉 sRGB、丟掉全部 metadata；靜態不透明輸出 JPEG（品質 90）、有透明輸出 PNG、動態 GIF／WebP 輸出同格式動態圖。代價是有損與 CI、本機要裝 libvips |
| 剝除後只留方向，重寫成只含 Orientation 的最小 EXIF（JPEG APP1、PNG `eXIf`、WebP `EXIF` 加 VP8X 旗標） | 手機直拍的照片要靠方向旋轉才正確，丟掉會橫躺 | 部分成立：從零設計是上傳時就把像素旋正、不留任何 EXIF | 業界做法同上 | 不沿用；重新編碼時直接把像素依方向旋正，輸出不帶任何 EXIF。動態圖不套用方向（各影格疊成高圖，旋轉會打亂影格） |
| 解碼前的資源上限（Java 只限上傳位元組數） | 小檔案可以展開成極大像素（decompression bomb），解碼會吃光記憶體 | 成立 | 業界做法是讀標頭後先檢查像素數再解碼 | 新增；`model.MaxImagePixels` 4000 萬（單格，約 7000x5700，涵蓋現行手機與相機的最高解析度；解碼後 RGB 約 120 MB、含轉色約 2 倍）、`model.MaxAnimatedPixels` 5000 萬（動態圖影格數乘每格像素；全部影格以 RGBA 載入約 200 MB）。超過回 `UNRECOGNIZED_FORMAT`（沒有獨立原因碼，見 `RejectReason`）。libvips 執行緒設 1、運算快取全關：並行度來自同時執行的處理 job，每個上傳內容不同，快取不會命中。上限是「每個 job」的；處理 job 在專用 River queue `model.ProcessQueue`（`media_process`）、併發 `model.ProcessQueueWorkers` = 2（與像素上限同在 `model`，cmd/hawkr 的 worker 角色設定該 queue），每個 process 的解碼記憶體預算 = 2 x（單格約 120 MB、含轉色約 2 倍，動態約 200 MB）≈ 最壞 0.5 GB。vipsgen 沒有中止運算的介面（無 kill 或 progress 回呼），`Sanitize` 只在載入前與各步驟之間檢查 ctx；以 `ProcessTimeout` 5 分鐘涵蓋：本機實測（libvips 8.18.7、單執行緒）40 MP 雜訊 JPEG（12.7 MB）約 1.0 秒、1000x1000 x 50 格的動態 GIF 約 2.8 至 4.8 秒，餘裕超過 60 倍。載入後先以一次完整解碼確認像素，之後的轉色、方向與編碼失敗是一般錯誤（River 重試，用盡轉 `PROCESSING_FAILED`），只有載入、標頭與像素解碼失敗才是 `ErrMalformed`（永久）。APNG（IDAT 前有 `acTL`）回 `ErrUnrecognized`，因為 libvips 只讀第一格；有 alpha 通道但全部不透明的圖輸出 JPEG |
| 辨認不出格式：Java 回 `null`，由呼叫端「照原樣處理」 | 無 | 不成立：計畫不變量是「辨認不出就拒絕」，照原樣寫進 `public/` 等於繞過剝除 | 以內容辨認並拒絕不支援的型別是上傳處理的標準做法 | 不搬；`image.Sanitize` 回 `ErrUnrecognized`（HEIC 等也在此，由 client 先轉 JPEG），處理 job 轉成永久失敗（`UNRECOGNIZED_FORMAT`）；無法解碼（`ErrMalformed`）與超過像素上限（`ErrTooLarge`）同一個原因，因為 client 面對的結果都是「這不是可用的圖片」 |
| 內容型別取宣告值（Java 的 `Finalize` 沿用 session 記的 content type） | 無 | 不成立：宣告值是 client 給的，可能與內容不符 | 以內容辨認出的型別為準 | 不搬；`ProcessResult.ContentType` 與寫入 `public/` 的物件型別取自實際輸出格式（`image/jpeg`、`image/png`、`image/webp`、`image/gif`），資產列的 size 也取自重新編碼後的實際位元組 |
| 處理時驗實際大小與 MD5（Java 只靠預簽綁 Content-Type，事後 HEAD 兜底大小） | 預簽 PUT 雖綁 Content-Length 與 Content-MD5，但處理 job 是第二道、也是唯一讀到位元組的地方 | 成立 | 縱深防禦：儲存層與應用層各驗一次 | 新增；讀取以宣告大小加一為上限（多一位元組就判定「比宣告大」，記憶體不隨任意大的物件成長），大小不符 `SIZE_MISMATCH`、MD5 不符 `CHECKSUM_MISMATCH` 都是永久失敗；tmp 物件不存在也算永久失敗（`SIZE_MISMATCH`，與 B1-2b 的測試處理一致） |
