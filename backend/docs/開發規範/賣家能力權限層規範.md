# 賣家能力權限層規範

> 本規範為賣家能力權限層的最終權威，面向**未來所有實作賣家面機能的工程師**。權威設計見 `docs/詳細設計書/46-賣家能力權限層（Seller Capability Authorization）詳細設計書.md`。
> **核心原則**：「這個賣家能不能做這件事」只有一個推導點——seller 模組的 `CapabilitiesOf`。Connect 入口與 gateway 都只檢查能力集合的成員，不自己從停權或生命週期推導。

---

## 一、為什麼有這層（背景）

賣家 gating 散落在各入口，「賣家能做什麼」就沒有 SSOT，停權漏洞會在新機能重新出現。**新機能跳過本規範 = 把停權漏洞重新鑿回來。**

---

## 二、新入口必宣告 capability（強制）

實作任何**賣家面機能**（新增/修改賣家可觸及的 Connect 方法、HTTP 路由或功能）時：

1. **Connect 的賣家方法**：在 `internal/httpapi/seller/declaration.go` 的宣告表加一筆——需要的 `model.Capability`，或豁免並附理由。表與 `SellerAppService` 的方法必須一一對應，缺宣告或多餘宣告使 service 不能啟動。handler 不自己檢查能力，interceptor 以 `seller.ActingStore` 檢查並把店家放進 ctx。
2. **gateway 的賣家專屬路由**（尚未搬進單體的服務）：一律 `requireSeller(cap)`（capability 為**必填參數**，宣告=掛載合一）。不給 capability 編譯不過。
   - 群組級掛載處若群組內路由 capability 不同 → 拆 per-route 或子群組。**capability 粒度決定掛載粒度**：同 capability 才可共用群組級掛載。
3. **買賣共用 `?view=` 路由**：用 `sellerViewGuard(cap)`——`view=seller/selling` → 賣家面走能力檢查；其他 view → 放行（買家面）。授權判斷移出 handler，HTTP 契約仍保留 `?view=`（前端相依）。
4. **JWTAuth-only 共用路由要豁免**：必須列入 46 號設計書 §4.4 豁免清單並**附「為何豁免」理由**（review 檢核）。**禁止裸 `JWTAuth()` 承載賣家專屬功能。**
5. **禁止 `/api/v1/app` 下新增 wildcard `Any("/*path")` 代理路由**——它使路由表 ≠ 攻擊面全集，deny-by-default 保證失效；boot 斷言會 panic（見四）。
6. **新增能力**：在 seller 模組的 `model/capability.go` 加常數與 `needs` 一列（能力需要哪些條件），同時在 gateway 的 `authz/capability.go` 加同名 token（`TestCapabilityTokensMatchGateway` 守兩邊一致）。能力 token **不進 CodeMeta**（CodeMeta SSOT 對象是跨服務/前端可見值）。

---

## 三、禁止散落判斷（強制）

- 賣家能力與停權的**推導只准在 seller 模組的 `CapabilitiesOf`**；gateway 的 `IsSeller(` 與停權判斷只准出現在 authz package 與 router 的 seller guard。禁止在 handler / usecase 內自行組裝賣家身分或停權 `if`。
- **唯一例外類**：IM / social 的「訂單關聯細分」（設計書明列）——gateway 看不到 payload，由下游 usecase 讀 `injectSellerSuspension()` 注入的 `X-Seller-Suspended` header 做細分（判準綁定對話雙端、order_no 伺服器端推導，見 46 號 §4.4 + 14 號）。此例外**不得擴大**到其他機能。
- 這條**沒有 CI lint 在守**（無對應 gate，全靠 review）：`grep 'IsSeller('` 應只落在 authz package 與 router 的 seller guard（`gateway/internal/router/seller_capability.go`），出現在其他 handler / usecase 即視為違規。

---

## 四、結構性防呆（不可移除）

1. **Connect 啟動期**：`CheckDeclarations` 雙向對照宣告表與 descriptor，缺、多、不合法都使單體不能啟動。
2. **gateway 編譯期**：`requireSeller(cap Capability)` 唯一簽章——新賣家路由不宣告 capability 編譯不過。
3. **gateway 啟動期斷言（boot fail-fast）**：router 建構後 walk `engine.Routes()`，斷言 (a) `/api/v1/app` 下無未豁免 wildcard；(b) `strictSellerPrefixes` 下每條路由都已宣告 capability，否則 **panic**（部署即炸）。
4. **CI 檢查**：`go test`——`gateway/internal/router/seller_capability_test.go` 的 `expectedSellerRoutes` 表逐條斷言 live authz registry 與功能矩陣終判**完全相等**，兩個方向的漂移（既有掛載改了 capability、新增 gated 路由沒進表）都會讓 CI 紅。

**殘餘風險**：機器無法判定「賣家路由被錯誤加進豁免清單」的語意錯誤 → 豁免清單每條附理由靠 review 把關；三的散落判斷禁令同樣無 gate，只能靠 review。

---

## 五、新賣家機能設計書必答題（強制）

新賣家機能的設計書**必須明載**：

1. **停權賣家可否使用 ＋ capability 歸屬**（該方法或路由掛哪個 `CAP_*`）。
2. **分類原則 deny-by-default**：只有以下四類才進停權白名單（suspended 仍可用，即該能力在 `needs` 裡不含 `NOT_SUSPENDED`）：
   - 訂單/出貨/售後處理（處理既有已付款訂單）；
   - 收縮型操作（只減不增，如 cancelShipment、刪自己貼文、撤自己券、關店）；
   - 救濟管道（查違規 / 申訴）；
   - 通知 / 看自己狀態。
   - **純唯讀查看也鎖**：dashboard / CRM 查詢 / 報表 / AI 助理即使唯讀也 BLOCK。唯讀 ≠ 放行。
3. 其餘一律 BLOCK（deny-by-default）。

---

## 六、收斂點不可繞（強制）

以下兩個收斂點檢查是停權正確性的兜底（兜住「繞過瀏覽路徑直接打 API」），**任何重構不得移除或繞過**：

1. **結帳鏈 `CheckoutValidate`** 的 `can_accept_orders` 檢查（fail-closed）——擋買家對停權賣家下單（直接打 API 亦擋）。
2. **product ACTIVE transition** 的 `can_accept_orders` 檢查（fail-closed）——停權賣家不得把商品轉 ACTIVE。

---

## 七、fail 策略（強制）

- **授權層一律 fail-closed**：推導出錯、`X-Seller-Capabilities` 與 `X-Store-Id` 不成對、不認得的 token 或停權原因，都拒絕（Connect 回錯誤；單體轉給 gateway 時不轉發）。停權狀態**沒有快取**，不得為效能加快取或標記。
- **收斂點（正確性關鍵）**：SellerMeta 查詢失敗 **fail-closed**（擋單/不得轉 ACTIVE）。

可用性由白名單能力保證：出貨/售後/救濟/通知/IM 的能力不因停權而缺。不得把授權層改成 fail-open。

---

## 八、狀態傳播與責任邊界

- 停權狀態**寫入權威 = seller 模組的措施**（`seller.effective_measures`）；沒有 Redis 標記，也沒有第二份狀態副本。能力在每個請求由權威資料推導。
- 轉給 gateway 的停權資訊只有 header：`X-Seller-Suspended`（管理員停權 9601、9602、9603，治理停權 `SUSPENDED_GOVERNANCE`，缺省 = 未停權）與 `X-Seller-Capabilities`，由 `internal/legacy/gatewayproxy` 對每個轉發的登入請求組出，gateway 只讀。
- **禁止**引入 reconciliation / backfill / drift 偵測（見 [後端服務責任邊界規範](./後端服務責任邊界規範.md)）；正確性由權威資料的即時推導與收斂點兜底。
