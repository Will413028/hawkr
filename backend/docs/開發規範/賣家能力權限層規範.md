# 賣家能力權限層規範

> 本規範為賣家能力權限層的最終權威，面向**未來所有實作賣家面機能的工程師**。權威設計見 `docs/詳細設計書/46-賣家能力權限層（Seller Capability Authorization）詳細設計書.md`。
> **核心原則**：「這個賣家能不能做這件事」只有一個問答點——Gateway authz package 的 `GrantedCapabilities(SellerContext)`。停權是第一個 policy，會員分級/個別權限是未來 policy，全部走同一層。

---

## 一、為什麼有這層（背景）

能力層建立前，賣家 gating 散落於 16 個 `requireSeller()` 掛載點 ＋ handler 內 `?view=` 分流 ＋ 2 條 JWTAuth-only 死代理 wildcard，「賣家能做什麼」無 SSOT，光盤點就耗掉整輪 session（全 405 條 /app 路由逐條人工判定，其中賣家面 106 條進功能矩陣終判）；`can_accept_orders` 抽象做了卻全 repo 零消費（設計意圖從未接線）。**新機能跳過本規範 = 把停權漏洞重新鑿回來。**

---

## 二、新路由必宣告 capability（強制）

實作任何**賣家面機能**（新增/修改賣家可觸及的 HTTP 路由或功能）時：

1. **賣家專屬路由**：一律 `requireSeller(cap)`（capability 為**必填參數**，宣告=掛載合一）。不給 capability 編譯不過。
   - 群組級掛載處若群組內路由 capability 不同 → 拆 per-route 或子群組。**capability 粒度決定掛載粒度**：同 capability 才可共用群組級掛載。
2. **買賣共用 `?view=` 路由**：用 `sellerViewGuard(resolver)`——`view=seller/selling` → 賣家面走能力檢查；其他 view → 放行（買家面）。授權判斷移出 handler，HTTP 契約仍保留 `?view=`（前端相依）。
3. **JWTAuth-only 共用路由要豁免**：必須列入 46 號設計書 §4.4 豁免清單並**附「為何豁免」理由**（review 檢核）。**禁止裸 `JWTAuth()` 承載賣家專屬功能。**
4. **禁止 `/api/v1/app` 下新增 wildcard `Any("/*path")` 代理路由**——它使路由表 ≠ 攻擊面全集，deny-by-default 保證失效；boot 斷言會 panic（見四）。

capability token 是 **Gateway 內部授權概念**，定義在 `gateway/internal/authz/capability.go`（Go 常數），**不進 CodeMeta**（CodeMeta SSOT 對象是跨服務/前端可見值）。

---

## 三、禁止散落判斷（強制）

- `IsSeller(` / 停權判斷（`suspended` 相關）**只准出現在 authz package**；禁止在 handler / usecase 內自行組裝賣家身分或停權 `if`。
- **唯一例外類**：IM / social 的「訂單關聯細分」（設計書明列）——Gateway 看不到 payload，由下游 usecase 讀 `injectSellerSuspension()` 注入的 `X-Seller-Suspended` header 做細分（判準綁定對話雙端、order_no 伺服器端推導，見 46 號 §4.4 + 14 號）。此例外**不得擴大**到其他機能。
- 這條**沒有 CI lint 在守**（無對應 gate，全靠 review）：`grep 'IsSeller('` 應只落在 authz package 與 router 的 seller guard（`gateway/internal/router/seller_capability.go`），出現在其他 handler / usecase 即視為違規。

---

## 四、三層結構性防呆（不可移除）

1. **編譯期**：`requireSeller(cap Capability)` 唯一簽章——新賣家路由不宣告 capability 編譯不過。
2. **啟動期斷言（boot fail-fast）**：router 建構後 walk `engine.Routes()`，斷言 (a) `/api/v1/app` 下無未豁免 wildcard；(b) 每條路由屬「已宣告 capability ∪ 明文豁免清單 ∪ 買家面清單」三者之一，否則 **panic**（部署即炸）。
3. **CI 檢查**：`go test`——`gateway/internal/router/seller_capability_test.go` 的 `expectedSellerRoutes` 表逐條斷言 live authz registry 與功能矩陣終判**完全相等**，兩個方向的漂移（既有掛載改了 capability、新增 gated 路由沒進表）都會讓 CI 紅。

**殘餘風險**：機器無法判定「賣家路由被錯誤加進豁免清單」的語意錯誤 → 豁免清單每條附理由靠 review 把關；三的散落判斷禁令同樣無 gate，只能靠 review。

---

## 五、新賣家機能設計書必答題（強制）

新賣家機能的設計書**必須明載**：

1. **停權賣家可否使用 ＋ capability 歸屬**（該路由掛哪個 `CAP_*`）。
2. **分類原則 deny-by-default**：只有以下四類才進停權白名單（suspended 仍可用）：
   - 訂單/出貨/售後處理（處理既有已付款訂單）；
   - 收縮型操作（只減不增，如 cancelShipment、刪自己貼文、撤自己券、刪帳號）；
   - 救濟管道（查違規 / 申訴）；
   - 通知 / 看自己狀態。
   - **純唯讀查看也鎖**（2026-07-10 裁決）：dashboard / CRM 查詢 / 報表 / AI 助理即使唯讀也 BLOCK。唯讀 ≠ 放行。
3. 其餘一律 BLOCK（deny-by-default）。

---

## 六、收斂點不可繞（強制）

以下兩個收斂點檢查是停權正確性的兜底（關閉 Gateway fail-open 殘留），**任何重構不得移除或繞過**：

1. **結帳鏈 `CheckoutValidate`** 的 `can_accept_orders` 檢查（fail-closed）——擋買家對停權賣家下單（直接打 API 亦擋）。
2. **product ACTIVE transition** 的 `can_accept_orders` 檢查（fail-closed）——停權賣家不得把商品轉 ACTIVE。

兩者是 A5 抽象的首次接線（歷來零消費，見 46 號 §11）。

---

## 七、fail 策略（強制遵守非對稱設計）

- **可用性關鍵（白名單 capability：出貨/售後/救濟/通知/IM）**：guard 不查 Redis，Redis 故障零影響——出貨/售後永不因授權層斷。
- **BLOCK-if-suspended capability**：Redis 故障 **fail-open**（放行）——避免 Redis blip 打擊全體 active 賣家可用性。
- **收斂點（正確性關鍵）**：SellerMeta 查詢失敗 **fail-closed**（擋單/不得轉 ACTIVE）。

不得把可用性層改 fail-closed 或把正確性層改 fail-open（打破 defense-in-depth）。

---

## 八、狀態傳播與責任邊界

- 停權狀態**寫入權威 = seller-service**（`SetSellerSuspended`/`ClearSellerSuspended`，Redis key `seller:suspended:<accountId>`，無 TTL）；Gateway 只讀。
- `sellers.status` 單欄多來源，所有寫 status 路徑一律呼叫 domain helper `recomputeSellerStatus()`（precedence：deleted > suspended > suspended_governance > active），禁止各路徑直接寫死值。
- **禁止**引入 reconciliation / backfill / drift 偵測（見 [後端服務責任邊界規範](./後端服務責任邊界規範.md)）；Redis 為加速層，`sellers.status` 為權威，正確性由收斂點兜底。
