## 新增服務 — 共用步驟

不論 Go 或 Java，以下幾個地方**都必須**更新。

> 🔴 **本節不完整，而缺漏的那幾類全部是靜默的。** 2026-08-29 新增 invoice-service 時實查
> 出六類本指南從未涵蓋的登記位置——它們的共同特徵是**漏掉不會編譯錯、不會測試紅、
> CI 全綠**，逐類與後果見下方〈本指南曾經漏掉的六類〉。做新服務時那一節與本節同等必讀。

### 0. 本指南曾經漏掉的六類（每一類都不轉紅）

| # | 類別 | 具體位置 | 漏掉的後果 |
|---|---|---|---|
| 1 | **CI workflow 的手寫服務清單** | `.github/workflows/go-checks.yml` 的 module 清單、`code-quality.yml` 的 `for svc in`、（有 testcontainers 才需要）`integration-tests.yml` | 該服務**永遠不被那支 workflow 檢查**，而 workflow 本身照樣綠 |
| 2 | **NetworkPolicy** | `k8s/external-services/networkpolicy.yaml`：新服務自己的 `*-ingress`（每個對外 port 一條 `from`）＋ **它要呼叫的每個上游服務的 caller 白名單**（上游在 `external-services` 或該服務 chart 的 `networkPolicy.grpcAllowedCallers`，兩處擇一、不可都寫） | pod Ready、gRPC 全斷。⚠️ `podSelector` 的 label key 是 `app.kubernetes.io/name` 不是 `app`——寫錯不會有任何錯誤，policy 照樣 apply 成功，只是那條 `from` 匹配到零個 pod |
| 3 | **`scripts/init-databases.sh` 的 `DATABASES`** | 加一行 DB 名 ＋ `scripts/README.md` 的 service ↔ DB 對照表 | DB 不存在 ⇒ pod CrashLoop（`database does not exist`） |
| 4 | **`db/atlas.hcl`** | Go 服務必備。四個細節任一寫錯會擋下**全部**服務的 deploy job，不只自己 | deploy job 全紅。**另外：`migrations/` 目錄必須真的產生過一次**（`atlas migrate diff`）——空目錄會讓 `make atlas-validate-all` 直接紅，而它是由 root `Makefile` 的 `GO_SERVICES` 推導的，服務一登記就被拉進來 |
| 5 | **監控** | `monitoring/prometheus/rules/*.yml` 的告警 group、`service-alerts.yml` 的 `ProdServiceAbsent`、`monitoring/sql-exporter/sql_exporter.yml` 的 job ＋ collector、兩份 compose 的 DSN、`monitoring/.env.example` | 監控 stack **不在 `deploy-k8s.yml` 的部署路徑內**，沒有任何 CI 會發現。漏掉的後果是告警 PromQL 回 no data ⇒ 永不觸發 ⇒ **與一切正常在儀表板上完全一樣** |
| 6 | **硬上限依賴治理登記** | `docs/開發規範/硬上限依賴接入治理規範（配額與容量）.md` §5 的依賴登記表 | 新服務帶進來的配額／容量上限沒有人在看 |

**兩個「自動偵測」的靜默陷阱**（§12.2.0 同源）：

- CI 的 build 服務清單是靠 **`services/<name>/Dockerfile` 存在**自動偵測的 ⇒
  Dockerfile 檔名打錯或缺席 ＝ 該服務**從不 build、從不部署**。
- Dockerfile 有、`k8s/values/<release>.yaml` 沒有 ⇒ 腳本只印一行 WARNING 就 `continue`
  ⇒ **服務從未部署**。⇒ 兩者必須列為同一個交付項。

✅ **2026-09-06 起這兩個方向都會讓 CI 轉紅**（在那之前是「CI 全綠」，本節原文如此記載）：
`k8s/scripts/test-content-addressed-tag.sh` 的**性質 8「build set 與 deploy set 雙向對得起來」**
——方向一「每個 release 宣告的 image 都算得出 tag」、方向二「每個算得出 tag 的 image
都至少有一個 release 部署它」。該檔逐字註明「8-9 是 2026-09-06 加的」。
它已完成 gate 的**三處登記**（`static-gates.yml` 的 step id `content_addressed_tag`
＋ 彙總 `env` ＋ 彙總 `report`）⇒ 失敗會真的讓 job 轉紅，不是只印紅字。

⚠️ **但兩件事仍然無聲**，這也是為什麼下面那句自檢要留著：
① **兩者同時缺席**（既無 Dockerfile 也無 values）——它不在任何一個集合裡，雙向都看不到它；
② **release 名不得靠與 image 同名推論**——一個 image 可以有多個 release
（現成先例：`social-service` 與 `social-media-reconciler` 共用 image），
所以「有 Dockerfile 就會有同名 release」是錯的推定。

**一句話自檢**：新服務第一次 merge 之後，去叢集 `kubectl get deploy <svc> -n hawkr`。
查不到就是踩到上面幾條之一。

### 1. 建立 Helm values 檔案

在 `k8s/values/<new-service>.yaml` 建立服務設定。Go 與 Java 的差異見下方各節。

### 2. 建立 Dockerfile

CI/CD 靠 `services/<new-service>/Dockerfile` 存在來偵測服務，**沒有 Dockerfile 就不會被 build 也不會被 deploy**。

### 3. Gateway — 加服務 host 設定

在 `k8s/values/gateway.yaml` 的 `config` 區段加入新服務的 host：

```yaml
config:
  NEW_SERVICE_HOST: new-service
  NEW_SERVICE_GRPC_PORT: "99X1"
```

### 4. 同步新增 docker-compose 本地容器定義

`docker-compose-local.yml`（本地開發）與 `k8s/values/*.yaml`（dev/prod 部署）是兩套並行維護的服務清單，**新增服務必須同步在 `docker-compose-local.yml` 加一段 service block**，否則本地起不了該服務（曾漏加導致啟動 Fx exit 1，issue #1500）。

在 `docker-compose-local.yml` 的 `services:` 下新增：

```yaml
  new-service:
    image: hawkr/new-service:latest    # 或 build:（依 Go / Java 慣例）
    # ... ports / depends_on ...
    environment:
      # 依賴哪個基礎設施，就配對應的連線變數（與其他服務用同一組值）：
      #   postgres → DB_HOST / DB_PORT / DB_NAME / DB_USER / DB_PASSWORD
      #   redis    → REDIS_HOST / REDIS_PORT / REDIS_PASSWORD（禁 REDIS_URL，見下方 Helm values 範例）
      #   rabbitmq → RABBITMQ_HOST / RABBITMQ_PORT / RABBITMQ_USERNAME / RABBITMQ_PASSWORD / RABBITMQ_VHOST
      # 其餘 environment key 要覆蓋 k8s/values/new-service.yaml 的 config + secretRef
      # 宣告的每個 key（compose 慣例上不需要者除外，見下方 CI gate）。
    healthcheck:                              # 必配；dev.sh status / up 的就緒判斷靠它
      test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:99XX/health"]
      interval: 10s
      timeout: 5s
      retries: 5
```

**CI gate 會擋漏加**：`static-gates.yml` 的「compose ↔ k8s/values 對齊檢查」step（`scripts/check-compose-k8s-align.sh`）在 PR 階段檢查兩件事——(1) compose 業務服務清單 == `k8s/values/*.yaml` 檔名集合；(2) 每服務 k8s 宣告的 config/secret key ⊆ compose environment（扣除腳本頂部白名單）。漏加 service block 或漏配 k8s 宣告的 key 都會讓 CI 失敗。若某 key 是 compose 慣例上不需要的（如 service discovery 靠 docker DNS、MQ 用分項變數而非 `RABBITMQ_URL`），把它加進腳本頂部白名單並註明理由。

**祕鑰禁寫死 default**：加密金鑰 / JWT secret 等機敏值一律 `${VAR}`（無 default，逼 `.env` 提供）或 `${VAR:-}`（空 default），禁止把真實金鑰當 fallback default 寫進檔案（compose 已入 git，default 洩漏 = 洩金鑰）。個人本地差異走 `docker-compose.override.yml`（gitignore，範本見 `docker-compose.override.yml.example`）。

## Go 服務額外步驟

### go.work 加入新 module

```bash
go work use ./services/new-service
```

### Helm values 範例

```yaml
# k8s/values/new-service.yaml
image:
  repository: <org>/backend-payuni/new-service

ports:
  http:
    containerPort: 99X0
    servicePort: 99X0
  grpc:
    enabled: true
    containerPort: 99X1    # HTTP + 1
    servicePort: 99X1

probes:
  healthPath: /health      # Go 固定用這個

resources:
  requests:
    cpu: 50m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi

config:
  SERVER_PORT: "99X0"
  GRPC_PORT: "99X1"
  DB_HOST: postgresql
  DB_PORT: "5432"
  DB_NAME: hawkr_newservice
  REDIS_HOST: redis
  REDIS_PORT: "6379"
  RABBITMQ_HOST: rabbitmq
  RABBITMQ_PORT: "5672"
  RABBITMQ_VHOST: /
  NACOS_ENABLED: "false"
  TRACING_ENABLED: "true"
  OTEL_EXPORTER_OTLP_ENDPOINT: otel-collector:4317

secretRef:
  - secretName: hawkr-db
    keys: [DB_USER, DB_PASSWORD]
  - secretName: hawkr-common
    keys: [REDIS_PASSWORD, RABBITMQ_USERNAME, RABBITMQ_PASSWORD, RABBITMQ_URL]
```

**`hawkr-common` 禁止宣告 `REDIS_URL`**（Go / Java 皆同）：Redis 連線目標的唯一來源是 `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD`。`REDIS_URL` 會靜默覆蓋 `REDIS_HOST`，且只活在 Secret（不進 git）——2026-07-29 事故即由此而來（20 服務連錯 Redis 跑 12 天）。CI gate `scripts/check-redis-single-source.sh`（`static-gates.yml` 的「Redis 連線設定唯一來源檢查」step）會擋。真的需要受管 / TLS Redis 時加一個顯式的 `REDIS_TLS` 旗標，不要加回會覆蓋 `REDIS_HOST` 的 URL。

## 新增環境變數

環境變數分兩類，放法不同：

| 類型 | 存放位置 | 範例 |
|------|----------|------|
| 非敏感設定 | `k8s/values/<service>.yaml` → `config:` | port、host、feature flag |
| 敏感資訊 | k8s Secret → `secretRef:` | 密碼、token、API key |

### 非敏感變數 — 直接加 config

直接在該服務的 `k8s/values/<service>.yaml` 的 `config:` 區段新增：

```yaml
config:
  SOME_FEATURE_FLAG: "true"
  EXTERNAL_API_URL: "https://api.example.com"
```

這會自動注入 ConfigMap，不需要額外操作。

### 敏感變數 — 加進 k8s Secret

Secret 是用 `k8s/scripts/create-secrets.sh` 從本機的 `.env` 檔一次性建立進 k3s 叢集，**不是**手動 patch、也不是把 `.env` 放到 VM。

現有的 Secret 群組（**權威清單**：`k8s/scripts/create-secrets.sh` 的 `kubectl create secret generic` 段落；由 repo 外流程手動建立的另登記在 `k8s/scripts/check-secret-declarations.sh` 的 `MANUAL_SECRETS`，兩者由 CI gate 對帳，不要憑本節記憶）：
- `hawkr-db` — DB 帳密
- `hawkr-common` — Redis、RabbitMQ、JWT（⚠️ 禁 `REDIS_URL`，見上方 Helm values 範例）
- `hawkr-r2` — R2 物件儲存憑證（`R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME`/`STORAGE_BACKEND`；僅 media-service／product-import-service 兩服務掛載）；`ENCRYPTION_MASTER_KEY`（機敏檔 AES-GCM 加密金鑰，機制不變）隨 media-service 續留同組（詳見 49 號設計書 §8.5）
- `hawkr-firebase` — Firebase credentials
- `hawkr-google-oauth` — Google OAuth client IDs
- `hawkr-payuni` — PAYUNi 金流設定
- `hawkr-ai` — AI API key
- `hawkr-origin-auth` — 來源驗證（CF ↔ origin）
- `hawkr-internal-auth` — 微服務間 HMAC 簽章密鑰（52 號設計書）
- `hawkr-address` — 地址驗證第三方憑證
- `hawkr-mitake` — 三竹簡訊憑證
- 手動建立（`MANUAL_SECRETS`）：`hawkr-media`、`hawkr-seller`、`hawkr-apple-pay`、`egress-proxy-caller-credentials`、`tgos-proxy-caller-credentials`

**步驟一：在 `.env.dev` 加入新變數**

```bash
NEW_API_KEY=xxxxx
```

**步驟二：在 `k8s/scripts/create-secrets.sh` 對應群組加入新 key**

```bash
kubectl create secret generic hawkr-common \
    --from-literal=REDIS_PASSWORD="$(get_env REDIS_PASSWORD)" \
    --from-literal=NEW_API_KEY="$(get_env NEW_API_KEY)"   # ← 新增這行
    --dry-run=client -o yaml | kubectl apply -f -
```

**步驟三：SSH 進 VM，更新 `.env`，重新執行腳本**

```bash
# 1. 把更新後的 .env 傳到 VM
scp .env.dev root@<VM_IP>:/tmp/.env

# 2. SSH 進 VM 執行（kubectl 在 VM 上直接操作本機 k3s）
ssh root@<VM_IP>
./k8s/scripts/create-secrets.sh /tmp/.env hawkr
```

**步驟四：在服務的 values 的 secretRef 加入 key 名稱**

```yaml
secretRef:
  - secretName: hawkr-common
    keys:
      - REDIS_PASSWORD
      - NEW_API_KEY    # ← 新增這行
```

### 跨服務共用的新變數

如果多個服務都要用這個新變數，在 `k8s/values/overlays/<env>/common.yaml` 加入（非敏感）或更新 Secret（敏感）。

### 服務名稱對應

Helm release name = 服務目錄名稱 = `k8s/values/` 下的 yaml 檔名（去掉 `.yaml`）。

三者必須一致：
```
services/java/order-service/        ← 服務目錄
k8s/values/order-service.yaml  ← values 檔案
helm release: order-service    ← Helm release name（自動對應）
```

---

### 服務互連 `connection refused`

k8s 內服務互相呼叫要用 **k8s service name**，不能用 IP。

```yaml
config:
  ORDER_SERVICE_HOST: order-service    # ✓ service name
  ORDER_SERVICE_HOST: 10.0.0.5        # ✗ IP（Pod 重啟會換）
```

### push 了但服務沒被重新部署

可能原因：
1. 修改的檔案不在 CI/CD 偵測範圍內（例如只改了文件）
2. `k8s/values/<service>.yaml` 不存在，CI/CD 會 WARNING 並跳過
3. `services/<service>/Dockerfile` 不存在

用 GitHub Actions 手動觸發並勾選「強制重新 build 所有服務」可強制全量部署。
