# 硬上限依賴接入治理規範（配額與容量）

> 制定：2026-07-30（源起：backend#2014 —— 2026-07-29 dev 全站無法登入數小時。root cause：gateway session 寫在一個外部受管 Redis，其免費層月配額 500,000 commands 於 07-29T03:13:17Z 耗盡，寫 session 失敗 → 所有新登入 500）。
> 本檔為最終權威。

事故的病根不是「配額太小」，而是：**一個不能失敗的狀態，被放在一個沒有容量規劃、也沒有量測的地方。** 本規範把「算過、量得到、會叫」變成接入前置條件。

---

## 1. 適用範圍：什麼算「硬上限依賴」

**判準（一句話自測）**：這個依賴用滿了會怎樣？

- 答案是「**回錯誤／拒絕服務／丟資料**」→ 硬上限依賴，適用本規範。
- 答案是「變慢」→ 不適用（走一般效能監控）。

四類典型（不限於此）：

| 類型 | 例子 |
|---|---|
| 用量配額 | 月/日 request 或 command 數、API call 額度、免費層 quota |
| 容量上限 | Redis `maxmemory`、磁碟空間、物件儲存容量、MQ disk watermark |
| 連線數上限 | `maxclients`、DB max_connections、連線池上限 |
| 速率上限 | 第三方 rate limit、QPS 上限、Cloud Run max-instances |

適用對象包含**自架**依賴——自架不等於無上限，本次事故切回自架後上限只是換成 `maxmemory 512mb`（見 §4）。

## 2. 接入前置三件（缺一不得接上任何環境的生產路徑）

任何硬上限依賴接上任何環境的生產路徑之前，必須**同時**具備：

| # | 項目 | 驗收（做不到＝不合格） | 反例 |
|---|---|---|---|
| ① | **與該上限對齊的指標** | 監控裡同時有「**當前用量**」與「**上限值**」兩個 series，能直接算出佔比 | 只有 `used_bytes` 沒有 `max_bytes` → 永遠算不出離上限多遠，等於沒量 |
| ② | **告警規則** | 至少兩條：**逼近上限**（比例或趨勢）＋**已觸上限的副作用**（逐出／拒絕／失敗計數） | 只設「服務掛了」告警——上限耗盡時服務通常還活著，只是開始拒絕，這條永遠不響 |
| ③ | **預算數字** | 白紙黑字寫在文件裡：現況用量、上限、單位成本（每筆佔多少）、上限能撐多少、什麼情況會逼近 | 「應該夠用」「量很小」——沒有數字＝沒有預算 |

**「任何環境」包含 dev。** dev 不是豁免區：本次炸的正是 dev，全體開發與 CI 停擺數小時。判準是「**這條路徑上有沒有人的工作會因為它失敗而停下**」，不是環境名稱。

## 3. 選型判準：按次計費的服務不適合放需要被監控的東西

**這是本規範最違反直覺、也最重要的一條。**

實測一（#2014，事故當下的外部受管實例）：抽樣 60 秒共 106 個指令，其中 **76 個（72%）是監控 exporter 自己發的**（INFO / SLOWLOG / LATENCY / CONFIG），應用層僅 13 個。

實測二（本 repo 自架 dev 實例覆核，2026-07-30 由 Prometheus 累計指標取得，uptime 2,992,033 s）：

| 指令 | 次數 | 佔比 |
|---|---|---|
| `INFO` | 1,396,048 | 35.2% |
| `CONFIG GET` / `CLIENT SETNAME` / `LATENCY HISTOGRAM` / `LATENCY LATEST` / `SLOWLOG GET` / `SLOWLOG LEN` | 各 ≈ 199,46x | 合計 30.2% |
| 小計（exporter，不含 PING） | 2,592,846 | **65.5%** |
| 含 exporter 的 PING | 2,890,991 | **73.0%** |
| 全部指令 | 3,961,513 | 100% |

（全部指令＝`sum(redis_commands_total)`，上表各列佔比皆以此為分母。）

exporter 每次 scrape 平均發 **13** 個管理指令——`INFO` ≈7 ＋上列六個各 1，由本表累計數 ÷ 199,465 次 scrape 導出。**此數非固定值**：2026-07-30 以 1 小時窗口覆核（`increase(redis_commands_total[1h])`）為 **16／scrape**（`INFO` 10、六個管理指令仍各 1，`config|get` = 240 次 ÷ 240 scrape）。scrape 間隔 15.0 秒（2,992,033 s ÷ 199,465 次，1 小時窗口覆核 3,600 ÷ 240 亦為 15.0）。兩次獨立實測（外部 72% / 自架 73%）結論一致。

**推論**：在按次計費模型下，把一個依賴接上監控，等於**主要為監控本身付錢**。於是實務上必然二選一：

- 不接監控 → 零指標零告警，配額見底時第一個發現的是「使用者登不進去」，不是儀表板（本次事故的真實經過）。
- 接監控 → 監控吃掉大部分配額，配額規劃全部得為 exporter 重算。

**因此：按次計費（per-command / per-request 計量）的服務，根本不適合放需要被監控的東西。** 尤其不能放不能失敗的狀態。

**供需差（#2014 實測）**：免費層持續額度 0.19 commands/s；dev 實際 1.6~3.0 commands/s、尖峰 10.7 commands/s ＝ 供需差 5~15 倍、尖峰 55 倍。同一批流量在自架實例上是「量不到」的等級（2.57MB / 512MB）。本 repo dev 自架實例平均 1.32 commands/s（3,961,513 ÷ 2,992,033 s）＝ 月約 343 萬 commands ＝ 免費層 500,000 的 **6.9 倍**，其中 73% 是 exporter。

**負載從來不是問題，位置才是。**

## 4. 狀態放置判準（不能失敗的狀態 vs 可拋棄的快取）

| 類別 | 定義 | 放置要求 |
|---|---|---|
| **不能失敗的狀態** | 丟了會直接造成使用者可見故障：session、分散式鎖、冪等記錄、一次性 token | 必須放在①有預算數字②量得到③失效模型明確的地方；且**不得與無成長上限的快取共用同一個逐出預算** |
| **可拋棄的快取** | 丟了只是多打一次 DB：商品詳情/列表、分類表、地址查詢結果 | 可放共用實例，但必須認知：**它的成長會擠掉同實例的狀態** |

**禁止**：把兩者放進同一個 `allkeys-*` 逐出策略的實例，而快取端沒有成長上限——`allkeys-lru` 不區分 session 與快取，記憶體壓力下逐出的可能正是 session ＝ 靜默的大規模登出。

現況（自架 Redis）正是這個結構，已量化並記錄在 `docs/速查參考/Redis 快取管理.md` §5「容量與失效模型（容量契約）」，緩解與待辦同列該處。gateway 側「`redis.Nil` 被當成確實登出」的那一半已由 #2014 治本 A 在程式碼層消除。

### 5.1 R3 的預算數字（PostgreSQL／PlanetScale 連線）

**現況**（2026-09-11 由 `k8s/values/overlays/prod/` 逐服務計算：`Σ(replicas × pool)`）

| 項目 | 值 |
|---|---|
| 每個 Java 服務的 pool | `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE = 2`（prod overlay）。⚠️ **各服務 `application.yml` 裡寫死的 `maximum-pool-size: 10` 不生效** —— env var 優先權較高，該處註解逐字寫明 |
| 每個 Go 服務的 pool | `DB_POOL_MAX_CONNS = 2`（prod `common.yaml`） |
| 例外 | `invoice-service = 4`（八支常駐排程器各自持有連線，58 號 §9.4.1） |
| 多副本 | cart／order／payment／payuni-webhook 各 `replicas: 2` |
| **app 端連線上界合計** | **≈ 56** |
| **PlanetScale plan 上限** | **50** |

🔴 **56 > 50**：app 端的理論上界已超過直連上限 1.1 倍。**這不是缺陷，是設計** —— 所有 app 執行期連線走 `DB_POOL_PORT=6432`（PlanetScale 內建 PgBouncer，transaction pooling），把大量 app 端連線多工到少量後端連線。5432 直連只保留給 migration（Atlas／Flyway 的 session-level advisory lock 不支援 transaction pooling）與 admin bootstrap。

**能撐多少 / 何時逼近**

- **PgBouncer 在前面時**：app 端連線數不直接消耗 `max_connections`，瓶頸換成 PgBouncer 的後端 pool size。⚠️ **那個數字由 PlanetScale 管理、repo 內查不到**（待坐實：需 PlanetScale 主控台或 `SHOW POOLS`）。這是本預算目前唯一的未知數。
- **PgBouncer 失效、或有人把 app 指回 5432 時**：56 條連線立刻打爆 50。**2026-07-12 的 iptables incident 復原時就是這樣撞上的** —— 那次是直連撐不住才發現上限存在。
- **成長曲線**：每新增一個單副本服務 +2；每把一個服務的 prod `replicas` 從 1 調到 2 也 +2。以現況 56 推算，**再加 7 個單副本服務就到 70（上限的 1.4 倍）**，屆時 PgBouncer 的多工比要重新驗證。
  ⚠️ `replicas` 同時是《多副本排程搶佔規範》§29 的判定輸入 —— 調它的時候兩份文件都要看。

**單位成本**：PlanetScale 依 plan 計費，`max_connections` 隨 plan 檔次變動，**不是按連線數計價** ⇒ 逼近時的正確處置是「檢視 pool size 是否過大」而非「升 plan」（§8 已否決「加大額度當修法」）。

**何時要重算**：新增服務、調整任何 `DB_POOL_MAX_CONNS` / `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`、或調整 prod `replicas` 時。計算方式：逐服務從 `k8s/values/overlays/prod/` 讀，overlay 未覆寫者取 `common.yaml` / `java-common.yaml` 的預設。

## 6. 接入流程（新增硬上限依賴時照做）

1. **寫預算**：需求量（實測或估算）× 峰值倍數 × 成長頭寸 vs 供給上限，白紙黑字寫進對應文件；供需差 < 3 倍即視為不合格選型。
2. **接指標**：確認能同時取得「用量」與「上限」兩個 series。只有用量沒有上限 → 不合格（算不出佔比）。
3. **寫告警**：逼近上限（比例／`predict_linear` 趨勢）＋ 觸頂副作用（逐出／拒絕／失敗計數）各至少一條。
4. **登記** §5 表。
5. **演練失效**：明寫「上限到達時系統會怎麼表現」，並確認那個表現可接受（fail-closed／降級／明確拒絕，而不是靜默丟資料）。寫不出來＝失效模型不明，不得接上。

## 7. 禁止事項

- 禁止把 session／分散式鎖／冪等記錄放在沒有預算數字的依賴上。
- 禁止「先接上去再說，監控之後補」——本次事故的完整因果就是這句話。
- 禁止用「只是 dev」當豁免理由。
- 禁止把 exporter 關掉／調稀來省配額：那是拿可觀測性換成本，正是本規範要杜絕的交換（要省就換掉計費模型，見 §3）。
- 禁止把「加大額度／升付費方案」當作修法（見 §8 否決理由）。
- 已知缺口（R4 三件全缺）不得再複製到新依賴上；新接入一律走 §6。
  ⚠️ R3 的預算文件原本也在這份缺口清單裡，2026-09-11 補齊於 §5.1（#3331）——**那一節自己標了一個未坐實項**（PgBouncer 後端 pool size 由 PlanetScale 管），不要把它讀成「已經沒有未知數」。

## 8. 已評估並否決的止血方案（#2014）

| 方案 | 否決理由 |
|---|---|
| 加大額度 / 升付費方案 | 位置與失效模型都沒變，配額仍是硬上限，只是把炸的時間往後推；且監控佔 72~73% 指令的結構不變 → 付的錢主要買監控（§3） |
| 降低 CI / 健康檢查頻率 | 拿可觀測性與驗證頻率換配額；且 dev 用量本就是自架實例「量不到」的等級（2.57MB / 512MB），問題不在量 |
| 改打 prod 資源 | 把 dev 的失效直接接進 prod 的爆炸半徑，違反環境隔離 |
| 只修 gateway 讓它容忍 Redis 失敗 | **必要但不充分**（＝ #2014 治本 A，已實作）：它消除「Redis 讀不到就當使用者登出」，但 session 本身仍會消失、使用者仍需重登；不解決「不能失敗的狀態放在沒有容量契約的地方」 |

## 9. 教訓

**「量很小，應該不會有事」不是預算。** 上限存在而沒人算過、沒人量過、沒人設告警，等於把「什麼時候炸」外包給運氣；而按次計費的服務連監控都要收錢，於是它天生就把你推向「不要監控」——這正是它不該承載重要狀態的原因。
