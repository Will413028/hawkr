# 後端服務責任邊界規範

> 本團隊**沒有獨立 ops / SRE 角色**。後端工程師同時負責 application 程式碼與運維動作。責任邊界劃在「程式碼層級」而不是「角色層級」。

## 一、三類動作分類

### 屬於 application code（codebase 內必須做）

- 業務寫入路徑寫對（create / update / delete / cascade **同事務**維護所有反正規化欄位）
- 讀取路徑根據當下 DB 狀態正確回傳

### 禁止寫進 application code（這條才是「不做」）

- `*BackfillCLI.java` / `*BackfillRunner.java`（一次性歷史資料補值的 application）
- `*ReconciliationJob.java` / `@Scheduled` drift 偵測
- `reflow_task` / `resync_task` 等補償任務基礎設施表 + runner
- application-level outbox（除跨服務 saga 業務 unwind）

### 仍是後端工程師責任（不寫進 codebase 但必須主動做）

**日常責任**（每次有相關需求時都會碰到）：

- **環境變數變更**：四個位置必須一起改，**缺一即靜默失效**（完整步驟見 [開發工作流程](./開發工作流程.md) §3「環境變數配置流程」）：
  1. 各 `.env*`（`.env` / `.env.dev` / `.env.local` / `.env.template`）—— 只改這裡，遠端 k3s 讀不到。
  2. `docker-compose-local.yml` 對應服務的 `environment` —— 漏了本地容器讀不到（compose ↔ `k8s/values` 的對齊由 CI `static-gates.yml` 把關）。
  3. `k8s/values/{service}.yaml`（敏感放 `secretRef`、非敏感放 `config`）—— 漏了部署後服務拿不到值。
  4. Secret 的**值**不進 git，但**有哪些 key、值從哪來**必須進 git（`k8s/scripts/create-secrets.sh` 建立 + values 的 `secretRef` 引用），由 `k8s/scripts/check-secret-declarations.sh` 在 CI 把關。values 引用了沒有任何 repo 流程建立的 key 時 **pod 照樣起得來、該功能靜默失能**（`PAYUNI_API_URL` 曾因此讓 prod 三個服務全打 sandbox）。

  改完 commit + push → PR（base `dev`）→ merge → CI/CD apply。**禁止 SSH 進 VM `kubectl patch` 取代這條路**（不 rebuild image ＝ 假部署，且叢集狀態脫離版控、下次 CI 部署會被蓋掉）。
- **一次性舊資料清整**：
  - **小量 / 單純 backfill** → 寫成 `V{N+1}__backfill_xxx.sql` 走 Flyway 自動 apply（推薦）
  - **大量 / 分批 / 需停機協調 / 跨 DB** → 手動連遠端 DB 跑 SQL `UPDATE / DELETE`
  - **清測試殘留** → 手動 SQL（驗證完當下就清，不要留 row 等 cron 或交給下一個人）
- **純 configmap patch 後的 rollout restart**：configmap 變更不會自動重啟 pod。但**一般部署 CI/CD 已 rollout**，只有「configmap 改了但沒重新 deploy」才需要手動 `kubectl rollout restart`。

**緊急 SOP**（不該發生但發生時要會處理，不算「常規」）：

- **Flyway checksum mismatch**：平時不該發生（V1 凍結、V2+ append-only）。若發生通常代表有人改了 V1 或環境間 Flyway state 不一致，正解是把 history 表的 checksum 對齊回當前 SQL 檔案（`flyway/flyway` 官方 image 直接跑 `repair`，不執行任何 DDL、不碰業務 table、可重複執行；命令與各服務 DB 名對照見 [38-Flyway 自動同步詳細設計書](../詳細設計書/38-Flyway%20自動同步與%20DB%20自動初始化（Flyway%20Auto%20Sync%20%26%20DB%20Auto%20Init）詳細設計書.md) §4 Step 3）。**不要改 V1 檔案讓 checksum 過**——那會破壞凍結、把問題推給下一個環境。

> ⚠️ **DDL 不在這層**：自 2026-05-26 V1 凍結 + V2+ 自動同步後，**所有 schema 變更走 `V{N+1}__xxx.sql` 由 CI/CD Flyway 自動 apply 到 dev / stage**（詳見 [38-Flyway 自動同步詳細設計書](../詳細設計書/38-Flyway%20自動同步與%20DB%20自動初始化（Flyway%20Auto%20Sync%20%26%20DB%20Auto%20Init）詳細設計書.md)）。**禁止**手動 SSH 進遠端 DB 跑 `ALTER` / `CREATE`，反而會破壞 Flyway 狀態。

## 二、判定關鍵字

規劃時遇到下列關鍵字，**先反問**：「這要寫進 application code 嗎？還是 SQL / script 一次性執行？」前者一律拒絕（污染 codebase），後者**必須主動做**，不可回答「這不是後端責任」。

| 關鍵字 | 反問 | 處理 |
|---|---|---|
| reconciliation / 對齊 | 正常寫入路徑會 drift 嗎？ | 不會 → 直接 SQL；會 → 修寫入路徑 |
| reflow / re-sync | 觸發點是寫入入口嗎？ | 是 → 同事務 cascade；否 → 直接 SQL |
| backfill | DDL 後既有 row 補值？ | 直接 SQL（不寫 CLI） |
| async runner / job | 同事務不行嗎？ | 同事務通常可；上線資料量真撐爆再加 |
| drift detection | 屬監測層級？ | 監測屬 observability，不在 application |

## 三、屬於後端 vs 不屬於後端

| 範疇 | 後端責任 | 不在後端 |
|---|---|---|
| Create / Update / Delete / Cascade 同事務內維護所有反正規化欄位（cat_*_name、searchable_text、counter 等） | ✅ | |
| 同事務內 row-lock 維護 counter（多 row 場景按 id ASC 排序避免死鎖） | ✅ | |
| 讀取路徑根據當下 DB 狀態正確回傳 | ✅ | |
| 既有資料 backfill（DDL 加新欄位後既有 row 補值） | | ✅ 直接 SQL |
| Counter drift 偵測 / reconciliation job | | ✅ 直接 SQL |
| Async 大批補償任務基礎設施（task 表、runner、worker） | | ✅ |
| Sample 比對 / drift 偵測 / 不一致記 ERROR 監測 | | ✅ DB observability |

> **「即使只是偵測 + log warn」也算後端在做資料完整性監測，仍違反邊界**。監測屬資料層，不屬 application。

## 四、不應該存在的元件清單

下列元件**不應**存在於微服務 codebase（除非經 review 確認有業務理由）：

- `*ReconciliationJob.java` / `*ReconcileJob.java`
- `*BackfillCLI.java` / `*BackfillRunner.java`
- `reflow_task` / `resync_task` / `compensation_task` 類「任務記錄表」+ runner
- `@Scheduled` 跑「sample 比對」「drift 偵測」「count 校對」的 class
- application-level outbox（除跨服務 saga 業務 unwind 外）

## 五、cascade 處理採同事務、不切兩條路

寫入入口（admin 改 category 名、批次更換 category）影響大量 row 的反正規化欄位時，**同事務內逐筆 reflow**：

```java
@Transactional
public void updateCategoryName(...) {
    categoryRepository.updateName(id, newName);
    // ✅ 同事務內直接 reflow
    productCascadeService.reflow(affectedIds, "CATEGORY_RENAME");
}
```

**禁止**：

```java
// ❌ 把 cascade 切成 sync 與 async 兩條路
if (affected.size() <= 200) syncReflow(affected);
else writeReflowTask(affected); // 補償任務基礎設施
```

上線後若真因資料量超大導致 timeout，那是**容量問題**；schema 不需動、加 runner 不算 DDL 變更。設計階段不先做。

## 六、設計書 §一致性章節必寫

`§一致性、交易與補償` 章節必須明寫：

> **單一寫入路徑為唯一真實來源；不引入補償任務基礎設施。**
>
> 寫入路徑：[列出所有寫入點]，每個寫入點同事務內維護所有反正規化欄位 + counter。
>
> 不做：reconciliation job、async reflow runner、backfill CLI、sample 比對監測。
>
> 既有資料維護由開發者直接 SQL 處理，不在後端寫補償流程。

## 七、例外（罕見）

> **單體（2026-09-24 起）**：下列 1、2 兩類例外的前提是「跨服務、沒有共用的 transaction」。單體內模組共用同一個 transaction（`docs/adr/2026-09-24-go-modular-monolith.md` D4），跨模組的業務 unwind 與「commit 後保證事件發出」都不再需要 saga 或 outbox；剩下的例外只有外部 provider 呼叫，做法見 D5。本節只適用遷移期間仍在運作的舊服務。

下列情況可考慮例外，需於設計書明確標注理由：

1. **跨服務 saga 業務 unwind**（如付款失敗 unwind 庫存扣減）— 分散式系統不可避免，但**只限跨服務、只限業務 unwind**。
2. **Outbox 模式**（DB commit 後保證 MQ event 一定發出）— 技術可靠性，與資料清整無關。
3. **CDC 整合** — 由 DB 層或專用平台處理，application 只是消費者。

**判定準則**：**這個基礎設施存在的目的是「業務正確性」還是「資料完整性監測」？** 前者可考慮，後者一律歸維運 SQL。

**判準補充：同步前置 gate ≠ reconciliation job（issue #1349）**：於既有 mutate 動作**執行前**、在**同一觸發流程內**同步查 SoT 以決定分支（例：訂單逾期取消前反查 payment `GetActivePaymentStatusByOrderNo`，PAID 則不取消並經既有冪等路徑收斂 → PAID），屬**把寫入路徑寫對**（§一首條，等同 CAS 前置檢查），**不是**補償任務基礎設施，不需標例外。與被禁止的 reconciliation / drift job 分辨：

| 特徵 | 同步前置 gate（允許，屬 §一寫入路徑） | reconciliation / drift job（禁止，§二） |
|---|---|---|
| 觸發 | 綁在既有寫入動作**之前**，逐單同步 | 獨立 `@Scheduled` 週期性掃描 |
| 資料結構 | 無 task 表 / 無 runner | 需 task 表 / runner / worker |
| 目的 | 該筆寫入的業務正確性 | 全表資料完整性監測 / 對齊 |
| 收斂 | 復用既有冪等寫入路徑 | 另寫補償邏輯 |

## 九、Frontend Cache Invalidation Contract（強制）

> 適用於 `hawkr-website` 前端 Next.js `'use cache'` 包裝的 SSR cache。對應 `backend-payuni#1041` / `hawkr-website#122`；系統性根治（傳輸重試 + 覆蓋缺口全補 + 防復發矩陣）見 `backend-payuni#1271`。

### 9.1 為什麼是 backend 的責任

`hawkr-website` 用 Next.js `cacheTag()` 包 SSR fetch（`lib/api/cached.ts`）。任何 backend mutation 改了某個 entity 的可見狀態 → 對應 `cacheTag` 必須在 mutation 完成後**即時 bust**，否則使用者要等 `cacheLife` profile expire（PR #122 為了不留壞體驗已縮到 5 分鐘）。

frontend 已備好 `POST /api/revalidate` endpoint + secret-protected + fails-closed。**呼叫 endpoint 是 backend 的責任** — 因為只有 backend 知道哪個 entity 被改了。

這不是維運動作（不像 §一「仍是後端工程師責任」列的那些 SQL / k3s 操作），是純 application code：
- 寫入入口同 transaction 完成後觸發
- 失敗只 log，不阻擋業務（best-effort，cacheLife 是 safety net）

### 9.2 Cache tag schema（SSOT 在 frontend；taxonomy 全貌見 53 號設計書 §4.1）

由 `hawkr-website/lib/seo/tags.ts` 定義。**backend producer 只發 entity tag**；domain-collection tag（`products:list` / `sellers:list` / `posts:list` …）由 web `/api/revalidate` 於信任邊界依 entity **展開產生**，**backend 不直接發**（展開映射見 53 號 §4.3）。

| Tag（backend 發） | 對應 frontend cache surface |
|---|---|
| `product:<id>` | `getCachedProduct` / `getCachedProductReviews`（PDP detail / reviews list）；經 web 展開 `products:list` / `posts:list` 失效所有商品卡列表（市集／首頁貨架／storefront）與含商品區塊的貼文卡 |
| `seller:<id>` | `getCachedSeller` / `getCachedSellerStats` / `getCachedSellerReviewStats` / `getCachedSellerReviews` / `getCachedSellerProducts` / `getCachedSellerStorefrontProducts`（seller profile / 賣場列表 / 賣家評論）；經 web 展開 `sellers:list` / `products:list` / `posts:list` 進而失效推薦賣家卡與含賣家名／頭像的商品卡、貼文卡 |
| `post:<id>` | 經 web 展開 `posts:list` 失效貼文流（`getCachedPublicPosts`） |
| `recipe:<id>` | 經 web 展開 `recipes:list` 失效當季食譜（`getCachedSeasonalRecipes`） |
| `hashtag:<id>` | 經 web 展開 `hashtags:list` 失效熱門標籤（`getCachedPopularHashtags`）。**key 是 hashtag 的數字 id，不是名稱**——理由見 §9.3 表格下方的警告 |
| `category:<id>` | 經 web 展開 `categories` 失效分類樹（`getCachedCategoryTree`，TTL 21600s 為全站最長） |

> 上列四個 entity tag 目前**沒有任何 fetcher 直接掛載**（web 端無 `postTag()` / `recipeTag()` / `hashtagTag()` / `categoryTag()` 的消費者），它們存在的唯一目的就是讓 web 於信任邊界展開成對應的 domain-collection。這是刻意的：producer 只知道「哪一筆變了」，不該知道「哪些聚合嵌了它」。

> **M3 tag 收斂（`hawkr-website#339` Phase 3）**：原 legacy `home` tag（唯一 producer＝product-service）已拆除，改由 producer 發完整 entity tag、web expansion 精準展開 domain-collection tag。**backend 不再發 `home`**（`ProductRevalidationService` 的 `HOME_TAG` 與 `*AndHome` 變體、Go `pkg/revalidate.HomeTag` 皆已移除）。

### 9.3 觸發點 matrix（強制 · 防復發 SSOT）

> ⚠️ 本表是「mutation → 必 bust tags」的**唯一真實來源**。任何改動 entity 可見狀態的 mutation 都必須在表中有一列，且 impl 與此表一致。**新增 / 修改 mutation 路徑必須回頭更新此表 + impl + dev verify**（屬本 §9 對齊責任）。
>
> ★ **判定原則（決定要不要共發 `seller:<sellerId>`）**：看該 mutation 是否改變**「這個賣家有哪些公開商品」**。
>
> - **改變**（建立即上架 / 刪除公開商品 / 上下架跨 ACTIVE / 賣家商品批次下架）→ 共發 `product:<id>` + `seller:<sellerId>`。
> - **不改變**（純欄位編輯：改價 / 描述 / 圖片；庫存增減；改分類 / 分類改名 cascade）→ **只發 `product:<id>`**。storefront 商品列表（`getCachedSellerProducts` / `getCachedSellerStorefrontProducts`）同掛 `products:list`，由 `product:<id> → products:list` 展開命中，不會出現「詳情頁新、列表頁舊」。
>
> 坐實依據（M3 step3，`#339`）：掛 `seller:<id>` 的 fetcher 全數不嵌商品欄位——`getCachedSeller` 只回賣家 profile 欄位（`seller-service/internal/grpc/mapper.go:14`）、`getCachedSellerStats` 的 `total_products` / `total_orders` / `total_sales` 後端**從未賦值**（`seller-service/internal/grpc/handler.go:298-315` 只填 rating / followers / reviewCount，web 亦只讀 `followers`）、`getCachedSellerReviews` 的 `sku_name` / `item_image_key` 是**訂單快照欄位**（`review-service/db/schema/schema.sql:15-16`）、推薦賣家榜由 order 營收排名驅動且無「有無在架商品」過濾（`seller-service/internal/usecase/recommended_sellers.go:31`）。故商品欄位 mutation 共發 `seller:<id>` 純屬 over-invalidation（會霰彈失效推薦賣家 rail 與 home-discovery bootstrap），已於 step3 收斂。
>
> ★★ **producer 自足原則**：backend producer 只發 **entity tag**（`product:<id>` / `seller:<id>`），發的 entity tag 必須**自足完整**——不靠 `home` 這種「顯示耦合粗網」補漏。landing 的失效由 web expansion（entity → domain-collection，53 號 §4.3）精準驅動：`product:<id>` 展開 `products:list` 涵蓋貨架組成變化，`seller:<id>` 展開 `sellers:list` 涵蓋推薦賣家卡。
>
> ⚠️ **行為變化知會（M3 既定）**：舊設計「賣家 routine 編輯不擴散、推薦賣家名／頭像 stale 由 TTL 收斂」在新 taxonomy 下改變——`seller:<id>` 現經 web `sellers:list` / `products:list` 展開即時失效推薦賣家卡與商品卡（坐實：卡片直接顯示 `seller.name` + `seller.logoUrl`）。此為**正確性提升**（消除賣家改名後列表顯示舊名的 under-invalidation），但比舊「TTL-bounded」策略多刷相關 landing。

**批次 mutation**：一次 mutation 一次 POST（去重後單次送出），禁止逐筆 POST。`batchChangeProductCategory` / `StockService` 走 `ProductRevalidationService.revalidateProducts`（只組 `product:<id>`×N，不需反查賣家）；`CategoryService.updateCategoryName` 走 `revalidateCategoryWithProducts`（分類樹 tag 與 cascade 商品 tag 屬同一 mutation，合成單次 POST）；`CategoryService.softDelete` 走 `revalidateCategories`；`SellerProductOffShelfService` 走 `revalidateProductsWithSellers`（反查每筆 `createdBy` 併入 `seller:<id>` 後去重）。

**內容側 under-invalidation 已補齊（#1919）**：貼文流 / 食譜 / 熱門 hashtag / 分類樹原本無任何後端 producer，內容變更只靠 `cacheLife` TTL 兜底（60s ~ 21600s）。此為「缺 producer」的 under-invalidation，與 M3 收斂處理的「over-invalidation + legacy home」不同 class（`#339` 裁決 D6，故未擴入 M3）。四條 producer 已補進上表（social-service 貼文＋hashtag、食譜（原 content-service，現為單體 content 模組）、product-service `CategoryService` 分類），web 端 expansion 早已就緒，backend 只發 entity tag 即生效。

> ⚠️ **hashtag tag 必須以「hashtag 的 id」而非名稱為 key**。web 的 `ENTITY_TAG` allow-list 是 `^(?:product|seller|post|category|hashtag|recipe):[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`，而 hashtag canonical 名稱保留 CJK / 全形字元原樣（`social-service/internal/domain/hashtag/normalizer.go`）。用名稱當 key → 任何中文 hashtag 都會被判 `invalid tag` 回 **400**，而該 endpoint 是**整包拒收**：同一次 POST 裡的 `post:<id>` 也會一起被丟掉，變成「貼文快取從此不失效」的靜默故障。共用 helper `pkg/revalidate.HashtagTag` 已封裝此約束，`pkg/revalidate/tags_test.go` 以該 regex 釘住全部 tag builder。

### 9.4 HTTP contract

```
POST {WEB_REVALIDATE_BASE_URL}/api/revalidate
Headers:
  Content-Type: application/json
  x-revalidate-secret: {WEB_REVALIDATE_SECRET}
Body:
  {"tags": ["product:123", "seller:456"]}

成功：200 { code: 0, message: "success", data: { revalidated: [...] } }
401：secret 不匹配（fails-closed，server side missing secret 也 401）
400：tags 空 / 格式錯
```

### 9.5 觸發語意（強制）

- **時序**：mutation 主 `@Transactional` commit **之後**才觸發（避免 HTTP 拉長 tx hold 時間）
- **執行模式**：fire-and-forget async（Java `HttpClient.sendAsync()` / Go `go client.Bust(ctx, tags)`）
  - **單體（`backend/internal/`）改用 River job**（ADR `2026-09-24-go-modular-monolith` D6 否決 in-process goroutine：行程重啟就遺失）：use case 在寫入的 transaction 內排入 `platform/revalidate.Args`，commit 後才會執行，所以「commit 之後才觸發」由 transaction 保證。timeout 5 秒與 WARN log 的規則不變，由 worker 實作。重試不照下面的「限連線層 IOException」：那條的前提是在請求路徑上 fire-and-forget，重試會拉長 ack；job 在 worker 執行、不佔請求，所以連線錯誤、timeout、5xx、429 都以 River 預設的退避（attempt^4 秒）重試，最多 5 次（最後一次約在 6 分鐘後，落在食譜的快取 TTL 900 秒之內）；其他非 2xx（400、401、404）是設定錯誤，取消不重試（Will 2026-09-27）。
- **錯誤處置**：失敗只走 `ObsLogger.warn` / `logger.Warn`，**不 throw**、**不阻擋業務 response**。**送出失敗（non-2xx / timeout / 例外）不得靜默吞掉**，必留 WARN log（含 tag 與狀態）供 obs 偵測
- **未啟用告警**：`baseUrl` / `secret` 任一為空 → client no-op，但**啟動時必發一次 WARN log**（明標「revalidate 未啟用，前端快取將不失效」），避免部署漏設 env 卻無任何訊號；不 fail 啟動（本地無此 config 時仍可開發）
- **timeout**：5 秒
- **重試（限連線層 IOException）**：僅對**連線層 IOException**（fast-fail，如 stale keep-alive pooled connection 被 server 端關閉後被 client 重用 → `header parser received no bytes`）做**冪等有限重試**（取 fresh connection，最多 2 次、無退避或極短退避）。`revalidateTag` 冪等，重試安全且不留副作用。**對 timeout / non-2xx（如 401 secret 不符）不重試**（那是設定問題 / 已延長的窗口，重試只會拖長 ack 不確定時間，且無助於恢復）。
  - 背景（#1271）：dev 實測 `send.error` ≈ 24% 全為此連線層 IOException；上次 PR #1041 強制 HTTP/1.1 只堵了「h2 打 cleartext server 被重置」一個成因，未堵「HTTP/1.1 stale pooled connection 重用」此第二成因，故同一錯誤簽名持續發生。fast-fail 重試取 fresh connection 即可安全消除，將失敗率壓到 <1%。
- **批次**：同 mutation 影響多個 tag 一次 POST（單一 request 含 N 個 tag 即可）

### 9.6 共用 helper

- **Java**：`services/java/shared/common-core/.../cache/RevalidateClient.java` Bean（底層用 `safeFetchHttpClient` bean）。連線層 IOException 冪等重試（§9.5）集中於此 helper，各服務只呼叫 `bustAfterCommit(tags)` 即自動享有重試，不各自實作。
- **Go**：`pkg/revalidate/Client`（重試同樣集中於此 helper）；單體是 `internal/platform/revalidate`（job 與 worker）
- 兩端皆讀 env `WEB_REVALIDATE_BASE_URL` + `WEB_REVALIDATE_SECRET`
- **HTTP 版本必須 HTTP/1.1（強制）**：frontend `/api/revalidate` 是 cleartext（`http://`）的 Next.js Node server，**不支援 HTTP/2 cleartext（h2c / prior-knowledge）**，收到 HTTP/2 連線即重置 → client 端拋 `java.io.IOException: HTTP/1.1 header parser received no bytes`，revalidate 永久靜默失敗。Java `HttpClient` 預設為 HTTP_2，故共用 `safeFetchHttpClient` bean **必須**顯式 `.version(HttpClient.Version.HTTP_1_1)`（此 bean 亦被 `SafeFetcher` 共用；設在 bean 層 → SafeFetcher 對 https:// 目標亦降為 HTTP/1.1，僅失去多路複用、單次 SSRF-safe fetch 無實質效益，**有意接受**以一次根治整個「HTTP_2 預設打 cleartext HTTP/1.1 server」class）。Go `net/http` cleartext 預設即 HTTP/1.1，無此問題。

### 9.8 禁止

- ❌ tx 內等 HTTP（拖長事務）
- ❌ HTTP 失敗 throw / 影響 mutation response
- ❌ 對 timeout / non-2xx 重試（只允許對**連線層 IOException** 冪等有限重試，見 §9.5）
- ❌ 商品「集合變動」類 mutation（建立即上架 / 刪除 ACTIVE / 上下架跨界 / 批次下架）漏發 `seller:<sellerId>`（見 §9.3 ★ 判定原則）
- ❌ 反過來：純欄位 / 庫存 / 改分類 mutation 仍共發 `seller:<sellerId>`（over-invalidation，會霰彈失效推薦賣家 rail；§9.3 ★ 已坐實賣家層 surface 不嵌商品欄位）
- ❌ 在 service 內手寫 `HttpClient` 不走 helper
- ❌ 用 HTTP/2 / 預設版本打 `/api/revalidate`（cleartext server 不支援 → 連線重置靜默失敗，必 HTTP/1.1）
- ❌ backend producer 直接發 domain-collection（`products:list` 等）／`tab:*`／`home` tag（只發 entity tag，domain-collection 由 web `/api/revalidate` expansion 產生；`home` 已於 53 號 §4.4 step3 拆除）
- ❌ 把 cache tag 字串硬編碼（必須從 helper / 配合 frontend `lib/seo/tags.ts` 同步維護命名）
- ❌ 跨 mutation 合併批次（每 mutation 一次 POST，避免拖延）
