# 開發工作流程

## 1. 強制順序

**設計書 → Code Gen → DB → 程式碼 → 測試**，禁止跳過任何步驟。

| 步驟 | 說明 | 禁止事項 |
|------|------|---------|
| 1. 設計書 | 先寫 / 更新設計書（含 CodeMeta `.md`），使用者 review 確認後才動手 | 禁止跳過設計書直接寫程式碼 |
| 1.5 Code Gen | 若涉及共享代碼值（錯誤碼 / 狀態碼 / 類型碼 / 技術碼），先改 `docs/代碼管理（CodeMeta）/*.md` 再執行 `generate.sh`（見 [CodeMeta README](../代碼管理（CodeMeta）/README.md)） | 嚴禁手動修改生成檔案 |
| 2. DB | Java：**V1 永久凍結**，變更一律新增 `V{N+1}__{verb}_{target}.sql`（見 [Java 微服務開發規範 §9.3](./Java%20微服務開發規範.md)）。Go：改 `db/schema/schema.sql` → `atlas migrate hash` | 禁止修改既有 V1~V{N}；禁止 SSH 手跑 DDL 取代 migration |
| 3. 程式碼 | Proto → common-core → Java 微服務 → Gateway | — |
| 4. 測試 | 驗證功能正確 | — |

### 1.1 Go sqlc nullable boundary

使用 `sqlc + pgx/v5` 的 Go service，所有 PostgreSQL generator 必須設定
`emit_pointers_for_null_types: true`。普通 nullable 欄位的 generated
`*string`、`*int32`、`*int64`、`*bool` 等 pointer，就是 repository boundary 的唯一
契約；application code 不得重新建構 `pgtype.Text`、`pgtype.Int*`、`pgtype.Bool` 或
`pgtype.Float*` literal，也不得再建立泛用 nullable conversion helper。

- repository mapper 負責 pointer 與 domain model 的轉換，並明確保留 empty/zero policy。
- non-null query parameter、JSON/JSONB OID override 等確實需要 driver value 的情境，
  只能使用具名的 `pkg/pgxutil` helper 或 service-local `nullable.go`/`pgx_types.go` boundary。
- NUMERIC、UUID、array、JSON/JSONB 等 special type 維持明確處理，不重建泛用 kitchen sink。
- pagination 統一使用 `pkg/pagination`；`pkg/sqlutil` 不提供 pagination API。

CI static gate：`python3 scripts/check-pgx-nullable-boundary.py`；generated output drift
由 `sqlc-generated-diff.yml` 把關。修改 query 或 schema 後，執行
`./scripts/gen-sqlc.sh <service>`，再跑受影響 module 的測試。

## 2. 設計書品質要求

設計書**必須包含**以下內容，缺一不可：

| 必要內容 | 說明 |
|---------|------|
| 時序圖（Sequence Diagram） | Mermaid `sequenceDiagram`，描述服務間呼叫順序 |
| 業務流程圖（Flowchart） | Mermaid `flowchart`，描述完整業務判斷邏輯 |
| API 規格 | 路徑、參數、回應格式、錯誤碼 |
| Proto 定義 | RPC + Message 完整定義 |
| 實作位置 | 需要新增 / 修改的檔案清單 |

**禁止**：設計書只改文案 / 文字描述而不更新圖表。圖表必須反映實際邏輯變更。

## 3. 環境變數配置流程

新增 / 修改環境變數時，**必須完成以下所有步驟**：

| 步驟 | 檔案 / 操作 | 用途 |
|------|----------|------|
| 1 | 所有 `.env*`（`.env`, `.env.dev`, `.env.local`, `.env.template`） | docker-compose 本地 / 遠端開發 |
| 2 | `docker-compose-local.yml`（注入到對應服務 environment） | 本地開發容器 |
| 3 | `k8s/values/{service}.yaml`（加入 `config` 或 `secretRef`） | k3s 部署配置（進版控） |
| 4 | push → PR（base `dev`）→ merge → CI/CD 自動部署 | 唯一上線路徑，見 [Git 分支與交付路徑規範](./Git%20分支與交付路徑規範.md) |
| 5 | 部署後驗證服務讀到新的環境變數 | — |

**步驟 4 為什麼不能 SSH 進 VM 手改**：`k8s/values/*.yaml` 的變更由 `.github/workflows/deploy-k8s.yml` 自己偵測——只改 values 沒改 code 的服務會被列為 values-only，走 `helm upgrade` 套上新的 ConfigMap（不重 build image）；改了 code 的服務則重 build 再部署。**SSH 進去 `kubectl patch` / `kubectl rollout restart` 不會 rebuild image，等於假部署**：改動看起來「上線了」，實際跑的還是舊 binary，而且叢集狀態就此脫離版控、下一次 CI 部署會把它蓋掉。

- 部署漏跑（deploy drift）的補救是重新觸發 workflow，不是手工同步：
  `gh workflow run deploy-k8s.yml --ref dev -f services=<svc1>,<svc2>`（`--ref` 必須與目標環境對齊：dev 用 `--ref dev`、prod 用 `--ref main`）。
- **例外只有 Secret 的「值」**：值不進 git，是以 `k8s/scripts/create-secrets.sh` 從 `.env` 一次性建立進叢集的人工維運步驟（dev / prod 各做一次，做法見 [新增微服務指南](./新增微服務指南.md)）。但**有哪些 key、值從哪來必須進 git**（`create-secrets.sh` ＋ values 的 `secretRef`），由 `k8s/scripts/check-secret-declarations.sh` 在 CI 把關。這是「建立密鑰」不是「部署程式碼」，不構成繞過 CI/CD 的理由。

**注意**：
- 只改 `.env*` 不夠，遠端跑 k3s，必須同步 `k8s/values/` 並經 CI/CD 部署
- `k8s/values/` 中敏感資訊（密碼 / key）放 `secretRef`，非敏感放 `config`
- 步驟 2 ↔ 3 的對齊（compose 服務清單與 env key vs `k8s/values`）由 CI `static-gates.yml` 的「compose ↔ k8s/values 對齊檢查」step 把關；**新增服務**時同步新增 compose service block 的細節見 [新增微服務指南](./新增微服務指南.md)。祕鑰禁在 compose 寫死 default（一律 `${VAR}` / `${VAR:-}`），個人本地差異走 `docker-compose.override.yml`（gitignore）

## 4. 受改動波及之既有路徑驗證（bounded regression）

**所有 code change 都適用**，不分大小、不分是否走 issue flow。「我只改了一行」不是豁免理由——一行 cascade 改動炸掉全環境結帳的事故就是這樣來的。

### 4.1 兩個階段驗不同的東西

| 階段 | 驗什麼 | 典型內容 |
|------|--------|---------|
| **本地** | **本次修改的功能本身** | 改的那個行為對不對、邊界情況（空值 / 邊界數量 / 失敗中途返回 / 重複觸發）、**鑑別力**：把它弄壞 → 驗證轉紅 → 還原 → 轉綠。只會轉綠不會轉紅的測試等於沒測 |
| **dev** | **完整 E2E ＋ 受影響功能的回歸** | 跨服務串接、真實資料量、部署後的實際狀態，以及 §4.2 六類共用點有沒有被打壞 |

兩階段是不同的問題，不是同一件事做兩次：本地跑得過不代表部署後成立（真實資料、跨服務時序、快取只有 dev 有）；反過來也不要把本地就看得出來的行為留到 dev 才第一次看。

### 4.2 要驗的共用點（六類）

1. **同 endpoint 的其他情境**：其他 query 參數組合、分頁（第一頁 / 中間頁 / 末頁）、空集合
2. **同 repository / utility 的其他 caller**：本次改的方法還有誰在呼叫
3. **跨服務共用 proto 的其他 consumer**：改了 message / RPC，其他服務的解析端
4. **共用 MQ event 的其他 producer / consumer**：改了 payload 欄位，其他訂閱者
5. **共用 cache key**：寫入路徑改了，對應的 evict 有沒有跟著對
6. **cascade / 反正規化的讀路徑**：寫入時同步維護的冗餘欄位，讀它的地方

### 4.3 挑選原則

- 共用點 ＝ **本次修改直接觸碰者**；不測與本次改動沒有 code share 的功能。
- caller **≤5 全測**；**>5 挑代表性 2–3 個**（挑「最常走的」與「參數最極端的」，不是挑最好測的）。

### 4.4 禁止

- **「這不會影響到別人」這種未驗證假設**——要嘛列出共用點驗過，要嘛明說沒驗。
- **拿 `go test` / `mvn test` 通過當行為層 PASS**：編譯與單元測試綠只證明語法層與被覆蓋的分支沒壞，不證明真實路徑仍然正確。
- 把回歸驗證 punt 給使用者手測。

## 5. 同一 root cause 一次全修

root cause 若是**可枚舉的 class**（一句 grep / SQL query 就掃得出全部命中），就**掃全 repo，把命中的全部一次修完**。

- **數量多、跨服務，都不是拆單理由。** 留一半沒修，等於留著同一顆地雷換個位置再爆一次。
- **界線 ＝ 同一 query 的判定準則**：這句 query 掃得到的才修。不擴到不同 root cause、不借機重構周邊程式碼。
- **唯一可拆的情況**：跨服務需要各自獨立部署驗證 → 拆成**同一波並行的多個 PR**，不是拆成「以後再說」的 issue。

> ⚠️ **修復與驗證的方向相反**：**修復要全覆蓋**（§5），**驗證要 bounded**（§4）。全修不代表要把每一處都跑一次 E2E，也不代表可以只修看得順眼的那幾處。

### 5.1 本 repo 的 grep 陷阱

因為[禁止硬編碼](./Java%20微服務開發規範.md)（Java 微服務開發規範 §6），狀態碼 / 類型碼一律走 CodeMeta Enum 與 `#{param}` 注入，**SQL 與程式碼的字面上看不到那個值**。以「字面值」為錨的 grep 在這個 repo 會**系統性漏掉**——而且漏得很安靜：你會拿到一份看起來很乾淨的零命中結果。

正確做法：改用「**動詞 ＋ 常數符號**」為錨。例如要找「把某狀態改成 X 的所有寫入」，錨下在 `UPDATE <表名>`、`@Update`、`LambdaUpdateWrapper`、`.updateById(`、以及該 Enum 的**符號名**，而不是它的碼值。做窮舉掃描前先問一句：**我要找的東西，在這個 repo 的規範下會以什麼形式出現？**

## 6. 結帳 hot path smoke（強制）

**適用範圍**：改動 `product` / `order` / `cart` / `payment` / `shipping` 任一服務的 service / repository / gRPC / MQ Consumer 層。

**動作**：push 前必跑 `infra/smoke-checkout.sh` 全綠（打遠端 dev 用 `--env=dev`）。

它走的是真實的結帳鏈：找一個真實 SKU → AddToCart → CheckoutPreview → CheckoutConfirm → CreatePayment（ATM）→ 斷言 `orders` 與 `shipments` 各有新 row。也就是說，它驗的是**跨這五個服務的整條線還通不通**，不是單一服務的單元行為。

> ⚠️ **沒有任何 CI 會幫你跑它。** 實查 `.github/` 對 `smoke-checkout` 零引用 —— 它純粹靠開發者自己在 push 前執行。CI 全綠**不代表**結帳鏈沒被打斷。

**禁止的三種自我豁免**（每一種都對應過真實事故）：

- 「我只改了一行」—— 一行 cascade 改動曾讓全環境結帳回 500
- 「`mvn compile` 過了就 push」—— 編譯過是語法層，結帳鏈斷掉是行為層
- 「這是 admin 路徑，不影響 checkout」—— admin 與 checkout 可能共用同一個 repository，共用點才是爆點

**資料清理**：這支腳本預設會在成功後刪掉自己造出來的資料（`orders` / `order_items` / `order_outbox` / `shipments` / `payment_*`）。若要保留造出來的訂單做後續檢查，帶 `--no-cleanup`，但**檢查完要自己清**（見 §7）。

## 7. 測試資料清理

**測完當下就清，不要留著等排程。** 留下來的測試資料會被後續的排程器、對帳流程、統計反正規化當成真實資料處理，污染範圍會隨時間擴大。

- 整支流程測完要一併清掉**去重表 / 冪等記錄**，否則下一輪同樣的 event 會被當成重複而靜默跳過，你會以為功能壞了
- ⚠️ **刪 outbox row 之前先看 `event_published_at`**：還沒派送就刪掉 ＝ 那個事件永遠不會發出去，而且不會有任何錯誤訊號
- 例外：QA 回合中**尚未全綠**的那一輪，資料保留供追根因；證據檔（截圖、log、報告）一律不清
