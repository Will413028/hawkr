## A. How comparable systems model the queue and the SLA

### A1. ServiceNow
- **Shared supertype table.** Every work kind (incident, problem, change, request) extends the `task` table, so "my work" lists and SLAs work over one table (INFERENCE from long-standing platform knowledge; not re-fetched).
- **SLA instance is a stored record (`task_sla`)**, one per (task, SLA definition). Fields: Stage (In progress / Cancelled / Paused / Completed; old 2010 engine also had Breached), Breach time = Planned end time "adjusted for pause duration", Original breach time "calculated when the SLA is first attached", Business elapsed time / percentage / time left measured "between start time and now, minus pause duration". VERIFIED: https://www.servicenow.com/docs/r/QykF2iRSIs6VXztArCSo3w/DkrtAbz5bi4lTcYZODfaIQ
- **Conditions:** "up to six SLA conditions: start, cancel, pause, resume, stop, reset", evaluated "each time a task record is created or updated"; new SLAs are checked for attachment first, then attached ones are updated. Reset = "the running SLA will be completed and a new SLA will be attached" (only if start also matches). Stop completes "regardless of whether it is breached". VERIFIED: https://www.servicenow.com/docs/r/QykF2iRSIs6VXztArCSo3w/WYN6nXXIBmOElVN~7E1oiQ
- **Retroactive start** (start time taken from a task field such as created) and retroactive pause exist. SEARCH: https://www.servicenow.com/docs/r/application-development/servicenow-sdk/fluent-sla-api.html
- **Time-triggered work:** elapsed/percentage fields are refreshed by scheduled jobs in `sys_trigger`, with frequency depending on closeness to breach (e.g. hourly for SLAs breaching within a day, daily for already-breached; already-breached recalculation stops after ~1 year or 1000%). Breach/warning notifications come from SLA flows/workflows with percentage timers. SEARCH (community): https://www.servicenow.com/community/itsm-forum/how-is-the-elapsed-time-on-the-sla-updated-in-sn-scheduled-jobs/td-p/853554
- **Drift is a known failure mode:** ServiceNow ships "Repair SLA", which deletes and recreates/recalculates task_sla records from the task's history when definitions/schedules changed or values are wrong. SEARCH: https://www.servicenow.com/docs/r/Recj91eIo1YnsOabQjgskg/0eb3bF8bg8qQkre79ljuRw ; a community case of a deactivated SLA scheduled job causing task_sla and timeline to disagree (SEARCH).
- Takeaway (INFERENCE): stored SLA instance written in the same transaction as the task update (business rule on insert/update) + scheduled jobs only for time-derived display fields and alerts + a repair path that recomputes from history.

### A2. Zendesk
- **SLA policy model:** policy = filter (`all` AND / `any` OR conditions) + `policy_metrics[]`, one object per (priority, metric) with `target` (minutes) / `target_in_seconds` and `business_hours` boolean. Metrics: `first_reply_time`, `next_reply_time`, `periodic_update_time`, `pausable_update_time`, `requester_wait_time`, `agent_work_time`, `total_resolution_time`. VERIFIED: https://developer.zendesk.com/api-reference/ticketing/business-rules/sla_policies/
- **Pause semantics are per metric, by status:** requester wait time pauses in Pending (waiting on customer), stops at Solved; agent work time pauses in On-hold and Pending; pausable update pauses in Pending; next reply time runs from oldest unanswered customer comment to next public agent reply (i.e. restarts per exchange); total resolution includes Pending. Policies apply in list order, most restrictive first; targets keyed on Priority, blank priority = no SLA. VERIFIED: https://support.zendesk.com/hc/en-us/articles/4408829459866-Defining-and-using-SLA-policies
- **Exposure:** `GET /api/v2/tickets.json?include=slas` returns `slas.policy_metrics[]` with `breach_at`, `stage`, `days` per metric (i.e. stored/computed breach timestamps per ticket metric). SEARCH: https://support.fivetran.com/hc/en-us/community/posts/17533665120407 . Breach history reporting lives in an "SLAs dataset" in Explore (SEARCH, Zendesk community).
- **Views = saved filters over tickets**, with SLA column; "order by SLA ... ascending" so "the tickets whose targets are most breached or are closest to breaching will get attention first"; column shows "calendar time left before the next target ... will be breached"; "Currently, there's no way to send notifications to agents based on SLA breaches." VERIFIED: https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies
- **Omnichannel routing (push):** default order = routing eligibility timestamp (+ priority on Professional+); optional global setting to order "by nearness to SLA breach, beginning with those that have already breached"; assignment by spare capacity or round robin (longest since last work); unaccepted work reassigned after a timeout. VERIFIED: https://support.zendesk.com/hc/en-us/articles/4828787357210-Activating-and-configuring-omnichannel-routing
- "Play mode"/guided mode (get-next button over a view) exists (INFERENCE from product knowledge; not fetched).

### A3. Jira Service Management
- **SLA = per-issue stored value with cycles.** Each SLA metric on an issue has an `ongoingCycle` (startTime, breachTime, breached, paused, withinCalendarHours, goalDuration, elapsedTime, remainingTime) and `completedCycles[]` (startTime, stopTime, breached, goalDuration, elapsedTime, remainingTime). Completed-cycle interface VERIFIED: https://docs.atlassian.com/jira-servicedesk/10.3.2/com/atlassian/servicedesk/api/sla/info/SlaInformationCompletedCycle.html ; ongoing fields SEARCH (CData connector https://cdn.cdata.com/help/GKK/py/pg_table-requestslacycles.htm).
- Start / pause / stop conditions, goals selected by JQL with calendars (working hours); multiple start/stop = multiple cycles, each with its own breached flag, so restart semantics and history are first-class. SEARCH (Atlassian docs nav + snippets): https://support.atlassian.com/jira-service-management-cloud/docs/create-service-level-agreements-slas/
- **Persistence and drift:** SLA values are stored per issue (custom field value plus an internal timeline of events). Atlassian documents missing/corrupted SLA data caused by DB corruption, plugin issues, "errors while calculating an SLA update" and a race where "multiple SLA updates in the same request override each other"; remedy is "reconstruct" from the timeline (graceful) or forced recompute that overwrites stored values. VERIFIED: https://support.atlassian.com/jira/kb/missing-slas-in-jira-service-management/ ; SEARCH: https://support.atlassian.com/jira/kb/how-to-bulk-recalculate-missing-slas/
- **Queues = JQL filters** ordered by an SLA field (e.g. `ORDER BY "Time to resolution"`); ongoing SLAs rank by remaining time, completed rank last; SLA JQL functions `breached()`, `elapsed()`, `remaining()`, `running()`, `paused()`, `withinCalendarHours()`; ordering by SLA on large projects has documented performance bugs (JSD-1429). SEARCH: https://community.atlassian.com/forums/Jira-Service-Management/Jira-Service-Desk-order-by-remaining-time-SLA/qaq-p/32656 , https://jira.atlassian.com/browse/JSD-1429

### A4. Salesforce Service Cloud
- **Entitlement process → CaseMilestone records** (stored per case per milestone): `StartDate`, `TargetDate` ("The date and time the milestone must be completed"), `CompletionDate`, `IsViolated`, `IsCompleted`, elapsed / remaining / stopped time, business hours. SEARCH (object reference 403 to fetcher): https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/api/sforce_api_objects_casemilestone.htm
- **Time triggers** on milestones: negative `timeLength` = warning (before target), positive = violation (after); actions run "if, at that time, the milestone is not completed"; `successActions` on completion; `useCriteriaStartTime`; milestones can recur (independent / sequential / chained — names from memory, INFERENCE). Case "Stopped" flag pauses milestones. SEARCH: https://developer.salesforce.com/docs/atlas.en-us.264.0.api_meta.meta/api_meta/meta_entitlementprocess.htm
- **Omni-Channel:** `PendingServiceRouting` = a work item waiting to be routed (QueueBased or SkillsBased, `RoutingPriority`, push timeout); `AgentWork` = the assignment offered/accepted by an agent (the claim + audit of who took what, when); routing models Least Active / Most Available; push to agents with capacity. SEARCH: https://developer.salesforce.com/docs/atlas.en-us.264.0.api_meta.meta/api_meta/meta_queueroutingconfig.htm , Omni-Channel dev guide https://developer.salesforce.com/docs/atlas.en-us.240.0.omni_channel_dev.meta/omni_channel_dev/service_presence_soap_api_intro.htm
- Key pattern (INFERENCE): Omni routes **heterogeneous objects** (cases, chats, leads, custom objects) through one routing record (`PendingServiceRouting` → `AgentWork`) that points at the source record. That is exactly the "central work item referencing domain records" pattern.

### A5. Trust & Safety tools and DSA
- **ROOST Coop:** report (`POST /api/v1/report`) → Coop "creates a moderation job" → routing rules pick a queue (default queue if none) → job offered to "the next available moderator" (pull / get-next). CSAM reports bypass rules into an NCMEC queue. A job's report history aggregates multiple reporters and sources (incl. automated detectors). Appeals arrive through a separate Appeals API. Invalidation actions emit audit trace spans. No SLA/priority ordering is documented on that page. VERIFIED: https://raw.githubusercontent.com/roostorg/coop/main/docs/user/reports.md ; overview SEARCH https://roost.tools/coop/
- **Osprey** is a rules/investigation engine over event streams (Discord, Bluesky), not a queue/case tool. SEARCH: https://discord.com/blog/osprey-open-sourcing-our-rule-engine
- **Tremau Nima / Checkstep / Hive:** public docs on queue/SLA internals not found; only marketing (moderation workflow orchestration, DSA statements of reasons). SEARCH: https://www.gi-de.com/en/ventures/trusttech-insights/tremau . Treat any claim about their internals as unverified.
- **DSA timeliness (no fixed hours, standard is "timely"/"without undue delay"):** Art 16(6) notices processed "in a timely, diligent, non-arbitrary and objective manner"; Art 20(4) complaints handled "in a timely, non-discriminatory, diligent and non-arbitrary manner", reverse unfounded decisions without undue delay; Art 22(1) trusted-flagger notices "given priority and ... processed and decided upon without undue delay"; Art 9(1) inform the authority "of any effect given to the order without undue delay". VERIFIED (EUR-Lex full text, articles section): https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32022R2065 . ## B. Synthesis per design question

### B1. Derived queue vs materialized work items vs event-projected read model
| Option | Who uses it | Strength | Failure modes |
|---|---|---|---|
| **Derived at read** (each source's state queried and merged) | Lists/views inside one system: Zendesk views, JSM queues (JQL) are saved queries **over a single shared table** (VERIFIED/SEARCH above) | No drift; "overdue" is just `due_at < now()`, no scheduler; zero write coupling | Across many owners it becomes API composition: N queries, in-memory merge, cross-source pagination, "inefficient in-memory joins of large datasets" (microservices.io, VERIFIED https://microservices.io/patterns/data/api-composition.html). Nowhere to store claim/assignee/snooze/history unless each source adds it. JSM's own "ORDER BY SLA" perf bugs. |
| **Materialized work item / SLA instance written with the domain command** | ServiceNow `task_sla`, Salesforce `CaseMilestone` + `PendingServiceRouting`/`AgentWork`, Zendesk `slas.policy_metrics.breach_at`, JSM SLA cycles, Stripe `review`, Coop job | One sortable/indexable table; claim, assignment, audit, SLA history natural; heterogeneous sources unified by a pointer to the source record | Drift (close not written, definition changed) — both ServiceNow ("Repair SLA") and JSM ("reconstruct", documented races and corruption) ship a **recompute-from-history** repair. Time-triggered transitions need jobs (ServiceNow sys_trigger; Salesforce time triggers). |
| **Event-projected read model (CQRS)** | Microservices with separate DBs | Decoupled; scales | "Views can lag ... eventually consistent", added complexity (VERIFIED https://microservices.io/patterns/data/cqrs.html); "If the activation signal ... is lost or delayed ... the view silently serves stale results" (VERIFIED https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view). Needs outbox for reliable publish (VERIFIED https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html). |

INFERENCE — when industry picks each: every vendor product whose job is "work queue + SLA" materializes the work/SLA record and keeps the queue itself as a query over that record. Derived-at-read is what they do *within* one table, not across owners. Event projection is chosen when the writer and the queue are in different processes/DBs.

**No-debt end state for multiple operators + growing sources (INFERENCE):** a central work-item store (one row per open obligation, pointing at the source record, carrying `due_at`), written by the owning module **in the same Postgres transaction** as its command (possible because it is one monolith and one DB, so no dual-write; outbox only for the external invoice service). The domain fact stays the source of truth; the work item is a projection that must be **rebuildable**: each module also exposes "list my open obligations from facts", used by a reconciliation check/repair job — the same lesson ServiceNow and JSM learned (repair/reconstruct).

### B2. SLA representation
- Industry baseline: **per-obligation SLA record** with start, target/breach time, pause accounting, stop/met time, breached flag (all four ITSM vendors). JSM additionally keeps **completed cycles**, which is the cleanest model for "clock restarts": restart = close cycle N (met/breached recorded) + open cycle N+1. ServiceNow "reset" is the same idea (complete + reattach). Zendesk "next reply time" restarts per customer message.
- Pause ("waiting on customer") vs restart: pause keeps one target and extends it by paused time (ServiceNow breach time "adjusted for pause duration"; Zendesk requester wait pauses in Pending). Restart starts a new target from the new event. INFERENCE for your case: "case awaiting decision, clock restarts when the seller answers" is restart (new cycle), not pause; the inquiry period itself is a separate obligation on the seller (with its own overdue item). Legal deadlines generally don't pause unless the statute says so.
- Compute-from-facts vs store: computing is fine for "current due_at" if the deadline policy is a pure function of stored facts. But attainment reporting ("% decided within target", median time to action — DSA Art 15 style) needs per-cycle outcomes that survive policy changes; vendors store the original target (ServiceNow "Original breach time") precisely so later definition changes don't rewrite history. INFERENCE: store target at open time; never recompute history with a new policy.

### B3. Queue consumption UX
- Three modes all coexist in vendors: (1) sorted list views (Zendesk views ordered by SLA ascending, JSM JQL queues); (2) pull "get next" (Coop "next available moderator", Zendesk play mode); (3) push routing with capacity (Zendesk omnichannel, Salesforce Omni). Filters per kind/queue sit on top of (1).
- Sort key: breached first, then nearest breach (Zendesk omnichannel "beginning with those that have already breached", VERIFIED), then priority/age as tie-breaker. Items with no SLA: Zendesk/JSM sink them (completed/no-SLA last).
- Sort key moving while browsing (INFERENCE): sort keys only change on domain events (restart, pause), not with time, if you sort by absolute `due_at` rather than "time remaining". Use keyset pagination on `(due_at, id)`; accept that an item can jump on refresh. Get-next sidesteps it entirely with an atomic claim (`SELECT ... FOR UPDATE SKIP LOCKED` + claim row) — which is why routing systems create an assignment record (`AgentWork`).

### B4. Calendar vs business hours, priority targets, warnings
- Every vendor makes hours a **per-target attribute** (Zendesk `business_hours` per policy metric, VERIFIED; JSM calendars per goal; Salesforce business hours per entitlement/milestone; ServiceNow schedule per SLA definition). So mixed calendar (legal 48h) and business-day (invoice) targets in one queue is standard: store the computed absolute `due_at`; the calendar only matters when computing it.
- Priority-dependent targets: Zendesk targets keyed by priority (VERIFIED); Linear defaults per priority (SEARCH).
- Warning thresholds: Salesforce warning triggers (negative offset) vs violation (SEARCH); ServiceNow percentage timers (SEARCH/INFERENCE); Linear "at risk" states/notifications (VERIFIED). INFERENCE: store `warn_at` alongside `due_at` (or derive from a per-kind %), so "approaching breach" is also a read predicate.
- Day-counting of legal "3 days" (start-day exclusion, holiday rollover under Taiwan law) is a legal question — confirm with statute; INFERENCE only.

### B5. Cross-source aggregation in a modular system
- microservices.io: API Composition is "a simple way to query" but has in-memory-join cost; CQRS view DB is the alternative (VERIFIED, above). Azure: for microservices "Materialized views can help you consolidate data from your services. If ... aren't appropriate ... aggregate their data on demand" (VERIFIED). AWS: outbox when DB write + notification must be atomic (VERIFIED).
- Shopify modular monolith: components exposed via public APIs, boundaries enforced statically (Packwerk privacy/visibility checks). SEARCH: https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity , https://shopify.engineering/enforcing-modularity-rails-apps-packwerk
- INFERENCE for a modular monolith with one Postgres: a **shared task table owned by a dedicated work-queue module**, reached only through that module's public API (open/restart/close obligation, called inside the caller's transaction), satisfies schema ownership and gives atomicity without an outbox. Domain modules depend on the queue module (like they depend on audit), the queue module depends on none of them (it stores kind + subject ref + display snapshot). Outbox/event ingestion only for out-of-process sources (invoice service).

### B6. Assignment, audit, SLA reporting — day one or later?
- Vendors treat assignment/claim and history as core of the work record (Zendesk assignee + capacity routing, Salesforce AgentWork, Coop audit spans, GitHub done/save, Linear triage responsibility). SLA attainment reporting is core in ITSM (Zendesk SLAs dataset, JSM completed cycles). T&S regulation (DSA transparency) needs per-item timestamps from the first item handled (INFERENCE).
- What is *not* day-one anywhere: push routing with capacity/skills (enterprise tier features in Zendesk/Salesforce).

## C. Recommended architecture for this case

**Premise check for the caller:** confirm whether any listed kind's state lives outside the monolith's DB besides the invoice service; that changes only the ingestion path for that kind.

**Recommend (industry baseline, adjusted only for real constraints):**
1. A `workqueue` (name free) module owning `work_item` (kind, source module, subject ref, opened_at, due_at, warn_at, deadline basis/policy id, state open|closed, outcome met|breached|cancelled, closed_at, assignee/claimed_at nullable) and `work_item_cycle` or an event history table (open / restart / close / claim / unclaim with actor + time).
2. Owning modules call `Open / Restart / Close` through its public Go API **inside their command transaction**; the owning module computes `due_at` from its own deadline policy (the queue does not know domain rules), store the target at open time.
3. "Overdue"/"approaching" are read predicates on stored `due_at`/`warn_at`; no scheduler is needed for ordering. A scheduler only for time-triggered *actions* (notifications, auto-escalation) if/when wanted.
4. Each module also exposes `OpenObligations()` computed from its facts; a reconciliation test/job diffs it against `work_item` (repair = rebuild), mirroring ServiceNow Repair / JSM reconstruct.
5. Back office reads one indexed query: `ORDER BY (due_at < now()) DESC, due_at, id` with keyset pagination, filters per kind; "get next" = claim with SKIP LOCKED when >1 operator.
6. Invoice service (external, business-day SLA): ingest via its events/outbox or a poller into the same table with `due_at` computed by the adapter using its business calendar.

**Constraints that could justify deviating (classify REAL vs SELF-IMPOSED yourself):**
- Single operator today, pre-launch, no data: makes claim/assignment and SLA reporting unused *now*. It does not make the materialized table wrong; it only lets you defer the claim column/UI and routing. A purely derived queue (API composition over module `OpenObligations()`) is acceptable as the first step **only if** those per-module derive functions are kept as the reconciliation source later, so nothing is thrown away.
- Triggers to have the materialized table in place (if you start derived): second operator (claim/assignment needed), any SLA attainment or regulator reporting requirement, history of "was it on time" needed for a closed item, the social/moderation module adding high-volume kinds, cross-source pagination getting slow, or the invoice service being added to the same list.

**End state:** one work-item table owned by one module, written transactionally by owners (outbox only across process boundaries), per-cycle SLA records with stored original target, reconciliation from facts, list + get-next consumption, routing/capacity only when operator count makes it worthwhile.
