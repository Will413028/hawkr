## 1. 要你決定

### D′1 待辦佇列：跨模組怎麼合（3d；同時回答 A7-D8）

**建議：**
- **來源**：每個模組用自己的推導查詢，提供「這個模組的待辦」：依同一個全序排序的 keyset 查詢，判定式與 ReviewPolicy 都留在模組內。seller 的來源就是 v2 D7 的 UNION ALL。
- **合併**：httpapi 的讀取組裝依全域 keyset `(有無期限, due_time, open_time, 來源, kind, id)` 合併，對 admin 提供 `ListReviewQueue`（`api/hawkr/admin/reviewqueue/v1alpha1`）。
- **不做**：不寫事件投影，不另建模組。
- **分工**：3d 做 seller 的來源、合併、admin 契約與待辦頁；A7-1e 只加 moderation 的來源與它的種類。
- **ADR**：修訂 ADR D3 第 3 點與 backend 單體規則 2（文字見下）。

**業界基準**
- 跨服務（或跨模組）的查詢有兩種 pattern。［外部查證：microservices.io、AWS Prescriptive Guidance］
  - **API Composition**：呼叫擁有資料的各方，在記憶體合併。AWS 稱它「the simplest way to gather data from multiple microservices」。缺點是遇到需要 in-memory join 大量資料的查詢時效率差，來源一多可用性也會下降。
  - **CQRS 讀取模型**：訂閱事件、另存一份投影。代價是複雜度、資料重複，以及「replication lag／eventually consistent views」。
- 工作佇列實體化，是為了路由與獨占指派。
  - 信任與安全的工具 ROOST Coop 依路由規則把 job 送進 queue，保證「Two moderators will never receive the same job」，job 也可以搬到別的 queue。［外部查證］
  - v2 D7 的研究也得到同樣的結論：要另存工作實體，只在需要存「不屬於業務狀態」的東西時才出現，也就是指派、路由、認領、暫停、升級。
  - 「跨模組」本身不在這份清單裡。
- composition 在這裡成立的前提：**每個來源都自己擁有篩選與排序需要的全部屬性**（期限、開始時間、種類），合併層只依一個全序合併，不 join、不篩選來源沒有的屬性。這個前提不成立時，正好就是終局的觸發條件。

**為什麼現有機制是那樣**
- **v2 D7**：它把「跨模組合併」等同「實體化」。依據是約束帳的「不能跨表分頁再合併」（CARRYOVER:88），但那一列否決的是舊收件匣「兩張表各自 limit／offset 再合併」。漏件來自 offset 分頁的合併，全域 keyset 的合併沒有這個問題。
- **ADR D3 第 3 點與單體規則 2**：寫「必須拿下層模組的資料來篩選或分頁時，在自己的 schema 維護讀取模型，由對方的事件在同一個 transaction 內更新」。它要防的是 Integration Database 與應用層 join。待辦的每個來源都篩選、排序自己的資料，合併層不拿別人的資料來篩選。但條文沒有區分這種情況，所以照字面，D′1 偏離了它。
- **A7-D8 v2 的建議**是 A，加兩點修正：開啟事件帶上由擁有者算好的 `due_time`；時間觸發的項目由擁有者的 River job 發事件。A7 也考慮過查詢聯邦，否決的理由是：「之後要指派時還得實體化，等於做兩次，不採」。回應如下：
  1. 實體化的觸發條件是指派。指派被 **REAL** 的約束擋著：只有一位營運人員。
  2. 投影本來就要每個來源一支全量重建查詢（A7 計畫:303、307），那支查詢就是 D′1 的來源查詢。之後要實體化時，丟掉的只有合併層（約一個檔），其餘都留下。
  3. 現在就投影，事件、重建指令、開關路徑都要先寫好並一直維護；指派出現時還是要加認領與路由的狀態。「做兩次」的成本，(c) 是一個合併層，(b) 是整套基礎設施提前持有。
  4. ADR D4：in-process 訂閱者在發布方的 transaction 內同步執行，失敗就讓整個 transaction rollback。佇列投影的 bug 會擋下 `AcknowledgeReport`、`CreateMeasure` 這類指令；D′1 不碰寫入路徑。

**ADR D3 第 3 點的修訂文字**（建議，同時改 backend 單體規則 2 的措辭與 A7 計畫:71 不變量表那一列）：

**不變式**（寫進設計與測試）
- **只有一份比較函式**，放在 platform，給 httpapi 與各來源共用。
  - 各來源的 SQL `ORDER BY` 與 seek 條件必須和它一致。
  - 有無期限用明確的旗標，不讓 row-value 比較碰到 NULL。
  - 來源與 kind 用整數 rank，不用字串比較，避免 DB collation 和 Go 的位元組順序不同。
  - 時間精度統一到 µs。
- **一次請求只用一個 `now`**，傳給所有來源（設計書 32:166：「現在」是注入的 clock）。來源有兩個以上時，在 `db.InReadSnapshot` 內讀（規則 3）。
- **page token 綁住 kind 篩選**（`rpc.FilterScope`）。每個來源取 N＋1 筆，用來判斷有沒有下一頁。
- **加來源不改合併層**（A7 的要求）：來源介面是「rank＋依全序的 keyset 查詢＋它擁有的種類」。比較函式、FilterScope 與 page token 的形狀都不帶來源特有的欄位，新來源只要登記 rank 與查詢。
- **跨頁的語意**：
  - 新進入、而且排在游標之前的項目，要等重新整理才看得到。這和 Elasticsearch 的 `search_after` 不配 PIT 時一樣。
  - 項目留在佇列期間 key 不變，才保證跨頁不重複。8 種裡只有 KYC 補件後重送會換 `submitted_at`。
- **測試**：
  - 隨機資料加上第二個來源用測試替身的 property test，驗證不漏不重。
  - mutation：把其中一個來源的 kind 排序反過來，測試必須失敗。
  - 「成員資格 ⇔ 判定式」的資料集測試（v2 原本就有）。

**終局與觸發條件**
- 出現無法推導的工作狀態時，改成投影或工作項目表，API 形狀不變。例如指派、認領、暫停時鐘、升級（v2 D11）。
- 出現來源自己算不出的篩選或排序鍵時，同樣改。例如指派人、跨來源的優先序、店家風險分數。
- 效能門檻：page_size 50 時，`ListReviewQueue` 的 p95 超過 300 ms。
- 這些條件取代 v2 D7「social 搬進單體就實體化」的觸發條件。

### D′2 通報清單的狀態篩選（3c）

**建議：保留已核准的「全部｜待處理｜調查中｜已結案」（D6′-2）。契約把 `ListReportsRequest.status` 改成 `repeated ReportStatus statuses`：任一相符就列出，空的就不篩選。「已結案」送查證屬實與不成立。這是新的慣例，寫進〈API 設計規範（Connect）〉，之後的清單照它做。**

- **現況**：`status` 只能填一個值（8g 的形狀），表示不出「已結案」。盤點建議契約不動，篩選改成 5 個選項。
- **業界基準**：
  - 工作清單常用「進行中／已結束」分頁，結束的原因另外顯示。GitHub issues 是兩層：`state`（open／closed）加上 `state_reason`（completed／not planned）。
  - Google 的清單篩選基準是 AIP-160 的 `filter` 字串。
  - 本專案沒有重複值篩選的先例：`ListMeasuresRequest` 全是單值。

### D′5 期限的顯示（3c、3d）

**建議：沿用 admin 既有的期限樣式（`SlaCountdown`、發票的 `tax-reviews.ts`：「剩 N 天」／「已逾期 N 天」，文字與色階一起出），改成日曆時間的版本。**
- **清單的期限欄**：「剩 {時長}」，或 danger「已逾期 {時長}」。
  - 剩下不到期限長度的四分之一時，轉成 warning（用開始時間與期限計算）。
  - 絕對時間放在 `title`。
- **詳情頁**：「{期限名}：{日期時間}（剩 {時長}）」，逾期時括號內是 danger「已逾期 {時長}」。
  - 日期時間用既有的 `formatDateTimeShort`，例如 `2026/10/18 14:30`。
- **時長**一律無條件捨去：
  | 長度 | 寫法 | 剛好整數時 |
  |---|---|---|
  | 滿 1 天 | 「{d} 天 {h} 小時」 | 「{d} 天」 |
  | 1 小時到 1 天 | 「{h} 小時 {m} 分」 | 「{h} 小時」 |
  | 不到 1 小時 | 「{m} 分」 | — |
  | 不到 1 分 | 「不到 1 分」 | — |
- **沒有期限，或義務已結束**：顯示「-」（§2 第 12 項：伺服器只在義務還在時輸出期限）。
- **措施清單的徽章**維持「已逾期」（D6′-4 原文）。「複審到期」分頁的「複審期限 {日期}」改成詳情頁的寫法。
- **清單與待辦頁每 30 秒自動更新**，相對時間跟著更新。

這取代 D6′-2 的「{HH:mm} 前確認」與「已逾時 {h} 小時 {m} 分」。

- **業界基準**：Zendesk 的 SLA 徽章顯示剩下的日曆時間，捨入到分、時或天，已違反時是紅色負值，例如「-15m」［外部查證］。
- **為什麼 D6′-2 不同**：它是在只有 4 小時期限時訂的。一般通報 72 小時（D8）會跨日，只寫時刻會被誤讀；「已逾時」「已逾期」也是兩個詞。
- **選項**：
  - (i) 只寫絕對時間「2026/10/18 14:30 前確認」：要自己減，看不出急不急。
  - (ii) 相對時間加色階（建議）：和既有元件一致，絕對時間在詳情頁與 `title`。
  - (iii) D6′-2 原樣：會跨日。
- **約束帳**：「先重用既有元件與 pattern」是根目錄 UI 規則，SELF-IMPOSED，符合基準，保留。

### D′9 已是措施來源的通報，判定不成立（3c）

**建議：允許，但結案對話框在選「不成立」時提示：「這筆通報已是措施 {id} 的依據來源。判定不成立不會撤銷那個措施；如果它只依據這筆通報，請到措施詳情撤銷認定。」措施清單用 D′3 的 `ListMeasures(source_report_id)`。**

- **現況**：3b 允許待處理或調查中的通報當來源，`Resolve` 不檢查它有沒有導出的認定，所以會出現「生效中的措施，來源卻是一筆不成立的通報」。

- **業界基準**：通報（notice）和平台的決定是兩件事，決定可以依據多份通報與自己的調查［一般知識］。
- **選項**：
  - (a) 有導出措施時不能判定不成立：在多對多之下太嚴。
  - (b) 允許並提示（建議）。

  - (c) 只看通報人選的類別：確認收件之後就不準了。

### D′11 複審在到期前多久進待辦（3d）

**建議：RISK 措施的複審在 `review_by` 前 24 小時進入待辦，期限是 `review_by`。措施清單的「複審到期」分頁用同一個判定式。**
