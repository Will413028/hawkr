# 遷移計畫 A2：identity 搬進單體、入口從 gateway 移到單體

**Goal：** account-service（不含代行編排）搬進 `internal/modules/identity`；對外的入口從 gateway 移到單體：認證、CORS、CSRF 成為 `internal/httpapi` 的中介層，還沒搬的 REST、SSE 與 WebSocket 由單體轉給 gateway，gateway 改成信任單體帶的身分 header。四個 client 的登入改用 Connect。完成後刪除 account-service。

**上層：** 遷移計畫 `2026-09-24-go-modular-monolith.md` 的 A2 與「模組完成的定義」（本檔不重複那張清單，只寫 A2 特有的步驟與驗收）。進度寫在本檔，主計畫的 A2 只指向這裡。

**決策：**
- 身分驗證改用 Clerk：ADR `2026-09-27-identity-clerk.md`（Will 2026-09-27：顧客與後台各一個 Clerk application，顧客用 Google、Apple、LINE，不驗手機；Flutter 過渡期用 `clerk_flutter`）。它取代下一條的 D1、D2、D4、D5，步驟在〈改用 Clerk〉。
- 憑證、OTP 與簡訊：ADR `2026-09-27-identity-opaque-sessions.md`（Will 2026-09-27：web 與 App 都是 opaque session；OTP 改存 Postgres，簡訊由 River job 發送）。
- 刪除四個 client 都沒有呼叫的功能（Will 2026-09-27）：provider 的列出、綁定、解綁；單獨的綁定手機（`VerifyPhone`）；登出全部裝置；持久化 active role；管理員的密碼登入與 `create-admin`；後台帳號的 get、suspend、unsuspend、stats 端點；App Review 的 demo 登入與 1303 的手機 bypass；公開的「手機是否已註冊」與 seller-app 在 1303 的預先檢查（手機刻意不唯一，#944；端點可以列舉帳號）。帳號停權留在模組的公開 API（social 的 `BAN_USER` 經 legacy gRPC 呼叫，A7 改成直接呼叫）。App Review 的登入是重新上架時的題目（legacy-backlog 的 P）。
- 其餘「從零設計」的結論在模組 `CARRYOVER.md` 的兩張沿用盤點表；需要 Will 決定的另外標出。

## 前提（開工時核對過）

- gateway 當過渡入口、identity 搬進單體時入口移到單體：Will 2026-09-26（ADR `2026-09-26-external-contract-protobuf-connect.md` D6，主計畫 A0）。
- content 的特性測試（含經 gateway 的執行）保留到 A2，入口移轉時一起退役：Will 2026-09-27。
- 帳號與管理員的主鍵過渡期用 `bigint GENERATED ALWAYS AS IDENTITY`：8 個 Java 服務的 migration 把 `account_id`、`buyer_id`、`store_id` 存成 `BIGINT`，管理員 ID 也是（aftersales 的 `decided_by_admin_id`、payment 的 `created_by`），ADR `2026-09-25-row-identity-by-data-kind.md` 的過渡規則仍成立（2026-09-27 核對）。
- gateway 與舊服務不會部署：後端 CD（第 4 步）以本遷移完成後的單一 image 為對象，gateway 在階段 C 刪除。單體→gateway 的明文身分 header、legacy gRPC 不驗服務間簽章，都只存在於本機與 CI。

## 範圍

**搬進 identity：** 帳號（principal）、角色、管理員、OAuth 連結、session、手機 OTP、Apple token 的撤銷、帳號的刪除與停權、代行的 session 與稽核資料（ADR `2026-09-24-go-modular-monolith.md` D2 的 identity 列）。

**不搬、留在原處到所屬模組：**
- 代行的編排（gateway 的代行路由與 guard、店家狀態檢查）：A10。店家狀態由 `internal/legacy` 的轉接層向 seller-service 讀取後傳給 identity；identity 不依賴 seller。
- 後台刪除帳號的編排（刪賣家、刪買家、再刪帳號）：gateway，A3 搬進 http 層。
- vendor portal 的 Google step-up（`VerifyGoogleIdToken`）：gateway 經 legacy gRPC 呼叫，A3 隨 seller 搬。
- 依手機查帳號（`GetAccountByPhone`，賣家 CRM）：gateway 經 legacy gRPC 呼叫，A6 隨 crm 搬。
- 賣家綁定（`PUT /app/buyers/me/seller_binding` → `BindSeller`）：gateway 經 legacy gRPC 呼叫，A3 搬。

**還在的舊呼叫方（經單體的 legacy gRPC）：** buyer（BindBuyer、GetAccountInfo、RemoveRole）、seller（BindSeller、GetAccountInfo、RemoveRole）、social（GetAccountInfo、GetAccountInfoBatch、SuspendAccount、代行稽核）、crm（GetAccountInfo、GetAccountInfoBatch）、coupon（Java，GetAccountInfo、GetAccountInfoBatch），以及 gateway（上一段的四項與代行的 19 支）。`account.deleted`（buyer、im、notification、seller、social 消費）與 `delegation.operation.completed`（notification 消費）經 legacy 的 RabbitMQ 送出。

## 步驟

步驟 3 到 6 是同一次入口移轉：可以分開 commit，但本機環境要到步驟 6 做完才又能完整登入。

- [x] **0. 盤點與決定**（2026-09-27）
  - `make new-module name=identity from=account-service`；三份盤點（account-service、gateway 的入口、四個 client 的認證）；需要 Will 決定的四項已決定（上方「決策」）；ID token 的 nonce 不加（`google_sign_in` 7.2 只能在 `initialize` 設定一次，理由在模組的沿用盤點）。
  - ADR `2026-09-27-identity-opaque-sessions.md`；被取代的 `2026-09-18-web-session-ssot-and-cache-layering.md`、mitake ADR 的 D1（存 Redis）與 D6 標上 superseded。
  - 模組 `AGENTS.md` 的職責、資料、不變量，`CARRYOVER.md` 的兩張沿用盤點表。
- [x] **1. 模組本體**（`internal/modules/identity`，2026-09-27）
  - schema：帳號、角色（現況表，保留 `source_id` 柵欄到 A3）、管理員、OAuth 連結（主鍵 `(provider, subject)`）、session、OTP、連結確認的一次性 token、Apple token 撤銷的 intent。帳號與管理員的主鍵是 IDENTITY，其餘 UUIDv7 或自然鍵。
  - 登入：Google、Apple（驗證 ID token 的 port，實作放模組的 `internal/`，沒有設定時該方式回 `unavailable`）；1303 手機 detour（OTP 在同一個 transaction 內消耗）；1304 連結確認（伺服器端的一次性 token，取代共用 `JWT_SECRET` 的 tempBindToken）；管理員 Google 登入（網域白名單比對 `hd` claim 與 `email_verified`）。
  - session：建立、解析（一次查詢讀出帳號狀態、角色）、每日最多一次的滑動續期、登出。
  - OTP：發送（冷卻、每日與每小時上限由表算出）、River job 呼叫三竹（`clientid`＝OTP ID，重試只在有效期內）；本機與測試用假的 sender。
  - 角色的授予與移除（`source_id` 柵欄、最後一個角色移除時 cascade 刪除帳號）、停權（解除停權沒有呼叫方，不提供）、刪除帳號：同一個 transaction 內刪 session、刪 OAuth 連結、排入 Apple token 撤銷（刪帳號時也撤銷，App Store 5.1.1(v)），以 `events.Publish` 發出 `AccountDeleted`。
  - 驗收：unit 與跑在自己 schema 的 integration 測試；盤點找到的疑似缺陷各有一個會在舊行為失敗的測試：併發核碼只能成功一次（#2510）、軟刪帳號的 OAuth sub 可以重新註冊且只建一個帳號（盤點 G5）、同一個連結確認 token 只能用一次（G7）、同時第一次登入不回 internal（G6）、管理員與帳號同號時不會互相解析（G8）。
- [x] **2. 對外 API**（根目錄 `api/`，〈API 設計規範（Connect）〉，2026-09-27）
  - `hawkr.identity.v1alpha1.IdentityPublicService`：Google、Apple 登入（web 與 App 共用，由 client 類別決定 cookie 或回傳 token）、連結確認、發送手機驗證碼、管理員 Google 登入。
  - `IdentityAppService`（第一個登入後的 service）：目前的 session（帳號、角色、解析後的 active role）、登出。
  - `hawkr.admin.identity.v1alpha1.IdentityAdminService`：管理員自己的 session 與登出、帳號清單（後台會員頁）。
  - 錯誤：1303、1304、1305 等改成 `ErrorReason`（只為 client 會分支的情境新增）；舊的業務碼隨 CodeMeta 的 identity 段標上擁有者。
  - 驗收：`buf lint`、`make connect`、handler 測試、`TestEveryServiceInTheContractIsMounted`。
- [x] **3. 入口移到單體**（`internal/httpapi`，2026-09-27）
  - 認證中介層：cookie 或 Bearer → identity 解析 → principal 放進 ctx；`rpc.authorize` 改讀 ctx，不再讀 header。
  - CORS（直接呼叫單體的 web 的 origin，單一來源寫在設定）；CSRF 用 `http.CrossOriginProtection`，信任同一份 origin，金流與物流的瀏覽器回跳（`/payment/return` 等）列為 bypass。後台的瀏覽器只打自己的 BFF，跨來源的防護在 admin 的 middleware（BFF 對單體是伺服器的請求，不轉送瀏覽器的 Origin）。
  - 限流：Connect 在單體（依 service 類別分級，subject 沿用 origin-auth 的判定）；轉給 gateway 的 REST 由 gateway 照舊。
  - 轉給 gateway（`httputil.ReverseProxy`）：`/api/v1/*`、webhook 與金流、物流的回跳、`/.well-known/*`。入口一律刪掉 client 帶來的身分 header，認證過的請求設上身分 header（契約寫進〈API 設計規範（Connect）〉§二）；保留 path、Origin、`CF-Connecting-IP` 與 XFF、Set-Cookie；SSE 逐筆送出、WebSocket upgrade、multipart 各有測試。
  - trace 從入口開始：不接續 client 帶來的 `traceparent`（legacy-backlog 的 L265），轉給 gateway 時注入。
  - 驗收：中介層與代理的測試；「只有入口連得到 gateway、入口刪掉 client 帶的身分 header」寫進 wiki 的 CD 待辦。
- [x] **4. gateway 改成信任單體**（2026-09-27）
  - 認證改成讀單體帶的身分 header（重建 gin ctx 與往下游的 metadata），刪除 web session、Redis 撤銷名單、讀穿與負向快取、CSRF、CORS、auth 的 REST 路由與 handler、demo 登入，以及 Connect 代理（單體不再在 gateway 後面）。
  - 現有 API 清單（`api/openapi/openapi.yaml`）刪掉對應的端點，`maxRESTOperations` 隨之下降；路由覆蓋測試通過。
- [x] **5. legacy 轉接與代行資料**（2026-09-29）
  - `internal/legacy` 的 gRPC server（AccountService 的子集、DelegationService），在獨立的 listener；舊服務的 `ACCOUNT_SERVICE_GRPC_ADDR` 指向單體。bitmask 在這裡由角色投影。
  - `AccountDeleted` 與代行完成事件：同一個 transaction 排入 River job，由 legacy 的 publisher 送到 RabbitMQ。
  - 代行的 session、授權與稽核搬進 identity（設計書 56；另做一次沿用盤點，寫進模組 `CARRYOVER.md`）；店家狀態由 legacy 的 seller-service client 讀取後傳入。
  - 驗收：舊服務對單體的呼叫在 compose 環境跑通（buyer 登入後的 EnsureProfile、seller 綁定、social 的停權、gateway 的代行 preflight）。
- [x] **6. client**（由 C1–C10 取代並完成：session 改用 Clerk，見上方 C 段）
  - website：authed 的 Connect transport（`credentials: "include"`、`X-Active-Role`、`unauthenticated` 發 `AUTH_EXPIRED_EVENT`、代行工作區內直接拋錯）；登入、連結確認、session 探測、登出改用 Connect；還沒搬的 REST 指向單體的網址。實測跨來源的 cookie 與 CSRF（試點通過條件 3 延後的部分）。
  - admin：BFF 的登入與登出路由改呼叫 Connect 並轉回 Set-Cookie；`unauthenticated` 時登出；會員頁的帳號清單改用 Connect。
  - buyer-app、seller-app：登入改用 Connect，session token 以 Bearer 帶；刪除 refresh 與 single-flight；buyer 的登出呼叫伺服器（現在只清本機）；每個請求帶固定的 `X-Active-Role`。
  - 刪除各 client 對應的手寫 REST 呼叫與型別。
- [x] **7. 特性測試**（2026-09-29：identity 的特性測試退役，Will 決定；理由與替代的 integration 測試在模組 `AGENTS.md`〈特性測試〉）
  - 舊的一側只能跑不需要 Google、Apple 簽章的情境（未登入的 session 探測、登出、手機檢查、OTP 的限流）：OAuth 的登入由 integration 測試以假的 verifier 涵蓋，理由記在模組 `AGENTS.md`。
  - content 的 REST driver 與經 gateway 的執行退役（Will 2026-09-27）。
- [x] **8. 收尾**（2026-09-29）
  - 盤點 CSV 的去向（53 支 RPC、2 個事件、副本）；刪除 account-service、compose service、CI 的路徑；`pkg/` 裡只剩 account-service 使用的套件一併刪除。
  - CodeMeta：`AccountType` 從 platform 移到 identity 的型別（ADR `2026-09-25-codemeta-retirement.md` 過渡第 1 步）；identity 的業務碼標上擁有者。
  - legacy-backlog 的「A0（改綁 A2）」與「A2 identity」兩段、`account-id-allowlist`、`pkg-refactor-plan` 的 A2 項逐項處置。
  - 相關 ADR 逐份核對：identity 的五份（2026-06-29、07-07、07-11、08-19、09-18 blacklist）、Apple OAuth、internal auth HMAC、代行的六份、seller capability。
  - D9 gate、`check-migration-inventory.py --assume-gone account-service`、獨立設計審查（design-review）。

## 改用 Clerk（Will 2026-09-27）

決策與理由在 ADR `2026-09-27-identity-clerk.md`。上面的步驟 1–8 是自建版本的紀錄；以下的步驟完成時，自建的登入、session 與手機驗證一併刪除。C1 任一項不成立就停下來回報 Will（ADR 的重新評估條件），不在不成立的前提上繼續做。

- [x] **C0 前置（Will，2026-09-27）**：建立 Clerk 帳號與兩個 development instance（顧客：Google、Apple、LINE；後台：Google）。publishable key 與 secret key 存在本機（website、admin 的 `.env.local`，backend 的 `.env`），不經過對話。
- [x] **C1 前置驗證**（2026-09-27，在 scratchpad，不進 main；測試使用者以 Backend API 建立，驗證完刪除，兩個 instance 都確認沒有殘留）：
  - 單體在本機驗 token：成立。以單體已有的 `go-oidc` 驗 Backend API 簽出的 session token（`iss` 是 frontend API，RS256，JWKS 取一次），竄改與 issuer 不符都被拒；token 效期 60 秒，claims 是 `exp`、`fva`、`iat`、`iss`、`nbf`、`sid`、`sts`、`sub`、`v`。Backend API 簽的 token 沒有 `azp`，所以 `azp` 只在出現時比對允許的 origin。撤銷 session 之後，已簽出的 token 在效期內仍驗得過，停權因此要每個請求查 identity（ADR D5）。
  - Next.js SDK 在 OpenNext（Cloudflare Workers）上：成立。最小專案，版本同 website（Next 16.3.4、OpenNext 1.20.6、wrangler 4.125.0、`@clerk/nextjs` 7.9.7），以 `wrangler dev`（workerd）執行。Bearer 的請求在 route handler 認得使用者，`getToken()` 取得到 token；匿名的瀏覽器走完 development instance 的 handshake，middleware 在同一個回應寫出多個 Set-Cookie，瀏覽器都收到，之後不再重導。沒驗到的：真人登入之後以 cookie 認人（instance 只開社群登入，ticket 登入需要 email 之類的識別），留到 C5 以 Google 或 LINE 實際登入驗收。
  - `clerk_flutter`（0.0.18-beta，底層 `clerk_auth` 是純 Dart）：可行，有條件。對顧客 instance 實際呼叫：啟用的策略是 `oauth_apple`、`oauth_google`、`oauth_line`，三者都能建立 OAuth 的 sign-in，外部網址分別是 accounts.google.com、access.line.me、appleid.apple.com；完成的 API 是 `completeOAuthSignIn`（redirect 帶回的 rotating token）。套件預設以 App 內的 WebView 開 OAuth，Google 不允許內嵌 WebView 登入，所以一律改用系統瀏覽器（`SFSafariViewController` 或 `ASWebAuthenticationSession`）加 deep link 回到 App。原生登入走 `idTokenSignIn`：Apple 需要在 Clerk 登錄 iOS App（App ID prefix 與 bundle ID），Google 需要換成自己的 Google 憑證（development instance 的共用憑證不接受 `google_one_tap`）。沒驗到的：在 iOS 上真人完成登入，留到 C7。
  - 刪除 Clerk 的使用者時 Apple 的 token：不會撤銷（Clerk 的 iOS 文件：「Deleting the user from Clerk does not reset this on Apple's side」），Clerk 也不把 Apple 的 token 交給我們。ADR 的後備（刪資料、引導使用者手動撤銷）成立；另一個做法是刪帳前 App 再以 Sign in with Apple 取得授權碼，由 identity 換成 token 後撤銷（沿用現有的 `internal/apple`），待 Will 決定（2026-10-08 改成登入時交出授權碼、伺服器保存並在刪帳時撤銷，見 identity-clerk ADR 文末修訂）。

      - `packages/hawkr_auth` 的 `clerk.dart` 登出先 `signOutOf(session)` 再 `signOut()`，繞過 `clerk_auth` 0.0.18-beta 只清本機、不結束伺服器 session 的 bug：每次升級 `clerk_auth` 時以該套件的 `test/clerk_test.dart` 確認 bug 是否還在，不在就拿掉。
      - 撤銷先於刪帳的代價、LINE 按鈕用官方素材與否、seller 的 iOS URL scheme：同 buyer 刪帳，第一次送外部測試之前。
