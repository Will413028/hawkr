# 跨專案文件搬到根目錄 `docs/`

**Goal：** repo 層級的文件（全部 ADR、四端共用的規範、之後的跨專案計畫）放在根目錄 `docs/`，只有某個子專案需要的留在該子專案的 `docs/`。搬完之後，每個指向搬走文件的路徑都解析得到檔案，由 CI 的路徑檢查擋下斷掉的引用。

**來源：** 2026-11-05 的單體架構 review 追問（Will：「文件是不是不該放在 backend 裡面」）。`backend/docs` 是公司時期多 repo 的 backend repo 自帶的文件，併成 monorepo 時整包帶進來，位置沒有重新決定過（根目錄 `AGENTS.md`「沿用也是決策」）〔推論〕。

**本檔的位置：** 決定之前根目錄還沒有 `docs/`，所以本檔照現行慣例寫在 `backend/docs/plans/`；完成後在收尾步驟分流並刪除（D9）。

**狀態：** 草稿，D1–D8 待 Will 決定，決定前不開工。另有硬前提 P0（見「全域約束與完成定義」）：分支 `payment-onboarding` 合進 `dev` 之前不開工。

證據等級：〔量測〕＝以指令或讀檔確認；〔推論〕＝由程式與文件推得；〔推測〕＝憑公開資料記憶，未逐條查證。

## 全域約束與完成定義

- **硬前提 P0：分支 `payment-onboarding` 合進 `dev` 之後才開工，開工時重跑「前提」段的全部盤點。** 前提段的數字（引用處數、檔案數、ADR 數）是在 `f71a7a8` 量的，那個分支改了 `backend/docs` 底下 39 個檔並新增引用，合併後這些數字都會過時，不能沿用。P0 沒滿足不得開始任何步驟（包括步驟 0 之外的所有搬檔與改引用）；步驟 0 負責核對 P0 並重跑盤點，不滿足就停下來問 Will，不自行繞過。
- 只動文件、引用、指令檔與一支新的檢查腳本；不改任何程式行為。程式裡當作執行路徑使用的字串（工具在 `backend/` 目錄執行時讀的路徑）不改，只改註解與文件。

- 搬檔一律 `git mv`。搬檔與改它的引用在同一個 commit，每個 commit 的路徑檢查與 CI 都是綠的。
- 每個要改的目錄開工前跑 `git status --short <目錄>`；有其他 session 未提交的改動就跳過該單元並回報。

  - 收尾的舊路徑 grep 歸零（指令在步驟 5）；
  - 路徑檢查在 CI 的 repo-hygiene 執行並通過；
  - 根目錄與 backend 的 `AGENTS.md`、`設計文件治理規範.md`、ADR README 指向新位置。

## 決定（待 Will）

- **D1 搬哪些 ADR**（擋住：步驟 2）
  - **A（建議）：全部搬成一份紀錄。** ADR 是整個產品的決策紀錄，每份已經有「影響範圍」欄位；分成兩處的話，每開一份新 ADR 都要先判斷放哪，索引也要兩份，ADR 之間互相引用還會跨兩個目錄。不少看似後端的 ADR 也牽動 client，例如錯誤模型、ETag、圖片 URL。
  - B：只搬影響範圍含後端以外的。代價：110 份要逐份分類，之後每份新 ADR 都要判斷。
- **D2 搬過去的 ADR 裡既有路徑的基準**（擋住：步驟 2）
  - **A（建議）：保留相對 backend 的寫法。** 在每份搬過去、有這種路徑的 ADR 表頭加一列「路徑基準｜`backend/`」，ADR README 寫明新 ADR 一律相對 repo 根目錄。表頭是中繼資料，不改結論。
  - B：全部改成相對根目錄（372 處、76 份）。不少路徑指向已刪除的舊服務，無法用「檔案存在」驗證改寫是否正確。
- **D3 歷史計畫與舊設計書裡的引用**（擋住：步驟 2、3）
  - **A（建議）：照 D8 的規則改路徑字串，內容不動。** 路徑不改，歷史紀錄就打不開。AGENTS.md 分層計畫選擇不改歷史計畫（「它們是紀錄」），但那裡引用的是段落，段落還在原檔；這裡是檔案換了位置，只改路徑字串不改變紀錄的內容。
  - B：不改，在根目錄 README 放舊路徑對照表。
- **D4 根目錄放規範的目錄名**（擋住：步驟 3）
  - **A（建議）：`docs/共通規範/`。** 和 `backend/docs/開發規範/` 不同名，D8 選 C 時必須如此；名稱對應根目錄 `AGENTS.md` 的「共通規則」。四份檔名不變。
  - B：`docs/開發規範/`。只有 D8 選 A 時可行。
- **D5 計畫放哪**（擋住：步驟 4 的 README 內容）
  - **A（建議）：** 新開的跨專案計畫放根目錄 `docs/plans/`，backend 專屬的留 `backend/docs/plans/`；進行中的計畫不搬（見延後），本檔也不搬。
  - B：計畫全部留在 backend。
- **D9 完成的計畫不留在 repo**（已決 2026-11-12，Will，選 A；擋住：步驟 4b、5）
  - **A：** 計畫在自己的收尾步驟分流後刪除：決定併入 ADR，現行行為併入 `docs/modules/` 或規範，延後項搬回主清單，指向計畫的引用改指 ADR 或模組文件，然後刪計畫檔與附件；git 歷史是紀錄。已接受的 ADR 裡指向計畫的引用不改寫正文，加修訂段說明計畫已刪、內容併到哪裡。失敗條件：沒分流就刪，理由只剩 git 歷史。
  - 未採 B（留在原地當紀錄）：計畫寫的是當時的步驟，與現行程式矛盾時仍會被搜尋到，而且只增不減。未採 C（搬到 archive 子目錄）：引用照樣要改，過時內容照樣搜得到。
  - 推翻條件：要讓訪客在 GitHub 上讀到計畫當作過程證據；或有程式註解需要步驟層級的理由而 ADR 與模組文件放不下。
  - 可逆性：`git` 可整份找回；已公開的檔案連結會斷。
- **D6 舊 gateway 的文件檢視器**（擋住：步驟 4）
  - **A（建議）：** 接受 ADR 不再出現在本機的 `/docs` 檢視器。gateway 是遷移期的舊服務，檢視器只在本機用，GitHub 也能讀 markdown。
  - B：`docker-compose-local.yml` 加掛根目錄 `docs/`，並改 gateway 的檢視器支援兩個根。
- **D7 路徑檢查的範圍**（擋住：步驟 1）
  - **A（建議）：** 只檢查指向 `docs/adr/`、`docs/共通規範/`、`docs/plans/`（根目錄與 backend 兩處）的引用。今天這些引用沒有斷的，可以從第一天就零容忍。
  - B：所有 `docs/` 路徑。今天有樣板路徑（`docs/modules/{1}.md`、`<模組>.md`）與指向已刪文件的引用，要先建例外清單。
- **D8 引用的寫法**（擋住：步驟 1–3；決定前最重要的一題）
  - 問題：backend 裡的檔現在用相對 backend 的 `docs/…` 寫法（1,402 次、641 檔）。搬完之後，`docs/adr/` 在根目錄、`docs/modules/` 在 backend，同一個前綴會有兩種基準。
  - A：全面改成從 repo 根目錄起算（`docs/adr/…`、`backend/docs/modules/…`）。之後沒有歧義，檢查只需要一種解析規則。代價：
    - 改註解與文件約 1,400 處；
    - `payment-onboarding` 等進行中的分支會大面積衝突；
    - 程式裡當作執行路徑的字串要逐一排除。
  - **C（建議）：維持「相對所在子專案」的寫法，靠目錄名不重複消除歧義。**
    - backend 的檔寫 `docs/x/…` 時：`backend/docs/x` 存在就指它，否則指根目錄 `docs/x`。
    - 根目錄 `docs/` 與 `backend/docs/` 的第一層目錄名不得重複（D4 選 A），由路徑檢查強制。
    - 相對 backend 的 121 處 `docs/adr/…` 一字不改就指到新位置；要改的只有 `backend/docs/adr/…` 167 處、markdown 相對連結 146＋12 處，以及四份規範的 35 處。
    - markdown 連結改成以 `/` 開頭的 repo 根目錄路徑。GitHub 會把 `/` 開頭的連結解析成 repo 根目錄〔推測〕，開工時在 GitHub 頁面實際點一次確認。
  - 若選 A，排在 `payment-onboarding` 合進 `dev` 之後。
