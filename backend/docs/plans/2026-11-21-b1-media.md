# 遷移計畫 B1：media 改寫成 Go，並改成不認識業務

**Goal：** 單體的 `internal/modules/media` 擁有自己的 schema 與儲存層，只管資產與其生命週期（暫存 → 確認 → 刪除）與可見性（public／secure），不認識任何業務類型；引用只存在擁有者的資料表。完成後（可驗證的終態見 B1-8）：

- 7 個 Go 擁有者模組（buyer、content、im、moderation、review、seller、social）在自己的 transaction 內確認與標記刪除資產；`media_ref_sync`、`retired_assets` 共 14 張表與 14 種 `media_sync`／`media_sweep` job、`media.RefSyncer` 等引用同步演算法全部刪除。
- 上傳與機敏上傳以 `api/` 的 Connect 契約由單體提供，四個 client 的上傳全部改用生成的 client；gateway 的 `/api/v1/app/media/*`、代行營運的 media 路由與 `openapi.yaml` 對應 operation 全部刪除（B1-D7）。
- `internal/legacy/mediaservice` 刪除；單體不再呼叫 Java media-service。
- Java media-service 與它的 Java 呼叫端不改程式、不寫轉接；四個 Java 服務與四個舊 Go 服務（review、im、invoice、ai）需要 client 上傳的流程從 B1-4 起本機失敗，直到各自改寫（B1-D7、B1-D11，Will 2026-11-21 接受）。

**上層：** 主計畫 `2026-09-24-go-modular-monolith.md` 的「全域約束」「模組完成的定義」與 B1 段；本檔只寫 B1 特有的步驟與驗收。進度寫在本檔，主計畫 B1 段只指向這裡。本檔取代 ADR `2026-10-03-media-references-owner-side.md` 的「過渡（Java media 不變）」段的適用範圍：過渡機制在 B1-5 刪除。

## 範圍

- 做：Go media 的 schema 與儲存層（R2＋測試用 fake）、上傳（公開與機敏）、確認、刪除、暫存 GC、機敏讀取；7 個擁有者模組改用新介面並刪除過渡機制；Connect 契約與四個 client；gateway 與 openapi 的 media 路由刪除；`internal/legacy/mediaservice` 刪除；Go 端 `ref_type` 與 CodeMeta 中只剩 Go 使用的值域處理；缺陷 5.1、5.3、5.4、5.7、5.8、5.12、5.14–5.17 在新實作修掉。
- 不做：改 Java media-service 與它的 Java 呼叫端（B3、B4、B8、B9 才遷），也不為它們保留舊上傳路徑或寫轉接（B1-D7）；Go 舊服務目錄（seller、im、ai、review、invoice-service）裡的 media client（隨各服務目錄刪除；invoice 是 B10）；`imageai` 模組搬遷（不在 B1）。
- 延後：
  - Java media-service 退場（刪服務目錄、compose service、Java CI 路徑、`api/proto/media`、CodeMeta 中仍被 Java 使用的 `AssetReferenceType` 值）。觸發：最後一個 Java 呼叫端（B3、B4、B8、B9）與 Go invoice-service（B10）遷出；退場時一起刪 Java `ImageMetadataStripper` 等。B1 期間它原封不動，不為它新增任何程式。
  - 四個 Java 服務的上傳流程恢復（`upload-routing.md` 第三節的每一條）。觸發：各自的改寫步驟（B3、B4、B8、B9）改用 Go media 的 `Confirm`。
  - 四個舊 Go 服務的上傳流程恢復（`upload-routing.md` 第四節的 8 條，B1-D11）。觸發：評價圖與聊天傳圖是 A6-6（client 切到單體的 review、im）；稅籍證明與發票解鎖佐證是 B10；AI 風格縮圖是 ai-service 搬進單體。

      - 密文格式（`internal/modules/media/internal/secure`，只用標準庫）：header ＝ magic 4 位元組＋版本 1＋段大小 uint32＋nonce 前綴 7 位元組；每段 AES-256-GCM，nonce ＝ 前綴＋big-endian uint32 段序號＋1 位元組末段旗標；每段的 AAD 是整個 header。段大小 64 KiB（age 的值）；解密端拒絕版本不符、段大小為 0 或超過 1 MiB 的 header；段序號溢位回錯誤。空明文是一個空的末段。解密端預讀一段判斷末段，一段驗過 tag 才交出它的明文。
      - 金鑰：每檔 32 位元組隨機 DEK；以 KEK 用 AES-256-GCM 包裹（隨機 12 位元組 nonce，AAD ＝ 資產 ID 加 `kek_id`，防止把別列的 wrapped DEK 換過來），`wrapped_dek` ＝ nonce＋密文＋tag。KEK 設定比照 `internal/platform/seal` 的金鑰環寫法：單一字串、逗號分隔的 `<kek_id>:<標準 base64 的 32 位元組>`，第一把用來寫入、全部都能讀；空字串、格式錯、長度不是 32、id 重複時 `ParseKeyring` 回錯誤（啟動失敗）。環境變數 `MEDIA_KEKS` 由組裝點讀（B1-5 接線），模組不自己讀環境。新寫入用第一把（下稱 primary）；讀取依列上的 `kek_id` 找，找不到回錯誤。沒有 keyring 的模組 `UploadSecure`、`ReadSecure`、`RewrapDEKs` 回錯誤，不寫任何物件。

- **B1-D1 暫存 → 確認由誰、何時做**（狀態：已決 2026-11-21，Will：A；擋住：B1-2、B1-5；需要的事實：無）
  - A：擁有者在自己的 transaction 內呼叫 `Confirm(ctx, tx, …)`，業務列與確認原子；GC 只刪未確認的暫存（建議：業界基準 Rails Active Storage 的 attachment 與業務列同一 transaction，ADR `2026-10-03`「基準 1」）。
  - B：維持兩步（transaction 外先確認、後寫業務列）——確認了卻沒掛上的資產沒人回收，因為終態的 GC 不再刪已確認資產。
- **B1-D2 staged token 與暫存上傳的形狀**（狀態：已決 2026-11-21，Will：A；擋住：B1-2、B1-3）
  - A：不透明 ID＋查表，撤銷與過期都在表（建議：單體內有表就不需要簽章的第二份真相）。
  - B：沿用 HS JWT（Java `StagedTokenService.java:90`）。
- **B1-D3 資產用途模型（取代 22 個 `ref_type`）**（狀態：已決 2026-11-21，Will：A；擋住：B1-2；事實：`spike.md` (b)(d)）
  - A：只有 `visibility`（public／secure），object key 不含 category（建議；用途在擁有者的表本來就有）。
  - B：media 持有封閉的 `purpose` 列舉——又把業務清單放回 media，違反 ADR 終點。
  - C：擁有者傳自由字串 purpose，只用於 key 前綴與觀測。
- **B1-D4 機敏檔密文格式與讀取介面**（狀態：已決 2026-11-21，Will：A；2026-11-22 Will 修訂金鑰為信封加密：每檔隨機 DEK 以 KEK 包裹存資產列，輪替只重新包裹，不重寫 R2 物件；原 A 的「HKDF 由主密鑰導出每檔金鑰」被取代。ADR `docs/adr/2026-11-22-media-secure-stream-aead.md`；擋住：B1-2；事實：`spike.md` (a)，標準庫可行）
  - A：分塊 AEAD（STREAM 構造）＋`io.ReadCloser`，竄改在送出明文前失敗，記憶體不隨檔案大小成長（建議，前提是標準庫可行）。
  - B：沿用單段 GCM，讀完驗 tag 再回 `[]byte`（≤ 上限全進記憶體）。
  - 兩者都加 key id 與兩把主密鑰並存（缺陷 5.7，不列選項）。
- **B1-D5 上傳通道**（狀態：方向已決 2026-11-21，Will：「照業界做法，不因為是作品集而略過」；擋住：B1-3；事實：`spike.md` (e)，預簽 PUT 可綁確切大小、型別與只寫一次）
  - 業界基準（推論，依 AWS S3 與 Cloudflare R2 文件與 Rails Active Storage direct upload、Shopify staged uploads 的公開做法；B1-0 (e) 核對 R2 實際支援）：client 以短效預簽網址直傳物件儲存的**私有暫存區**，簽章綁定 `Content-Length`（或上限）與 `Content-Type`，上傳流量不經應用伺服器；client 回報完成後，伺服器端非同步處理：依 magic bytes 辨認格式、驗大小、剝除 metadata、產生正式物件寫入 `public/`（或機敏區），處理完成前資產不可被確認或公開；暫存區由儲存端生命週期規則加 GC 清除。
  - 原建議「全部經單體串流」被這個基準取代：它把上傳流量與長連線壓在應用伺服器上，業界在有物件儲存時不這樣做。
  - 機敏檔：依同一基準直傳私有暫存區，伺服器端處理時做應用層加密寫入機敏區並刪暫存物件；加密格式依 B1-D4。若 spike (e) 顯示這會讓明文在暫存區停留超出可接受範圍，列回決定題。
  - 實作細節（處理 job 的重試、client 輪詢或推播處理結果）在 B1-2、B1-3 設計，不再交 Will。
  - **修訂（Will 2026-11-22）**：機敏檔不走預簽直傳，改由 client 經單體上傳、單體在請求內辨認格式並邊收邊加密寫入 `secure/`，明文不落 R2；public 圖片維持預簽直傳。ADR `docs/adr/2026-11-22-media-upload-channels.md`。B1-2b 為 secure 實作的預簽路徑由 B1-2c 移除。
- **B1-D6 對外契約與 client 切換的切分**（狀態：已決 2026-11-21，Will：A；擋住：B1-3、B1-4）
  - 契約是 Connect 已由 ADR `2026-09-26-external-contract-protobuf-connect.md` 決定，不列選項。
  - A：B1-3 單體端先落、B1-4 四個 client 同一步切完並刪 gateway 路由（建議；上線前沒有相容性窗口）。
  - B：單體提供同路徑的 REST 轉接，client 之後再換——留下會被刪的轉接層。
- **B1-D7 Java 呼叫端還在時 Java media 怎麼處理**（狀態：已決 2026-11-21，Will：都不選，改為 D。結論：client 與 gateway 全部切到 Go media，不保留舊上傳路徑、不寫轉接；四個 Java 服務的上傳流程暫時失敗到各自改寫；Java media-service 原封不動到退場。理由：系統未上線，不寫之後要拆的東西；擋住：B1-4、B1-5、B1-6、「延後」第一項；事實：四個 Java 呼叫端都吃 client 經 media 上傳會話取得的 staged token，見前提）
  - A′：兩套並存、client 依功能分流：Go 擁有者的上傳（頭像、店家圖、KYC、聊天、評價、貼文、banner）打 Go media 的 Connect；Java 服務的上傳（商品圖、訂單評論、售後佐證、出貨照片）繼續打 gateway 舊路徑到 Java media。分流在 client 的呼叫點，不在 media（D3 選 A 後 media 不認識用途）。舊路徑隨 B3、B4、B8、B9 逐一刪除；Java media 退場條件＝最後一個 Java 呼叫端與 Go invoice-service 遷出（建議）。代價：過渡期 client 有兩套上傳碼。
  - B：單體為 Java 呼叫端開一個舊契約的 gRPC 轉接面，client 全部改打 Go media——要在 Go 實作 Finalize／Link／Unlink／Release 的語意給 Java 用，與 ADR 終點矛盾，而且是之後要拆的轉接層。
  - C：B1 排在 B3、B4、B8、B9 之後——那些模組改寫時又需要 Go media，形成循環，實際上要先做 B1。
- **B1-D8 資產 ID 方案**（狀態：已決 2026-11-21，Will：A；擋住：B1-2、B1-5）
  - A：UUID v7（建議；ADR `2026-09-25-row-identity-by-data-kind.md` 的方向，從零設計的做法）；7 個模組的 `*_asset_id` 欄位改型別隨 B1-5 的 migration。
  - B：沿用 TSID（BIGINT，序列化成字串）。

  - A：擁有者 transaction 內 `MarkDeleted(tx, …)`，media 自己的 job 刪 R2 物件（建議；同一個 Postgres，沒有指令遺失的窗口，media 不必認識事件）。ADR `2026-10-03` 決策段字面寫 outbox，選 A 要在 ADR 文末加修訂。

  - A：新增 CI job，以 compose 子集起 Postgres、Java media、gateway，REST driver 對 Java 跑情境；Connect driver 對單體跑同一份（建議；這是主計畫階段 B 開工前條件 1 的字面要求，也是之後 B2–B10 每個 Java 改寫都要用的基礎，一次做起來。代價：新 job 的 CI 時間與維護，B1-0(c) 估）。

- **B1-D11 token 交給舊 Go 服務的 8 個上傳呼叫點在 B1-4 後怎麼辦**（狀態：已決 2026-11-21，Will：A；擋住：B1-4、B1-5 的範圍；事實：`upload-routing.md` 第四節——review-service 2、im-service 3、invoice-service 2、ai-service 1；B1-D7 只涵蓋四個 Java 服務）

- **B1-D12 CI 對 Java media 跑特性測試時用什麼當物件儲存**（狀態：已決 2026-11-21，Will：A；擋住：B1-1；事實：Java 的 R2 endpoint 寫死、沒有 path-style 開關，S3 替身接不上，`spike.md` (c) 阻礙 1）
  - A：不接儲存。Java 在 R2 設定不完整時照常啟動，「建立上傳會話」與「完成」可測（完成時不回查物件）；機敏上傳與機敏預覽對 Java 測不到，這兩個端點的行為規格改以 Java 原始碼與既有單元測試為準，寫進 `test-map.md`。不改 Java、不加依賴。
