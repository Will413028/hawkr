**驗收基線：** B7-0 跑單體與 gateway 的 unit 測試、`make lint-monolith`，以及 Java coupon-service 的 `mvn test`，結果記在文末「基線」。既有失敗不在本階段修。integration 與 e2e 不在本機跑，推上去看 CI；CI 一次只推一批。

## 決定

選項、業界基線、限制帳、各選項失敗條件與可逆性見 `2026-11-23-b7-coupon/decision-brief.md`；本段只留結論。全部 Will 2026-11-23 依簡報建議拍板。

- **D1 Java order／aftersales 在 B8／B9 前的呼叫**：`legacy/couponserver` 以 gRPC 轉接 5 支 RPC，B8／B9 刪除。模組 API 照 B8 的形狀設計（在呼叫方 transaction 內執行的 `Lock`／`Redeem`／`Release`，冪等），轉接只包一層。Java 送 `couponTemplateId`，轉接對到該買家在該活動下可用、最早到期的 voucher；沒領過就回「未領取」，不當場發券（client 先領券）。
- **D2 資料模型**：錢包模型。`coupon_campaigns`（活動規則、總量、資格）與 `coupon_vouchers`（買家持有的券；狀態 `available`／`locked`／`redeemed`／`voided`，到期從 `end_at` 推導，不用排程改狀態）。領券、admin 發券、系統補償都只是建立 voucher；`coupon_claims` 併入 voucher，`coupon_target_accounts` 保留為資格名單。資格只有一個判定函式，領券與鎖券都呼叫它。數量上限以條件式 UPDATE 原子遞增。
- **D3 訂單相關資料**：
  - B7 期間的釋放（Will 2026-11-23 選 A）：鎖沒有到期時間，只有持鎖訂單的 Release（Java 取消、付款逾時時呼叫）或 Redeem 能解除；被鎖的券不能再被別的訂單鎖。不做反查 order 的對帳 job、不做推導式釋放。Release 漏送時券卡在 `locked`，由 admin 作廢單張券（D6）人工處理；spike 1（`spikes.md`）查到 Java 的 Release 全無重試，且結帳鎖券失敗的補償（`CheckoutService.java:1072-1088`）不呼叫 Release。Will 2026-11-23 選 A：轉接層的 Release 以 `order_no` 為鍵、冪等（`instance_id` 可省略，現有 proto 已有欄位）；Java 鎖券失敗補償補呼叫 Release；Java 各取消路徑的 Release 改寫進既有 `coupon_consumption_tasks` 由 worker 重試。這些 Java 改動在 B7-4、與 D4 同批，B8 隨 Java 刪除。B8 改成訂單狀態轉換同 transaction 釋放。
  - MEMBER 資格：coupon 持有 `store_buyer_membership` 投影，由訂單完成事件餵入（B7 期間來自 Java 的 MQ，B8 改同 transaction 事件並 backfill）。spike 2 查無可用事件時，改同步 port，由 `legacy/orderservice` 實作。
  - 出站：Account、Buyer、Seller 的 6 支改成直接呼叫模組 API，不沿用「失敗回空」的降級；顯示資料讀取失敗時整個請求失敗。
- **D4 補償券冪等**：以 `(source_type, source_id)` UNIQUE 去重。轉接 RPC `GrantSellerCompensationCoupon` 加必填的 `source_id`（售後單 id），兩份 proto（`backend/api/proto/coupon/coupon.proto`、`services/java/shared/java-proto/src/main/proto/coupon/coupon.proto`）與 Java aftersales 的呼叫在同一個變更裡修改。
- **D5 提前結束活動**：只擋新的領取與鎖定；`locked` 照常完成或釋放；`available` 作廢。
- **D6 admin**：只做營運必要的能力：建立、發布與提前結束平台活動（結束語意同 D5）、指定發放、作廢單張券、賣家配額。後端走 Connect admin 方法（宣告權限、audited），admin 畫面同一階段做，版面先給 Will 同意（B7-5 的停止條件）。其餘 admin RPC 刪除。
  - D6 修訂（Will 2026-11-24）：admin 另有三支唯讀方法——列活動（含店家活動，可依狀態、發行者篩選）、活動明細（含已發數量）、列某買家的券——供 B7-5 畫面找 ID；舊系統沒有對應 RPC，屬新增能力，B7-3b 一起做。
- **D7 到期提醒**：依 A8 計畫 D13（不做 legacy 通知轉接），coupon 發 in-process 事件 `VoucherExpiring`，由 notification 模組訂閱。因此 B7-5 被 A8-3 擋住。
- **D8 刪帳、停權**：刪帳直接訂閱單體 buyer 的 in-process 事件 `BuyerDeleted`（`modules/buyer/events.go`），在同一個 transaction 內處理，並依 `platform/lockorder` 的順序上鎖；`buyerrelay`、`sellerrelay` 轉給 coupon 的部分在 B7-5 刪除。
  - 修訂（Will 2026-11-23，B7-2 實作時）：店家停權不改活動資料、不訂閱 `StoreSuspended`／`StoreUnsuspended`；資格判定經 seller port 查店家是否停權，停權期間擋領券與 Lock，解除後自動恢復。ALL 資格不沿用 Java 的「買家註冊早於活動建立」限制。
