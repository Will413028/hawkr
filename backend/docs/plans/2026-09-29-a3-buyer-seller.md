# 遷移計畫 A3：buyer、seller 搬進單體

**Goal：** buyer-service 搬進 `internal/modules/buyer`，seller-service（推薦賣家排行除外）搬進 `internal/modules/seller`；兩者往上的補資料移到 `internal/httpapi` 的讀取組裝；gateway 裡跟著它們的編排（申請開店、後台刪帳號、賣家停權檢查、store／buyer ID 的解析）搬到單體。四個 client 改用 Connect。完成後刪除 buyer-service、seller-service，identity 拿掉為它們保留的過渡機制（`source_id` 柵欄、`RoleState`、`ActsAsBuyer`）。

**上層：** 遷移計畫 `2026-09-24-go-modular-monolith.md` 的 A3 與「模組完成的定義」（本檔不重複那張清單，只寫 A3 特有的步驟與驗收）。進度寫在本檔，主計畫的 A3 只指向這裡。

**盤點：** `2026-09-29-a3-buyer-seller/` 的三份（buyer、seller 的領域與機制、seller 的介面），快照為 `bdf13a034`。文中的計數與產生它的指令都在那裡；盤點時的輔助腳本沒有保留。

## 前提（開工時核對過，2026-09-29）

- 帳號、買家、賣家 ID 過渡期用 `bigint GENERATED ALWAYS AS IDENTITY`：Java 服務仍以 `BIGINT` 保存 `buyer_id`、`store_id`（主計畫 A3 段下方；ADR `2026-09-25-row-identity-by-data-kind.md` 的過渡規則）。
- identity 的買家 profile 目前經 `internal/legacy/buyerservice` 呼叫 buyer-service，暱稱一律取當次 token 的 name claim（210179ec1）。A3 由 buyer 模組接手，這個行為保留。
- 依賴表（`internal/arch/modules.go`、ADR D2）：buyer → identity、media；seller → identity、media；buyer 與 seller 互不依賴。ADR D2 的理由欄寫「seller 的往上呼叫都是推薦排行」不準：評價統計、粉絲數、商品瀏覽的歸屬也是（seller 盤點 §3.8），步驟 0 更正。
- gateway 與舊服務不會部署（A2 前提），單體→gateway 的身分 header 只存在於本機與 CI。
- product、order、cart、coupon 等仍是 Java，A3 之後還會呼叫 buyer、seller：單體要提供 legacy gRPC server，事件仍要經 `internal/legacy/rabbitmq` 送到 RabbitMQ。

## 範圍

**搬進 buyer：** 買家 profile 與 stint、收貨地址、收藏、瀏覽紀錄、補貨通知訂閱、買家會員與額度（`GetBuyerEntitlement` 仍被 ai-service 使用）、追蹤賣家（歸屬見決定第 3 項）、買家的刪除與 PII 清理。

**搬進 seller：** 店家 profile 與 stint、申請開店、KYC 認證、PayUni 子商店、管理員停權、治理（檢舉、食安通報、違規、申訴）、商品瀏覽數、刪店與 PII 清理、商家名單（歸屬見決定第 6 項）、停權的能力檢查（從 gateway 移進單體）。

**搬到 `internal/httpapi`（讀取組裝，依賴表不允許模組做的）：** 收藏、瀏覽、追蹤、補貨清單、收藏中心、會員卡、消費紀錄的補顯示欄位；seller 的評價統計與粉絲數。還在 Java 的 product、order 以 `internal/legacy` 的 client 讀取。

**不搬（依 ADR D8 刪除，去向寫「刪除」與理由）：**
- buyer：`notifications` 表與通知 RPC、`MemberLevel` 升等、`GetBuyerProfileBatch`、`POST /app/buyers/me`、後台 `agent_entitlements` 與 `/buyers/me/assistant/quota`、Redis 的收藏集合與地址快取。
- seller：沒有呼叫方的 7 支 RPC（`GetSellerByMemberId`、`ValidateSeller`、`RegisterPayuni`、`RetryPayuniRegistration`、`GetSellerPayuniConfig`、`SaveCertificationDraft`、`SubmitCertification`）、`seller_store_visitors` 與讀取它的路由、申請時的商家名單邀請碼歸屬、沒有 exchange 也沒有消費者的 5 個 `seller.governance.*` 事件、兩個沒實作的 `payment.membership.seller.*` consumer、Redis 的停權標記與 store 解析快取。
- `PUT /app/buyers/me/seller_binding`：website 在建店前先授予 SELLER（還沒有店就有角色）；建店與授予角色同一個 transaction 之後多餘。

**留給之後的步驟：**
- 推薦賣家排行（`GetRecommendedSellers`、`/public/sellers/recommended`、`/public/marketplace`）：A11，過渡做法見決定第 8 項。
- 商品與訂單側的停權連動（下架、取消待付款訂單）仍由 Java 的 consumer 處理，B 階段隨 catalog、ordering。
- #2785 刪店時清 pricebook 的行情追蹤：A4。

## 決定（Will 2026-09-29：11 項全照建議）

每項先列選項與取捨，再寫建議；Will 全部採用建議。沒列在這裡的（D8 刪除清單、缺陷修正、D5 的 intent、樂觀鎖統一、依 ADR 的停權回應）照上方步驟做。第 4 項的 App 刪帳號入口是 UI 改動，當時沒有建議，列為未決：後端在 A3 做，App 入口另外取得同意（觸發條件見步驟 6 的記錄）。

1. **A3 的切法**
   - (a) 一次搬 buyer 與 seller：identity 的過渡機制一次拿掉，但一次改動約 150 支 RPC、130 條路由，review 與驗收的單位太大。
   - (b) 先 buyer 後 seller，共用步驟先做：buyer 小，先驗證「補資料移到 http＋legacy client 讀 Java」的做法；identity 的 BUYER 部分在 A3a 拿掉，`source_id` 柵欄與 `RoleState` 到 A3b。
   - (c) 先 seller：停權、D10 的端到端驗證較早完成，但最大的一塊先做、做法還沒驗證。
   - **建議 (b)。**
2. **還沒搬的模組怎麼拿到 `buyer_id`、`store_id` 與停權狀態**（gateway 約 150 個呼叫點）
   - (a) legacy gRPC 繼續提供 `GetBuyerProfile`、`GetCurrentStoreID`、停權查詢，gateway 保留 Redis 快取：gateway 不用改，但保留 60 秒的過期問題與兩份快取。
   - (b) 單體轉發時帶上已解析的 `X-Buyer-Id`、`X-Store-Id`、停權狀態，gateway 讀 header：延續 A2「gateway 信任單體的身分 header」，刪掉兩個 resolver 與快取；代價是單體每個轉發的請求多一次查詢（同一個 DB，索引讀）。
   - **建議 (b)。**
3. **追蹤賣家（`seller_subscriptions`）歸誰**
   - (a) 留在 buyer（與收藏一致）：粉絲數由 http 組裝，排行（A11 discovery 可依賴 buyer）直接讀；追蹤時確認店家存在與停權由 http 層呼叫 seller。
   - (b) 移到 seller（店家的聚合）：粉絲數是 seller 自己的資料，但「我追蹤的店」要以 `buyer_id` 查 seller，買家刪除的清理要靠 identity 的事件或上層編排。
   - **建議 (a)。**
4. **買家刪除與未結訂單**：buyer 不能依賴 ordering，App Store 5.1.1(v) 要求 App 內能刪帳號，現在沒有任何 client 呼叫買家自助刪除。
   - (a) 刪帳號是 `internal/httpapi` 的一個 use case：未結訂單以 port 檢查（ordering 在 Java 期間由 legacy 實作），在同一個 transaction 內刪賣家、買家、帳號；`pending_deletion` 只在有未結訂單時存在，且不先移除角色（盤點 D7）。自助刪除在 A3 做後端，App 的入口是 UI 改動，另外取得同意。
   - (b) buyer 維護「未結訂單數」的讀取模型（order 事件更新）：buyer 自己判斷，但要在 Java 期間接一個 legacy consumer，B8 再改。
   - (c) 維持現狀（只有後台刪除）：App Store 的要求留到重新上架。
   - **建議 (a)**；App 的刪帳號入口要不要在 A3 一起做，請 Will 決定。
   - 2026-09-30 修訂：編排的位置改成 `accountdeletion` 模組（流程管理者），不放在 `internal/httpapi`；其餘不變（ADR `2026-09-30-account-deletion-module.md`）。
5. **KYC 個資的範圍**（ADR `2026-07-20-seller-kyc-pii-encryption-scope.md`）：它當時的限制「不拆表」「要停機回填」在沒有資料的新 schema 不成立。
   - (a) 維持 ADR 的範圍（加密身分證號與銀行帳號；姓名、生日明文供後台模糊搜尋），修掉 `raw_request` 的明文、補齊 PII 清理。
   - (b) 個資拆到獨立的表、整筆加密，後台以 blind index 只做精確比對：外洩面最小，但後台失去姓名的模糊搜尋。
   - **建議 (a)**：後台以姓名模糊搜尋仍是真實需求；外洩主要來自 `raw_request`，修掉即可。
6. **商家名單與 vendor portal 放哪裡**：商家名單是後台的 BD 名單加上 ai 採購的候選搜尋；vendor portal 是採購向非會員供應商詢價的邀請與 session，只有 ai-service 與 notification 在用。seller-service 刪除時它們必須有新的擁有者。
   - (a) 都進 seller，A9 再搬：這一步最少事，但 vendor portal 會搬兩次。
   - (b) 商家名單進 seller；vendor portal 先建 `agent` 模組只放它（A9 再搬其餘 ai-service）：擁有者一次到位，但 A3 提前建一個只有一部分的模組。
   - (c) 兩者都進 `agent`。
   - **建議 (b)**：商家名單是入駐前的店家資料，vendor portal 是採購的功能。
7. **賣家會員方案**：只有後台能指派，`monthly_order_cap` 沒有任何地方執行，價格都是 0，計費沒實作，唯一效果是 ai 的排行因子。
   - (a) 依 D8 刪除，計費真的要做時重新設計；(b) 照搬。
   - **建議 (a)**（買家的會員保留：ai 的助理額度在用）。
8. **推薦賣家排行在 A11 之前怎麼服務**：seller-service 刪除後它要有地方跑。
   - (a) A3b 建 `discovery` 模組，只放排行（依賴表已經有 discovery → ordering、catalog、buyer、seller、review；Java 的部分由 legacy 實作 port）：A11 只要把其餘部分補進來。
   - (b) 在 `internal/httpapi` 暫時組裝：少建一個模組，但是暫時寫法。
   - **建議 (a)。**
9. **TGOS 地址查詢**（buyer 的地址定位、seller 的 KYC 地址建議與驗證）：現在經舊公司 GCP 的 egress proxy，違反 D9。
   - (a) 功能先拿掉（client 已能處理 9700 的查詢失敗），有自己的 TGOS 帳號時再接；(b) A3 就申請新的帳號與 proxy。
   - **建議 (a)**；(b) 需要 Will 申請外部帳號。
   - 決定 (a) 的後果：shipping 的 Uber 報價需要經緯度；在 TGOS 或其他地理編碼來源接上之前，沒有經緯度的地址會使報價失敗。shipping 搬遷或接上地理編碼時必須處理這個前置條件。單體的 legacy `BuyerService.ValidateAddress` 固定回業務碼 9700（`internal/legacy/buyerserver`）：Java shipping 的 `UberQuoteService.resolveDropoff` 把 code != 0 轉成 `UberAddressUnparseableException`，報價降級為「Uber 不可用（ADDRESS_UNPARSEABLE）」。不能改成不實作：gRPC `UNIMPLEMENTED` 不會被接住，已設定 Uber 的賣家整個報價會失敗。gateway 的 `/app/address/suggestions`、`/app/address/validate` 只剩賣家分支，買家角色回 400。觸發條件：shipping 搬進單體或接上地理編碼時，由那一步決定經緯度的來源與失敗時的降級方式。
10. **買家的 email、phone 副本與賣家 CRM 的手機查詢**：`buyers.email`、`phone` 是建帳時從帳號複製的；identity 的帳號已經沒有手機，賣家 CRM 以手機找顧客現在一律找不到。
    - (a) 刪 email 副本（Clerk 有）；phone 保留為買家自己維護的聯絡電話，CRM 的手機查詢改查 buyer（A6 隨 crm 接上）。
    - (b) 兩者都刪，CRM 改用別的方式找顧客（例如訂單號）。
    - **建議 (a)。**
11. **特性測試**：identity 在 A2 退役了特性測試（Will 2026-09-29），理由是舊的一側啟動成本高、API 重新設計後兩個 driver 對不上。
    - (a) buyer、seller 比照退役，以 integration 測試與 handler 測試涵蓋，盤點的行為寫成回歸測試；(b) 寫一份情境、REST 與 Connect 兩個 driver。
    - **建議 (a)**，理由寫進各模組 `AGENTS.md`。
