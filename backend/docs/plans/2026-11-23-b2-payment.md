# B2 payment：Java payment-service 改寫進單體的 payment 模組，付款改走 Stripe

**Goal：** 買家付款、退款與訂單完成後轉帳給賣家，都經 payment 模組的 provider port（作品集 adapter 是 Stripe 測試模式，fake adapter 給測試與本機），webhook 先寫 inbox、以 event id 去重，外部呼叫都在 transaction 外由 River job 執行；Java `payment-service` 與 `payuni-webhook-service` 的金流部分、PayUni 程式與 gateway 的付款路由全部刪除。驗收見步驟 9。

**上層：** `2026-09-24-go-modular-monolith.md` 階段 B 的 B2；全域約束與「模組完成的定義」在那裡，本檔不重複。

**檔案標記：** 本檔路徑除非註明，`internal/legacy/paymentserver`、`paymentrelay`、`spikes.md` 與 schema 的新表是新增；`internal/platform/stripe`、payment 模組、client 與 Java order 是修改；步驟 6 列的是刪除。

**附件：** `2026-11-23-b2-payment/`：`inventory.md`（Java 服務盤點，快照 `df21e0d8a`，每列附 file:line 與計數指令）、`charge-model-brief.md`（收款模式比較）、`spikes.md`（步驟 1 的 sandbox 實測）。

## 前提（開工時核對過，2026-11-23）

- 會改到或取代的既有部署是否在線：不在線（系統從未上線，根 `AGENTS.md`），不受回滾、相容性窗口與資料搬移約束。
- PayUni 特有的流程直接刪、不改寫：`AtmReactivationService`、`PendingPaymentReconcile*`、`PaymentReturnController`、`PaymentPageService`、`UnknownPaymentFallbackConsumer`、`PayUniRefund*Consumer`、`RescueRefundConsumer`，由 Stripe webhook（inbox、event id 去重）與冪等鍵取代（Will 2026-11-23，主計畫 B2；已確認）。同一理由一併刪：`DuplicatePaymentService`、`PaymentRedirectFormStore`、`GrantResponseRules`、`PayUniAuditLogger`（步驟 1 以 rg 核對：呼叫者還有 `PaymentNotifyHandler`、`PaymentGrpcService` 的導轉表單 RPC、`PaymentApplicationService` 的 PayUni 撥款分類與對帳，全是 PayUni 專屬路徑，結論不變；清單見 `spikes.md`；已確認）。
- 收款模式是 separate charges and transfers（Will 2026-11-23，D1；ADR `2026-11-13-payment-onboarding-provider-port-stripe.md` D20 已修訂）。
- 物流財務與責任判定已刪（commit `5883f499e`、`125db5844`、`28a120564`），Java 只剩 Flyway V9–V16 的 10 張沒人讀寫的表（盤點 §4；已確認）。主計畫 B2 那行「先留在 Java」已過時，本步一併改。
- B2 不做對舊 Java 的 REST 特性測試（Will 2026-11-23，D2）：付款換 provider，對外行為本來就不同，`backend-characterization.yml` 也已在 `cb9ad1cad` 刪除。改以 Java integration 測試對照表加上 Connect 端的新測試，與舊行為的差異寫進模組 `CARRYOVER.md`。
- 呼叫 payment 的 Java 服務（order、aftersales、invoice）在 B2 之後還活著，到 B8（ordering）、B9（aftersales）才改寫：過渡期由單體提供 `internal/legacy/paymentserver`（gRPC）與 relay（RabbitMQ `payment.*`），沿用 `internal/legacy/sellerserver`、`sellerrelay` 的既有做法（預設，可推翻）。
- Stripe 付款事件（`payment_intent.*`、`refund.*`、`transfer.*`）是 v1 snapshot events，與帳戶的 v2 thin events 走不同的 event destination：snapshot destination 收 thin 事件會被拒，每個 destination 各有簽章密鑰（2026-11-23 sandbox 實測，`spikes.md`；已確認）。
- 單體回給 Java 的 `payuni_mer_id` 一律空字串（`internal/legacy/sellerserver/server.go:175`），推論 dev 上舊的付款建立已不能用（未實測）。SCT 下收款進平台帳戶，結帳不再需要賣家的商店代號，Java checkout 的 `SELLER_MERCHANT` 檢查改看可接單（步驟 6）。
- Stripe sandbox 金鑰已在本機個人脈絡檔記的位置；webhook 本機轉發用 `stripe listen`（已確認，A3b 使用過）。

**驗收基線：** 開工 commit `df21e0d8a` 上，dev 的最近一次 CI 結論在步驟 0 記錄；本機不跑 Java 與 testcontainers 的整套（全域指令），以 CI 為準。

## 本階段依賴的不變量

| 不變量 | 依賴它的機制 |
|---|---|
| 搬錢呼叫的結果不明只靠查回收斂：換新冪等鍵之前以強一致查回證明上一次不存在；異常進 `ANOMALY` 佔住唯一性（D10、ADR D68） | 建立付款、轉帳、撤回、退款的 job 與補掃；port 的錯誤分類（`ErrPermanent`、可重試拒絕、不明）與查回方法；`transfers_active_payment` 與退款額度加總涵蓋 `ANOMALY`；後台人工結案 |
| 外部呼叫不在 transaction 內，先寫 intent 再由 River job 呼叫（D5，單體規則 5） | 付款建立（請求內、transaction 提交後呼叫，失敗由 job 以同一把冪等鍵補做，D7 修訂）、退款、轉帳、轉帳撤回、同步的 job；fake provider 的 `Violations` |
| webhook 先寫 `inbox.events`，以 provider event id 去重；收到後重讀物件，不信事件內容 | `internal/platform/inbox`、payment 的付款與退款 handler |
| 一筆付款只對一家店（結帳依 `storeId` 拆單） | Java `order/checkout/CheckoutService.java`、payment 的 `transfer_group`、轉帳金額 |
| 累計退款不超過已收金額 | payment 的退款 use case：同 transaction `SELECT … FOR UPDATE` 付款列，再加總非失敗的退款（跨列加總，單列 CHECK 守不住）；鎖順序（付款列先於退款列）寫進 `backend/docs/modules/payment.md` |
| 轉帳只在訂單完成後建立，且一筆付款最多一筆有效轉帳 | 轉帳 job 的唯一鍵、`transfers` 表的唯一索引 |
| 外部 client 的 log 不含憑證與個資（#2805、D5 outbound 遮罩） | `internal/platform/stripe` 的請求記錄、遮罩測試 |

## 範圍

- 做：付款建立與結果、退款、訂單完成後轉帳與轉帳撤回、後台的付款與退款查詢、付款事實給 invoice；Connect API 與 website、buyer-app、admin 改用生成的 client；過渡期給 Java 的 legacy gRPC 與 relay；刪除 Java payment-service、payuni-webhook-service 的金流部分、gateway 的付款路由與 openapi 端點；#2805 與 D5 outbound 遮罩一起結案；盤點 CSV 過時列補去向。
- 不做：ATM 虛擬帳號與 PayUni 的頁面版退款（Stripe 沒有台灣 ATM，前提）；平台手續費與對帳報表（B10 已退場，見主計畫）；多賣家合併付款（結帳仍依店拆單）。
- 延後：Stripe 對平台持有資金的時間上限（觸發：步驟 1 spike 查到上限，或上線前），若短於「完成期限加售後期限」，D1 改為 destination charges 加手動撥款；代理收付的法規前提（觸發：決定上線）。

## 決定

- **D1 收款模式**（已決 2026-11-23，Will；擋住：步驟 3）
  - 結論：separate charges and transfers；付款帶 `transfer_group`，訂單完成才建立帶 `source_transaction` 的轉帳，完成後的退款先撤回轉帳、賣家餘額不足由平台吸收。ADR：`docs/adr/2026-11-13-payment-onboarding-provider-port-stripe.md` D20 修訂；比較在 `charge-model-brief.md`。
- **D2 特性測試**（已決 2026-11-23，Will；擋住：步驟 7）
  - 結論：B2 不做對舊 Java 的 REST 特性測試，改用 Java integration 測試對照表加 Connect 端新測試，差異寫進 `CARRYOVER.md`。
- **D3 買家付款介面**（已決 2026-11-23，Will；擋住：步驟 3、5；需要的事實：步驟 1）
  - A：web 用 Payment Element、App 用 `flutter_stripe` 的 PaymentSheet——原生體驗，Apple Pay／Google Pay 隨錢包自動出現；要新增兩個依賴（需同意），App 要處理 3DS。業界大型市集 App 多用原生付款元件（推論）。（建議）
  - B：三端都用 Stripe Checkout 託管頁（App 開外部瀏覽器）——不新增依賴、程式最少；App 跳出到瀏覽器，回 App 靠回跳頁與重讀，與收款開通同一套做法。
  - 推翻建議的事實：`flutter_stripe` 的發佈版本或授權不符依賴規則，或 spike 發現 PaymentSheet 對 recipient／SCT 有限制。
  - 兩案都刪 PayUni 的 Apple Pay 商家驗證（`ValidateApplePayMerchant`）：A 由 Stripe 的錢包處理，B 由託管頁處理。
  - 結論（ADR D64）：A：web 用 Payment Element、App 用 `flutter_stripe` 的 PaymentSheet。新增的依賴（`flutter_stripe` 候選 14.2.0，MIT；web 的 Stripe.js 套件）在步驟 5 開工時列版本另取同意。
- **D4 退款併發規則**（已決 2026-11-23，Will；擋住：步驟 3）
  - A：同一筆付款可以同時有多筆進行中的退款，累計上限在 transaction 內鎖付款列加總（含進行中的），每筆退款有呼叫端給的冪等鍵——Stripe 支援多筆部分退款，上限才是要守的不變量。（建議）
  - B：沿用 Java 的「已有進行中的退款就拒絕」（`REFUND_ALREADY_PROCESSING`）——較簡單，但售後同時有兩個案件時第二個會失敗、要重試；這條規則是為了 PayUni 同步定案而有。
  - 結論：A：可以並行，只守累計上限，每筆退款帶呼叫端的冪等鍵。
- **D5 付款成功但訂單已不可付**（已決 2026-11-23，Will；擋住：步驟 3）
  - A：收到成功後若訂單已取消或過期，排自動全額退款 job，後台可見——取代 Java 的 CONFLICT、duplicate、rescue 三套。（建議）
  - B：記異常進後台待辦由人處理——錢會卡在平台。
  - 選 A 時，自動退款完成照舊通知買家（取代 rescue 的通知，見步驟 4）；不通知的話買家看到扣款卻不知道已退。
  - 結論：A：自動全額退款 job，後台可見，買家收到通知。
  - 修訂（2026-11-23，Will；開工時 design-review）：判斷與發起由訂單擁有者負責（saga 的補償由擁有狀態的一方發起），過渡期是 Java order 的 `AutoRefundWorker` 經 `CreateRefund`，B8 移進 ordering；payment 只提供退款並以原因標記自動退款，不讀訂單狀態。
- **D6 轉帳的觸發與範圍**（已決 2026-11-23，Will；擋住：步驟 3、4）
  - A：B2 做轉帳機制：Java order 的 `GrantPaymentWorker` 在訂單完成時經 legacy gRPC 呼叫，payment 寫轉帳列並排 job；B8 改寫 ordering 時改成 in-process 呼叫；B10 只剩手續費與對帳。（建議）
  - B：轉帳全留到 B10，B2 只做付款與退款——B2 完成到 B10 之間賣家永遠收不到錢，`GrantPayment` 要先做空實作。
  - 結論：A：B2 做轉帳機制，B8 改 in-process，B10 只剩手續費與對帳。

- **D7 `CreatePayment` 何時回 client_secret**（已決 2026-11-23，Will；擋住：步驟 3、5；盤點 §1 #1、§5 #1）
  - A：請求內寫付款列與 job 後同步等 job 建好 PaymentIntent（有上限的等待），逾時回 pending 讓 client 以 `GetPayment` 重讀——買家一次往返，仍守「外部呼叫在 transaction 外」。（建議）
  - B：一律先回 pending，client 輪詢 `GetPayment` 取 client_secret——最單純，但每次付款多一段輪詢與等待畫面。
  - 結論（ADR D65）：A：有上限的同步等待，逾時回 pending 由 client 以 `GetPayment` 重讀。
  - 修訂（2026-11-23，Will；開工時 design-review：「等 job 完成」是 repo 沒有的新機制）：transaction 寫付款列與補做 job，提交後在請求內帶冪等鍵直接建立 PaymentIntent 回 client_secret（Stripe accept-a-payment 的標準做法，沿用 `CreateOnboardingSession` 的先例）；失敗或逾時回 pending，job 以同一把冪等鍵補做，client 以 `GetPayment` 重讀。
- **D8 付款嘗試歷程與賣家版**（已決 2026-11-23，Will；擋住：步驟 3、5；盤點 §1 #3、§2a #3–#4）
  - A：一張訂單一個 PaymentIntent，重試在同一張上；只留買家 `GetPayment` 與後台查詢，賣家看訂單的付款狀態即可，刪 seller-app 的歷程呼叫——Stripe 本身保留嘗試紀錄。（建議）
  - B：保留買家歷程與遮蔽個資的賣家版（現有 seller-app 呼叫）。
  - 結論（ADR D66）：A：一張訂單一個 PaymentIntent；只留買家 `GetPayment` 與後台查詢，刪 seller-app 的歷程呼叫。
  - 補充（2026-11-23，Will；3a 第 2 輪審查）：Stripe 取消後的 PaymentIntent 是終局；訂單仍可付時，同一個付款列換新的 PaymentIntent 重付，每次嘗試的 PaymentIntent ID 留在歷程表，舊 PaymentIntent 晚到的成功仍對得到付款列（不靜默丟棄）。一張訂單同時只有一個有效 PaymentIntent。
- 盤點中其餘「預設，可推翻」（`product_name` 作 Stripe description、`PaymentMethod` 不另列錢包、legacy paymentserver 不擋非內部呼叫者）屬實作細節，照預設。

- **D9 付款與轉帳的幣別**（已決 2026-11-23，Will；擋住：步驟 3、5；需要的事實：步驟 1，已有）
  - 事實：測試平台是 US，款項以 USD 入帳；以 TWD 收款時，轉帳幣別必須是入帳幣別 USD，TWD 轉帳被拒（`spikes.md` #10，實測）。現有契約與訂單金額沒有幣別欄位（`rg -i currency api/` 無結果），金額是隱含的新台幣整數。
  - A：Stripe adapter 以 USD 收款，把訂單的整數金額當 USD 的最小單位（cent）照搬，不做匯率——port 與資料模型不帶幣別，demo 金額數字與畫面不一致（NT$100 變 US$1.00），不影響機制示範。
  - B：以 TWD 收款，轉帳金額由付款的 balance transaction（USD 淨額）依比例換算——畫面金額正確，但轉帳金額、退款撤回都要處理匯率與捨入，payment 表要存入帳幣別與金額；這些複雜度在台灣上線、換台灣金流商後不存在（ADR D20 已寫 Stripe 只示範機制）。
  - C：契約與訂單全面加幣別欄位，demo 用 USD 計價——最接近多幣別市集的業界做法，但改到訂單、商品、client 的契約，超出 B2。
  - 建議 A：ADR 已定 Stripe adapter 只示範機制，台灣上線會換金流商；port 只收整數金額，幣別由 adapter 的設定決定，換金流商時不改 port。
  - 結論（ADR D67）：A：Stripe adapter 以 USD 收款，訂單整數金額照搬成 cent，port 與資料模型不帶幣別。
- **D10 搬錢呼叫的結果不明**（已決 2026-11-23，Will；擋住：步驟 3a 修正、3b、3c、3d；來源：3b 的 `/code-review` 與 diff 審查，轉帳結果不明 12 小時後進 FAILED 會讓出唯一索引、可能重複撥款）
  - A：三分結果（成功、確定失敗＝可重試／終局、不明），換新鍵前以強一致查回證明上一次不存在，異常進 `ANOMALY` 佔位告警、後台人工結案；四種呼叫統一。（建議）
  - B：不明一律進待人工核對——每次網路抖動都要人處理。C：維持期限後失敗——違反「一筆付款最多一筆有效轉帳」。
  - 結論（ADR D68）：A。查回方法的事實：Stripe List Transfers 可依 `transfer_group` 篩選（文件，2026-11-23 以 Context7 查 docs.stripe.com/api/transfers/list；sandbox 未實測，3d 以樣本驗）。
