# 遷移計畫 A7：social 搬進單體

**Goal：** social-service 搬進 `internal/modules/social`，完成後的系統如下（可驗證的終態見步驟 A7-5）：

- 檢舉與處置拆成新的 `internal/modules/moderation`；處分紀錄歸執行效果的模組（買家的社群處分在 social、帳號停用在 identity、店家措施在 seller）；帳號停權與解除只經新的編排模組 `accountsuspension`，被停權的帳號是受限登入而不是停用。
- 封鎖放在發起者的模組：個人封鎖在 buyer，店家封鎖在 seller。
- 平台下架店家內容，改成 seller 的措施「內容下架」。
- 後台待辦加入 moderation 的來源（`reviewqueue` 的 `pub_*` 組合）。
- 排程發布由 social 擁有，代行排程的授權與稽核由 delegation 在同一個 transaction 內處理。
- 代行貼文改走單體的 Connect；四個 client 改用生成的 Connect client。

同時刪除：social-service、gateway 全部社群路由（40 條，含 `/app/blocks*` 3 條與留言 SSE）、代行貼文 6 條路由與 `admin_delegated_post.go`、`SocialClient`、`openapi.yaml` 的 40 個社群 operation、四端手寫的社群呼叫、`backend/api/proto/social`、`pkg/proto/social`、Java 那份 `social.proto`。

聊天與評價的封鎖、檢舉入口不在 A7 改：從 A7-4e 刪掉 `/app/blocks*` 起到 A6 的 client 步驟完成，這些按鈕在本機會失敗（Q1，Will 2026-10-18 接受）。A6 排在 A7 之後下一個階段。

**上層：** 遷移計畫 `2026-09-24-go-modular-monolith.md` 的 A7 段與「模組完成的定義」；本檔不重複那張清單，只寫 A7 特有的步驟與驗收。進度寫在本檔，主計畫的 A7 段只指向這裡。

**做：**

- 封鎖：buyer 的個人封鎖、seller 的店家封鎖（A7-D2）。

- relay：`socialrelay` 給 notification-service（S4）。
- 四端改用 Connect：C1–C10 的文案與畫面改動；店主讀留言，含不公開的貼文、店家範圍的留言、未回覆篩選的 API；website 的封鎖名單頁（A7-D12）；隱私權政策加一句匿名瀏覽計數的說明（Q4）。

- 舊資料不搬（從未上線）。
- `/public/hashtags`、`/public/hashtags/popular`、`/app/hashtags` 不動：它們是 product 的商品 hashtag，跟 catalog 搬。
- 不寫往舊 im、review 的橋：不做 legacy SocialService、「是否封鎖」legacy RPC、moderation 對 im／review 的 legacy port（S3，Q1）。
- 一般貼文的留言不即時推，打開或下拉時才拉（Q3）；gateway 的留言 SSE 刪除，不做 server streaming。
- 店家封鎖不含禁止下單（brief D2）。

## 預設（可推翻；沒有真正的替代方案，或由 repo 規則決定）

- **ID**
  - social 與 moderation 擁有的實體用 UUIDv7；讚表用複合自然鍵。
  - 貼文讚只會是買家，不存 kind 欄（`domain-inventory.md` M1、M2）。
- **檢舉對象**：`target_type` CHECK 加型別正確的對象欄（social 內容是 UUID、買家是 bigint 的 `buyer_id`），CHECK 限定恰好填一欄；不用 `target_id TEXT` 混裝（S3 後不再有 im、review 的 bigint ID）。
- **計數**（業界基準與定案在 `2026-10-18-a7-social/counts-brief.md` v4，Will 2026-10-23）
  - 讚、留言（含回覆）、回覆、瀏覽、分享都存在獨立的 stats 表；「是否計入」只有一支 SQL 定義；trigger 在同一個 transaction 加減；外部事實改變時排重算；每日對帳覆寫並記錄漂移；手動重算子命令。所有觀看者看到同一個數字。熱點分片的觸發寫進取代 `2026-09-18-mq-social-counter-async-delta` 的 ADR。
  - hashtag 的數量不存，讀取時依公開可讀述詞計算。
- **封鎖讀取**：不建投影。個人封鎖要篩選列表，social 的查詢內 join `buyer.pub_blocked_buyers()`、`buyer.pub_blocked_stores()`，強一致（backend 單體規則 2；`domain-inventory.md` Q7；`d3-read-model-brief.md` §4.2）。店家封鎖只擋寫入、不篩選讀取，寫入檢查與列表的 `viewer_can_*` 都是依 ID 的查詢，照規則 2 呼叫 seller 的 API，不發布 `seller.pub_blocks`（A7-1b 開工的 design-review）。
- **曝光**：不建投影，不訂閱 `StoreExposureChanged`。social 的查詢內 `EXISTS (SELECT 1 FROM seller.pub_exposable_stores($now) …)`，時間用請求的 clock。
- **分頁**：用 AIP-158 keyset，不回總數；要顯示留言數就用貼文上的 `comment_count`。
- **etag**
  - 貼文用 `version` 推導 `etag`。
  - 留言與討論區不加版本：只有作者自己能編輯，last-write-wins 不會蓋掉別人的內容。
- **hashtag**
  - 保留由 client 明確送標籤。
  - 字元集維持 `a-z0-9` 加漢字，足夠 zh-TW 與 en 使用。
  - 「包含」搜尋要不要用 pg_trgm，由 A7-1a 的 spike 決定；趨勢以發布時間分窗。
- **能力宣告**：照 ADR `2026-09-29-seller-suspension-and-business-identity-in-monolith` 的文末修訂。
  - use case 依資源推導出店家身分，再呼叫 `seller.ActingStore`／`CapabilitiesOf`。
  - 無法靜態宣告的方法，在宣告表寫「依資源判斷」的豁免並附理由（`alignment-facts.md` §7）；該 ADR 隨 A7-2 加修訂段。
- **反正規化快照**：留言與討論區不存作者名稱、頭像快照，讀取時再補；買家刪除後，列上不留 PII。兩支回填指令刪除（`domain-inventory.md` M19、M25）。
- **媒體**：換圖時在 transaction 內 finalize，舊引用由 job 釋放；軟刪的貼文在店家退場時釋放引用（`domain-inventory.md` M15）。
- **隱藏與處分理由**
  - social 的隱藏與警告 API 帶理由（`PolicyCategory` 加說明），由 social 存，作者讀得到。
  - 店家內容被下架的理由取自措施（seller 的 `pub_content_takedowns` 與措施 API）。
  - social 不讀 moderation（依賴方向）；moderation 的案件以不透明的參照記在處分紀錄上。
- **後台貼文列表的檢舉數**（`domain-inventory.md` Q8）：由 httpapi 組裝，向 moderation 批次查；social 不存檢舉。
- **髒字詞典**：放 `internal/platform/textfilter`，social 與 moderation 共用（`domain-inventory.md` Q12）；im、review 到 A6 前用 `pkg/moderation` 那份。

- [x] **A7-1b 封鎖**（被擋於：A7-1a）

### A7-D7 的十項（Will 2026-10-18）

1. **對象**：新表 `seller.measure_contents(measure_id, content_kind, content_id)`，一個措施可以對應多則內容；`MeasureCreated`、`MeasureRevoked` 事件帶上對象。
2. **依據**：VIOLATION 加認定，認定的類別取 `PolicyCategory` 的社群類別（Q5）；不新增依據種類。
3. **建立者**：仍是 admin。moderation 處理檢舉、admin 從貼文管理頁下架，都是 admin 的動作；`CreateInTx` 由呼叫方傳入處理的管理員 ID。不新增「系統」這種建立者。
4. **期間與影響**：沒有結束時間；不影響店家的能力與曝光，也就是不算 `Restrictive`。
5. **解除**：只走申覆。接受申覆就撤銷措施，social 的同 transaction 訂閱者刪掉該措施的複本列，內容立即還原（D-sync，Will 2026-10-23 取代原本「讀取時 join `seller.pub_content_takedowns`」的寫法）。不開放補正後解除：店家可以自己刪掉內容，再發一則合規的新貼文。
6. **admin 貼文管理頁**：店家貼文的「下架」改成建立措施的對話框；「恢復」改成撤銷措施，用既有的手動撤銷原因。
7. **認定的來源**：多對多，和 seller 通報的 `finding_reports` 同結構：`seller.finding_moderation_reports(violation_id, report_id UUID)`，`report_id` 是不透明的外部參照，不加 FK（不合成一張帶 `source_kind` 的表，那樣會失去 `finding_reports` 對 `seller.reports` 的 FK）。
8. **升級**：社群類認定照樣算進「90 天第 3 次 MEDIUM 升 HIGH」，只有一條累計規則；嚴重度由 admin 建立時選。
9. **案件結案後的更正**（10e R12）：案件結案是終態，不重開也不改判；結案後對同一對象的新檢舉開新案件（案件粒度見 A7-D14）。措施要更正就在 seller 撤銷，用手動撤銷原因（例如 `ADMIN_CORRECTION`）；`SOURCE_REVOKED` 只由關聯帳號終止的連帶撤銷寫入，`RevokeMeasure` 不接受它（`seller.proto`、`governance.proto` 的 `RevokeMeasure` 說明）。案件頁要顯示措施的現況時，讀取時呼叫 seller 的 API，不訂閱 `MeasureRevoked`。案件改判見「延後」。
10. **驗證與 transaction**：由 moderation 經 social 驗證內容存在、而且屬於該店，再呼叫 seller。整個流程在 moderation 開的同一個 transaction 內（`InTx` 可重入，`CreateInTx` 不另開 transaction）。冪等靠案件的狀態轉移：案件 open → closed 只發生一次（`UPDATE … WHERE closed_at IS NULL AND version = $n`，0 列即衝突並回滾），同一案的處置只執行一次（A7-D14）。
