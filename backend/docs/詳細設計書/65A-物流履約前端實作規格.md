### 0.2 既有畫面 vs 新建畫面（沿用優先）

> 🔴 **本節只給判準；「既有畫面實際要改哪些檔」的逐檔清單在 §12。**
> 新建畫面的規格在 §0.1 的總表（狀態欄 `新建`），既有畫面的 migration 在 §12。

🔴 **沿用優先不是節省成本的口號，它是避免第三份實作的紀律。**
現況：**同一組出貨動作在 website 與賣家 App 各有一份**
（`lib/seller/shipment.ts` 的檔頭自承 mirror 自 Dart），
再加第三份就是三處要一起改，而**漏一處不會有東西轉紅**。

| 判準 | 動作 |
|---|---|
| 既有元件能承接（只是多幾個選項／多幾個狀態值） | **擴充既有**，禁止另建 |
| 既有元件的資料模型不同（例如批次是二維，既有是一維） | 新建，但**共用 design token 與狀態呈現規約**（§1） |
| 兩個 repo 都需要同一個東西 | 🔴 先問「**能不能只做在一邊**」——例如複雜對帳只做 Web，App 給連結 |

### 1.1 設計 token

直接採用需求書 image23 給的值，**不另立一套**。四個 repo 各自的落點：

| repo | token 落點 | 動作 |
|---|---|---|
| website | Tailwind theme | 沿用 |
| ADM | Tailwind theme | 沿用 |
| buyer／seller | Flutter `ThemeData` | 沿用 |

⚠️ **Tailwind v4 會掃註解與測試檔**：寫在註解或測試裡的 class 字面值**會進 production CSS**。

### 1.2 元件規範

**主要 CTA 手機滿寬單欄**。

### 1.3 狀態呈現規約

🔴 **狀態不能只用顏色**（無障礙）：每一個狀態徽章 ＝ **顏色 ＋ 文字 ＋（可選）圖示**。

🔴 **最重要的一條：兩套碼、四種做法並存，必須收斂。**

現況：

| 碼 | 現況做法 | 問題 |
|---|---|---|
| 我方 `ShippingStatus`（91／210／920／990…） | 走 CodeMeta 生成檔查表 | ✅ 正確 |
| **PayUni 原始 `shipStatus`（0／1／2／…／99）** | 🔴 **website 與賣家 App 各手抄一份硬編碼 map**（`lib/seller/shipment.ts` 的 `SHIP_STATUS_TEXT`；`payuni_logistics_service.dart` 內同型的表） | **無任何 gate**；兩份會各自演化 |
| 訂單狀態文案 | 買家／賣家 App **各有一組手寫中文 switch**（`order_status_presentation.dart`） | 同上 |
| 時間軸步驟 | 🔴 **兩條硬編時間軸都在「訂單狀態軸」，不是配送軸**：website 5 步（`orderStatusTimelineModel.ts:ORDER_STATUS_TIMELINE_STEPS`，key 是 `pending_payment`／`paid`… 等英文字面，不是 `OrderStatus` 的 CodeMeta value `0`／`10`…）；買家 App 4 步（`step_indicator.dart:logisticsStepFromStatus`，key 是 `OrderStatus` value） | 新增狀態值時不會有東西提醒。⚠️ **改它們之前先分清楚軸**——把配送的 normalized 值餵進去會把兩個值域混成一個（§2.3 第 1 點） |

⇒ **規約（四條，缺一即回到現況）**：

1. **我方碼值一律走 CodeMeta 生成檔**，禁止在畫面層寫 switch／map 對映中文。
2. 🔴 **PayUni 原始碼不得再手抄**。它應該由**後端翻成 normalized 值**之後才給前端
   （65 §7.1.2 的 31 值就是為此存在）；前端若仍需顯示原始碼，
   走**單一共用模組**並在該模組檔頭寫明「本表的 SSOT 在後端，任何新增先改後端」。
   🔴 **那兩份手抄表的確切位置、19 值逐值相同的證據、以及刪除前的過渡對拍 gate 在 §12.2。**
3. **配送時間軸的步驟由 normalized 配送值推導**，不是由畫面各自硬編。
   🔴 **先分清楚是哪一條軸**：現況那兩條硬編時間軸（website 5 步、買家 App 4 步）都在**訂單狀態軸**不是配送軸
   ⇒ **本條不適用於它們**（§2.3 明令不要改 `orderStatusTimelineModel.ts`）。
   本條要求的是「新增的**配送**進度時間軸」。
   買家沒有 `code_meta_display` 這一層（賣家有）⇒ **要補上**，否則買家端每個畫面各自 switch。
4. **未知值一律 fail-closed 地顯示**：顯示「處理中」＋原碼，**不猜測、不隱藏**
   （隱藏會讓使用者看到一個空白的時間軸）。

### 1.4 空狀態／錯誤／降級的統一處理

四態一律走同一組元件：**載入中／空／錯誤／降級**。

| 態 | 規約 |
|---|---|
| 載入中 | skeleton，**不得用 spinner 蓋住已載入的部分** |
| 空 | 一句說明 ＋ 一個可行動作（不是只有一張圖） |
| 錯誤 | 顯示**業務碼對應的文案**（§1.8），不顯示 raw payload |
| **降級** | 🔴 後端 fail-open 時（例如 POD 抓不到），畫面要說「暫時取得不到」而不是**假裝沒有這個東西** |

### 1.5 無障礙

- **320px 至桌面不得水平溢位**（表格與時間軸要各自 `overflow-x: auto`，不是讓 body 橫捲）
- 主要 CTA 手機滿寬單欄
- 狀態不只用顏色（§1.3）
- 觸控目標 ≥ 48dp

### 1.6 金額與時間的顯示規約

| 項目 | 規約 |
|---|---|
| **金額** | 後端傳字串整數「元」⇒ 前端**不得做浮點運算**；顯示時加千分位 |
| **時間** | 🔴 **存傳 UTC、顯示層轉 `Asia/Taipei`**。後端一律 ISO 8601 帶 `Z` |
| **倒數** | 以**後端給的絕對時間**倒數，不是前端算的相對秒數（分頁休眠會漂） |

⚠️ **「當地日」與「UTC 日」不是同一天**：定期配送的到貨日是**當地日**（67），
顯示時不得直接 `toLocaleDateString()` 一個 UTC 午夜的值——那會差一天。

### 1.7 `allowedActions[]` 是唯一出口

🔴 **前端不得自行判斷可做什麼。**

後端每個資源回應都帶 `allowedActions[]`；前端只渲染這個陣列裡的動作。

| 反例（禁止） | 為什麼 |
|---|---|
| `if (status === 'DELIVERED') show(確認收貨)` | 狀態值域會長（24 → 31），前端會漏 |
| `if (labelUrl) show(列印標籤)` | 🔴 **現況實例**：賣家端的黑貓分支就是以 `labelUrl` 有無判斷而不是狀態 ⇒ 語意漂移 |
| `if (isSeller && order.storeId === me) show(出貨)` | 授權判斷在後端；前端重算必然與後端不一致 |

⚠️ **`allowedActions[]` 為空時要顯示原因**，不是顯示一個沒有任何按鈕的畫面（§1.8）。

🔴 **`actor` 欄不需要前端做任何事。**
每一條動作都帶 `actor`（`AccountType` 值：`"1"` 買家／`"2"` 賣家／`"4"` 管理員），
而它在回應裡**恆等於呼叫者**——因為後端已依身分過濾過。
⇒ 前端**不得**拿它做 `if (actor === '2') show(...)` 這類過濾，那會退回上表第三列的反例
（授權判斷在後端，前端重算必然不一致）。它存在的意義是讓「這條動作屬於誰」
在契約上可讀、可測，而不是留給實作各自解讀。

⚠️ 同一個動作在買家端與賣家端可能有**不同的 `href`**（例：`track` 買家指向
`/app/orders/{no}/logistics`、賣家指向 `/app/shipments/{no}/tracking`）。
前端一律跟隨回應裡的 `href`，**不要快取一份 action → URL 的對照表**。

### 1.8 fail-closed 的使用者文案（D-13）

🔴 **選項不可用時要說明，不得憑空消失。**

| 情境 | 錯誤做法 | 正確做法 |
|---|---|---|
| Uber 未啟用（U-5） | 選項列表少一個，使用者不知道 | 顯示但 disabled ＋「此配送方式尚未開放」 |
| 賣家未完成建店 | 同上 | disabled ＋「賣家尚未開通此配送方式」 |

**業務碼 → 文案的對照表**在 §7.1 的對照表內逐端點列出。

### 1.9 provider 特有 UI 與通用 UI 的分離

> 🔴 **§1.7 規定「動作由 `allowedActions[]` 決定」、§1.10 規定「禁止二元 fallback」，
> 而 provider 特有的畫面要放在哪裡由本節定義。** 沒有這個落點，新 provider 的 UI
> 只能繼續長在通用元件的 `if` 裡。

**現況：四個 repo 沒有 provider 抽象層，provider 分流只以畫面內 `if` 存在。**

```bash
# 四個 repo 都跑，命中皆為 0
/usr/bin/grep -rniE "providerRegistry|ProviderStrategy|providerSlot|CarrierAdapter|shippingProviderMap" \
  <repo> --include='*.ts' --include='*.tsx' --exclude-dir=node_modules --exclude-dir=.next
# 對照組（證明 grep 打得到東西）：website 的 "registry" 字樣 ＝ 84 命中
```

⇒ **provider 分流今天只有一種形式：在畫面裡寫 `if`。**

#### 1.9.1 三層分類（每個 UI 元素都要歸到其中一層）

| 層 | 內容 | 允許知道 provider 嗎 |
|---|---|---|
| **A 通用元件** | 配送狀態時間軸、費用摘要、`allowedActions[]` 驅動的 CTA 列、空／錯誤／降級四態、狀態徽章 | 🔴 **不允許**。只吃 normalized 值與 `allowedActions[]` |
| **B provider slot** | 塞進通用容器裡的一塊 provider 專屬區域 | ✅ 只有 slot 內部知道 |
| **C provider 專屬頁** | 整頁只服務一個 provider（例如 Uber 啟用三階段 `SW-02`） | ✅ 整頁都知道 |

**B 層今天已經有哪些內容**（要把它們從 `if` 裡搬進 slot）：

| provider | slot 內容 | 現況落點 |
|---|---|---|
| `3002` 7-11 C2C | 超商門市選擇器、ibon 寄件說明、驗證碼（`validationNo`） | buyer `store_pickup_form_screen.dart`；seller `cvs_shipping_section.dart` |
| `3001` 黑貓 | 預約取件對話框、託運單 PDF 下載、四天效期提示 | seller `tcat_reservation_dialog.dart`／`call_tcat_dialog.dart`；web `ShipmentDialogs.tsx` |
| `3003` Uber | 外送員資訊與即時地圖、取件點 | **新建**（U-5 前 disabled，§1.8） |
| `3004` 7-11 B2C | 批次、標籤列印、交倉 | **新建**（68 號） |
| `3005` 商家自送 | 承運商名稱與單號輸入、服務範圍 | **新建**（69 號） |

#### 1.9.2 分離的機制：通用容器 ＋ provider slot registry

🔴 **由後端的 capability／`allowedActions[]` 決定渲染哪個 slot，前端不做 provider 判斷。**

```
通用容器（A 層，不知道 provider 是誰）
  └─ 讀後端給的 provider 識別 → 查 registry → 拿到一個元件 → 渲染
        registry: Record<ShippingMethodValue, ProviderSlot>
```

三條硬性要求：

1. **registry 是唯一的 provider→元件對映處**，一個 repo 一份。
   新增 provider ＝ **在 registry 加一列 ＋ 寫一個 slot 元件**，不改任何 A 層檔案。
2. 🔴 **A 層元件內禁止出現 provider 字面值**（`3001`～`3005`／`TAQBIN`／`isTaqbin`／
   `LGS_TYPE.HOME`／`黑貓`／`7-11`／`超商`）。要 provider 專屬行為就開一個 slot。
3. **registry 查不到 ⇒ 走「未知配送方式」的 slot**（fail-closed，§1.8），
   不得 fallback 到任何既有 provider（§1.10）。

⚠️ **不是每個 provider 都要有 slot**：查不到就渲染通用區塊即可——
「沒有 slot」與「fallback 到別人的 slot」是兩件事，後者才是禁令要擋的。

#### 1.9.3 可機械檢查的斷言

🔴 **一條 grep 就能跑，放進各 repo 既有的 unit test。**

```bash
# A 層目錄（通用元件）內，provider 字面值必須零命中
/usr/bin/grep -rnE "isTaqbin|LGS_TYPE\.|ShippingMethod\.taqbin|ShippingMethod\.sevenEleven|\b300[1-5]\b|黑貓|7-11" \
  <通用元件目錄> && exit 1 || exit 0
```

⚠️ **這道斷言的觀測窗是「目錄」**（§06 no-small-tails §3.10 的四問）：
- 有人把 provider 判斷抽成 helper 放到 A 層目錄外再 import 回來 ⇒ **它看不到**
  ⇒ 因此第 2 條的措辭是「**A 層元件內禁止 provider 專屬行為**」，不只是禁字面值；
  review 時要問「這個 helper 是不是在替 A 層做 provider 判斷」。
- **對「目錄不存在」必須 FAIL 不是 SKIP**（目錄被改名的那天它會靜默轉綠）。

⚠️ **本斷言擋不住的**：registry 本身當然含 provider 字面值（那是它的職責）；
slot 元件內部也含。斷言只守 A 層——**這是它誠實的邊界，寫在這裡免得有人把它當成牆。**

### 1.10 🔴 禁止 `provider → 預設值` 的二元 fallback

> **規則來源（本書複述，不在此改動）**：65 §7.7.4.5「禁止任何 `provider → 預設值` 的前端 fallback」、
> 66 附錄 D、69 附錄 D。

**禁止的形式**（二元或三元，都是同一個病）：

```ts
const lgsType = isTaqbin ? LGS_TYPE.HOME : LGS_TYPE.C2C;   // ❌ 3003/3004/3005 全被當成 C2C
if (isTaqbin) { ... } else { ...超商... }                   // ❌ else 吞掉所有未列舉的 provider
```

**要求的形式**：

```ts
switch (method) {
  case ShippingMethod.TAQBIN:                  return ...;
  case ShippingMethod.SEVEN_ELEVEN_STORE_PICKUP: return ...;
  case ShippingMethod.UBER_INSTANT:            return ...;
  // 3004 / 3005 同理逐一列出
  default:                                     return unknownProviderView(method);
}
```

三條硬性要求：

1. **一律 `switch`（Dart 用 `switch` 運算式），且每個 provider 一個 `case`。**
2. 🔴 **`default` 走「未知狀態」顯示**：顯示「處理中」＋原碼（§1.3 第 4 條），
   **不猜測、不隱藏、不 fallback 到任何既有 provider**。
3. **`if/else` 只在「這一格與 provider 無關」時才可用**——
   判準：把一個沒見過的 method 代進去，答案錯了嗎？錯了 ⇒ 它是 provider 分流，必須 `switch`。

⚠️ **為什麼二元 fallback 特別危險**：它**沒有任何訊號**。
`isTaqbin ? HOME : C2C` 對 `3003` 回的是一個**合法值**，型別對、不拋例外、測試全綠，
畫面只是把 Uber 訂單畫成 7-11 的進度條 ⇒ **靜默錯誤，只有使用者看得到**。

⚠️ **同一個 repo 內已有兩種寫法並存**（65 §7.7.4.5 逐字記載：
`SellerOrdersPage.tsx` 已三路、`OrderDetailClient.tsx` 仍二元）
——**那個不一致本身就是修改範圍的指標**（D-13#4）。

🔴 **既有命中點逐檔清單在 §12**（migration 對象）。

### 1.11 即時通道前端契約（SSE ／ Push）

> **四端共用**：買家 Web／買家 App／賣家 Web／賣家 App 的連線、重連、去重、降級規則**完全一樣**，
> 所以寫在這裡一次。§2／§3／§4／§5 各節只寫「這一端消費哪些事件」，**不重複本節的機制**。

**後端的傳播鏈**（時序圖在 66，本規格不重畫）：

```
provider webhook ／ polling → normalize → state machine → DB commit
  → Domain Event ／ Outbox → SSE ／ Push ／ ADM
```

🔴 **DB／Domain state 是唯一真實來源，不是 SSE 事件、也不是 Push payload。**

| 通道 | 前端的用法 |
|---|---|
| **SSE** | 前景即時 UI（畫面開著的時候） |
| **Push** | 背景／重要里程碑 |
| ADM | 營運異常，不是使用者端通道 |

**六條硬性規約**：

1. 🔴 **收到 Push 後必須重新 `GET` 該資源的 Domain 狀態**，再依回應重繪。
   **不得**把 Push payload 當狀態真相——它是「去看一下」的訊號，不是狀態本身。
2. 🔴 **後端不會推 provider 原生 payload**，前端也不得解析任何 provider 原生欄位
   （§1.9 的 A 層規約在即時通道上同樣成立）。
3. **SSE 連線必備四件**：`Last-Event-ID`（resume cursor）／自動重連（指數退避）／
   **去重**／重連後補齊。**去重維度 ＝ `order` ／ `event` ／ `leg` ／ `state-version`**
   ——🔴 **四個維度缺一都會出錯**：同一筆訂單的去程與返程是兩個 `leg`，
   只用 `order + event` 去重會把返程事件當成重複而丟掉。
4. **亂序與落後一律以 `state-version` 判**：收到的版本 ≤ 目前畫面版本 ⇒ **丟棄**，不回退畫面。
5. 🔴 **Push 投遞失敗不影響 Domain 狀態**，前端也不得為此補償——下一次 SSE 重連或 `GET` 自然收斂。
6. 🔴 **`allowedActions[]` 也要跟著即時更新**（§1.7）。賣家畫面開著時後端已收回某個動作，
   而畫面還留著那顆按鈕 ⇒ 賣家按下去吃業務碼錯誤。
   ⚠️ **這是即時通道對賣家端最重要的一件事**，不是「順便刷新一下」。

**連線失敗的降級（§1.4 第四態）**：

| 情形 | 畫面要顯示什麼 |
|---|---|
| SSE 斷線、重連中 | 既有內容**保留**，加一行「即時更新已中斷，重新連線中」。🔴 **不得清空畫面**、不得轉 spinner |
| 重連連續失敗 | 退回**定期 `GET`**（前景輪詢），並顯示「目前為定時更新」。🔴 **輪詢頻率由後端給，前端不自訂** |
| 完全取不到 | 顯示最後一次成功取得的資料 ＋ 取得時間，**不得顯示成「沒有配送資訊」** |

**各端消費哪些事件（本表只是索引，文案在各節）**：

| 端 | 節 | 消費 |
|---|---|---|
| 買家 Web | §2.3 | 已約定取件時間變更／重新媒合中／取件完成／配送中／送達／配送失敗終態 |
| 買家 App | §3.2 ＋ §3.4 | 同上；🔴 **另要處理背景 ↔ 前景切換的重連**（回前景先 `GET` 一次再開 SSE，不要只靠 SSE 補齊） |
| 賣家 Web | §4.3 ＋ §4.3.1 | `allowedActions[]` 變更（`REPORT_READY` 出現／消失）／外送員即將抵達／處理期限接近 |
| 賣家 App | §5.2 | 同上（🔴 高優先警示見 §4.3） |
| ADM | §6.3 | 事件時間線 |

⚠️ **恢復類事件不要重複打擾**：重新媒合成功恢復時**只更新畫面與預計時間，不再發推播**
——A→B→A 的切換各推一次，使用者手機會連響三下而事情根本沒變壞（§2.3 第 8 點）。

🔴 SSE 端點與事件欄位走 proto／gateway DTO 定義，
事件名走 CodeMeta `EventType`（**不得留裸字串**）；前端的事件型別由該契約生成，**不得手抄**。

#### 2.1.1 🔴 `3003` 選項卡要顯示什麼

原始需求已明確要求：買家選 Uber 時看得到 **運費 ＋ ETA ＋ 報價有效期**。正式形狀：

```
Uber 即時配送
運費：NT$xxx
預計送達：約 hh:mm
最晚約：hh:mm
報價有效：xx:xx
```

| 行 | 來源 | 前端規約 |
|---|---|---|
| 運費 | 後端報價 | **前端不算**（同上表「到貨天數」那一列的原則） |
| **預計送達** | `buyer_display_eta`（66 §5.1.4a C） | 🔴 **顯示絕對時刻**（「約 hh:mm」），不是「約 N 分鐘後」——§1.6 的時間顯示規約 |
| **最晚約** | delivery-window 上界 | 🔴 **後端沒給就整行不顯示**（見下） |
| 報價有效 | `expires` | 以後端給的絕對到期時間倒數（§1.6） |

🔴 **文案禁令**：**不得**寫成「最快 13:00／最慢 13:15」。
`最快`／`最慢` 是統計量的說法，而 provider 契約**尚未**把這兩值定義為 statistical min／max
⇒ 那樣寫等於前端替 provider 發明語意（66 §5.1.4a D）。

🔴 **「最晚約」缺值時的降級是「不顯示」，不是「自己算一個」**：
provider 端有沒有 delivery-window 上界欄位**尚待書面確認**（66 §5.1.4a D，併入 `UP-24`）
⇒ 後端未回該值時，**只顯示「預計送達」單值**。
⚠️ **前端不得用「預計 ＋ N 分鐘」補一個上界**——那會變成憑空發明的對外時間承諾，
而它在畫面上與有依據的數字看起來一模一樣。⚠️ 這是 §1.10「禁止 `provider → 預設值` 的二元 fallback」的同一條。

⚠️ **買家看到的 ETA 不含平台寬限期**（`platform_grace_period`）——那是逾期取消的保護門檻，不是服務承諾
（66 §5.1.4a A）。前端拿到什麼顯示什麼，**不得自行加總任何期限類的量**。

🔴 **選項卡附近必須有配送失敗政策的簡短揭露 ＋ 政策連結。**

| 要求 | 內容 |
|---|---|
| **位置** | 🔴 **緊鄰 `3003` 選項卡**（選中時展開的區塊內，或其正下方）。**不得只放在頁尾 Footer 的條款連結裡**——買家在選配送方式的當下就要看得到 |
| **內容** | 一句話：配送失敗時**是否向買家退款要看責任歸屬**；責任歸屬在買家一方時**不向買家退款**。後接「配送政策」連結到 Web 公開政策頁 |
| **術語** | 🔴 一律寫「**向買家退款／不向買家退款**」。**禁止**寫成「買家不退款」——那句話的主體是反的（讀起來像買家不退錢給別人） |
| **不得誇張** | 🔴 **不得**在選項卡上放大段風險警語。它是一個配送選項，不是同意書；嚇退買家與隱藏資訊一樣糟 |
| **結帳頁重述一次** | 買家在 §2.2 選「指定放置」或填配送指示時，那些選擇正是責任歸屬的輸入 ⇒ 用**同一份文字**在該處重述 |

🔴 **文字本身屬 `LV-02`（Legal Verification），本設計階段只定落點與呈現位置，不寫最終法律文案。**
`LV-02` **不阻塞**前端實作（先接佔位文案 ＋ 真連結），
但 🔴 **阻塞正式對外上線**（§11 第 7 列）。
⚠️ **這是 Legal Verification，不是 Product Decision，也不是外部廠商確認**——
三者的解除者是三批不同的人，登記錯了它會永遠等不到人。

| 🆕 🔴 **交付方式與配送指示是「責任歸屬」的輸入，後果要說清楚** | 選「指定放置」、填了外送員到不了的指示、或給了錯的地址 ⇒ 配送失敗時責任歸屬會落在買家一方 ⇒ **不向買家退款**（用 §2.1.1 的同一份文字重述，並帶同一個政策連結）。🔴 **不得寫成恐嚇**，但**也不得省略**：省略等於讓買家在不知情下做出影響自己退款權利的選擇 |
| **驗證碼預設遮罩** | 例如 `••21`；只在接近交付時才允許揭露全碼，並說明「只交給實際外送的夥伴」。🔴 **它是憑證不是個資**——單獨持有即可領走貨，遮罩規則與一般個資不同 |
| **驗證碼的來源** | 碼由 Uber 產生，**會回傳在我方建單的回應裡** ⇒ 🔴 **前端拿得到全碼，遮罩／揭露流程是可實作的**，不必依賴 Uber 的簡訊。<br/>🔴 **而且不能只依賴 Uber 簡訊**：那封簡訊寄到買家在 Uber 側的號碼，一旦號碼有問題，**我方 App 是買家唯一的取碼管道**，拿不到碼的後果是**收不到貨並轉入返程**。⇒ **揭露入口是必要功能，不是加分項** |
| 🆕 **三選一必須互斥，不得做成加購** | 🔴 官方硬互斥：**「指定放置」不可同時要求簽名或驗證碼**（會直接拒單）。⇒ UI 維持單選即可，**但不得出現「指定放置 ＋ 要驗證碼」這種組合選項** |
| **選了「指定放置」要說明會拍照** | 讓買家知道證據怎麼留。✅ **官方會自動要求照片**（`leave_at_door` 一律附帶照片確認）⇒ 這句文案有契約支撐 |
| 🆕 **選了其他兩種就不會自動有照片** | 🔴 官方 `meet_at_door` 的預設是**不帶任何驗證** ⇒ 證據是我方在建單時要求來的。文案**不得**寫成「所有訂單都會有送達照片」 |

   ⚠️ **也不得顯示成空白或「處理中」**——那讓買家以為訂單壞了。

   ⇒ 這一格從付款持續到賣家回報備妥或約定取件時間到來，**不是幾秒鐘**。
   🔴 **`91` 在 `3003` 上不再有「已建單／未建單」兩種子狀態**——付款成功即已有配送單
   ⇒ 前端**不得**再用「有沒有配送單」把 `91` 分成兩種畫面。
5. 🔴 **訂單追蹤頁不得出現買家的「取消訂單」入口。**
   買家付款成功後沒有自行取消訂單的能力（65 §6.2.1 第 2a 點），這條規則**不因 provider 而異**
   ——即使 `3003` 的物流商有真正的取消 API 也一樣。
   ⚠️ **「物流商技術上能取消」與「買家業務上可以取消」是兩件事**；把它們混在一起，
   會把一個 provider 能力偷偷升格成一條新的買家權利。
   ⚠️ 這與第 2 點的 `992` 是同一組約束的兩半：`992` 的**文案**要寫（因為賣家或營運觸發時買家看得到），
   **入口**不開。
6. **provider 若提供外送員資訊與預計送達時間，這一頁是它們對買家的唯一出口**
   （外送員姓名、遮罩後的聯絡電話、預計送達、送達證明）。🔴 **不得為此另開一個頁面或端點**
   ——那會讓買家端的履約載體變成兩個，而其中一個永遠會忘記更新。
   🔴 **「遮罩後的聯絡電話」指的是 provider 給的匿名轉接號，不是外送員的真實號碼**
   ——真實號碼**一律不得出現在任何畫面**（賣家端同，§4.3）。
   ⚠️ **匿名轉接號是「撥打能力」，不是「通聯紀錄」**：畫面上**不得**出現「已聯繫過 N 次」
   這類敘述，provider 並沒有給我方那份資料。
   ⚠️ 本頁的即時更新走 **§1.11**，**前端不自行輪詢**。
7. 🆕 🔴 **「已約定取件時間」要顯示出來（`3003`）。**
   付款成功時我方已向物流商建立一張**未來取件**的配送單，取件時點是報價當下凍結的絕對時間
   ⇒ 買家在 `91` 這一格看到的不該只有「賣家備貨中」，還要有「**預計 hh:mm 取件**」。
   - **顯示絕對時刻**（§1.6），不是「約 N 分鐘後」
   - 🔴 **值一律由後端給，前端不得用「付款時間 ＋ 備貨時長」自己算**
     ——那兩個量的原點不同（§4.3），自己算會與物流商實際的約定時間對不上
   - 賣家提早回報備妥時這個時間**會提前**（後端向物流商送出更新）
     ⇒ 前端**跟隨後端的值重繪**，不做本地預測
   - 後端沒給就**整行不顯示**，🔴 **不得補一個猜的值**（與 §2.1.1「最晚約」同一條）
8. 🆕 🔴 **「重新媒合中」要有文案。**
   外送員中途放棄時物流商會自行重新媒合，**期間不會有任何 webhook**、配送單也不會退回「等待接單」
   ⇒ 這一段對買家而言是「時間到了卻沒人來」。
   - **文案**：「**配送夥伴正在重新媒合，配送時間可能稍有延遲**」
   - 🔴 **不得顯示成「配送失敗」或「異常」**——它是進行中的正常恢復路徑，多數會自行恢復
   - 🔴 **不得顯示成「配送中」**——沒有人在送，顯示配送中會讓買家站在門口等
   - 恢復之後 🔴 **只更新畫面與預計時間，不再發推播**（§1.11）
9. 🆕 🔴 **配送失敗的買家端文案分三格，分界是「責任是否 financially final」，不是「有沒有人做過判定」。**
   🔴 **financially final ＝ 該責任判定已不存在任何會改變「向不向買家退款」的待覆核／未結案案件**
   （正式判定條件在 65／03）⇒ 前端**一律讀後端給的 finality 結果，不得自行從責任歸屬推導**（§1.7 同一條）。
   - **尚未 financially final**（責任尚未判定／提案已送出但覆核未完成／同一筆仍有未結案的責任案件
     ——三者在買家端是**同一格**）⇒「**配送未完成，正在確認責任／處理結果**」＋**預計回覆時間**。
     🔴 **不得顯示退款金額、不得顯示「最終已退款」也不得顯示「最終不退款」**——**兩個方向都還沒決定**；
     🔴 **也不得顯示「訂單已取消」**——訂單此時仍停在配送異常，說成已取消是假的。
     ⚠️ **責任歸屬欄已經有值，不等於可以翻到下面兩格**：即使已初判為買家一方，
     只要 finality 尚未成立，買家看到的**仍是這一格** ⇒ 🔴 **前端不得提前給出最終結果**。
   - **financially final ＋ 責任不在買家**（物流商／賣家／平台一方）⇒「配送失敗，已**向你全額退款**」＋退款進度
   - **financially final ＋ 責任在買家一方** ⇒「配送失敗」＋**政策說明**（為什麼這種情形不向買家退款）
     ＋ 🔴 **客服申訴管道入口**。
     🔴 **不得沿用既有的取消／退款文案**：既有的履約失敗通知逐字是
     「已停止履約並向你全額退款」⇒ 那句話在這一格是**假的**
     ⚠️ **這個入口是受理與說明的管道，不是撤銷這個終態的按鈕**：
     🔴 畫面**不得**承諾「申訴成立就會退款」或「訂單會回到處理中」
     ——該終態在後端不可逆（03），寫成可逆會讓買家等一個不會發生的結果。
     🔴 **它也不改變責任判定。** 會修改責任歸屬或退款資格的覆核**一律在責任判定階段（訂單 `35`）完成**，
     終態成立之後沒有任何路徑回得去（finality 的正式定義在 65／03）
     ⇒ 🔴 入口文字**不得**叫「責任判定申訴」，也不得用任何隱含可翻案的名稱；
     它承接的是客服受理、說明與善意補償，🔴 **不進退款鏈、不重開責任案件**。

   🔴 **financially final ＋ 責任在買家一方的那一格是一個新的訂單終態**（正式定義在 03／65，概念名
   `DELIVERY_FAILED_NO_REFUND`）：它**不是**「已送達」、**不是**「已完成」、也**不是**「已取消」
   ⇒ 買家的訂單分頁要**獨立呈現為「配送失敗」**，🔴 **不得歸入「已完成」或「已取消」**。
   🔴 **未 financially final 期間訂單不會進入這個終態**——那段時間買家端一律停在上面第一格。
   ⚠️ **商品退回賣家不等於退款**：貨物回到賣家手上只是實體處置，
   🔴 **不得因此在畫面上出現任何退款進度**。
   ⚠️ 前端在該值同步進來之前會把它當未知值（§1.3 第 4 條顯示「處理中」＋原碼）
   ⇒ **買家會一直等一筆永遠不會到、也不會退錢的訂單**。
   🔴 **買家訂單分頁必須把 `OrderStatus.DELIVERY_FAILED_NO_REFUND`（Value `54`）歸到獨立的
   「配送失敗」分頁**，🔴 **不得歸入「已完成」或「已取消」**——碼值已在 CodeMeta 與四份前端拷貝裡，
   但**碼值同步不等於畫面分類對了**，分類述詞是獨立的一件事。

（「Uber 停用了這個取件門市」「這個地址現在不在服務範圍」），塌縮成「目前無法回報備妥」等於叫賣家去猜。

### 4.4 整單承載快照與報價政策快照

顯示「這一單當時是用哪一版政策算的」。🔴 **INV-P5 的六個快照欄一個都不能少，逐欄列出**：

| # | 欄位 | 為什麼不能省 |
|---|---|---|
| 1 | `fee_rate` | 費率 |
| 2 | `fee_base` | 費基 |
| 3 | `rounding` | 進位方式 |
| 4 | 🔴 `tax_treatment` | **稅務處理**——爭議時最會被吵的兩格之一 |
| 5 | 🔴 `fee_bearer` | **費用承擔方（PLATFORM／SELLER）**——另一格 |
| 6 | `policy_version` | 政策版本 |

🔴 **這是爭議發生時的唯一依據**（65 §0.3 INV-P5）。訂這條不變式的理由逐字是
「事後任何人都能用同一組輸入重算出同一個數字」⇒ **缺 `tax_treatment` 或 `fee_bearer`
就重算不出同一個數字**（誰付、含不含稅都不知道）。


### 4.5 結算與撥款 Gate（D-3 的投影表）

🔴 **後端 11 條 → 賣家端顯示幾格，是本節的核心決定。**

| 顯示格 | 對應後端條件 | 不成立時的文案 |
|---|---|---|
| **這筆適用撥款嗎** | G0 `commerce_model` | 「本筆為賣家自收，不經平台撥款」（**這不是「被擋住」**，是不適用） |
| 收款完成 | C1 | 「付款尚未完成」 |
| 已送達並確認 | C2 ＋ C3 | 「配送尚未完成」／「等待買家確認收貨」 |
| 發票已驗證 | C4 | 「請上傳發票」／「發票審核中」／「發票已退件」 |
| 無退款與爭議 | C5 ＋ C6 | 「有退款處理中」／「有爭議案件」 |
| 帳務就緒 | C7 ＋ C8 ＋ C9 ＋ C10 | 「帳號驗證未完成」（C7）／🔴「先前退款尚未沖抵完，帳上有負餘額」（**C8**）／「尚未到撥款日」（C9）／「本期無可撥金額」（C10） |

🆕 🔴 **「已送達並確認」那一格必須容得下「配送失敗但仍可撥款」的終態。**
**financially final ＋ 責任歸屬在買家一方**的配送失敗是一個**終態、且可撥款**的訂單（§2.3 第 9 點）：
它**永遠不會送達，也永遠不會有買家確認收貨** ⇒ 照現行文案，賣家會在這一格
**永遠看到「配送尚未完成」**，而後端其實早就放行了。**畫面與事實相反，而且是關於錢。**

⇒ 這一格的顯示一律以**後端回的該格結果**為準（`blockedBy` 不含 C2／C3 即視為通過），
🔴 **前端不得用「訂單是否已送達」自行判斷這一格**（§1.7 的同一條）。
⚠️ 該格因此通過時的文案要說得出原因：「**配送以不成功結案，本格不適用**」，
🔴 **不得顯示成「已送達」**——那是一句假話。

🆕 🔴 **但這一格的放行只發生在 financially final 之後。** 責任尚未 financially final 時
後端**根本不會**建立撥款任務（deliberate financial hold）⇒ 這一格在該期間**回的是未通過**，
賣家端因此**不得**顯示「本格不適用」或任何已通過的樣式。
該期間的文案是「**配送未完成，正在確認責任／處理結果**」，🔴 **一樣不得顯示成「已送達」**。
⚠️ **兩句話是同一格的兩個時點，不是兩種寫法**：拿「不適用」提前蓋掉「還在確認」，
等於在財務結論成立之前就對賣家宣告結果。

🔴 **這一格罩著四條，文案就要有四句**（`C7`／`C8`／`C9`／`C10` 各一句，**`C8` 最容易漏**）。
四條與文案必須**一對一**，否則 `blockedBy` 回 C8 時，賣家看到的會是另外三句裡最像的那一句
——而那三句沒有一句說得出「被扣」這件事。

⚠️ **C8 不是「帳務處理中」**：65 §5.3 已把它的述詞從「該結算期所有分錄淨額為 0」修正成
**`SellerNegativeBalance(store_id) = 0`（賣家不欠平台錢）**——照原述詞實作的話撥款永遠不會發生。
撥款後的退款會讓該賣家出現負餘額 ⇒ **下一筆撥款被它擋住，等於跨訂單自動扣抵**
⇒ 文案必須說得出「為什麼被扣、扣的是哪一筆」，寫成「處理中」會讓賣家以為只要等。

🔴 **六格 ＝ 一格適用性判斷（G0）＋ 五格條件（C1..C10 併成五格）**。
G0 不成立時**只顯示第一格**，其餘**五格**不顯示
——顯示「五格全部被擋」會讓賣家以為出了問題。
（§5.3「Web 是六格」、§6.5「六格投影」、65 §6.1.1 的 A-7「六格投影」講的都是這個 6，
指的是**含 G0 的列數**。）

🔴 **每一格不成立時必須指得出是哪一條**（`blockedBy`，端點 S-7）。
⚠️ **後端 C4 在賣家發票軸落地前恆 `BLOCKED`**（65 §0.5 gate #2）⇒ 前端會長期看到那一格紅，
文案要說「此功能尚未開放」而不是「請上傳發票」（否則賣家會一直上傳而永遠不通過）。

### 4.8 取消與責任提醒

沿用既有 `ShipmentDialogs.tsx`，擴充 `992`（取消處理中）：
🔴 **送出取消後顯示「處理中」，不是「已取消」**——provider 可能拒絕（65 §7.4.3 情況 B）。

🔴 **取消的責任提醒要分兩種情形寫，不得共用一段文案**

🔴 **分界是「物流商是否已完成取件」，不是「我方有沒有發動派車」。**
`3003` 的配送單在**付款當下**就已經建立 ⇒ 「尚未發動派車」這個狀態**根本不存在**；
拿它當分界，等於在一個恆為假的條件上對賣家承諾「不會有取消費」。

| 情形 | 賣家該被告知什麼 |
|---|---|
| **物流商尚未完成取件** | 「取消這筆訂單，買家會收到全額退款。」<br/>🔴 **此時尚無已確認的正常運費**，不要嚇賣家。<br/>⚠️ **但不得寫成「一定不會有任何費用」**——物流商仍可能有等待費之類的附加費用，最終一律以物流商帳單為準。文案用「**目前沒有已確認的運費**」，🔴 **不用「不會有費用」** |
| **物流商已完成取件** | 「外送員已取件。取消會向物流商送出取消請求，**去程運費一定產生且不退**，並可能另有返程費用（返程運費與去程同額）。」<br/>⚠️ 物流商可能拒絕取消 |

⚠️ **外送員即將抵達時，畫面要提醒「非必要不取消」**——此時最容易落在兩種情形的交界上，
而賣家看到的分界會在他按下去的那幾秒內翻面。

⚠️ **用一段最嚴格的文案涵蓋兩種情形看似安全，實際有害**：
在「尚未取件」的情形嚇阻賣家取消，會讓賣家改用「拖著不回報備妥」來處理缺貨
——而那條路的終點是**逾期自動取消**，買家等更久，結果更差。

🔴 **「費用歸屬依實際原因判定」要說得出值域，不能只留一句籠統話。**

| 責任歸屬 | 向買家退款（`refund_to_buyer`） | 這筆配送成本跟誰結算 | 算不算賣家的履約失敗 |
|---|---|---|---|
| **買家一方**（`BUYER_CAUSED`） | 🔴 **不向買家退款**（`= 0`） | **賣家** | 🔴 **不算** |
| **賣家一方**（`SELLER_CAUSED`） | **向買家全額退款**（`= full`） | **賣家** | 算 |
| **物流商一方**（`PROVIDER_CAUSED`） | **向買家全額退款**（`= full`） | 🔴 不向賣家結算 | 不算 |
| **平台一方**（`PLATFORM_CAUSED`） | **向買家全額退款**（`= full`） | 🔴 不向賣家結算 | 不算 |
| **尚未判定**（🔴 **不是 cause**：讀案件的 `FulfillmentExceptionCategory.RESPONSIBILITY_UNRESOLVED`） | 🔴 **尚未決定**（**既不是退款，也不是不退款**） | 🔴 **尚未決定** | 🔴 **尚未決定** |

🆕 🔴 **上表右三欄只在該責任判定 financially final 之後才是結論。**
在那之前**每一列都要當成「尚未決定」呈現**——**包含已經初判為「買家一方」的那一列**。
⚠️ 值域表講的是「判定結果長什麼樣」，不是「什麼時候可以拿它做結論」，兩者混用會讓賣家提前看到答案。

🔴 **退款只有二元兩種：`= 0` 或 `= full`。** 沒有第三種拆分公式
——**不得**寫成「商品款另外決定」「運費單獨不退」「從退款裡扣物流成本」。
🔴 **畫面文案一律寫「向買家退款／不向買家退款」**，**禁止**寫成「買家不退款」（主體反了，§2.1.1）。
🔴 **上表前四列是 `ResponsibilityCause`，第五列不是。**
`ResponsibilityCause` **只有四個 resolved 值**（`SELLER_CAUSED`／`BUYER_CAUSED`／`PLATFORM_CAUSED`／`PROVIDER_CAUSED`），
且**不會**有第五個——`RESPONSIBILITY_UNRESOLVED` 屬 **`FulfillmentExceptionCategory`**（案件分類，不是成因）。
⇒ 前端要顯示「責任未判定」時讀的是**案件 category**，把它當成 cause 寫進去會被
`chk_logrecv_responsibility_cause` 以 23514 拒絕。
🔴 **前端不得硬編任何一邊的字串**，一律走 CodeMeta 生成的拷貝。

🔴 **最容易讀反的一格：買家一方造成的失敗，買家拿不到退款，而這筆配送成本仍然算在賣家帳上。**
兩者不矛盾——**「誰造成的」與「這筆成本最後跟誰結算」是兩個不同的問題**。
賣家頁面必須把這個理由寫出來，否則賣家會以為系統判錯了。

🔴 **而且要明寫：買家一方造成的配送失敗，不計入賣家的履約失敗。**
賣家在這一格承擔的是**成本**，不是**責任**。
⚠️ **賣家履約指標系統今天尚不存在**（這是對未來的約束，不是對現況的描述）
⇒ **本書不涵蓋賣家 KPI 畫面**（§0.3），
但上面那句話**現在就要出現在賣家看得到的文案裡**——
🔴 **不得等 KPI 系統做出來才補**，那時賣家已經看過一次錯的因果。

🔴 **責任尚未 financially final 期間，賣家頁面不得顯示任何結論。**
分界與買家端同一條（§2.3 第 9 點）：**有人做過判定 ≠ financially final**
⇒ 提案已送出但覆核未完成、或同一筆仍有未結案的責任案件時，賣家看到的仍是「還在確認」那一格。
不得顯示「已向買家退款」、不得顯示「不向買家退款」、不得顯示「本筆由你承擔」——**全部都還沒決定**。
🔴 **同一期間也不得宣稱「已確認賣家收款」或「已確認物流費用（logistics charge）」**：
撥款任務與物流應收在 financially final 之前都尚未建立（§4.5）
⇒ 把它們寫成已確認，等於對賣家承諾一筆還沒成立的錢。
正確文案是「**配送失敗，平台正在確認原因**」＋**預計回覆時間**
＋（後端要求時）**上傳佐證的入口**。
⚠️ 這一格會停留一段時間 ⇒ 畫面要看得出是「還在等」而不是「壞掉了」。

處置提案送出**之前**顯示三個數字。

🆕 🔴 **三個數字之外還要顯示兩個分類欄，否則覆核者審的是一個沒有前提的提案。**

| 欄 | 值域 | 為什麼不能省 |
|---|---|---|
| **責任歸屬** | 買家一方／賣家一方／物流商一方／平台一方／**尚未判定** | 退款與否是從它推導出來的（§4.8 的表）。提案上看不到它，覆核者就只能覆核金額 |
| **這筆配送成本跟誰結算** | 賣家／不向賣家結算 | 🔴 **與責任歸屬刻意不一致的那一格就在這裡**（買家一方造成 ⇒ 成本仍算賣家）。兩欄並列才看得出這是設計，不是錯誤 |

——顯示 `0` 會讓覆核者以為已經判成不退款。
🆕 🔴 **尚未 financially final 時同理**：即使責任歸屬欄已有值，退款金額欄**仍顯示「尚未決定」**，
並在提案上標明 finality 尚未成立（§6.3）⇒ 覆核者才知道自己正在覆核的是**讓它成立的那一步**。
🔴 **預覽必須由後端算**（同一支 `PayoutInstructionFee`），前端不得自己乘 1%

（前端不送、後端算）。
⚠️ **`平台費用影響`／`賣家實收影響` 兩欄對責任判定軸不顯示**——不是顯示 0，是**不顯示**：

責任判定的預覽只有**退款金額**一項（`BUYER_CAUSED` ⇒ 0；其餘三值 ⇒ 全額）。

⚠️ **只改前三處會讓測試紅在一個看起來無關的地方**（數量不符），

| 2 | 「外送員即將抵達而尚未回報備妥」的**高優先 banner**（§4.3） | **同一筆單**在賣家已回報備妥後**不得**再出現該 banner |
| 3 | 買家端「**配送夥伴正在重新媒合**」（§2.3 第 8 點） | 同一筆單**不得**同時顯示「配送中」 |
| 4 | 買家端**責任尚未 financially final** 的「配送未完成，正在確認責任／處理結果」（§2.3 第 9 點） | 畫面上**不得**出現任何退款金額，不得出現「最終已退款」或「最終不退款」，🔴 也**不得**出現「訂單已取消」 |
| 5 | 買家端 **financially final ＋ 責任在買家一方**的配送失敗終態 | 🔴 **不得**出現「已向你全額退款」，也**不得**出現「申訴成立將退款」這類可逆承諾；🔴 入口文字**不得**是「責任判定申訴」或任何隱含可翻案的名稱（§2.3 第 9 點）；**必須**看得到政策說明與客服申訴入口 |

🆕 🔴 **第 4 項要三端同筆同時拍**（同一筆訂單、同一個時間點）：
賣家端**不得**出現「已確認賣家收款」或「已確認物流費用」（§4.8）；
ADM 案件詳情**必須**看得到 finality 尚未成立（§6.3）。
⚠️ **分開拍會讓三張截圖落在不同時點**，而要驗的保證正是「未 financially final 期間三端說法一致」
——不同時點拍到的三張圖，對這個保證零鑑別力。

🔴 **第 2～5 項的陰性驗證是這一組的實質內容**：它們的價值都能用「只有 X 才會 Y」描述
⇒ 只拍陽性等於完全沒驗到那個保證。

⚠️ **即時通道的降級態也要拍**（§1.11）：把連線切斷，畫面必須**保留既有內容** ＋
顯示「即時更新已中斷」。🔴 **拍到空白畫面或無限 spinner 即 FAIL。**

### 11.1 🔴 `992`：鎖入口、不鎖顯示

§2.3 第 2 點要求買家端補齊 7 個新值的文案（含 `992`），而 §11 第 6 列要求 `992` 不得對買家開放
——**兩者單獨看都對，照字面實作會互相抵銷**（第二個人把第一個人做的東西關掉，而兩人都以為自己照規格做了）。

🔴 **定案**：`992` 的買家端文案**照 §1.3 第 4 條顯示**（「處理中」＋原碼），
**但不開買家的取消入口**（B-3 的按鈕）。

🔴 **不要寫成「fail-closed 的預設是不顯示」**——那與全書相反且做不到：
- §1.8「選項不可用時要說明，**不得憑空消失**」、§1.3 第 4 條「不猜測、**不隱藏**」
- 而且**擋不住**：賣家走 S-4 取消一樣會寫 `992`，買家端沒有入口可鎖；
  真把文案停掉，`992` 對 UI 就變成未知值 ⇒ 觸發 §1.3 第 4 條照樣顯示「處理中」＋原碼
  ⇒ **買家看得到，只是看得更差**。

⚠️ **「要不要開買家入口」的最終裁決在 65**（65 §6.1.1 與 65 §11 在 65 內部就已打架，
不是 65A 這一層改得掉的）——追蹤在 **#3505**。裁決結果若與上面不同，要回頭改本節。
🔴 **不得因為「文案已經寫好了」就順手把入口接上去**——那正是這組互斥會被靜默解掉的方式。

### 11.2 最大的執行風險

🔴 **不是任一條未決，是「同一件事散在多個檔案而沒有 gate 比對」**（§1.3、§5.1）：
PayUni 原始碼對映表在 website 與賣家 App 各一份；
四動作出貨是**三層 × 兩端**（API 呼叫／業務碼處置／按鈕狀態機，見 §5.1 的表），
**而沒有任何 gate 比對它們**。每動一次都要把三層一起看，
且 §10.1 的第 4 條契約測試是唯一會提醒你的東西。

🔴 **處置在 §12.2**：兩份 PayUni status 表刪除**之前**先加一道 digest 對拍 gate
（過渡物，兩份刪掉時一併刪）。

### 12.0 這份清單怎麼產生的（可重跑）

🔴 **下面的清單以這三支命令重跑產生；命中數不寫進本節**——凍結的數字會漂，
而漂掉的那一份不會告訴讀者它漂了。**動工前先跑一次，逐檔清單才是交付對象。**

```bash
# ① provider 身分判斷式（窄口徑：真正的分流點）
P='isTaqbin|isTaqbinMethod|LGS_TYPE\.|lgsType ==|lgsType ===|ShippingMethod\.taqbin|ShippingMethod\.sevenEleven|SHIPPING_METHOD\.|method === "300|methodKey =='
/usr/bin/grep -rcE "$P" <website|adm> --include='*.ts' --include='*.tsx' \
  --exclude-dir=node_modules --exclude-dir=.next | /usr/bin/grep -v ':0$'
/usr/bin/grep -rcE "$P" <buyer|seller>/lib --include='*.dart' | /usr/bin/grep -v ':0$'

# ② 寬口徑（含 provider 名稱與碼字面值，會混進法務頁與生成檔，只拿來找漏網）
PW='LGS_TYPE|lgsType|isTaqbin|TAQBIN|taqbin|UberDirect|uber|SEVEN|seven|\b300[1-5]\b|黑貓|7-11|超商|C2C|c2c'

# ③ provider 抽象是否存在
/usr/bin/grep -rniE "providerRegistry|ProviderStrategy|providerSlot|CarrierAdapter|shippingProviderMap" <repo>
```

🔴 **要比較兩次盤點時，先確認兩次用的是同一個 `$P`**——換了 pattern 就不是同一個量，
**四個 repo 必須用同一個 pattern 跑完再相加**，分兩次用不同 pattern 跑再相加得到的數字沒有意義。

🔴 **零命中都要附對照組**（同一支命令、同一個範圍，查一個確知存在的東西）：
否則「這裡沒有」與「我查錯地方」分不出來。窄口徑對 `shipment`／`registry` 這類確定存在的字串
必須有命中，那才證明 grep 打得到該 repo。

⚠️ **總數是口徑的函數，不是事實的函數**：寬口徑會混進法務頁的「7-11」、生成的 `code_meta.dart`
與和物流無關的 `C2C` ⇒ **寬口徑只拿來找漏網，不拿來當交付量**。

⚠️ **E1／E2 的 provider 專屬 widget 檔（`taqbin_shipping_section.dart` 等）方向是對的**——
它們已經是 slot 的形狀，**缺的只是 registry**。⇒ 這兩列是**補一層對映**，不是重寫，
不要當成大改動而延後（那正是它一直沒被做的原因）。

### 12.6 ADM：migration 對象是「零」，但那不代表沒事

`hawkr-admin` 沒有 provider 分流點。
🔴 **原因不是它做對了，是它根本沒有物流畫面**（§6.10 已記載：ADM 對結算／對帳端點零命中）。
⇒ ADM 的 7 個新畫面（`AD-01`／`AD-03`～`AD-08`）是**從零建**
⇒ **它是唯一一個可以一次就照 §1.9／§1.10 蓋對的 repo**，
不要把 website／seller 的既有形狀複製過去。

### 12.7 `allowedActions[]`：不是零，而是「零 fulfillment 消費」

🔴 **`allowedActions` 在 website 有命中，但全部屬 PayUni 錢包／商家資料軸**
（`edit_merchant_profile`／`resync`）⇒ **fulfillment 軸的消費 ＝ 0**。
⚠️ ADM 的 `product-certifications/[id]/page.tsx:allowedActions(status)` 是**本地自己算的函式**，
不是後端給的陣列 —— 那正是 §1.7 禁止的形狀，**不得照抄**。

✅ **有一個現成的正例可以照抄**：
`features/seller-center/wallet/WalletClient.tsx` 逐字
`{payuni?.allowedActions?.includes("edit_merchant_profile") && (<MerchantProfileEditCard … />)}`
——後端給陣列、前端只做 `includes` 判斷、不重算授權。
🔴 **§1.7 要求的形狀在本 repo 已經有人做出來了**，要做的是把它擴到 fulfillment 軸，不是發明新模式。

⚠️ 唯一要補的是 §1.8：那個正例在 `allowedActions` 不含該動作時是**靜默不渲染**，
而 §1.8 要求「不可用要說明、不得憑空消失」⇒ **照抄機制，但不要照抄那個靜默行為。**
