# 錯誤碼

gRPC Response Code 與 API Error Code。所有錯誤文案由本文件集中管理，程式碼禁止硬編碼錯誤訊息。

---

## GrpcResponseCode

- **類別**: 錯誤碼
- **介面**: ErrorCode
- **前端可見**: Yes（透過 Gateway 轉換為 HTTP 回應）
- **使用服務**: 全部微服務
- **DB 儲存欄位**: 無
- **說明**: 跨服務統一 gRPC Response Code，成功=0，錯誤依範圍分配

**3004／3005 的涵蓋範圍於 #2755 擴大**（19 §8.4 三道防線，值域未變、語意變寬）：3004 `GOV_CERT_API_UNAVAILABLE` 新增涵蓋政府 API 回 `RS != "OK"`（金鑰錯／失效／配額用盡時 HTTP 200 且完全沒有 `Data` 欄，舊實作判成「認證不存在」⇒ **金鑰一出事全站所有編號都被判為假的且無任何錯誤訊號**）；3005 `GOV_CERT_API_RESPONSE_INVALID` 新增涵蓋編號自我校驗失敗（政府 API 忽略未知查詢參數並回傳整個資料集，參數名一旦打錯任何編號都會「驗證通過」）。

**3030 `CERT_REVERIFY_COOLDOWN` 隨「reverify 繞過結果快取」一併登記**：繞過快取之後，
每一次「重新查驗」都真的打農業部並消耗每日配額（19 §9.3），而該端點**沒有** `expectedVersion`
可以擋，冪等鍵又刻意每次點擊都換新（同一筆本來就會被查很多次）⇒ 沒有任何東西擋得住
「管理員連點」與「多位管理員同時看同一筆」。3030 是最低限度的護欄：同一筆申請
`gov_verified_at` 在冷卻窗內時直接拒絕，**不打外部**。
⚠️ **`gov_verified_at IS NULL` 不套用冷卻**——§15.3 migration 產生的 legacy 列從未查驗過，
而「重新查驗」是它們**唯一**的查驗觸發方式（§8.3 明令禁止掃 `PENDING` 的排程），
擋住首次查驗等於讓那批列永遠停在待查驗。
⚠️ HTTP status → **429**（`gateway/internal/response/bizhttp.go`）。未登錄會塌縮成 409，
而 409 的語意是「你看到的畫面過時了、重新載入即可」——重新載入對冷卻中的申請沒有任何幫助，
會把管理員推去做一件不會有用的事。
⚠️ **第一個 `%s` 是「為什麼現在被擋」**，兩種情形共用本碼、訊息不同：
`另一個查驗正在進行中`（租約持有中）／`剛在 N 秒前查驗過，約 M 秒後可再試`（上次查驗未滿冷卻窗）。
**兩者缺一不可**：只看 `gov_verified_at` 的時間差擋不住「呼叫還在飛」的那 90 秒
（政府 API 背景 read-timeout ＝ 90 秒 ⇒ 第二個管理員在這段期間讀到的仍是舊時間戳，照樣放行），
而那正好就是「多位管理員同時看同一筆」與「跨分頁連點」會落進來的窗口。

**3025~3029 隨 #2755（商品認證申請與審核）登記**，各有實際 emitter，判準是「操作者看到這個碼之後的下一步動作是不是同一件事」：3025 查無或非本人商品（ADM／賣家都回這個碼，防 IDOR 枚舉）；3026 `expectedVersion` 不符或已被別的管理員裁決（重新載入即可）；3027 非法狀態轉移（19 §5.1 轉移表以外一律命中，四個終態不再轉出）；3028 `reject`／`revoke` 缺 `reasonCode`（`approve` 不需要）；3029 同 `(product, type)` 已有待審申請的併發衝突（partial unique `uk_pca_pending` 命中）。
⚠️ **五個新碼的 HTTP status 必須登錄進 `gateway/internal/response/bizhttp.go`**，未登錄會塌縮成 409：3025 → 404、3026 → 409、3027 → 409、3028 → 400、3029 → 409。**該表的值一律必須是 4xx**（Cloudflare 會把 origin 的 5xx body 整個換掉，前端拿不到業務碼），由 `TestBizHTTPStatus_NoServerErrorStatuses` 守住。

### 平台功能開通業務碼（9703~9709）

> 本碼段由 backend#3329 定案。
> 它描述的不是「使用者做錯了什麼」，而是「**這個環境還沒開通這項功能**」——一個**合法的部署狀態**。
>
> 🔴 **存在的理由**：這些功能的憑證／金鑰原本被列為啟動必要條件，於是「已部署但未開通」不是
> 合法狀態，維運只能把整個服務 `replicas: 0`，結果是**與該功能無關的數十條路由一起消失**
> （#3230 即此：invoice-service 76 條路由靜默全滅三天）。改成 graceful degradation 之後，
> 服務照常啟動、無關端點照常服務，而用到未開通功能的那幾條路徑在**使用點**回本碼段的業務碼。
>
> 🔴 **fail-closed，不是 fail-open**：未開通時必須明確回錯，不得靜默放行或回空結果——
> 後者會讓「功能沒開」長得像「查無資料」，那是比 CrashLoop 更貴的失效。
>
> 每一個碼都必須配一支 `*_enabled` gauge（0/1）讓停用狀態在監控上現形，見各服務的 metrics 定義。

| Name | Code | Message |
|------|------|---------|
| FEATURE_AI_ASSISTANT_DISABLED | 9703 | AI 助理尚未開通，請稍後再試 |
| FEATURE_PAYUNI_MERCHANT_DISABLED | 9704 | 金流商家建檔服務尚未開通，請稍後再試 |
| FEATURE_SHIPPING_PROVIDER_DISABLED | 9705 | 物流服務尚未開通，請稍後再試 |

🔴 **三者皆須登錄 `gateway/internal/response/bizhttp.go` 為 424 Failed Dependency**，未登錄一律塌縮成 409。

選 **424** 而非 403／503 的理由與 9505 同一條：這是**我方配置缺失**，不是使用者資格不成立（403）、
也不是「此環境沒有這個端點」（503／404 會被前端讀成永久不存在而隱藏入口）。前端對 424 的既定處置
是顯示「暫時不可用」並保留入口，正是本碼段要的行為。

⚠️ **9705 不與 9503 `FULFILLMENT_PROVIDER_NOT_ENABLED` 合併**：9503 是 403「這個賣家沒有開通這個
配送方式」（資格問題，賣家自己去建店就能解決），9705 是 424「**我方**的 PayUni 代理商憑證沒設定」
（賣家做什麼都沒用，要動的是維運）。合成一個碼會把後者顯示成前者，賣家會被導去重複申請建店。

### 設計原則

1. **文案集中管理**：所有前端顯示的錯誤訊息由本文件定義，程式碼禁止硬編碼錯誤字串
2. **動態替換**：Message 含 `%s` 的為模板，程式碼透過 `BusinessException(code, arg1, arg2)` 傳入參數，由 `String.format(message, args)` 組裝
3. **無參數預設**：`BusinessException(code)` 不帶參數時，直接使用 `code.message()` 作為回應訊息
4. **每個場景一個碼**：不同的錯誤訊息模板使用不同的錯誤碼，禁止共用碼覆寫訊息
