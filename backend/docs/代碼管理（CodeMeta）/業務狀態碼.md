# 業務狀態碼

隨生命週期變動的狀態值。前端需根據這些狀態碼顯示對應 UI。

## OrderStatus

- **類別**: 業務狀態碼
- **介面**: CodeMeta
- **前端可見**: Yes
- **使用服務**: order, cart, payment, shipping
- **DB 儲存欄位**: orders.status（存 Value）
- **說明**: 訂單生命週期狀態
- **特殊方法**: 無（原 isTerminal/canApplyRefund 為 0 caller 死碼，依[踩坑與變遷紀錄.md](./踩坑與變遷紀錄.md) 教訓 2 已刪除）
  - `isTerminal()`: COMPLETED(50) / FULLY_REFUNDED(70) / CANCELLED(80) — 確認收貨後自動撥款，不可再發起售後或退款
  - `canApplyRefund()`: PAID / PENDING_SHIPMENT / IN_TRANSIT / WAITING_PICKUP / SHIPPING_ABNORMAL / DELIVERED — 不含 COMPLETED

| Name | Code | Value | Label | Description |
|------|------|-------|-------------|-------------|
| PENDING_PAYMENT | PENDING_PAYMENT | 0 | 待付款 | 庫存已扣減，等待支付事件 |
| PAID | PAID | 10 | 已付款 | 已完成付款，等待賣家出貨 |
| PENDING_SHIPMENT | PENDING_SHIPMENT | 20 | 待出貨 | 物流單已建立，等待出貨 |
| IN_TRANSIT | IN_TRANSIT | 30 | 配送中 | 物流配送中 |
| WAITING_PICKUP | WAITING_PICKUP | 32 | 待取貨 | 超商到店待取（僅超商） |
| SHIPPING_ABNORMAL | SHIPPING_ABNORMAL | 35 | 物流異常 | 物流異常，admin 端處理 |
| DELIVERED | DELIVERED | 40 | 已送達 | 消費者已取貨，等待確認收貨，可申請售後 |
| COMPLETED | COMPLETED | 50 | 已完成（終態） | 買家確認收貨 → 自動撥款，不可再發起售後 |
| DELIVERY_FAILED_NO_REFUND | DELIVERY_FAILED_NO_REFUND | 54 | 配送失敗未退款（終態） | 🔴 **配送未成功、不向買家退款的財務結案終態，不可逆**。唯一入邊 ＝ `SHIPPING_ABNORMAL(35) → 54`，唯一驅動者 ＝ `fulfillment.responsibility.finalized` 且 `responsibilityCause = BUYER_CAUSED`（履約責任判定已 financially final）。與 `50` 同屬撥款結案 band ⇒ payout eligible。**無出邊**：不得新增 54→70／54→80／任何 post-54 的 refund reversal。⚠️ 取 `54` 而非 `55` 是因為 `ShippingStatus` 已用 `55 = SELLER_NOT_PICKED`（責任方相反），見 03 §2.1 |
| PARTIALLY_REFUNDED | PARTIALLY_REFUNDED | 60 | 部分退款 | 已完成訂單的部分退款終態；唯一進入轉移 = 50→60。進行中訂單（10~40）的部分退款不改狀態，僅累加 `orders.refund_total_amount`（03 §5.7.1） |
| FULLY_REFUNDED | FULLY_REFUNDED | 70 | 全額退款（終態） | 全部商品已退款 |
| CANCELLED | CANCELLED | 80 | 已取消（終態） | 未付/手動/超時取消 |

## ShippingStatus

- **類別**: 業務狀態碼
- **介面**: CodeMeta
- **前端可見**: Yes
- **使用服務**: shipping, order

  Stripe 的相容性清單立場相反，是刻意選擇，故明寫於此。
- **特殊方法**: 無

### 本組 registry 的邊界（重要，避免被「順手統一」）

以下五個 status 欄位**不屬於本 registry，字面值一律不動**——它們是 domain 狀態機
（描述業務物件走到哪），不是執行生命週期（描述一次 agent run 的進度）。
（此處刻意用條列而非表格：本 generator 的 Markdown 解析器會把章節內的表格一律當成
enum 資料表，多寫一個表格會產出語法錯誤的 Go。）

- `procurement_requests.status` — CLARIFYING, REQUIREMENT_READY, MATCHING, CANDIDATES_READY
- `procurement_request_revisions.status` — ACTIVE, SUPERSEDED
- `procurement_quote_batches.status` — OPEN, SUPERSEDED, WITHDRAWN
- `procurement_quote_invites.status` — PENDING, CONFIRMED, LOST
- `procurement_quote_outbox.status` — pending, done, failed（小寫，純內部表）

這條邊界不只是分類潔癖：`procurement.sql` 有四個 partial index 把 status 字面值寫進
`WHERE` 述詞（其中 `uq_procurement_request_revisions_active` 是守「同一 request 只有一個
ACTIVE revision」的 unique index）。把上表任何一個併進本 registry 並改名，就必須重建那些
index；維持邊界則一個都不用動。outbox 的小寫尤其不要「順手統一大寫」。

### 與 FreshnessLabel／PredictionStatus 的相反決定

那兩組明文選擇「維持現行字面值不改名，因為 `hawkr-website` 已硬編這些字串」。
本組**相反，選擇改名**（`COMPLETED`→`SUCCEEDED`、lane 的 `OK`→`SUCCEEDED`、step 的
`DONE`→`SUCCEEDED`），差別在三個可查證的前提：

1. procurement 功能尚未對外上線，prod 的 12 張 procurement 表**實測 0 rows**
   （schema 已 migrate，零業務資料），backfill 只需處理 dev 的測試資料。
2. 對外唯一消費端是 `hawkr-website`（Flutter buyer/seller 與 admin 皆零命中），
   與後端同團隊、可同波部署，不存在 native app 那種無法原子更新的相容期問題。
3. 舊值 `OK` 是全 repo 唯一的孤兒同義詞（其他所有成功態都叫別的名字），留著就是
   registry 從第一天起自帶二義。

前提 1 或 2 若在未來不再成立（例如已上線、或出現第二個消費端），同類改名就不能再照本例辦理。

### 舊值 PARTIAL 的處置（本組唯一被移除的既有值）

`procurement_candidate_sets.status` 今天有 `PARTIAL`，本 registry **不收**它——理由同
ProcurementLaneStatus 砍 PARTIAL：部分成功由「run `SUCCEEDED` + 其中一條 lane `FAILED`」
表達，不在 run 主軸上開第三種終態。

- `services/ai-service/internal/procurement/repository/candidate.go` 的讀取 gate
- `hawkr-website` `features/procurement-assistant/session-logic.ts` 的
  `isTerminalCandidateStatus`（漏改會讓前端永遠等不到終態而無限輪詢）
- `hawkr-website` `features/procurement-assistant/CandidateBrowser.tsx` 的
  「部分來源未完成」提示（`candidateSet.status === "PARTIAL"`）——**唯一只出現 PARTIAL
  的地方**

## ProcurementErrorReason

- **類別**: 業務狀態碼
- **介面**: CodeMeta
- **前端可見**: Yes
- **使用服務**: ai-service, gateway
- **DB 儲存欄位**: 無（僅出現在錯誤回應）
- **說明**: Hawkr Agent 對外錯誤 envelope 的 `reason` 欄位值域，即**機器可讀的錯誤身分**。
  issue #2446 對外契約凍結的一部分。
- **傳輸值形態**: Value 即 UPPER_SNAKE 字串本身，同 `PricebookQualityReasonCode` 慣例。

### 為什麼放這裡而不是「錯誤碼.md」

`錯誤碼.md` 的模型是 `(Name, 數字 Code, Message)` 三元組，對應 gRPC Response Code
與有數字業務碼的錯誤（4001、9266…）。procurement 對外的錯誤 envelope 形狀是
`{code: int, reason: string, message: string, traceId: string}`——其中 `code` 就是
**HTTP status**（`gateway/internal/handler/procurement_errors.go`），沒有、也不需要
第二套數字業務碼；穩定的機器身分掛在 `reason` 上。這與 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)
把 `status` 定為 advisory、身分交給 `type` 的立場一致，也符合
[AIP-193](https://google.aip.dev/193) 對 `ErrorInfo.reason` 的規定（≤63 字元、
match `[A-Z][A-Z0-9_]+[A-Z0-9]`、domain 內唯一且穩定）。

因此本組以字串 reason code 的形態登記在本檔，與同為 reason code 的
`PricebookQualityReasonCode` 一致，而不是硬塞一組數字碼進 `錯誤碼.md`。

### 契約規則（凍結後生效）

- 命名形狀 `<SUBJECT>_<STATE>`，UPPER_SNAKE。凍結後**永不改字面值**；要改只能新增並保留舊值。
- 值域為 open（可加值，加值不算破壞性變更）→ client 必須有 default 分支。
- `reason` **不得為空**。今天約 52 個 `procurementStatus(..., "", msg)` 呼叫點傳空字串，
  等於契約承諾了機器碼卻沒給；改用本表的通用碼另行處理。
- 動態值（品項、數量、供應商、`currentVersion`）走結構化欄位，**不得**串進 `message`——
  AIP-193 對此是 must。`message` 是給人看的，凍結後可自由改文案。
  ⚠️ 但改文案前必須先確認消費端沒有在解析它：`hawkr-website`
  `features/procurement-assistant/errors.ts` 目前用 `message.toLowerCase().includes("request not found")`
  判斷 CONVERSATION_GONE，在那行改成讀 `REQUEST_NOT_FOUND` 之前，`message` 仍是機器可讀路徑。
- SSE 串流路徑的 AG-UI `RUN_ERROR` frame 帶同一套 reason，但必須放在**獨立的 `reason` 欄位**：
  該 frame 的 `code` 只接受十進位數字字串（HTTP status 的字串形式），消費端以
  `/^-?\d+$/` 過濾、不符即丟棄並 fallback 到 500。把 UPPER_SNAKE 塞進 `code` 會讓
  fail-closed 的 409 冪等處理靜默降級，且不會有任何編譯錯誤。

- **編碼選擇**: Value 採 UPPER_SNAKE 字串（同 `ReportStatus` 慣例），不佔數字值段——本值直接寫進 VARCHAR 欄位並由 DB CHECK `ck_pca_status` 逐字比對，換成數字碼會讓約束與碼表對不上。

## ProcurementOrderProvisioningState

- **類別**: 業務狀態碼
- **介面**: CodeMeta
- **前端可見**: Yes
- **使用服務**: ai-service, gateway
- **DB 儲存欄位**: `procurement_buyer_quote_acceptances.order_provisioning_state`（存 Value）
- **說明**: 買家接受報價之後，那張 order shell 建到哪一步（#2538 決策 D3、doc 64 §6.2 決策 B）。acceptance 寫在 Go `ai-service` 的 DB、order shell 建在 Java `order-service` 的 DB，兩者之間**必然有一個可觀察的窗口**——這個欄位就是把那個窗口講出來，而不是假裝它不存在。
- **傳輸值形態**: Value 即 UPPER_SNAKE 字串本身（與 Code 相同），同 `ProcurementArtifactType` 慣例。
- **值域為 open（可加值，不可刪值、不可改字面值）**: 同 `ProcurementRunStatus`。
- **note**: 🔴 **`CREATING_ORDER` 是買家看得到的狀態，⛔ 不得畫成「已成交」或「已下單」。** 接受成功後的固定文案是 v6.0 V.11.5 凍結的那句——「已接受這個報價版本，成交價格已凍結，尚未付款」——它剛好對 `CREATING_ORDER` 也成立。ACK 在此狀態下 `orderNo` 與 `paymentDeadline` 皆為空字串。
- **note**: 商務 award 在 acceptance 成立的當下就發生，**不等** `ORDER_CREATED`。本欄描述的是建單進度，不是成交與否。
- **特殊方法**: 無

| Name | Code | Value | Label | Description |
|------|------|-------|-------|-------------|
| CREATING_ORDER | CREATING_ORDER | CREATING_ORDER | 訂單建立中 | 已接受、價格已凍結、**尚未付款**；`orderNo` 與 `paymentDeadline` 為空字串 |
| ORDER_CREATED | ORDER_CREATED | ORDER_CREATED | 訂單已建立 | order shell 已建；`orderNo` 與 `paymentDeadline` 此時才有值 |
| ORDER_FAILED | ORDER_FAILED | ORDER_FAILED | 建單失敗 | 需要前滾或補償；acceptance 本身仍成立 |
