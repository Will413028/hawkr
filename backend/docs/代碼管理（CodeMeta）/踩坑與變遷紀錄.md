# CodeMeta generate 變遷與踩坑

紀錄 CodeMeta 生成體系演進過程中的決策與踩坑，避免重蹈覆轍。CodeMeta 規範本身見 [`README.md`](./README.md) 與 [`docs/開發規範/Java 微服務開發規範.md`](../開發規範/Java%20微服務開發規範.md) §6「Enum 與禁止硬編碼」。

## 教訓 1：直接修改生成檔案 → 下次覆蓋遺失

**事件**：曾因直接修改 `GrpcResponseCode.java` 而未同步 `錯誤碼.md`，導致下次 `generate.sh` 覆蓋時遺失手動新增的錯誤碼，造成執行期 crash。

**結論**：Markdown 與生成碼不一致是最難追查的 bug 來源之一。**永遠先改 Markdown 再執行 generate.sh**，禁止直接修改生成檔案。

## 教訓 2：CodeMeta enum 自定義方法區塊（2026-04-08 已徹底移除）

**舊機制**：generate.sh 早期版本支援「自定義方法區塊」(`extract_custom_block` / `extract_marked_block`)，允許在 enum 內保留業務輔助邏輯（routing / mapping / I18n 等）。

**問題**：
- 污染 common-core，產生不必要的依賴（例如為了 `topic()` import `MqConstants`）
- 不同語言生成器難以對齊（Go / Flutter 沒有對應方法）
- 違反 CodeMeta「value/code 對應 + 描述」的單一職責

**處置（2026-04-08）**：
- generate.sh 的自定義方法區塊機制徹底移除
- 14 個 enum 的舊自定義方法已全數遷移至各服務 helper class（單服務）或 `common-core/utils/code/helper/`（跨服務共用）
- CodeMeta enum 僅承載 `(code, value, label, description)` 4 個欄位與 generate.sh 產出的 4 個 helper（`fromCode` / `fromValue` / `isValidCode` / `isValidValue`）

**新做法**：在使用該 enum 的服務或模組內建立獨立 helper class。
範例：`PayUniEventRouting.exchange(PayUniEventType)` 提供 enum → MQ exchange 的對應，**不是** `PayUniEventType.exchange()`。

**Helper class 命名與位置慣例**：

| 使用範圍 | 位置 | 範例 |
|---------|------|------|
| 單一服務 | `services/{service}-service/.../{Domain}Rules.java` | `PaymentStatusRules` |
| 跨服務共用 | `services/java/shared/common-core/.../utils/code/helper/{Enum}Rules.java` | `ShippingStatusRules`、`AccountTypeRules` |

helper 必須為純函式，不得引入 enum 套件以外的依賴。
