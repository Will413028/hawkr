# Food Safety Incident Runbook（食安事件處理 runbook）

> **適用對象**：hawkr 營運人員（目前單人營運，沒有輪值、主管與 oncall；等有第二位營運人員才適用的段落標「有第二位營運人員時」，K16）。
> **適用範圍**：買家、賣家或公眾針對「食品安全」面向（疑似食物中毒、商品污染、過敏反應、群聚發病、食品標示異常等）所提交的通報。食安通報可匿名送出（`/public/food_safety_reports`），登入端的通報由通報人選類別，平台分案時判定；兩者都在 admin「商家通報」處理。設計見設計書 32。
> **與一般通報的差異**：分案期限 4 小時（一般 72 小時）；食安案件另有轉報主管機關（Ch3）。其他類別的通報走 [seller-violation-management-runbook.md](./seller-violation-management-runbook.md)。

## Emergency Cheat Sheet（一頁式速查）

```
admin「商家通報」→「待分案」分頁（每 30 秒自動更新）。食安的通報有分案期限（建立後 4 小時）：
  剩不到 1 小時轉黃，逾期轉紅（期限只顯示，不強制，沒有 push）

  1. 開通報詳情：看通報內容、補充、佐證、檢舉人
       匿名通報有電話或信箱時，聯繫通報人確認情況（電話打不通 → 留 voicemail + email + 簡訊）
  2. [分案]：判定類別（食安）、嚴重度；系統把它加入這家店的食安案件，沒有就開一個
       通報人選錯類別也在這裡改判
  3. 案件詳情的內部註記：記錄聯繫結果（時間、是否接通、陳述摘要）

查證屬實後（< 4h 內決定）：
  4. 立即停權？案件詳情 → [建立措施]
         { 種類: 停權, 類別: 食安（案件預填）, 嚴重度: 高 / 嚴重,
           結束時間: <now + N 天>,
           來源通報: 案件裡的通報（預填，最多 20 筆）, ... }
       API 是 SellerGovernanceAdminService/CreateMeasure（帶 source_case_id），欄位見 1.4
       建立措施沒有離線 SQL 後備
  5. 暫不停權？建立警告，或在案件註記寫明「請賣家協助調查／下架自查」並以平台管道聯絡賣家
  6. [結案]：採取措施／不採取措施；還沒有結果的通報會帶入結果，並通知通報人

是否轉報主管機關？→ 看 Ch3 decision tree
  - 住院 / 群聚 ≥ 3 / 商品污染 / 過敏 → 立即 1919 + 衛生局
  - 個別輕症          → 食藥署線上表單
  - 標示異常 / 包裝瑕疵 → 不轉報，內部要求賣家修正
  轉報在系統外完成，不必等結案；之後在案件詳情 [記錄已轉報主管機關]（只能記一次，不能修改）

事件結束後（案件結案後 7 天內）：
  7. 寫 postmortem → docs/postmortems/food-safety/YYYY-MM-DD-{case-id}.md
       模板見 docs/postmortems/food-safety/_template.md

> 完整流程往下翻
> 轉報 → Ch3
> 單人營運與有第二位營運人員時 → Ch4、Ch6
```

**快速決策參考**：

| 你看到 | 你應該 | 時限 |
|---|---|---|
| 待分案分頁的食安通報，期限轉黃（剩不到 1 小時） | 馬上開詳情，分案 | 立即 |
| 期限轉紅「已逾期 {時長}」 | 立即分案；單人營運沒有人可升級，分案後在註記寫明逾期原因 | 立即 |
| 食安案件進行中，已分案 | 聯繫通報人、查證，做出決定（建立措施／不採取措施） | 4h 內 |
| 食安案件查證後需要轉報，還沒有轉報紀錄 | 依 Ch3 決定轉報管道 | 24h 內 |

## Ch1: admin UI 處理流程

> admin UI 位置：「商家通報」（`/admin/violation-reports`，側欄「賣家 / 商品」群組）。後端是單體的 seller 模組（Connect `SellerGovernanceAdminService`）。

### 1.1 巡視規範

- 頁面每 30 秒自動更新，但沒有 push（D9：食安事件不上 push channel，避免半夜誤報騷擾）；營運人員要自己看。
- 單人營運：營業時間內至少每 30 分鐘看一次待分案分頁（分案期限 4 小時的 1/8）；離開電腦超過 30 分鐘，回來第一件事先看待分案。
- 有第二位營運人員時：離開電腦超過 30 分鐘要口頭交接給另一位（見 Ch4）。

### 1.2 清單的讀法

| 視覺元素 | 意義 | 動作 |
|---|---|---|
| 待分案分頁的食安通報，期限「剩 {時長}」 | 建立後 4 小時內要分案 | 依期限由近到遠處理 |
| 期限轉黃 | 剩下不到整段期限的四分之一（1 小時） | 立刻分案 |
| 「已逾期 {時長}」（紅色） | 已過 4 小時 | 立即分案（Ch6） |
| 滑鼠停在期限上 | 顯示絕對時間 | — |
| 案件分頁的狀態篩選 | 全部｜進行中｜已結案 | 預設「全部」，找未結的選「進行中」 |

時長無條件捨去；每 30 秒重讀，相對時間會跟著走。

### 1.3 處理的進展

```
通報：待分案  →  處理中（在案件裡）  →  有結果（已採取措施／未違規／內容不足／重複／濫報）
案件：進行中  →  已結案：採取措施／不採取措施（或通報都移走時由系統關閉）
```

| 動作 | 位置 | 做什麼 |
|---|---|---|
| 分案（`TriageReport`） | 通報詳情 | 判定類別與嚴重度，加入或新開案件 |
| 設定結果（`ResolveReport`） | 通報詳情／案件裡的通報 | 單筆通報的結果；不會撤銷以它為來源的措施 |
| 移到其他案件（`MoveReport`） | 通報詳情／案件裡的通報 | 通報放錯案件或類別時；原案件通報都移走時自動關閉 |
| 詢問賣家（`CreateCaseInquiry`） | 案件詳情 | 提供紀錄（進貨來源、批次、效期、進出貨及流向）或請說明，期限預設 3 天（1 到 14 天）；案件進入「等賣家」。賣家端畫面上線前，系統不會通知賣家，要另外聯絡。只寫你轉述的內容，不附通報原文或檢舉人資料 |
| 記下回覆／撤回（`RecordCaseInquiryReply`、`WithdrawCaseInquiry`） | 案件詳情的詢問卡 | 在系統外收到回覆後記下管道、收到的時間、內容與最多 5 份附件（機敏檔）；不必再回覆就撤回。結案會自動撤回還沒結束的詢問；撤回之後才收到的回覆寫在案件的內部註記 |
| 結案（`DecideCase`） | 案件詳情 | 採取措施／不採取措施；還沒有結果的通報帶入結果，每筆通知通報人 |
| 改嚴重度 | 案件詳情 | 原因必填，寫成內部註記 |
| 內部註記 | 案件詳情 | 聯繫通報人、通話結果、查證過程 |

**重要約束**：
- 按鈕只看伺服器：不能操作時隱藏，不顯示原因。
- 補充（匿名或登入的後續內容）不改案件的版本；結案前有新補充會提醒先看。匿名補充是以電話或信箱比對到原通報的，送出者不一定是原通報人。
- 沒有 `dismissed` 這種終態：誤報、撤回、無法佐證，設定結果為「未違規」「內容不足」或「濫報」。有新證據時，新通報會進案件，或把原本的通報移到進行中的案件。
- 沒有建立通報的方法：通報人選錯類別，在分案時改判；放在錯的案件，移到其他案件。

### 1.4 建立措施（CreateMeasure）

**前提**：通報查證屬實，而且案件還在進行中：導出的措施要在結案**之前**建立（結案後案件詳情沒有建立措施的按鈕；結案後才發現要處分，在店家詳情建立，不會記為案件導出的措施）。

admin UI 案件詳情 → [建立措施]／[建立風險措施]／[終止合作]（權限 `seller.measures.create`；店家詳情與發票申訴頁開的是同一組對話框，從案件開會帶 `source_case_id`，頂端說明「這個措施會記為案件導出的措施」）→ 表單欄位：

| 欄位 | 值 | 備註 |
|---|---|---|
| 種類（`warning`／`suspension`） | 警告／停權 | 食安查證屬實一般用停權；終止合作有自己的對話框，見 [`seller-violation-management-runbook.md`](./seller-violation-management-runbook.md) §4.1 |
| 類別（`finding.category`） | 食安（案件預填） | 其他類別見下拉 |
| 嚴重度（`finding.severity`） | 高／嚴重（食安一般選這兩級） | 中以下不停權，走警告 |
| 來源通報（`finding.source_report_ids`） | 案件裡的通報（預填最早的 20 筆） | 選填，最多 20 筆；只列這家店、結果不是未違規、內容不足或濫報的通報；同一事件有多筆通報時一起勾選 |
| 依據的認定（`cited_finding_ids`） | 同一帳號既有的認定 | 選填；必須未撤銷 |
| 給賣家的理由（`statement`） | 賣家看得到 | 必填，最多 2000 字 |
| 內部註記（`note`） | 賣家看不到 | 必填，最多 2000 字；沒有來源通報時附明確證據連結 |
| 結束時間（`suspension.end_time`） | 台北時間，晚於現在 | 停權必填（例：現在起 7 / 14 / 30 天）；警告沒有結束時間 |

**種類與嚴重度的選用建議** → 見 [seller-governance-shared.md §1](./seller-governance-shared.md)。

API 是 Connect 的 `hawkr.admin.seller.v1alpha1.SellerGovernanceAdminService/CreateMeasure`（admin UI 的對話框呼叫的就是它）。`request_id`（UUIDv4，選填，AIP-155）：重送同一個請求用同一個 `request_id`，內容相同回傳原本的措施，內容不同的重送會被拒絕；`source_case_id` 不同是不同的請求。API 範例：

```http
POST /hawkr.admin.seller.v1alpha1.SellerGovernanceAdminService/CreateMeasure
Authorization: Bearer <admin_token>
Content-Type: application/json

{
  "requestId": "0b7c2d9e-5f4a-4c1b-9d3e-6a8f1e2c4b7d",
  "storeId":   "2685914682",
  "sourceCaseId": "0192f3c0-7d10-7a3e-8f21-5b4c6d7e8f90",
  "statement": "貴店販售的冷藏即食便當經 5 位買家通報群聚發病，醫院確診沙門氏菌，暫停營業 14 天",
  "note":      "通報者群聚發病 5 人，醫院確診沙門氏菌；商品為冷藏即食便當",
  "suspension": {
    "violation": {
      "finding": {
        "category":        "POLICY_CATEGORY_FOOD_SAFETY",
        "severity":        "VIOLATION_SEVERITY_CRITICAL",
        "sourceReportIds": ["0192f3c0-8a1e-7b52-9c4d-3e5f60718293"]
      }
    },
    "endTime": "2026-11-01T00:00:00Z"
  }
}
```

**沒有離線 SQL 後備**：CreateMeasure 在同一個 transaction 寫認定、來源通報（`finding_reports`）與措施，直接改表會繞過升級規則、停權期間的重算、事件與稽核。admin UI 不可用時，由能呼叫 admin API 的人照上面的範例送出（同一個 `request_id` 重送是安全的）。

建立措施後系統會：
- 新增認定（類別、嚴重度，帳號 90 天內第 3 次中度會自動升為高；有來源通報時一併記下）、措施、第 1 版與第一則內部註記
- 停權：帳號停權，買家看不到這家店，商品連動下架，未付款訂單與優惠券會陸續取消、停用；有結束時間的停權由 job 在結束時間自動結束
- 賣家在「處置與申訴」看得到措施與給賣家的理由，可以申訴
- 案件詳情的「導出的措施」列出它；店家已關閉時案件不再提供建立措施的按鈕

### 1.5 申訴決議流程

賣家收到措施通知後可在 seller app 的「處置與申訴」提交申訴（每個措施一次）。申訴與補正的收件匣、`DecideAppeal` 的兩種結果（`ACCEPTED` 撤銷措施、`REJECTED` 維持）與決議標準，見 [`seller-violation-management-runbook.md`](./seller-violation-management-runbook.md) §5 與 [`seller-governance-shared.md`](./seller-governance-shared.md) §3。

**申訴 SLA**：申訴提交後 7 個日曆天內決議（與一般申訴相同，見 violation runbook §5；K18 在 3d 校準，原本的 14 天是公司時期的過時值）。

## Ch2: 沒有 SQL 後備

舊流程在 admin UI 不可用時用 SQL 直接改 `food_safety_reports`（`docs/runbooks/food-safety/sql/`）。新的通報、案件、措施與認定都不再有 SQL 後備：直接改表會繞過推導點、事件、通知與稽核，也會讓停權期間與措施不一致。寫入只經 admin 的 Connect 方法。

admin UI 不可用時：
1. 先確認是不是頁面問題：重新整理、換瀏覽器；伺服器句子與錯誤文字會直接顯示在頁面上。
2. 仍不可用：由能呼叫 admin API 的人用 Connect 方法送出（`TriageReport`、`ResolveReport`、`MoveReport`、`DecideCase`、`RecordFDAReferral`、`CreateMeasure`），帶 `etag`／`request_id` 的規則同 UI；欄位以 `api/hawkr/admin/seller/v1alpha1/governance.proto` 為準。
3. 恢復後在案件的內部註記補記這次是怎麼處理的。

`docs/runbooks/food-safety/sql/` 是舊 seller-service 表的 SQL，隨 seller-service 在步驟 11 刪除，不要執行。

## Ch3: 轉報主管機關手動清單

> **背景**：台灣食藥署（TFDA）規範食品中毒 / 群聚 / 重大污染必須通報；輕症 / 商品瑕疵則由業者內部處理。
> **平台立場**：hawkr 不是食品製造商，但作為平台對「重大食安事件」有協助通報義務（避免下游消費者持續受害）。
> **此章節用於協助判斷**：哪些事件要轉報、走哪個管道、轉報後如何記錄。轉報本身在系統外完成，系統只記一次紀錄。

### 3.1 Decision tree

| 情況 | 處置 | 時限 |
|---|---|---|
| **住院** / **群聚 ≥ 3 人** / 明顯**商品污染**（異物、發霉、變質）/ **過敏性反應**（蕁麻疹、休克、就醫） | **立即** 1919 食安專線 + 傳真衛生局 | 24h 內 |
| **個別輕症**（單一通報者、無住院、無群聚、症狀輕微如腹瀉一次） | 食藥署「食品藥物消費者服務專區」線上表單 | 72h 內 |
| 商品**標示異常** / 包裝瑕疵（無症狀，僅標示錯誤 / 包裝破損） | **不轉報**，內部處理（要求賣家限期修正 + 下架該批） | N/A |
| **不確定**（症狀模糊、佐證不足、只有 1 人但有住院） | 保守原則：寧可轉報。有第二位營運人員時，先升級給另一位判斷 | 4h 內 |

**判斷依據**：案件詳情的通報內容、佐證與註記。沒有「建議轉報」旗標；食安案件只要裡面還有通報（不是因通報都移走而關閉），案件詳情就顯示 [下載轉報資料（.md）] 與 [記錄已轉報主管機關]，進行中或已結案都一樣，不必等結案；記錄已轉報之後只剩下載。**最終決定權在營運人員**。

### 3.2 不應轉報的場景（避免過度通報）

過度通報會：(a) 浪費主管機關行政量能；(b) 讓未來真案被忽視；(c) 對賣家不公（被列入觀察名單）。**以下情況一律不轉報**，僅作平台內處置：

- **偏好抱怨**（口味不合 / 份量少 / 賣相不佳 / 與圖不符）→ 走一般買家爭議流程
- **賣家服務態度**（出貨慢、態度差、退款拒不處理）→ 走客服爭議流程
- **配送延遲 / 物流問題**（商品送達時退冰、外觀壓壞）→ 走物流爭議流程
- **已確認誤報**（通報人承認誤會、撤回，或買家找錯賣家）→ 設定結果「未違規」或「內容不足」即結案

**判斷不確定時**：寧可內部再查證一輪，不要直接轉報。轉報後不可撤回，會在主管機關系統留下對該賣家的紀錄。

### 3.3 管道與聯繫方式

#### A. 1919 食安專線（24h 緊急）

**何時**：上述「立即轉報」類別。

```
撥 1919 → 語音選單按「食品安全」
告知：
  1. 自己身分：「hawkr 線上生鮮平台營運」
  2. 事件摘要：何時、何地、何商品、幾人、何症狀
  3. 平台案件 id：case id（案件詳情）
  4. 通報者聯絡：主管機關可能要直接聯繫；聯絡方式在通報詳情的「檢舉人」區（匿名通報的聯絡方式有保留期限，過期已清除）
  5. 賣家資訊：店家名稱與 store id
  6. 商品資訊：商品名稱與批號（若有）
```

**準備動作**：撥電話前在案件詳情按 [下載轉報資料（.md）]（檔名 `fda-referral-case-{id}.md`）。內容含店家資料、案件與通報摘要，只列結果不是「未違規」「內容不足」「濫報」的通報；**不含檢舉人的聯絡方式**，佐證只寫份數、另附。列印或螢幕開啟備用，避免通話中查資料。

#### B. 食藥署線上表單（一般）

**何時**：個別輕症 / 標示問題但有疑慮想留紀錄。

```
url: https://consumer.fda.gov.tw/
路徑：「食品藥物消費者服務專區」→「食品中毒/檢舉」表單
填欄：
  - 事件發生時間 / 地點
  - 商品名稱 / 購買來源（填 hawkr 平台 + 賣家名稱）
  - 通報者基本資料（取得通報者同意後填）
  - 症狀描述
  - 是否就醫 / 醫院名稱
  - 平台案件 id（填在「補充說明」欄）
```

填送後系統會 email 通報者一個受理編號（FDA-XXXXXXXXXX），**填到 [記錄已轉報主管機關] 的案號欄**。

#### C. 傳真衛生局（嚴重事件）

**何時**：「立即轉報」類別且事件涉及單一縣市群聚 → 通報該縣市衛生局更快觸發稽查。

```
1. 衛生局傳真表單：填寫格式參考 docs/templates/fda-fax-template.pdf（待補）
2. 傳真至該縣市衛生局食安科（號碼依地區，常用列表見 docs/runbooks/food-safety/contacts.md，待補）
3. email subject 格式：「[食安通報] {case_id} {seller_name} {date}」；副本寄 fda-incident@hawkr.example
```

### 3.4 轉報後的內部紀錄

**完成轉報後** → 案件詳情 [記錄已轉報主管機關] → 表單：

| 欄位 | 值 |
|---|---|
| 管道 | 1919 食安專線／線上表單／傳真衛生局／親自送件／其他 |
| 主管機關的案號（選填） | 受理編號 / 1919 通話紀錄編號 / 傳真回執號 |

說明：轉報本身在系統外完成；這裡只記一次，記過之後不能修改。轉報時間與記錄人由系統寫入。再按一次（或另一個視窗已記過）時，顯示「這個案件先前已記錄轉報，以下是原本的紀錄，這次輸入的內容沒有寫入。」

| 欄位 | 值 |
|---|---|
| 追蹤日期（選填） | 到了這天還沒收到主管機關的回覆就聯絡主管機關；不填是轉報日（台北）加 30 天。過了追蹤日期而還沒有回覆時，案件詳情的日期用 warning 色 |

**決定不轉報**（例如主管機關已經介入）→ 案件詳情 [不轉報]，必填原因。不轉報也是這個案件唯一的轉報紀錄：標記之後不能再記錄轉報，記錄轉報之後也不能標記不轉報；標記不轉報的案件不再出現在「待轉報」。

**主管機關的回覆**（移送通知、結果通知各一則）→ [記下主管機關的回覆]：收到的日期（不早於轉報日、不晚於今天）、內容，可以同時改下一個追蹤日期或選「不再追蹤」。回覆只新增、不修改；已標記不轉報或還沒有轉報紀錄的案件沒有這個按鈕。

**主管機關後續回函** → 寄到 `fda-incident@hawkr.example`，用 [記下主管機關的回覆] 記在轉報紀錄上（回覆的內容與收到的日期）；回函之後的內部判斷與處置（裁罰 / 不立案 / 補件等）仍寫在案件的內部註記。

### 3.5 主管機關來函（限制或移除商品、調取資料、暫停帳號）

入口：側欄「主管機關來函」（處理中｜已完成兩個分頁，每 30 秒自動更新）。

- **收到公文** → [登記來函]：機關、文號、收文時間、種類、內容摘要、指名的帳號（與選填的店家、商品）；期限依種類預設（限制或移除商品、暫停帳號 48 小時，調取資料與其他 72 小時；來函寫了期限時照填）。
- **登記就是保存**：指名的帳號或店家，資料保存到收文後 184 天，不會被關店後的兩段清理（30 天的公開內容與下游刪除、184 天的店家聯絡、身分認證與登錄字號）刪除；每家店的涵蓋狀態逐家顯示。「登記之前已依保留期限清除」表示登記太晚，回覆機關資料已依保留期限刪除。帳號在平台沒有店家資料（例如只是買家）時照樣登記，但買家與帳號資料的保存尚未支援，要人工另外處理。
- **看涵蓋狀態**：來函詳情的「指名的對象」逐家列出：保存中、登記之前已依保留期限清除、保存期限已過、保存期限已過而個資已依保留期限清除。後兩個之後，即使延長保存，已清掉的資料也回不來。
- **進入訴訟** → [延長保存]，原因寫明（例如延長到裁判確定後 3 個月）；只能延長，每次延長都留紀錄。
- **完成** → [完成]：處理摘要，加上**每個被指名者的告知**——已告知（時間與方式）；機關要求暫不告知（例如偵查不公開，必填向機關確認的日期，到期會進待辦「告知被指名者」，確認後在來函詳情用 [記下告知] 改成已告知或寫新的日期；暫不告知的對象旁會一直顯示確認日期與這個提醒）；由措施告知（只限暫停帳號、限制商品，而且已建立這份來函導出的措施）。調取資料的來函填實際提供資料的時間，保存期限自動延到提供之後 184 天。
- **需要處置**：在來函詳情從來函建立措施（建立措施、建立風險措施、終止合作；來源來函記在措施上，列在來函的「導出的措施」；來函指名多家店時先在「先選帳號」選要處置的那一家；暫停帳號的來函最常見的是 RISK 停權）。限制或移除商品在商品限制措施（B4）上線前，人工於商家頁強制下架，並把做法寫在完成的處理摘要。
- 登記錯了（例如對象或文號登記錯）：在完成之前用 [撤銷登記] 寫明原因，保存隨之解除、紀錄保留，再登記正確的一筆（來函建立後不能改）。已完成的來函不能撤銷，錯誤寫在處理摘要。

## Ch4: 營運安排與責任邊界

> 目前單人營運，沒有輪值表、oncall 與交接。最終排班表（有的話）存於 ops wiki，本檔不維護當期排班。

### 4.1 單人營運（現行）

| 任務 | 目標時間 |
|---|---|
| 看待分案分頁 | 營業時間內每 30 分鐘 |
| 食安通報分案 | 建立後 4 小時內（只顯示，不強制） |
| 聯繫通報人（首次嘗試） | 分案後 1 小時內 |
| 查證並決定（建立措施或不採取措施） | 分案後 4 小時內（食安期望 8 小時內結案） |

營業時間外沒有人值班，也沒有 push：隔天第一件事先看待分案分頁；逾期的在案件註記寫明原因。嚴重事件（住院、群聚）只要自己得知，可以不等分案完成，先轉報主管機關。

### 4.2 有第二位營運人員時

以下在第二位營運人員加入後才適用；沒有加入前不要照做，也不要維護班表。

- **雙班制**（人力 ≤ 3）：09:00–21:00 主班在線，21:00–09:00 oncall 手機暢通、收到電話 1 小時內上線。**三班制**（人力 ≥ 4）：早班 09:00–17:00、晚班 17:00–01:00、01:00–09:00 oncall。
- **oncall 邊界**：職責是讓待分案的期限不再逾期（分案），不是立刻完成調查；嚴重事件（住院、群聚）可以直接轉報並通知另一位，不必等隔天。不在半夜決定停權或申訴。
- **交接**：每次班次結束口頭加文字紀錄，內容為待分案的通報、已聯繫等回覆的案件與賣家、未完成的操作、可聯繫的人。文字紀錄放案件內部註記，不另開 channel。
- 離開電腦超過 30 分鐘要先交接。

## Ch5: Postmortem 模板

### 5.1 何時寫

**觸發條件**：食安案件結案後 **7 天內**提交。

**判斷標準**：
- **必寫**：結案決定是「採取措施」的食安案件（真實食安事件）
- **必寫**：結案決定是「不採取措施」，但已轉報主管機關的案件（走過程序，需留紀錄）
- **可選不寫**：不採取措施、未轉報、無賣家處分的案件（純誤報 / 撤回）

> 不寫 postmortem ≠ 不留紀錄；案件詳情的內部註記已有完整 audit trail，postmortem 是給「組織學習 + 未來預防」用。

### 5.2 位置與流程

```
位置：docs/postmortems/food-safety/YYYY-MM-DD-{case-id}.md
模板：docs/postmortems/food-safety/_template.md
流程：單人營運時直接 commit 到 main（repo 只有 main 一條分支），不需要 PR review；有第二位營運人員時走 PR，由另一位 review 後 merge
時限：結案後 7 天內提交
```

### 5.3 8 sections 模板說明

postmortem 必含以下 8 章節（內容空時填「無」/「N/A」也要保留標題）：

1. **事件摘要**（1-2 段）
   時間、地點、商品、影響人數、最嚴重結果（住院 / 群聚 / 死亡）。回答「發生什麼？」。

2. **時間線**（bullet list with timestamps）
   通報者首次反映 → 通報建立 → 分案 → 聯繫通報者 → 查證屬實 → 建立措施 → 通知賣家 → 轉報主管機關 → 結案。每個事件附操作人與 UTC+8 timestamp。

3. **涉案資訊**（table）
   店家與 store id、商品與批號（若有）、通報者人數與症狀、購買時間、食用時間。回答「誰、什麼東西、什麼狀況？」。

4. **處置動作**（bullet）
   分案時間、案件決定、是否建立措施（種類 / 結束時間）、是否下架商品、是否通知賣家、賣家是否申訴、申訴決議。回答「平台做了什麼？」。

5. **轉報情況**
   是否轉報、走哪個管道（1919 / 線上 / 傳真 / 親自送件 / 其他）、案號、主管機關後續回應（裁罰 / 不立案 / 進度待回）。若未轉報，填判斷依據。

6. **賣家通知紀錄**
   通知時間、通知管道（push / email / 簡訊）、賣家回應（承認 / 否認 / 沉默）、賣家是否提交申訴。若 RabbitMQ publish 失敗 → 補貼 ops 介入紀錄（D7）。

7. **後續預防措施**（bullet, action items with owners + due dates）
   - 平台層：是否需要新增 product 上架檢核、是否新增此類別的自動偵測、admin UI 是否要加新欄位
   - 賣家層：是否要要求此賣家加強 SOP、是否要追蹤該賣家後續案件率
   - 流程層：runbook 是否要更新

8. **Lesson learned**（1-2 段）
   學到什麼？下次會做不一樣？是否有 wiki/tech 等級的踩坑值得抽出？回答「organizational memory」。

完整空白模板見：[`docs/postmortems/food-safety/_template.md`](../postmortems/food-safety/_template.md)（待建立首版）。

## Ch6: 逾期與升級

### 6.1 食安分案期限（4h）

**視覺變化**（admin UI 內建，不依賴 push，只顯示、不強制）：

| 經過時間 | 待分案分頁的期限 |
|---|---|
| 0 - 3h | 一般顯示「剩 {時長}」 |
| 3h - 4h | **黃色 warning**（剩不到整段期限的四分之一） |
| 4h+ | **紅色**「已逾期 {時長}」 |

**單人營運**：沒有可升級的對象。看到紅色逾期就立即分案，並在案件註記寫明逾期原因（例：夜間無人值班）；累積的逾期原因是改人力與通知機制（觸發條件：第二位營運人員，或食安通報出現逾期造成的實際延誤）的依據。

**有第二位營運人員時**：看到列表的任何人，3h 後仍未分案，應主動聯繫另一位：

```
「目前有 N 個食安通報已超過 3h 未分案：
 通報 9876... / 通報 1234... / ...
 負責人是 @xxx，目前狀態未知，請裁示是否接手。」
```

**為何不依賴系統 push**：D9 設計決策，食安事件不上 push channel（避免半夜 false positive 騷擾）；人工電話比系統 alert 更不容易漏。

### 6.2 一般通報

不是食安類別的通報，分案期限 72 小時（待分案分頁顯示），完整流程見 [seller-violation-management-runbook.md](./seller-violation-management-runbook.md)。案件的決定期限依嚴重度（嚴重 24 小時、高 3 天、中 7 天、低 14 天），所有期限都在側欄「待辦」依期限排序。

### 6.3 轉報後的 escalation

轉報後 **48h 內未收到主管機關回函** → 主動致電 1919 / 衛生局確認受理進度（即使案件本身已結案）。追蹤日期（預設轉報後 30 天）過了而案件詳情還沒有主管機關的回覆時，日期會用 warning 色，也是聯絡主管機關的提醒；收到回函後用 [記下主管機關的回覆] 記下，並可改下一個追蹤日期或選「不再追蹤」。

主管機關後續若裁罰 / 要求補件 → 單人營運時自行處理並在案件註記留紀錄；法律性質的公文先諮詢法務再回覆。有第二位營運人員時，立即轉知另一位與 legal。
