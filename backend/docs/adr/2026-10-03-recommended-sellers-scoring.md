## 脈絡

seller-service 的推薦賣家（`GetRecommendedSellers`，盤點於 7d 開工時，快照 152dab261）沒有分數公式：近 30 天營收由高到低，過濾掉沒有公開商品的店，不足時以最新的店補位。每個請求即時呼叫 Java 的 order 與 product，再呼叫 buyer。

- 營收榜讓大店越來越前面、容易被自買刷高，新店永遠排不上；部分退款整筆計入，與 CRM 的口徑不同。
- order 失敗時整個請求失敗；product 失敗時不過濾，空店會曝光。
- 「可公開」在兩條 SQL 各寫一次，只看狀態與 PayUni，沒有 KYC 與店家資料的完整度。
- order 端把候選上限夾在 50，`limit` 大於 16 時被過濾掉的名額悄悄改由補位填上。

約束：
- 繼承：discovery 只放排行（決定第 8 項），其餘在 A11。仍成立。
- 繼承：order、product 在 Java，review 在 review-service（A6）；它們的資料只能經 port 讀取，由 `internal/legacy` 實作。
- 不再成立：「排行只用 order 現有的 `GetTopSellersByRevenue`」——它只回前 50 名的營收，不夠做分數；Java 可以加 RPC。

## 考慮過的方案

**排序依據**

| 方案 | 代價 | 判定 |
|---|---|---|
| 基準：先以硬門檻決定資格，再在合格者之間依品質訊號排序，並給新店曝光（Etsy 搜尋的品質與顧客體驗分數、蝦皮優選賣家、Amazon 精選報價的門檻） | 權重要隨資料調整；Java 要新增一支統計 RPC | ✓ |
| 照搬營收榜 | 大店壟斷、可刷、新店冷啟動 | ✗ |
| 人工策展（設計書 45 的 `featured_sellers`） | 需要後台策展工具；是另一個功能 | ✗（營運置頂與排除在 A11） |

**計算時機**

| 方案 | 代價 | 判定 |
|---|---|---|
| 基準：分數離線或近線計算，線上讀取時套用即時規則（推薦系統的兩階段）；有時間窗的統計以排程從權威資料整批重算 | 分數最多落後一個週期 | ✓ |
| 讀取時即時計算 | 每個請求依賴 Java 是否可用 | ✗ |
| 以事件增量維護讀取模型 | 要處理時間窗過期、漏收與漂移；換不到需要的新鮮度（website 快取 900 秒） | ✗ |

## 決策

- **資格**：讀取時由 seller 批次判斷「可公開曝光」（店家營運中、沒有停權、KYC 與 PayUni 的流程已核准、必填的店家資料齊全），停權即時生效；「至少一個公開商品」在重算時由 product 判斷。
- **分數**：每個成分正規化到 0–1 後加權，扣分項相減：
  - 需求：近 30 天成立訂單的不重複買家數（取 log，以全體最大值正規化）。用買家數而不是營收，降低大單與自買的影響。
  - 品質：評分的貝氏平均，評價少時向全站平均收斂。
  - 可靠度（扣分）：賣家造成的取消占比，同樣以先驗平滑。
  - 新店曝光：第一次可公開曝光（KYC 與 PayUni 都核准）起 30 天內線性遞減的加分。從申請開店起算的話，審核拖得久的店會在第一次曝光前就失去加分。
  - 公式有版本，權重在程式裡；每列存各成分的值與版本。
- **沒有訂單時**：所有店的訊號都是零，由新店加分與可曝光的時間決定順序。沒有另一條補位路徑。
- **成立訂單**：已付款、沒有取消也沒有全額退款的訂單，時間窗以付款時間計；賣家取消以取消時間計。部分退款的訂單仍是成立的購買（只計買家數與筆數，不計金額，所以退款金額不影響）。
- **重算**：River 每 15 分鐘從 ordering、review、product 的 port 與 seller 重算全部合格店家，整批取代分數表；每次重算記下開始時間，只有比上一次成功的那次更晚開始的才能寫入（重疊或重試時舊的結果不會蓋掉新的）。上游任一失敗就整次失敗、保留上一份並記錄失敗（stale-if-error，RFC 5861 的精神：推薦清單舊一點遠比沒有好）；上游回傳違反契約的資料同樣讓整次失敗，不靜默排除。新鮮度（最後一次成功、最後一次嘗試與錯誤）存在 discovery，讀取時一併回傳；告警屬於單體監控（River job 狀態），在 CD 的監控待辦，不在模組內。讀取依分數排序、在同一個快照內分頁，再套用即時的資格判斷。
- **輸出**：discovery 回傳排序後的店家 ID，以及排名用到、要和排名一致的事實（近 30 天的成立訂單數、評價數與平均），與快照的計算時間；店名、logo、粉絲數等顯示欄位由 `internal/httpapi` 組裝。
- **上游**：Java order 新增一支各店統計（不重複買家數、成立訂單數、賣家取消數）的 RPC，以 `store_id` 游標分頁；review-service 新增批次的評分統計 RPC（與 order 同一個理由：重算不逐店呼叫），A6 後改呼叫模組。

## 後果

- 上線前沒有訂單與評價，榜單由新店加分決定；權重要等有資料再調整，調整時只換公式版本。
- 店家下架最後一個商品後，最多一個重算週期仍會出現在榜上。
- 營運的置頂與排除、其他探索功能在 A11；ordering 搬進單體後只換 port 的實作。
- 重新評估：出現刷單或評價操弄時，加入異常偵測；資料量足以做離線評估時，改以實驗調整權重。

## 修訂：推薦清單的評分由店家卡片提供（2026-10-07，Will 決定）

本節修訂「決策」的「輸出」。

**脈絡**：店家卡片帶即時評分（ADR `2026-10-03-public-store-identity-and-visibility.md` 的 2026-10-07 修訂）之後，`RecommendedSeller` 的快照評分讓同一家店在推薦清單上有兩個可能不同的數字（最多差一次重算）。業界基準（Etsy、Amazon）是全站卡片顯示同一個評分，排名用的訊號不對外；「與排名一致」是本 ADR 自己的選擇，不是外部約束。

**決策**：刪除 `RecommendedSeller.review_count`、`rating_average`（號碼 reserved）；推薦清單的評分由卡片提供，與其他清單同一份批次組裝。排名用的評價數與平均只留在 discovery 的快照內，不對外。
