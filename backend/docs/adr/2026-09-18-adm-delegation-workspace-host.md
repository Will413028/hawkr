# 代行營運：工作區落在哪個 repo、憑證怎麼跨 host、身分由什麼承擔

| 項目 | 值 |
|---|---|
| 狀態 | accepted；遷移計畫 A2（2026-09-27）不影響：工作區與 handoff 的流程照舊，只有兌換 handoff 的實作搬進單體的 identity 模組 |
| 日期 | 2026-09-18（決策內容成形於 2026-08-10） |
| 影響範圍 | `hawkr-website`、`hawkr-admin`、Gateway 路由與 boot 斷言、account-service `delegated_operation_sessions` |

## 1. 代行工作區的實作 repo

**考慮過**：① 留在 `hawkr-admin`，把賣家中心的畫面在 admin 重建
② 留在 admin，但把賣家中心元件抽成跨 repo 共享套件 ③ **搬到 `hawkr-website`，與賣家本人共用同一份元件**
④ 起一個新的第三方 repo 專放工作區

**決策：③。** 兩條裁決同時指向它：

- **(i) 「UIUX 完全依照 mockup」**——mockup 右側是**貨真價實的賣家中心頁面**
  （完整表單、富文本工具列、規格卡、運送設定、批次選取列），不是示意。
- **(ii) 「無技術債」**——mockup 把兩條線畫進同一個「共享展示層」方框並標「同一視覺契約」，
  而那份元件在 `hawkr-website`。

**否決 ①**：它要在 admin 重建 37 個賣家頁面的畫面與表單，而 admin **一頁賣家管理端都沒有**、
UI 棧也不同。**這正是「兩份必然漂移」否決過的形狀，只是換到前端**——同一把尺不能只在後端用。

**否決 ②**：跨 repo 共享要先統一 UI 棧或建 monorepo，成本大、且風險落在 prod 賣家頁面上；
換來的好處（工作區留在 admin）本身沒有價值。

**否決 ④**：第三個前端 repo ＝ 第三份 CI、部署、design system 與 session 機制，
而它一行既有程式碼都用不到。

**③ 的代價要誠實記帳**：(a) 憑證必須跨 host 傳遞，因此新增 handoff 兌換端點（見下節）；
(b) 賣家資料層要重構成可注入 fetcher，動到 prod 賣家路徑；
(c) `hawkr-website` 走直接 push `dev` 無 PR，代行相關改動缺 PR review ⇒ 需要逐步驗證。

⚠️ **原定版（留在 admin）的唯一依據是「前端已上 dev、契約寫死」，
而那份工作區是 140 行的殼（零內容 UI、零資料呼叫）——一個空殼不構成契約權威。**
判定程序見 `2026-09-18-adm-delegation-authority-test.md`。

## 2. 工作區渲染哪些模組：渲染集合 ⊋ 可操作集合

**考慮過**：① 只渲染有 read capability 的四塊 ② 渲染完整選單，未開放者以 `disabled` 呈現
③ **渲染完整選單，未開放者點入顯示「不在本次代行授權範圍」空狀態；可操作集合不變**
④ 為 mockup 每一個選單項各開一個 capability（9 → 15）

**決策：③。**

**否決 ①**：除了與 mockup 衝突，它的兩條原理由本身也站不住——
「渲染集合＝攻擊面」與「UI 隱藏不是授權」直接矛盾（被排除在機械保證之外的層，
渲不渲染都改變不了攻擊面；攻擊面的定義是端點總表 ＋ boot 斷言掃描的路由 registry，
源碼對源碼、與畫面無關）；「畫出點不動的入口會讓沒權限與壞了長得一樣」的正解是
**明確的空狀態文案**而不是隱藏。隱藏製造的誤解更嚴重：模組整個消失時，
操作者看到的是「這家店沒有優惠券功能」，而那是假的（賣家自己有），還會被寫進對賣家的說明裡。

**否決 ②（`disabled`）**：`disabled` 恰好保留了 ① 想避免的那個缺點——
它答得出「不能點」，答不出「為什麼」；而空狀態頁有地方寫原因。

**否決 ④：這是本案最大的技術債來源，而且它的錯不在工作量。**
六個 capability 各要付一次四道機械保證的全部代價，外加兩條 DB CHECK、proto 欄位、跨 repo 同波；
但真正的問題是**其中四項各自有獨立的否決理由**（優惠券的收拾路徑落在平台治理、
CRM 與逐筆揭露原則衝突、IM 沒有真正的唯讀、數據分析等於放寬統計 RPC）
⇒ **該做的裁決是「不開」，不是「開了但很貴」。**

**③ 為什麼零技術債**：後端**零改動**——不新增 capability、不動兩條 DB CHECK、不動 proto、
不動 golden、不動 CodeMeta；前端變更整個落在 `hawkr-website`，
**沿用賣家中心既有的側欄**，只把不可操作的項目切成空狀態，**零新增選單資料結構**。

⚠️ **不是「在 admin repo 的選單陣列裡補六筆」**：那份宣告連同 admin 的整個工作區
已列入刪除清單，照它施工會造出**第二份選單宣告**，而兩份選單必然隨賣家中心的演進分岔。

**誠實記帳**：③ 的代價是操作者會看到五個點得進去卻做不了事的選單項。
**這是 UX 代價不是安全代價**，換到的是「未開放」與「禁區」在畫面上可區分——
而後者正是「本次代行未執行任何出貨或財務操作」這句對外宣稱所依賴的區別
（禁區連選單項都不渲染）。

## 3. operation credential 怎麼跨 host 交到工作區手上

**考慮過**：① 把 session cookie 的 `Domain` 放寬成 `.example.com`，兩個 host 共用
② 工作區的瀏覽器直打 Gateway ③ 把 credential 放進導向 URL
④ **一次性 handoff code：ADM 建立完成後 303 帶 code，website BFF 伺服端兌換出 credential 並寫自己 host 的 cookie**
⑤ 兩個 Worker 共享一把對稱密鑰，ADM 簽一張含 credential 的短期 JWT 放進 URL

**決策：④。**

**否決 ①**：`__Host-` 前綴在定義上禁止 `Domain`，放寬只能降級成 `__Secure-`，
而那正是先前刻意移除掉的寬網域形狀。**為了一個新功能把已經收斂完成的登入安全性倒回去，
代價與收益不成比例。**

**否決 ②**：那個瀏覽器在 www 上沒有任何 ADM 憑證，送出的是使用者自己的 session。
⚠️ **它的失敗模式不是「不能用」而是「用成功了，但操作的是錯的店」**——
一個同時是賣家的管理員會在零稽核之下改到自己的店。

**否決 ③**：credential 進瀏覽器歷史／`Referer`／任何記錄 URL 的中介層，
而它是「單獨持有即可操作」的憑證（判準是拿到它能做什麼，而非它含不含個資）。

**否決 ⑤**：credential 一樣進 URL（③ 的全部缺點），外加一把**沒有輪替機制、
沒有 gate 守著**的跨 Worker 共享密鑰。

**④ 的四道防護**：單次（同句 CAS 清空）／60 秒／只兌換得出自己那個 session 的 credential／
session 已終態一律拒。把連結貼給第二個人＝410。

**credential 全案只存在一份**（www host）：ADM 用完即丟。
兩個 host 各存一份必然有一份清不掉——同「兩份必然漂移」的理由。

## 4. 賣家中心元件怎麼從 `/app/*` 切到 `/admin/*`，以及怎麼保證不漏切

**考慮過**：① 每個元件自己判斷要打哪條路徑 ② 元件收一個 `basePath` prop
③ **資料層工廠化（repo 收 fetcher）＋ 單一 dispatch 切換點在代行執行期直接 throw**
④ 在 website BFF 做路徑改寫，元件完全無感

**決策：③。**

**否決 ①**：把「這次算不算代行」散進每個元件，等於沒有單一問答點——
與在後端建立單一問答點的理由完全同構。
**否決 ②**：prop 會漏傳，而漏傳的後果是靜默打到 `/app/*`。
**否決 ④**：BFF 收到的是已經成形的 `/app/*` 請求，改寫器必須逐條維護一張路徑對照表，
而**漏一條就是靜默放行**；更糟的是它讓「代行能打哪些端點」重新變成不可列舉。

**③ 的三層保證，由弱到強**：
(a) ESLint／CI grep（可繞過）
(b) **`dispatch()` 的 `mode === "authed"` 分支**在代行執行期 throw ——**全 repo 唯一切換點**
(c) **結構性**：代行瀏覽器沒有賣家 session，`/app/*` 對它一律 401 ⇒ 漏切＝壞掉，不是打穿禁區。

⚠️ **(c) 有一個例外，而它正是 (b) 非做不可的理由**：管理員本人同時也是賣家
且在同一瀏覽器登入過 www 時，`/app/*` 會**成功**——操作到他自己的店、零稽核、零告警。

## 5. 跨 host 之後，代行執行期的操作者身分由什麼承擔

跨 host 的直接後果：資源端點、`GET`／`DELETE current`、媒體 upload session 全部改由
**www host 的 BFF** 發出，而那個 host 沒有 ADM session cookie ⇒
「session 快照的 `actor_admin_id` ＝ 當前 ADM session 的 admin」這道比對失去比對對象。

**考慮過**：① 把 ADM 身分也交到 www ② **credential 即身分**：代行執行期的端點不要求 ADM session
③ 兌換時把 `actor_admin_id` 存進 website 自己的 cookie，每次請求回送給 Gateway 比對
④ website BFF 不直打 Gateway，改把每一支代行請求轉給 ADM BFF，由後者補上 ADM cookie 再轉發

**決策：②。**

**否決 ①**：那是把 admin 身分**本體**複製到唯一一個有真實買家流量的 host 上。
它一旦存在，`/api/v1/admin/**` 底下的**全部治理端點**（停權、認證、SEO、異常訂單查詢…）
就對持有者開放——三層鎖定的第一層在 API 層被整個繞過，而那條線正是
「本次代行未執行任何出貨或財務操作」這句對外宣稱所依賴的區別。
這與否決「放寬 cookie 作用域」是同一把尺，但更重：那一條只是放寬作用域，這一條是把身分搬過去。

**否決 ③**：比對的兩邊同源——`actor` 值本身就是兌換回應的一部分，
等於拿 credential 推導出來的東西去驗證 credential 自己，**恆等成立、鑑別力為零**。
**它比不做更糟**：文件與程式碼裡都會留下一行「已比對 actor」，讀的人會以為這道防線還在。

**否決 ④**（它是唯一真的保得住這道防線的選項，因此要逐條寫清楚為什麼仍不划算）：
它確實有效——B 用同一個瀏覽器打 www，website BFF 轉給 ADM BFF 時帶的是 **B 自己**的 admin cookie，
Gateway 比對 A ≠ B 即命中。代價三條，任一都足以否決：

- **(a)** 二十支資源端點要在**兩個 repo 各維護一份**轉送路由，正是「兩份必然漂移」否決過的形狀；
- **(b)** 每一次代行請求多一次**跨 host 公網往返**，逾時預算與效能預算整表重算；
- **(c)** 它換到的保護只在一個窄交集成立——「同一瀏覽器 ＋ A 未登出 ADM ＋ B 已登入 ADM」；
  最常見的形狀（**同一個人**的瀏覽器留著一份未清的 credential、沒有第二個登入者）它一點也擋不到。

**② 為什麼成立**：credential 是伺服端核發的 opaque 值、與工作階段一對一，
而 session 列上就有 `actor_admin_id`。持有它 ⇒ 就是這個工作階段。
`DelegationContext.operator_admin_id` 本來就取自 session 快照而非 ADM session，
稽核的 actor 也由 account-service 依 `session_id` 推導 ⇒ **稽核記在誰頭上，一個字都不變**。

### 誠實記帳：少掉的是什麼

舊設計擋得住一個具體情境——**同一台電腦上「ADM 的登入者換了人，而 operation cookie 沒清」**。
跨 host 之後這個錯配**仍然可能發生**（www 上遺留的 credential 與 admin host 上此刻是誰登入完全無關），
只是**再也沒有第二個事實可以拿來察覺它**。
⇒ 這道防線不是「攻擊面消失了」而是**判定依據消失了**，本條是實實在在的弱化。

接手的是三道既有機制，各自的邊界必須看清楚：
**(i)** ADM 登出連動撤銷——**它只在 A 真的登出時成立**；
**(ii)** idle 900 ／ hard 1800——遺留的 credential 最長 30 分鐘、無人操作 15 分鐘即失效；
**(iii)** 撤銷端點（治理側主動止血）。
**三者都不是即時攔截**：在「A 沒登出、且落在窗口內」的那一段，同一台電腦的第二個人可以無聲接手，
而稽核會記在 A 頭上。**不得**把這三道寫成「所以更安全」。

### 四項配套（缺一即為漏洞或根本做不出來）

- **(a)** 授權鏈第 1 項分成兩組身分來源，第 4 項標記為本期不適用且**編號一律不重排**；
- **(b)** `/api/v1/admin/**` 這個前綴從此**不再蘊含 `requireAdmin`** ⇒ boot 斷言新增具名白名單一條，
  否則日後有人把一支治理端點掛到 credential-only 群組上，就是一支沒有任何身分要求的治理端點；
- **(c)** 授權判定由四項收成三項、`AdminDelegationContext` **移除** `ActorAdminID`——
  留著一個不參與判定的欄位就是 ③ 那種「看起來有比對」的假象；
- **(d)** 對應的業務碼保留碼位、本期無 emitter。

## 6. 資源樂觀鎖的載體與維護義務

**載體**：**body 的 `expectedVersion` 欄位**，不用 HTTP `If-Match`／`ETag`。
這是**物理限制不是偏好**：代行走 same-origin BFF，而該 BFF **完全不轉送任何瀏覽器 header**，
`If-Match` 送不到後端。

**維護義務落在三張表的每一條既有寫入路徑上**（而非改用 last-write-wins 或拿 `updated_at` 當版本）：

- **否決 last-write-wins**：直接放棄「不覆寫賣家較新的修改」這個對賣家的核心保證。
- **否決 `updated_at` 當版本**：DTO 時間戳截到秒，同秒內的兩次修改會互相失明——
  **比沒有樂觀鎖更糟**（它會給出一個看起來成立的保護）。

**這一條必須是 ADR 而不只是一張窮舉表的理由**：它的影響面跨 Java MyBatis-Plus 與 Go sqlc 兩種 ORM，
而**兩邊的失敗模式都是靜默的**——Java 的攔截器對 `@Update`／`LambdaUpdateWrapper`／`setSql`
不生效**且不報錯**，Go 側逐句手寫、漏了同樣不報錯。
⇒ 代價必須被登記成一個決策，而不是散在一張「今天有哪些」的表裡。

## 後果

- 代行相關的前端改動落在有真實買家流量的 repo 上，因此賣家本人路徑的回歸驗證是每一批的必要條件。
- `/api/v1/admin/**` 不再蘊含身分要求，boot 斷言的具名白名單成為安全邊界的一部分。
