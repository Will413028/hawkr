# Hawkr 幫找採購助手 MVP-A 的六項架構決策

| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-09-18（決策本身作成於 2026-08-07） |
| 影響範圍 | ai-service `internal/procurement/`、gateway 的 procurement 端點 |

規格本身見 `docs/詳細設計書/55-Hawkr 幫找採購助手（Procurement Assistant）詳細設計書.md`。
本檔只保存「為什麼選它、否決了什麼」。

## D1：下一題由誰決定 → 固定 slot ＋ 純函式選題，模型只負責文案

| 方案 | 代價 | 判定 |
|---|---|---|
| 全交模型 | 「不重問已知欄位」變成機率事件，且無法回歸測試 | 否決 |
| 每品類一套版本化題組 | 要先定義各品類題組，開工被產品端阻塞 | 否決 |
| **固定 slot ＋ 純函式選題** | 品類專屬欄位要後續增補 | **採用** |

## D2：模型呼叫是否經 adk-go → 單次結構化抽取直呼 genai

本模組的三個 LLM 職責都是單次、無工具選擇、無多輪推理，agent runtime 不提供價值。
且 adk-go 依 Go `reflect.Kind` 推導 output schema、**不看 json tag**，與 TSID（64-bit）
搭配已經有實例出錯。

既有買賣家小幫手維持 adk-go 不變——這是兩套用途，不統一。

## D3：執行狀態持久化層級 → run-level durable ＋ 快照恢復

| 方案 | 代價 | 判定 |
|---|---|---|
| 無持久化，斷線重跑 | 長任務斷線即白跑 | 否決 |
| **run-level durable ＋ 快照恢復** | 無法回放事件的確切順序 | **採用** |
| 逐事件 ledger ＋ cursor replay | 成本遠高於價值——它的價值在回放**不可逆動作**的順序，而 MVP-A 沒有不可逆動作（不寄信、不收款） | 延後 |

⚠️ 第三案是**加法**：出現不可逆動作時可以在第二案之上補，不需要拆除既有結構。

## D4：擁有者欄位命名 → `buyer_id`

Gateway 注入的是現任 buyer stint surrogate，**不是**登入 principal；
既有買家資料表（收藏、地址、訂閱）一律使用 `buyer_id`。見 44 號設計書。

## D5：候選比對策略 → 加權評分 ＋ 回報命中事實

三條件嚴格 AND 在真實資料上只要缺一個條件的字面提及，整筆候選就消失，
而且回空時無法說明原因。加權評分同時滿足產品端對「可驗證配對事實」的要求。

## D6：無法驗證的候選條件如何呈現 → 標示「需向賣家確認」

應用層對已取回分頁做二次過濾，**只能過濾已取回的那一頁**，會靜默漏掉符合條件但不在該頁的候選
——錯誤不可見且無法察覺。候選本來就不是供貨承諾，誠實標示為正解。

⚠️ 重新評估條件：平台商品資料補上「可否配送至指定城市」與「庫存量」兩個維度時，
這兩項可以改為伺服器端篩選。
