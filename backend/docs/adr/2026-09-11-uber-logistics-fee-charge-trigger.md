# Uber 物流服務費的收費時點（Charge Trigger）

| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-09-11 |
| 影響範圍 | payment-service 物流服務費收費時點 |

- **脈絡**：`2026-09-11-uber-commerce-model-seller-direct.md` 定案後，線 B 的應收「什麼時候成立」沒有規則。
  Uber 生命週期有四個可觀測時點：建立配送成功 → 正式接單（`pickup`）→
  取件完成（`pickup_complete`）→ 送達（`delivered`）。
  任務書第 17 節逐字要求**本次不可自行猜**。
- **決定：D —— 配送送達完成時，賣家物流服務費的應收才成立。**
  選項為 A 建單成功／B Uber 接單／C 取件完成／**D 送達完成**（四案的代價評估見下表）。
- **後果**：
  1. 🔴 **不需要事後退還流程**（A/B/C 三案都要配一套）——這是本案最大的節省。
  2. 🔴 **所有「沒送到」的情境自然不收**，因此 `2026-09-11-responsibility-based-cost-attribution.md` 的矩陣可以用一條規則寫完。
  3. **取消情境的 Uber 費用（線 C 的取消費／等待費／退回費）**：
     依責任成因歸屬，不依費用名稱（見 `2026-09-11-responsibility-based-cost-attribution.md`）
     （賣家原因⇒賣家／買家原因⇒仍歸賣家物流成本且平台不得向買家二次收／
     平台或系統原因⇒平台且不得轉嫁賣家／provider 原因⇒先爭議後歸屬）。
     🔴 未送達 ⇒ **不向賣家收「配送服務費」**（本 ADR 的核心；
     那是服務價金，與額外成本是兩種錢）。
     配套防線仍是**賣家能力權限層**（取消率超標停用其即時配送），**不是回頭收配送服務費**；
     門檻值屬另一波。
  4. 觀測點不需新增：`delivered` 在我方已有現成落點（66 §7.1：→ 我方 `11`／訂單軸 `40` ＋ 發 `shipment.delivered`）。
- **已落實於**：66 基設 §2.2／§2.3／§4.2／§6.2；65 基設 §3 線 B ＋ §5.2；66 詳設 §11.2 **UP-11 已關閉**。
