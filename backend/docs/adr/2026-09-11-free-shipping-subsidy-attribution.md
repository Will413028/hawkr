# 免運／補貼的成本歸屬：賣家主辦、平台主辦、雙方共同是三件事

| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-09-11 |
| 影響範圍 | shipping-service 免運與補貼成本歸屬 |

- **脈絡**：`2026-09-11-logistics-amount-semantics-separation.md` 把金額拆開之後，還剩一個問題沒答：`buyer_shipping_charge = 0` 時，
  物流成本由誰吸收？既有模型的 `ShippingFeePayer` 只有 `BUYER(3101)`／`SELLER(3102)`
  ——它表達得出「賣家吸收」，**表達不出「平台吸收」，更表達不出「兩邊各吸收一部分」**。

## 選項

> **每案都要答「使用者看到的東西會不會變少」**——本 ADR 三案都不會，
> 但**成本落在誰身上不同** ⇒ 商務決策。

- **A：只有賣家主辦一種**（維持現況值域）— ❌ 否決：平台無法辦免運活動，而那是常規行銷手段。
- **B：三型態各自明確記錄** — ✅ **採用**。
- **C：只記一個「補貼總額」** — ❌ 否決：事後無法回答「這次活動平台花了多少、賣家花了多少」，
  而那正是行銷與財務都要看的數字；合成之後**再也拆不回來**。

## 決定：**B**

| 型態 | 買家配送費 | 物流商實際成本 | `seller_subsidy` | `platform_subsidy` | 賣家最終負擔 |
|---|---|---|---|---|---|
| 不免運 | 照收 | 照發生 | 0 | 0 | 全額 |
| **賣家主辦** | 可為 **0** | **照發生** | ＝買家原應付的配送費 | 0 | 🔴 **仍為全額**（平台**不**因買家端免運而吸收） |
| **平台主辦** | 可為 **0** | 照發生 | 0 | ＝平台明確補貼的金額 | **實際成本 − 平台補貼** |
| **雙方共同** | 可為 0 或部分 | 照發生 | 賣家那一份 | 平台那一份 | **實際成本 − 平台補貼** |

🔴 **資料模型必須能獨立表達六個量**（客戶逐字）：
`buyer_shipping_charge`／`provider_actual_cost`／`seller_logistics_charge`／
`seller_subsidy`／`platform_subsidy`／`reconciliation_adjustment`。
**不得只留單一 `shipping_fee`。**

## 後果

1. 🔴 **`buyer_shipping_charge` 永遠推導不出成本負擔者**——三型態的它都可能是 0。
   負擔者由**促銷／運費補貼政策**決定並記錄。
   ⚠️ 特別是：**平台主辦補貼時平台只負擔「明確的補貼金額」**，
   **不得因為買家配送費為 0 就推導平台全額吸收 Uber 成本**。
1b. 🔴 **`platform_subsidy` 與「平台原因造成的成本」是兩件事，不得混記**（`2026-09-11-responsibility-based-cost-attribution.md`）：
   前者是**商業促銷**（行銷費用／活動成效），後者是**平台或系統錯誤的成本責任**
   （損失賠付／事故成本）。合成一個數字之後，財務歸因與營運分析都會失真。
2. 🔴 **賣家補貼不影響線 B**：它改變的是「買家付多少」，不改變「賣家要付平台多少」。
3. **實作缺口（非決策缺口）**：`ShippingFeePayer` 需要平台側的表達，
   並新增 `seller_subsidy`／`platform_subsidy` 兩欄。連帶影響運費計算（21）、
   結帳金額快照（20）、帳務科目與對帳 ⇒ 另一波。
   **落地前平台主辦補貼只能人工處理，不得用賣家主辦免運的路徑冒充**（兩者買家配送費都是 0 而正解相反）。
