# 社群計數器走非同步 MQ delta，並保留一支收斂 reconciler

| 項目 | 值 |
|---|---|
| 狀態 | superseded by 2026-10-23-social-counts-in-stats-tables.md（social 搬進單體，計數改存 stats 表、trigger 同 transaction 維護；本檔保留歷史，現況讀新檔） |
| 日期 | 2026-09-18 |
| 影響範圍 | social-service 貼文／留言計數器、`hawkr.content` 的 `counter.delta` |

## 脈絡

貼文與留言的按讚數、留言數直接顯示在使用者面前。它們原本由同步 `Incr`／`Decr` 在主要寫入
路徑內維護；熱門內容上這條路徑會產生 row-lock 競爭——**使用者越多、內容越熱門，鎖競爭越嚴重，
剛好卡在最重要的那些內容上**。

《後端服務責任邊界規範》§七 禁止在 application code 建立 reconciliation job，
而社群計數器的收斂路徑看起來正是那個形狀，因此需要明確記錄它為什麼是例外。

## 考慮過的方案

| 方案 | 代價 | 判定 |
|---|---|---|
| **同步 `Incr`／`Decr`（原狀）** | 正確性最好，但熱門內容 row-lock 競爭 | ❌ |
| **`TxManager` 把 `Incr`／`Decr` 包進主要寫入的同一個 transaction** | 解決正確性，**解決不了 row-lock 競爭**——競爭正是它要避免的東西 | ❌ 明確否決 |
| **DB trigger 維護計數** | 把業務邏輯藏進 DB，難測、難觀測、難隨服務一起部署 | ❌ |
| **即時 `COUNT(*)`** | 無漂移，但每次讀取都掃描；熱門貼文的讀取量遠大於寫入量 | ❌ |
| **非同步 MQ delta ＋ 一支收斂 reconciler** | 計數器有短暫落後；`counter.delta` **非冪等**（at-least-once 重送會重複計數），需要一條收斂路徑 | ✅ **採用** |

## 決策

計數器改由 `counter.delta` 事件非同步維護，並保留一支走共用 `outbox.Scheduler` 的
收斂工作（**無 task 表、無獨立 runner、無獨立 `@Scheduled`**）。

它是《後端服務責任邊界規範》§七 的合法例外，依據是該規範的判定準則
——「這個基礎設施存在的目的是**業務正確性**還是**資料完整性監測**？」
計數器直接顯示給使用者看，MQ 掉一則就是使用者看到錯的數字，屬前者。

## 後果

- 接受計數器的短暫落後。
- **這支收斂工作是該架構唯一的收斂路徑，直接刪掉會真的丟計數。**
  它與 §八 刪掉的 `HashtagCounterReconciliationJob` 不同：後者被刪是因為
  「同事務 row-lock 已是真實來源」⇒ 那支 job 是多餘的；這裡的前提不成立。
- **撤銷條件**：若計數器改回同事務維護，這支收斂工作立刻變成多餘，照 §八 前例刪除。
