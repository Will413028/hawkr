## 1. 賣家在代行期間被停權／關店／刪帳號時，進行中的工作階段立即失效

**考慮過**：① 繼續有效至自然到期，僅靠 preflight 擋新建 ＋ 人工撤銷止血
② **立即失效**：每次請求重驗店家狀態，命中即拒絕並轉終態 ③ 只擋寫入、放行唯讀
④ **事件驅動撤銷**：account-service 新增 consumer 消費既有的 `seller.suspended`／`seller.deleted`

**決策：② 立即失效（安全優先）。**

停權是**即時的風險控制**，而觸發它的原因往往正是這家店出了問題；讓一個已建立的代行工作階段
繼續寫入，等於讓風險控制對「正在進行中的操作」失效——事後沒有任何說法能解釋為什麼
治理按下停權之後，平台自己的帳號仍在以該店名義改商品、改店面、發貼文。

**代價與收益的量級不對稱**：曝險窗口上限是 30 分鐘，選 ② 的代價是「一次操作被中斷、
未儲存內容遺失」，選 ① 的代價是「停權後仍有寫入成立且無法解釋」。
窗口愈長，① 的「等它自然到期」愈不可接受，② 的「一次操作被中斷」則與窗口長度無關。

**否決 ①**：它把「有沒有出事」交給運氣（要沒人正在代行才安全），
而人工撤銷需要有人**知道**當下有一個進行中的工作階段——治理端按停權時看不到這件事。
安全機制不能建立在時機上。

**否決 ③**：裁決字面是「**工作階段**立即失效」不是「寫入立即失效」；
且它留下最不該留的窗口——代行者寫不了卻仍讀得到一家**已刪除**店家的訂單收件資訊
（`orders.read` 是九個 capability 之一），與 PII 最小化直接衝突。

**否決 ④（事件驅動撤銷）**：**它不是被「禁補償流程」擋掉的**——
`seller.suspended`／`seller.deleted` 今天就存在、由 seller-service 走 outbox 保必達發布，
而「Outbox 保 MQ 必發」正是責任邊界規範明列的合法例外。它被否決的理由是**覆蓋面與時效**：

- **(a) 覆蓋面不足**——要擋三件事，而**關店（`status='closed'`）沒有任何事件**；
  靠事件就得先新造一個 `seller.closed`，於是「這家店能不能被代行」多出第二個答案來源，
  與「判定只有一份」直接衝突。
- **(b) 時效**——MQ 有投遞與消費落後，而 fail-closed 要求的是「**下一次請求就拒絕**」，
  事件抵達前的那個窗口正是本決策要消滅的東西。

⇒ **④ 只能是 ② 的補件，不能是替代品。** 補件的價值是實的（操作者停手不動時工作區
不會自動切成阻擋畫面），本期不做的理由是它換到的只有「UI 早一點更新」，
而寫入面已由 ② 完全擋住；**重開本題的觸發條件**＝出現第一起
「停權後代行工作區仍顯示進行中」的客訴或內控指正，屆時先驗 (a) 的關店事件缺口。

**否決「由治理端在停權當下推送撤銷」**：那是補償流程的形狀（要追殺 session、
要處理推送失敗與重試）。本設計所有終止語意都建立在「被終止方下一次動作時自己撞上」，
② 沿用同一條路徑、零新機制。

**否決「命中時只回錯誤、不轉終態」**：拒絕當次請求解決不了另外兩件事——
工作區仍顯示「進行中」，以及該工作階段先前建立的排程到點仍會發。兩者都只有終態轉換才消得掉。

> ⚠️ **最容易做錯的一點**：「確知不可代行」與「問不到答案」必須分開處置。
> seller-service 逾時／不可用時一律 fail-closed 拒絕本次請求，但**不得轉終態**——
> 轉終態不可逆，而上游抖動是暫時的；混為一談會讓一次 30 秒的 seller-service 不可用
> 把當下所有進行中的工作階段永久打死。

### 誠實記帳：代價確實存在且本期無緩解

代行者可能在填到一半時被中斷，未儲存內容確實會遺失，且終態不可回到 `active`。
**不得寫成「緩解＝前端保留本地草稿，與版本衝突的 409 處置是同一套既有慣例」**
——那兩個機制都不存在，工作區是從零新建的。
**這不翻案本決策**（量級論證本身成立：不可解釋的寫入 ≫ 一次操作被中斷），
但論證必須誠實。仍然是 UX 代價不是資料損失：被中斷的那一筆寫入從未成立，
稽核上也沒有半成品。

## 2. 賣家通知的投遞通道：只做站內訊息

**考慮過**：① 站內訊息 ＋ Email ② 只做站內訊息（inbox ＋ App 推播）
③ 本案自建 Email 通道當前置工作

**決策：② 只做站內訊息。**

**否決 ①**：決策當下平台沒有任何 Email 寄送能力，① 是一個**做不出來的承諾**——
實作者照著做只會發現無處可填模板；而承諾內容會出現在稽核 UI 與對外說明上，
寫錯的成本是對賣家講了不成立的話。
⚠️ **這個前提後來改變了**：`pkg/mail`（含 resend provider）已存在，notification-service 亦有消費者。
⇒ 「做不出來」不再成立，但通知模板表仍沒有 channel 維度（`UNIQUE (event_type, target_user_type)`
在 schema 上擋掉同事件的第二列）。**重開本題的前提是先為 `notification_templates` 加 channel 維度**，
那屬 12／13 號設計書的範圍。

**否決 ③**：建 Email 通道是平台級基礎設施（寄信服務選型、SPF／DKIM／DMARC、
退信與退訂、通知模板加 channel 維度、12／13 號改版），工作量與風險都遠大於本案，
綁成前置＝本案無限期不能上線。

⇒ **本條改變的是承諾內容不是實作細節**：全書措辭一律「站內訊息」，
禁止再出現「站內訊息 ＋ Email」。

## 3. 訂單完整收件資訊的揭露方式

**考慮過**：① 詳情 DTO 直接帶完整地址與手機 ② 遮罩為預設，完整值走獨立端點且落稽核

**決策：② 獨立端點 ＋ 落稽核。**

UI 同時出現「遮罩手機」與「查看完整地址」動作，代表揭露是一個**動作**而不是一個欄位。
① 會讓每一次訂單列表請求都把全店買家的個資送進前端，違反 API 設計規範對回應欄位
deny-by-default 的要求。② 讓「誰在什麼時候看了誰的地址」成為可查的稽核事實。

⚠️ **作用域限制（本決策的收益只在代行工作區的訂單路徑內成立）**：
同一個 admin 帳號走既有治理路徑就能取得未遮罩的收件人姓名／手機／完整地址，
且該路徑沒有任何稽核。⇒ 對**刻意避開稽核**的操作者，② 的稽核收益為零；
代行稽核表的空白**不等於**沒有人看過那筆地址。此洞早於本案、屬治理面，本案不順手修。

**這條作用域同時是「本期揭露不通知賣家」日後改動的前提**：
若把代行揭露改成「要通知賣家」而既有 admin 路徑仍無稽核無通知，會造出**反向誘因**
——理性的操作者改走無稽核那條路。⇒ 要改必須與既有路徑的稽核同波，不可單獨施行。

## 4. `seller_request` 是管理員的記錄，不是委託證據

本平台沒有工單系統，賣家也沒有任何向平台提出請求並留痕的管道
（IM 的會話只有買賣家兩方，無 admin／platform 維度）。
⇒ `reason_code='seller_request'` 是 **admin 的自我宣告**，
`case_reference` 是 **admin 自填的自由文字**，沒有任何獨立於 admin 的證據存在。

**定版**：label 由「賣家委託」改為「**賣家請求（管理員記錄）**」，
preflight 下發值、稽核 UI、結束摘要與對外說明一致表述。
**不得**再出現「賣家委託的證據就是 `case_reference` 指向的工單」這類敘述——那個工單不存在。

**為什麼要改**：稽核表的價值全部建立在「上面寫的每一件事都成立」。
一個叫「賣家委託」的 `reason_code`，在爭議發生時會被當成賣家授權過的證據，
而它從頭到尾只是操作者在下拉選單裡選的一個值。**這是誠實性缺陷，不是功能缺陷。**

**事前確認被否決**（推通知給賣家、賣家按確認才能建 session）：
代行的典型情境正是「賣家沒空／不會操作」，要求他即時上線確認等於在最需要代行的情境下
讓代行不可用。

## 5. 代行不對治理狀態加特判

**Q1：代行的 `products.publish` 要不要對治理狀態加特判？答案唯一：不要。**
代行沿用 product-service 既有上架規則，不多不少。加了特判就造出
「代行者不能上架、賣家本人可以」的反轉。

支撐事實三條：

1. **賣家本人今天就撤銷得掉**：`validateSellerStatusTransition` 允許 `INACTIVE → ACTIVE`，
   店家未停權時一鍵重新上架。
2. **「治理強制下架的商品」這個類別在資料層根本不存在**：沒有 per-product 的治理處分，
   唯一的 per-product admin 動作端點 body 只有一個 `status` 欄位（無原因、無案件編號、無稽核落點）
   ⇒ 落庫結果與賣家自行下架在 DB 上完全無法區分。要在代行側加特判，連判準所需的資料都不存在。
3. **日後補上的治理規則，代行會自動繼承**——這是「既有 RPC 加 `DelegationContext`」
   那個決策今天付出的紅利：業務規則只有一份實作。

> ⚠️ 樂觀鎖在這裡的作用是「讓代行者**看得見**治理改過」，不是「**阻止**代行者改回去」。
> 混為一談會讓人以為「做完樂觀鎖就等於關掉這一題」，實際上沒有。

「平台強制下架的商品該不該能被上架回去」是業務裁決，但**與代行無關**（賣家本人今天就做得到），
歸 32 號／02 號。

## 6. 貼文在等待排程期間被刪除或被強制下架，排程一律不執行

| 項 | 定版 ／ 理由 |
|---|---|
| **發不發** | **不發**。賣家自刪與平台強制下架**同等處理**——既有程式碼對兩欄的排序是 `deleted_at` ≻ `hidden_at`，下架都要擋，刪除沒有理由不擋 |
| **記成什麼** | **兩個新終態值**：`cancelled_by_deletion`／`cancelled_by_governance`。這一題答案與上一題**相反**：`hidden_at` 可被 `RestorePost` 清成 NULL，只記一個籠統的 `cancelled` 會讓事後反查在申訴成功之後回答錯的原因 |
| **做在哪一側** | **讀時防禦（worker 端）**，不做寫時收斂。寫時收斂要改三條與代行無關的既有路徑，**且未來新增第 4 條刪除／下架路徑必然漏且不報錯**；讀時防禦自動涵蓋 |
| **通知賣家嗎** | **不通知、不寫代行稽核**，與既有 `cancelled_by_revocation` 對齊；可解釋性由指標承擔。若日後改為要通知，**三種取消必須一起做** |
| **被否決：只擋 `hidden_at`、放行 `deleted_at`** | 它與既有語意方向相反，會造出「治理下架擋得住、賣家自刪擋不住」的狀態機；其原始理由「賣家自刪視為放棄」邏輯不通——放棄的是這則貼文，不是「反對排程但同意內容」 |
| **被否決：只加 claim 述詞、不加收斂語句** | 被擋的列會停在 `pending` 每個 tick 被重撈、CAS 恆 `rows=0`（每列 2,880 次／日），最後轉成 `expired` ⇒ 告警為一個完全預期的情形而響。省下一句 SQL，付出一條告警的可信度 |

**與停權決策的交叉點**：刪帳號會同時觸發兩者，**停權與關店則只觸發停權那一道**
——`seller.suspended`／`seller.closed` 不會去動 `cms_post` 的任何欄位。
⇒ **只做貼文這一道不做店家那一道，停權中的店家排程照發。** 兩條路徑都要留著，
它們不是同一件事的兩種寫法：前者看的是**這則貼文**（在 worker 的 SQL 內判定，不需跨服務呼叫），
後者看的是**這家店**（在稽核 intent 內判定）。

## 7. 批次 `items` 上限不是技術阻擋項

批次語意下 Gateway 的跳數與 `items` 筆數**無關**，因此上限 50 不構成時間問題。

| 被否決的選項 | 理由 |
|---|---|
| 縮 `items` 到 5–8 | **不可行**：即使在逐項語意下也一樣超出預算；且 5–8 **低於**列表頁大小 ⇒「全選本頁 → 下架」這個最自然的手勢永遠失敗。若仍想要更小的上限，那是產品體驗題，不是技術必要——且下限應 ≥ 列表頁大小 |
| 放寬前端逾時到 60s | 它治的是症狀不是病：把逾時放寬等於接受一支請求佔住 60 秒，期間 Gateway goroutine 與兩個服務的連線全被佔用。⇒ 只當**餘裕**，不當解法 |
| 批次改非同步（202 ＋ job） | **正確的否決理由是成本與責任邊界**：要做對就得有 job 表 ＋ 租約 worker ＋ 查詢端點 ＋ 輪詢 UI ＋ 一組新業務碼，而它要解的問題是「N 次 UPDATE 花了幾秒」。其變體「Gateway 背景 goroutine ＋ 前端輪詢稽核表」**比同步更糟**：那個 goroutine 沒有租約、沒有 retry owner，rolling deploy 或 OOM 一殺，剩餘項永遠不會執行、稽核列永遠停在 `PENDING` |

⚠️ **不得以「前端明確拒絕 202」為否決理由**——該約束的出處只約束
`DELETE /api/admin/delegated-operations/current`，與資源 mutation 端點無關。

「一次批次下架最多幾件是想要的操作體驗」是產品體驗題，不阻擋實作。

## 後果

- 「這家店能不能被代行」的判定規則只有一份，preflight／Gateway 授權鏈／排程稽核 intent 三處共用。
- 通知承諾的措辭是對外可見的，改動它等於改動對賣家的承諾。

## 修訂：賣家通知加上 email（2026-10-05，Will）

脈絡：§2 否決 email 的前提是平台沒有寄信能力、模板表沒有 channel 維度。`pkg/mail` 已存在；ADR `2026-10-05-notification-module.md` 把通知型別改成在程式碼定義，每個型別宣告自己的渠道，`notification_templates` 退場，重開本題的前提成立。

決策：賣家通知是站內訊息，帳號有已驗證 email 時依通知型別另外寄送；寄送清單與平台工作見該 ADR 決策 8，代行完成屬於安全類、會寄 email。「不得對賣家承諾做不到的事」仍成立：用 LINE 登入的帳號可能沒有 email，對外措辭改成「站內訊息；有 email 時另外寄送」，不寫無條件的「站內訊息＋Email」。`pkg/mail` 現有唯一真正寄信的 provider 是舊公司的 Resend 帳號，不得使用，所以新措辭在 A8 的寄信平台工作（新的寄信服務帳號與寄件網域）完成後才生效，之前維持「站內訊息」。原決策段保留歷史。
