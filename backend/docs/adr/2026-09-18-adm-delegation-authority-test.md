# 代行營運：規則權威歸屬的判定程序（Authority Test）

| 項目 | 值 |
|---|---|
| 狀態 | accepted；遷移計畫 A2（2026-09-27）不影響：判斷方法與服務落在哪裡無關 |
| 日期 | 2026-09-18（決策內容成形於 2026-08-09／2026-08-10） |
| 影響範圍 | ADM 代行營運（56 號詳細設計書）的全部規則取值；跨 `backend-payuni`／`hawkr-admin`／`hawkr-website` |

## 脈絡

代行營運的規則有三個來源互相衝突：**產品需求（ADM 代行營運 v2.0 及其 UI mockup）**、
**已上 dev 的前端程式碼**、**後端設計**。三者不一致時沒有「誰天生優先」的規則，
而實務上最常見的誤判是把「誰已經寫了」當成「誰說了算」。

需要一組**可機械複查**的判定步驟，讓每一條規則的權威歸屬都得到唯一答案，
並且讓「前端已經寫死」這種說法不能再當成理由。

## 決策

建立五問判定程序（Q1→Q4 依序問、先命中先定案；Q5 最後再跑一次、命中即覆寫前面的結論），
並要求把三個名詞永久分開：

| 名詞 | 它回答的問題 |
|---|---|
| **權威** | 這條規則的**值**應該是什麼？ |
| **現況** | 目前誰實作了它、實作成什麼樣？ |
| **成本** | 要改它，誰得動手、動幾支檔、要不要同波發布？ |

**「前端已經寫了」只回答現況與成本，從不回答權威。**
反向也成立：**權威在後端 ≠ 前端不用改**——權威決定「值是什麼」，成本決定「誰動手」，兩者正交。

判定的產物是**一句判斷**，合法句型只有三種：

- 「此項屬編碼／傳輸／節奏細節，前端有權威」（Q2／Q3 命中）
- 「本書定版為 V，理由是（不引用前端的業務推導）；前端現況為 W」（Q1／Q4／Q5 命中）
- 「此項撞某條工程約束，具名登記為例外，讓步理由是…，此例外不擴散到…」（Q2 陷阱）

一律不接受：「因為前端已寫死，所以…」「前端不送，所以不做」「這是本書的輸入」。

### 五問各問什麼

**Q1 語意測試** —— 這條規則改了值，**後端的接受集合或稽核事實會不會跟著變**？
*機械驗算*：想像一個**只用 curl 直打 Gateway、完全不經 admin BFF** 的 client，
問「這條規則對它還要不要成立」。要 ⇒ Q1 命中 ⇒ **後端權威**。

**Q2 編碼測試** —— 它是不是同一個事實的**另一種寫法**（大小寫、格式、序列化形狀）？
*機械驗算*：寫出這條規則的兩種寫法，問「後端能不能寫一個**雙向轉換函式**，
讓兩種寫法在業務上完全等價」。能 ⇒ Q2 命中 ⇒ **前端權威**
（`ACTIVE` ⇄ `active` 可以；`上限 100` ⇄ `上限 200` 不行）。
*為什麼排在 Q1 之後*：先問 Q2 會把值域上限這類**語意**規則誤判成格式規則。

> **Q2 的陷阱**：若該編碼方式**同時是本專案某條規範的管轄對象**
> （envelope 形狀、數字對外一律 string、CodeMeta SSOT、分頁 key 與 Swagger 契約），
> 它就**不再只是編碼** —— 此時要嘛具名登記為例外並寫出讓步理由，
> 要嘛判定「Q2 命中但規範優先」，同樣要寫出理由。

**Q3 節奏測試** —— 它是不是**在瀏覽器那一端執行**的時序事實（輪詢間隔、逾時、重試、渲染與否）？
*機械驗算*：問「這個值是在瀏覽器那一端執行的嗎？後端能不能強制它？」
後端只能**被動承受**、無法強制 ⇒ Q3 命中 ⇒ **前端權威**。
*為什麼排在 Q2 之後*：節奏事實常常長得像業務規則，必須先排除 Q1 與 Q2 才判得準。

**Q4 預設值：以上皆非 ⇒ 後端權威。**
*機械驗算*：**把前端那份實作整個刪掉**，問「這條規則還成立嗎」。
不成立 ⇒ 後端缺一份獨立實作，必須補；同時檢查文件裡這條規則的 SSOT 指向哪裡，
**指向前端檔案即為缺陷**。

### Q5 為什麼凌駕 Q2／Q3

Q2／Q3 判給前端的是「怎麼寫」與「何時發」；一條**拒絕**規則若把權威放在前端，
等於把「能不能做」交給請求方自己保管。機械驗算：**把前端那份實作整個刪掉**，
問「這條規則還成立嗎」——不成立 ⇒ 後端缺一份獨立實作，必須補。

## 被否決的推理形狀（三種，收工前逐段掃自己寫的理由）

| # | 形狀 | 怎麼認出來 | 正解 |
|---|---|---|---|
| ① | **後果當理由** | 整句只說「不這樣做前端會 502／入口會消失／功能會死」 | 補一句「而且後端自己也要這個值，因為…」；補不出來代表它真的落在 Q2／Q3，那就明寫「此項屬編碼／節奏細節，前端有權威」 |
| ② | **循環論證** | 「因為前端不送 X，所以 X 永遠是 NULL，所以不做 X」 | X 會是 NULL 正是因為前端不送。要問的是「業務上需不需要 X」 |
| ③ | **既成事實化** | 用「已凍結」「已寫死」「是本書的輸入」描述一條 Q1 命中的規則 | 改成「已實作，改動成本為 N 支檔；本設計定版為 V，理由是…」 |

## 成本也要有依據：部署狀態不是實作完整度

權威判對了、成本估錯了，結論一樣是錯的。曾以「前端已上 dev、契約已寫死」為由
把 11 張高擬真 mockup 判成「殘留／舊版本／參考」，而那份工作區實際是 140 行的殼
（一個 capability matrix ＋ 四個區塊標題，零內容 UI、零表單、零資料呼叫），
且該 repo 沒有任何賣家管理端頁面。

**「已部署」只證明它被 build 過，不證明它承載了任何契約。**

估成本時逐條跑：

| 問題 | 怎麼查 | 為什麼是這個問題 |
|---|---|---|
| 它有多少行、其中多少是資料流？ | `wc -l` ＋ 看它有沒有呼叫任何 API | 純結構宣告的檔案改起來近乎免費 |
| 它有沒有**消費者**？ | 有沒有測試鎖住它、有沒有別的模組 import 它 | 沒有消費者的程式碼不是契約，是佔位 |
| 它鎖住的是**契約**還是**佔位**？ | 契約的判準是「後端改了它會壞」；佔位的判準是「後端改了它毫無反應」 | 只有前者才構成同波成本 |

這一條與形狀③ 是同一個病的兩面：形狀③ 防的是「把 Q1 規則說成已凍結」，
本節防的是「把一個空殼說成已實作」。**兩者都會讓真正該做的改動被一句「成本太高」擋掉，
而那個成本是虛構的。**

## 三方裁決的個案結論（K1–K9）

判定程序套在九個具體爭點上的結果。**規格值本身以 56 號詳細設計書為準**，
本節只保存「為什麼是這個值」與「否決了什麼」。

| # | 判準 | 爭點 | 裁決理由 ／ 被否決的是什麼 |
|---|---|---|---|
| K1 | Q1 | 操作理由放工作階段層級還是每筆 mutation | **下沉到每筆 mutation**。稽核要回答的是「這一筆改動為什麼」，不是「這次登入為什麼」——一個工作階段可能改十筆不相干的東西，單一 300 字理由對其中任何一筆都不成立；下沉之後理由與 before／after 差異才一一對應。mockup 的 300 字 textarea 作廢 |
| K2 | Q1 ＋ Q5 | TTL 可否由操作者在下拉選 | **可選（只能選更短）**。原先的否決理由是「讓操作者自選時長等於讓被稽核的人決定自己被稽核的窗口有多長」——但在伺服端硬夾上限之下操作者能選的只有更短，而更短嚴格更安全 ⇒ 該風險論證對「可選」本來就不成立，它成立的對象是「可選**更長**」，而那條路由 `min()` ＋ DB CHECK 兩道擋死 |
| K3 | Q1 | 做不做 idle expiry | **做**。原先以時間尺度不等式「`idle 門檻 ≥ hard 上限` ⇒ idle 永不先觸發」否決，其唯一輸入是 `hard 上限 = 900`；hard 改為 1800 之後不等式當場破。詳見 `2026-09-18-adm-delegation-session-lifecycle.md` |
| K4 | Q1 | `case_reference` 上限 100 還是 200 | **200**。案件編號來自外部工單系統，上限收緊只會讓真實工單號塞不進來，而放寬對後端沒有代價。前端那個 200 是通用字串安全函式的值，不是案件編號的業務規則，兩者只是恰好一致 |
| K5 | Q1 ＋ Q5 | capability 可否由操作者勾選 | **唯讀展示**。capability 是伺服器對「這個管理員對這家店能做什麼」的裁決結果，讓被授權者自己勾選等於把授權決定權交出去；勾選 UI 還會把「我沒勾」與「後端不給」混成同一個畫面，出事時分不出是誤操作還是授權缺陷 |
| K6 | Q2 → 陷阱（撞 CodeMeta SSOT，選擇不讓步） | 稽核快照存字串狀態還是數字碼 | **存數字碼**。狀態字面值一旦寫進稽核列就成了第二份狀態定義，日後改名時歷史列與現行 enum 永久對不上，而稽核的價值正是「三個月後還讀得懂」 |
| K7 | 形式＝Q2、值域＝Q1 | capability 命名形式與值域 | **形式跟隨前端（小寫點號式）、值域由後端定版為封閉九值**。值域是跨 repo 硬契約，兩套命名同時流通時任何一次同步遺漏都是靜默失效而不是編譯錯；命名形式跟隨已上 dev 的那份，是為了讓同波發布只需要改值域、不需要改形，把破壞面縮到最小 |
| K8 | 渲染＝Q3、模組集合＝Q1 | 未開放的模組渲不渲染 | **渲染集合 ⊋ 可操作集合**。詳見 `2026-09-18-adm-delegation-workspace-host.md` |
| K9 | 行為＝Q1、文案與位置＝Q3 | 工作區側欄「登出」的語意 | **＝結束本次代行，不得呼叫 ADM 登出端點**。(a) 代行工作區沒有第二個登入態可以登出——actor 始終是 ADM 管理員，沒有賣家 session；(b) 接到 ADM 登出會污染稽核的 `revoke_reason` 判讀（ADM 登出會連帶把該 actor 名下所有 active 工作階段以 `admin_logout` 撤銷） |

## 後果

- §3.1／§3.4 的每一列都必須填得出判準編號，讓分類可被機械複查。
- 任何以「前端已寫死／已上 dev／改動成本高」為由做出的裁決，都必須附上成本三問的答案。
  答不出來就不是成本論證，是印象。
