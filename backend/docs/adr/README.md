# ADR（架構決策記錄）· 總覽

> **ADR 回答的唯一問題：`WHY THIS DESIGN` / `WHY NOT THE ALTERNATIVES`。**
>
> 責任劃分 SSOT：`docs/開發規範/設計文件治理規範.md` §4。

## 這個資料夾裝什麼

- alternatives（考慮過哪些方案）
- tradeoff（各自的代價）
- decision rationale（為什麼選這個）
- 被否決的方案與否決理由
- 長期必須保存的重大技術裁決

## 不裝什麼

| 不裝 | 歸宿 |
|---|---|
| 逐欄規格、端點簽章、狀態值域 | 詳細設計書 |
| 系統目的、高階架構、Non-Goal | 基本設計書 |
| 做到哪了、誰在做 | Issue |
| 這次改了什麼、驗證證據 | PR |

## 什麼時候要開一份 ADR

判準：**這個決策被推翻的代價很高，且未來會有人問「為什麼不那樣做」。**

只影響一次實作的小取捨**不開** ADR——寫在 PR 描述裡即可。開一份沒有人會回頭看的
ADR，只是把雜訊搬到另一個資料夾。

## 慣例

- 檔名：`YYYY-MM-DD-<kebab-slug>.md`
- 依狀態決定怎麼改（Nygard 的 ADR 原文、adr-tools、MADR 的 status 流程）：
  - **proposed**（還沒經決定）：直接改，不留修訂段。
  - **accepted**：**結論不改**（決策是已經發生的事實）。小幅調整在文末加 `## 修訂：<主題>（YYYY-MM-DD，誰決定）`，
    寫脈絡與新的決策，註明「原決策段保留歷史」；核心決定被推翻時**新增**一份 ADR，並在舊檔頂端標 `superseded by <新檔名>`。
  - 同一份 ADR 的修訂超過 3 段時，寫一份整合後的新 ADR 取代它（舊檔標 `superseded by`），讓讀者只讀一份就知道現況。
- 詳細設計書可以寫 `參照 ADR-xxx`，但**不得複製 rationale**——
  複製必然漂移，而漂移的那一份不會告訴讀者它漂了。

## 建議骨架

```markdown
# <決策標題>

| 項目 | 值 |
|---|---|
| 狀態 | proposed / accepted / superseded by <檔名> |
| 日期 | YYYY-MM-DD |
| 影響範圍 | <服務 / 契約> |

## 脈絡
（什麼問題逼出這個決策；當時不可動的約束。）

約束逐條標來源：
- 外部：<約束>（法規、第三方合約、線上使用者或資料、期限）
- 繼承：<約束>（來自現有實作、公司時期的規範或先前的決策）；現在仍成立的理由：<…>
  不再成立的繼承約束直接拿掉，不遵守。

## 考慮過的方案
| 方案 | 代價 | 判定 |
|---|---|---|
| 基準：<同樣條件下、假設還沒有程式碼時的業界標準做法>（附來源） | | |

必含「基準」這一列。否決它要寫具體理由，「現有程式不是這樣做」只有在改寫成本是外部約束時才算理由。

## 決策
（選了什麼，一句話。）

## 後果
（接受了什麼代價；什麼條件成立時應該重新評估。）
```
