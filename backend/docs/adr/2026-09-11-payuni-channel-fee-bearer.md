# PayUni 代理商收付通道交易手續費的經濟負擔方

| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-09-11 |
| 影響範圍 | payment-service 收付通道手續費 |

- **最終規則（一句話）**：
  > 🔴 **因平台向賣家收取 Uber 物流費而產生的 PayUni `agent_fee` 實際交易手續費，
  > 由賣家負擔。**
- **理由**：Uber 配送是**賣家使用的物流服務**。平台不應因為**替賣家收取物流費**
  而長期吸收該筆第三方收款成本。
- **歷程（寫下來避免下一個人以為它還開著）**：同日曾一度選 B，
  其後客戶一度指示列回待決（理由：成本模型已拆得更細），
  依「Default to Decision, not Default to Pending」正式收斂為**由賣家負擔**。

## 🔴 即使都由賣家負擔，也**不得記成一個數字**

```
❌ 錯：uber_cost = 121.2

✅ 對：Uber Provider Actual Cost = 120
      PayUni Collection Fee     = 1.2
```

**為什麼**：兩者是**不同來源的成本**，對帳時要分別對到不同的對象——
`120` 要對得上 Uber 的月帳單，`1.2` 要對得上 PayUni 的收付紀錄。
合成之後**兩邊都對不起來**，而且再也拆不回來。

## 🔴 不得把「1%」硬寫成商業常數

PayUni 文件曾提及 `agent_fee` 的相關費用機制，但以下**全部**必須由
**Uber Scoped Review** 依官方文件、sandbox 與正式契約驗證：

| 待查證 | 為什麼不能猜 |
|---|---|
| 精確費率 | 契約可能與公開文件不同 |
| 扣費時點 | 影響應收與實收的時間差 |
| gross／net 計算方向 | 決定送出金額要不要加回 |
| 手續費是否另扣 | 影響是否需要 gross-up |
| `agent_fee_query` 回傳的**實際** Fee | 這才是記帳依據 |
| 合約是否可能不同 | 同上 |

⇒ **本 ADR 只定「實際發生的收款成本由賣家負擔」這個商業原則**，
🔴 **不定計算方式**。實作時**一律以 `agent_fee_query` 回來的實際金額記帳**，
**不得用任何預估值（含 1%）冒充實際值**。

## 後果

1. **賣家最終物流負擔的公式多一項**（見 `2026-09-11-logistics-cost-true-up.md` 的合併公式）。
2. 🔴 **需要兩個獨立的金額欄位**：物流商實際成本、收款通道實際手續費。
3. **對賣家的說明義務**：契約要寫明向賣家收取的金額包含代收手續費；
   賣家對帳頁要能解釋得出那一段。
4. ⚠️ **發票品項怎麼表達**（合為一項，或拆「物流服務費 ＋ 代收手續費」）
   **會影響稅務科目** ⇒ 屬 **External Accounting／Tax Verification**，不是 business decision。
