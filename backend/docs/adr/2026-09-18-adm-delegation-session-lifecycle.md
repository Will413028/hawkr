# 代行營運：工作階段的到期機制、併發範圍與識別碼

| 項目 | 值 |
|---|---|
| 狀態 | accepted；§6 superseded（遷移計畫 A2，2026-09-27）：它的前提是 `display_code` 由 TSID 的 `id` 推導，而 session ID 改成 IDENTITY（row-identity ADR 的過渡規則），給人看的編號也不再由 ID 推導（同一份 ADR 的 D1）。`display_code` 改由 CSPRNG 產生 13 碼，靠 UNIQUE 與 `ON CONFLICT DO NOTHING` 的重試保證不撞號（同一個 transaction 內不會觸發 25P02），對外格式與 `{13}` 的 CHECK 不變。§1–§5 仍有效，期限改成單體的常數（值同原本的預設） |
| 日期 | 2026-09-18（到期機制定版於 2026-08-10，取代 2026-08-09 的兩個前版） |
| 影響範圍 | account-service `delegated_operation_sessions`、Gateway 授權鏈、hawkr-admin 常數、hawkr-website 工作區 |

## 1. 到期機制：hard 1800 ＋ idle 900，兩者皆為讀取時推導

**考慮過**：① 維持 `600`／`900`、無 idle ② 只把 hard 拉到 1800、仍不做 idle
③ **hard 1800 ＋ idle 900，兩者皆為讀取時推導** ④ hard 1800 ＋ idle，但 idle 靠**前端心跳**回報活動
⑤ hard 1800 ＋ idle，靠**排程 worker** 掃描到期列

**決策：③。**

**兩個輸入，缺一不可**：

- **(i) 「UIUX 完全依照 mockup」**——mockup 建立 modal 的下拉預設是「30 分鐘」、
  同一個 modal 明載「閒置 15 分鐘後自動結束」、各頁情境列的倒數是
  `24:18`／`22:41`／`18:42`／`18:07`／`12:54`／`04:18`、結束 modal 是「工作時長 23 分鐘」。
  **這六組數字在 `MAX=900` 之下結構上一個都造不出來。**
- **(ii) 「無技術債、容易維護」**——決定了 idle 怎麼做。

**否決 ②**：拉高 hard 而不補 idle，等於把曝險窗口從 15 分鐘加倍到 30 分鐘而**沒有任何補償**。

**否決 ④（前端心跳）**：心跳是**瀏覽器可控的自我宣告**，分頁開著就永遠不逾時 ⇒
機制在最該生效的情境（人離開、分頁沒關）**恰好失效**；且它是一條純為判定而生的新請求流量，
落在已經很緊的限流桶裡。

**否決 ⑤（排程 worker）**：憑空生出一支排程器，屬後端服務責任邊界規範明令拒絕的
「資料完整性監測」型基礎設施（與否決「排程器把 active 改成 expired」是同一條理由），
而且它一出現就要同時滿足多副本搶佔規範——**為了一個可以被推導出來的值，付出一支帶租約的 worker**。

**③ 為什麼零技術債**：判定與 hard expiry **完全同形**——`now() >= last_active_at + idle`
是讀取時推導，DB 不落 `expired`、沒有任何東西需要定時掃；順延則**併進本來就要做的那一次
credential 反查**，把一句 `SELECT` 換成一句 `UPDATE … RETURNING` ⇒
零額外往返、零新 RPC、零排程器、零心跳、零新表。

**「什麼算活動」的判準**：`GET current` 的 30 秒輪詢**不算**活動；判準是
「是否經 `delegatedHandle` 註冊」而非「稽核列有沒有新增」，因為後者會把**純瀏覽**
排除在活動之外（讀取不落稽核），而在工作區裡翻商品列表 16 分鐘再按儲存是真實情境。

**曝險窗口的誠實記帳**：最壞情況由 15 分鐘變成 **30 分鐘**（操作者持續操作滿 30 分鐘）。
這是本條的**實際代價**，不得寫成「有 idle 所以更安全」——idle 只縮短「無人操作」時的窗口，
縮短不了「有人一直在操作」時的窗口。

### 被這一條取代的兩個前版（為什麼它們不再成立）

| 前版 | 原理由 | 為什麼失效 |
|---|---|---|
| 只做 hard expiry、不做 idle | 時間尺度不等式：idle 門檻要有意義必須明顯短於 hard 上限，而 hard 上限是 900 ⇒ `idle 門檻 ≥ hard 上限` ⇒ idle 在數學上永遠不可能先於 hard 觸發 | 它的唯一輸入 `hard 上限 = 900` 不成立了。**它不是被新資訊推翻，是被它自己預告的那個動作推翻的**——原文末段就寫著「唯一會打破它的動作是把 TTL 上限拉高到大於 idle 門檻」 |
| `DEFAULT` 600／`MAX` 900、不做續期 | 標準 E2E 情境（改店面 → 編商品 → 上架 → 發貼文草稿 → 看訂單 → 結束）合計 250–585 秒，落在 600 之內 | 它把「600 秒放得下標準情境」當成 TTL 的**充分**依據，而 TTL 的另一半功能是**倒數要顯示得出來**，mockup 的六組數字在 `MAX=900` 之下一個都造不出來 |

### 仍不做續期端點

理由是**投入產出，不是做不到**（這個區別在日後重開本題時很重要）：
續期換到的不是「某個情境從做不到變做得到」，只是省掉重選 reason／重填案件編號的摩擦；
代價是跨兩 repo 同波，且在此架構下**無法只做後端**——operation cookie 的 `maxAge`
由 `expiresAt` 推導，後端單方面延長 `expires_at` 對瀏覽器零效果，必須有一支 BFF route handler
重設 cookie；連帶還要新增業務碼、新稽核 action、`revision` 的**第三種** bump 來源與跨 repo gate。

「做不完」的正解是**結束後重新建立工作階段**——而重建**不是缺陷**：每次重建都重跑 preflight
（重新評估店家狀態與授權是否仍有效）並留下**新的稽核歸屬**（新 `display_code`、新 reason、
新 `case_reference`），在稽核上比續期是**更好**的形狀。

> ⚠️ 更正一個曾經的過度推論：「不可 sliding ⇒ 不可續期」**不成立**——
> 九欄對帳只在建立流程跑一次，一支顯式續期端點不經過它。

## 2. 不快取 Operation Session（含 Redis 與 in-memory）

**考慮過**：① 不快取，每次都查 account-service ② Redis 快取 session ③ Gateway 行程內記憶體快取

**決策：① 不快取。**

**三條否決理由裡有一條是安全不是效能，這正是本條必須進 ADR 而不能只留在效能章節的原因**
——留在效能章節，它讀起來像一個「等量到了就可以讓步」的取捨，實際上不是。

**否決 ②**：session／授權判定屬硬上限依賴治理規範定義的「不能失敗的狀態」，
放進一個無容量預算的依賴即違規。
**否決 ③**：Gateway 是**多副本**，各副本各持一份到期時間不同的 session 狀態 ⇒
**撤銷延遲生效**，而撤銷（含店家狀態命中）是安全動作，它的延遲是安全問題不是效能問題。

⇒ 重開本題的前提是先解決「撤銷如何即時穿透所有副本」，不是「P95 變高了」。

## 3. 併發代行的允許範圍

**考慮過**：① 全部允許，靠樂觀鎖擋 ② 同一 admin 只能代行一家；同一店家只能被一個 admin 代行
③ 只留前半條（限制同一 admin 只能代行一家，放行多 admin 對同一店家）

**決策：② 兩條都限制**，且由 DB partial UNIQUE 索引保證。

- **同一 admin 對不同店家**：允許的話，操作者在兩個分頁之間切換卻只有一個 operation cookie，
  寫入會落到錯誤的店家——這是**沉默的錯誤**，樂觀鎖擋不住。
- **不同 admin 對同一店家**：允許的話會產生版本衝突風暴，兩人互相覆蓋且都以為自己成功。

① 的「靠樂觀鎖擋」只擋得住同一資源的同時寫入，擋不住上述兩種。

**兩條限制的論證彼此獨立**，因此 **③ 是一個真實存在的中間形狀**。
**否決 ③ 的理由不是「做不到」而是併發模型尚未定義**：目前只覆蓋「賣家本人 vs 一個 admin」，
兩位 admin 同改一家店的衝突解決語意與 UI 呈現仍未裁決；在那之前放行等於把版本衝突風暴放進來。
⇒ 日後放寬時**只動 `target_store_id` 那一條 partial UNIQUE，`actor_admin_id` 那條不動**。

## 4. 排程發布與工作階段到期的關係

**考慮過**：① 到期即取消所有未執行的排程 ② 到期不影響已建立的排程，仍會執行

**決策：② 仍會執行。**

到期的是**操作者的操作權**，不是**已授權動作的效力**——排程建立當下 capability 檢查、原因、
稽核 intent 都已完成，那一刻授權就已經發生。① 會讓「排程明天早上發布」在實務上永遠無法使用
（工作階段上限 30 分鐘，與「明天早上」差一個數量級）。

**作用域只到「操作者的操作權消失」為止，共有兩個例外，兩者都是對授權本身的否定**：
**(a) 撤銷**會連帶取消未執行的排程；**(b) 目標店家被停權／關店／刪帳號**時排程一律不執行
（見 `2026-09-18-adm-delegation-suspension-and-notification.md`）。
另有一個**更早生效**的相鄰防線不屬本條例外：**貼文本身被刪除或被強制下架時排程不執行**
——那防的是「這則貼文」，(b) 防的是「這家店」。

## 5. `case_reference` 的值域：最低門檻而非格式驗證

**考慮過**：① 沿用前端 `isSafeReference` 的規則 ② 依實際案件編號規則定格式
③ 維持自由文字，但把「平台未驗證其指向」明文標註

**決策：③ ＋ 最低門檻**（長度 4–200 且至少含一個數字）。

**否決 ②**：格式驗證只能證明它長得像、不能證明它存在，反而**製造假的確定性**；
且治理案件的 reference 是純數字 TSID，與任何「HK-YYYY-NNNN」式樣不相容，
一個要同時容納 TSID／外部合約號／自由描述的規則最後必然放寬回「任意字串」。

**最低門檻不是格式驗證的縮水版**，兩者的判準不同：格式驗證假裝能證明「它指向某個東西」，
最低門檻只主張「這不是隨手填的」——後者做得到，前者做不到。

未來若引入工單系統或賣家請求留痕，正解是升級成 `case_ref_type` ＋ `case_ref_id`
兩欄做 resolve 驗證——**那時才有東西可驗**。

## 6. `display_code` 必須用完整 base36，不得截斷

**考慮過**：① 當日流水號 `OPS-YYMMDD-NNNN`，撞唯一鍵時重取
② 由 `id` 推導但**截斷成後 8 碼** ③ 由 `id` 推導，完整 base36 左補零至 13 碼

**決策：③ 完整 base36。**

**否決 ①**：create 是單一交易，而 PostgreSQL 交易內任一句 SQL 失敗即整個交易 aborted
（`25P02`）⇒「撞鍵後在同一交易內重取」物理上做不到。

**否決 ② ——這條是少數失敗模式「靜默且不可逆」的決策，也是它必須進 ADR 的理由**：
`pkg/tsid` 的 `id = unixMilli << 22 | seq` 在本案頻率下 `seq` 恆為 0 ⇒ **低 22 位恆為 0**；
而 `36^8 = 2^16 × 3^16` ⇒ 截斷後的相異值空間從 `2.82×10¹²` **塌縮成 43,046,721**，
週期恰 **11.96 小時**——相隔 11.96 小時建立的兩個工作階段拿到同一個代號。
以本案的量代入生日碰撞式，兩年內撞鍵機率 **> 99.99%**。
**而它不會在測試中現形**（單一測試不會跨 11.96 小時），只會在 prod 撞上，
且撞到的是**對外舉證用的稽核編號**。

⇒ 「代號太長想省幾個字元」是每個接手者都會冒出的念頭，而擋住它的機械保證只有一道：
DB CHECK `chk_dos_display_code_format`——**它的 `{13}` 不得放寬**，
放寬之後 `uq_dos_display_code` 才會開始被違反，而那時已經是 prod。

## 後果

- TTL 相關常數有三個必須同波的落點（前端常數、DB `chk_dos_lifetime_max`、契約測試邊界），
  缺一即「前端擋下／DB 擋下／後端放行」的三方不一致。
- `DELEGATION_SESSION_TTL_MAX_SECONDS` 或 `DELEGATION_SESSION_IDLE_SECONDS` 變更時，
  本 ADR 應提前複審。
