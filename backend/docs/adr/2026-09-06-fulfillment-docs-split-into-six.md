# 物流履約領域切成一組六本文件，而不是一本

| 項目 | 值 |
|---|---|
| 狀態 | accepted |
| 日期 | 2026-09-06 |
| 影響範圍 | 物流履約文件組（65／65A／66／67／68／69） |

- **脈絡**：需求書 v1.4 共 **2,463 行結構化文字 ＋ 28 張圖**，涵蓋 Uber Direct 即時配送、
  商家自有出貨、正規化配送域、帳本／撥款／結算、Amego 發票鏈、定期配送訂閱、7-ELEVEN 大宗寄倉。
  母系統 06 號（物流微服務）本身已 5,535 行，而物流履約平台是它的**重大擴充**。

## 選項

> 三案逐一評估。**每案都要答「使用者看到的東西會不會變少」**——
> 答案是「會」的才需要產品裁決，答案是「不會」的就只是工作。

## A：一本（把全部塞進 65）
- **代價**：需求書實測涵蓋**三個彼此獨立的商流**，而它們的**帳務軸互斥**（見下方 §決定的第 1 點）。
  塞進一本會產生**互相矛盾的狀態機**——同一份文件裡既說「撥款走 10 條 AND」又說「本章禁止出現撥款」。
- **使用者看到的東西會不會變少**：不會（純文件組織）
- ❌ **否決**

## B：切成六本（65 骨幹 ＋ 66／69／67／68 ＋ 65A 前端）
- **代價**：跨文件引用的維護成本；需要一份共用規約避免各寫一份
- **使用者看到的東西會不會變少**：不會
- ✅ **採用**

## C：切成兩本（65 後端 ＋ 65A 前端）
- **代價**：65 會超過 15,000 行（58 號一本 12,559 行，而物流履約範圍更大），
  且 67／68 各自有獨立的 provider 契約與狀態機，混在一起讀者無法只讀自己那塊
- ❌ 否決

## 決定：**B**

| 編號 | 文件 | 獨立的理由（**結構性**，不是「內容多」） |
|---|---|---|
| **65** | 物流履約平台（骨幹） | **唯一定義**正規化配送域、統一狀態機、事件 envelope、identity 鍵、金額口徑、provider adapter 邊界、責任與退款矩陣、帳本／撥款／結算、與 58 發票鏈的接縫 |
| **66** | Uber Direct 即時配送整合 | **外部契約密度最高**：官方 OpenAPI 的硬門檻、webhook 規約、台灣可用性未決。且**需求書有 6 條技術宣稱與官方不符**（D-21），需要一整章處理差異 |
| **69** | 商家自有出貨 | 它是**被 66 與 67 共同引用的橫向能力**（`fulfillment_mode = SELLER_MANAGED`），且有一份**對外的商家 API 契約**（給第三方 ERP 開發者看），混在 65 裡找不到 |
| **67** | 定期配送訂閱 | 🔴 **帳務軸互斥**：需求書 §20.15 明文「定期配送資料庫不得出現平台買家發票、1%、seller net、payout batch」「平台不發起或攔截撥款」 |
| **68** | 7-ELEVEN 大宗寄倉（B2C） | 🔴 同上（預設 `SELLER_DIRECT`，且明寫「**不得複製 Uber 模式推論**」）＋ 獨立的 provider 契約、batch 聚合層、**17 個 S0 狀態**需專章 |
| **65A** | 前端實作規格 | 比照 58A。43 個畫面 ID 橫跨四個 repo、五端；後端契約與畫面契約的讀者不同 |

## 理由（對照決策優先序逐條）

1. **沒有技術債** — 🔴 **決定性理由是「帳務軸互斥」，不是「內容太多」**。
   三種商流的收款主體、發票 issuer、是否進撥款鏈**三者全都不同**（D-7）。
   一本文件無法同時說「撥款資格是 10 條 AND」與「本章禁止出現撥款」而不自相矛盾。
2. **業務邏輯完美閉環** — 每本各自可獨立施工，且 65 的共用規約保證跨本一致。
3. **既有 SSOT 與契約** — 沿用 58／58A 的「主書 ＋ 前端實作規格」二分先例。
4. **既有實作與慣例** — repo 既有物流四本（06／21／22／37）已是分本形式。

## 後果

- **65 是唯一骨幹**：狀態機、事件 envelope、identity 鍵、金額口徑**只在 65 定義一次**，
  66／67／68／69 **只准引用，不得各寫一份**（共用規約十一節見 65 §3）
- 66／67／68／69 **彼此不得有循環引用**
- 🔴 **註冊時機**：66／67／68／69 的註冊（`00-總覽.md`／`_sidebar.md`／`docs/index.md`）**延到該本定版之後**
  ——「不足 800 行者併回 65」的規則要等內容寫完才判得出來，提前註冊會導致併回時要撤銷已 merge 的內容。
  **65 是骨幹不會被併掉，可先註冊**
- **69 是唯一有併回風險的一本**：需求書原料只有 §4.1＋§4.2（約 49 行摘要，是 67／68 的 1/25）。
  撐不起 800 行就併回 65 **並在 65 內獨立成章**（不散開），對外 API 契約抽成 65 的附錄
- **需求書的三份 WBS 時程（§14／需求書 §20.22／需求書 §21.19）一律不收**，只取「階段之間的技術依賴順序」
  寫進各本的遷移步驟節（需求書 §21.19 的「關鍵路徑」那一條是例外，要收）

## 什麼情況要重新檢視

- 66／67／68／69 任一本寫完後**不足 800 行** ⇒ 依規則併回 65
- 若未來出現第四種商流，先問它的**帳務軸**與現有哪一種相同；相同則併入該本，不同才開新本

⚠️ `2026-09-11-uber-commerce-model-seller-direct.md` 把五種履約方式收斂到同一條帳務軸之後，
「帳務軸互斥」對 66／67／68 **不再是分本理由**；結論（維持六本）不變，現行理由是：
provider 契約密度與承載規則的差異、對外契約的讀者不同（69 的商家 API）、
batch 二維模型（68）、契約×週期兩層（67）。
