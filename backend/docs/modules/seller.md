# seller 模組行為規格

本文是單體 `seller` 模組行為的唯一來源。店家業務身分與店家 profile 的擁有者；涵蓋申請開店、入駐同意、profile、logo 與封面、店家封鎖、措施與停權、治理（通報、案件、認定、申訴）、KYC、PayUni 子商店、關店與清理、商家名單、商品瀏覽數、能力與刪帳參與者。

## 1. 範圍與公開面

店家業務身分與店家 profile 的擁有者：申請開店、profile、logo 與封面、商家名單（站外業者的 BD 名單）、商品瀏覽數、措施（警告、停權與終止合作，依據是認定、風險類型或契約條款）與停權狀態的檢查、商家治理（通報、認定、措施、申訴）、關店，以及刪除帳號時的店家參與者。

### 1.1 資料

是不可變的開始時間，`termination_ground`、`source_measure_id` 是終止的事由與關聯帳號的來源；`version` 是後台的 etag，`current_revision` 是賣家的 etag；`source_case_id` `measures.lead_finding_id`）、`measure_contents`（內容下架措施的對象，一列一個（措施，內容種類，內容 id），只在建立時寫入）、`finding_moderation_reports`（認定引用的 moderation 檢舉，不透明的外部參照，不加 FK）、`governance_notes`（內部註記，只新增，掛在措施或案件剛好一個，不動 是它的佐證）、`measure_identities`（停權措施建立時快照的身分 blind index，措施結束或撤銷就刪）、`suspension_periods`（停權期間，停權事件的身分）、`reports`（通報：一位檢舉人的一次送出，帶結果 `outcome`、所在案件與平台判定類別、`version`；沒有狀態欄，處理狀態由事實推導）、`report_supplements`（補充，只新增）、`report_evidence`（原通報與補充的佐證；位置從 0 連號，上界是 `MaxReportEvidence`（原通報加每則補充各 5 張），DB 的 CHECK 與 Go `due_at`、一則回覆與撤回欄位在同一列，`case_inquiries_one_open` 保證每個案件同時最多一筆還沒結束的；`case_inquiry_reply_evidence` 是回覆的附件）、`violations`（認定：帳號、類別、嚴重度、升級前的嚴重度、撤銷紀錄，不帶處分與申訴）、`evidence_accesses`（佐證的讀取紀錄，通報、申訴請求與詢問回覆共用，append-only）、`kyc_applications`（以 `store_id` 為鍵）、`kyc_identity_hashes`（申請的身分比對索引：每個識別欄位、金鑰環每一把金鑰的 asset_id，append-only）。`payuni_registrations`（以 `store_id` 為主鍵：綁定意圖與 PayUni 的目前狀態）、`payuni_observations`（PayUni 狀態的觀測，append-only，觀測 ID 同時是對應事件的 `event_id`）。通報、認定、措施、請求與 KYC 申請（`application_id`，審核與稽核列同為 UUIDv7）的 ID 是 UUIDv7（應用層產生）；`store_id` 與停權期間的 `period_id` 是 IDENTITY（原因見 §23）。`prospects`（商家名單，`prospect_id` 是 IDENTITY：ai-service 以 BIGINT 存；稽核欄是 `created_by_admin_id`、`updated_by_admin_id`）、`prospect_contacts`（聯絡方式）、`prospect_distinct_pairs`（標記為不是同一家的配對）、`prospect_categories`（分類樹 ID）、`product_views_daily`（`(store_id, day)` 的每日瀏覽數，`day` - SQL 的 view 與函式（寫在 `db/objects.sql`、手寫 migration，單體規則 6；Atlas 只讀 `schema.sql`）：`store_requirement_flags`（view，每家店與時間無關的條件一欄一個布林：`active`、`not_pending_deletion`、`kyc_approved`、`has_store_name`、`has_logo`、`has_town_code`；`stint.WithConditions` 讀它填 `Store.Conditions`）、`effective_measures(at)`（「措施生效中」唯一的定義，回傳 `effective_measure (id, account_id)`；`EffectiveMeasures`、`EffectiveMeasuresAll` 與 `pub_exposable_stores` 都讀它；寫成單一 SELECT，不用 UNION ALL，外層的帳號條件才推得進 `measures_enforced_suspension`，`TestExposableStoresJoinProbesMeasuresByAccount`）。`has_store_name` 只看 NOT NULL，「不是空白」由 `stores_store_name_check` 保證（頭尾不是 Unicode 空白，`platform/trimtext.Check`，與寫入端的 `trimtext.Trim` 同一個集合，`TestStoreNameCheckRejectsEveryUnicodeSpaceAtEitherEnd`）。

### 1.2 子領域套件

- `internal/onboarding` 申請開店；`internal/profile` 讀取與 profile、logo、封面的寫入；`internal/suspension` 停權期間的維護（`Recompute`）、身分快照（`RecordIdentities`）、`ActingStore`，以及措施的到期與對帳 job；`internal/measure` 措施的建立（含認定、升級、終止事由與關聯帳號、`request_id` 冪等）、修改、結束、撤銷與連帶撤銷（認定撤銷、來源終止撤銷）、複審期限、申訴與裁定、內部註記、讀取（停權一律經 `suspension.Recompute`）；`internal/governance` 通報、補充與佐證的寫入、分案、設定結果、移動，案件的決定、改嚴重度與註記，以及聯絡欄位的清理；`internal/closing` 關店（查店家未結訂單的 port `Orders` 在這裡宣告）、終止合作生效後的關店（`seller.termination_effect`、每小時的 `seller.reconcile_terminations`）、恢復營業（`ReopenPlan`、`Reopen`）與刪帳參與者；`internal/purge` 關店後的兩段清理（每小時 River 排程：關店 30 天退場——清公開內容、釋放 logo 與封面並發 `StoreRetired`；關店 184 天清店家的註冊資料、KYC 與 PayUni；證件在刪除時記成退場並排入引用的同步）；`internal/mediaref` 是 logo、封面、業者圖片、證件與佐證在 media 的引用同步（退場資產、版本與 `seller.media_sync` job，演算法是 `media.Sync`）；`internal/kyc` 是 KYC 認證（草稿、送出、取消、審核、顯示全文、身分比對、證件圖片；加密與 blind index 用 `internal/platform/seal`，與 identity 共用）；`internal/payuni` 是 PayUni 註冊（意圖、sync／輪詢／webhook 套用的 job、觀測、流程狀態、錯誤目錄的使用；呼叫 PayUni 的 port `Client` 在這裡，真正的 HTTP client 是 `internal/platform/payuni`，payuni 不碰 KYC 金鑰，解密由 kyc 以 `KYCSource` 提供）；`internal/prospect` 是商家名單（建立、比對、更新、封存、合併、轉換、對帳、搜尋、圖片；比對鍵的解析器 `model.ContactMatchKey` 在 `internal/model/prospect_match.go`，並加共用平台的排除）；`internal/views` 是商品瀏覽數的彙總與統計；`internal/exposure` 是可曝光規則的套用（`Classify`）與公告（`Announce`）；`internal/stint` 是共用的列鎖（`LockAccountOf`）、停權狀態的推導（`Derive`、`Load`）、型別轉換與快取失效；`internal/model` 是型別、儲存的代碼、能力、事件與輸入規則；`internal/store` 是 sqlc 生成物。鄉鎮市區代碼的表在 `platform/twaddr`。

### 1.3 公開的 Go 讀取

- 讀取模型：沒有獨立的讀取模型。`CurrentStore` 與 `Store` 回傳完整的 stint（含已關閉的，`Status` 標示）；對外怎麼呈現由 ADR `2026-10-03-public-store-identity-and-visibility` 決定：店面頁只給可公開曝光的店家，卡片只給曾經公開過的店家（`first_exposed_at` 有值，或此刻可公開曝光），見 §12。

- 店家與停權狀態的公開讀取：`StoreWithActiveMeasures(storeID)`，同一個讀取快照回傳 `StoreMeasures`：店家（`Store`）、它的停權狀態與帳號此刻生效中的全部停權措施（`Active`，帳號範圍，新 stint 也讀得到舊 stint 的措施）；`CurrentStore(accountID)` 與 `Store(storeID)` 回傳店家與推導的停權狀態：`Store.Sanctions` 是唯一來源（帳號此刻生效中的停權措施，依據、風險類型、主要依據的類別，給 legacy 分類用），用 `Suspended()` 判斷、`EffectiveMeasures()` 讀措施；`Sanctions` 是 nil（沒有推導過）視為停權，legacy 的出口（`sellerreason.Classify`、`Of`）遇到 nil 回錯誤，`TestStoreWithoutDerivedSuspensionIsTreatedAsSuspended`、`TestUnderivedSanctionsAreRejected`。後台 `GetStore`（`active_measures`）、賣家 `GetMyStore`（`suspended`）與 legacy（停權原因碼、`seller.suspended` 的原因）都用它。

- 只為 legacy SellerService 存在的公開讀取（`internal/legacy/sellerserver` 是唯一的呼叫方；每個方法的 doc comment 寫了退場時機，呼叫方搬進單體、改呼叫 §12 的方法時刪除）：`BatchStores(ids)`（含已關閉的 stint，每個帶推導的停權，依輸入順序）、`StoresWithExposure(ids)`（同上加 `Exposable`：規則仍只有 `seller.pub_exposable_stores`，與 `exposedRows` 同一個 `classify`；固定四次查詢）、`ResolvePrincipals(ids)`（存活的 stint 的 store_id 到帳號；已關閉的不解析，舊契約的 unresolved 是「沒有存活的店家列」，舊 seller-service 關店等於軟刪除）、`StoreIDsByAccount(accountID)`（全部 stint，不鎖）、`ExposableStoreIDsByCounty(countyCodes)`（內政部 5 碼縣市代碼，每個要求的縣市都有鍵；讀 `store_exposures` 最後公告為可曝光的店再依縣市過濾，與 Java 的 `seller.exposure.changed` 消費者是同一份公告，落後最多一個對帳週期）、`MatchCertificateHolder(storeID, holderName)`（業者名稱歸屬比對，呼叫方是 product-service 的農業認證自動核准（設計書 19 §8.5.1 是呼叫端行為）：請求 `store_id` 與 `holder_name`（原樣送出，正規化在 seller 端），回應 `matched`（任一名稱相符即 true）、`matched_field`（`REAL_NAME`／`COMPANY_NAME`／`NONE`，稽核只記欄位名不記值）、`has_reference`；`real_name` 是 PII，不跨服務傳輸，也不寫進呼叫方的資料；基準只有目前 stint 上人工核准（`KYCStatusApproved`）的申請的姓名與公司名稱（不要求 PayUni 核准），正規化是去除空白與全形空白、全半形、大小寫與公司型態後綴表（含農場、商行、工作室等商號用詞），不做子字串或編輯距離，規則在 `model.MatchCertHolder`；回傳只有判定與相符的欄位，名字不出模組；沒有基準時 `HasReference` 為 false，讀取失敗回錯誤，呼叫方 fail-closed）。批次最多 `MaxBatchSize` 個。`TestBatchStoresIncludesClosedStintsInInputOrderWithTheDerivedSuspension`、`TestStoresWithExposureAgreesWithExposableStores`、`TestResolvePrincipalsExcludesClosedStints`、`TestStoreCarriesTheEffectiveMeasuresOfTheSameRead`、`TestStoreFindsAMeasureRecordedOnAnEarlierStint`、`TestExposableStoreIDsByCountyAppliesTheExposureRule`、`TestExposableStoreIDsByCountyReadsTheAnnouncedValue`、`TestMatchCertificateHolder` 驗證。

## 2. 申請開店與店家身分

- 每個帳號最多一個目前的 stint（`status` 不是 `CLOSED`）：DB `stores_current_account` partial UNIQUE；開店在 transaction 內先 `identity.LockAccount` 再檢查，所以 UNIQUE 只是保底。重新入駐建立新的 stint，帶新的 `store_id` 與 `store_code`（PayUni 的 MerID 是一次性的外部綁定）。`TestApplyRejectsSecondStoreAndReonboardsWithNewStint` 驗證。

- SELLER ⇔ 帳號有目前的 stint：開店時在同一個 transaction 授予，任何關閉（`CloseCurrent`、`CloseForDeletion`、終止合作的關店）在同一個 transaction 移除，恢復營業（`closing.Reopen`）在同一個 transaction 重新授予（前提：帳號存活且未被 identity 停權，與開店同一個判斷；被停權的帳號撤銷終止只撤銷紀錄、不重開）。`accountdeletion` 遇到有 SELLER 卻沒有店家，當成不變量被破壞。

- 開店先驗證全部輸入，任何一欄不合法就不建店、不授予角色、不發事件：`TestApplyValidatesEverythingBeforeWriting`、`TestApplyEventFailureRollsBackStoreAndRole`。

- 地址以內政部的 8 碼鄉鎮市區代碼（`town_code`，縣市是前 5 碼）表示：寫入端以 `platform/twaddr` 檢查是現行的代碼，DB 的 `stores_town_code_check` 檢查格式；地址要有鄉鎮市區（`stores_address_detail_check`）。網站網址的 scheme 與主機在寫入前轉成小寫（DB 的 CHECK 區分大小寫）。文字欄位不存空字串（沒有值是 NULL）。

- 開店只鎖帳號列、不鎖舊 stint：開店與「延長舊 stint 上已到期的處分」併發時，新 stint 已經停權（能力在讀取時推導，即時正確），但停權期間與 `StoreSuspended` 要等每小時的對帳補上；只影響事件的時間，不影響權限。下游需要即時時，開店改成先 `LockAccountOf`。

- 入口、gateway 與舊服務都讀本模組，店家只有一份資料。有 SELLER 卻沒有現任店家是不變量被破壞：`gatewayproxy` 回 500、`accountdeletion` 回 internal，不當成「沒有店家」。

- 入駐同意（ADR `2026-10-19-seller-kyc-payuni-consolidated`「入駐同意紀錄」）：現行版本與網址（站內路徑，對外由 `internal/httpapi` 以 `PUBLIC_WEB_ORIGIN` 組成絕對網址，PayUni 的本來就是絕對網址）只在 `internal/model/agreement_gen.go` 的 `CurrentAgreements`，它由 `website/scripts/generate-legal.ts` 從 `website/docs/legal/` 的正本與 manifest 產生，不得手改；改版是改正本（版本行）或 manifest 後在 `website` 跑 `pnpm gen:legal`。同意的紀錄與開店、送出 KYC 的寫入在同一個 transaction，每次同意事件一列（KYC 的列綁定那次送出的審核紀錄，由資料表的 CHECK 把關）；關店 184 天的第二段清理（`StoreRetention`，連線紀錄）把來源 IP 與 User-Agent 清成 NULL，其餘保留。

### 2.1 身分鍵與 stint 的生命週期

- `store_id`（`seller.stores` 主鍵，`BIGINT GENERATED ALWAYS AS IDENTITY`，建立後不變）是賣家歸屬的 aggregate 身分，跨服務的賣家歸屬鍵一律用它；`store_code`（`BIGINT NOT NULL`，唯一索引 `stores_store_code`，範圍 1–9999999999）是 PayUni MerID `HAWK{store_code}` 的推導鍵（`seller.FormatPayUniMerID`）；`account_id`（非唯一，建立後不變）是登入 principal，同一個帳號可累積多個 stint。三者是不同的值，不得互相代入，也不得假設任兩者相等（包含守衛比對與測試 fixture）。`store_id` 由資料庫發號，`store_code` 由 seller 自己產生，兩者不同來源。
- `store_code` 由 `onboarding.RandomStoreCode` 產生：西元年後兩碼乘以 10^8，加上 8 位 `crypto/rand`；撞到 `stores_store_code` 時換一個再試，最多 5 次（`maxStoreCodeAttempts`），連續撞號回錯誤；撞號不使 transaction 失效（`INSERT … ON CONFLICT DO NOTHING`）。
- 開店的順序（同一個 transaction）：鎖 identity 帳號列（`LockAccount`）→ 確認沒有目前的 stint、帳號沒有生效中的停權或終止合作、帳號沒有被 identity 停權（`OpeningState.AccountSuspended`，`accountsuspension` 停權的帳號開店要等解除，與停權序列化；`TestOpeningWaitsForASuspensionAndThenIsRefused`） → 建立 stint → 授予 SELLER（`source_id` 是新的 `store_id`）→ 發 `StoreOpened`；帳號等待刪除時 identity 拒絕授予，整筆回滾。`Apply` 與 `CloseMyStore`（對外的關店方法，契約是 `api/hawkr/seller/v1alpha1/seller.proto`；有未結訂單回 `failed_precondition`，停權中也可以關店）都先鎖 identity 帳號列、再鎖該帳號的 stint（帳號列先於店家列），序列化同一帳號併發的開店與關店；`stores_current_account` 是最後的資料庫防線。
- `status`：`ACTIVE`、`PENDING_DELETION`（隨帳號刪除進入等待）、`CLOSED`；停權不存在這裡，由措施在讀取時推導（§5）。轉移：`Apply` 建立 `ACTIVE`；關店（賣家自助、終止合作、帳號刪除）`ACTIVE` → `CLOSED`；帳號刪除等待 `ACTIVE` → `PENDING_DELETION`，刪除流程關閉後 → `CLOSED`；恢復營業（終止合作撤銷或申覆成立，退場前，§11）`CLOSED` → `ACTIVE`；退場與個資清理後 row 保留。
- 索引：`stores_current_account`（`UNIQUE(account_id) WHERE status <> 'CLOSED'`，每個帳號至多一個目前的 stint，「找某人現在的店」走它）、`stores_account`（以帳號找全部的 stint）、`stores_store_code`（MerID 唯一性的防線）。
- 只有賣家走 insert-new-stint：帳號再次開店另開新列、舊列與舊 `payuni_registrations` 保留，新列必須鑄新 `store_code`，否則新 MerID 會撞上舊綁定（`AGENT04017`）。買家與帳號同生命週期，不重新授予。
- `seller.deleted`（MQ `hawkr.seller`／`seller.deleted`，at-least-once，`event_id` 為冪等鍵）在 stint 退場（關店後的第一段清理，`StoreRetired`）時由 legacy relay 轉出；關店本身（`StoreClosed`）不發，因為關店在退場前可逆。`account.deleted` 只在帳號刪除時經 accountdeletion 發，關店時帳號仍在，不發。
- legacy 讀取 `GetCurrentStoreID(account_id)`：回帳號目前的 `store_id`，沒有目前的店回 `NotFound`（呼叫方只認 gRPC `NotFound`，不解析業務碼字串）；`ResolvePrincipals` 回 `{code, message, principals, unresolved_ids}`，只解析存活（未關閉）stint 的 `store_id` 到 `account_id`，已關閉或不存在的 id（含非正數）只出現在 `unresolved_ids`，不把 id 原樣回填；`principals` 的 value 保持 int64（純內部呼叫，不經 gateway）；批次上限 `MaxBatchSize`，呼叫方一次送整批。

## 3. 店家 profile、logo 與封面

## 4. 店家封鎖

- 店家封鎖（`store_blocks`）：店家封鎖一位買家，主鍵 (store_id, buyer_id)，buyer_id 不建外鍵，買家刪帳時 accountdeletion 在同一個刪帳 transaction 呼叫 `ClearBlocksAgainstBuyer` 刪掉以他為對象的列（在買家的刪除事件派發之前）。單向：只擋買家在這家店的新互動（檢查在 social），不擋下單。`BlockBuyer`／`UnblockBuyer` 冪等，回「有沒有改變」；模組 API 不做能力檢查（封鎖是保護動作，停權時仍要能封鎖與解除），誰能代表店家操作由 httpapi 的 `ActingStore` 決定。`ListBlockedBuyers`（keyset）、`StoreBlocksBuyer`、`StoresBlockingBuyer`（批次，給列表每列的 `viewer_can_comment`）。不發布 `seller.pub_blocks`：封鎖不篩選讀取，檢查是依 ID 的查詢。`TestStoreBlockAndUnblockAreIdempotent`、`TestStoreBlocksAreDirectedAndBatchedPerBuyer`、`TestListBlockedBuyersPaginatesNewestFirst`、`TestClearBlocksAgainstBuyerDeletesOnlyThatBuyersRows` 驗證。

- `BlockBuyer` 不鎖也不查對象買家（seller 不依賴 buyer，`internal/arch/modules.go` 擋，模組內無法檢查）：與買家刪帳並發時可能留下指向已關閉買家的列，也收得進不存在的 buyer_id；這是接受的現況，因為對已關閉買家沒有效果，對象是否存在由 `internal/httpapi/seller` 的 handler 從留言參照或買家 API 解析時把關，封鎖名單裡的已關閉買家也由 handler 組裝名單時顯示成已刪除，模組不提供這個行為。出現 seller 依賴 buyer 的理由，或名單顯示出現問題時重新評估。

## 5. 措施與停權

- 措施的紀錄以 `account_id` 與 `store_id` 記歸屬，效果以帳號為單位：帳號任何一個 stint（含已關閉的）在 now 有生效中的停權措施（狀態 `ENFORCED`、種類 `SUSPENSION` 或 `TERMINATION`、`starts_at` 不晚於 now、`measures.ends_at`（目前值）為 NULL 或晚於 now；now 是注入的 clock，不用 SQL 的 `now()`）就是停權。**停權狀態不存，讀取時推導，推導點只有一個：`stint.Derive`**（指定帳號的查詢 `EffectiveMeasures`；結果放進 `Store.Sanctions`，停權與生效中的措施是同一個來源）。措施的 `state`（ISSUED、SCHEDULED、ACTIVE、ENDED、REVOKED）也是讀取時推導，不存。`TestSuspensionIsDerivedAtReadTimeWithoutAnyJob`、`TestSuspensionStateChangesTogetherEverywhere`、`TestMeasureFollowsTheAccount`。

- 措施的版本化是 SQL:2011 的系統版本表模式：`measures` 存給賣家的理由（`statement_to_seller`）與 `ends_at` 的目前值，`measure_revisions` 是含目前那一版的不可變快照歷史；寫入新版本只經 `InsertMeasure`、`AdvanceMeasureRevision`（單一 SQL 語句同時更新主表並追加歷史），不得另寫一條路徑；「此刻生效中」的讀取只讀 `measures`（部分索引 `measures_active_timed`、`measures_active_open`），不 join `measure_revisions`。`assertCurrentValuesMatchHistory` 檢查兩者一致。

- 措施有三種依據（`measures_basis_check`、`measures_basis_value_check`）：VIOLATION 依據一到多筆既有或新建的認定（`measure_findings`，是集合，沒有順序；主要依據 `lead_finding_id` 建立時由規則決定，不看清單的位置：有新的認定時是新的認定，否則是引用的認定中最嚴重的（CRITICAL > HIGH > MEDIUM > LOW），同嚴重度取最新建立的，`model.LeadFindingOf`；`TestLeadFindingOfACitedOnlyMeasureIsTheMostSevereThenTheNewestWhateverTheOrder`、`TestANewFindingIsAlwaysTheLead`、`TestMaterialBreachLeadIsTheMostSevereCitedFindingNotTheFirstOne`），停權一定有結束時間且只能由撤銷或接受申訴結束；RISK 依據風險類型（`risk_ground`，條款第 17.1、17.5 條的八個風險類型），沒有固定結束時間，必須有複審期限 `review_by`（上限 `ReviewWindow`），風險排除時由管理員結束（`EndMeasure`）；CONTRACT 依據契約條款，只配終止合作（§6）。同一帳號可以有多個生效中的停權措施，共用一段停權期間。前置條件只寫在 `model.Measure` 的 `Can*`，方法與 API 的 `can_*` 共用，`TestCanFlagsMatchWhetherTheActionSucceeds` 逐格比對。兩個 etag：後台是 `measures.version`（新版本、撤銷、複審期限、請求的提出、裁定與系統結案都加一，註記不加），賣家是 `current_revision`（賣家看得到的版本），`TestSellerAndAdminEtagsFollowWhatEachSideSees`。提出申訴起措施的理由與延長被凍結，縮短與撤銷（只經裁定）不受影響。

- 建立措施的輸入規則：恰好一種依據（認定、風險類型、終止事由）；風險類型的措施只能是停權；給賣家的理由（`statement_to_seller`）與內部註記各必填、1 到 2000 字，內部註記寫成這個措施的第一則 `governance_notes`；警告不能有 `ends_at`，依據認定的停權必須有；`ends_at` 必須晚於現在；RISK 的 `review_by` 必須晚於現在且不超過 `ReviewWindow`（30 天），沒有伺服器預設值；終止與依據認定的措施沒有 `review_by`。一個措施一次最多引用 20 筆既有認定（`MaxCitedFindings`），一個新認定最多 20 筆來源通報（`MaxSourceReports`），來源通報可以是 0 筆。無狀態的驗證先於 `request_id` 重送查詢，與時間或資料有關的驗證在其後。

- **內容下架**（種類 `CONTENT_TAKEDOWN`）：社群內容（`POST`、`COMMENT`、`FORUM_ENTRY`）的處分，沿用 `measures` 當唯一來源，特例見 `CARRYOVER.md`「A7-1c」。
  - 形狀：依據一定是認定（`measures_takedown_check`：`VIOLATION`、`starts_at = created_at`、沒有 `ends_at`）；建立即生效、沒有結束時間；不限制帳號，不算 `Restrictive`，不進 `effective_measures`、停權期間與 `pub_exposable_stores`；未撤銷時 `StateOf` 是 `ISSUED`，列表的 `ISSUED` 篩選包含它。對象 1 到 `MaxTakedownContents`（20）筆、(種類, id) 不重複；建立者傳入的 `Contents` 同時隨 `MeasureCreated` 與 `MeasureRevoked` 發出。
  - 對象不可變：`measure_contents` 只在建立時寫入，`UpdateMeasure` 沒有對象欄位；要改就撤銷再建立。
  - 解除：只走申覆（接受申覆撤銷措施）。延長、縮短、結束的可用性原因只有 `CONTENT_TAKEDOWN_REVOKE_ONLY`，已撤銷的只有 `REVOKED`；補正請求只收 RISK。
  - 認定的類別：`policy.Assessable()` 是全部除了 `Other`，含社群的 `SPAM`、`HARASSMENT`、`HATE`（`violations` 與 `cases` 的 CHECK 跟著）；`ReporterSelectable()` 不含它們（`reports` 不變）。內容下架的認定可引用 moderation 的檢舉（`finding_moderation_reports`，每個認定最多 20 筆）；升級規則照常累計，社群類別的 MEDIUM 計入。
  - 建立入口：`CreateInTx`（`CreateMeasureInTx`）加入呼叫方的 transaction，建立者是傳入的管理員，不收 `request_id`，給 moderation 讓處理與措施同生共死；handler 路徑的 `request_id` 在同一個 transaction 內先鎖目標帳號的全部 stint，再查 `(admin, request_id)` 重送（重送先於關店店家的檢查，已建立的措施重送仍成功），插入用 `ON CONFLICT DO NOTHING`，落空（只剩目標在不同帳號的並行請求）回 `InvalidInput` 並回滾。
  - 內容屬於哪個店家不在本模組驗證，而在 social 的 `MeasureCreated` 同 transaction 訂閱者（`social.md` §4）：每則內容必須存在、沒有刪除、作者就是措施的店家（買家寫的走隱藏），不成立回 `social.TakedownContentError` 讓措施回滾。後台 handler、`CreateInTx` 的呼叫方（moderation）共用這一條檢查；admin 的 `CreateMeasure(content_takedown)` 把這個錯誤對到 `InvalidInput`、欄位 `content_takedown.contents[i]`。對象的種類代碼（`POST`、`COMMENT`、`FORUM_ENTRY`）由 `platform/contentkind` 擁有，seller 的 `ContentKind` 與 social 共用；不認得的種類是錯誤，不略過。
  - 賣家端的 `Measure` 帶 `contents`（`ContentRef`，依種類、id 排序，與後台同一份），賣家據此知道被下架與申覆的是哪些內容；後台的類別下拉還沒有社群類別，在 A7-4。

- 停權期間（`suspension_periods`）與 `StoreSuspended`／`StoreUnsuspended` 只由 `suspension.Recompute` 寫入：帳號從未停權變成停權時在**帳號目前的 stint** 上開始一段期間並發 `StoreSuspended`，恢復時結束它、發帶同一個 `PeriodID` 的 `StoreUnsuspended`；持續停權中新增、結束或撤銷其中一個措施（只要還有一個生效中）是同一段、不發事件，所以事件不帶停權的種類。沒有目前的 stint（所有 stint 都關閉）時沿用已經進行中的那一段，沒有進行中的就不開始。`TestRiskAndViolationMeasuresShareThePeriod`、`TestTwoRiskMeasuresOnOneAccountBothSucceedAndShareOnePeriod`、`TestExpiryOnAnAccountWithoutAStintEndsThePeriodOnTheClosedStint`。

- **Recompute 先鎖再讀**：先鎖住帳號全部的 stint（依 `store_id` 的順序；寫措施的流程一律先經 `stint.LockAccountOf` 以同一個順序鎖，不會互鎖），鎖住之後才讀措施；先讀再鎖會讓兩個同時進行的重算各拿對方還沒 commit 之前的措施，把生效中的停權結束掉。`TestRecomputeReadsMeasuresAfterLockingTheStores`。 措施結束但期間還沒被 job 結束時帳號開了新的 stint：其他 stint 上進行中的期間在下一次 `Recompute` 以 `StoreUnsuspended` 結束，新 stint 開始自己的一段；`Recompute` 同時刪除已撤銷或已結束措施的身分快照，並在最後重新公告可曝光。

- 措施到期：建立或改結束時間時在同一個 transaction 排入排在 `ends_at` 的 `seller.measure_expiry`（以措施與到期時間為唯一鍵），它只負責期間與事件，權限不靠它。執行時以 `max(排入時的 ends_at, 現在)` 判斷：`TestExpiryJobWithASlowWorkerClockStillEnds`；措施後來延後時，判斷時間仍是排入時的 ends_at，新的結束時間更晚，措施繼續生效（`TestStaleExpiryJobAfterExtendingTheMeasureKeepsItEffective`）。`seller.reconcile_suspensions` 每小時修補期間與措施不一致的帳號（有進行中期間的帳號 `AccountsWithOpenPeriod`，加此刻有生效中停權措施的帳號 `stint.SuspendedAccounts`，不讀歷史）：`TestReconcileScansOnlyAccountsWithAnOpenPeriodOrAnEffectiveSuspension`。

- RISK 複審：`ScheduleMeasureReview` 只限生效中的 RISK 停權，新的 `review_by` 必須晚於現在且不超過 30 天，內部註記必填並與重排在同一個 transaction。到期未處理的措施出現在複審收件匣（`ListMeasures` 的 `review_due` 篩選與待辦 `MEASURE_REVIEW`）：成員是 RISK、生效中、現在不早於 `review_by` 前 24 小時（過期後仍在），不需要 job。

- `seller.measure_close_ended_requests`（每 5 分鐘、啟動即執行）：只掃已結束而仍有儲存為 `PENDING` 解除請求的措施，每個帳號在自己的 transaction 內先鎖帳號再重讀，以 `CLOSED`（`ENDED`、`decided_at = ends_at`）結案、發 `MeasureRequestClosed`、後台 etag 加一；單一帳號失敗不影響其他帳號（錯誤合併回傳讓 River 重試）。它只決定儲存值與通知的時效，對外狀態由讀取時推導，job 遺失不影響正確性；停權的到期 job 與對帳不處理請求。

- 措施只能建在還沒關閉的 stint（`TestMeasureOnClosedStintIsRejected`）。升級規則（帳號 90 天內第 3 次 MEDIUM 認定升為 HIGH，記下 `escalated_from`）**以帳號計**（`violations.account_id`，所有 stint 一起算），以帳號全部 stint 的鎖串行，不用 advisory lock：`TestEscalationThirdMediumWithinNinetyDays`、`TestEscalationCountsTheAccountAcrossStints`、`TestEscalationIsSerialisedByTheAccountLock`。建立措施先鎖店家列、再鎖來源通報列（鎖順序：店家列先於通報列），來源通報必須是同一個店家、結果不能是未違規、內容不足或濫報（`Report.Supporting`；API 的 `can_cite_as_source` 是同一個規則加上店家沒有關閉）；從案件建立時（`source_case_id`，任何依據的警告、停權、RISK 與終止都能連）案件必須是同一家店、還沒結案，措施記下來源案件（`TestCreateMeasureCanLinkAnyKindToAnOpenCaseOfTheSameStore`）。`request_id`（選填，AIP-155，範圍管理員、永久保存）的流程：先查重送（相同輸入回原本措施的目前狀態、`Replayed`，不同輸入回 InvalidInput 指向 `RequestID`），再做有狀態的驗證，最後寫入；唯一索引 `measures_request` 的競爭退回重送路徑。「相同輸入」由 `requestHash` 定義：所有 id 清單（來源通報、引用的既有認定）都是集合，順序不同的同一組算相同（hash 編碼排序後的複本，沒有例外，不改動輸入）；主要依據由規則決定，不編碼在位置裡，所以同一組引用不論怎麼排都是同一個請求、同一個主要依據。`TestCreateMeasureRequestIDIsIdempotent`、`TestConcurrentCreateMeasureWithTheSameRequestIDWritesOneRow`、`TestCreateMeasureRequestIDIgnoresTheOrderOfSourceReportsAndCitedFindings`、`TestCreateMeasureRequestIDIgnoresTheOrderOfCitedFindingsWithoutANewFinding`、`TestRequestHashIgnoresTheOrderOfSourceReports`、`TestRequestHashIgnoresTheOrderOfCitedFindingsWithoutANewFinding`。

- 措施的鎖順序：店家列先於措施列。撤銷與接受申訴在同一個 transaction 結束它的效果並重算（`TestAppealAcceptEndsTheEffectInTheSameTransaction`）；撤銷時帶 `revoke_findings`（只在 `Measure.CanRevokeFindings()` 為 true 時可設：VIOLATION 依據而且措施自己建立了尚未撤銷的認定；API 的 `can_revoke_findings`；`TestRevokeFindingsIsRejectedWhenTheMeasureOnlyCitesOthersFindings`）會一併撤銷措施自己建立的認定，並連帶撤銷引用那些認定的其他 ENFORCED 措施（原因 `FINDING_REVOKED`，只由連帶撤銷寫入），那些措施上待處理的申訴以 CLOSED 結案，`Recompute` 只跑一次（`TestAcceptingAnAppealWithRevokeFindingsRevokesTheMeasuresThatCiteTheFinding`、`TestCascadeClosesThePendingAppealOfTheRevokedMeasure`）。申訴每個措施一次、資格是「帳號擁有這筆措施」（任何 stint 都算；不看帳號現在有沒有店家或店家有沒有能力：措施以帳號為單位、關店不解除，所有 stint 都關閉的帳號照樣受措施，必須還能申訴；賣家的 Connect 方法不得以 `ActingStore` 擋申訴，`TestAppealWorksForAnAccountWhoseStintsAreAllClosed`），已結束的措施也可以申訴。申訴的 etag 是賣家的 `current_revision`；重送同一個申訴因為「已申訴」回 FailedPrecondition，不是 VersionConflict。內部註記（`CreateMeasureNote`／`MeasureNotes`，權限 `seller.measure_notes.create`、`seller.measure_notes.list`）只新增、不帶 etag、不動 `measures`（`TestMeasureNotesAreAppendOnlyAndDoNotBumpAnyVersion`）。

- admin 改理由、延長、縮短與撤銷的前置條件只有 `model.Measure.UpdateStatementUnavailableReasons`、`ExtendUnavailableReasons`、`ShortenUnavailableReasons`、`RevokeUnavailableReasons`（成立的原因全部列出，結構性的在前；錯誤取第一個），`CanUpdateStatement`、`CanExtend`、`CanShorten`、`CanRevoke` 是「清單為空」，方法的前置檢查與 `Measure.can_*`、`*_unavailabilities` 都只看它們；新增或改動動作的條件時改原因函式，不另寫布林判斷。原因的使用者文字只有 `model.ActionUnavailableText(reason, action)` 一個函式（回 `uitext.Message`）：API 的 `MeasureActionUnavailability.message` 與 `errActionUnavailable` 的 `LocalizedMessage` 都用它（錯誤取第一項的文字）；句子在 `internal/text/zh-TW.json` 的 `staff` 段（`action_unavailable.*`，後台員工受眾，只有 zh-TW，`make uitext` 生成）；新增原因時同時補這個函式與 JSON 條目，句子要有主詞、不寫 client 的畫面名稱。`TestActionUnavailableReasonsAgreeWithTheLegacyPredicatesOnEveryCell`、`TestActionUnavailableReasonsAreExactAndOrdered`、`TestActionUnavailableTextCoversEveryValidCombination`、`TestActionUnavailableErrorSaysTheFirstReasonText`。

- 各動作不能操作的原因（依序，全部適用的都列出，賣家請求造成的凍結排最後；空清單＝可以做）：改理由——`REVOKED`（已撤銷）、`NOT_ACTIVE`（狀態不是已發出、預定生效、生效中）、`REQUEST_PENDING_FROZEN`（曾申覆或有待處理的解除請求）。延長——`REVOKED`、`KIND_HAS_NO_END_TIME`（警告）、`TERMINATION_RECREATE`（未撤銷的終止，要改期間請撤銷後重建）、`NOT_ACTIVE`（停權不在生效中）、`REQUEST_PENDING_FROZEN`。縮短——同延長但沒有 `REQUEST_PENDING_FROZEN`。結束——`REVOKED`、`NOT_ACTIVE`、依據不是 RISK（終止是 `TERMINATION_RECREATE`，依據認定的是 `VIOLATION_BASIS`）、`REMEDIATION_PENDING`（有待處理的解除請求要先裁定）；只有生效中的 RISK 停權能結束。撤銷——`REVOKED`、`APPEAL_PENDING`（申覆待裁定，只經 `DecideAppeal`；已結束的措施可以撤銷）。重排複審：生效中的 RISK 停權。

- 管理員撤銷措施的原因（`ManualRevokeReasonValues`）由 `measure.Service.Revoke` 自己檢查，拒絕 `APPEAL_ACCEPTED`、`FINDING_REVOKED`、`SOURCE_REVOKED`（`TestRevokeInputRules`）；傳輸層的 `AdminRevokeReason` 只是讓請求表示不出這些值，不取代模組的檢查。

- 修改措施只動賣家看得到的內容（理由、結束時間），帶後台 etag。新的結束時間必須晚於現在（不得縮到過去）；比目前晚是延長、比目前早是縮短，RISK 從無固定期間改成有期限算縮短、清除結束時間算延長；依據認定的停權不能清除結束時間，警告不能設結束時間；只有生效中的停權可以延長或縮短，已結束的要加重請另立措施。賣家提出過申覆起，不能改理由、不能延長，只能縮短；有待處理的解除請求時同樣（縮短到期後該請求以 `CLOSED`（`ENDED`）結案）。合併後沒有任何改變時不寫入、不產生新版本、不發事件；實際寫入時同一個 transaction 寫下一版、`version` 加一並重算停權。內部註記不經這條路徑。

- 賣家對措施的請求是 `measure_requests`，狀態 `PENDING` → `ACCEPTED`｜`REJECTED`｜`CLOSED`；`ACCEPTED`／`REJECTED` 必帶裁定理由（1 到 2000 字）與裁定的管理員；`CLOSED` 帶 `close_cause`：`REVOKED`（措施被撤銷，帶管理員）或 `ENDED`（措施已結束而解除請求失去標的，系統結案，沒有管理員）。每個措施一筆申覆、同時最多一筆待處理的請求（兩者由部分唯一索引保證）。申覆可在已結束、預定生效的措施上提出；解除請求（補正）只限生效中的 RISK 停權，可重複提出。接受申覆＝撤銷措施（可帶 `revoke_findings`）；接受解除請求＝同一個 transaction 寫一版結束時間是現在的新版本（作者是裁定的管理員、理由不變）、重算停權、發 `MeasureEnded`，這是結束不是撤銷，認定與撤銷原因不動，賣家仍可申覆，賣家與後台 etag 都前進；駁回只讓後台 etag 前進。裁定要帶措施的後台 etag，先於狀態檢查比對。

- 冷卻由請求推導、不存：同一措施上被駁回（申覆與解除請求合計，`CLOSED` 不計）的請求累計超過 2 次後，每再被駁回一次從那次駁回起算冷卻 7、14、28 天，上限 28 天（`CooldownAfterRejections`）；`NextRemediationTime`（冷卻中）與 `RejectionCooldown`（下一次若被駁回的冷卻長度）由伺服器給，client 不自己算。

- 請求對外的狀態在讀取時推導（`Measure.EffectiveRequest`）：措施不在生效中而儲存為 `PENDING` 的解除請求輸出 `CLOSED`／`ENDED`，結案時間是措施的結束時間；`SubmitAppeal` 在同一個 transaction 先把這種請求以 `CLOSED`（`ENDED`）結案，不擋申覆（`AppealUnavailableReasons` 不算它）；已結束措施上無法裁定解除請求。賣家不能申覆的原因依序：`REVOKED`、`ALREADY_APPEALED`、`APPEAL_WINDOW_ENDED`（只有終止）、`REQUEST_PENDING`；不能請求解除的原因依序：`NOT_RISK`、`NOT_ACTIVE`、`APPEAL_PENDING`／`REMEDIATION_PENDING`、`COOLDOWN`（結構性的在前，第一項是 `NOT_RISK` 或 `NOT_ACTIVE` 就沒有入口）。

## 6. 終止合作

- 終止合作（條款第 21 條，ADR `2026-10-18-seller-governance-consolidated`「決策」的「終止合作」）：`kind = TERMINATION`，一定有事由 `termination_ground`（`NOTICE` 第 21.2 條預告、`MATERIAL_BREACH` 第 21.3 條第 1 款、其他 21.3 CONTRACT，組合由 CHECK 保證（`TestTerminationSchemaConstraints`）；建立時沒有 `ends_at`，API 不接受終止的 `end_time`（只有系統在店家關閉時為預告終止寫入）。`starts_at` 不可變：立即生效的是 `created_at`，`NOTICE` 是 `created_at + 720 小時`（固定時數，不用 `appeal_unavailabilities`、`remediation_unavailabilities`，`reason` 加 `LocalizedMessage`）與 `OpeningBlocker.Text(l)`；句子在 `internal/text/zh-TW.json`（`make uitext` 生成 - 關聯帳號：措施詳情（`Measure`，只有單筆讀取）的 `LinkedAccounts` 由身分快照反查其他帳號的 KYC 申請（`LinkedAccountHits`：身分證號對本人與負責人、統編對統編，銀行帳號不算；解密身分後以金鑰環的每一把金鑰重算 blind index 再比快照，不比申請上已存的 hash，所以 HMAC 輪替前後都比得到；比對在 `kyc.Service.LinkedAccountHits`）；管理員對每個帳號另建一筆 `LINKED_ACCOUNT` 終止（`source_measure_id`，來源必須是另一個帳號、未撤銷、事由不是 `NOTICE` 或 `LINKED_ACCOUNT` 的終止，伺服器用同一支查詢再驗證本帳號確實命中，同一來源對同一帳號同時只能有一筆未撤銷的：部分唯一索引 `measures_linked_source`）。來源撤銷（`RevokeMeasure`、接受申訴、`FINDING_REVOKED` 三條路徑）時同一個 transaction 連帶撤銷以它為來源的關聯終止（`SOURCE_REVOKED`，待處理請求以 `CLOSED` 結案，申覆期間內的關聯店家恢復），關聯措施自己申訴成立只撤銷它。`TestLinkedAccountsListCreateAndCascade`、`TestLinkedAccountsAreFoundAcrossHMACKeyRotation`、`TestSourceRevocationCascadesInTheSameTransactionOnEveryPath`、`TestSourceRevocationRollsBackTogetherWithTheCascade`。

## 7. 治理：通報與案件

- 通報的對象只能是曾經公開過的店（`SubmitReport` 先問 `StoreCards`，與店家卡片同一個規則，已關閉的也算）：從沒公開過的與不存在的是同一個 NotFound，公開的匿名入口不能拿來探測從沒公開過的店家 ID。

- 類別是平台共用的政策分類 `platform/policy`（契約 `api/hawkr/common/v1alpha1/policy_category.proto`）。店家治理各入口只接受自己的子集，伺服器逐入口驗證：檢舉人可選 12 個（沒有 `PLATFORM_ABUSE`），平台判定類別與認定可用 12 個（沒有 `OTHER`：認定的理由要指到條款，不能是「無法歸類」，分案時要改判成有依據的類別或直接設結果）；社群類別 `SPAM`、`HARASSMENT`、`HATE` 兩個子集都不接受。DB 的 CHECK 與 Go 的 `Values()` 一致由 `TestChecksMatchGo` 守。匿名入口 `SubmitFoodSafetyReport` 的類別固定為 `FOOD_SAFETY`（傳輸層寫死；模組的 `SubmitReport` 本身接受檢舉人可選的任一類別）。

- 通報人剛好一種（`reports_reporter_check`）：登入的買家（`reporter_buyer_id`，呼叫方給的業務鍵）或匿名的電話、email（正規化後存），匿名不收佐證。登入的檢舉人不能檢舉自己的店（`SubmitReportInput.AccountID` 與店家的帳號比對；匿名入口在呼叫者登入時也帶上它）。嚴重度不由檢舉人填，也不在通報上：它是案件的欄位，開案時由 admin 決定。`TestSubmitReportValidatesTheReporter`、`TestAReporterCannotReportTheirOwnStore` 驗證。 輸入格式：說明 1 到 2000 字；`product_id`、`order_no` 各 1 到 64 字、不透明、不驗證存在；匿名通報人的電話正規化成 `0` 開頭的 9 到 10 位本國號碼、email 轉小寫且不超過 254 字、稱呼 1 到 100 字，電話與 email 至少一個。

- 去重是 partial UNIQUE，只比對還沒有結果的通報（`outcome IS NULL`），日與週以台北時間為界：登入的同店家、同類別一個台北日一筆；匿名的同電話或同 email、同店家一個台北 ISO 週一筆。去重期間內同一位檢舉人再次送出的不是失敗也不是新通報，而是**補充**：併成原通報的 `report_supplements` 一列（內容與佐證，只新增），原通報的版本前進，不鎖也不改案件（案件只顯示 `unseen_supplement_report_count`，不擋結案）。補充編號 `report_supplements.seq`（1 到 10，每筆通報內唯一，由 DB 保證）。「有新的補充」記在通報上：`reports.supplements_seen_seq` 是管理員最後一次分案、移動或明確已讀（`MarkReportSupplementsSeen`，不讓 etag 前進）這筆通報時看到的最新補充的編號（0 = 沒看過；比編號不比時間，不依賴任何時鐘；三個動作都帶讀到的 etag，etag 含當時全部補充，所以做了就等於看過；`GetReport` 讀取不記、設定結果、結案帶入的預設結果、改嚴重度都不記），`Report.HasUnseenSupplements` = 還沒有結果而且存在編號大於它的補充，案件的 `unseen_supplement_report_count` 是有成員沒看過的筆數（對成員 A 設定結果不會把成員 B 的補充標成看過；`TestSupplementsAreSeenOnlyWhenTheAdminActsOnThatReport`）。一筆通報最多 10 則補充，超過時登入的回 `failed_precondition`，匿名的內容不存、只計入 `discarded_submissions`；原通報已經有結果時不再去重，這次是新的檢舉。登入的補充回原通報與一句說明（`Notice`；去重的鍵含買家，所以一定是呼叫者自己的）；匿名的補充與丟棄不回原通報的內容、聯絡方式或任何檢舉人的資料，只記是以電話、email 或兩者比對到原通報（`matched_by`）：只知道電話號碼的人重送不該讀到原檢舉人的姓名、email 與描述，傳輸層對新的、補充與丟棄回同樣的空回應。每次送出都在同一個 transaction 發 `ReportReceived`（新的、補充、丟棄；匿名帶這次送出的 email 給寄確認信的消費者，不落表）。`TestDuplicateSubmissionReturnsOnlyTheReportID`、`TestReportDedupUsesTaipeiDayAndWeek`、`TestAReportWithAnOutcomeIsNoLongerDeduplicated`、`TestSupplementsAttachToTheOriginalReport`、`TestAnonymousSupplementsRecordHowTheyMatchedWithoutStoringContactDetails`、`TestSupplementLimitIsTenAndAnonymousOverflowIsDiscardedQuietly`、`TestASupplementNeverInvalidatesTheCaseVersion`、`TestEventFailuresRollBackTheWholeCommand` 驗證。

- 通報沒有狀態欄，處理狀態由事實推導（`Report.State`）：沒有案件也沒有結果是待分案，在案件裡而沒有結果是在案件中，有結果是已有結果；案件的狀態由 `closed_at` 推導（進行中、已結案）。結果只有五種（已採取措施、未違規、內容不足、重複、濫報），設定後不能改。分案（`TriageReport`）把待分案的通報放進請求指定的去處（`CaseTarget`：加入這家店這個平台判定類別進行中的案件並帶讀到的案件 id 與 etag，或開新案件並帶嚴重度，嚴重度以案件為準；鎖內驗證意圖仍然成立，案件已關閉或版本前進、或這個類別已經有了進行中的案件，都回案件版本衝突，不悄悄改成另一個去處）；每個類別此刻的去處由伺服器隨 `GetReport` 的 `triage_targets` 給，client 不另讀案件清單推導；移動（`MoveReport`）把還沒有結果的通報移到另一個類別的案件，通報都移走的案件以 `NO_REPORTS` 自動關閉（不算決定、不發事件），所以案件有導出的措施時，最後一筆通報不能移走（案件上的措施不會留在空案件上）；設定結果（`ResolveReport`）：「已採取措施」只能設在案件裡的通報，而且案件要已有可以說「採取措施」的作為（有導出的措施，不論狀態，或已有成員的結果是已採取措施）；決定（`DecideCase`）即結案：採取措施把還沒有結果的成員帶入「已採取措施」、不採取措施帶入「未違規」，說明一併帶入。通報與案件各有 `version`（API 的 etag），分案、設定結果、移動、決定與改嚴重度都要帶讀到的版本，過期回版本衝突；補充讓通報的版本前進，不讓案件的前進。什麼動作此刻做得到，只由 `model.ReportFacts.Availability` 與 `model.CaseFacts.Availability` 回答：API 的 `can_*`、`available_outcomes`、`decision_options` 與指令的前置檢查（第一個原因的句子成為 `failed_precondition` 的訊息）看同一份結果，新增或改動條件時只改它們。案件導出的措施（`source_case_id` 指向它，或措施依據的認定以它的成員為來源）在 SQL 有四處寫法：`CaseMeasureCounts`，與措施清單三支查詢（`AdminMeasures`、`AdminMeasuresPendingRequests`、`AdminMeasuresReviewDue`）的 `source_case_id` 篩選（`source_report_id` 的篩選在三支清單查詢也各一份）；改定義時四處一起改，由資料集測試逐一鎖住。`TestTriageOpensTheCaseForTheStoreAndCategoryAndLaterReportsJoinIt`、`TestResolveRulesFollowTheCaseAndItsMeasures`、`TestMoveReportsBetweenCasesKeepsARecordAndClosesAnEmptiedCase`、`TestMoveIsBlockedByTheReportsStateItsFindingsAndTheCasesMeasures`、`TestDecideClosesTheCaseAndCarriesTheDefaultOutcomeIntoUnresolvedReports`、`TestDecideFollowsTheDerivedMeasuresAndNeverLeavesACaseWithoutAChoice`、`TestConcurrentResolutionsTransitionOnce` 驗證；資料集測試鎖住「清單的成員＝狀態判定式」（`TestListMembershipEqualsTheStatePredicates`）、「可用性＝指令接受什麼」（`TestReportAvailabilityIsExactlyWhatTheCommandsAccept`、`TestCaseAvailabilityIsExactlyWhatTheCommandsAccept`）、「四處導出措施的定義一致」（`TestDerivedMeasuresHaveOneDefinitionInAllFourQueries`），確定性的隨機指令序列守住不變量（`TestRandomCommandSequencesKeepTheInvariantsAndAvailabilityHonest`：每個進行中的案件至少有一個可以選的決定、已結案的案件的成員都有結果）。

- 移動（`MoveReport`）的前置條件：通報在進行中的案件裡、還沒有結果、不是任何認定的來源通報；去處的規則同分案（加入該店該類別進行中的案件，或開新案件）；移動不改 `triaged_at`、`triaged_by_admin_id`（保留第一次分案），並把管理員已看過的補充編號設為當時最新。`resolution_note` 與案件的 `decision_note` 是給檢舉人的結果說明，各 1 到 2000 字，選填。

- 案件的 `version` 與 `updated_at` 在成員進出、成員有了結果、改嚴重度、結案、詢問的建立、記下回覆與撤回時前進；補充、純註記與措施不會。結案欄位只有三種組合：進行中、`DECIDED`（決定 `ACTION_TAKEN` 或 `NO_ACTION`，說明選填）、`NO_REPORTS`（通報都移走，系統自動關閉，無決定、無說明）。

- 案件的嚴重度在開案時由 admin 決定，之後只經 `ChangeCaseSeverity` 修改：必須附原因，寫成案件的一則內部註記（`governance_notes.severity_from`／`severity_to` 記改前改後），與嚴重度同一個 transaction；案件的純註記（`CreateCaseNote`／`ListCaseNotes`）只新增，不改案件的版本與 `updated_at`（`TestChangeCaseSeverityWritesANoteAndOnlyWhileOpen`、`TestCaseNotesAreAppendOnlyAndDoNotBumpTheCase`）。不提供要求賣家配合的操作。

- admin 的通報清單與案件清單各是一張表一個 keyset：通報依 `created_at`、`id`（待分案與某個案件的成員舊到新，其他新到舊），案件依 `opened_at`、`id` 新到舊；翻頁不漏不重：`TestAdminInboxKeysetHasNoGapsOrDuplicates`。

- 匿名檢舉人的電話、email、姓名由 `seller.erase_report_contacts` 分批清成 NULL（記下 `contact_erased_at`），兩條路：有結果的在 `greatest(建立 + 90 天, 結果 + 30 天)` 之後（結果信要寄到這個地址，所以結果設定之後還要留 30 天）；不論有沒有結果，建立滿 365 天一律清（絕對上限：儲存限制，保留要有期限；`ContactRetentionCap`，邊界是嚴格大於 365 天）。沒有結果卻拖滿一年的匿名通報代表處理流程卡住了，所以清理 job 回報其中只靠 365 天上限清掉的筆數（`ContactErasure.Capped`），大於 0 時記一筆 warn log（「強制清除」，帶 `capped` 與 `erased`）。待分案的期限只顯示、不強制，案件也沒有總時長上限，上限由這條保留規則兜底。不做 hash：`TestAnonymousContactErasedByTheOutcomeRuleAndTheAbsoluteCap`（兩條路的邊界與只靠上限的筆數）。補充不另存聯絡方式（只記 `matched_by`），確認信的 email 只在事件裡。 每批 500 筆、每批一個 transaction，直到一批不滿為止。

### 7.1 介面

權限名稱是 `seller.<資源>.<動作>`（後台方法逐一檢查）。通報與案件（`SellerGovernanceAdminService`，每個通報與案件都帶推導出的 `can_*` 與 etag）：

| 方法 | 行為 |
|---|---|
| `ListReports`、`GetReport` | 通報；清單不帶聯絡方式與佐證，`GetReport` 帶補充與佐證；可依狀態、類別、店家、案件篩選 |
| `MarkReportSupplementsSeen` | 標記補充已看過 |
| `TriageReport` | 分案：判定平台判定類別，放進這家店、這個類別的進行中案件，沒有時開新案件（開新案件要給嚴重度）；etag 必填 |
| `ResolveReport` | 直接設定結果（已採取措施只能設在案件裡的通報，而且案件要已有作為）；etag 必填 |
| `MoveReport` | 移到另一個類別的案件；通報都移走的案件以 `NO_REPORTS` 關閉；etag 必填 |
| `ListCases`、`GetCase` | 案件（帶 `decision_options`、成員數、導出的措施數與 `unseen_supplement_report_count`） |
| `DecideCase` | 決定即結案：採取措施或不採取措施，還沒有結果的成員帶入結果；etag 必填 |
| `ChangeCaseSeverity` | 改嚴重度：必須附原因，寫成案件的註記；etag 必填 |
| `CreateCaseNote`、`ListCaseNotes` | 案件的內部註記，只新增，不帶 etag |

案件詢問與主管機關來函的方法見 §8。措施與認定（權限 `seller.measures.*`、`seller.measure_notes.*`、`seller.violations.*`；註記存在 `governance_notes`，掛在措施或案件剛好一個）：

| 方法 | 行為 |
|---|---|
| `CreateMeasure` | 建立措施（violation 依據：新建或引用既有認定；risk 依據：風險類型；`request_id` 冪等；第一則內部註記必填；可帶 `source_case_id` 連到案件、`source_authority_order_id` 連到來函） |
| `GetMeasure`、`ListMeasures` | 篩選：`account_id`、`store_id`、`kind`、`basis`、`state`、`request_state`、`request_kind`、`review_due`、`source_case_id`、`source_report_id`、`source_authority_order_id`；`request_state=PENDING` 是申訴與補正合一的收件匣 |
| `UpdateMeasure` | `update_mask` 只能列 statement、end_time；etag（`measures.version`）必填；提出申訴後只能縮短 end_time |
| `EndMeasure` | 結束生效中的 RISK 措施 |
| `RevokeMeasure` | 撤銷（`revoke_findings` 連帶撤銷，只在 `can_revoke_findings` 時可設）；申訴待裁定時回 `failed_precondition` |
| `ScheduleMeasureReview` | 重排 RISK 的複審期限（必填內部註記） |
| `DecideAppeal` | 裁定申訴（接受 ⇔ 撤銷，`APPEAL_ACCEPTED`） |
| `DecideRemediation` | 裁定補正（接受 ⇒ 措施結束，不是撤銷；不帶 `request_id`；權限 `seller.measures.decide_remediation`） |
| `CreateMeasureNote`、`ListMeasureNotes` | 內部註記，只新增，不帶 etag |
| `GetViolation`、`ListViolations` | 認定，唯讀 |

賣家端（`SellerAppService`）：`ListMyMeasures`（`state` 篩選）、`GetMyMeasure`、`SubmitAppeal`、`RequestRemediation`（etag 是賣家的 `current_revision`，必填；提出請求不改變 etag，重送回 `failed_precondition`）；`GetMyStore.suspended` 是帳號此刻是否停權。檢舉人端：`CreateReport`、`ListMyReports`（登入）與 `SubmitFoodSafetyReport`（匿名）。公開的違規列表不存在；停權的店家依停權事件下架。

佐證讀取：`GET /api/files/admin/seller/reports/{report_id}/evidence/{position}`、`GET /api/files/admin/seller/measure_requests/{request_id}/evidence/{position}`、`GET /api/files/admin/seller/case_inquiries/{inquiry_id}/evidence/{position}`（權限 `seller.report_evidence.get`、`seller.measure_request_evidence.get`、`seller.case_inquiry_evidence.get`），每次讀取先寫 `evidence_accesses`。管理員停權就是建立 RISK 停權措施，沒有獨立的停權方法，也沒有 SQL 後備流程：直接改表會繞過推導點、事件與稽核，也會讓停權期間與措施不一致。

## 8. 主管機關來函與案件詢問

- 主管機關來函（ADR `2026-10-18-seller-governance-consolidated`「修訂：主管機關來函、保存期限與措施的來源來函」）：`authority_orders` 是獨立的收件（不是通報），對象 `authority_order_targets` 是任何帳號（選填店家與商品；`UNIQUE NULLS NOT DISTINCT`，整個帳號加它的店家是重疊，拒絕），保存期限 `hold_until` 預設收文後 4416 小時、只能延長（`authority_order_hold_extensions` 只新增），調取資料完成時延到 `max(目前, 提供時間 + 4416 小時)`（`TestCompletingADataRequestExtendsTheHoldToSixMonthsAfterProvision`）；完成時每個對象必填告知（已告知、暫不告知＋確認日期、由措施告知；`WITHHELD` 之後可以 `RecordAuthorityTargetNotice`，被取代的值留歷史）；`etag` 只給完成、延長與記下告知（`conflictTarget` 是 `authority_order`）；`request_id` 的範圍是（登記的管理員, request_id）；不發事件。保存只擋刪除（兩段清理）、不影響恢復營業（`TestReopenIgnoresTheAuthorityHold`）；寫入保存的一方先鎖店家列、清理鎖住候選之後再問 `StoreHolds`（固定交錯測試 `TestPurgeRechecksTheAuthorityHoldAfterLockingTheCandidates`、`TestPurgeStageTwoRechecksTheAuthorityHoldAfterLockingTheCandidates`、`TestAuthorityOrderRegisteredAfterThePurgeShowsAlreadyPurged`）。**撤銷登記**（`RevokeAuthorityOrder`，登記錯誤的更正）：只在完成之前（`Availability().Revoke`），必附原因、帶 etag；撤銷之後保存解除（`StoreHolds` 不看已撤銷的來函）、不在處理中（`Open()`、清單 `OPEN`、後台待辦的「主管機關來函」都排除）、不能完成、延長或記下告知（原因 `REVOKED`），也不能再當作措施的來源（`OrdersNamingMeasureTarget` 以 `FOR SHARE` 讀來函列，與撤銷的 `FOR UPDATE` 串行）；紀錄（`revoked_at`、`revoked_by_admin_id`、`revoke_reason`）保留；冪等以管理員為範圍：已由同一位管理員撤銷時回原本的紀錄（`already_revoked`），別人撤銷的回 failed_precondition；權限 `seller.authority_orders.revoke`（`TestRevokeAuthorityOrderReleasesTheHoldAndKeepsTheRecord`）。記下告知的可用性（`Availability().RecordNotice`，API 的 `can_record_notice`）與每家店的建立措施入口（`AuthorityTargetStore.can_create_measure`／`can_create_termination`，與 `CreateMeasure` 的 `TerminationTarget.AllowsMeasure`／`BlockFor` 同一份規則）由伺服器推導（`TestTargetNoticeAndMeasureEntryAvailabilityAreServerDerived`）。措施的來源來函 `measures.source_authority_order_id` 與認定引用 `finding_authority_orders`：來函必須指名措施的帳號（指名店家時只算那一家），`ListMeasures.source_authority_order_id` = 明確連結 ∪ 認定引用。新資料的保存期沿用「治理資料沒有保存政策」。 來函登記時沒有指定期限，收文後預設：限制或移除商品、暫停帳號 48 小時，調取資料與其他 72 小時；期限與保存期限都從收文時間起算。

- 案件的詢問（ADR 2026-10-18-seller-governance-consolidated 文末「修訂：案件的詢問」）：`CreateCaseInquiry`／`RecordCaseInquiryReply`／`WithdrawCaseInquiry`／`CaseInquiries`（`governance/inquiry.go`）。每個案件同時最多一筆還沒結束的詢問；發詢問在 `CaseFacts.Availability().CreateInquiry` 裡可做才寫（案件進行中、店家個資還沒清除、沒有還沒結束的詢問；**只是關店不擋**），期限預設 72 小時、可指定 24 小時到 14 天、建立後不能改；回覆一則即結束（管理員記下系統外收到的內容，**收到的時間**不早於詢問建立、不晚於現在，附件最多 5 份、機敏、以 `media.Uploader{ID: 管理員, Admin: true}` 轉正，`mediaref.FinalizeEvidence` 收 `media.Uploader`）。建立、記下回覆、撤回都讓案件的 `version` 與 `updated_at` 前進（`TestInquiryCommandsAdvanceTheCaseVersion`）；指令不帶 etag：建立帶 `request_id`（範圍是（管理員, request_id），重送先於有狀態的驗證，鎖住案件之後再查一次），回覆與撤回重送回原本的結果。案件的「等賣家」（`Case.AwaitingSeller`：進行中而且有還沒結束的詢問）與「待決定」（進行中而且不在等賣家，沒有獨立的 Go 判定式）在進行中時剛好一個成立，待決定的開始時間只在 `seller.review_case_decision`（`max(開案, 最後一筆詢問的收到時間或管理員撤回時間)`，輸出為 `Case.DecideDeadline.Start`；測試由 fixture 的事實比對，`TestCaseListAwaitingSellerAgreesWithTheGoPredicates`）；清單的 `awaiting_seller` 與 `OpenCaseInquiries` 同一個定義。結案（決定，或移動造成的 `NO_REPORTS`）在同一個 transaction 由系統撤回還沒結束的詢問（`CASE_CLOSED`，`TestClosingTheCaseWithdrawsItsOpenInquiry`、`TestDecideAndAConcurrentReplyNeverLeaveAnOpenInquiryOnAClosedCase`）。詢問不發事件（沒有消費者）。回覆附件讀取：`ReadEvidence` 的 `kind` 加 `INQUIRY`（以詢問 ID 定址，`/api/files/admin/seller/case_inquiries/{inquiry_id}/evidence/{position}`，權限 `seller.case_inquiry_evidence.get`），讀取紀錄的擁有者加 `inquiry_id`（`TestInquiryEvidenceReadIsRecordedBeforeTheRead`）。詢問不存在的 NotFound 沒有伺服器句子（`apperr.NotFound` 的訊息是空字串，httpapi 換成 Connect code 的預設文字）。詢問的說明、回覆與附件沿用「治理資料目前沒有保存政策」。

## 9. 佐證與 media 引用

- 所有 media 引用（logo 與封面、業者圖片、KYC 證件、治理佐證）只由 `seller.media_sync` 同步 job 寫入（`internal/mediaref`）：寫入端在 transaction 外只 `Finalize`（轉正，不建立引用），transaction 內寫業務列、把被換掉或終態清掉的資產記成退場（`retired_assets`）、遞增 `media_ref_sync.seq` 並排入同步；job 以 (ref_type, ref_id) 去重（含執行中），Link 業務列目前的資產、精確 Unlink 退場的資產，結算時 seq 變了或退場資產還在第二次解除的等待期內就再跑一輪。已退場的資產不能寫回同一個 ref（同一個 staged token 重新轉正會回到同一個資產，回 InvalidInput）。新資產要在 media GC 的 7 天寬限（從資產建立起算）內被 Link，重試用盡或 job 遺失由 `seller.media_sweep`（每 15 分鐘）補排 `synced_seq < seq` 的 ref，監控訊號是擁有者端的落後時間（見 `docs/adr/2026-10-03-media-references-owner-side.md`）。沒有補償路徑。決策見該 ADR。

- logo 與封面的 media 引用以 `ref_id = store_id` 登記，店家列同時存 object key 與 asset ID（`stores_image_assets_check` 成對）。換圖在鎖住店家列的 transaction 內把被換掉的那一張記成退場，關店不動它們（可逆），個資清理把兩張都記成退場（清理過的店家沒有資產）。`TestImagesLinkByStoreIDAndUseVersion`、`TestSyncBetweenFinalizeAndCommitKeepsTheStoreImages`、`TestImageFailureAfterFinalizeLeavesNoReference`，以及 `internal/closing` 的 `TestCloseKeepsTheImagesAndTheirMediaReferences`、根套件的 `TestCloseKeepsTheImagesUntilThePurgeReleasesThem`。

- 佐證（通報、申訴與詢問回覆）在 transaction 外轉正（不建立引用），以通報、申訴請求或詢問的 UUID 為 `ref_id` 登記 `GOVERNANCE_EVIDENCE`：寫入的 transaction 內排入同步；撞到重複時沒有寫入，轉正的資產沒有引用、由 GC 回收。佐證的鍵是 `(report_id, submission_seq, position)`：第幾次送出（0 是原通報、1 到 10 是補充）加次內位置 0 到 4，所以「每次送出最多 5 張」由 DB 保證（`supplement_id` 與 `submission_seq` 一致由 CHECK 與複合外鍵保證）；API 的「第 n 張」與 `/evidence/{n}` 是依送出的順序與次內位置編的序號，讀取時算、不存，讀取紀錄（`evidence_accesses`）以真正的鍵指向那一張。佐證寫入後不可改、不可刪，所以沒有退場。`TestReportEvidenceIsLinkedByTheSyncJobUnderTheReportID`、`TestAppealEvidenceIsLinkedByTheSyncJobUnderTheRequestID` 驗證。

- 佐證是機敏檔（ADR 2026-10-18-seller-governance-consolidated「決策」的「佐證」）：轉正時 media 必須回報 `is_secure`，公開上傳的在寫入之前回 InvalidInput（`EvidenceTokens`），什麼都不寫（`TestEvidenceMustBeSecureAssets`）。後台以 `ReadEvidence(adminID, kind, refID, position)` 讀（`kind` 是 `REPORT` 以通報 ID、`REQUEST` 以申訴請求 ID、`INQUIRY` 以詢問 ID 定址）：授權是後台的權限（`httpapi/adminauth`），模組只要求管理員 ID，沒有理由或限時授權；紀錄不存在、位置沒有佐證、種類與 ID 對不上都是 NotFound，不寫紀錄、不問 media；transaction 內先寫一列 `evidence_accesses`（`(report_id, position)` 或 `(request_id, position)` 剛好一個，以複合外鍵指向那一張佐證：佐證不可改，所以就是送出的檔；管理員、時間；不含內容），commit 之後才經 `mediaref.ReadSecure`（與 KYC 證件共用）取內容，紀錄寫不進去就不讀，media 失敗時紀錄仍在；media 讀不到時分成 `ErrFileNotSynced`（引用的同步還沒結算，`MediaSyncSettled` 在呼叫之前讀）、`ErrFileMissing`、`media.ErrNotSecure`。`TestEvidenceReadIsRecordedBeforeTheBytesAreRead`、`TestEvidenceReadFailuresAreDistinguished`。佐證的 asset ID 與 object key 不對外：API 只回位置與檢視網址（`httpapi/seller.AdminEvidence`）。

- 證件圖片的讀取（`ReadDocument`）經 media 的 `ServerReadSecureAsset`，整份內容在記憶體（media 的 RPC 不串流），只適合證件大小的檔案。該 RPC 要求 `secure/` 前綴的物件，所以轉正時要求 media 回報 `is_secure`（草稿存檔拒絕非機敏的證件）；讀取時 media 回 400（不是機敏資產）是 `media.ErrNotSecure`，與找不到分開。每次讀取都要記錄，簽章網址記不到讀取、R2 存的又是 media 加密過的密文，所以由擁有者的端點代理；沒有通用的 admin 機敏下載，證件影像只經這條端點。

- 證件與佐證讀取時 media 的失敗分三種（`mediaref.ReadSecure`，兩者共用；`TestKYCDocumentReadFailuresAreDistinguished`）：引用的同步還沒結算（`media_ref_sync.synced_seq < seq`，新轉正的證件，job 最多落後一個週期）是 `ErrFileNotSynced`，端點回 503 加 `Retry-After`（warn）；同步過了、資料庫有這張證件而 media 說沒有是 `ErrFileMissing`，與 `media.ErrNotSecure` 都是資料不一致，端點回 404 並記 error（要人處理）。三種都已經先寫了讀取紀錄。

## 10. 能力與權限

- 能力只由 `model.CapabilitiesOf(store)` 推導（store 的 `Sanctions` 與 `Conditions` 是讀店家時由 SQL 帶上的這一刻的結果：`stint.Load` 與批次讀取都經 `stint.WithConditions`；沒有推導過的條件一律不滿足），回傳 `model.AllCapabilities()` 每一項的 `{Active, Missing}`，缺的條件依 `Requirements()` 的順序。每個能力需要哪些條件只寫在 `model/capability.go` 的 `needs` 表（停權白名單 `GrantedWhenSuspended` 與缺項都由它推導，不另寫規則），結果是：停權（不論依據，§10.1）時只剩能力檢查 ADR 的白名單，其餘缺 `NOT_SUSPENDED`；等待刪除時經營類（`CAP_STOREFRONT_WRITE`、`CAP_PRODUCT_MANAGE`、`CAP_MARKETING`、`CAP_INVOICE_MANAGE`、`CAP_SHIPPING_SETUP`）與 `CAP_ACCOUNT_CLOSE`（它由刪帳流程關閉）缺 `NOT_PENDING_DELETION`；物流建店（`CAP_SHIPPING_SETUP`）另缺 `KYC_APPROVED`（`Conditions.KYCApproved` 為假）；關閉時每個能力缺 `STORE_ACTIVE`。`CAP_PUBLIC_LISTING` 是店家狀態不是動作：只在 `CapabilitiesOf` 的結果，不在 `Capabilities()`（方法不能宣告它，`checkDeclarations` 拒絕），不進 gateway 的 header（`ActiveCapabilities` 只回啟用的動作類能力）。`Store.Can` 與 `CapabilitiesOf` 同一個推導（`TestStoreCanAgreesWithCapabilitiesOf`），非動作類能力 panic（程式錯誤，`TestStoreCanRejectsCapabilitiesItCannotAnswer`）。`Authorize(store, capability)` 是檢查：已關閉 NotFound；停權 PermissionDenied（帶 `ReasonSellerSuspended`）；其他前置條件沒有滿足 FailedPrecondition（帶 `ReasonSellerRequirementMissing`，metadata `missingRequirements` 是缺的條件的值名（不加前綴），依列舉的數字由小到大以逗號連接）；條件沒有推導過的店家一律拒絕（程式錯誤，`TestStoreWithoutDerivedConditionsHasNoCapability`）。profile、logo、封面的寫入要 `CAP_STOREFRONT_WRITE`，`CloseCurrent` 要 `CAP_ACCOUNT_CLOSE`。`TestCapabilitiesOf*`、`TestPublicListingMirrorsMissingExposure`、`TestAuthorizeDenialsCarryTheirReason`、`TestActingStoreRequiresAnApprovedKYCFlowForShippingSetup`、`TestCapabilitiesGateStoreWrites` 驗證。

- 能力檢查 fail-closed：`ActingStore(account, capability)` 每次讀 DB，讀取失敗回錯誤，呼叫方一律拒絕。`TestActingStoreFailsClosed` 驗證。

- 停權不阻擋關店與刪帳號：`TestSuspendedSellerCanCloseStore`，以及 `accountdeletion` 的 `TestAdminRequestDeletesSuspendedSeller`。

- 能力名稱沿用 ADR `2026-09-18-seller-capability-authorization` 及其 2026-10-08 修訂；能力的檢查（`ActingStore`）見 ADR `2026-09-29-seller-suspension-and-business-identity-in-monolith`。

### 10.1 能力表與停權白名單

賣家能不能做某件事只在 seller 模組推導一次（`CapabilitiesOf`）：每個入口宣告它需要的能力，執行處只檢查能力集合的成員，不自己從停權或生命週期推導；deny-by-default，入口沒有顯式宣告能力就不能被賣家存取。能力層沒有 tier 維度，不承載「何時停權」的商業判定（§5）。

| Capability | 語意 | 啟用時 | 停權時 |
|---|---|:---:|:---:|
| `CAP_ACCOUNT_SELF_READ` | 看自己 profile 與停權狀態 | ✓ | ✓ |
| `CAP_STOREFRONT_WRITE` | 店面設定寫入（profile、logo、封面、onboarding、KYC 草稿、送出與取消） | ✓ | ✗ |
| `CAP_PRODUCT_MANAGE` | 供給定義：商品建立、編輯、上下架、匯入、分類、運費試算、認證、hashtag；物流方案供給 | ✓ | ✗ |
| `CAP_ORDER_FULFILL` | 既有契約的履約：出貨、物流、售後、訂單查詢、PayUni 狀態；結算與撥款檢視 | ✓ | ✓ |
| `CAP_ORDER_CONTRACT` | 收縮型：取消出貨與退款受理 | ✓ | ✓ |
| `CAP_MARKETING` | 行銷經營：優惠券建立、CRM、貼文發佈、AI 助理、dashboard、報表、市場行情查詢、雷達與追蹤增刪 | ✓ | ✗ |
| `CAP_CONTENT_CONTRACT` | 收縮型：刪自己貼文、自行下架貼文、撤自己券 | ✓ | ✓ |
| `CAP_CHAT_SEND` | IM 送訊（停權時 IM 再做訂單關聯細分） | ✓ | ✓（受限） |
| `CAP_CHAT_READ` | IM 讀取 | ✓ | ✓ |
| `CAP_NOTIFICATION` | 通知收件箱、偏好、device-token | ✓ | ✓ |
| `CAP_ACCOUNT_CLOSE` | 收縮型：關店 | ✓ | ✓ |
| `CAP_INVOICE_MANAGE` | 發票與稅務憑證的查詢與設定；擴張型與唯讀查看 | ✓ | ✗ |
| `CAP_INVOICE_TAX_REMEDY` | 稅務身分申請、補件、延長申請、自行開票責任條款同意與自行開立回報——救濟管道 | ✓ | ✓ |
| `CAP_SHIPPING_SETUP` | 物流建店、啟用與關閉配送方式；前置條件是 KYC 流程核准 | ✓（KYC 核准後） | ✗ |
| `CAP_PUBLIC_LISTING` | 狀態不是動作：買家看得到店面、可以結帳；缺的條件就是 `MissingExposure` | 條件齊全時 | ✗ |

- 唯讀不等於放行：dashboard、CRM 查詢、報表、AI 助理、發票查詢即使純唯讀也不在停權白名單。
- 停權白名單（`GrantedWhenSuspended`）＝動作類能力中不需要 `NOT_SUSPENDED` 的那些，納入判準只有四類：既有訂單、出貨、售後的處理；收縮型操作（只減不增）；救濟管道（申訴、補件）；通知與看自己狀態。新增能力判不進這四類，就不能放進不需要 `NOT_SUSPENDED` 的那一類。
- `CAP_PRODUCT_MANAGE` 與 `CAP_ORDER_FULFILL` 的分派：碰供給定義（方案、版本、發布、上下架、開通）→ `CAP_PRODUCT_MANAGE`（不在白名單）；碰既有契約的履約（日曆、例外、承載、出貨、結算檢視）→ `CAP_ORDER_FULFILL`（在白名單）。停權賣家必須處理得完既有訂單，但不得再產生新的供給。
- 發票軸是兩個 token：白名單成員資格由「能力需不需要 `NOT_SUSPENDED`」編碼，同一個 token 不可能既擋又放行，而發票同時需要兩類。把 `CAP_INVOICE_TAX_REMEDY` 設成需要 `NOT_SUSPENDED` 會靜默失效（只有停權賣家遇到：補不了稅務件，審核不完成，恢復後依然接不了單）。
- 停權的兩類來源（依據風險類型的措施、只依據認定的措施）共用同一個白名單，差異只在生命週期。

### 10.2 入口與傳播

- Connect：`SellerAppService` 每個方法在 `internal/httpapi/seller/declaration.go` 的宣告表宣告需要的能力，或附理由字串的豁免；interceptor 讀取並執行，呼叫 `seller.ActingStore` 把店家放進 ctx，handler 不自己檢查能力。`checkDeclarations` 在建構 interceptor 時雙向對照宣告表與 service descriptor，缺宣告、多餘宣告、宣告不合法（既無能力也無豁免理由）任一項都使 service 不能啟動。模組對 KYC 等寫入再以 `Authorize` 檢查一次同一個能力（深度防禦）。`GetMyStore` 回傳呼叫者目前的能力（`SellerCapability`），client 事前即知哪些操作可用，伺服器仍逐方法檢查。
- 停權狀態沒有快取也沒有標記：能力在每個賣家請求由讀店家時帶上的條件（`seller.store_requirement_flags`）與有效措施（`seller.effective_measures`）一次推導，措施 commit 後的下一個請求即生效。每個賣家請求多一次索引讀取。
- 轉發到 gateway 的請求（`internal/legacy/gatewayproxy`）：對每個轉發的登入請求解析 `X-Buyer-Id`、`X-Store-Id`，帶 `X-Seller-Capabilities`（只放啟用的動作類能力，不含 `CAP_PUBLIC_LISTING`，與 `X-Store-Id` 同時出現）與 `X-Seller-Suspended`（缺省表示未停權；依據風險類型的停權是 `sellerreason.Of` 的原因碼，只依據認定的停權是 `SUSPENDED_GOVERNANCE`）；同一個請求先清掉呼叫者自帶的這些 header 再設值。推導或查詢失敗、現任店家沒有任何能力（已關閉）卻出現、能力 token 不認得、停權原因不認得，一律回錯誤，請求不轉發。能力 token 與 gateway 的 `authz.Capability` 是同一組字串，由 `TestCapabilityTokensMatchGateway` 守；token 不進 CodeMeta。
- 停權的寫入點只有措施：寫入措施的 transaction 發出 `StoreSuspended`／`StoreUnsuspended` 模組事件，舊契約的 `seller.suspended`／`seller.unsuspended` MQ 訊息由 `internal/legacy/sellerrelay` 轉出；能力檢查與結帳收斂點不消費這兩個事件，一律以權威資料推導，與事件消費順序無關。
- `can_accept_orders`（舊契約 SellerService 回應的旗標，`internal/legacy/sellerserver` 以店家的可曝光狀態 `Exposable` 產出）是 gateway 之外的收斂點讀取的兜底旗標。

## 11. 關店、恢復營業與兩段清理

- 關店要先確認沒有未結訂單：`CloseCurrent` 在 transaction 外問 `Orders`（含未付款與售後處理中），有未結訂單回 FailedPrecondition、查詢失敗回 Unavailable，都不關店；交易內鎖帳號後確認仍是同一個 stint，否則回 Unavailable 請重試。`TestSelfCloseIsRejectedWhileTheStoreHasOpenOrders`、`TestSelfCloseFailsClosedWhenOrdersCannotBeChecked`、`TestSelfCloseRechecksTheStintInsideTheTransaction`。

- 關店的紀錄只在 `store_closures` 一處（`stores` 沒有 `deleted_at`、`closed_by`、`closed_by_measure_id`）：每次關店一列，`reopened_at` 為 NULL 的是目前這一次（`store_closures_current` 保證每個 stint 最多一列）；`closed_by`（`ACCOUNT_OWNER` 賣家自己、`TERMINATION` 終止合作、`ACCOUNT_DELETION` 隨帳號刪除）；`TERMINATION` 一定有 `closed_by_measure_id`（造成關店的措施，關店當時的事實，理由與作者在措施裡；`store_closures_measure_check`），其他沒有。`stores.status = 'CLOSED'` 的 stint 恰有一列目前的紀錄、不是的沒有，由資料庫在 commit 時保證：`stores.current_closed_at` 指向目前那一列（`stores_current_closure_check` 綁住它與 status），`stores_current_closure_fkey` 與 `store_closures_current_fkey` 是互指的可延遲複合外鍵（`store_closures.open_closed_at` 是 `reopened_at` 為 NULL 時的 `closed_at`，生成欄位）；`closing` 套件（`close`、`Reopen`）在同一個 transaction 寫兩處（`CloseStore` 設指標、`ReopenStore` 清指標），資料庫約束由 `TestDatabaseGuaranteesClosedIffOneCurrentClosure` 守，各路徑之後的狀態由 `TestClosedStoresHaveExactlyOneCurrentClosure` 守；讀取經 `stint.WithClosures`（`Store.Closure` 帶關店時間、原因與措施，沒有關閉時是 nil）。管理員沒有直接關店的方法（沒有 `closed_by = ADMIN`，也沒有權限 `seller.stores.close`）。**所有關店走同一條路徑 `closing.close()`**：記紀錄、結束帳號上尚未結束的預告終止（條款 21.2，賣家在預告期間或生效後自己關店、終止的關店、刪帳關店都一樣；寫一版 `ends_at` 是關店時間、作者是系統、發 `MeasureEnded` 並重算停權，不做的話 `stint.Derive` 會永遠擋住 21.2 的重新申請）、移除 SELLER、發 `StoreClosed`、公告不可曝光。關店可逆：logo、封面與它們的 media 引用留著（卡片仍對外隱藏它們），不可逆的下游動作（relay 的 `seller.deleted`、圖片釋放）都在退場（第一段清理）的 `StoreRetired`。恢復營業時結束目前這一列（補 `reopened_at`），歷史永久保留。紀錄是稽核，不是申請人的欄位，個資清理不動它。`TestEveryClosePathRecordsWhoClosedTheStore`、`TestTheClosureSurvivesThePIIPurge`、`TestClosureSchemaConstraints`、`TestStoreClosuresSchemaConstraints`、`TestStoreClosuresMigrationBackfillsTheCurrentClosure`、`TestNoticeEndsOnEveryPathThatClosesTheStore`、`TestCloseKeepsTheImagesUntilThePurgeReleasesThem`。

- 終止合作生效後的關店（`closing.EffectTermination`，job `seller.termination_effect` 以 measure_id 為唯一鍵、排在 `starts_at`；River 的唯一狀態集合含 running、不含 completed）：三步——(1) transaction：鎖帳號全部的 stint，重讀措施（已撤銷或已結束就結束），以 `max(starts_at, now)` 重算停權期間；(2) transaction 外 `Orders.HasOpenStoreOrders`（fail-closed：查詢失敗回錯誤讓 job 重試），有未結訂單就結束這一次；(3) 關店 transaction：identity 帳號鎖、帳號全部的 stint、**重讀措施並重新判斷**（未撤銷、生效中）、stint 仍是第 2 步查過的那一個而且不在等待刪除，才以 `TERMINATION` 關店。帳號在等待刪除時視為終局、不做事，由刪帳以 `ACCOUNT_DELETION` 關店。「待關閉」不存（生效中的終止加 stint 未關閉）。`order.completed` 經 `buyerconsumer.AdvanceStore` 加速一次，每小時 `seller.reconcile_terminations`（`closing.ReconcileTerminations`，啟動即執行）保底，遺失的 job 與被去重掉的加速都只是晚關。`TestNoticeTerminationIsScheduledThenTakesEffect`、`TestTerminationClosesTheStoreOnlyWithoutOpenOrdersAndFailsClosed`、`TestTerminationRechecksTheMeasureInsideTheClosingTransaction`、`TestTerminationOfAnAccountWaitingForDeletionIsTerminalAndTheDeletionClosesIt`、`TestReconcileTerminationsCoversALostJob`。

- 恢復營業（可逆關店，`closing.ReopenPlan`／`closing.Reopen`，在撤銷、接受申訴與連帶撤銷的同一個 transaction）：恢復 ⇔ 帳號最近的 stint 是由 `TERMINATION` 關閉的、未清理、造成關店的那一筆（目前關店紀錄的 `closed_by_measure_id`）已撤銷（這次撤銷之前就已撤銷，或在這個 transaction 要撤銷的措施裡）、撤銷之後（同一個 transaction 要撤銷的措施不算，含連帶撤銷的）帳號沒有任何 ACTIVE 的終止合作、`¬RetireDue`（`RetireDueStores` 不選它，與清理同一個判斷式）（預定生效的預告終止與已結束的不算：`stint.Effective`）、帳號是存活的（不在等待刪除）；動作是 `CLOSED → ACTIVE`（同一個 `store_id` 與店號，商品與 KYC 欄位都在）、結束目前的關店紀錄、重新授予 SELLER、重新公告可曝光、發 `StoreReopened`、補排 PayUni 被放棄的綁定（`payuni.Resume`：sync job 對已關閉的店不做事、PENDING 的綁定會被放棄）、`Recompute`。**恢復與否在改動任何請求之前決定**（`measure.planRevoke`）：否則期滿前提出、期滿後裁定的申覆，會因為同一個 transaction 裡待處理申覆結案、legal hold 消失而不能恢復。帳號已開新店（21.2 允許，最近的 stint 不是已關閉的）、帳號在等待刪除、保留期已滿而清理還沒跑、帳號還有別的生效中終止、或撤銷的不是造成關店的那一筆（預告終止先關店，之後在同一個已關閉的店建立並撤銷 21.3，店仍因預告終止而關閉）時只撤銷（`TestRevokingATerminationThatDidNotCloseTheStoreNeverReopensIt`、`TestTwoTerminationsKeepTheStoreClosedUntilTheLastOneIsRevoked`、`TestCascadeRevocationReopensOnlyAccountsWithNoOtherEffectiveTermination`）。清理與恢復都鎖帳號全部的 stint，互相串行。`TestRevokingATerminationInsideTheAppealWindowReopensTheSameStore`、`TestAnAppealFiledInTimeAndDecidedAfterTheDeadlineStillReopensTheStore`、`TestRevokingAfterTheRetentionButBeforeThePurgeJobDoesNotReopen`、`TestRevokeDoesNotReopenWhenTheAccountHasANewStoreOrIsLeaving`、`TestRetentionDependsOnWhoClosedTheStore`、`TestLegalHoldCoversTheWholeAccountAndLinkedAccounts`、`TestReopenRequeuesThePayUniBindThatWasDroppedWhileClosed`。

- 兩段清理只在期滿後做：第一段（退場）的候選必須是 `CLOSED`、還沒退場、`now > retire_after`，第二段的候選必須已退場、個資還沒清理、`now` 晚於同一個式子以 `StoreRetention` 計的期限；兩段的時間條件只有 `RetireDueStores` 一支查詢（清理與恢復營業共用），保存條件只有 `StoreHolds` 一支。資料庫保證：`stores_retired_check`（已退場 ⇒ 已關閉、說明、獎項、網站是 NULL）、`stores_closed_images_check`（已退場的店沒有圖片）、`stores_pii_purged_check`（已清理 ⇒ 已退場、已關閉、店名與聯絡地址是 NULL），都不檢查時間。`retire_after`：`closed_by = TERMINATION` 是 `greatest(關閉時間 + 段的時數, 帳號上未撤銷的終止合作中最晚的 starts_at + 申覆期間 4416 小時)`（已撤銷的終止不延長，造成關店的那一筆撤銷後也不再延長；關店之後才發現的 21.3 事由、關聯終止的申覆期限可能比較晚；`TestRetentionFollowsTheLatestAppealDeadlineAmongAllTerminations`、`TestARevokedLaterTerminationDoesNotExtendTheRetention`），其他是關閉時間 + 段的時數（第一段 720 小時、第二段 4416 小時）；`appeal_hold`：帳號上未撤銷的 `TERMINATION` 措施有待處理申覆，或帳號上未撤銷的 `LINKED_ACCOUNT` 終止其來源措施有待處理申覆時，帳號全部已關閉的 stint 兩段都暫停（`TestRevokedLinkedTerminationDoesNotHoldThePurge`）。退場的同一個 transaction 釋放 logo 與封面（記成退場、排入同步）並發 `StoreRetired`。KYC 與 PayUni 的子表只清店家列已清理的列，清理過的列由 `*_purged_check` 保證被清的欄位是 NULL。批次以 `store_id` 做 keyset、沒有上限，重跑是 no-op，處分的身分快照不受影響，關店之後才到的 PayUni 通知不把 `reason` 寫回。清理與寫入保存條件的競態（READ COMMITTED 下候選語句的快照看不到在它開始之後、掃到那一列之前才 commit 的 hold，那一列也沒有被寫入方鎖過）：每一段在候選鎖住（`FOR UPDATE SKIP LOCKED`）之後，以新的語句再判斷時間（同一支查詢限定在候選上）並問 `StoreHolds`，只處理成立而且沒有被保存的；寫入保存條件的一方（終止的申覆、關聯終止來源的申覆、來函的登記、完成與延長）都先鎖被保護帳號的店家列，所以候選鎖住之後不會再出現新的保存，寫入方鎖到時店家已退場或已清理就是登記太晚。`submitRequest`（申覆）在鎖之後才取 `now`，並重讀措施所在店家的 `retired_at`：只在措施是終止合作、而且店家目前這次關閉是它造成的（`store_closures` 目前那列 `closed_by = TERMINATION` 且 `closed_by_measure_id` 是它）時，已退場就回「申覆期限已過」（那種關閉的退場只在 `now > retire_after ≥ 申覆期限` 時發生，第二段一定在退場之後，所以結果不依賴時鐘）；其他措施不套這個檢查：停權與警告沒有申覆期限，賣家自己關店的退場只看關店後 30 天，預告終止的期限（生效後 184 天）可能還沒到（`TestSuspensionAppealStillWorksAfterTheSelfClosedStoreWasRetired`、`TestNoticeTerminationAppealStillWorksAfterTheSelfClosedStoreWasRetired`）；只看措施所在的店家，帳號早先自己關閉而退場的舊 stint 不算：`TestAppealStillWorksWhenAnOlderStintOfTheAccountWasRetired`。賣家請求（申覆、解除請求）對終止合作先鎖措施所在帳號與以它為來源的關聯終止所在帳號（`lockForRequest`：不加鎖預讀、依 account_id 升序鎖 stint、鎖措施列後重讀，範圍變了回 `errScopeChanged`，`retryScope` 整個 transaction 重來最多 5 次，用完回模組句子 `measure.retry_exhausted`）。固定交錯的測試 hook 只在 `integration` build tag 下編譯（`purge/hooks_integration.go` 的 `Service.SetAfterCandidates`〔第一段〕、`SetAfterPurgeCandidates`〔第二段〕，`measure/hooks_integration.go` 的 `Service.SetRequestHooks`〔預讀之後、鎖成功之後〕，正式程式是各自的 `hooks_prod.go` 空實作；module 層的 setter 在帶同一個 tag 的 `export_test.go`）：`TestPurgeRechecksTheAppealHoldAfterLockingTheCandidates`、`TestAppealAfterTheRetirementLockedTheStoreSeesItRetired`、`TestLinkedSourceAppealBlocksThePurgeOfTheLinkedAccount`、`TestLinkedSourceAppealLockedFirstMakesThePurgeSkipTheLinkedAccount`、`TestAppealRetriesWhenALinkedTerminationAppearsAfterThePreRead`、`TestPurgeStageTwoRechecksTheAuthorityHoldAfterLockingTheCandidates`、`TestPurgeStageTwoRechecksTheAppealHoldAfterLockingTheCandidates`。`TestRetirementAtThirtyDaysAndPersonalDataPurgeAtOneHundredEightyFourDays`、`TestRetirementAndPurgeSchemaConstraints`、`TestHoldsBlockEachStageAndReleaseWhenTheyEnd`、`TestARetiredStoreIsNeverReopened`、`TestPurgeClearsEveryPersonalColumn`、`TestPurgeOnlyTouchesStintsClosedForMoreThanTheStoreRetention`、`TestSanctionSnapshotSurvivesThePurgeOfItsSourceKYC`、`TestPurgeIsIdempotentAndLateNotificationsStayClean`、`TestPurgeIsNotCappedAtOneBatch`。清理後 `Store.StoreName` 是空字串，墓碑文字由呈現層依 `Status` 決定。

- 兩段清理不處理的資料：治理的通報、違規與停權紀錄（自由文字、處分原因）各有自己的保留規則（匿名檢舉人的聯絡欄位 `greatest(建立 + 90 天, 結果 + 30 天)`，見 §7）；`kyc_reviews.reason` 與 `kyc_reveals.reason` 是審核員的文字、不含申請人的欄位值，保留。清理也不處理對未來處分的覆蓋：身分快照與清理的關係見 `CARRYOVER.md`「處分的身分快照與清理的關係」。

- 兩段清理的內容與時間：**第一段（退場）**在 stint 關閉之後過了 `model.StoreRetireAfter`（720 小時，30 天）後清公開內容（說明、獎項、網站），logo 與封面在這時才釋放，發 `StoreRetired`（relay 轉成 `seller.deleted`，下游刪除商品、貼文、聊天的個資等），記下 `stores.retired_at`；退場之後不能恢復營業。**第二段（個資清理）**在已退場、關閉之後過了 `model.StoreRetention`（4416 小時，184 天，詐欺犯罪危害防制條例第 37 條第 1 項的六個月）後，把註冊、身分與連線資料清成 NULL：店名、店家聯絡（電話、聯絡人姓名與手機、客服信箱）與地址、KYC 個人欄位與證件、登記資料查詢、PayUni 的自由文字、同意紀錄的來源 IP 與 User-Agent，記下 `pii_purged_at`；審核事實、PayUni 狀態碼與措施的身分快照保留。因終止合作而關閉的，期限延到帳號上未撤銷終止中最晚的申覆期限，且不早於一般期限。時數由 `StoreRetireAfterHours`、`StoreRetentionHours`、`AppealWindowHours` 傳進 `RetireDueStores`（`second_stage` 選段）。保存條件兩種：`appeal_hold` 擋兩段，也讓恢復營業不恢復（第一段的時間條件成立而且沒有 `appeal_hold` 就是「保留期已過」）；`preservation_hold`（帳號上有沒撤銷登記、`hold_until` 晚於現在的主管機關來函指名，不指定店家或就是這家店）擋兩段，不影響恢復營業。實作在 `internal/purge`，每小時 River 排程；每一批：時間條件選候選並鎖住（keyset，`FOR UPDATE SKIP LOCKED`）→ 鎖住之後以同一支查詢再判斷時間、再問 `StoreHolds` → 只處理仍然成立而且沒有被保存的。

## 12. 可曝光公告

- 可曝光的公告（ADR `2026-10-05-store-exposure-to-legacy` 決策 1）：`store_exposures` 記每家店最後公告的值與 `version`（從 1 開始、每次公告加一），只有 `exposure.Announce` 寫入。每個可能改變六個條件（營運中、沒有生效中的停權、KYC 流程 APPROVED、店名、logo、鄉鎮市區代碼）的寫入，在自己的 transaction 的最後呼叫它：profile 的 `writeProfile`、`suspension.Recompute`（所有處分來源）、`closing`（等待刪除、關店）、`kyc`（`SaveDraft` 回退、送出、取消、核准、退回）、`payuni`（觀測的套用與綁定結果）。**先鎖再算**：先鎖住公告列（開店時與店家列在同一個 transaction 建立，version 0 是還沒公告過；公告函式不插入，列不存在是不變量被破壞），鎖住之後才讀店家、算現在的可曝光（先算再鎖，兩個同時進行的寫入各拿著對方還沒 commit 之前的輸入，後鎖到的會以舊的輸入覆蓋先 commit 的公告）；與最後公告的值不同才更新（version 加一）並在同一個 transaction 發 `StoreExposureChanged`，沒有翻轉的寫入不發。鎖順序：店家列、（申請、註冊）、公告列（公告永遠是 transaction 裡最後一個鎖）。時間造成的變化（處分到期與 job 之間的空窗）與任何漏接的寫入由 `seller.reconcile_exposure`（每 15 分鐘、啟動即執行）補發：候選是所有未關閉的店加上最後公告為可曝光的店（關店之後補發 false）。`TestExposureFlipsAreAnnouncedByEveryKindOfWrite`、`TestWritesThatDoNotFlipExposureAnnounceNothing`、`TestReconcileAnnouncesAnExpiryThatNoWriteObserved`、`TestReconcileCoversStoresWhoseAnnouncementDisagreesWithTheRule`、`TestAnnouncementLocksBeforeItComputes` 驗證。開店（`Apply`）建立 version 0 的公告列但不公告：新店缺 logo 與 KYC，一定不可曝光；`CompleteOnboarding` 與 `UpdateSEO` 不改六個條件之一。

- 全量重新公告（`ReannounceExposures`，`exposure.Reannounce`）：每一列公告列（含已關閉的店）不比對最後公告的值，都更新並發 `StoreExposureChanged`，版本照常加一；計算與寫入與 `Announce` 是同一支（`announce` 的 `force`），分批依 store_id、每批一個 transaction。用在種子重寫之後，以及 Java 的 `store_exposure` 重建或死信處理之後（Java 依版本丟棄舊的事件，重發一定新於它已有的值）。命令是 `make reannounce-exposures`（`cmd/hawkr reannounce-exposures`，事件經 relay job 排入資料庫、由 worker 送出，所以不需要另外接線）。`TestReannounceExposuresAnnouncesEveryRowWithoutComparing` 驗證（mutation：拿掉 `force` 讓它跳過沒變的列，測試失敗）。

- 可公開曝光的推導（給探索、目錄等對買家公開的清單）：`ExposableStores(ctx, storeIDs)`（最多 `MaxBatchSize` 個 ID，超過或含非正數回 InvalidInput）回傳可曝光的店家 `ExposableStore{StoreID, PublishedAt}`（`PublishedAt` 是公開時間：`stores.first_exposed_at`，第一次可公開曝光的時間，由 `exposure.Announce` 記下、永久保留（可曝光當場記，時間造成的變化由 `seller.reconcile_exposure` 補）；還沒被記下的可曝光店（對帳最多落後一個週期）是讀取當下，視為剛公開，這個規則只在 `classify`（`exposedRows` 建在它之上）寫一次；不是核准時間：一月核准、三月才補齊 logo 的店從三月起算），依輸入順序，不存在或不可曝光的略過。規則只有一處，在 SQL：`seller.pub_exposable_stores(at)`（§21；Go 只在 `internal/exposure` 的 `Classify` 讀它，`profile.classify` 在它之上加公開時間）。說明缺什麼用 `model.MissingExposure(store)`：把讀店家時由 SQL 帶上的條件（`Store.Conditions`，讀自 `seller.store_requirement_flags`；停權是 `Store.Sanctions`，讀自 `seller.effective_measures`）對應到 `Requirement`（固定順序，與 proto 的 `SellerRequirement` 數字一致），Go 不重算任何述詞；賣家看自己的店用 `CapabilitiesOf(store)`（`PUBLIC_LISTING` 缺的條件就是 `MissingExposure`，`TestPublicListingAgreesWithExposableStores`）。「全部條件的 AND」在 SQL 函式與 Go 的 `needs` 表各寫一次，由 `TestExposureRuleAgreesBetweenSQLAndGoOnADataset` 鎖住（函式、`ExposableStores`、`PUBLIC_LISTING` 與人工標註在每家店、每個評估時刻相等；KYC 條件與顯示用的 `DeriveKYCFlow` 的 `APPROVED` 相等）。條件：（店家沒有關閉且沒有正在隨帳號刪除（`STORE_ACTIVE`、`NOT_PENDING_DELETION` 互不重疊）、沒有生效中的停權、KYC 申請核准且 PayUni 已綁定、審核結果核准、店名、logo 與鄉鎮市區代碼都有值）。讀取固定四次查詢（店家、處分、條件、`pub_exposable_stores`），停權經 `stint.EffectiveMany`（與 `Derive` 同一支 `EffectiveMeasures`），條件經 `stint.WithConditions`；讀取失敗回錯誤，不回部分結果。「至少一個上架商品」由曝光端檢查。`TestMissingExposureMapsEachConditionToItsRequirement`、`TestExposableStoresExcludesEachFailingCondition`、`TestExposableAgainAfterTheSuspensionEndsOrIsLifted`、`TestPublishedAtStartsWhenTheStoreFirstBecomesExposable`、`TestPublishedAtIsTheReadTimeUntilStampedThenTheStamp` 驗證。

- 公開讀取（ADR `2026-10-03-public-store-identity-and-visibility`）：`PublicStoreByCode(storeCode)`（店面頁）與 `PublicStores(ids)`（需要完整店家資料又只能對公開的店用，例如追蹤）只回可公開曝光的店家，四條讀取路徑（`ExposableStores`、`PublicStores`、`PublicStoreByCode`、`ListPublicStores`）都經同一個 `classify`（前三條經 `exposedRows`），規則仍只有 `seller.pub_exposable_stores`；不存在與不公開同一個 NotFound，`PublicStoreByCode` 的鍵只有 `store_code`（`store_id` 連號、可逐號列舉）。`StoreCards(ids)`（最多 `MaxBatchSize` 個）給收藏、追蹤、聊天、訂單這類參照卡片：曾經公開過的店（`stores.first_exposed_at` 有值，或此刻可公開曝光）回 `StoreCard{StoreID, StoreCode, Name, LogoKey, CoverKey, Status}`，從沒公開過的略過（管理員核准但 PayUni 還沒核准的店不回）；`first_exposed_at` 的唯一寫入者是 `exposure.Announce`（算出可曝光的店記上現在，已有的不覆寫；寫入路徑當場記，`seller.reconcile_exposure`（`profile`，每 15 分鐘，`ReconcileExposure`）補時間造成的變化）；`Status` 是 `model.CardStatusOf`：已關閉 `CLOSED`、此刻可公開曝光（同一個 `exposedRows`）`OPEN`、其餘 `PAUSED`；個資清除之後 `Name` 是 nil，關閉的店沒有 logo 與封面。`PublicStoreByCode` 與 `ListPublicStores` 回 `PublicStore{Store, UpdateTime}`：`UpdateTime` 是 `model.PublicStoreUpdateTime`（`updated_at`、`first_exposed_at` 與 `store_exposures.exposable_changed_at`（公告值最後一次翻轉的時間）最晚的一個，sitemap 的 lastmod，唯一算法）。`ListPublicStores`（`SellerPublicService.ListStores`）依 `store_id` 由小到大、keyset（`PublicStoreCursor`）、預設 100、上限 1000：以 `ExposedStoresAfter` 讀 `store_exposures` 最後公告為可曝光的候選（`page_size+1` 家，多的一家只用來判斷有沒有下一頁），再對這一頁經同一個 `classify` 濾掉公告落後現況的店；一頁可以少於 `PageSize`，結束只看 `Next` 是不是 nil，cursor 是這一頁最後一個候選（含被濾掉的）；剛變得可曝光的店在公告之後才出現；`StoreExposure.HasPublicCard`（`model.HasPublicCard`：曾經公開過或此刻可曝光，`StoreCards` 同一條規則）給 legacy 驗證。

- 店家卡片（`StoreCards`）帶店名、logo、封面、營運狀態與所在地 `TownCode`（8 碼鄉鎮市區代碼；個資清除之後與店名一樣是 nil）；評價不在模組內，由 `internal/httpapi/seller` 的 `StatsSource.RateCards` 對一批卡片批次讀取。

### 12.1 快取失效（website）

- 店家頁的 website 快取失效在每個可能改變公開內容的寫入的同一個 transaction 內排入 River job（`stint.Invalidate`／`InvalidateByID`，`revalidate.Args`），commit 之後才送出 `POST /api/revalidate`；觸發點不限於 profile：開店、profile、KYC（送出、取消、核准、退回）、關店與恢復營業、停權與恢復、PayUni 觀測的套用、個資清理都會排入。
- cache tag 是 `seller:{store_id}` 與 `seller:{store_code}`（`revalidate.StoreTags`，兩個都送，因為店鋪頁網址片段兩種識別碼都接受，website 以網址片段當快取鍵；與 website 的 `lib/seo/tags.ts` 的 `sellerTag()` 是同一份契約）。
- 每次送出 5 秒 timeout、最多 5 次嘗試（含第一次），暫時性的失敗由 River 退避重試；`WEB_REVALIDATE_BASE_URL`／`WEB_REVALIDATE_SECRET` 沒有設定時啟動記 warn log 且 revalidate 停用（website 快取維持到自己的 TTL 到期）。bust 同一個 tag 重複執行沒有副作用。

## 13. KYC 認證

- KYC 申請以 `store_id` 為鍵：一個店家同時最多一筆還沒取消的申請（partial UNIQUE `kyc_applications_open`，取消後可以重建；被退回的申請編輯後回到 DRAFT、沿用同一列），新 stint 沒有舊申請。`status` 只記人工決定（`DRAFT`、`SUBMITTED`、`APPROVED`、`REJECTED`、`CANCELLED`），PayUni 的綁定結果不在這條軸上。草稿與送出共用同一組具型別的欄位（沒有自由格式 JSON），必填由 `kyc_applications_complete_check` 依狀態表達；日期是 ISO 日曆日，解析不了、不存在、早於 1900 或晚於台北的今天就整筆拒絕。所有寫入者（草稿、送出、取消、核准、退回）帶讀到的版本。`TestKYCDraftSubmitApproveFlow`、`TestOneOpenKYCApplicationPerStoreIsEnforcedByTheDatabase`、`TestKYCInvalidDatesAreRejectedNotKept`、`TestKYCSchemaConstraints`、`TestKYCStaleVersionsConflict` 驗證。

- KYC 欄位的規則各只有一處：統編是 8 碼數字加 2023 年起的檢查碼（`model.NormalizeTaxID`，草稿與登記資料查詢共用）；送出前必填的項目是 `requirements` 表（`complete` 與申請檢視的 `MissingFields` 由它推導，欄位用 `model.KYCFieldNames()` 的路徑，與對外 `KYCApplication` 的欄位路徑一對一，個人與企業專屬的欄位依 `model.FieldAppliesTo` 的前綴規則）；同一張圖片（asset）在整份申請只能是一個證件。

- KYC 個資：身分證號、負責人身分證號、銀行帳號是 `bytea` 密文（AES-256-GCM，AAD 是申請 ID 加欄位名，所以密文搬到別的列或欄就解不開），姓名與生日明文（後台以姓名 ILIKE 搜尋）。回傳給賣家與後台的 `KYCApplication` 型別沒有任何欄位能放明文（遮蔽發生在型別轉換）；全文只由 `RevealSensitive` 回傳，同一個 transaction 寫一列 append-only 的稽核（誰、哪筆申請、何時、理由、授權到期的時間，不含值），稽核寫入失敗就不回傳。`TestKYCNeverReturnsOrStoresPlaintext`、`TestRevealWritesAnAuditRowAndNeverTheValue`、`TestKYCCiphertextCannotBeSwappedBetweenRowsOrColumns` 驗證。金鑰（`Deps.KYCKeys`、`KYCMAC`）必填，`seller.New` 缺了或兩者相同就 panic，cmd 缺了就啟動失敗。

- 身分比對：每個識別欄位（身分證號與負責人身分證號同一種、統編、銀行帳號連同銀行代碼）一個 HMAC blind index，輸入帶欄位標籤（`kyc:id:v1|`、`kyc:ubn:v1|`、`kyc:bank:v1|`），金鑰與加密金鑰分開（啟動檢查），hash 帶金鑰 ID；銀行帳號只去分隔符、保留前導 0。停權措施建立時（`suspension.RecordIdentities`）把帳號全部申請的 hash 快照到 `measure_identities`，措施結束或撤銷（同一個 transaction，`Recompute`）、到期 job 與對帳時刪除。比對只讀快照：以金鑰環的每把金鑰重算申請的 hash 查詢，命中別的帳號後，「處分是否生效」一律經 `stint.Derive`（不另寫第二份定義）。送出時先查（身分證號或統編命中回泛用錯誤、不透露欄位與帳號），核准時在鎖住帳號全部 stint、申請列之後再查一次，以後者為準；銀行帳號命中只在後台詳情標記（`SharesBankAccountWithSanctionedAccount`）。核准還要求申請人的帳號沒有停權、店家在營業中。`TestKYCIdentityMatchBlocksAcrossAccounts`、`TestKYCApproveRechecksTheIdentityInsideTheTransaction`、`TestKYCBankAccountMatchFlagsButDoesNotBlock`、`TestKYCLiftedOrExpiredSanctionNoLongerBlocksAndItsSnapshotIsDeleted`、`TestKYCApproveRejectsASuspendedApplicant` 驗證。

- KYC 審核的鎖順序：店家列（`stint.LockAccountOf`，帳號全部的 stint）先於申請列，鎖內重新確認版本與狀態，再寫決定、審核紀錄與事件，同一個 transaction（賣家自己的寫入鎖單一店家列再鎖申請列）。`TestKYCApproveAndRejectAreSerialisedUnderTheLock` 驗證。核准在同一個 transaction 寫入 PayUni 的綁定意圖並排入 job（`payuni.RequestBind`；鎖順序：店家列、申請列、註冊列），外部呼叫不在 transaction 內；核准與退回的版本檢查先於狀態檢查，不推斷重送：命令已經生效後帶舊版本再送一次一律 VersionConflict，不重複寫審核紀錄、事件與 job：`TestStaleEtagAfterApproveAndRejectConflicts`。

- KYC 事件在寫入的 transaction 內發出，`EventID` 是審核紀錄的 UUIDv7（穩定，relay 重送時不變）：`KYCSubmitted`、`KYCApproved`（人工決定）、`KYCRejected`（對應舊的 `merchant.verification.rejected`，帶退回理由）、`KYCCancelled`。PayUni 的結果（`forwarded`、`approved`、`pending_info`、`under_review`、PayUni 端的 `rejected`）是 `payuni` 的事件，見 §14；`KYCRejected` 由 `internal/legacy/sellerrelay` 轉成 `merchant.verification.rejected`，其餘 KYC 事件沒有舊的 routing key、不轉送。

- 證件圖片（身分證正反面、存摺封面各一張，公司文件最多 10 張）以 `ref_id = application_id` 登記 `CERTIFICATION`（7111）：轉正在 transaction 外、不建立引用；存檔時被換掉的證件記成退場（只算不再被任何位置指著的 asset，公司文件改順序不退場）、申請取消與個資清理把全部證件記成退場。草稿的證件是狀態：`KYCDraftInput` 的 `IDCardFront`、`IDCardBack`、`BankBook`（nil 保留、非 nil 換成指定的那一張、空的清掉）與 `CompanyDocuments`（nil 保留、非 nil 整個換成清單，順序是位置），每個元素是這份申請目前的圖片（`AssetID`，保留）或新的 `StagedToken`；沒有帶版本（要建立）卻已有申請回 AlreadyExists（`VERSION_CONFLICT`）。`TestKYCDocumentsLinkByApplicationIDAndSync`、`TestKYCDocumentsAreReplacedAsState`、`TestSyncBetweenFinalizeAndCommitKeepsKYCDocuments` 驗證。

- 審核佇列只列送出過的申請（`status <> 'DRAFT' AND submitted_at IS NOT NULL`：草稿與沒送出就取消的不在），排序鍵是送出時間、以申請 ID 定序；篩選審核中舊到新（等最久的在最前面），其他與沒有篩選新到舊，方向只有 `KYCListInput.OldestFirst` 一處，兩支 query（`AdminKYCApplicationsOldestFirst` 與 `AdminKYCApplications`）條件相同；索引 `kyc_applications_status_submitted`、`kyc_applications_submitted`。`Query` 是姓名、公司名稱、統編的子字串（ILIKE，`%`、`_` 是字面）。`TestAdminKYCQueueIsOrderedBySubmitTime`、`TestAdminKYCListFiltersAndPaginates`、`TestAdminKYCListSearchesCompanyNameAndTaxID`、`TestAdminKYCQueueVariantsFilterIdentically`（兩支 query 的篩選條件必須一致）。審核的服務水準以等待時間計，所以審核中等最久的先看。

- 審核者只記管理員 ID（`kyc_reviews.reviewer_admin_id`：核准、退回、重新綁定必有、賣家的動作必無，`kyc_reviews_reviewer_check`），沒有名稱快照；`ApproveKYCInput`、`RejectKYCInput` 沒有 `AdminName`。理由與 comment 的規則只有 `platform/auditreason`：退回與顯示全文 `Required`（空白或超過 1000 字回 InvalidInput），核准的 comment 與賣家取消的原因 `Optional`（空白等於沒有，超過 1000 字回 InvalidInput，不是讓 `kyc_reviews_reason_check` 擋成 internal）。`TestApproveCommentIsValidatedBeforeTheDatabaseSeesIt`。

- 證件圖片是限時授權的 JIT 存取：`RevealSensitive` 寫的 `kyc_reveals` 那一列就是授權，`expires_at` = `revealed_at` + `RevealGrantTTL`（15 分鐘，注入的時鐘）。`ReadDocument(adminID, applicationID, slot, position)`：沒有「這位管理員、這筆申請、`expires_at` 晚於現在」的授權一律 PermissionDenied（不分申請存在與否）；授權之後申請是草稿或已取消（取消時證件已退場）、個資已清除（`pii_purged_at`），或位置沒有圖片，是 NotFound，不寫讀取紀錄、不呼叫 media（`TestCancelledApplicationHasNoReadableDocuments`）；已取消的申請顯示全文時不回證件位置與網址；transaction 內先寫一列 `kyc_document_accesses`（授權 ID、位置、實際送出的 asset ID、時間；不含內容），commit 之後才經 `media.ReadSecure`（`ServerReadSecureAsset`，三元組 `object_key`、`RefTypeCertification`、`application_id`）取內容，紀錄寫不進去就不讀（fail closed），媒體讀取失敗時紀錄仍在。證件在 API 上只用 (申請, 位置) 定址，遮蔽的檢視沒有 asset ID 與網址，只有顯示全文的回應有 `view_uri`（`httpapi/seller.AdminDocuments`）。`TestKYCDocumentAccessNeedsAnUnexpiredGrantOfTheSameAdmin`、`TestKYCDocumentAccessIsRecordedBeforeTheBytesAreRead`、`TestKYCDocumentAccessOfAPurgedApplicationIsNotFound`。

- 退回是逐項問題（`model.KYCIssue`：欄位路徑、文件類欄位指到的那一張的 asset ID、原因碼 `KYCIssueCode`、給賣家看的說明 1 到 500 字）加只給後台看的 `internal_note`，存在 `kyc_review_issues` 與 `kyc_reviews.internal_note`，不含欄位值。`Reject` 至少一項，欄位適用於申請的賣家型態，asset 必須是這份申請在那個欄位目前的文件，違規指到 `Issues[i].<欄位>`。「賣家還沒處理的」（`KYCApplication.OutstandingIssues`）只算最近一次退回、而且之後沒有別的審核紀錄（重送、核准、取消）的問題；`KYCApplication.LastRejection`（賣家要處理的那次退回）只在最近一次審核紀錄是退回、之後沒有重送、核准或取消時有，賣家處理完每一項、還沒重送時仍在。「已處理」只在寫入申請的 transaction 內判定：欄位用寫入路徑（`applyDraft`）回報的 `draftDiff`（比明文與正規化後的值，個資密文與 blind index 都不能比；PayUni 已收下之後不能改身分欄位的檢查用同一份），文件指到某一張時是那張不在了、沒指到時是那個位置的組成變了；讀取不推導，client 也不推導。`TestFieldDiffsCoverEveryNonDocumentField` 守著新增的 KYCField 要接上 diff。`TestRejectKYCValidatesIssuesAgainstTheApplication`、`TestOutstandingIssuesAreResolvedByTheSellersEdits`、`TestOutstandingCompanyDocumentIssuesFollowTheAssetNotThePosition`、`TestInternalNoteIsOnlyOnTheAdminReviewRecord`、`TestKYCReviewIssueChecksMatchGoAndRejectBadRows` 驗證。

- 流程狀態是推導的（`model.DeriveKYCFlow`，不存）：`DRAFT`、`SUBMITTED`、`REJECTED`、`NOT_STARTED`，以及核准之後由綁定與 PayUni 結果合成的 `BINDING`、`BIND_FAILED`、`FORWARDED`、`UNDER_REVIEW`、`PENDING_INFO`、`APPROVED`、`PAYUNI_REJECTED`；`CanResubmit` 是草稿、被退回、已取消（與沒有申請相同，`SaveKYCDraft` 版本 0 建立新的），或已核准而且 `SellerPayUniOf` 是 FIXABLE（依序：不是 `NeedsReonboarding`、`PaymentEnabled` 還沒成立；PayUni 拒絕而且補救方式不是聯絡客服，即會員層級的整份表單碼 `MEMBER_8`、`MEMBER_92`；或綁定失敗、補救方式是賣家可修、而且依賣家型態與身分鎖過濾後仍有申請欄位）。`MEMBER_99`（會員關閉或停權，聯絡客服）、`MER_91`／`MEMBER_5` 補件（PENDING_INFO）、`PAYUNI_UNAVAILABLE`（RETRY_LATER）、只指出店家欄位（FIX_VIA_SUPPORT）都不能重送，各有一個 `resubmit_unavailabilities` 原因。能重送時賣家可以直接 `SubmitKYC`（`Submit` 接受草稿與 `CanResubmit` 的申請，已核准的在鎖內以 `payuni.CheckResubmit` 重查；不必先 `SaveKYCDraft`；`CanResubmit` 為假的狀態回 FailedPrecondition），或先 `SaveKYCDraft` 更正再送出，再核准時：還沒綁定過的註冊回到 `PENDING`；已綁定的（PayUni 端已有這個商店，再 bind 只會得到 `AGENT04017`）維持 `BOUND`，記下 `resubmitted_at`，由 job 以 `update_merchant` 送修正後的聯絡欄位與地址，輪詢在 7 天內繼續問新的結果（拒絕是舊的狀態；PayUni 的狀態與觀測保留，`TestReapprovalAfterAMemberRejectionSendsTheCorrectedDataAndResumesPolling`）；改回草稿修正時只能改聯絡資料與地址，身分欄位仍鎖住（`KYCFlow.IdentityLocked`；此時 `CanResubmit` 只表示聯絡與地址更正，身分的錯誤只能關店重新入駐；`SaveKYCDraft`、`UpdateProfile` 與 `CancelKYC` 是身分鎖的強制點，鎖定時取消回 FailedPrecondition，鎖順序是店家、申請、PayUni 註冊列）；商家層級的終止狀態（`NeedsReonboarding`，TERMINATED）不行：同一個 stint 只能關店、以新的 `store_code` 重新入駐。流程隨申請的檢視回傳（`KYCApplication.Flow`，清單不帶）。`TestFlowStatusAndResubmissionAfterAPayUniRejection`、`TestTerminalPayUniStatusCannotBeResubmitted` 驗證。

- 身分比對（`SubmitKYC`）是身分證號、統編存在與否的探測面（泛用錯誤不夠，攻擊面是重複送出），所以頻率限制在入口：`internal/httpapi/seller` 的宣告表給 `SubmitKYC` 每個帳號每小時 5 次（`limitedTo`，在能力檢查通過之後、handler 之前計數）。模組本身不限流，直接呼叫模組的程式（job、測試）不受它約束。

- KYC 金鑰（`KYC_ENCRYPTION_KEYS`、`KYC_HASH_KEYS`）必填。啟動檢查（serve 與 worker，`CheckKYCKeys`）：資料庫參照的每一把金鑰 ID（KYC 密文開頭、申請的 hash、處分身分快照）都要在金鑰環裡，缺了就不啟動（`TestStartupChecksThatEveryKeyReferencedByTheDatabaseIsConfigured`）。金鑰環新增 HMAC 金鑰（輪替）之後，serve 與 worker 在 `CheckKYCKeys` 之後呼叫 `RehashKYCIdentities`，只解密缺新金鑰那一列的申請、補算 blind index，可重複執行，沒有輪替時什麼都不做（`TestRehashFillsTheKeysAddedByARotation`）。處分的身分快照沒有明文可以重算，用來算快照 hash 的舊 HMAC 金鑰要留在金鑰環直到對應的處分結束。

- 後台的 KYC 審核與 PayUni（`SellerAdminService`）：審核佇列 `AdminKYCApplications`（keyset `KYCCursor{SubmittedAt, ApplicationID}`；`Query` 搜姓名、公司名稱與統編）、單筆檢視 `AdminKYCApplication`（遮蔽值、審核紀錄、銀行帳號命中的標記；顯示全文與證件讀取的稽核各自分頁：`ListKYCReveals`、`ListKYCDocumentAccesses`，新到舊的 keyset，申請不存在回 NotFound）、`ApproveKYC`／`RejectKYC`（etag；回傳的後台檢視在同一個 transaction 內讀）、`RevealKYCSensitive`（顯示全文，同時是 15 分鐘的證件授權）、`ReadKYCDocument`（以授權讀證件圖片）、`PayUniRegistrationOf`、`RebindPayUni`、`PayUniObservations`（keyset）、`RefreshPayUniStatus`。

- 公司型申請的登記資料快照（ADR `2026-10-19-seller-kyc-payuni-consolidated`「登記資料快照」）：送件（`kyc_applications.submission_seq` 每次轉成 SUBMITTED 加一，退回後重送是新的一輪）時在同一個 transaction 新增一列 PENDING 的 `kyc_registration_checks`（綁定這一輪的 `submission_seq`）並排入 `seller.kyc_registry_check`（`internal/kyc`；以 `check_id` 為 River 唯一鍵，狀態集合不含 completed、discarded；寫入的冪等仍由條件寫入保證）。job 在 transaction 內認領（申請不是這一輪審核中、同一輪已有更新的查詢，或已不是公司型就寫 `CANCELLED` 結束）、transaction 外呼叫 `Registry` port（`platform/gcis` 的 client 直接是它的實作，回來源的原始資料；轉成模組型別、現況分類、停業期間的合理性與地址拆分只有 `model.NewRegistration` 一處，互動的 `LookupBusinessRegistration` 與快照共用），再用另一個 transaction 寫入結果（只在仍是 PENDING 時；最後一次嘗試的任何失敗都記 `UNAVAILABLE`，不留 PENDING）。查詢是有期限的資源：建立時寫入 `deadline_at`（`requested_at` 加 15 分鐘，後台的 `deadline_time` 讀它），伺服器保證在期限前到終態。PENDING 的出口：寫入結果、認領時放棄、後台重新查詢取代、job 執行時已過期限直接記 `UNAVAILABLE`（不再呼叫資料來源）、掃描 job `seller.kyc_registry_sweep`（每 1 分鐘：`deadline_at` 不晚於現在加一個掃描間隔的 PENDING 收成 `UNAVAILABLE`／`CANCELLED`，閒置超過 3 分鐘的補排 job）；`RequeryKYCRegistration`（只在 SUBMITTED）把這一輪的 PENDING 全部收成 `CANCELLED` 再新增一筆並回傳它（帶期限）。FOUND 時存登記資料與現況並逐欄比對（名稱、設立日期、地址；組織型態在快照裡，申請人不填，不比對）：不一致與無法比對只記錄，不改申請狀態。後台顯示申請目前這一輪 seq 最大的已完成查詢（這一輪還沒有就沒有快照），「查詢中」只在 SUBMITTED 時計算；後台 etag 是申請版本加顯示的查詢序號，核准與退回把顯示的查詢記進審核紀錄。個資清理一併刪除查詢列。

### 13.1 認證軸轉移與可收單條件

| 當前狀態 | 允許轉換至 | 觸發 |
|---|---|---|
| `DRAFT` | `SUBMITTED`、`CANCELLED` | 賣家送出／取消 |
| `SUBMITTED` | `APPROVED`、`REJECTED`、`CANCELLED` | 管理員核准／退回；賣家取消（身分已鎖定、PayUni 已收下時不能取消） |
| `REJECTED` | `DRAFT`、`SUBMITTED` | 賣家修改後儲存草稿，或不修改直接重送；沿用同一筆申請 |
| `APPROVED` | `DRAFT`、`SUBMITTED` | 只在 `CanResubmit` 為真時；其餘狀態儲存與送出都回 `failed_precondition` |
| `CANCELLED` | 終態 | 取消之後可以重新建立新申請 |

- `decided_at` 有值 ⇔ `APPROVED` 或 `REJECTED`（`kyc_applications_decided_check`）。轉移一律以目前的狀態與版本為條件（`transition`），0 列受影響視為版本衝突。
- 流程狀態的條件：`NOT_STARTED`＝沒有申請或申請已取消；`BINDING`＝已核准且沒有註冊列或 `bind_status = PENDING`；`BIND_FAILED`＝已核准且 `bind_status = FAILED`，等管理員處理；`FORWARDED`＝已綁定且 `outcome` 為 `NONE` 或 `UNRECOGNIZED`；`UNDER_REVIEW`、`PENDING_INFO`、`PAYUNI_REJECTED`＝已綁定且 `outcome` 為同名（`REJECTED`）值；`APPROVED`＝已綁定且 `outcome = APPROVED`，可以收款。
- 「KYC 流程核准」（店家能力 `KYC_APPROVED`、`seller.store_requirement_flags.kyc_approved`）＝目前那一筆還沒取消的申請已核准，而且 PayUni 註冊已綁定、審核結果核准（流程狀態 `APPROVED`）；它是物流建店能力與店家公開曝光的條件之一（§10）。管理員核准後、PayUni 尚未通過前不能收單；PayUni 在核准之後退件時流程狀態離開 `APPROVED`，條件自然不成立，沒有額外的降級路徑。
- 只有申請已核准，或申請是草稿且註冊屬於這份申請而且推導為 `FIXABLE`（賣家正在修正 PayUni 拒絕或綁定失敗的那份申請，問題要留著）時才有 PayUni 狀態。問題的處置（`PayUniRemedy`：`SELLER_FIX`、`CONTACT_SUPPORT`、`RETRY_LATER`）與要補的欄位由 `ClassifyPayUniCode` 決定；欄位清單依賣家型態過濾，已鎖定的身分欄位不列。

### 13.2 介面行為

賣家端（`SellerAppService`，能力由宣告表檢查，§10）：

| 方法 | 能力 | 行為 |
|---|---|---|
| `SaveKYCDraft` | `CAP_STOREFRONT_WRITE` | 部分更新（update_mask）呼叫者店家的草稿。申請是店家的單例資源：沒有申請時不帶 etag 的呼叫建立它；已有申請時 etag 必填，沒帶回 `already_exists`、版本不符回 `aborted`，ErrorInfo.reason 都是 `VERSION_CONFLICT`。被退回的申請在這裡回到 `DRAFT`。全部欄位先驗證才寫入，任何一欄不合法都不寫入；不能重新送出（`CanResubmit` 為假）回 `failed_precondition`，訊息是 `resubmit_unavailabilities` 的第一句。申請以帳號目前的店家為準，不接受別人的申請 ID |
| `GetMyKYC` | `CAP_ACCOUNT_SELF_READ` | 回傳目前的申請（身分證號與銀行帳號遮蔽）、證件、最近一次退回的理由與逐項問題（含是否已處理）、流程狀態、PayUni 狀態與 `missing_fields`、`missing_store_fields`；還沒有申請（或已取消）回 `not_found` |
| `SubmitKYC` | `CAP_STOREFRONT_WRITE` | 送出審核。每個帳號每小時最多 5 次，超過回 `resource_exhausted`（帶 RetryInfo） |
| `CancelKYC` | `CAP_STOREFRONT_WRITE` | 取消草稿或審核中的申請 |
| `LookupBusinessRegistration` | `CAP_STOREFRONT_WRITE` | 表單輔助：以統編代為查經濟部商業司公開資料；每個帳號每分鐘最多 10 次 |

後台（`SellerAdminService`，管理員權限）：`ListKYCApplications`（審核佇列：只列送出過的申請，以狀態與關鍵字篩選，keyset；篩選 `DRAFT` 回 `invalid_argument`；清單項目不帶證件圖片）、`GetKYCApplication`（遮蔽的欄位、證件、審核紀錄、銀行帳號是否與受處分帳號相同的標記、登記資料查詢結果、各動作的不可用原因 `approve_unavailabilities` 等；賣家的草稿讀不到，`not_found`）、`ListKYCReveals` 與 `ListKYCDocumentAccesses`、`ApproveKYC` 與 `RejectKYC`（etag 必填，不符回 `aborted`（`VERSION_CONFLICT`）且不寫入）、`RevealKYCSensitive`（POST，回應不可快取）、`RequeryKYCRegistration`（只對審核中的公司型申請）、`GetPayUniRegistration`（店家還沒有核准過申請時 `not_found`）、`RebindPayUni`、`ListPayUniObservations`、`RefreshPayUniStatus`（排入一次向 PayUni 查詢審核狀態的 job，回應不等結果；PayUni 沒有設定或註冊還沒綁定時 `failed_precondition`）。

證件圖片是 HTTP GET 而非 Connect（回應是圖片本身）：`GET /api/files/admin/seller/kyc_applications/{application_id}/documents/{slot}/{position}`，`slot` 是小寫位置名（`id_card_front`、`id_card_back`、`bank_book`、`company_document`）；驗證與後台 Connect 方法相同，授權是管理員且持有這筆申請未到期的顯示全文授權；機敏檔案 `no-store`。

錯誤約定：缺少的欄位 `invalid_argument`，BadRequest 的每個 field 是 `KYCApplication` 的欄位路徑（`real_name`、`id_card_front`、`business.tax_id`……，與 `KYCField` 一對一）；版本衝突 `aborted`／`already_exists`（`VERSION_CONFLICT`）；不能做的動作 `failed_precondition`，訊息是對應 `*_unavailabilities` 的第一句；同意文件版本不是現行版本 `failed_precondition`，reason `AGREEMENT_OUTDATED`；身分比對沒有通過 `failed_precondition`，訊息固定，不透露是哪個欄位或哪個帳號；能力不足（停權、等待刪除）見 §10。

### 13.3 流程步驟

- 送出（`SubmitKYC`）的順序：（1）驗證同意文件（種類不對 `invalid_argument`；版本不是現行版本 `AGREEMENT_OUTDATED`），先於一切業務檢查；（2）鎖內重新檢查能力與 `CanResubmit`，必填欄位與證件齊全（缺的一次全部列出）；（3）申請齊全之後，PayUni 綁定需要的店家資料（地址、聯絡人姓名與手機、客服信箱）還缺時回 `failed_precondition`，client 讀 `GetMyKYC` 的 `missing_store_fields`，以 `UpdateMyStore` 補齊；（4）身分比對（見上）；（5）同一個 transaction：寫入、同意紀錄（綁這次送出的審核紀錄，表 `agreement_acceptances`，含 IP 與 User-Agent）、`SUBMIT` 審核紀錄、`KYCSubmitted` 事件，公司型再新增一列 `PENDING` 的登記資料查詢並排入 job。
- 儲存草稿：證件圖片在 transaction 之外轉正（轉正不建立引用，失敗的請求已轉正的資產由 media 的 GC 在建立滿 7 天後回收），寫入的 transaction 內把被換掉的證件記成退場並排入引用的同步；證件請求的位置是狀態不是指令（單張的位置整個換成請求的那一張，公司文件整個換成請求的清單；同一個 staged token 在整個請求只能出現一次）。
- 取消：已核准的不能取消，被退回的申請就留著；身分已鎖定（PayUni 已收下）時不能取消，否則店家可以新申請繞過身分鎖（訊息提示關店後重新入駐）；轉移為 `CANCELLED`、寫 `CANCEL` 審核紀錄、證件引用全數記退場、發 `KYCCancelled`、重新公告曝光。
- 核准：帳號停權時不能核准、可以退回；店家不是營運中或帳號停權的期間，申請不在後台待辦、沒有審核期限，恢復之後自動回到待辦。核准重新檢查 etag（申請版本加顯示的登記資料查詢序號，版本不符先於狀態檢查）、狀態、店家在營業中、帳號沒有停權、身分沒有命中別的帳號生效中的處分。核准寫入（或刷新）PayUni 綁定意圖，`bind_status` 回到 `PENDING`，這裡不呼叫 PayUni。
- 退回：`reason` 必填；`issues` 至少一項；帳號停權中仍可退回；賣家修改後重送沿用同一筆申請。
- client 的串接次序（伺服器保證的行為，client 不複製規則）：進入認證先 `GetMyKYC`（`not_found` 表示還沒有申請）；`SaveKYCDraft` 第一次不帶 etag、之後帶最近讀到的 etag，`VERSION_CONFLICT` 時保留輸入並顯示最新版本；證件圖片先以機敏上傳取得 staged token 再放進草稿；`SubmitKYC` 帶同意的文件與版本，`AGREEMENT_OUTDATED` 時重新取得現行版本（`GetSellerAgreements`）；`SUBMITTED` 時身分尚未鎖定才可 `CancelKYC`；被退回顯示 `reason` 與逐項問題（欄位路徑對應表單欄位）；已核准時依 PayUni 狀態（§14）顯示對應的面板與動作，`APPROVED` 不顯示面板；`permission_denied` 加 `SELLER_SUSPENDED` 導向停權公告頁。表單欄位以 `KYCApplication` 的欄位路徑為準（共用、個人 `individual.id_card_no`、企業 `business.*`，公司文件最多 10 張），必填項目與缺少時的說明由伺服器的 `requirements` 決定。

## 14. PayUni 子商店

- PayUni 註冊以 `store_id` 為鍵（主鍵），一個 stint 一列，那一列就是綁定意圖：`bind_status` 是 `PENDING`／`BOUND`／`FAILED`（`FAILED` ⇔ 有 `bind_error_code`，DB CHECK），只記綁定；PayUni 的審核結果是原碼（`mer_status`、`member_status` 等，外部事實）加推導的 `outcome`（`NONE`／`UNDER_REVIEW`／`PENDING_INFO`／`APPROVED`／`REJECTED`／`UNRECOGNIZED`），兩者由同一個條件式 UPDATE 寫入；付款能力（`PaymentEnabled`）不存，已綁定而且 `APPROVED` 才有。註冊列的鎖順序：店家列先、註冊列後（核准、重新綁定、賣家改資料、job 的結果寫入一致；寫觀測列的外鍵會對店家列取 KEY SHARE，先鎖註冊列會互鎖）。**沒有 raw_request**，也不存任何請求或回應本文：請求在 job 執行時由 KYC（解密）、店家與聯絡欄位組出來，送出就丟。`TestPayUniTablesNeverStoreTheRequestOrTheIdentity`、`TestPayUniSchemaConstraints`、`TestPayUniChecksMatchGo`、`TestStoredOutcomeAlwaysMatchesTheDerivation` 驗證。

- 外部呼叫不在 transaction 內（規則 5）：核准、重新綁定與店家改聯絡資料或地址都只在 transaction 內寫意圖（`intent_seq` 加一）並排入 `seller.payuni_sync`（以 `store_id` 為唯一鍵，唯一的狀態集合是排隊中、執行中、等重試，**不含 completed**：River 的預設會讓完成的 job 在被清掉之前擋住之後的改動；`running` 不能排除，所以執行期間的改動靠 `intent_seq`，結果寫入後 `intent_seq` 比 job 讀到的大，`Sync` 回 `again`，worker 以 snooze 再跑一輪）。同一個店家同時只有一個 job 呼叫 PayUni，由這個唯一鍵保證（含 `running` 與 River 的 rescuer：job 的 timeout 遠小於 rescuer 判定卡住的時間），沒有另外的租約（`TestSyncJobIsUniquePerStoreInRiver` 證明執行中的 job 擋下新的 job）。job 三段：transaction 讀註冊列、確認有事要做並記下 `intent_seq`；transaction 外讀目前的資料（KYC 解密、店家的地址與聯絡資料）並呼叫 PayUni（有 deadline，fake 在測試裡確認每次呼叫都在 transaction 外、有 deadline）；transaction 寫結果與事件（鎖順序與所有寫入者相同：店家列先、註冊列後，`TestSyncFinishLocksTheStoreBeforeTheRegistration`）。`TestApproveWritesTheIntentAndEnqueuesWithoutCallingPayUni`、`TestSyncJobIsUniquePerStoreInRiver`（真的 River）、`TestAddressChangeDuringTheCallRunsAnotherRound` 驗證。

- 錯誤分類：傳輸錯誤（連線、逾時、非 200、回應解不開）與 PayUni 的暫時性錯誤碼（目錄的 `RETRY_LATER`）回錯誤，由 River 退避重試（`syncMaxAttempts` 次，最後一次改為記錄結果：綁定記為 `FAILED`（`PAYUNI_UNAVAILABLE`）、同步記為同步失敗），絕不轉成業務結果；其餘 PayUni 的碼是永久的，綁定記為 `FAILED` 加原碼（同一個 transaction 發 `PayUniBindFailed`），同步記在 `sync_error_code`（`synced_seq` 照樣前進，賣家再改一次才重送）；目錄以外的碼 fail closed（`CONTACT_SUPPORT`）。錯誤目錄是 Go 的表（`model.ClassifyPayUniCode`，`TestPayUniCatalogMatchesTheLegacyGolden` 逐碼比對 136 筆），文案屬於 client 的呈現層。`AGENT04017`（MerID 已存在）先查詢狀態認領（所以結果不明之後重送一律安全）；查到商家層級的終止狀態（2、8、92、99）記為 `FAILED`（`MERCHANT_TERMINAL`），不能重新綁定，要關店重新入駐。沒有設定 PayUni（`Deps.PayUni` 為 nil）時綁定記為 `PAYUNI_NOT_CONFIGURED`，不呼叫任何東西、輪詢不排。`TestBindFailureIsRecordedAtomicallyWithItsEvent`、`TestTransportErrorIsRetriedAndOnlyTheFinalAttemptFails`、`TestAlreadyBoundMerchantIsClaimedBySelfHealing`、`TestAlreadyBoundTerminalMerchantNeedsReonboarding`、`TestNotConfiguredPayUniFailsWithAClearCodeAndDoesNotPoll` 驗證。

- 資料不完整不送假資料：店家沒有地址（`town_code`、`address_detail`）、或沒有官網又沒有設定店家頁網址時，綁定記為 `FAILED`（`INCOMPLETE_DATA`），不呼叫 PayUni；這是唯一會自動回到 `PENDING` 的失敗：店家補上地址（`RequestSync`）而且資料真的補齊了（`bindLocation` 的完整性檢查，與 job 同一份定義）才重新排入，不相干的修改維持 `FAILED`、不發事件、不重置嘗試次數（`TestIncompleteDataFailureReturnsToPendingOnlyWhenTheDataIsComplete`）。PayUni 的地址是店家的地址（縣市加鄉鎮市區加詳細地址，3 碼郵遞區號由 `twaddr` 推導），不是公司登記地址。`TestMissingAddressFailsWithoutSendingFakeValues` 驗證。

- 聯絡資料與地址都是店家的欄位，走同一個 job：店家的聯絡人姓名、聯絡人手機、客服信箱（`stores.contact_name`、`contact_mobile`、`support_email`）、商店電話（既有的 `contact_phone`，對應 `MerTel`）與地址是唯一來源，PayUni 註冊列沒有副本（聯絡資料是店家擁有的資料，PayUni 只是同步的對象；ADR `2026-10-19-seller-kyc-payuni-consolidated`「PayUni 聯絡資料的擁有者是店家」）。`UpdateProfile` 改了其中任何一欄（`payuniDataChanged`）就在同一個 transaction 登記意圖（`payuni.RequestSync`）並排入 job；job 不帶資料，執行時讀店家目前的值，所以連續的修改合併、PENDING 期間改的也會被送到，核准（含重新核准）不會重設它們。「同步到 PayUni 的店家欄位」只在 `payuni.StoreData` 定義一份（變更偵測 `SyncedFieldsChanged`、完整性 `Missing`／`MissingStoreFields`、bind 與 update 的請求都由它推導，新增欄位只改這裡）；有 PayUni 註冊之後必填欄位不能清掉（`checkRequiredNotCleared`，`TestRequiredStoreFieldsCannotBeClearedOnceARegistrationExists`），同步時必填值是空的就不呼叫 PayUni、記 `INCOMPLETE_DATA`（`TestSyncFailsLoudlyWhenARequiredStoreValueIsEmpty`）。送給 PayUni 的電話在 `platform/payuni` 轉成「區碼-電話號碼」（`phone.FormatWithAreaCode`）。綁定時會員的 `Email` 與 `MerEmail` 都是客服信箱（PayUni 的 `Email` 綁定之後不能改，之後只送 `MerEmail`），企業的 `MBCMail` 同樣是客服信箱；`ContactTel` 與 `MBCTel` 讀註冊所指申請的 `company_phone`（個人沒有），bind 與 update 同一個讀取點（`KYCSource.CompanyPhone`），不複製。送出 KYC 要店家的地址、聯絡人姓名、聯絡人手機與客服信箱齊全：申請自己的缺項先回 `invalid_argument`，之後店家資料還缺回 `failed_precondition`，缺哪些看 `KYCApplication.missing_store_fields`（同一份規則 `payuni.MissingStoreFields`）；綁定時的 `INCOMPLETE_DATA` 用同一份規則當防線，問題只指向店家現在實際缺的欄位。`TestAddressChangeDuringPendingAndAfterBindingIsSynced`、`TestStoreContactEditsRegisterTheSyncAndAreSentByTheSameJob`、`TestContactEditBeforeTheBindIsWhatGetsSent`、`TestSubmitKYCRequiresTheStoreContactData`、`TestContactToStoreMigrationDropsTheOldCopiesAndTightensTheChecks` 驗證。

- 身分欄位鎖：`update_merchant` 只能改聯絡方式、地址與支付設定，核心身分欄位由 `bind_merchant` 建立後不可變更（`backend/docs/第三方整合/PayUni 代理商專用 API 總覽.md` §8）。所以 KYC 審核中、或註冊有 MerID 而且 PayUni 已收下（或正要收下，`bind_status` 不是 `FAILED`）時，店名、介紹與 KYC 的身分欄位（真實姓名、公司名稱、身分證號、負責人身分證號、統編、英文名稱、官網、商品類型、賣家型態）不能改，包含 PayUni 拒絕後申請改回草稿的期間；只有聯絡信箱、聯絡手機、公司電話與店家地址能改，也只有它們會送出。由模組強制（`UpdateProfile`、`SaveKYCDraft` 回 `FailedPrecondition`），不只靠 UI；綁定失敗或還沒有 MerID 時不鎖；讀取失敗時拒絕。`TestStoreNameAndDescriptionAreLockedWhilePayUniHoldsThem`、`TestIdentityStaysLockedWhileThePayUniRejectedApplicationIsBackInDraft`、`TestIdentityIsEditableBeforeAnyMerIDExists` 驗證。

- 重新綁定只由狀態檢查保護（沒有 etag、沒有理由）：只有 `FAILED` 能綁，`PENDING` 重送冪等，其餘 FailedPrecondition，終止狀態（`NeedsReonboarding`）不能綁；回傳的註冊與 `Registration` 一致，帶申請的賣家型態。`TestRebindReturnsTheRegistrationWithTheSellerType`。觀測紀錄 `PayUniObservations` 是 `(executed_at, observation_id)` 的 keyset（索引 `payuni_observations_store`），店家不存在回 NotFound，`TestPayUniObservationsPageNewestFirstPerStore`。

- PayUni 狀態一律先追加成觀測（`payuni_observations`，只有 INSERT 的查詢；來源 `WEBHOOK`／`POLL`／`REFRESH`／`BIND`），再經同一個 `record` 套用到註冊列：`(store_id, event_key)` 唯一（重複的 webhook 只記一次、只套用一次）；`executed_at`（webhook 是 PayUni 的 `ExecuteTime`，台北時間；其他是收到回應的時間）比 `status_observed_at` 新才更新（條件式 UPDATE，亂序的舊通知不倒退，舊的仍留在歷史）；完整的觀測（輪詢、刷新、認領）整組取代狀態，webhook 只有 `MerStatus` 與說明，沒有回報的欄位保留；狀態有實質變化（`mer_status` 或 `member_status` 不同）時在同一個 transaction 發 `merchant.verification.*` 事件：核准、待補件、拒絕各一個，審核中只在從待補件回來時發，認不得的狀態不發。`TestDuplicateWebhookIsAppliedOnce`、`TestOutOfOrderObservationsDoNotRegressTheStatus`、`TestWebhookKeepsTheFieldsItDoesNotReport`、`TestPollAppliesTheStatusAndSweepSchedulesPolls` 驗證。

- webhook 的路徑：legacy consumer（`internal/legacy/sellerconsumer`，在 worker 執行）呼叫 `ReceivePayUniNotification`：驗證形狀（沒有 event_key、MerID 不是 `HAWK` 加店號、沒有 `MerStatus` 是 `InvalidInput`，consumer 記錄後進 dead-letter）後排入以 `event_key` 為唯一鍵的 `seller.payuni_observe` 並持久化，之後才 ack；job 套用失敗回錯誤讓 River 重試（不吞掉），未知的店家回 `ErrPayUniPermanent`，worker 取消（不重試）。沒有（或格式不合）`ExecuteTime` 的通知無從排序，不套用它的內容，改排該店家的狀態刷新（以 `store_id` 為唯一鍵的 poll job，來源 `REFRESH`），由查到的權威狀態更新（未知店家仍是永久錯誤）：`TestNotificationWithoutAUsableExecuteTimeTriggersARefresh`。`TestApplyFailureIsReturnedNotSwallowed`、`TestMalformedOrUnknownNotificationsArePermanent` 驗證。

- 輪詢與掃描：`seller.payuni_sweep`（啟動即執行、每 15 分鐘）排輪詢（已綁定、`outcome` 還沒有定論、超過 2 小時沒問過的註冊，每筆一個以 `store_id` 為唯一鍵的 `seller.payuni_poll`）與補排遺失的 sync（有資料沒送出、閒置超過 10 分鐘的註冊：job 被丟棄、當掉，或結果寫入與 River 標記完成之間的空檔）；管理員手動刷新排同一個 poll job，套用走同一個函式。已核准與已拒絕的註冊不輪詢（PayUni 之後改狀態靠 webhook）。`TestSweepReschedulesSyncsThatWereLost`、`TestAdminRefreshUsesTheSamePollJob` 驗證。

- PayUni 事件（`PayUniForwarded`、`PayUniApproved`、`PayUniPendingInfo`、`PayUniUnderReview`、`PayUniRejected`，加沒有舊 routing key 的 `PayUniBindFailed`）在寫入的 transaction 內發出，`EventID` 是寫進去的那筆觀測的 UUIDv7（穩定），wire 的 `{event_id, status, reason?, merchant_id（= AccountID）, store_id}` 與 routing key 照舊（`tests/contract/golden/event_payload_keys.json`），由 `internal/legacy/sellerrelay` 轉送；`pending_info` 與 `rejected` 的 reason 是 PayUni 的審核意見（沒有時空字串，預設文案由 relay 依舊的規則補）。`TestBindSendsTheCurrentDataAndRecordsTheForwardedEvent` 驗證。

- 2 QPS 的外部限制由 `platform/payuni` 的 `golang.org/x/time/rate` 限流器守住（`PAYUNI_MAX_QPS`，預設 2，burst 1，一個程序一個 client）；排不進 deadline 的呼叫回暫時性錯誤，由 River 重試。限流器只在程序內，所以只能有一個 worker 程序，第二個 worker 需要共用的限流器才能開。PayUni 規格要求固定的 IV，同一把金鑰下相同的明文產生相同的密文。

- `seller.payuni_sync` 結果寫入之後、River 標記完成之前到達的改動，因為唯一鍵含 `running`，不會另排 job；`seller.payuni_sweep` 在閒置 10 分鐘後補排（最多延遲約一個掃描週期）。同步被 PayUni 永久拒絕（`sync_error_code`）時賣家要再改一次才會重送，沒有自動重試。webhook 的 consumer（`sellerconsumer`）跑在 worker；`PayUniBindFailed` 沒有舊 routing key，不轉送。

- PayUni 子商店（同一份 ADR「核准與綁定」「PayUni webhook」）：核准時在同一個 transaction 寫入綁定意圖並排入以 `store_id` 為唯一鍵的 job，job 在 transaction 外向 PayUni 綁定（MerID 已存在時查詢認領）與同步店家的聯絡資料、地址；管理員重新綁定失敗的註冊（在 `kyc_reviews` 留下 `REBIND` 紀錄：誰（管理員 ID）、何時、哪一份申請，`TestAdminRebindIsRecorded`；回傳的註冊與一般讀取一致，帶賣家型態）；PayUni 的審核狀態（webhook、輪詢、手動刷新、綁定認領）先追加成觀測再套用，cert 軸與 PayUni 軸合成流程狀態。賣家看到的 PayUni 狀態在 `KYCFlow.payuni`（`PayUniState`、說明句、審核意見、能修正的欄位），由 `model.SellerPayUniOf` 推導（階段只經 `PayUniPhaseOf`）；流程、PayUni 狀態與不能重送的原因出自 `payuni.SellerViewOf` 的同一次註冊載入（帶賣家型態與店家缺的欄位），`DeriveKYCFlow` 的 `CanResubmit` 與 `SellerPayUniOf` 吃同一份、呼叫同一個 `sellerPayUniOf`，`KYCFlow` 不帶 PayUni 的事實（它們在 `PayUniRegistration`）；`KYCFlow.can_resubmit` 是 `SaveKYCDraft` 與 `SubmitKYC` 此刻會被接受（PayUni 階段 ⇔ 推導結果是 FIXABLE），不能做的原因與句子只在 `model.ResubmitUnavailableReasons`，兩個 RPC 的 `failed_precondition` 與 `resubmit_unavailabilities` 同一個函式；沒有 `GetMyPayUni`。綁定重試用完（`PAYUNI_UNAVAILABLE`）進後台待辦 `review_payuni_bind_retry`（`bind_failed_at` 起算 24 小時）；重新綁定的可用性與方法同一個函式（`model.RebindUnavailableReasons`，見 §17）。

### 14.1 審核結果與賣家看到的狀態

`outcome` 由 PayUni 回報的 `(MerStatus, MemberStatus)` 推導（`model.PayUniOutcomeOf`，認不得的碼 fail closed 為 `UNRECOGNIZED`，不當成核准、不通知）：

| 條件 | outcome |
|---|---|
| 兩者皆無 | `NONE` |
| `MerStatus` 為 `2`、`8`、`92`、`99`（商家層級終止） | `REJECTED`（MemberStatus 無關） |
| `MerStatus` 為 `91` | `PENDING_INFO`（MemberStatus 無關） |
| `MerStatus` 為 `1` 或 `9` 且 `MemberStatus` 為 `8`、`92`、`99` | `REJECTED` |
| `(1,1)` | `APPROVED` |
| `(1,5)`、`(9,5)` | `PENDING_INFO` |
| `(1,9)`、`(1,空)`、`(9,1)`、`(9,9)`、`(9,空)`；`MerStatus` 為 `1` 或 `9` 的其他組合 | `UNDER_REVIEW` |
| `MemberStatus` 為 `5`（其他 MerStatus） | `PENDING_INFO` |
| 其餘 | `UNRECOGNIZED` |

`MemberStatus`：`1` 啟用、`5` 待補資料、`8` 拒絕、`9` 待審核、`92` 審核失敗、`99` 關閉／停權；它是自然人層級，同一賣家旗下多個商店共用。`bind_merchant` 只建立商店；PayUni 判斷賣家是否已是會員，非會員時自動建立會員並寄信給賣家，新會員必須自行到 PayUni 後台驗證 email、填會員資料並送審，`MemberStatus` 才由 `5` 轉 `1`。這段完全在 PayUni 端，平台無法代填，查詢狀態也不回會員層缺漏細節（`Reason` 只用於商店層退件），所以 `PENDING_INFO` 且是會員層待補時，client 只能引導賣家到 PayUni 後台。

賣家看到的 PayUni 狀態（`PayUniState`，`SellerPayUniOf`）一個值對應賣家的一種動作：

| 值 | 意義 | 賣家動作 |
|---|---|---|
| `REVIEWING` | 綁定中或 PayUni 審核中 | 等 |
| `PENDING_INFO` | PayUni 要求補件 | 看 PayUni 的信、到 PayUni 後台補 |
| `FIXABLE` | 申請的資料有問題 | 修改申請後自己重新送出 |
| `FIX_VIA_SUPPORT` | 店家設定的資料有問題 | 改店家設定後由平台重新處理 |
| `CONTACT_SUPPORT` | 沒有賣家能修正的資料 | 找客服 |
| `RETRY_LATER` | PayUni 暫時無法處理 | 等平台重新送出 |
| `TERMINATED` | PayUni 端的商店已是終止狀態（`MER_2`／`MER_8`／`MER_92`／`MER_99`），同一個店家無法再綁定 | 關店後以新的 `store_code` 重新入駐 |
| `APPROVED` | 可以收款 | — |

### 14.2 綁定、同步與觀測的參數

- `seller.payuni_sync` 一次 PayUni 呼叫的 deadline 是 20 秒、一次 job 上限 60 秒（`payuni.go` 的 `callTimeout`、`jobTimeout`）；暫時性失敗由 River 退避重試最多 8 次（`syncMaxAttempts`），最後一次仍失敗時綁定記為 `FAILED`（`PAYUNI_UNAVAILABLE`）、同步記為同步失敗；永久的失敗（驗證類的碼、資料不完整、沒有設定）直接記錄。
- 第一段（transaction）鎖住註冊列、確認有事要做並記下 `intent_seq`；沒有註冊列、已失敗等管理員處理、沒有資料待送、店家已關閉都不做事。`PENDING` 的註冊做 `bind_merchant`，`BOUND` 而且有資料沒送出的做 `update_merchant`（PayUni 拒絕之後重新送出再核准的註冊也走這裡）。
- MerID 是 `store_code` 的確定性函式；`AGENT04017`（MerID 已存在）不是失敗，先查詢狀態認領，所以結果不明（逾時）之後重送一律安全。
- 店家還沒有註冊列時，`RequestSync` 什麼都不做。恢復營業的 transaction 內補排關店期間被放棄的綁定與同步（`Resume`）。
- 觀測的曝光與保留：PayUni 的審核狀態與綁定是「可公開曝光」的輸入，改變時在同一個 transaction 內重新公告曝光並排入 website 店家頁的快取失效（§24）；觀測紀錄併入店家個資清理的保留期，店家關閉滿保留期後 `reason` 清成 NULL，狀態碼與時間保留。
- 認證與 PayUni 的每個狀態變化都是模組事件，與狀態寫入在同一個 transaction，`event_id` 是觸發它的審核紀錄或觀測的 ID；通知服務仍消費的 `merchant.verification.*` 由 `internal/legacy/sellerrelay` 轉出，欄位、JSON 型別與時間格式與舊契約逐欄位相同；通知以 `reference_id` 去重由消費端負責。
- 重新綁定（`RebindPayUni`）：對 `FAILED` 的註冊回到 `PENDING` 並排入新的 job（不是再核准一次）；清單空就重新綁定，已在重新綁定（`PAYUNI_BIND_IN_PROGRESS`）時重送安全、回傳目前的列，其餘原因（PayUni 端已終止、店家已關閉或等待刪除、已綁定、註冊所根據的申請不是已核准）回 `failed_precondition`。

## 15. 商家名單

- 商家名單的聯絡方式（ADR `2026-10-04-prospect-contact-points-and-matching`）：`prospect_contacts` 每列是類型（`EMAIL`、`PHONE`、`WEBSITE`、`SOCIAL`）、管理員輸入的原值、解析器 `model.ContactMatchKey` 推導的比對鍵（帶種類前綴；佔位值、共用平台的網域、短網址、貼文路徑、社群平台的裸網域都是 NULL，不參與比對）與是否主要的；Create 與 Update 整批替換（`Contacts` 在 Update 為 nil 保留、空清單清空）。某類型有聯絡方式時恰好一個主要的：同類型至多一個由 partial 唯一約束 `prospect_contacts_primary`、至少一個由 deferred 自我參照外鍵 `prospect_contacts_has_primary`，模組的 `model.NormalizeContacts` 在寫入前檢查（同類型多列必須恰好一列標主要的，只有一列時它就是主要的）。`ProspectContact` 回主要的 email，搜尋結果帶主要的網站。`TestExactlyOnePrimaryContactPerKindIsEnforcedByTheDatabase`、`TestUpdateProspectReplacesTheContactListAndKeepsOmittedFields`、`TestProspectContactReturnsThePrimaryEmail`、`TestSearchProspectsReturnsThePrimaryWebsite`、`internal/model` 的 `TestNormalizeContacts`、`TestContactMatchKey`。

- 商家名單的比對：統編是權威識別碼，在未封存（`prospects.live`：ACTIVE 與 CONVERTED）的業者之間 partial UNIQUE（`prospects_tax_id`），建立撞到回 AlreadyExists，修改與還原撞到回 FailedPrecondition，都帶 reason `PROSPECT_TAX_ID_HELD` 與 metadata `prospectIds`（持有者的 ID）；句子依操作與持有者的狀態（持有者進行中的修改說該做的是合併，已入駐的說請封存這筆，還原說不需要還原），確認不是同一家也繞不過。建立、修改（統編有改）與還原在檢查持有者之前以統編取交易級 advisory lock（`LockProspectTaxID`；統編沒有 aggregate 列可鎖），同一個統編的寫入排隊，應用層的檢查就是權威；撞到唯一約束代表程式有錯，照原樣傳回。合併搬統編不取鎖（輸家清除與贏家取得在同一個交易）。比對鍵不唯一：Create、改到聯絡方式的 Update（檢查新清單的全部比對鍵）與 Restore，與其他未封存的業者有相同比對鍵、而且 `prospect_distinct_pairs` 沒有標記時回 FailedPrecondition，reason `PROSPECT_MATCH_FOUND`、metadata `prospectIds` 是全部相符的業者（`model.NewProspectMatchFound`，模組附上，傳輸層沒有特例）；輸入的 `ConfirmedDistinct` 涵蓋全部相符的業者時才寫入，並在同一個 transaction 記下配對（較小的 ID 在前、管理員、時間，沒有相符的 ID 不記）。換圖的請求同樣在轉正之前做這些檢查。`TestSharedContactKeyNeedsConfirmationThenIsRemembered`、`TestSharedPlatformWebsitesAreNotMatchKeys`、`TestPlaceholderContactsNeverMatch`、`TestTaxIDIsUniqueAmongLiveProspects`、`TestUpdateProspectContactMatchNeedsConfirmation`、`TestArchiveNeedsTheCurrentVersionAndYieldsTaxIDAndMatching`。

- 合併：輸家與贏家都必須是 ACTIVE，兩列依 ID 順序鎖，兩邊的版本都要相符；輸家的聯絡方式併入贏家（同一個比對鍵、或同類型同一個值只留一列，贏家的主要聯絡方式不變；贏家在某類型沒有聯絡方式時，輸家那個類型的主要的成為主要的）、輸家的聯絡方式移走、輸家的「不是同一家」配對改掛贏家（變成自己對自己或重複的刪除，明確合併一對標記為不是同一家的業者就是撤銷那個標記）、分類補進贏家、已被輸家吸收的列改指贏家（`merged_into` 的鏈永遠一層）、統編只在贏家沒有時搬過去、輸家的統編一律釋放，輸家封存並記 `merged_into`（不可還原），贏家版本加一；輸家的聯絡方式之後再被建立會撞到贏家，建立前的比對也指向贏家。`TestMergeUnionsContactsAndRepointsDistinctPairs`、`TestMergeKeepsExactlyOnePrimaryPerKind`、`TestMergeTaxIDAndPathCompression` 驗證。

- 疑似重複清單是尚未處理的候選配對：ACTIVE 的業者之間名稱（忽略大小寫與前後空白）相同、或比對鍵相同（並行建立漏網的），排除已標記為不是同一家的；keyset 分頁（不是 LIMIT 501 截斷），永不自動合併；候選配對的處理方式是合併，或 `MarkProspectsDistinct`（直接標記不是同一家：不帶版本，只限兩個進行中的業者，冪等，不改寫第一次的管理員與時間；`TestMarkProspectsDistinctDismissesACandidatePair`）。`TestDuplicatesAreUnresolvedPairsBySameNameOrSharedKey` 驗證。

- 業者的寫入以 `prospects.version`（整列，文字、聯絡方式與圖片共用）做樂觀鎖：`UpdateProspect` 必帶讀到的版本，只有 ACTIVE 的業者可以改，沒有任何改變時不寫入（版本不變，過期的版本照樣衝突）；`OutreachStatus` 的 `CONVERTED` 只由轉成店家寫入，管理員不能手動設。合併（兩邊）、轉成店家、封存同樣必帶版本（etag ADR `2026-09-25-optimistic-concurrency-etag` 的判準）：沒帶回 InvalidInput，不符回 VersionConflict、什麼都不寫；版本檢查先於狀態檢查，不推斷重送：命令生效後帶舊版本再送一次一律 VersionConflict、不寫入、不發事件（`TestStaleEtagAfterArchiveMergeAndConvertConflicts`）；已經封存的業者帶目前的版本再封存，回傳目前的列、不寫入、不發事件；還原不帶版本（依據的是封存這個狀態）。`TestUpdateProspectOptimisticLock`、`TestConcurrentProspectUpdatesConflict`、`TestStaleVersionsRejectMergeConvertAndArchiveWithoutWriting` 驗證。

- 手動轉成店家（`ConvertProspect`，帶 `ExpectedVersion`）：店家必須是目前的 stint（`status <> CLOSED`），只有 ACTIVE 的業者可以轉（二次轉換、封存與被合併的回 FailedPrecondition），同一個店家只能被一個業者認領（`prospects_converted_store`，AlreadyExists）；`converted_store_id` 指向 `store_id`，`prospects_converted_check` 綁 CONVERTED、`converted_store_id`、`converted_at` 與 `outreach_status`。統編對帳以 KYC 申請的 `store_id` 為鍵、只對目前的 stint，已被其他業者認領的店家不列。`TestConvertProspectToStore`、`TestConcurrentConversionOfOneProspectSucceedsOnce`、`TestTaxIDMatchesAreKeyedByStoreID`、`TestTaxIDMatchesExcludeStoresClaimedByAnotherProspect` 驗證。

- 業者圖片的 media 引用以 `ref_id = prospect_id` 登記（`SELLER_PROSPECT_LOGO` 7122、`SELLER_PROSPECT_COVER` 7123）：換圖在鎖住業者列的 transaction 內把被換掉的那一張記成退場；封存與合併把圖片欄位清成 NULL（`prospects_images_check`）並在同一個 transaction 把清掉的圖記成退場，封存之後的還原不會把圖帶回來，所以退場的圖不會再被寫回（還原後換圖，目前的圖照樣被登記）。換圖併進 `UpdateProspect`（`Logo`、`Cover` 上傳 {暫存 token、選填且只收 https 的來源網址}，必須在 transaction 外呼叫）：轉正之前先做所有不需寫入的檢查（狀態、版本、驗證、統編、比對），被拒絕的請求不消耗 token；轉正後在鎖住業者列的同一個版本條件 transaction 內一次寫文字、聯絡方式與圖片（版本只加一）。`TestProspectImagesLinkByProspectIDAndUseVersion`、`TestProspectImageUploadValidation`、`TestRejectedProspectUpdateDoesNotConsumeTheStagedToken`、`TestProspectImageWriteLosesToAConcurrentEdit`、`TestArchiveAndMergeRetireImagesAndSyncUnlinksThem`、`TestSyncBetweenFinalizeAndCommitKeepsTheProspectImage` 驗證。

- 採購候選搜尋：只看 ACTIVE（已入駐、封存、被合併的不出現），填了的條件是加權 OR、不是 AND，分類、地區、關鍵字是部分比對（使用者的 `%`、`_` 不當萬用字元，舊實作會），分類樹 ID 走子表，結果不排序（算分是 ai-service 的事），`Limit` 預設 500、上限 1000 只是安全上限。`TestSearchProspectsSemantics` 驗證。

- 範圍邊界：模組不含邀請子系統（沒有消費者）；`category`、`region` 的自由文字與分類樹 ID 並存，分類由後台 `CreateProspect`、`UpdateProspect` 的 `category_ids` 寫入，分類標註工具是 `services/ai-service/cmd/prospect-category-gen`。共用平台的排除清單（`prospectSharedHosts`）只有已知的 `linktr.ee` 與 `pinkoi.com`，新的共用平台出現時加進去。

- 合併不搬圖片（引用依 `prospect_id` 登記，沒有搬移的操作）：輸家的圖片釋放，贏家沒有圖片時要重新上傳。

## 16. 商品瀏覽數

- 商品瀏覽數以 `store_id` 為鍵，日以台北時間為界（`internal/platform/twtime`），期間由呼叫者給（賣家儀表板是最近 7 個完整台北日對前 7 日）；總次數、不去重（欄位名稱或顯示文案像是唯一數也不得改成去重；顯示文案由 App／Website 各自負責）；不回百分比，比較的呈現在 client。沒有商品與來源欄位（沒有讀取者）、`product_views_daily.store_id` 參照 `seller.stores`，列數隨店數乘天數成長。`TestRecordProductViewOnlyAppendsAnEvent`、`TestRollupBucketsByStoreAndTaipeiDayOfOccurrence`、`TestProductViewsBetweenCountsTaipeiDaysHalfOpen`、`TestProductViewsBetweenIsIsolatedPerStoreAndValidatesInput`、`TestViewRange`、`TestViewDayUsesTaipeiBoundaries` 驗證。

- 瀏覽事件的流程：

- 寫入：登入買家的 `RecordVisit(buyerID, productID)` 在同一個 transaction 發 `ProductViewed{EventID, OccurredAt, BuyerID, ProductID}`（沒有 StoreID，請求路徑不解析商品），`cmd/hawkr` 的 `subscribeSellerViews` 訂閱後呼叫 `IngestProductView`，只有一句 insert（以 `EventID` 為主鍵，重送不會多一列；`OccurredAt` 由 buyer 的 clock 給）；匿名打點呼叫 `RecordProductView`（`event_id` 由 `uuid.NewV7`、時間由注入的 clock）。seller 與 buyer 互不 import。給 notification 的 legacy relay 的 payload 不變（`seller_id` 是帳號 ID）。

- 彙總（`seller.product_views_rollup`，每 5 分鐘、啟動即執行、unique）：依 `occurred_at, event_id` 讀一批（100 筆）沒處理的事件；在 DB transaction 之外以 `ProductStores`（一次批次呼叫、10 秒 deadline；legacy 的 product client 實作，在 cmd 接線）解析去重後的商品；再一個 transaction：取共享 advisory lock、`FOR UPDATE SKIP LOCKED` 鎖住仍沒處理的列，一句 SQL 內標記（`store_id`、`processed_at`、`outcome`）並以事件 `occurred_at` 的台北日曆日累加 `product_views_daily`——標記與計數在同一句，不會只成功一半。一次執行最多 50 批，積壓留給下一次。port 暫時性錯誤整個 job 回 error，這批沒有事件被標記，River 重試時只計一次。商品不存在、沒有店家或店家不在 `seller.stores` 標 `UNRESOLVED`（不計入任何地方、不重試，留著除錯；`TestRollupMarksEventsOfUnknownStoresUnresolvedAndTheBatchContinues`）。

- 重算：`RebuildProductViews` 以已處理（`COUNTED`）事件儲存的 `store_id` 在一個 transaction 內先刪區間、再重建（分成兩句：同一句的 CTE 看同一份 snapshot，刪除尚未生效，重建會撞主鍵），取獨占 advisory lock，彙總 job 與清理不會插進來；起日的台北 00:00 早於 now − 7 天回 InvalidInput（更早的事件可能已清掉）。重算只涵蓋原始事件的保留期，更早的日子只剩彙總，無法重建。

- 保留：已處理且 `occurred_at` 早於 now − 7 天的事件由 `seller.product_views_purge`（每小時）刪除；沒處理的不刪。

- 驗證：`TestRollup*`、`TestRebuild*`、`TestPurgeOnlyDeletesProcessedEventsOlderThanRetention`，以及 `cmd/hawkr` 的 `TestLoggedInProductViewSucceedsWithoutProductServiceAndIsRolledUpLater`（商品服務不通時瀏覽照樣成功，port 不在請求路徑上被呼叫）。

- 匿名打點入口是 `SellerPublicService.RecordProductView`：只計訪客，有呼叫者時回成功但不寫入（登入買家由 `RecordVisit` 計，同一次瀏覽不會算兩次），不檢查商品是否存在（只有一句 insert，不存在的商品不回錯，彙總 job 解析不到店家的事件標為 `UNRESOLVED`，不計入也不重試），每個來源 IP 每分鐘 120 次（`internal/httpapi/ratelimit.go` 的 `procedureTiers`，在程序的記憶體內計數）。

- 匿名打點寫入失敗時回錯誤給 client（client 對打點 fire-and-forget、靜默忽略）；打點被爬蟲觸發時計數會失真，現行防線只有每個來源 IP 的額度，沒有 bot detection。

- 儀表板的商品瀏覽區塊呼叫 `ProductViewsBetween` 本期與前一期各一次；該區塊失敗或逾時只讓區塊不設（記 warn），不變成 0，也不讓 `GetMyDashboard` 失敗。只讀每日彙總，最近一次彙總之後的瀏覽還沒計入。

- 不做：商品個別瀏覽數、去重統計、細分來源（登入／匿名、iOS／Android／Web）、即時排行。

## 17. 後台店家清單與措施生效中的定義

- 後台清單固定五次查詢（店家、處分、條件、KYC 申請、PayUni 註冊），每頁的停權經 `stint.EffectiveMany`、條件經 `stint.WithConditions`、顯示用的 KYC 流程經 `exposure.KYCFlows`；翻頁用 `(created_at, store_id)` 的 keyset，同一個建立時間的店家以 `store_id` 定序。篩選：帳號（完全相符）、目前那一筆還沒取消的 KYC 申請的狀態（`APPROVED`、`REJECTED`；審核中、草稿與已取消回 InvalidInput：「待審核」不是儲存的事實）、`KYCAwaitingReview`（商家認證申請在後台待辦裡，是 `seller.review_kyc_application` 的成員；統計的 `KYCAwaitingReview`、待辦與 `decide_deadline` 讀同一支函式，待審核只有這一個定義）、PayUni 註冊的 `bind_status`（儲存的事實）、帳號此刻是否停權。**「措施生效中」的 SQL 定義有兩支查詢，存取路徑不同、定義相同（`starts_at <= now ∧ (ends_at IS NULL ∨ ends_at > now)`，種類 `SUSPENSION` 與 `TERMINATION`），「預定生效」是 `ScheduledMeasureIDs`（`starts_at > now ∧ (ends_at IS NULL ∨ ends_at > now)`；措施列表的 SCHEDULED 篩選用它，ENDED 篩選是不在生效中也不在預定生效），`seller.account_sanction_lifted_at(account_id, at)` 是第五種讀法（帳號最近一次停權結束的時間：在 at 以前已結束的停權與終止措施的結束時間最大值，到期是 `ends_at`、撤銷是 `revoked_at`，只算真的生效過的；只給 `review_kyc_application` 算暫停審核的起點，`TestKYCReviewPausesDuringSuspensionAndResumesWhenItEnds` 在 `ends_at`、`revoked_at` 等於 at 的瞬間鎖住它與 `effective_measures` 一致），`StateOf` 是第四種寫法（順序：已撤銷、警告、已結束、預定生效、生效中，不認得的種類 panic；預告期間內因店家關閉而結束的措施 `ends_at` 早於 `starts_at`，是 ENDED；devseed 不寫自己的措施 SQL，種子檢查問 `EffectiveMeasures`，`TestDevSeedHasNoMeasureSQLOfItsOwn`）**：指定帳號的 `EffectiveMeasures`（能力檢查、讀店家、身分快照的清理，走 `measures_enforced_suspension`）與問全部帳號的 `EffectiveMeasuresAll`（清單的停權篩選 `stint.SuspendedAccounts`，結果當陣列參數傳給清單；措施清單的 ACTIVE、ENDED 篩選 `stint.ActiveMeasureIDs`；每小時的對帳；讀取量隨生效中的措施成長，不隨歷史成長）；`model.StateOf` 是同一個定義的 Go 寫法（讀取時推導措施的 `state`），以 ## 18. 交易邊界與鎖順序

- 鎖順序：identity 帳號列先於店家列，店家列是帳號全部的 stint（依 `store_id`，`LockAccountStores`；所有關店路徑都鎖它，不先鎖目前的 stint 再寫措施（會與措施寫入的升序鎖互鎖）），再來是通報列（多筆依 id 升序）、案件列（多筆依 id 升序）、詢問列、措施列（發詢問、記下回覆與撤回：店家列 → 案件列 → 詢問列；決定與移動造成的 `NO_REPORTS` 關閉在鎖案件之後以一個 UPDATE 撤回還沒結束的詢問，同時鎖住它）。分案、移動、決定與建立措施都先鎖店家列：同一家店、同一個類別的開案由它串行（`cases_one_open` 只是保底，撞到時是 invalid_argument，不是 23505）；決定在店家列之後先讀成員、鎖成員通報、最後鎖案件；補充只鎖原通報列（不鎖案件、不改案件的版本）；建立措施的來源通報（`measure.lockSourceReports`）在店家列之後依 id 升序鎖，連到案件（`source_case_id`）時不鎖案件：關閉案件的指令都先鎖同一組店家列。`TestConcurrentTriageOfTheSameStoreAndCategoryOpensExactlyOneCase`、`TestDecideAndAConcurrentTriageNeverLeaveAnUnresolvedMemberInAClosedCase`、`TestDecideAndMoveNeverDeadlockWithASupplementToTheSameReport`、`TestTriageAndDecideNeverDeadlockWithCreatingMeasures`（壓力測試，各 200 輪）。開店、`CloseCurrent` 與終止合作的關店自己先鎖帳號；`BeginDeletion`／`CloseForDeletion` 只由 `accountdeletion` 在已鎖住帳號列的 transaction 內呼叫，本模組不再鎖帳號。跨帳號的寫入（建立關聯終止、撤銷有關聯終止的來源）一律依 `account_id` 升序先鎖 identity 帳號列再鎖各帳號的 stint；撤銷在鎖之前預讀要碰的帳號、鎖住之後重讀，範圍變了（剛好有新的關聯終止）整個 transaction 重來（`retryScope`）。賣家對終止合作措施的申覆（`measure.lockForRequest`）同一套：不加鎖預讀以它為來源的關聯終止所在的帳號，與來源帳號依 `account_id` 升序鎖（`stint.LockAccounts`），鎖措施列之後重讀，範圍變了回 `errScopeChanged` 由 `retryScope` 重來，因為個資清理的 legal hold 含「關聯終止的來源有待處理的申覆」，被關聯帳號的清理要和這筆申覆競爭同一組店家列（`TestLinkedSourceAppealBlocksThePurgeOfTheLinkedAccount`）。`TestConcurrentSourceRevokeAndLinkedCreateNeverDeadlock`、`TestConcurrentMeasureCreationAndCloseOnAnAccountWithTwoStintsNeverDeadlock`（壓力測試，各 200 次）。主管機關來函的登記、完成與延長保存先依 `account_id` 升序鎖被指名帳號的店家列（`stint.LockAccounts`），再鎖來函列，讓寫入保存條件的一方和個資清理在同一組店家列上競爭；登記時鎖住之後把已清理的店家記進 `authority_order_prepurged_stores`，涵蓋狀態 `PURGED_BEFORE_REGISTRATION` 只看這份快照，不比較清理與登記的時鐘（多實例時鐘有差）；來函對象的位置連續由 `prev_position` 外鍵保證。

- 全域鎖順序（單體規則 4，適用 identity、buyer、seller、social）：identity 帳號列 → buyer → seller（店家與 stint 列 → 申請 → 登記 → 公告列；措施與通報在店家列之後）→ 依依賴表由下往上的上層模組 → 編排者（moderation、accountdeletion）自己的列；同一層多列依 ID 升序。seller 在 transaction 內發出的事件，其同 transaction 訂閱者（例如 social 的 `OnMeasureCreated`）在 seller 的列之後鎖自己的列，所以措施建立與撤銷總是先 seller 後 social。

- 事件與快取失效都在寫入的 transaction 內：handler 失敗或 job 排入失敗，整筆回滾。進入等待刪除只在真的從 ACTIVE 轉移時發一次 `StorePendingDeletion`（`TestDeletionParticipantIdempotency`）。

- 本模組的事件由 `internal/legacy/sellerrelay`（`cmd/hawkr` 的 `subscribeSellerRelay`，serve、worker 與 `reannounce-exposures` 都訂閱）轉成 RabbitMQ 訊息給 Java 與晚搬的 Go：`seller.deleted`（由 `StoreRetired`，關店 30 天後的退場時；`StoreClosed` 與 `StoreReopened` 不轉送：關店可逆，曝光與停權的變化各有事件）、`seller.suspended`、`seller.unsuspended`、`seller.profile.changed`、可曝光變化的 `seller.exposure.changed`（Java 依它在讀取時隱藏不可曝光的店的商品，等待刪除也由它涵蓋；ADR `2026-10-05-store-exposure-to-legacy.md`）與 `merchant.verification.*`。不轉送的事件（`StoreOpened`、`StoreClosed`、`StoreReopened`、`StorePendingDeletion`、`KYCSubmitted`、`KYCApproved`、`KYCCancelled`、`PayUniBindFailed`）與原因在 sellerrelay 的套件說明。治理事件（`ReportReceived`、`ReportResolved`（每筆通報有了結果發一次：個別設定、案件結案帶入都算）、`MeasureCreated`、`MeasureRevised`、`MeasureEnded`、`MeasureRevoked`、`MeasureRequestSubmitted`、`MeasureRequestDecided`、`MeasureRequestClosed`）沒有轉送，賣家、檢舉人與 admin 都以拉取的方式看到結果。

- 同 transaction 發布 lifecycle、profile、治理、KYC、PayUni 與商家名單的事件，排入 website 的快取失效。商家名單的事件給 agent 模組：`ProspectArchived{ProspectID}`（只在進行中變成封存時發；已封存的不發）、`ProspectMerged{SourceProspectID, TargetProspectID}`（輸家封存並指向贏家；輸家的封存只由這個事件表達，不另發 `ProspectArchived`）；還原不發事件。`TestArchiveProspectPublishesInTheTransactionOnlyOnTheTransition`、`TestMergeProspectsPublishesOnlyProspectMerged` 與兩個事件失敗回滾的測試驗證。

- 治理事件的發出時機：`ReportReceived`——每次送出：新的通報、補充（帶 `SupplementID`）、補充已達上限而沒有存下的匿名送出（`Discarded`），匿名的帶這次送出的 email；`ReportResolved`——通報有了結果，每筆一次（個別設定、不開案件直接設定、案件結案帶入都算）；`MeasureCreated`——建立措施；`MeasureRevised`——賣家看得到的內容（理由、結束時間）實際改變（結束時間改為現在不算，那是 `MeasureEnded`）；`MeasureEnded`——admin 結束 RISK 措施、接受解除請求，或店家關閉而結束預告終止（作者是系統），自然到期不發；`MeasureRevoked`——admin 撤銷、接受申覆或連帶撤銷，效果的解除另由 `StoreUnsuspended` 表示；`MeasureRequestSubmitted`——賣家提出申覆或解除請求（帶 `Kind`）；`MeasureRequestDecided`——admin 裁定（帶 `Kind`、`Outcome`），接受申覆同時發 `MeasureRevoked`，接受解除請求同時發 `MeasureEnded`；`MeasureRequestClosed`——待處理請求由平台結案（`Cause`：`REVOKED` 或 `ENDED`）；`StoreSuspended`／`StoreUnsuspended`——帳號從未停權變停權、恢復（以停權期間為單位）。事件不帶原檢舉人的聯絡方式。

## 21. 發布的讀取介面（pub_*）語意

- 形狀宣告在 `db/pub.sql`（依賴表允許的上層模組的 sqlc 讀它，`internal/arch` 的 `TestSQLCReadsOnlyItsOwnSchemaAndAllowedPubContracts` 擋住讀內部表），定義在 `db/objects.sql` 與手寫的 migration，`cmd/hawkr` 的 `TestPubContractsMatchMigrations` 比對兩者（欄位、型別、參數與回傳，雙向；函式的寫法由 `TestSchemaFileMatchesMigrations` 檢查）。`pub.sql` 裡宣告成表的 `pub_exposable_store` 只是函式回傳列的形狀，消費端的 query 不得直接參照它，只能呼叫函式（同一個 arch 測試；pgx 手寫的 SQL 字串不在檢查範圍，現在單體的正式程式碼裡沒有 seller 表的手寫 SQL）。改 `pub_*` 的形狀等於改契約：同一次變更內更新 `pub.sql` 與所有消費端；底層欄位改型別或刪除時在同一份 migration 內 drop 再建。

- `seller.pub_exposable_stores(at timestamptz) RETURNS SETOF seller.pub_exposable_store (store_id bigint)`：`at` 這一刻可以公開曝光的店家，曝光規則唯一的家（ADR `2026-09-24-go-modular-monolith` 文末修訂的曝光規則段）。`at` 由呼叫方以請求的 clock 傳入，不用 `now()`；函式會被內聯（沒有 Function Scan），join 時每家店對 measures 的讀取是以帳號為鍵的索引探測。上層用法：`EXISTS (SELECT 1 FROM seller.pub_exposable_stores(sqlc.arg(now)::timestamptz) e WHERE e.store_id = p.store_id)`。`store_exposures`、`StoreExposureChanged` 與 15 分鐘對帳只為行程外的 legacy 消費者保留，消費者搬進單體後刪除。

- `seller.pub_content_takedowns() RETURNS SETOF seller.pub_content_takedown (measure_id, content_kind, content_id)`：此刻生效中（未撤銷）的內容下架措施的對象，一列一個（措施，內容）；不收 `at`，因為下架建立即生效、沒有結束時間。給 social 每日對帳核對自己的複本，social 的讀取不 join 它（規格 `social.md` §4）。部分索引 `measures_active_takedown` 服務它。`TestPubContentTakedownsListsOnlyActiveTakedownTargets` 鎖住它。

- `seller.pub_review_items(at timestamptz) RETURNS SETOF seller.pub_review_item (kind, item_id, 對象的鍵, store_id, store_name, start_at, due_at)`：`at` 這一刻營運要處理的全部待辦（10 種，都有期限），是 10 支 `review_<種類>(at)` 的 `UNION ALL`，成員、開始與期限的規則只在那些函式。`reviewqueue` 模組讀它排序分頁（`due_at, start_at, kind, item_id` 的 keyset），沒有排序保證；`at` 由呼叫方傳入。`TestPubReviewItemsIsTheUnionOfTheReviewFunctions` 鎖住它等於逐支函式的集合。

- 10 種待辦各有營運期限（日曆時間，讀取時推導、不另存，規則只在 `seller.review_<種類>(at)`，Go 不寫時長；催辦靠 admin UI 強調與排班輪詢，不推播）：`REPORT_TRIAGE` 待分案（建立起，檢舉人選 `FOOD_SAFETY` 4 小時，其他 72 小時）；`CASE_DECISION` 待決定（從可以決定起算；依案件嚴重度 `CRITICAL` 24 小時、`HIGH` 72 小時、`MEDIUM` 168 小時、`LOW` 336 小時）；`CASE_INQUIRY_OVERDUE` 詢問逾期（賣家期限 `due_at` 起 24 小時）；`AUTHORITY_ORDER` 來函（登記的 `due_at`）；`AUTHORITY_TARGET_NOTICE` 告知被指名者（暫不告知的確認日期起 72 小時）；`MEASURE_APPEAL`、`MEASURE_LIFT_REQUEST`（提出起 168 小時；解除請求僅限措施仍生效中）；`MEASURE_REVIEW` 複審（`review_by` 前 24 小時進入，期限是 `review_by`）；`KYC_APPLICATION` 商家認證（送出、最近一次恢復營業、最近一次停權結束三者最晚者起 168 小時；店家不是營運中或帳號停權時暫停）；`PAYUNI_BIND_RETRY` 重新綁定 PayUni（綁定失敗起 24 小時）。時長是起始值，依營運數據校準。

## 22. 刪帳參與者

- `accountdeletion` 是刪帳的編排者，本模組是參與者。三個動作都只由 `accountdeletion` 在已經以 `identity.LockAccount` 鎖住帳號列的 transaction 內呼叫（鎖順序：帳號列先於買家列、店家列）：`Lock`（鎖住店家所屬帳號的店家列，不改任何東西）、`BeginDeletion`（目前的 stint 從 `ACTIVE` 進入等待刪除，同一個 transaction 發 `StorePendingDeletion`、重新公告可曝光並排入快取失效；已在等待時不做事、不重發，已關閉時成功）、`CloseForDeletion`（經 `closing.close()` 以 `ACCOUNT_DELETION` 關店，見 §11；已關閉時成功）。兩個動作都重送安全（`TestDeletionParticipantIdempotency`）。

- 店家側的未結訂單查詢是本模組的 `Orders` port（§11），`accountdeletion` 在管理員刪帳號時也用同一個實作。停權不擋刪帳（§10）。有 SELLER 卻沒有現任店家時 `accountdeletion` 回 internal（§2）。

## 23. 已知限制

每條寫現況與解除條件；搜尋沒有索引的觸發條件在 `CARRYOVER.md` 的觸發條件表。

- **數字 ID**：`store_id` 與停權期間的 `period_id` 是 IDENTITY（BIGINT），因為 Java 的消費者（coupon-service 的 `SellerSuspendedConsumer`、`SellerUnsuspendedConsumer`）仍以 BIGINT 存（product 的停權快照以 `period_id` 為 scope，Java 稱它 suspensionId）。最後一個數字 ID 的消費者改寫時，依 row-identity ADR 換 UUID。通報、認定、措施、請求、KYC 申請與審核、稽核列的 ID 是應用層產生的 UUIDv7，沒有 Java 的消費者。

- **未結訂單檢查的時間窗**：`Orders` port（§11）在 transaction 外問 ordering 的現況（現在的實作是 `internal/legacy/orderservice`），與之後鎖帳號、關店之間仍可能有新訂單成立，舊服務的訂單不在單體的鎖裡。解除條件：訂單搬進單體，以 ordering 自己的判斷在同一個 transaction 內檢查（`CARRYOVER.md`「7c 審查後的結論」）。

- **media 引用有同步空窗**：新轉正的資產要在 media GC 的 7 天寬限內被同步 job Link，轉正之後、同步完成之前沒有引用；job 失敗由 River 重試並記 error log。解除條件：引用移進業務列的 transaction，同步 job 與退場表消失。

- **identity 的 `source_id` 柵欄**：只為 seller-service 的非同步移除而存在，開店與關店照樣帶 `store_id` 當來源。解除條件：seller-service 退場。

- **治理事件沒有訂閱者**：§18 的治理事件還沒有 notification 的訂閱與送達紀錄。解除條件：notification 與資料保存期限搬進單體。

- **登入的買家被算兩次**：website 的 `ProductViewTracker` 對所有訪客呼叫 `RecordProductView`（§16），但公開 transport 不帶憑證，伺服器看不到登入者，所以登入的買家同一次瀏覽仍會被 beacon 與 `RecordVisit` 各算一次；buyer-app 尚未接上。解除條件：website 對登入者以帶憑證的 transport 呼叫，buyer-app 接上。

- **PayUni 沒有對真實環境驗證**：沒有 sandbox 與真實呼叫，`platform/payuni` 只以本機的 httptest 驗證，欄位名稱、`search_merchant_status` 的回應格式與 AES-GCM 的格式照舊的 `pkg/payuni`。`ExecuteTime` 的格式（`yyyyMMddHHmmss`）與時區（台北）取自 Java 測試的樣本與 PayUni 慣例，沒有對真實通知驗證；輪詢（事件時間用我們的時鐘）與 webhook（PayUni 的時鐘）混用，假設兩邊的時差遠小於狀態改變的間隔。解除條件：取得 PayUni 的 sandbox 或第一筆真實通知。

- **KYC 加密金鑰輪替沒有遷移 job**：HMAC 金鑰輪替有 `RehashKYCIdentities`（§13），加密金鑰輪替則要解密後重寫，這支 job 還沒有。解除條件：第一次輪替加密金鑰之前要先有它（沒有資料之前不做）。

- **身分比對的防線邊界**：只擋「同一個身分」，用別人的證件、人頭入駐不在防線內（ADR 後果）。處分建立之後才由被處分帳號新增的申請不在快照裡；被處分的帳號開不了新店，既有申請的核准要求帳號沒有停權，所以不會被核准。核准與「另一個帳號的處分同時寫入」不需要額外的鎖：處分在核准讀取之後才 commit，結果等於「先核准、後處分」，是合法的序列順序，之後的核准都會看到快照。快照只能取到處分當下還沒清理的 KYC：舊 stint 關閉滿 184 天（第二段清理）、KYC 已清理之後才被處分時，舊 stint 用過的身分不在快照裡（目前 stint 的身分仍在）；這是「關店 184 天後清註冊與身分資料」的代價（ADR 的資料最小化），不另外保留 hash。重新評估的條件：第二段清理的 184 天改動，或要開始擋借證件、人頭入駐時。

- **`SubmitKYC` 的限流只在程序內**：計數在 serve 程序的記憶體內，多個 instance 各自計數。解除條件：單體跑超過一個 instance 之前，換成共用的計數（入口的 IP 限流不是它的補償）。

- **保留的自由文字**：管理員的自由文字理由（措施的 `statement_to_seller` 與內部註記 `governance_notes`、後台刪帳號的 `request_attempts.reason`）是稽核文字，可能夾帶賣家的個資，保留，個資清理不動它們。登入檢舉人的 `reporter_buyer_id` 不隨買家刪除清掉：它是指向買家墓碑列的擬名鍵，買家的個資由 buyer 自己的刪除流程清除，seller 不依賴 buyer，清掉它會讓檢舉人無法查自己的檢舉、也讓去重失效。匿名通報與補充的描述是自由文字，可能含個資，保留：它們是通報的實質內容，後續調查需要，保留期限的清理只動聯絡欄位。重新評估的條件：隱私政策定稿時，或 notification 與資料保存期限搬進單體時。

- **搜尋是全表掃描**：後台店家清單的店名與電話、KYC 佇列的姓名、公司名稱與統編、商家名單的 ILIKE 搜尋都沒有索引，上線前的資料量不是問題；超過 1 萬列或 p95 超過 200 ms 時加 pg_trgm GIN（`CARRYOVER.md` 觸發條件表）。

- **詢問沒有賣家端**：回覆只由管理員記下系統外收到的內容（`reply_channel` 只有 `PHONE`、`EMAIL`、`MESSAGING`、`OTHER`），賣家看不到也不能回覆。解除條件：賣家中心的詢問回覆（改成多則回覆時才拆表，觸發是賣家要能補交）與 notification 搬進單體。

- **解除請求不能撤回，也不能由申覆取代**：待處理期間賣家只能等裁定。解除條件：第一個要求撤回的實際案例，或上線後解除請求裁定的中位數超過 7 天（`MEASURE_LIFT_REQUEST` 的期限）。
