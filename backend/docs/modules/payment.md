# payment 模組行為規格

payment 是收款與付款的模組（ADR `docs/adr/2026-09-24-go-modular-monolith.md` 的依賴表葉節點）。擁有收款帳戶（收款開通 ADR D28）與付款（§9）；轉帳與撤回（§10）、結果不明的收斂（§11）；退款 use case 是 3c，撥款對帳與手續費是 B10，進來時擴充這份規格。

## 1. 範圍與公開面

- 資料：schema `payment`，表 `accounts`（收款帳戶）、`payments`、`transfers`、`refunds`（付款，§9；`db/schema.sql`）；`db/objects.sql` 有發布的 `pub_review_item`／`pub_review_items(at)`（後台待辦）。
- 子領域套件：`internal/account`（port、Stripe 與 fake adapter、帳戶快取、建立／同步／輪詢／關閉後刪除的 job、收款事件的 inbox handler）、`internal/charge`（付款，§9）、`internal/model`（對外型別、`PayoutAccountChanged` 與 `PaymentChanged`）、`internal/store`（sqlc）。
- 公開 API（根套件 `payment`）：
  - 擁有者用（seller 呼叫）：`RequestAccount`（擁有者核准的 transaction 內）、`Account`、`CreateOnboardingSession`、`SyncAccountUnlessFresh`（賣家觸發的 transaction 外同步重讀，§2）、`Configured`、`ForgetOwners`（擁有者個資清理的 transaction 內）。呼叫方先確認呼叫者是擁有者（收款開通 ADR D30：賣家端的 `GetMyPaymentAccount`、`CreatePaymentOnboardingSession` 留在 `SellerAppService`）。
  - 後台：`RefreshAccount`（與賣家同一條同步重讀，回傳重讀後的帳戶）、`RetryAccountCreate`（帶 `acknowledgeNoProviderAccount`）、`RetryAccountPurge`、`DeleteAccountMapping`（三個寫入都帶 `AdminActor`，在同一個 transaction 寫 platform 的後台紀錄 `adminaudit`，D62），帳戶訊息帶 `create_unresolved`（建立結果不明且超過冪等鍵保存期：建立失敗的列重試建立要確認；清理終局 `unresolved_creation` 的列不能重試關閉，後台隱藏它，D63）與 `purge_pending_time`（等待清理中，後台顯示「關閉中」並隱藏其他動作，D63），對外是 `hawkr.admin.payment.v1alpha1.PaymentAdminService`（`GetPaymentAccount`、`RefreshPaymentAccount`、`RetryPaymentAccountCreate`、`RetryPaymentAccountPurge`、`DeletePaymentAccountMapping`；權限 `payment.accounts.get`、`.refresh`、`.retry_create`、`.retry_purge`、`.delete_mapping`）。
  - 對外契約的收款帳戶列舉（`PaymentAccountStatus`、`RequirementCollection`）與呼叫端宣告用的內嵌開通執行環境列舉（`EmbeddedOnboardingRuntime`）由 payment 擁有，在 `hawkr.payment.v1alpha1`（`api/hawkr/payment/v1alpha1/payment.proto`）；seller 與 admin payment 的 proto 都 import 它，共用文案目錄的 key 是 `payment.PaymentAccountStatus.*`、`payment.RequirementCollection.*`。
  - webhook：`ReceiveEvent`（HTTP 入口 `POST /webhooks/stripe`，`internal/httpapi/payment`）；付款事件 `ReceivePaymentEvent`（`POST /webhooks/stripe-payments`，獨立的 destination 與簽章密鑰）。
  - 付款：`CreatePayment`、`GetPayment`（買家，§9）、`ChargeConfigured`；job 的內容 `CreatePaymentIntent`、`SyncPayment`、`SweepPayments` 給 worker 與測試。
  - 事件：`PayoutAccountChanged`、`PaymentChanged`（§5）。
- 擁有者鍵是 `store_id`（seller 的店家；不建跨 schema FK）。出現第二種擁有者時再通用化（D28）。payment 是葉節點，不讀 seller：擁有者是否營運中經組裝點注入的 `Owners`（cmd/hawkr 以 `seller.Module.Store` 實作）。
- 不在本模組：開通閘門（seller 的 `store_requirement_flags`，讀 seller 自存的副本）、防詐 hash（seller 的 `account_identity_hashes`）、可曝光公告（seller）、webhook inbox 的表與派送（platform 的 `internal/platform/inbox`，D29）。

## 2. 收款帳戶

- 一個擁有者一列，關店再開沿用（D19）；列只存狀態，不存擁有者的個資：聯絡信箱在建立外部帳戶的當下經 `Owners` 向擁有者讀（D50，修訂 D23 的核准時快照）。外部呼叫（建立帳戶、重讀帳戶、開通 session）不在 transaction 內（單體規則 5）。
- 建立：擁有者核准的 transaction 內 `RequestAccount` 只 INSERT「建立中」的列（`external_account_id` NULL、`NOT_CREATED`；`ON CONFLICT DO NOTHING`）並排入以 `store_id` 為唯一鍵的建立 job（`payment.account_ensure`）；已有列時不改它，還沒完成建立（含半建立）、也沒有進入建立失敗時重新排入建立 job。`RequestAccount` 不收也不檢查聯絡信箱（送審才要求帳號有信箱）。既有列已標記等待清理（`purge_pending_at`）時回 `failed_precondition`（不鎖、不改該列、不排 job），呼叫方的核准 transaction 隨之失敗，等清理完成才能核准。沒有設定 provider 時什麼都不做。
- 建立 job（D55、D59）：讀本地列，`Owners` 回答擁有者不在營運中就略過；在 transaction 外讀擁有者目前的聯絡信箱（`Owners.OwnerContactEmail`：identity 已驗證的信箱優先，其次自填；核准之後信箱改了用新的），沒有信箱時不呼叫 provider、視為永久失敗（重試不會生出信箱）。分兩步建立，收件方式取列上的 `requirement_collection`：**第 0 步**呼叫 provider 之前先在 transaction 內寫「已呼叫」的時刻（`create_called_at`，已寫過的保留最早的；列上因此分得出「從沒呼叫」與「結果不明」）。**第 1 步**經 port 的 `AcquireAccount` 以列上保存的 UUID（`create_idempotency_key`，寫列時產生的 v4）為冪等鍵取得外部 ID（Stripe：`POST /v2/core/accounts` 只帶 `metadata.store_id` 與 `metadata.hawkr_namespace`（設定 `STRIPE_ACCOUNT_NAMESPACE`，每個環境不同，D61），本文固定，同一把鍵在保存期（30 天，`IdempotencyRetention`）內永遠得到同一個帳戶），拿到 ID **立刻**在 transaction 內寫進列（`external_account_id`，不等第二步）；列已「呼叫過、沒有外部 ID」超過 7 天（`UnresolvedDeadline`，D63）時不再重送：記建立失敗（見下，不換新鍵、不列出帳戶）。**第 2 步**經 `ConfigureAccount` 完成設定（寫入這次讀到的聯絡信箱、recipient 設定、責任歸屬、identity 與 dashboard，可重複送出），成功才在 transaction 內記 `create_completed_at`、狀態進 `ACTION_REQUIRED` 並排入同步 job：**「已建立」看 `create_completed_at`，不看有沒有外部 ID**。第 2 步失敗時外部 ID 與已呼叫時刻留在列上（半建立的列：`status` 仍是 `NOT_CREATED`，不可開通、不輪詢、不同步、不重新整理，收款事件也不排同步），重試從第 2 步接續、不再取得 ID。暫時性失敗由 River 退避重試（最多 8 次）；最後一次嘗試或永久失敗記 `create_failed_at`，進後台待辦 `PAYMENT_ACCOUNT_CREATE_FAILED`（§6），管理員「重試建立」清空並重排。約束見 `db/schema.sql` 的 `accounts_created_check`、`accounts_snapshot_check`、`accounts_create_failed_check`、`accounts_completed_check`、`accounts_called_check`；守門：`TestTheFirstStepIDIsKeptWhenTheSecondStepFailsAndAHalfCreatedRowIsNotOnboardable`、`TestSweepResolvesACalledRowWithoutAnIDForANonOperatingOwnerWithTheSameKey`、`TestSweepResolvesAFailedCreateRowWithinTheWindowAndATransientFailureLeavesItForTheNextSweep`。
- 了結結果不明的建立（D63，取代 D59 的列出對帳）：週期掃描（`Sweep`）為每一筆「呼叫過、沒有外部 ID、沒有等待清理、已呼叫超過 10 分鐘」的列排 `payment.account_resolve`（唯一鍵 `store_id`；不論擁有者是否營運中、是否已記建立失敗；金流商明確拒絕〔永久失敗〕的列（含已建立失敗的列，保留原失敗時刻）記 `create_refused_at`，掃描不再選它，等管理員重試建立清除，partial index `accounts_unresolved` 支撐這個查詢），job 以列上同一把冪等鍵重送 `AcquireAccount` 取回 ID 寫進列（`storeResolved`：呼叫期間列被標成等待清理就走 `replayIntoPurge`，ID 不丟；否則 `SetPaymentAccountExternal`，列成為半建立：擁有者營運中時由閒置建立的補排接續第 2 步，建立失敗的列等管理員重試）；暫時性失敗由 River 重試，最後一次嘗試仍失敗只記警示 log、留給下一次掃描。「已呼叫」起 7 天仍了結不了：記 `create_failed_at`（待辦 `PAYMENT_ACCOUNT_CREATE_FAILED`），之後掃描與建立 job 都不再選它、不再送任何呼叫；任何重送都在 7 天內，小於保存期（`const _ = uint64(IdempotencyRetention - UnresolvedDeadline - 1)` 編譯期守住）。等待清理的列由清理 job 做同樣的事（下一條）。管理員「重試建立」看冪等鍵保存期（`IdempotencyRetention`，30 天；Stripe：保存期內重送同一把鍵回同一個結果，過期後沒有自動重試，要人工對帳）：保存期內（含已超過自動重送的 7 天）重試以同一把鍵重送，不需要確認、不換鍵、`create_called_at` 不變；列保持建立失敗（掃描因此不會再把它標成終局），同一個 transaction 排入 `payment.account_resolve`（`replay` 旗標，不屬於唯一鍵），job 取回 ID 後在同一個 transaction 寫進列、清空建立失敗並排建立接續第 2 步，永遠只有一個外部帳戶；重送失敗（永久或最後一次嘗試）只記警示 log，列留在建立失敗，管理員可再重試。超過保存期：帳戶的 `create_unresolved`（建立失敗、呼叫過、沒有外部 ID、超過 30 天）為真，重試等於聲明金流商那邊沒有這家店的帳戶，請求要 `acknowledge_no_provider_account = true`，沒有就回 `failed_precondition`；確認後在同一個 transaction 換新冪等鍵、`create_called_at` 重設成現在、清空建立失敗並排建立。兩種都寫後台紀錄（`adminaudit`，D62；內容有 `key_rotated` 與 `replayed_same_key`，`acknowledged_no_provider_account` 只在確認有必要而且照做〔換了新鍵〕時為真）。建立 job 與並行的了結取回同一個 ID 時（同一把鍵同一個帳戶），先寫入的贏，建立 job 的寫入被擋下但列上已是同一個 ID，繼續第 2 步（`holdsExternal`）。其他建立失敗的列（同一把鍵仍在 7 天內）不需要確認也不換鍵。守門：`TestAnUnresolvedCreatePast7DaysReachesTheTerminalStateAndNothingIsEverReplayedPastTheRetention`、`TestRetryCreateWithinTheKeyRetentionReplaysTheSameKeyWithoutAcknowledgement`、`TestRetryCreateOfAnUnresolvedTerminalRowNeedsAcknowledgementAndRotatesTheKey`。
- 同步 job（`payment.account_sync`，唯一鍵 `store_id`）：在 transaction 外重讀外部帳戶，在 transaction 內鎖帳戶列、整列覆寫快照（沒有觀測歷史，重讀即最新）、發布 `PayoutAccountChanged`（§5），並經 platform inbox 把這個外部帳戶在讀取開始前收到的事件整批標記已處理（`MarkRouteProcessed`，處理者 `payment.account_sync`）；之後仍有未處理事件（讀取期間到的）時回 `again`，worker 以 snooze 再跑一輪。外部帳戶不存在是永久失敗（job 取消）。外部帳戶已在 provider 關閉時（adapter 讀到 `closed`，`Snapshot.Closed`）列變成 `DISABLED`、原因碼 `closed`（終局：能力關閉、照常發布 `PayoutAccountChanged`、輪詢不再排它，D61）；守門：`TestSyncOfAnAccountClosedAtTheProviderIsDisabledWithTheClosedReasonAndNeverPolledAgain`。
- 同步與同步並行（D32）：`SyncAccountUnlessFresh` 給 seller 的 `RefreshMyPaymentAccount` 在 job 之外同步呼叫，所以「一個帳戶同一時間一個同步」只剩 River 唯一鍵保證。寫快照時只有這次讀取的開始時間不早於已存的 `fetched_at`（NULL 一律寫）才寫；被擋下的同步（較晚開始的讀取已經先寫入）不寫快取、不標記 inbox 事件、不發布 `PayoutAccountChanged`，`again` 由唯讀的 `RoutePending` 回答（較晚開始的那一次標記了在它開始之前收到的事件，之後收到的仍未處理，所以要回報）。必要條件是存在 job 以外的同步呼叫，那個呼叫拿掉時條件一起拿掉。賣家的同步呼叫遇到 `again` 自己排同步 job。守門：`TestAnOlderReadNeverOverwritesANewerCommittedRead`、`TestARejectedSyncDoesNotMarkEventsOrPublish`。
- 賣家與管理員觸發的重讀間隔（D33、D49-3；後台的 `RefreshAccount` 檢查帳戶狀態後呼叫同一個 `SyncUnlessFresh`，名額與賣家共用）：`SyncAccountUnlessFresh` 在讀 provider 之前以單一條件式 UPDATE 搶名額（`payment.accounts.seller_read_claimed_at` 與 `fetched_at` 都早於 `now - ReadDebounce`，10 秒，具名常數，時鐘由組裝點注入）；搶不到（間隔內已有讀取，含失敗的與並行的）不呼叫 provider，依列上的時間回答（`busyRetryAfter`）：`fetched_at` 不早於 `seller_read_claimed_at`（快取已涵蓋占名額的讀取）才成功，否則（那次讀取失敗或還在進行中）回 `ResourceExhausted` 並帶窗的剩餘時間（傳輸層放進 `google.rpc.RetryInfo`，至少 1 秒；client 對可重試的 `resource_exhausted` 照它等待後重試），失敗不會被舊快取蓋成成功；搶到才走同步，用搶到的那一列（不重讀），讀完仍有未處理事件就在自己的 transaction 排同步 job。同步 job 不受間隔限制、不寫這一欄。必要條件：外部讀取由賣家觸發，頻率不受 job 唯一鍵約束；那個呼叫拿掉時間隔與該欄一起拿掉。沒有 provider 回 `FailedPrecondition`；帳戶列的 provider 與目前的不同也回 `FailedPrecondition`；沒有帳戶列或還沒完成建立時什麼都不做；排同步 job 的寫入不隨呼叫者取消；重讀失敗是明確動作的失敗：暫時性回 `Unavailable`，外部帳戶不存在（`ErrPermanent`）回 `FailedPrecondition`。守門：`TestStaleBeforeIsOneDebounceWindowBack`、`TestBusyRetryAfterDecidesBetweenSuccessAndRetry`、`TestBusyOutcomeCarriesTheRetryDelay`、`TestSyncUnlessFreshWithoutProviderIsFailedPrecondition`、`TestSellerTriggeredRereadIsDebouncedAndFailsLoudly`、`TestConcurrentSellerRefreshesReadTheProviderOnce`、`TestASellerRefreshRejectedByTheGuardQueuesASyncForLaterEvents`。
- 狀態推導（`account.StatusOf`，D13）：還沒完成建立（`create_completed_at` 是 NULL，含半建立的列）＝`NOT_CREATED`；`active`＝`ENABLED`；`rejected`、`unsupported`＝`DISABLED`；任何一筆細節的行動方是賣家（含 `pending`）＝`ACTION_REQUIRED`；`pending`＝`UNDER_REVIEW`；`restricted` 加平台處理或無解法的細節＝`DISABLED`；不認得的狀態或行動方、`restricted` 但沒有細節＝`UNDER_REVIEW` 並記警示。細節多筆時賣家能行動的優先，其次 `DISABLED`。`status_reason` 是導出狀態的那一筆細節的 provider 原因碼（只給後台）。`transfers_active` 等於 `ENABLED`；`payouts_active` 只顯示。守門：`TestStatusOfFollowsTheDecisionTable`。
- 開通 session：外部帳戶還沒完成建立（含半建立的列）、被停用（`DISABLED`）時回 `FAILED_PRECONDITION`。session 只有兩種互斥的形狀（`model.OnboardingSession` 是封閉的 interface：`HostedSession` 託管連結、`StripeEmbeddedSession` 內嵌的 client secret 加公開金鑰，每種只帶自己的欄位，沒有型態欄位）。形狀由 `account.ChooseSession` 唯一決定：列保存的收款方式是平台收件（`CollectionPlatform`）、而且 provider 經 port 的 `Capabilities.EmbeddedRuntimes` 宣告支援的內嵌執行環境（Stripe 是 `STRIPE_CONNECT_JS`，fake 沒有）與呼叫端宣告的清單（`CreatePaymentOnboardingSessionRequest.embedded_runtimes`）有交集才回內嵌（Account Session），其餘一律回託管連結（Account Link；平台收件的帳戶走託管連結可行，sandbox 實測）。只看帳戶列，不看行程設定的收件方式；fake provider 不支援內嵌，一律回託管連結。provider 回傳的形狀與要求的不一致是內部錯誤，不把內容交給呼叫端。列的 provider 與目前設定不符時，`sessionTarget` 已在前置條件回 `FAILED_PRECONDITION`，決定表不需要比 provider 名稱。賣家 App 送空清單，一律拿託管連結，沒有「到網站完成」的路徑。守門：`TestChooseSessionIsEmbeddedOnlyForStripePlatformRowsWhenTheCallerCanEmbed`、`TestOpenSessionNeverCreatesAnAccountSessionForACallerThatDoesNotDeclareEmbedding`、`TestOnboardingSessionShapeComesFromTheAccountRowNotTheCurrentConfiguration`。
- 開通 session 的回跳網址不由 client 傳：請求帶回跳目的地（`OnboardingReturnDestination`），網站語系取自請求 ctx 的語系（`uitext.LocaleFrom(ctx)`，由 rpc interceptor 協商 `Accept-Language`，請求沒有 `locale` 欄位），`internal/httpapi/rpc/web_origin.go` 以 `PUBLIC_WEB_ORIGIN` 組成絕對網址（完成與連結過期各一個），再交給 port 的 `SessionInput.ReturnURL`／`RefreshURL`；未指定的目的地回 `INVALID_ARGUMENT`。目的地的路徑只在那個檔案，`web_origin_test.go` 守門它們在 `website/app/[locale]` 都有 `page.tsx`，語系前綴與 website 的路由設定一致。
- 內嵌開通的 session 帶初始化元件用的公開金鑰（`publishable_key`，設定 `STRIPE_PUBLISHABLE_KEY`，不是 secret）與 client secret；金流商由回應 `embedded` 的 `oneof provider` 分支表示（目前只有 `stripe`），client 不認得的分支視為不能開通。啟動規則比照 `STRIPE_WEBHOOK_SECRET`：設了 `STRIPE_SECRET_KEY` 卻沒有 `STRIPE_PUBLISHABLE_KEY` 就啟動失敗；`STRIPE_ACCOUNT_NAMESPACE`（這個環境的帳戶命名空間：小寫英數、連字號、底線，1 到 40 個字元，開頭是英數；每個環境不同）同樣必填、格式不合也啟動失敗；publishable key 的失敗與收件方式無關：行程設定改成金流商收件後，既有的平台收件帳戶仍會開內嵌 session。守門：`TestStripePaymentConfig`。
- 關閉後刪除（D52、D55、D59、D60）：擁有者個資清理的 transaction 內 `ForgetOwners` 為每個擁有者排入 `payment.account_purge`（唯一鍵 `store_id`，只排 job、不碰列、不呼叫 provider）。job 第一步：每一列先在自己的 transaction 標 `purge_pending_at`（呼叫 provider 之前，意義是「擁有者要求清理、還沒完成」，之後任何錯誤、逾時或程序被殺都由週期掃描接手；ForgetOwners 的 transaction 不鎖也不改既有的列），標好後重讀列，再依 `planPurge` 分流：(1) 從沒呼叫過（沒有 `create_called_at`，必然沒有外部帳戶）：直接刪，**不需要 provider**；(2) 呼叫過但問不到 provider（沒有設定或列的 provider 不同）：列留著，記警示 log，超過期限進終局；(3) 有外部 ID 且 provider 相同：在 transaction 外經 `CloseAccount` 先讀帳戶、照它實際的設定關閉（冪等：已關閉視為成功；空帳戶 `applied_configurations` 是 `[]`，已完成設定的是 `["recipient"]`，關閉要求傳實際的全部設定，否則 400 ## 3. 收款事件與 inbox（D29）

- 入口驗簽（`Provider.ParseEvent`）後在一個 transaction 內以 `inbox.Record` 寫進 platform 的 `inbox.events`（`(provider, event_id)` 唯一；路由鍵是外部帳戶 ID；原始 payload 原樣保存，保存期 `EventRetention` 30 天）並排入派送 job，commit 之後才回 2xx。重送的事件不寫入、不派送；驗過簽章但不處理的事件回 2xx、不寫 inbox；簽章或格式不合回 400；沒有設定 provider 回 503。
- 派送（platform 的 `inbox.dispatch` job）呼叫收款的 handler：外部帳戶對得到本地帳戶時只排入同步 job，**不標記已處理**——事件只是「重讀帳戶」的訊號，由涵蓋它的同步標記；同步被執行中的 job 合併掉時，事件留在 inbox 讓那一輪回 `again`。對不到本地帳戶、或對到但還沒完成建立（半建立，`create_completed_at` 為 NULL）的事件只留紀錄、不排同步、直接標記已處理（處理者 `payment.account_event`；建立完成時 job 排入的同步讀到的就是最新狀態）。守門：`TestAnEventForAHalfCreatedRowEnqueuesNoSyncAndIsMarkedProcessed`。
- 補掃分工：platform 的補掃只重派派送 job 被丟棄或用完重試、仍未派送成功也未處理的列；payment 的 15 分鐘輪詢（`payment.account_sweep`）排 UNDER_REVIEW、ACTION_REQUIRED、原因碼不是 `rejected*`／`unsupported*`／`closed` 的 DISABLED 帳戶的同步（Stripe 可以解除 restricted，掉了 webhook 時只有輪詢補得到）、inbox 有超過 1 分鐘未處理事件的帳戶的同步（`inbox.StaleRoutes`），以及閒置 10 分鐘的建立列（擁有者營運中才排）；沒有設定 provider 時只重排等待清理的列的清理 job（同步與建立都要 provider），呼叫過 provider 的列才能在期限後進終局。
- payload 與 `PayoutAccountChanged` 的明文 fingerprint 不寫 log。

## 4. 後台

- `GetPaymentAccount` 讀擁有者的帳戶（沒有回 `NOT_FOUND`）；`RefreshPaymentAccount` 同步重讀並回最新帳戶，走賣家同一條路徑（沒有 provider、還沒完成建立或帳戶在等待關閉回 `FAILED_PRECONDITION`，窗內與失敗的結果同賣家：`RESOURCE_EXHAUSTED`、`UNAVAILABLE`）；`RetryPaymentAccountCreate` 只有建立失敗的列可以重試（其他狀態 `FAILED_PRECONDITION`）；`RetryPaymentAccountPurge` 只有清理進終局的列可以（其他狀態 `FAILED_PRECONDITION`）：清除終局、等待清理的時刻重設成現在並重排清理；`DeletePaymentAccountMapping` 只有清理進終局的列可以（其他狀態 `FAILED_PRECONDITION`，沒有列 `NOT_FOUND`）：在同一個 transaction 寫紀錄並刪列，操作的管理員取自呼叫者，不呼叫 provider，需要 `payment.accounts.delete_mapping`（與 `.retry_purge` 分開）。後台卡片 `PaymentAccountCard` 在終局時於「重試建立」的位置顯示被擋下的原因與時間（`purge_blocked_reason`、`purge_blocked_time`）與兩個按鈕「重試關閉」「已在金流商處理，刪除對應」（後者先確認，`PaymentMappingDeleteDialog`）；待辦 `PAYMENT_ACCOUNT_PURGE_STUCK` 的標題是「處理無法關閉的收款帳戶」，連到同一個卡片錨點。

## 5. 事件

- `PayoutAccountChanged{OccurredAt, StoreID, Provider, TransfersActive, BankFingerprints}`：同步 job 寫快照的 transaction 內每次都發布（fingerprint 可能在轉帳能力不變時改變）。seller 的同 transaction 訂閱者把 `TransfersActive` 複製到開通閘門的副本、把 fingerprint 寫成防詐 hash（D12），轉帳能力有變時重新公告。訂閱者失敗時整筆同步 rollback，River 重試。
- `PaymentChanged{OccurredAt, PaymentID, OrderNo, StoreID, BuyerID, Amount, Provider, Status, Previous, PaidAt, LastError}`：付款的快照寫入、狀態與寫入前不同的 transaction 內發布（重複讀取與重複事件不重發）。訂單一方據此得知付款成功或取消，並在訂單已不可付時發起自動退款（D5 修訂）；payment 不讀訂單狀態。訂閱者同 transaction，只做原子的狀態變更或排 job。

## 6. 發布的讀取介面

- `payment.pub_review_items(at)`：後台待辦的 payment 部分（reviewqueue 讀，形狀在 `db/pub.sql`），兩種：`PAYMENT_ACCOUNT_CREATE_FAILED`（`create_failed_at` 有值的帳戶，開始是失敗的時刻）與 `PAYMENT_ACCOUNT_PURGE_STUCK`（`purge_blocked_at` 有值的帳戶，開始是進終局的時刻）。兩種的 item_id 都是店家 ID 的文字，期限 24 小時。只有店家 ID，店名由後台入口（`internal/httpapi/reviewqueue`）經 seller 的店家卡片補上。

## 7. 鎖順序

- 全域順序見單體規則 4 與 `platform/lockorder` 的 `Modules`（payment 在 seller 之前）。payment 自己的寫入只鎖帳戶列（`LockPaymentAccount`）；同步在帳戶列之後發事件，seller 的訂閱者再鎖 seller 的列。擁有者（seller）的 transaction 只對 payment 做 INSERT ON CONFLICT DO NOTHING 與排 job，不等 payment 的既有列；`inbox` schema 是 platform 的，不在模組順序內。
- 付款：鎖付款列（`LockPayment`）只在寫入快照時，寫完同 transaction 發 `PaymentChanged`。轉帳（3b）：`RequestTransfer` 只鎖付款列；撤回與轉帳成功的寫結果依序鎖付款列、轉帳列、退款列（`LockPayment` → `LockTransfer` → `LockRefund`）。3c 補退款的鎖順序（同一筆付款的多筆退款依 ID 升序），不得違反「付款列先於轉帳列先於退款列」。

## 8. 已知限制

- `PAYMENT_ACCOUNT_CREATE_FAILED` 不再排除已關閉的店家（payment 不讀 seller 的店家狀態）：關閉店家的待辦由管理員「重試建立」清掉，建立 job 會因擁有者不在營運中而略過。觸發：上線前，或後台待辦出現已關閉店家時。
- 本機種子（`dev-seed`）以 fake provider 走正式的建立與同步；店家已有別的 provider 的帳戶時種子不改它，只印出提醒。
- 付款的冪等鍵保存期取 24 小時（`PaymentIdempotencyRetention`，Stripe 的下限，3d 以文件核對）：結果不明的呼叫 23 小時內同鍵重送、之後只查回，見 §11。觸發：3d 核對文件後調整。
- 零元訂單不經 provider（`CreatePayment` 回 FailedPrecondition），怎麼完成由訂單一方決定。觸發：步驟 4。
- 付款事件的 handler 只涵蓋付款（PaymentIntent）；退款與轉帳的事件在 3b、3c 加入前，`ParseEvent` 回 ErrIgnoredEvent。

## 9. 付款

計畫：`backend/docs/plans/2026-11-23-b2-payment.md`；D7（修訂）、D8、D9。

- **表**：`payments`（一張訂單一列、同時只有一個有效的 PaymentIntent：`order_no` 唯一；金額整數、不帶幣別；`store_id`、`buyer_id`、`amount` 是建立當下訂單 port 回的快照）、`payment_attempts`（付款嘗試歷程，付款列一對多：每次嘗試的 provider、外部 ID、冪等鍵、呼叫時刻、最近讀到的狀態；`superseded_at` 為空的是有效嘗試，唯一索引守一個；付款列的外部 ID、冪等鍵、呼叫時刻是它的鏡像；`excess_paid_at` 標記重複入帳，索引給後台查）、`transfers`、`refunds`（3b、3c 的 use case 使用，schema 與狀態機一次設計）。主鍵 UUIDv7、不設 DEFAULT。
- **付款狀態**（`payments_status_check`，只由 provider 快照推導）：`CREATING`、`AWAITING_PAYMENT`、`PROCESSING`、`SUCCEEDED`（終局，記 `external_charge_id` 與 `paid_at`）、`CANCELED`（之後的入帳仍勝出）、`CREATE_FAILED`（建立的終局）、`ANOMALY`（待人工結案，§11）。失敗的付款嘗試不是狀態：PaymentIntent 回到等待付款，`last_error` 記原因碼。
- **建立**（`CreatePayment`）：transaction 外讀訂單 port（歸屬、可付、金額）→ 一個 transaction 寫「建立中」的列、第一個有效嘗試並排補做 job（`payment.charge_create`，付款 ID 唯一鍵）→ 提交後在請求內帶列上的冪等鍵建立 PaymentIntent，成功回 `client_secret`（不存）；失敗或逾時回狀態 `CREATING` 的付款（pending），補做 job 與週期掃描以同一把鍵重送，client 以 `GetPayment` 重讀。呼叫 provider 之前先記 `create_called_at`（付款列與有效嘗試各一份，獨立提交）；結果不明的收斂見 §11；provider 永久拒絕進 `CREATE_FAILED`（`CreatePayment` 回這個狀態，不是錯誤）。補做 job 排在請求內全部上限之後（`createJobDelay` = 記呼叫時刻與寫結果各 15 秒的寫入上限 + 呼叫 provider 的 10 秒上限 + 5 秒餘裕；掃描排的立刻執行），不與請求內的建立搶同一把冪等鍵；請求結束時列已是 `AWAITING_PAYMENT` 卻沒有 secret（補做先寫入、請求的快照被較新的讀取擋下）時，回應改以讀取路徑向 provider 取 secret。付款說明（`description`，訂單的商品名稱去頭尾空白、至多 200 字，沒有就用訂單編號）存在列上並送 provider，冪等重送時不變。建立中、沒有外部 ID 的列屬於別的 provider（設定換了）時，只在舊 provider 的呼叫從沒送出（`create_called_at` 為空）或查無已算數（超過 `PaymentNotFoundAfter`）時，補做才改成目前的 provider（舊嘗試記被取代、新嘗試用新鍵並重新起算呼叫時刻）；呼叫過又還沒到那個時刻的列不動，因為舊 provider 可能已經建出 PaymentIntent。回快照的 provider 與嘗試登記的不同時快照丟棄。買家再次建立同一張訂單：既有列沿用（金額或店家變動回 FailedPrecondition）；`CREATE_FAILED` 與 `CANCELED`（訂單仍可付）的列換新鍵重設回 `CREATING`（Stripe 取消後的 PaymentIntent 是終局：舊嘗試記被取代、留在歷程表，新嘗試另寫一列；一張訂單一列、同時只有一個有效的 PaymentIntent）；已成功的回目前狀態。零元與不可付的訂單回 FailedPrecondition。
- **讀取**（`GetPayment`）：只回呼叫者自己的付款（他人回 NotFound）；`AWAITING_PAYMENT` 時向 provider 讀 `client_secret`，provider 那邊已往前（買家剛付款）時不回 secret 並排同步 job。
- **付款事件**：`POST /webhooks/stripe-payments` → 驗簽 → 寫 inbox（provider 名稱 `stripe_payments` 這類獨立名稱，與收款帳戶不同）→ handler 排 `payment.charge_sync`（付款 ID 唯一鍵）→ handler 依外部 ID 經 `payment_attempts` 對回付款列（舊嘗試的 ID 也對得到）→ job 在 transaction 外重讀 PaymentIntent（有效嘗試一定讀；被取代的舊嘗試在未結案或有未處理事件時也讀）、同 transaction 推導狀態寫入、狀態改變時發 `PaymentChanged`，並標記讀取開始前收到的事件（判斷過的快照一律標記，包括與入帳終局衝突而保留列的；只有讀取過期、較新的讀取已標記的不標）。事件內容不被信任。入帳是終局；金額不符、外部 ID 不同的快照不寫入、記 error log，並把讀取開始前的事件標為已處理（已告警，列不動，掃描不再為它們重排）；入帳卻還沒有 charge 或入帳時間是暫時性的不一致：不寫入、事件保持未處理、由 job 重試與掃描重排；不認得的狀態不寫入、由 job 重試。快照寫進它所屬的嘗試列；只有有效嘗試的快照寫付款列，被取代的舊嘗試只更新嘗試列（舊 ID 不會寫回剛重設的列）。付款 webhook 的簽章密鑰是自己的設定 `STRIPE_PAYMENT_WEBHOOK_SECRET`（與收款帳戶的 `STRIPE_WEBHOOK_SECRET` 分開，相同啟動失敗；付款 provider 由 `PAYMENT_CHARGE_PROVIDER` 選，沒有設定時付款呼叫回 FailedPrecondition、webhook 回 503，與收款開通一致；Stripe adapter 在 3d 接上前設 stripe 啟動失敗）；本文上限 256 KiB（snapshot event 含完整物件），收款帳戶的 thin event 是 64 KiB。
- **舊 PaymentIntent 晚到成功**（D8 補充）：付款列還沒入帳 → 付款列記成功（成功優先於取消）並發 `PaymentChanged`，這個舊嘗試成為有效的、原有效的嘗試若還沒結案就排 `payment.charge_cancel`（嘗試 ID 唯一鍵，transaction 外呼叫 provider 取消）；付款列已經以另一個 PaymentIntent 入帳而這個也入帳 → 記 `excess_paid_at`（重複入帳，error log，後台以 `ExcessPaidPayments` 查），不自動退款（D5 修訂：退款由訂單一方發起）；付款列已入帳而這個舊 PaymentIntent 還沒結案 → 排取消。取消與入帳競態時取消的結果是 provider 的入帳快照，同樣記成重複入帳。
- **補掃**（`payment.charge_sweep`，15 分鐘）：閒置超過 10 分鐘的 `CREATING` 補排補做；超過 30 分鐘沒讀過的 `AWAITING_PAYMENT`／`PROCESSING` 補排同步；被取代、未結案又超過 30 分鐘沒讀過的舊嘗試所屬的付款補排同步；inbox 有超過 1 分鐘未處理事件的付款（含舊 PaymentIntent 的事件）補排同步。
- **外部 ID 的 schema**：退款與轉帳的外部 ID 在 provider 已回應的狀態都存得下來（退款 `REFUNDING`、`SUCCEEDED`、`FAILED`；轉帳 `SUCCEEDED`、`FAILED`），入帳一定要有 ID，還沒呼叫 provider 的狀態不能有，有 ID 一定要有呼叫時刻（`refunds_external_state_check`、`refunds_external_called_check`、`transfers_external_state_check`）。撤回的外部 ID 不綁狀態。
- **port**（`internal/charge.Provider`）：建立與讀取 PaymentIntent、取消 PaymentIntent、建立與讀取退款、建立轉帳、撤回轉帳（可部分）、`ParseEvent`；fake 全部實作並記 `Violations`（transaction 內或沒有 deadline 的呼叫）。Stripe adapter 是 3d。

## 10. 轉帳與撤回

計畫：`backend/docs/plans/2026-11-23-b2-payment.md` 步驟 3；D1、D6。

- **請求**（`RequestTransfer(orderNo)`，步驟 4 的 `GrantPayment` 呼叫）：一個 transaction 內鎖付款列、確認 `SUCCEEDED`、讀賣家的收款帳戶（`transfers_active` 且有外部 ID，外部 ID 寫成 `destination_account_id` 快照）、轉帳金額 = 付款金額 − 非失敗退款（進行中的也算），寫 `PENDING` 轉帳並排 `payment.transfer_create`（轉帳 ID 唯一鍵）。不呼叫 provider。已有有效（`PENDING`、`SUCCEEDED`、`ANOMALY`）轉帳時回傳它、不再排 job（唯一索引 `transfers_active_payment`）；付款不存在回 NotFound，未入帳、帳戶未開通、沒有可轉金額且沒有有效轉帳時回 FailedPrecondition。
- **轉帳狀態**：`PENDING`（已寫列、尚未呼叫或結果不明）→ `SUCCEEDED`（`external_transfer_id`）或 `FAILED`（終局，`provider_refused` 或 `provider_not_found`；不佔有效名額）、`ANOMALY`（待人工結案；佔有效名額）。
- **轉帳 job**：呼叫前在獨立 transaction 記 `called_at`（保留最早的）→ transaction 外帶列上的冪等鍵與付款的 `external_charge_id`（`source_transaction`）呼叫 `CreateTransfer` → 成功在新的 transaction 寫外部 ID 與 `SUCCEEDED`。`ErrPermanent` → `FAILED`（job 完成）；`ErrRetryableRefusal`（平台餘額不足）→ 換新冪等鍵、清 `called_at`、回錯誤由 River 重試、列保持 `PENDING`，不計任何期限；其他錯誤是結果不明，同鍵重送到 23 小時、之後只查回（§11）；最後一次嘗試只記警示、留給掃描。付款沒有 charge、provider 回的金額或外部 ID 與列不符 → `ANOMALY`（不寫成功、job 完成）。
- **撤回 job**（`payment.transfer_reversal`，退款 ID 唯一鍵；`EnqueueReversal` 由 3c 在寫 `REVERSING` 退款列的同一個 transaction 呼叫）：退款是 `REVERSING` 時，找付款的 `SUCCEEDED` 轉帳（沒有、或 `reversal_amount` 超過 `amount − reversed_amount` 是 `ANOMALY`，不呼叫 provider）→ 呼叫前記 `reversal_called_at` → transaction 外帶 `reversal_idempotency_key` 呼叫 `ReverseTransfer` → 一個 transaction 內依序鎖付款列、轉帳列、退款列，退款 `REVERSING` → `REVERSED`（記 `reversal_external_id`）並把 `reversal_amount` 累加到轉帳的 `reversed_amount`。provider 已撤回、退款卻已不在 `REVERSING`（同一個撤回 ID 的重複寫入除外）：記 error log（退款、付款、轉帳與撤回 ID）並發 `MoneyAnomaly`，不累加。已不是 `REVERSING` 的退款什麼都不做，所以同一把鍵重送不會重複累加。賣家餘額不足不是錯誤（#9），沒有對應分支。
- **撤回的終局**：`ErrPermanent` → 退款 `FAILED`（`provider_refused`）；`ErrRetryableRefusal` 換新的撤回鍵；結果不明與異常見 §11（查無滿等待 → `FAILED`，`provider_not_found`）。`FAILED` 的退款不佔累計額度，`ANOMALY` 佔。
- **補掃**：`payment.charge_sweep` 另外補排閒置超過 10 分鐘（`updated_at`，每次呼叫都更新）的 `PENDING` 轉帳與 `REVERSING` 退款（算在回傳的 created）；查詢走 partial index（`transfers_pending`、`refunds_reversing`），`ANOMALY` 一律不補排。

## 11. 結果不明的收斂（ADR D68、計畫 D10）

付款、轉帳、撤回（退款的 port 方法與查回已備，use case 在 3c）的 provider 呼叫結果只分三種：成功；確定失敗，再分終局（`ErrPermanent`）與可重試拒絕（`ErrRetryableRefusal`，例如平台餘額不足、429）；不明（其餘錯誤）。不變量：**換新冪等鍵之前，必須以強一致的查回證明上一次嘗試在 provider 不存在**，時間不能把「不明」推斷成「失敗」。

- **可重試拒絕**：換新冪等鍵（付款：付款列換鍵、有效嘗試記被取代、新嘗試另寫一列；轉帳與撤回：列上的鍵換掉、`called_at` 清空、查回失敗次數歸零）、回錯誤由 River 重試，不計任何期限。
- **不明**：這把鍵的第一次呼叫（`called_at`）起 `ResendWindow`（23 小時，小於保存期 `IdempotencyRetention`）內以同一把鍵重送（River 重試與週期掃描）；之後不再呼叫 provider，只以 `Find*`（`FindPayment`、`FindTransfer`、`FindReversal`、`FindRefund`）依嘗試 ID 查回。嘗試 ID 就是這把冪等鍵，adapter 在建立時寫進 provider 物件的 metadata。
- **查回的結果**：找到 → 與列核對後收下（等同呼叫成功）；查無 → 從第一次呼叫起滿 `NotFoundAfter`（`ResendWindow` + `NotFoundWait` 1 小時，等於 24 小時；最後一次重送在視窗內，列表可能晚一點才看得到）才算確定不存在，進終局 `FAILED`（付款是 `CREATE_FAILED`，原因 `provider_not_found`），之後才可以換新鍵建新的（轉帳靠 `RequestTransfer`、付款靠買家再次建立）；未滿就回錯誤稍後再查，列不動。查回本身失敗累計連續次數（`create_lookup_failures`、`lookup_failures`、`reversal_lookup_failures`），成功的查回歸零，連續 `LookupFailureLimit`（5）次進 `ANOMALY`。
- **ANOMALY**：provider 與本地紀錄不符（金額或外部 ID）、前置條件不成立（轉帳的付款沒有 charge、撤回對不到已成立的轉帳或額度超過剩餘可撤）、或查回連續失敗。列的 `status` 進 `ANOMALY`、`failure_reason` 記原因碼；它佔住 `transfers_active_payment`（一筆付款最多一筆有效轉帳）與退款額度加總（`NonFailedRefundTotal`），付款列仍佔那張訂單，補掃與 job 不再碰它；進入的同一個 transaction 發 `MoneyAnomaly`（`Kind`、`ObjectID`、`PaymentID`、`Reason`）給告警。付款的 `Next` 對 `ANOMALY` 一律保留，快照不會把它改寫。
- **人工結案**（`ResolveAnomaly(actor, kind, id, outcome, evidence)`，後台 Connect 端點在步驟 5）：管理員核對 provider 後結案成 `SUCCEEDED`（provider 確實執行了，`evidence` 是 provider 物件 ID，必填）或 `FAILED`（確認沒有執行）；領域變更與一筆 `adminaudit`（對象種類 `payment_payment`／`payment_transfer`／`payment_refund`，detail 含結果、原因碼與證據）在同一個 transaction，證據與別的列的外部 ID 衝突回 `ALREADY_EXISTS`，不在 `ANOMALY` 回 `FAILED_PRECONDITION`。付款：成功是把有效嘗試連上證據的 PaymentIntent、暫記 `AWAITING_PAYMENT` 並排同步 job，真正的狀態由重讀推導；失敗進 `CREATE_FAILED`。轉帳：成功記外部轉帳 ID 進 `SUCCEEDED`；失敗進 `FAILED`（讓出名額）。退款（撤回階段的 `ANOMALY`）：成功表示撤回成立，記撤回 ID、累加轉帳的 `reversed_amount`、進 `REVERSED`；失敗進 `FAILED`。鎖順序同 §7（付款列、轉帳列、退款列）。
- **已知限制**：退款階段（`REFUNDING`）的 `ANOMALY` 與它的人工結案、退款的建立與查回由 3c 補；Stripe 的錯誤分類與 `Find*` 的 Stripe 實作在 3d（`transfer_group` 列出轉帳為文件事實、sandbox 未實測）。
