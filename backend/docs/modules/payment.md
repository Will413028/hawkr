# payment 模組行為規格

payment 是收款與付款的模組（ADR `docs/adr/2026-09-24-go-modular-monolith.md` 的依賴表葉節點）。現階段只擁有收款帳戶（Stripe 計畫 D28，步驟 7d′）；付款、退款與撥款是 B2、B3、B8–B10 的範圍，進來時擴充這份規格。

## 1. 範圍與公開面

- 資料：schema `payment`，表 `accounts`（收款帳戶，`db/schema.sql`）；`db/objects.sql` 有發布的 `pub_review_item`／`pub_review_items(at)`（後台待辦）。
- 子領域套件：`internal/account`（port、Stripe 與 fake adapter、帳戶快取、建立／同步／輪詢／關閉後刪除的 job、收款事件的 inbox handler）、`internal/model`（對外型別與 `PayoutAccountChanged`）、`internal/store`（sqlc）。
- 公開 API（根套件 `payment`）：
  - 擁有者用（seller 呼叫）：`RequestAccount`（擁有者核准的 transaction 內）、`Account`、`CreateOnboardingSession`、`SyncAccountUnlessFresh`（賣家觸發的 transaction 外同步重讀，§2）、`Configured`、`ForgetOwners`（擁有者個資清理的 transaction 內）。呼叫方先確認呼叫者是擁有者（Stripe 計畫 D30：賣家端的 `GetMyPaymentAccount`、`CreatePaymentOnboardingSession` 留在 `SellerAppService`）。
  - 後台：`RefreshAccount`（與賣家同一條同步重讀，回傳重讀後的帳戶）、`RetryAccountCreate`、`RetryAccountPurge`、`DeleteAccountMapping`、`AccountMappingDeletions`（讀回「刪除對應」的紀錄），對外是 `hawkr.admin.payment.v1alpha1.PaymentAdminService`（`GetPaymentAccount`、`RefreshPaymentAccount`、`RetryPaymentAccountCreate`、`RetryPaymentAccountPurge`、`DeletePaymentAccountMapping`；權限 `payment.accounts.get`、`.refresh`、`.retry_create`、`.retry_purge`、`.delete_mapping`）。
  - 對外契約的收款帳戶列舉（`PaymentAccountStatus`、`RequirementCollection`）與呼叫端宣告用的內嵌開通執行環境列舉（`EmbeddedOnboardingRuntime`）由 payment 擁有，在 `hawkr.payment.v1alpha1`（`api/hawkr/payment/v1alpha1/payment.proto`）；seller 與 admin payment 的 proto 都 import 它，共用文案目錄的 key 是 `payment.PaymentAccountStatus.*`、`payment.RequirementCollection.*`。
  - webhook：`ReceiveEvent`（HTTP 入口 `POST /webhooks/stripe`，`internal/httpapi/payment`）。
  - 事件：`PayoutAccountChanged`（§5）。
- 擁有者鍵是 `store_id`（seller 的店家；不建跨 schema FK）。出現第二種擁有者時再通用化（D28）。payment 是葉節點，不讀 seller：擁有者是否營運中經組裝點注入的 `Owners`（cmd/hawkr 以 `seller.Module.Store` 實作）。
- 不在本模組：開通閘門（seller 的 `store_requirement_flags`，讀 seller 自存的副本）、防詐 hash（seller 的 `account_identity_hashes`）、可曝光公告（seller）、webhook inbox 的表與派送（platform 的 `internal/platform/inbox`，D29）。

## 2. 收款帳戶

- 一個擁有者一列，關店再開沿用（D19）；列只存狀態，不存擁有者的個資：聯絡信箱在建立外部帳戶的當下經 `Owners` 向擁有者讀（D50，修訂 D23 的核准時快照）。外部呼叫（建立帳戶、重讀帳戶、開通 session）不在 transaction 內（單體規則 5）。
- 建立：擁有者核准的 transaction 內 `RequestAccount` 只 INSERT「建立中」的列（`external_account_id` NULL、`NOT_CREATED`；`ON CONFLICT DO NOTHING`）並排入以 `store_id` 為唯一鍵的建立 job（`payment.account_ensure`）；已有列時不改它，還沒完成建立（含半建立）、也沒有進入建立失敗時重新排入建立 job。`RequestAccount` 不收也不檢查聯絡信箱（送審才要求帳號有信箱）。既有列已標記等待清理（`purge_pending_at`）時回 `failed_precondition`（不鎖、不改該列、不排 job），呼叫方的核准 transaction 隨之失敗，等清理完成才能核准。沒有設定 provider 時什麼都不做。
- 建立 job（D55、D59）：讀本地列，`Owners` 回答擁有者不在營運中就略過；在 transaction 外讀擁有者目前的聯絡信箱（`Owners.OwnerContactEmail`：identity 已驗證的信箱優先，其次自填；核准之後信箱改了用新的），沒有信箱時不呼叫 provider、視為永久失敗（重試不會生出信箱）。分兩步建立，收件方式取列上的 `requirement_collection`：**第 0 步**呼叫 provider 之前先在 transaction 內寫「已呼叫」的時刻（`create_called_at`，已寫過的保留最早的；列上因此分得出「從沒呼叫」與「結果不明」）。**第 1 步**經 port 的 `AcquireAccount` 以列上保存的 UUID（`create_idempotency_key`，寫列時產生的 v4）為冪等鍵取得外部 ID（Stripe：`POST /v2/core/accounts` 只帶 `metadata.store_id`，本文固定，同一把鍵 30 天內永遠得到同一個帳戶），拿到 ID **立刻**在 transaction 內寫進列（`external_account_id`，不等第二步）；冪等鍵從「已呼叫」起超過 30 天（`IdempotencyRetention`）時改走對帳：經 `ResolveAccount`（只找不建）列出 provider 沒有關閉的帳戶、以 `metadata.store_id` 比對，找到就用那一個，整份列完都沒有才換新鍵（`create_idempotency_key` 與 `create_called_at` 改成新鍵第一次呼叫之前的值）再取得。**第 2 步**經 `ConfigureAccount` 完成設定（寫入這次讀到的聯絡信箱、recipient 設定、責任歸屬、identity 與 dashboard，可重複送出），成功才在 transaction 內記 `create_completed_at`、狀態進 `ACTION_REQUIRED` 並排入同步 job：**「已建立」看 `create_completed_at`，不看有沒有外部 ID**。第 2 步失敗時外部 ID 與已呼叫時刻留在列上（半建立的列：`status` 仍是 `NOT_CREATED`，不可開通、不輪詢、不同步、不重新整理，收款事件也不排同步），重試從第 2 步接續、不再取得 ID。暫時性失敗由 River 退避重試（最多 8 次）；最後一次嘗試或永久失敗記 `create_failed_at`，進後台待辦 `PAYMENT_ACCOUNT_CREATE_FAILED`（§6），管理員「重試建立」清空並重排。約束見 `db/schema.sql` 的 `accounts_created_check`、`accounts_snapshot_check`、`accounts_create_failed_check`、`accounts_completed_check`、`accounts_called_check`；守門：`TestTheFirstStepIDIsKeptWhenTheSecondStepFailsAndAHalfCreatedRowIsNotOnboardable`、`TestEnsureAfterTheIdempotencyKeyExpiredReconcilesByListingAndOnlyThenRotatesTheKey`。
- 同步 job（`payment.account_sync`，唯一鍵 `store_id`）：在 transaction 外重讀外部帳戶，在 transaction 內鎖帳戶列、整列覆寫快照（沒有觀測歷史，重讀即最新）、發布 `PayoutAccountChanged`（§5），並經 platform inbox 把這個外部帳戶在讀取開始前收到的事件整批標記已處理（`MarkRouteProcessed`，處理者 `payment.account_sync`）；之後仍有未處理事件（讀取期間到的）時回 `again`，worker 以 snooze 再跑一輪。外部帳戶不存在是永久失敗（job 取消）。
- 同步與同步並行（D32）：`SyncAccountUnlessFresh` 給 seller 的 `RefreshMyPaymentAccount` 在 job 之外同步呼叫，所以「一個帳戶同一時間一個同步」只剩 River 唯一鍵保證。寫快照時只有這次讀取的開始時間不早於已存的 `fetched_at`（NULL 一律寫）才寫；被擋下的同步（較晚開始的讀取已經先寫入）不寫快取、不標記 inbox 事件、不發布 `PayoutAccountChanged`，`again` 由唯讀的 `RoutePending` 回答（較晚開始的那一次標記了在它開始之前收到的事件，之後收到的仍未處理，所以要回報）。必要條件是存在 job 以外的同步呼叫，那個呼叫拿掉時條件一起拿掉。賣家的同步呼叫遇到 `again` 自己排同步 job。守門：`TestAnOlderReadNeverOverwritesANewerCommittedRead`、`TestARejectedSyncDoesNotMarkEventsOrPublish`。
- 賣家與管理員觸發的重讀間隔（D33、D49-3；後台的 `RefreshAccount` 檢查帳戶狀態後呼叫同一個 `SyncUnlessFresh`，名額與賣家共用）：`SyncAccountUnlessFresh` 在讀 provider 之前以單一條件式 UPDATE 搶名額（`payment.accounts.seller_read_claimed_at` 與 `fetched_at` 都早於 `now - ReadDebounce`，10 秒，具名常數，時鐘由組裝點注入）；搶不到（間隔內已有讀取，含失敗的與並行的）不呼叫 provider，依列上的時間回答（`busyRetryAfter`）：`fetched_at` 不早於 `seller_read_claimed_at`（快取已涵蓋占名額的讀取）才成功，否則（那次讀取失敗或還在進行中）回 `ResourceExhausted` 並帶窗的剩餘時間（傳輸層放進 `google.rpc.RetryInfo`，至少 1 秒；client 對可重試的 `resource_exhausted` 照它等待後重試），失敗不會被舊快取蓋成成功；搶到才走同步，用搶到的那一列（不重讀），讀完仍有未處理事件就在自己的 transaction 排同步 job。同步 job 不受間隔限制、不寫這一欄。必要條件：外部讀取由賣家觸發，頻率不受 job 唯一鍵約束；那個呼叫拿掉時間隔與該欄一起拿掉。沒有 provider 回 `FailedPrecondition`；帳戶列的 provider 與目前的不同也回 `FailedPrecondition`；沒有帳戶列或還沒完成建立時什麼都不做；排同步 job 的寫入不隨呼叫者取消；重讀失敗是明確動作的失敗：暫時性回 `Unavailable`，外部帳戶不存在（`ErrPermanent`）回 `FailedPrecondition`。守門：`TestStaleBeforeIsOneDebounceWindowBack`、`TestBusyRetryAfterDecidesBetweenSuccessAndRetry`、`TestBusyOutcomeCarriesTheRetryDelay`、`TestSyncUnlessFreshWithoutProviderIsFailedPrecondition`、`TestSellerTriggeredRereadIsDebouncedAndFailsLoudly`、`TestConcurrentSellerRefreshesReadTheProviderOnce`、`TestASellerRefreshRejectedByTheGuardQueuesASyncForLaterEvents`。
- 狀態推導（`account.StatusOf`，D13）：還沒完成建立（`create_completed_at` 是 NULL，含半建立的列）＝`NOT_CREATED`；`active`＝`ENABLED`；`rejected`、`unsupported`＝`DISABLED`；任何一筆細節的行動方是賣家（含 `pending`）＝`ACTION_REQUIRED`；`pending`＝`UNDER_REVIEW`；`restricted` 加平台處理或無解法的細節＝`DISABLED`；不認得的狀態或行動方、`restricted` 但沒有細節＝`UNDER_REVIEW` 並記警示。細節多筆時賣家能行動的優先，其次 `DISABLED`。`status_reason` 是導出狀態的那一筆細節的 provider 原因碼（只給後台）。`transfers_active` 等於 `ENABLED`；`payouts_active` 只顯示。守門：`TestStatusOfFollowsTheDecisionTable`。
- 開通 session：外部帳戶還沒完成建立（含半建立的列）、被停用（`DISABLED`）時回 `FAILED_PRECONDITION`。session 只有兩種互斥的形狀（`model.OnboardingSession` 是封閉的 interface：`HostedSession` 託管連結、`StripeEmbeddedSession` 內嵌的 client secret 加公開金鑰，每種只帶自己的欄位，沒有型態欄位）。形狀由 `account.ChooseSession` 唯一決定：列保存的收款方式是平台收件（`CollectionPlatform`）、而且 provider 經 port 的 `Capabilities.EmbeddedRuntimes` 宣告支援的內嵌執行環境（Stripe 是 `STRIPE_CONNECT_JS`，fake 沒有）與呼叫端宣告的清單（`CreatePaymentOnboardingSessionRequest.embedded_runtimes`）有交集才回內嵌（Account Session），其餘一律回託管連結（Account Link；平台收件的帳戶走託管連結可行，spike Q23）。只看帳戶列，不看行程設定的收件方式；fake provider 不支援內嵌，一律回託管連結。provider 回傳的形狀與要求的不一致是內部錯誤，不把內容交給呼叫端。列的 provider 與目前設定不符時，`sessionTarget` 已在前置條件回 `FAILED_PRECONDITION`，決定表不需要比 provider 名稱。賣家 App 送空清單，一律拿託管連結，沒有「到網站完成」的路徑。守門：`TestChooseSessionIsEmbeddedOnlyForStripePlatformRowsWhenTheCallerCanEmbed`、`TestOpenSessionNeverCreatesAnAccountSessionForACallerThatDoesNotDeclareEmbedding`、`TestOnboardingSessionShapeComesFromTheAccountRowNotTheCurrentConfiguration`。
- 開通 session 的回跳網址不由 client 傳：請求帶回跳目的地（`OnboardingReturnDestination`），網站語系取自請求 ctx 的語系（`uitext.LocaleFrom(ctx)`，由 rpc interceptor 協商 `Accept-Language`，請求沒有 `locale` 欄位），`internal/httpapi/rpc/web_origin.go` 以 `PUBLIC_WEB_ORIGIN` 組成絕對網址（完成與連結過期各一個），再交給 port 的 `SessionInput.ReturnURL`／`RefreshURL`；未指定的目的地回 `INVALID_ARGUMENT`。目的地的路徑只在那個檔案，`web_origin_test.go` 守門它們在 `website/app/[locale]` 都有 `page.tsx`，語系前綴與 website 的路由設定一致。
- 內嵌開通的 session 帶初始化元件用的公開金鑰（`publishable_key`，設定 `STRIPE_PUBLISHABLE_KEY`，不是 secret）與 client secret；金流商由回應 `embedded` 的 `oneof provider` 分支表示（目前只有 `stripe`），client 不認得的分支視為不能開通。啟動規則比照 `STRIPE_WEBHOOK_SECRET`：設了 `STRIPE_SECRET_KEY` 卻沒有 `STRIPE_PUBLISHABLE_KEY` 就啟動失敗，與收件方式無關：行程設定改成金流商收件後，既有的平台收件帳戶仍會開內嵌 session。守門：`TestStripePaymentConfig`。
- 關閉後刪除（D52、D55、D59、D60）：擁有者個資清理的 transaction 內 `ForgetOwners` 為每個擁有者排入 `payment.account_purge`（唯一鍵 `store_id`，只排 job、不碰列、不呼叫 provider）。job 第一步：每一列先在自己的 transaction 標 `purge_pending_at`（呼叫 provider 之前，意義是「擁有者要求清理、還沒完成」，之後任何錯誤、逾時或程序被殺都由週期掃描接手；ForgetOwners 的 transaction 不鎖也不改既有的列），標好後重讀列，再依 `planPurge` 分流：(1) 從沒呼叫過（沒有 `create_called_at`，必然沒有外部帳戶）：直接刪，**不需要 provider**；(2) 呼叫過但問不到 provider（沒有設定或列的 provider 不同）：列留著，記警示 log，超過期限進終局；(3) 有外部 ID 且 provider 相同：在 transaction 外經 `CloseAccount` 先讀帳戶、照它實際的設定關閉（冪等：已關閉視為成功；空帳戶 `applied_configurations` 是 `[]`，已完成設定的是 `["recipient"]`，關閉要求傳實際的全部設定，否則 400 `configs_must_match_to_close`，spike Q25），成功才在同一個 transaction 刪列並把該外部帳戶在 inbox 的未處理事件標為已處理（處理者 `payment.account_purge`）；(4) 呼叫過、沒有外部 ID、provider 相同：冪等鍵 30 天內以同一把鍵 `AcquireAccount` 取得 ID，超過 30 天列出 provider 的帳戶以 `metadata.store_id` 比對（`ResolveAccount`）——找到就先把 ID 寫回已標記的列（`SetPaymentAccountExternalForPurge`），再關閉並刪列；整份列完都沒有才刪列；列出失敗或翻頁超過上限是錯誤，不當成沒有。ID 一定在關閉之前存下：帳戶關閉之後同一把鍵的重放會被金流商拒絕（measured：409 `idempotency_error`，永久）。刪列前鎖住列再檢查：計畫是直接刪時，列上仍不得有外部 ID、「已呼叫」的時刻也不得變（並行的建立剛呼叫過），否則重試重新決定。**終局（D59、D60）**：provider 明確拒絕關閉（永久失敗），或標成等待清理已超過 7 天（`PurgeDeadline`）而仍然關不掉（暫時性失敗不斷）或問不到 provider，列標 `purge_blocked_at` 與 `purge_blocked_reason`（原因代碼 `provider_refused`、`provider_unconfigured`、`deadline_exceeded` 加冒號與細節）；週期掃描不再重排它、清理 job 對它是 no-op，出現在後台待辦 `PAYMENT_ACCOUNT_PURGE_STUCK`（§6），開始時間是進終局的時刻。管理員有兩個動作（§4）：「重試關閉」清除終局、等待清理的時刻重設成現在（期限重新計算）並重排清理；「已在金流商處理，刪除對應」在同一個 transaction 寫一筆 `payment.account_mapping_deletions`（只增不改：店家、provider、外部 ID（可為 NULL）、操作的管理員、時間）並刪列，不呼叫 provider。暫時性失敗由 River 退避重試（最多 8 次），最後一次嘗試仍失敗而還沒逾期時列留著（標記已在第一步）、警示 log 帶 `store_id` 與外部帳戶 ID，由週期掃描重排。等待清理的列（`purge_pending_at` 不是 NULL）不被建立、不進同步輪詢、不被賣家與管理員的重新整理、同步 job。守門：`TestPurgeDeletesNeverCalledRowsWithoutAProviderAndKeepsCalledRows`、`TestPurgeAfterTheIdempotencyKeyExpiredReconcilesByListingNotByReplay`、`TestAPermanentCloseRefusalPutsTheRowInTheTerminalStateAndTheSweepStops`、`TestAPurgeThatCannotReachTheProviderForSevenDaysEntersTheTerminalState`、`TestAdminRetryPurgeAndDeleteMappingActOnlyOnTheTerminalStateAndLeaveARecord`。

## 3. 收款事件與 inbox（D29）

- 入口驗簽（`Provider.ParseEvent`）後在一個 transaction 內以 `inbox.Record` 寫進 platform 的 `inbox.events`（`(provider, event_id)` 唯一；路由鍵是外部帳戶 ID；原始 payload 原樣保存，保存期 `EventRetention` 30 天）並排入派送 job，commit 之後才回 2xx。重送的事件不寫入、不派送；驗過簽章但不處理的事件回 2xx、不寫 inbox；簽章或格式不合回 400；沒有設定 provider 回 503。
- 派送（platform 的 `inbox.dispatch` job）呼叫收款的 handler：外部帳戶對得到本地帳戶時只排入同步 job，**不標記已處理**——事件只是「重讀帳戶」的訊號，由涵蓋它的同步標記；同步被執行中的 job 合併掉時，事件留在 inbox 讓那一輪回 `again`。對不到本地帳戶的事件只留紀錄、直接標記已處理（處理者 `payment.account_event`）。
- 補掃分工：platform 的補掃只重派派送 job 被丟棄或用完重試、仍未派送成功也未處理的列；payment 的 15 分鐘輪詢（`payment.account_sweep`）排 UNDER_REVIEW、ACTION_REQUIRED、原因碼不是 `rejected*`／`unsupported*` 的 DISABLED 帳戶的同步（Stripe 可以解除 restricted，掉了 webhook 時只有輪詢補得到）、inbox 有超過 1 分鐘未處理事件的帳戶的同步（`inbox.StaleRoutes`），以及閒置 10 分鐘的建立列（擁有者營運中才排）。
- payload 與 `PayoutAccountChanged` 的明文 fingerprint 不寫 log。

## 4. 後台

- `GetPaymentAccount` 讀擁有者的帳戶（沒有回 `NOT_FOUND`）；`RefreshPaymentAccount` 同步重讀並回最新帳戶，走賣家同一條路徑（沒有 provider、還沒完成建立或帳戶在等待關閉回 `FAILED_PRECONDITION`，窗內與失敗的結果同賣家：`RESOURCE_EXHAUSTED`、`UNAVAILABLE`）；`RetryPaymentAccountCreate` 只有建立失敗的列可以重試（其他狀態 `FAILED_PRECONDITION`）；`RetryPaymentAccountPurge` 只有清理進終局的列可以（其他狀態 `FAILED_PRECONDITION`）：清除終局、等待清理的時刻重設成現在並重排清理；`DeletePaymentAccountMapping` 只有清理進終局的列可以（其他狀態 `FAILED_PRECONDITION`，沒有列 `NOT_FOUND`）：在同一個 transaction 寫紀錄並刪列，操作的管理員取自呼叫者，不呼叫 provider，需要 `payment.accounts.delete_mapping`（與 `.retry_purge` 分開）。後台卡片 `PaymentAccountCard` 在終局時於「重試建立」的位置顯示被擋下的原因與時間（`purge_blocked_reason`、`purge_blocked_time`）與兩個按鈕「重試關閉」「已在金流商處理，刪除對應」（後者先確認，`PaymentMappingDeleteDialog`）；待辦 `PAYMENT_ACCOUNT_PURGE_STUCK` 的標題是「處理無法關閉的收款帳戶」，連到同一個卡片錨點。

## 5. 事件

- `PayoutAccountChanged{OccurredAt, StoreID, Provider, TransfersActive, BankFingerprints}`：同步 job 寫快照的 transaction 內每次都發布（fingerprint 可能在轉帳能力不變時改變）。seller 的同 transaction 訂閱者把 `TransfersActive` 複製到開通閘門的副本、把 fingerprint 寫成防詐 hash（D12），轉帳能力有變時重新公告。訂閱者失敗時整筆同步 rollback，River 重試。

## 6. 發布的讀取介面

- `payment.pub_review_items(at)`：後台待辦的 payment 部分（reviewqueue 讀，形狀在 `db/pub.sql`），兩種：`PAYMENT_ACCOUNT_CREATE_FAILED`（`create_failed_at` 有值的帳戶，開始是失敗的時刻）與 `PAYMENT_ACCOUNT_PURGE_STUCK`（`purge_blocked_at` 有值的帳戶，開始是進終局的時刻）。兩種的 item_id 都是店家 ID 的文字，期限 24 小時。只有店家 ID，店名由後台入口（`internal/httpapi/reviewqueue`）經 seller 的店家卡片補上。

## 7. 鎖順序

- 全域順序見單體規則 4 與 `platform/lockorder` 的 `Modules`（payment 在 seller 之前）。payment 自己的寫入只鎖帳戶列（`LockPaymentAccount`）；同步在帳戶列之後發事件，seller 的訂閱者再鎖 seller 的列。擁有者（seller）的 transaction 只對 payment 做 INSERT ON CONFLICT DO NOTHING 與排 job，不等 payment 的既有列；`inbox` schema 是 platform 的，不在模組順序內。

## 8. 已知限制

- `PAYMENT_ACCOUNT_CREATE_FAILED` 不再排除已關閉的店家（payment 不讀 seller 的店家狀態）：關閉店家的待辦由管理員「重試建立」清掉，建立 job 會因擁有者不在營運中而略過。觸發：上線前，或後台待辦出現已關閉店家時。
- 本機種子（`dev-seed`）以 fake provider 走正式的建立與同步；店家已有別的 provider 的帳戶時種子不改它，只印出提醒。
