## 0. 這個平台解決什麼問題

**一個欄位不能決定四件事。** 配送方式一決定，收款主體、發票開立人、出貨流程、退款責任如果全部跟著被推導，
任何一種新配送方式都會讓這條推導鏈在多個地方同時出錯，而且大多是靜默的。

本平台把它拆開：**配送方式、收款主體、發票開立人、履約模式是各自獨立的欄位**，
由後端在訂單成立當下記錄快照，付款後不再變更，之後修改賣家設定不回溯既有訂單。

## 1. 誰在用，跟誰互動

| 角色 | 在這裡做什麼 |
|---|---|
| **買家** | 選配送方式；看配送進度；確認收貨 |
| **賣家** | 備貨與交付；處理配送單 |
| **平台營運（ADM）** | 對配送失敗的訂單判定責任（提案與覆核由兩個人完成） |

## 2. 訂單政策快照

訂單記錄四個政策維度與一個版本，詳細設計書 65 §1。

| 維度 | 值域 | 目前的推導 |
|---|---|---|
| 商流（誰收錢、誰開票） | 賣家直營／平台受託代銷 | 一律賣家直營 |
| 收款模式（款項經過誰的手） | 賣家子商店／平台代理商戶／物流商代收／外部預付 | 一律賣家子商店 |
| 履約模式（誰負責把貨送到） | 賣家自行履約／平台物流履約 | 平台安排的配送方式為平台物流履約；商家自行配送為賣家自行履約 |
| 發票模式（買家發票由誰開） | 賣家開／平台開 | 一律賣家開 |

- **收款主體不能由呼叫端指定。** 付款用的 PayUni 商戶號由收款模式快照決定，買家 request 不帶任何相關布林。
- **看不懂就擋下。** 未知的配送方式或收款模式不會被當成預設值處理，結帳直接失敗。
- 平台受託代銷等值域內的其他值存在於資料模型，但沒有任何路徑會寫入；啟用的改動點是政策推導的單一決定點。
- 採購助理（RFQ）成交的訂單由站外業者自行出貨，履約模式固定為賣家自行履約。

## 3. 收貨確認是獨立的一條軸

收貨確認不是訂單狀態的一部分，而是平行的一條軸：訂單送達時進入「待確認收貨」，之後由買家手動確認或逾期自動確認。
「買家手動確認」與「逾期自動確認」是不同的狀態值，後續判斷可以分別對待（詳細設計書 65 §2）。

## 4. 配送方式的擴充邊界：adapter 與兩層動作模型

新增或調整配送方式時，業務流程不寫在共用層，而是掛在 provider adapter 上。

- **adapter 只翻譯，不判斷。** 它把 provider 的原生狀態與回調轉成平台的正規化值；認不得的值一律拒絕，不猜測。
- **查無 adapter 是漏接線，不是「沒有能力」。** 前者讓呼叫端看見錯誤，後者以「此能力不存在」表達。
- **按鈕能不能按分兩層。** 第一層看配送單當下的狀態；第二層只在這個動作必須呼叫 provider 時，才看 provider 有沒有這個能力。
  只寫我方狀態的動作（例如沒有 provider 取消 API 的取消）不受 provider 能力影響。
- **對外的 `allowedActions[]` 由後端算好**，前端不從狀態自行推導按鈕；每個動作標明誰可以執行，買家不會拿到賣家的動作。

詳細設計書 65 §3、§4。

## 5. 配送失敗的責任判定

配送失敗但成因證據不足時，平台開一張責任判定案件，由 ADM 兩人完成：

1. **提案人**主張成因（賣家、買家、物流商、平台四選一），系統依訂單實付金額算出影響預覽（退款金額）；
2. **覆核人**核可或駁回，覆核人不得是提案人，且覆核時影響預覽必須仍然成立。

核可後案件定案，並發出事件：

- 買家原因：訂單進入「配送失敗未退款」終態；
- 賣家、物流商、平台原因：走既有的全額退款流程；
- 同一事件另由物流財務決定該筆配送的賣家應收處置（見 [70](70-物流財務結算（Logistics%20Settlement%20%26%20Receivable）基本設計書.md)）。

責任判定案件不能被「忽略」：訂單停在物流異常狀態等這個判定，沒有人工改狀態的後門。詳細設計書 65 §5、§6。

## 6. 帳本與物流商帳單

平台以雙分錄帳本記錄物流相關的金額異動（只增不改，更正一律開反向分錄）；物流商月結帳單逐列匯入並與應收對帳。
帳務的業務面見 70，資料契約見詳細設計書 65 §7。

## 7. 這個設計刻意不做的事

- 不讓前端自行推導按鈕、也不讓前端持有 provider 的原生狀態表。
- 不在共用層寫任何特定配送方式的流程。
- 不允許用人工直接改訂單狀態來繞過責任判定。
