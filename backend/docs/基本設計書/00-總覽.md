# 基本設計書 · 總覽

## 這個資料夾裝什麼

**基本設計＝外部設計**：使用者看得到的部分。業務流程、畫面一覽、資料項目的業務語意、外部介面的用途。

**詳細設計＝內部設計**（`docs/詳細設計書/`）：程式怎麼寫。DDL、proto、端點簽章、狀態機轉移邊、實作陷阱。

| 問題 | 去哪找 |
|---|---|
| 這個服務在做什麼？誰會用到它？ | **基本設計書** |
| 有哪些畫面？各自解決什麼問題？ | **基本設計書** |
| 這個業務流程從哪開始、到哪結束？ | **基本設計書** |
| 這張表有哪些欄位、CHECK 是什麼？ | 詳細設計書 |
| 這支端點的 request／response 長什麼樣？ | 詳細設計書 |
| 這個狀態機有哪些轉移邊、誰觸發？ | 詳細設計書 |
| 照直覺做會踩到什麼？ | 詳細設計書的靜默陷阱表 |

## 硬規則：不重複，只指向

🔴 **同一件事只有一個權威版本。** 基本設計書**不摘要**詳細設計書 —— 摘要必然漂移，而漂移的摘要比沒有摘要更糟（讀的人以為自己查過了）。

- 基本設計書提到任何實作細節時，**寫「見詳細設計書 §X」而不是複製一份**
- 兩邊不一致時，**實作契約以詳細設計書為準，業務意圖以基本設計書為準**
- 詳細設計書的 §1.1a 一律只放一行指標指回這裡，不放總覽內容

## 公版章節（以 58 號為範本定版）

每一節都回答一個**外部設計的問題**。沒有內容的節就刪掉，不要留空殼；順序不要換（它是一條理解路徑：為什麼存在 → 誰在用 → 概念 → 流程 → 畫面 → 邊界）。

| # | 章節 | 回答什麼 | 沒有它會怎樣 |
|---|---|---|---|
| 0 | **這個服務解決什麼問題** | 為什麼需要它、**不做會怎樣** | 讀者知道它做什麼技術動作，但不知道為什麼要有 |
| 1 | **誰在用，跟誰互動** | 角色表 ＋ 系統情境圖（外部相依、上下游服務） | 不知道自己改的東西會影響誰 |
| 2 | **核心模型** | 這個領域最重要的那一個概念（58 是「四個開票方向」） | 後面每一節都失去座標 |
| 2b | **高階架構與系統級取捨** | 這個系統怎麼切、為什麼這樣切、接受了什麼代價 | 讀者看得到形狀，但不知道哪些形狀是**刻意**的，於是重構時把設計當成偶然 |
| 3–N | **主要業務流程**（一條一節） | 每條流程：誰觸發、經過哪幾個關卡、有哪幾種結果 | **最常漏的一節**——只寫主線，而支線通常佔畫面數的一半 |
| N+1 | **主要物件會經歷什麼** | 業務層級的階段（不是狀態值域） | 不知道一筆資料的一生 |
| N+2 | **畫面地圖** | 每一端：路由 ／ 畫面代號 ／ **這一頁解決什麼** | 找不到入口 |
| N+3 | **刻意不做的事** | 不做什麼 ＋ 為什麼 | 有人把已經否決過的東西再提一次 |
| N+4 | **已知的外部相依** | 等誰、卡什麼、不阻擋什麼 | 以為可以直接開工 |

## 🔴 分際：哪些**不准**寫進基本設計書

同一件事只有一個權威版本。以下全部屬於詳細設計書，**基本設計書只能指向、不能複製** —— 複製必然漂移，而漂移的版本比沒有更糟（讀的人以為自己查過了）。

| 不准寫 | 為什麼 | 基本設計書該寫的替代 |
|---|---|---|
| **完整狀態值域與轉移邊**（`DRAFT → SUBMITTED → …`） | 它要對 DB CHECK、對 CodeMeta、對狀態機測試，三處同步 | 「經過哪幾個關卡、有哪幾種結果」的流程圖 |
| DDL、欄位、索引、CHECK | 那是 migration 的輸入 | 「這個概念由哪張表承載」一句話 ＋ 節號 |
| 端點簽章、request／response 欄位 | 那是契約 | 「這一頁打哪一支」的用途描述 |
| proto message、gRPC 方法 | 同上 | — |
| capability token、停權裁決逐條 | 那是授權契約 | 「這一頁誰能看」一句話 |
| 實作陷阱、失敗形狀、`⚠️` 警語 | 那是給實作者的，讀基本設計書的人不寫那行 code | 只留**會影響業務理解**的那幾條（例：作廢與折讓的分水嶺是關帳日） |
| 消費檔案路徑、元件名稱 | 那是實作位置 | — |

**判準一句話**：**這段話刪掉，會不會讓人看不懂這個服務在做什麼？** 會 ⇒ 留；只是少知道一個實作細節 ⇒ 刪，改成指向詳細設計書的節號。

⚠️ **反向也要守**：詳細設計書的 §1.1a 只放**一行指標**指向基本設計書，不放總覽內容。兩邊互相摘要，就是兩份都會爛。

### WHY 的三段分工（與 ADR、詳細設計書的界線）

`WHY` 不是一整塊，它有三個不同的 owner —— 全部堆在同一份文件裡，就是三份都難讀：

| 問題 | owner | 寫多深 |
|---|---|---|
| 這個系統為什麼存在、為什麼這樣切 | **基本設計書**（§0、§2b） | 結論 ＋ 一句話理由 |
| 考慮過哪些方案、為什麼否決、代價是什麼 | **ADR**（`docs/adr/`） | 完整比較與取捨 |
| 現在要怎麼實作 | **詳細設計書** | 只有結果，**不含任何理由** |

⚠️ 基本設計書寫「我們用 transactional outbox，因為跨服務一致性只靠 MQ 保證不了」——
一句話收尾。**不要展開 alternatives 比較表**，那是 ADR 的正文。

⚠️ 詳細設計書**一句理由都不留**（治理規範 §3.4）。
判準：拿掉這句，實作者會不會做錯？會 ⇒ 它是規格（留）；不會 ⇒ 它是理由（搬走）。

完整 taxonomy 見 `docs/開發規範/設計文件治理規範.md`。

## 驗收：寫完必須實測，不能自評「應該夠了」

⚠️ **章節表是用來對照的，不是用來驗收的。** 最常見的兩種缺口——漏掉大半主要場景、以及越界把詳細設計書的完整狀態機搬進來——都**不可能**靠「再讀一次章節表」發現，只有**實際拿問題去翻**才會現形。所以這一節不是可選的收尾動作，是這份規範唯一有鑑別力的部分。

### 檢查一：主要流程覆蓋率（最容易漏，先驗這個）

**判準：把畫面地圖上的每一個畫面，逐一問「它屬於哪一條業務流程」。有畫面歸不到任何一節，就是漏了一條流程。**

典型形狀：畫面地圖上有 34 個畫面，而流程節只寫了「開票」一條 ⇒ 申訴（6 個）與稅籍審核（6 個）**歸不到任何一節**。漏掉的那兩條流程佔了三分之一的畫面，而章節表看起來是完整的。

⚠️ **不要用「詳細設計書列了幾個場景」當判準。** 那個數字取決於該本用了什麼結構，而**各本的結構並不統一**（實測：58 號 8 個 `S-N` 場景、56 號 10 個、**40 號 0 個** —— 40 用的是「§5 業務流程詳細設計 ＋ §7 時序圖總覽」，根本沒有場景清單）。拿 grep 數字當門檻，在 40 號上會得到「0 個場景 ⇒ 一節都不用寫」這種荒謬結論。

**畫面歸屬法對任何結構都成立**，因為畫面是外部設計的產物，本來就該全部被基本設計書涵蓋。

### 檢查二：分際自檢（機械，可直接跑）

```bash
F="docs/基本設計書/<這一本>.md"
echo "完整狀態值域: $(grep -c 'stateDiagram' "$F")"      # 必須 0
echo "DDL/CHECK   : $(grep -cE 'CREATE TABLE|CHECK \(|varchar\(' "$F")"  # 必須 0
echo "端點簽章    : $(grep -cE 'GET /|POST /|PUT /|DELETE /' "$F")"        # 必須 0
echo "capability  : $(grep -c 'Cap[A-Z]' "$F")"          # 必須 0
```

非 0 就是把詳細設計書的內容複製過來了。**唯一合法的例外是文件開頭那句分際聲明本身**（它提到這些詞是為了說「不寫這些」）。

### 檢查三：四個問題實測（人工，但只要 5 分鐘）

假裝自己第一次接觸這個服務，逐一到文件裡找答案。**答不出來就是缺一節，不是「讀者要自己想」**：

| # | 問題 | 對應章節 |
|---|---|---|
| 1 | 這個服務在做什麼？**不做會怎樣？** | §0 |
| 2 | 誰在用？它跟哪些系統互動？ | §1 |
| 3 | 主要的業務流程有哪幾條？每一條怎麼走？ | §3–N |
| 4 | 我要找某個功能，該去哪一頁？ | 畫面地圖 |

## 這份規範管得到什麼、管不到什麼

**管得到**：產出的格式、章節、分際、驗收方法。照著做，產出會是一份合格的基本設計書。

**管不到**（這幾件事只能靠判斷，寫再多章節說明也補不了）：

| 判斷 | 為什麼規範不了 |
|---|---|
| 哪些場景算「主要業務流程」 | 詳細設計書的場景清單有主有次，取捨要看該領域 |
| 哪個概念是「核心模型」 | 58 剛好是一張四方向矩陣，別的服務可能是一條時間軸、一組角色關係，形狀不同 |
| 哪些警語會影響業務理解 | 「作廢與折讓的分水嶺是關帳日」要留，「`VOIDING` 中間態承載時間差」要刪——兩者長得很像 |

⇒ **這份規範降低下限，不保證上限。** 產出後仍要跑上面三個檢查，不能因為「照章節填完了」就當成完成。

### 🔴 物流領域：編號一一對應

物流有**七本**詳細設計書，**每一本都有自己的基本設計書，編號一一對應**：
06 對 06、65 對 65、66 對 66、67 對 67、68 對 68、69 對 69、**70 對 70**。

⚠️ **70 裝的是物流的錢**（平台向賣家收物流成本、平台與物流商月結），不是配送方式。
它獨立成書而不併進 65 或 66 的理由：① **provider 中立**（66／68／69 共用）
② 擁有者是**結算**而非物流履約 ③ 65 已逾萬行。

**為什麼要這樣切**：一本同時裝三種配送方式的完整流程，會讓想知道「Uber 的錢怎麼走」的人
得先讀完整個平台骨架，而想知道「商家自送的收貨規則」的人**在任何一本裡都找不到自己的位置**。
所以 65 只裝**共用骨架**（正交維度、三條資金線的總則、跨方式共通規則、營運工作台、憑證保存），
各配送方式的業務流程、金流圖、發票圖、失敗處置在各自那一本。

⚠️ **65A 是前端實作規格，不建立 65A 基本設計書**——它本身就是實作層文件。

⚠️ **68 的「B2C」是 7-11 超商物流的產品分類，不是筆誤**：
超商物流三種——**店到店 `C2C`**（我方 `3002`，已實作）、**大宗寄倉 `B2C`**（我方 `3004`，68 號的對象）、
**退貨便 `C2B`**（逆向）。`B2C` 講的是最後一哩（物流中心 → 門市 → **消費者**取貨）。
🔴 **PayUni 的 `LgsType` 值域只有 `B2C`／`C2C`／`HOME`／`C2B`，沒有 `B2B`** ⇒ 不要把 68 改名成 B2B。

## 新增一份基本設計書時

1. 確認它裝的是**外部設計**（上面那張表的前三列），不是詳細設計的摘要
2. **編號與檔名**都比照對應的詳細設計書，結尾換成「基本設計書」；沒有對應者用 `A` 系列
3. 更新本檔的表格與 `docs/_sidebar.md`
4. 在對應的詳細設計書加一行指標（不要加總覽內容）
